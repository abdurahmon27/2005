**Depth: daily, and it changed how I work more than any framework has.**

This note exists because the useful part is not "I use AI". Everyone says that.
The useful part is the setup around it — what the agent is allowed to touch,
what it is told, and what remains mine.

## The setup

I work through [t3-code](https://t3.chat), which runs Claude Code as the engine.
On top of that, three things do the actual work:

**Repo-local skills.** Each project carries its own, checked into the repo. On
[shoshshi](/lab/ideas/shoshshi): `deploy`, `backup`, `db-migrate`, `analytics`,
`moderate`. On [oris](/lab/ideas/oris) there are ten, one per area of the
codebase. A skill is a written procedure — the same thing I'd hand a new
teammate — and it turns "explain the deploy again" into a word.

**State files instead of memory.** `PLAN.md`, `PROGRESS.md`, `TODO.md` and a
small `state.json`. A session ends; the next one starts with *continue oris*,
reads the state, verifies a green build, and picks up the next task. Nothing
important lives in a chat scrollback, because chat scrollback is not a place
you can diff.

**A spec before the code**, which is the same rule I'd want on any team —
[spec-first delivery](/lab/spec-first). It matters more with an agent, not
less: an agent implements what the spec says, quickly, including the parts that
were vague. Ambiguity stops being a question someone asks on Tuesday and becomes
a working implementation of the wrong thing.

## The server has its own user for it

Nothing automated logs in as root. The box is provisioned by a script that
creates a **non-root, key-only user** in the `docker` group, with its own SSH
key and its own home, and hardens sshd behind it: `PermitRootLogin no`,
`PasswordAuthentication no`, ufw down to 22/80/443. Deploys and agent-driven
operations run as that user, and everything they can do is what that user can
do.

The reasoning is not that I expect an agent to go rogue. It is the same reason
services don't run as root: **the blast radius should be an argument about a
single account, not about the machine.** It also makes the question answerable
— "what can this thing actually reach?" has a concrete answer I can read off
`id`, the docker group and the firewall rules.

## What I hand over, and what I don't

**Delegated, happily:** scaffolding, mechanical refactors, test fixtures, the
tenth variation of a component, migrations from a written schema, reading a
codebase I've just cloned, and every single shell incantation I would otherwise
look up again.

**Not delegated:**

- **The decision.** What we're building and why is mine; an agent has no stake
  in the trade-off and will happily implement either branch.
- **The schema and the data model.** Everything downstream inherits its mistakes.
- **Security-shaped code** — auth, tokens, anything touching money. Reviewed
  line by line, always.
- **The final read.** If I can't explain a diff, it doesn't ship. That rule has
  caught more problems than any test suite I've written.

## The honest part

There's a tension I haven't resolved: I want to be a strong engineer *and* I
increasingly operate as the person directing agents. [The roast](/lab/me/roast)
put it sharply, and it isn't wrong.

Where I've landed for now: the leverage is real and pretending otherwise is
theatre — but it only compounds if the thinking stays mine. Writing specs,
naming the edge cases, reading the diff, keeping the blast radius small. The
typing was never the valuable part; if I let the deciding go too, there's
nothing left to be good at.
