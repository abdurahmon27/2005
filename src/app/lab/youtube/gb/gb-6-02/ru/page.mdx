## Что вы узнаете

Клиент передал цену товара строкой. Почему ответ раскрывает `productInput.price of type int64` — внутренний тип Go?

**Главная идея:** у одной ошибки два получателя. Сервер пишет полный текст в лог; `problemFor` выбирает статус и публичное сообщение. ID запроса связывает их.

После урока вы сможете:

- заменить старый формат ошибки на problem details из RFC 9457;
- распознавать обёрнутые ошибки через `errors.Is` и `errors.As`, не раскрывая внутренний текст в ответе;
- связать ответ с записями в логе и найти пропущенный `return`;
- добавить недостающие случаи 422 и 413 и пройти тесты задания.

| Термин | Простое объяснение | Английский термин |
|---|---|---|
| публичная ошибка | специально выбранное сообщение, которое разрешено читать клиенту | public error |
| problem details | стандартный JSON-формат описания ошибки HTTP API | problem details |
| преобразование ошибки в ответ | одна функция выбирает публичный ответ по значению ошибки | error mapping |

Два вспомогательных понятия: несколько `%w` сохраняют несколько обёрнутых ошибок; `fieldErrors` — тип map с методом `Error() string`.

## Внутренний текст попадает в ответ при записи

Раньше `writeDecodeError` копировал `err.Error()` в `message` этим вызовом:

```go
writeError(w, http.StatusBadRequest, apiError{Code: "bad_json", Message: err.Error()})
```

Это прежняя сигнатура помощника из GB-4.06. Предскажите: что раскроет строковая цена?

**A)** только публичное поле · **B)** информацию о внутреннем типе Go · **C)** ответ не придёт

<details>
<summary>Ответ</summary>

**B.** Старый код сериализует внутреннее сообщение декодера. Для A нужен специально выбранный публичный текст; C потребовал бы прервать ответ.

</details>

Команда повторно выполнена в копии `oldin`:

```console
$ curl -s localhost:8765/products -H "Content-Type: application/json" -d '{"name":"choy","price":"25000"}'
{"error":{"code":"bad_json","message":"json: cannot unmarshal string into Go struct field productInput.price of type int64"}}
```

`choy` — «чай». `cannot unmarshal string` означает, что JSON-строку нельзя поместить в это числовое поле. Остальная часть раскрывает внутреннюю структуру и тип. CWE-209 описывает раскрытие чувствительной информации в сообщениях об ошибках.

При `fmt.Errorf("context: %w", err)` добавленный контекст остаётся в тексте `Error()`. Следующие слои могут добавить пути к файлам или имена ограничений базы. Даже узбекское сообщение хранилища — внутренний текст, который может измениться. Это ужесточает прежнее правило GB-4.08.

| Этап | Лог сервера | Ответ клиенту |
|---|---|---|
| до изменения | запись о запросе | текст декодера, включая типы Go |
| после изменения | полный текст ошибки и ID запроса | выбранное сообщение, статус и тот же ID |

## Стандартный ответ: problem details

**Problem details** — JSON-формат ошибок из RFC 9457, опубликованного организацией интернет-стандартов IETF. `application/problem+json` обозначает именно этот формат ошибки, сохраняя синтаксис JSON.

| Поле | Значение в этом API |
|---|---|
| `type` | URI — идентификатор типа проблемы; `about:blank` не добавляет смысла сверх статуса |
| `title` | краткое описание типа; для `about:blank` используйте название статуса |
| `status` | копия фактического статуса HTTP |
| `detail` | публичное объяснение этого случая, помогающее клиенту исправить проблему |
| `errors` | наше расширение: имя поля → сообщение валидации |
| `request_id` | наше расширение: значение из `X-Request-Id` |

URI идентифицирует тип. Он не обязан открывать страницу, хотя документация рекомендуется. Предпочтительны абсолютные URI; относительным стоит включать полный путь, как `/problems/insufficient-stock`. Клиенту следует получать структурированные данные из расширений, а не разбирать `detail`. Если нужны числовые остатки, API может определить расширения `available` и `requested`.

Ниже фрагменты `cmd/api/problem.go`; полный файл приведён дальше:

```go
type problem struct {
	Type      string            `json:"type"`
	Title     string            `json:"title"`
	Status    int               `json:"status"`
	Detail    string            `json:"detail,omitempty"`
	Errors    map[string]string `json:"errors,omitempty"`
	RequestID string            `json:"request_id,omitempty"`
}

// newProblem — maxsus turi yoʻq xato: type "about:blank", title esa statusning standart nomi
// (RFC 9457 §4.2.1: about:blank boʻlsa title — HTTP status nomi).
func newProblem(status int, detail string) problem {
	return problem{
		Type:   "about:blank",
		Title:  http.StatusText(status),
		Status: status,
		Detail: detail,
	}
}

// writeProblem — har xato javobi shu funksiyadan chiqadi: sarlavha → status → body (GB-4.03 tartibi),
// media turi application/problem+json. request_id — GB-6.01'dagi requestID qoʻygan X-Request-Id: mijoz uni
// aytsa, log'dagi qatorni topamiz. (Middleware'siz, testda, sarlavha boʻsh: omitempty uni tashlaydi.)
func writeProblem(w http.ResponseWriter, p problem) {
	p.RequestID = w.Header().Get("X-Request-Id")
	w.Header().Set("Content-Type", "application/problem+json")
	w.WriteHeader(p.Status)
	json.NewEncoder(w).Encode(p) // Encode xatosi: log'ga yozish GB-8.02'da (writeJSON kabi)
}
```

| Строки фрагмента | Код | Что делает |
|---|---|---|
| 1–8 | `type problem struct` | экспортирует поля для JSON; теги задают публичные имена; `Status` имеет тип `int`, остальные скалярные поля — строки |
| 5–7 | `omitempty` | пропускает пустые `Detail`, `Errors`, `RequestID`; `Errors` сопоставляет строки строкам |
| 12–19 | `newProblem` | возвращает значение структуры; `http.StatusText(status)` задаёт заголовок, например `Not Found` для 404 |
| 24 | `writeProblem(w, p)` | получает writer и копию problem |
| 25 | `p.RequestID = …` | читает заголовок ответа, установленный `requestID` |
| 26–28 | заголовок → статус → кодирование | задаёт тип содержимого, записывает статус, затем сериализует `p` в writer |

Комментарии описывают функции; скобки закрывают литералы и тела функций. Игнорируемая ошибка `Encode` отложена до [GB-8.02 · Логирование](/lab/youtube/gb#gb-8-02), как и в `writeJSON`.

Замена `{"error":{"code":…}}` этим объектом ломает клиентов, ожидающих прежний контракт. Объявите об изменении или выпустите новую версию.

## Одна функция преобразует ошибки в ответы

```go
func problemFor(err error) problem {
	var se *store.StockError
	var te *json.UnmarshalTypeError
	switch {
	case errors.Is(err, store.ErrNotFound):
		return newProblem(http.StatusNotFound, "bunday ID'li mahsulot yoʻq")
	case errors.As(err, &se):
		return problem{
			Type:   "/problems/insufficient-stock",
			Title:  "Omborda yetarli emas",
			Status: http.StatusConflict,
			Detail: fmt.Sprintf("%s: omborda %d dona, soʻralgan %d", se.Name, se.Stock, se.Want),
		}
	// VAZIFA (TASK.md): 1) fieldErrors → 422 + errors; 2) store.ErrBadProduct, store.ErrBadQuantity → 422 + productRules;
	// 3) *http.MaxBytesError → 413 — errBadJSON case'idan OLDIN.
	case errors.Is(err, errBadID):
		return newProblem(http.StatusBadRequest, "id butun son boʻlishi kerak")
	case errors.As(err, &te) && te.Field != "":
		return newProblem(http.StatusBadRequest, te.Field+": qiymat turi notoʻgʻri")
	case errors.Is(err, errBadJSON):
		return newProblem(http.StatusBadRequest, "body bitta JSON obyekt boʻlsin, faqat maʼlum kalitlar bilan")
	default:
		return newProblem(http.StatusInternalServerError, "")
	}
}
```

`var se *store.StockError` и `var te *json.UnmarshalTypeError` объявляют целевые переменные. `errors.As(err, &se)` записывает найденный указатель в `se`; `&` передаёт её адрес. `errors.Is` узнаёт sentinel-ошибку через обёртки. `switch` без выражения проверяет случаи по порядку и выбирает первый истинный. Здесь используется `As`: его логический результат подходит для case, а найденное значение записывается в заранее объявленную переменную. `AsType` возвращает два значения.

| Случай | Результат | Причина |
|---|---|---|
| `ErrNotFound` | 404, наш текст | товара нет |
| `*StockError` | 409, наш тип и заголовок | собирает `detail` из разрешённых полей `Name`, `Stock`, `Want` |
| `errBadID` | 400 | ID в пути не является целым числом |
| ошибка типа с непустым `Field` | 400, текст для поля | `&&` требует оба условия; `+` соединяет путь поля с нашим сообщением |
| `errBadJSON` | 400, общие требования к телу | обрабатывает остальные ошибки декодирования |
| `default` | 500, пустой detail | неизвестные ошибки не раскрывают внутренний текст |

`fmt.Sprintf` создаёт строку: `%s` вставляет имя, `%d` — целые количества. Комментарии `VAZIFA` отмечают недостающие случаи задания; они их не реализуют.

Здесь `Field` равен `price`. В общем случае это путь к ошибочному значению, а не обязательно один буквальный ключ JSON. Для массива на верхнем уровне он пуст, поэтому запрос обрабатывает общий случай тела. Не раскрывайте `Struct`, `Type` или полный текст ошибки декодера.

## Сохраните обе ошибки при декодировании

`errBadJSON` — sentinel-ошибка API. Сохраниться должны и она, и исходная ошибка декодера:

```go filename="cmd/api/json.go" showLineNumbers
package main

// JSON kirish va chiqish (GB-4.06): qat'iy oʻqish va limit. GB-6.02: xato javobi endi problem.go'da.

import (
	"encoding/json"
	"errors"
	"fmt"
	"io"
	"net/http"
)

// writeJSON: sarlavha → status → body (GB-4.03 tartibi).
func writeJSON(w http.ResponseWriter, status int, v any) {
	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(status)
	json.NewEncoder(w).Encode(v) // Encode xatosi: log'ga yozish GB-8.02'da
}

// maxBody — body'ning eng katta hajmi, baytda (GB-4.06).
const maxBody = 1024

// decodeJSON body'ni dst'ga oʻqiydi: eng koʻpi maxBody bayt, nomaʼlum kalit yoʻq, bitta JSON qiymat.
// Xato boʻlsa javobni oʻzi yozadi va false qaytaradi: chaqiruvchi darhol return qiladi.
// GB-6.02: Decode xatosi errBadJSON bilan birga oʻraladi (ikkita %w): problemFor ikkalasini ham koʻradi,
// asl matn esa faqat log'ga boradi.
func decodeJSON(w http.ResponseWriter, r *http.Request, dst any) bool {
	r.Body = http.MaxBytesReader(w, r.Body, maxBody)
	dec := json.NewDecoder(r.Body)
	dec.DisallowUnknownFields()
	if err := dec.Decode(dst); err != nil {
		writeError(w, fmt.Errorf("%w: %w", errBadJSON, err))
		return false
	}
	// Decode faqat birinchi JSON qiymatni oʻqiydi: undan keyin hech narsa boʻlmasligi kerak.
	if err := dec.Decode(&struct{}{}); err != io.EOF {
		if err == nil {
			err = errors.New("body'da bitta JSON boʻlishi kerak")
		}
		writeError(w, fmt.Errorf("%w: %w", errBadJSON, err))
		return false
	}
	return true
}
```

| Строки файла | Код | Что делает |
|---|---|---|
| 1–11 | пакет, комментарий, импорты | `encoding/json` работает с JSON; `errors` создаёт ошибку, `fmt` оборачивает её, `io` предоставляет EOF, `net/http` ограничивает ввод |
| 14–18 | `writeJSON` | прежний успешный ответ: заголовок, статус, тело |
| 21 | `maxBody = 1024` | лимит в байтах |
| 27–30 | `decodeJSON`, reader, decoder | `dst any` — получатель результата; ограничивает ввод и запрещает неизвестные поля |
| 31–34 | первый `Decode` | при ошибке оборачивает две ошибки, записывает ответ и возвращает `false` |
| 36 | `dec.Decode(&struct{}{})` | второе чтение проверяет EOF; `&struct{}{}` — указатель на значение пустой структуры |
| 37–41 | ошибка второго чтения | ещё одно значение JSON или некорректное продолжение идёт тем же путём; при успешном чтении создаёт ошибку |
| 43–44 | `return true` | сюда доходит только полностью прочитанный корректный ввод; скобка закрывает функцию |

Несколько `%w` поддерживаются с Go 1.20. Для этой обёртки могут одновременно сработать `errors.Is(err, errBadJSON)` и `errors.As(err, &te)`:

```text
fmt.Errorf("%w: %w", errBadJSON, decoderError)
  ├─ errBadJSON
  └─ *json.UnmarshalTypeError
```

Конкретная ошибка типа должна предшествовать общему sentinel-случаю. Прежнее преобразование в 413 намеренно отсутствует в стартовом коде; ограничение размера продолжает работать. В задании вы восстановите его статус. Ошибки неизвестных полей получают общие инструкции; этот код не извлекает имя поля из их текста.

## Полную ошибку — в лог, публичный ответ — клиенту

```go
func writeError(w http.ResponseWriter, err error) {
	p := problemFor(err)
	log.Printf("%s xato %d: %q", w.Header().Get("X-Request-Id"), p.Status, err.Error())
	writeProblem(w, p)
}
```

Строка 1 принимает `err error`; строка 2 получает публичный problem. Строка 3 пишет ID, статус и полный текст в лог. `%q` заключает строку в кавычки и экранирует переводы строк как `\n`. Строка 4 записывает problem; строка 5 закрывает функцию. `err.Error()` должен быть только в вызове логирования.

Обработчики заменяют `writeStoreError` этим вызовом и сразу возвращаются:

```go
	p, err := a.st.Get(id)
	if err != nil {
		writeError(w, err)
		return
	}
```

`p, err :=` получает товар и ошибку; ветка `if` записывает ошибку и завершает функцию. Middleware с уже выбранным статусом вызывает `writeProblem` напрямую. Например, recovery до начала ответа:

```go
writeProblem(w, newProblem(http.StatusInternalServerError, ""))
```

`requireJSON` использует 415; `muxErrors` преобразует 404 и 405 от mux, сохраняя `Allow`. Panic после начала записи ответа нельзя заменить новым 500: унаследованный recovery прерывает такой ответ.

## Для валидации ещё нужен отдельный случай

Теперь `validate` возвращает этот именованный тип map:

```go
type fieldErrors map[string]string

func (f fieldErrors) Error() string {
	return fmt.Sprintf("validatsiya: %d ta maydon notoʻgʻri", len(f))
}
```

Строка 1 определяет map «имя поля → сообщение». Строки 3–5 добавляют метод `Error() string` получателю-значению `f`, удовлетворяя `error`. `len(f)` считает ошибочные поля; `%d` форматирует это число. Обработчик по-прежнему проверяет длину конкретного map:

```go
	if f := validate(in); len(f) > 0 {
		writeError(w, f)
		return
	}
```

Краткое объявление в `if` связывает `f`; `len(f) > 0` означает наличие ошибок. `writeError` принимает map как `error`, а `return` завершает обработчик. Не сравнивайте с nil интерфейс `error`, содержащий этот map: даже nil map внутри интерфейса даёт ненулевой интерфейс.

До добавления нового случая предскажите результат пустого имени и нулевой цены.

**A)** 400 · **B)** 422 · **C)** 500

<details>

**C.** Для `fieldErrors` ещё нет случая, поэтому срабатывает `default`. B — нужный результат после задания; A смешивает корректный JSON с неверными значениями.

</details>

```go filename="cmd/api/problem.go" showLineNumbers
package main

// Bir xil API xatolari (GB-6.02): har xato javobi RFC 9457 "problem details" shaklida.
// Qoida: err.Error() — dasturchi uchun matn, u faqat log'ga boradi. Mijoz faqat biz tanlab
// yozgan matnni oladi (detail, errors) va log'dagi qatorni topish uchun request_id'ni.

import (
	"encoding/json"
	"errors"
	"fmt"
	"log"
	"net/http"

	"github.com/abdurahmon27/bozor/internal/store"
)

// problem — RFC 9457 obyekti. type, title, status, detail — standart aʼzolar;
// errors va request_id — bozor'ning kengaytmalari (RFC 9457 §3.2).
type problem struct {
	Type      string            `json:"type"`
	Title     string            `json:"title"`
	Status    int               `json:"status"`
	Detail    string            `json:"detail,omitempty"`
	Errors    map[string]string `json:"errors,omitempty"`
	RequestID string            `json:"request_id,omitempty"`
}

// newProblem — maxsus turi yoʻq xato: type "about:blank", title esa statusning standart nomi
// (RFC 9457 §4.2.1: about:blank boʻlsa title — HTTP status nomi).
func newProblem(status int, detail string) problem {
	return problem{
		Type:   "about:blank",
		Title:  http.StatusText(status),
		Status: status,
		Detail: detail,
	}
}

// writeProblem — har xato javobi shu funksiyadan chiqadi: sarlavha → status → body (GB-4.03 tartibi),
// media turi application/problem+json. request_id — GB-6.01'dagi requestID qoʻygan X-Request-Id: mijoz uni
// aytsa, log'dagi qatorni topamiz. (Middleware'siz, testda, sarlavha boʻsh: omitempty uni tashlaydi.)
func writeProblem(w http.ResponseWriter, p problem) {
	p.RequestID = w.Header().Get("X-Request-Id")
	w.Header().Set("Content-Type", "application/problem+json")
	w.WriteHeader(p.Status)
	json.NewEncoder(w).Encode(p) // Encode xatosi: log'ga yozish GB-8.02'da (writeJSON kabi)
}

// API qatlamining oʻz sentinel xatolari (GB-2.08): decodeJSON va pathID asl xatoni shular bilan oʻraydi.
var errBadJSON = errors.New("body JSON sifatida oʻqilmadi")

var errBadID = errors.New("id butun son emas")

// fieldErrors — validate natijasi: maydon nomi → nima notoʻgʻri. Error() metodi bor, demak u error:
// handler uni boshqa xatolar kabi writeError'ga beradi, problemFor esa 422 qiladi.
type fieldErrors map[string]string

func (f fieldErrors) Error() string {
	return fmt.Sprintf("validatsiya: %d ta maydon notoʻgʻri", len(f))
}

// productRules — 422'da mijozga koʻrsatiladigan katalog qoidalari. Store xatosining matni emas:
// u ichki qatlam matni, ertaga unga boshqa tafsilot qoʻshilishi mumkin.
const productRules = "nom 1–20 belgi, narx 1 tiyindan 10 mln soʻmgacha, qoldiq 0–1 000 000"

// problemFor xatoni mijozga ketadigan problem'ga aylantiradi: status errors.Is/As bilan tanlanadi.
// Hech bir case err.Error()ni ishlatmaydi: detail faqat biz tanlagan maydonlardan yigʻiladi.
// switch birinchi mos case'ni oladi: aniqroq case (413) umumiyroq case'dan (errBadJSON) oldin turadi.
func problemFor(err error) problem {
	var se *store.StockError
	var te *json.UnmarshalTypeError
	switch {
	case errors.Is(err, store.ErrNotFound):
		return newProblem(http.StatusNotFound, "bunday ID'li mahsulot yoʻq")
	case errors.As(err, &se):
		return problem{
			Type:   "/problems/insufficient-stock",
			Title:  "Omborda yetarli emas",
			Status: http.StatusConflict,
			Detail: fmt.Sprintf("%s: omborda %d dona, soʻralgan %d", se.Name, se.Stock, se.Want),
		}
	// VAZIFA (TASK.md): 1) fieldErrors → 422 + errors; 2) store.ErrBadProduct, store.ErrBadQuantity → 422 + productRules;
	// 3) *http.MaxBytesError → 413 — errBadJSON case'idan OLDIN.
	case errors.Is(err, errBadID):
		return newProblem(http.StatusBadRequest, "id butun son boʻlishi kerak")
	case errors.As(err, &te) && te.Field != "":
		return newProblem(http.StatusBadRequest, te.Field+": qiymat turi notoʻgʻri")
	case errors.Is(err, errBadJSON):
		return newProblem(http.StatusBadRequest, "body bitta JSON obyekt boʻlsin, faqat maʼlum kalitlar bilan")
	default:
		return newProblem(http.StatusInternalServerError, "")
	}
}

// writeError — handler'dagi har Go xatosi shu yerdan chiqadi: log'ga toʻliq xato (err.Error()),
// mijozga problemFor tanlagan xavfsiz problem. Ikkalasida bir xil request ID.
// Metod, yoʻl va status logRequests qatorida (GB-6.01); bu qator — xatoning oʻzi. %q: xato matnida
// mijoz yuborgan narsa (yoʻl, kalit) boʻlishi mumkin, yangi qator log'da \n boʻlib qoladi (GB-6.01).
func writeError(w http.ResponseWriter, err error) {
	p := problemFor(err)
	log.Printf("%s xato %d: %q", w.Header().Get("X-Request-Id"), p.Status, err.Error())
	writeProblem(w, p)
}
```

Строки 50 и 52 создают sentinel-ошибки JSON и ID. Строки 56–60 реализуют `fieldErrors`; строка 64 задаёт `productRules`, публичное описание правил каталога для задания. Строки 69–93 преобразуют ошибки; строки 99–103 логируют и записывают ответ. Остальные строки — комментарии, пустые разделители и закрывающие скобки.

</details>

## Частые ошибки

Классическая ошибка — возвращать `err.Error()` в `detail`, даже для 4xx или узбекского сообщения хранилища. Показанная выше утечка объясняет причину. Исправление: выбирайте публичный текст в `problemFor`; внутренний оставляйте только в логах.

Вторая ошибка: пропустить `return` после `writeError`. Полный метод сломанной версии:

```go
func (a *api) getProduct(w http.ResponseWriter, r *http.Request) {
	id, ok := pathID(w, r)
	if !ok {
		return
	}
	p, err := a.st.Get(id)
	if err != nil {
		writeError(w, err)
	}
	writeJSON(w, http.StatusOK, p)
}
```

Сначала `pathID` обрабатывает некорректные ID. Затем `Get(99)` возвращает ошибку и товар с нулевыми значениями. После записи ошибки выполнение достигает `writeJSON`.

Предскажите: **A)** только один problem с 404 · **B)** problem с 404, затем нулевой товар · **C)** 500.

<details>
<summary>Ответ</summary>

**B.** Запись ошибки не завершает обработчик. Первый окончательный статус остаётся 404, но обе операции кодирования дописывают тело. Для A нужен `return`; C предполагает автоматический panic.

</details>

2026/11/27 22:10:12 http: superfluous response.WriteHeader call from main.(*statusRecorder).WriteHeader (middleware.go:48)
2026/11/27 22:10:12 LGTP4BKJBTUYLF3AO4XNVOT6QK GET "/products/99" 200 420.311µs

`superfluous response.WriteHeader call` означает лишний вызов записи статуса. `middleware.go:48` указывает строку вызова в обёртке. Настоящий HTTP-ответ сохраняет 404. Для окончательных статусов net/http допускает не более одного заголовка 2xx–5xx; у информационных ответов 1xx другие правила.

Исправьте обработчик:

```go
	p, err := a.st.Get(id)

		writeError(w, err)
		return
	}
	writeJSON(w, http.StatusOK, p)
```

Сохранение только первого окончательного статуса сделало бы обёртку надёжнее. Этого отдельного улучшения в данном снимке нет. Перед продолжением остановите сервер.

[Эталонное решение](https://github.com/abdurahmon27/go-backend-uz/tree/main/lessons/gb-6-02-api-xatolar/solution) добавляет два объявления целевых переменных выше и эти случаи:

```go
	case errors.As(err, &fe): // vazifa, 1-qadam
		return problem{
			Type:   "/problems/validation",
			Title:  "Qiymatlar notoʻgʻri",
			Status: http.StatusUnprocessableEntity,
			Errors: fe,
		}
	case errors.Is(err, store.ErrBadProduct), errors.Is(err, store.ErrBadQuantity): // vazifa, 2-qadam
		return problem{
			Type:   "/problems/validation",
			Title:  "Qiymatlar notoʻgʻri",
			Status: http.StatusUnprocessableEntity,
			Detail: productRules,
		}
	case errors.As(err, &tooBig): // vazifa, 3-qadam: errBadJSON'dan oldin
		return newProblem(http.StatusRequestEntityTooLarge, fmt.Sprintf("body %d baytdan oshmasin", tooBig.Limit))
```

`fieldErrors` реализует `error` как значение, поэтому цель `*fieldErrors` не совпадёт со значениями, создаваемыми здесь. Запятая во втором `case` допускает любой из двух sentinel. Последний случай читает известный лимит, не раскрывая текст ошибки.

`errors` — map-расширение этого API, а не обязательная структура RFC. Оба случая 422 используют один тип проблемы; один содержит ошибки полей, другой — публичное описание правил.

Выполните из корня урока (`cd solution` переходит в папку ответа):

```console
$ cd solution && go test ./...
ok  	github.com/abdurahmon27/bozor/cmd/api	(cached)
ok  	github.com/abdurahmon27/bozor/cmd/bozor	(cached)
ok  	github.com/abdurahmon27/bozor/internal/store	(cached)
```

Все пакеты проходят. `http.StatusText(413)` в Go даёт `Request Entity Too Large`; RFC 9110 называет статус `Content Too Large`. Go также сохраняет `Unprocessable Entity` для 422, тогда как RFC 9110 использует `Unprocessable Content`. Тесты намеренно ожидают формулировки Go.

</details>

После изменения запускайте `go test ./...` из корня своей папки урока, пока все пакеты не пройдут. Стартовый код также проходит vet:

```console
$ go vet ./...
```

Команда ничего не выводит. Успех vet не означает, что недостающие преобразования работают.

Для Postgres-хранилища GB-5.10 добавьте также `ErrOrderNotFound` → 404 и `ErrDuplicate`/`ErrInUse` → 409. В этом снимке хранилище находится в памяти.
