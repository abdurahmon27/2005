## What you will learn

In bozor, apples (`olma`) cost 12,000 soʻm, and 12 % VAT (Uzbek: QQS) is added on top. The answer should be
13,440 soʻm. If we compute the price with `float64`, Go prints `13440.000000000002`. Where does the extra `2` at the
end come from, and how should money be stored?

**One idea:** in Go, every number type is a place in memory with a fixed size. `int64` stores a whole number
exactly in 8 bytes, and when it goes past its limit it silently wraps around. `float64` is also 8 bytes, but it is a
binary fraction, and it cannot store 1.12 exactly. That is why money is stored in the smallest unit (tiyin) as an
`int64`.

By the end of this lesson you will:

- say how many bytes `int32`, `int64` and `int` take and how far they count;
- recognise silent overflow (a wrong result with no error) and avoid it;
- store a price in tiyin as an `int64`, compute a sale total with VAT, and print it in soʻm and tiyin;
- read the `mismatched types` error and fix it with the conversion `int64(sold)`.

The three core new words of this lesson:

| Word | Plain meaning | Term |
|---|---|---|
| overflow | the result goes past the type's limit, and Go silently writes a different number, with no error | overflow |
| smallest unit | keep money in tiyin, as a whole number: 1 soʻm = 100 tiyin | smallest currency unit |
| conversion | an explicitly written change of a value to another type: `int64(sold)` | conversion |

Two helper words: **`const`** (a named value that does not change) and the untyped constant (a constant with no
written type); and, for whole numbers, **integer division** `/` and the **remainder** `%`. Each gets its own section
below.

## Integer types: `int32`, `int64` and `int`

In Go, a whole number is not one type. The number in the names `int32` and `int64` is a count of **bits**: how many
bits the value takes in memory. 8 bits are one byte, so `int32` is 4 bytes and `int64` is 8 bytes. The more bits, the
higher the counting limit.

The program `misollar/olcham` prints the size and limits of each type. Its code uses the `math` and `unsafe`
packages, which we have not covered yet, so, as in the video, we read only the output (the code is in the folder if
you want to look). `bayt` means "bytes":

```console
$ go run ./misollar/olcham
int32: 4 bayt, -2147483648 … 2147483647
int64: 8 bayt, -9223372036854775808 … 9223372036854775807
int:   8 bayt (bu kompyuterda)
```

| Type | Size | Limits (about) |
|---|---|---|
| `int32` | 4 bytes (32 bits) | −2,147,483,648 … 2,147,483,647, that is ±2 billion |
| `int64` | 8 bytes (64 bits) | −9,223,372,036,854,775,808 … 9,223,372,036,854,775,807, that is ±9 quintillion |

Before you look at the third line (`bu kompyuterda` means "on this computer"), a question. The plain `int` we used
in GB-1.02 has no number in its name. How many bytes does it take?

**A)** always 4 bytes · **B)** always 8 bytes · **C)** it depends on the processor

<details>
<summary>Answer</summary>

**C: it depends on the processor.** The Go specification says `int` is "either 32 or 64 bits". On this computer
`int` is 8 bytes, because `amd64` from the `go version` output is a 64-bit processor.

- If you chose **A** or **B**, you thought the size of `int` is fixed. It is chosen by the processor the program is
  built for.

You can see this for yourself. `GOARCH` is an **environment variable** (a setting written as `NAME=value` before the
command). It tells Go to build the program for a different processor. `386` is a 32-bit processor:

```console
$ GOARCH=386 go run ./misollar/olcham
int32: 4 bayt, -2147483648 … 2147483647
int64: 8 bayt, -9223372036854775808 … 9223372036854775807
int:   4 bayt (bu kompyuterda)
```

`int32` and `int64` did not change, but the same `int` is now 4 bytes. (The command also worked on an amd64
computer, because an amd64 processor can also run 32-bit `386` programs.)

</details>

Summary: `int32` and `int64` have the same size on every computer, while `int` is 4 or 8 bytes depending on the
processor.

## Overflow: two phones do not fit in `int32`

Now a real case. A phone costs 15,000,000 soʻm. We write the price **in tiyin**: 1 soʻm = 100 tiyin, so
1,500,000,000 tiyin. Two were sold.

```go filename="misollar/int32/main.go" showLineNumbers
package main

import "fmt"

func main() {
	var price int32 = 1_500_000_000 // tiyin
	total := price * 2
	fmt.Println(total)
}
```

| Line | Code | What it does |
|---|---|---|
| 1–5 | `package main` … `func main() {` | from GB-1.01: a separate program, the `fmt` import, the `main` function |
| 6 | `var price int32 = 1_500_000_000 // tiyin` | a variable named `price`, its type written explicitly: `int32`, value 1,500,000,000 |
| 7 | `total := price * 2` | `*` is multiplication. `:=` gives `total` the type of the right side, that is `int32` |
| 8 | `fmt.Println(total)` | prints the result |

Line 6 has two new marks:

- **`_`, underscores in a number**, are only there to make it easier to read. Go ignores them: `1_500_000_000` and
  `1500000000` are the same number.
- After **`//`**, up to the end of the line, is a **comment**. The compiler does not read it; it is for people. Here
  it reminds you that the price is in tiyin.

1,500,000,000 fits in `int32`: the limit is about 2 billion. Two phones are 3,000,000,000 tiyin. What appears on the
screen?

**A)** `3000000000` · **B)** a compile error · **C)** a negative number · **D)** the program stops with an error

<details>
<summary>Answer</summary>

**C: a negative number.**

```console
$ go run ./misollar/int32
-1294967296
```

About minus 1.3 billion. The compiler gave no error, and the program did not stop. This is called **overflow**: the
result went past the limit of the type.

- If you chose **A**, you thought Go makes more room for the result by itself. The type of `total` is `int32`, and it
  does not change.
- If you chose **B**, you thought the compiler checks the product. `price` is a variable; the compiler does not
  compute its value.
- If you chose **D**, you thought there is a check while the program runs. Go has no such check for integer
  overflow.

</details>

**What happened in the bits.** To write 3,000,000,000 you need all 32 bits, including the leftmost one. But `int32`
reads the leftmost bit as a bit with a negative weight: its weight is not +2³¹ but −2³¹. This way of storing negative
numbers is called **two's complement**. As a result, the bits in memory are read as 3,000,000,000 − 2³²:

| Step | Value |
|---|---|
| the result we wanted | 3,000,000,000 |
| the `int32` limit | 2,147,483,647 (2³¹ − 1) |
| all 32 bits in use, leftmost bit = −2³¹ | subtracted: 2³² = 4,294,967,296 |
| the number in memory | 3,000,000,000 − 4,294,967,296 = **−1,294,967,296** |

By the Go specification (the official rules of the language), this is not an error. An integer "may legally
overflow", the result is exactly defined, and the program does not stop. The bug passes silently: the total becomes
negative, and nothing warns you.

**The fix is one word.** `int64` instead of `int32`. This file is not in the folder; we changed line 6 and ran it
separately:

```go
	var price int64 = 1_500_000_000 // tiyin
	total := price * 2
	fmt.Println(total)
```

```console
$ go run .
3000000000
```

| Line | `price` (`int64`) | `total` (`int64`) | Screen |
|---|---|---|---|
| 6 | 1,500,000,000 | — | |
| 7 | 1,500,000,000 | 3,000,000,000 | |
| 8 | 1,500,000,000 | 3,000,000,000 | `3000000000` |

In tiyin, `int64` counts up to about 92 quadrillion soʻm (9,223,372,036,854,775,807 / 100). Why not plain `int`? Its
size depends on the processor, and money must have the same size on every server.

## `float64`: why 12,000 × 1.12 is not exact

Now fractional numbers. The calculation from the start of the lesson:

```go filename="misollar/float/main.go" showLineNumbers
package main

import "fmt"

func main() {
	price := 12000.0
	fmt.Println(price * 1.12)
}
```

| Line | Code | What it does |
|---|---|---|
| 6 | `price := 12000.0` | the number has a point in it, so `:=` gives `price` the type `float64` |
| 7 | `fmt.Println(price * 1.12)` | multiplies the price by 1.12 (price + 12 % VAT) and prints the result |

```console
$ go run ./misollar/float
13440.000000000002
```

Not 13,440: there is an extra `2` at the end. This is not a bug in Go; it is how `float64` stores a number in
memory.

**What the machine does.** `float64` stores a number in 8 bytes as a **binary fraction**. This is the IEEE 754
standard. As a binary fraction, 1.12 never ends; it goes on forever, the way 1/3 is 0.333… as a decimal fraction.
Memory gets the nearest `float64` value, and it is slightly larger:

| Step | Value |
|---|---|
| in the code | `1.12` |
| in memory (nearest `float64`) | `1.12000000000000010658…` |
| × 12,000 | 13,440.0000000000012… — the difference also grew 12,000 times |
| nearest `float64`, on screen | `13440.000000000002` |

How we saw the value in memory is in the "Going deeper" section.

## Money in the smallest unit: tiyin

With money, even one tiyin of difference is an error. When such totals are added, the difference builds up, and
comparing `13440.000000000002` with `13440` wrongly answers "not equal".

The rule: **store money in the smallest unit, as a whole number.**

| | |
|---|---|
| unit | 1 soʻm = 100 tiyin |
| apples | 12,000 soʻm → 1,200,000 tiyin, `int64` |
| payment system | the Payme Merchant API also takes the `amount` field in tiyin: «Сумма платежа (в тийинах)» ("payment amount, in tiyin") |
| soʻm | only for display on screen |

Adding, subtracting and multiplying whole numbers is exact: 1,200,000 × 3 is always 3,600,000. Only division needs
care; it is in the "Sale total" section.

## When types mix: `mismatched types`

Now bozor's `main.go`, in its final state from GB-1.02. One change: `price` is now an `int64`, and its value is in
tiyin. At the end there are two new lines: the sale total `subtotal` and printing it. This intermediate state is not
a separate file in the folder; we ran it separately:

```go
package main

import "fmt"

func main() {
	fmt.Println("bozor ishga tushdi")
	fmt.Println("versiya: 0.1.0")

	var name string
	var price int64
	var active bool
	fmt.Println(name, price, active)

	name = "olma"
	price = 1_200_000 // tiyin
	active = true
	stock := 40
	weight := 1.5
	fmt.Println(name, price, active, stock, weight)

	sold := 3
	stock = stock - sold
	fmt.Println(name, stock)

	subtotal := price * sold
	fmt.Println(subtotal)
}
```

| Line | Code | What it does |
|---|---|---|
| 10 | `var price int64` | changed: it was `int`, now `int64` |
| 15 | `price = 1_200_000 // tiyin` | changed: 12,000 soʻm = 1,200,000 tiyin |
| 18 | `weight := 1.5` | unchanged: this is a weight, not money, so it stays `float64` |
| 21 | `sold := 3` | from GB-1.02: the number of items sold |
| 25 | `subtotal := price * sold` | new: the sale total, price × items |
| 26 | `fmt.Println(subtotal)` | new: prints the total |

On this computer both `int` and `int64` are 8 bytes; we saw that in the `olcham` program. What does `go run .` do?

**A)** prints `3600000` · **B)** a compile error · **C)** overflow: a negative number

<details>
<summary>Answer</summary>

**B: a compile error.** The program does not run.

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:25:14: invalid operation: price * sold (mismatched types int64 and int)
```

The first line is the package name; `go` prints it before the error. We read the second one as in GB-1.01:
`main.go`, line 25, column 14, where `price` starts (the Tab is column 1, `subtotal` is 2–9, a space, `:=` is
11–12, a space). *invalid operation*: "this operation is not allowed". *mismatched types int64 and int*: "the types
do not match: `int64` and `int`". `sold` got the type `int` through `:=`.

- If you chose **A**, you thought that the same size means the same type. To Go, `int64` and `int` are two different
  types.
- If you chose **C**, you thought 3,600,000 does not fit. It fits; size is not the issue here.

</details>

The rule: in Go, both sides of an arithmetic operation must have the same type. Go does not convert numbers of
different types by itself, even when their size is the same.

## Conversion: `int64(sold)`

The fix: on line 25, write `int64(sold)` instead of `sold`.

```go
	subtotal := price * int64(sold)
```

This is a **conversion**: first the type name, then the value in parentheses. It makes a **new** `int64` value from
the `3` in `sold`. `sold` itself stays an `int`. Now both sides of the multiplication are `int64`.

| Line | Code | `price` (`int64`) | `sold` (`int`) | `subtotal` (`int64`) |
|---|---|---|---|---|
| 15 | `price = 1_200_000` | 1,200,000 | — | — |
| 21 | `sold := 3` | 1,200,000 | 3 | — |
| 25 | `int64(sold)` → a new `int64` value `3` | 1,200,000 | 3 (unchanged) | 3,600,000 |

```console
$ go run .
bozor ishga tushdi
versiya: 0.1.0
 0 false
olma 1200000 true 40 1.5
olma 37
3600000
```

On the fourth line the price is now in tiyin: `1200000`. The last line is the sale total: 3,600,000 tiyin, that is
36,000 soʻm.

## `const` and the untyped constant

Two numbers repeat in the calculation: 100 (tiyin in a soʻm) and 12 (the VAT percentage). We give them names. The
start of `main.go` in the course folder:

```go
package main

import "fmt"

const tiyinPerSom = 100 // 1 soʻm = 100 tiyin
const vatPercent = 12   // QQS, foizda

func main() {
```

- **`const`** is a named value that does not change. Its value is known at compile time and does not change.
  `tiyinPerSom` ("tiyin per soʻm") equals 100, and `vatPercent` ("VAT percentage"; the comment `QQS, foizda` means
  "VAT, in percent") equals 12.
- Both `const` lines are **outside** `func main()`. In GB-1.02 we said that outside a function you can only write
  `var` (not `:=`). `const` can be written there too, and the name is visible in the whole package.

If you give a constant a new value, the compiler refuses. We added the line `tiyinPerSom = 50` inside `main` (the
video shows this only as a label):

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:18:2: cannot assign to tiyinPerSom (neither addressable nor a map index expression)
```

*cannot assign to tiyinPerSom*: "you cannot give `tiyinPerSom` a value". The part in parentheses means: this is not a
variable in memory. We delete the line.

**The untyped constant.** `tiyinPerSom` and `vatPercent` have no written type. Such a constant is called an
**untyped constant**. A number written straight into the code, such as `3` or `100`, is one too. An untyped constant
takes the type of the place where it is used:

| Code | Where the constant is | Which type it takes |
|---|---|---|
| `price = 12_000 * tiyinPerSom // tiyinda` | written into an `int64` variable | `int64` |
| `subtotal * vatPercent` | multiplied by an `int64` | `int64`, no conversion needed |
| `sold := 3` | a new variable with `:=` | its **default type**, that is `int` |

The last row explains why `sold` was an `int`: with `:=`, an untyped constant takes its default type. For a whole
number that is `int`; for a number with a point it is `float64`.

## Sale total: `subtotal`, `vat`, `total`

Now the full `main.go` from the course folder (the starting state of the task):

```go filename="main.go" showLineNumbers
package main

import "fmt"

const tiyinPerSom = 100 // 1 soʻm = 100 tiyin
const vatPercent = 12   // QQS, foizda

func main() {
	fmt.Println("bozor ishga tushdi")
	fmt.Println("versiya: 0.1.0")

	var name string
	var price int64
	var active bool
	fmt.Println(name, price, active)

	name = "olma"
	price = 12_000 * tiyinPerSom // tiyinda
	active = true
	stock := 40
	weight := 1.5
	fmt.Println(name, price, active, stock, weight)

	sold := 3
	stock = stock - sold
	fmt.Println(name, stock)

	subtotal := price * int64(sold)
	vat := subtotal * vatPercent / 100
	total := subtotal + vat
	fmt.Println(name, sold, "dona")
	fmt.Println("jami:", total/tiyinPerSom, "soʻm", total%tiyinPerSom, "tiyin")
}
```

| Line | Code | What it does |
|---|---|---|
| 5–6 | `const tiyinPerSom = 100`, `const vatPercent = 12` | two package-level untyped constants |
| 13 | `var price int64` | the price as `int64` |
| 18 | `price = 12_000 * tiyinPerSom // tiyinda` | 12,000 soʻm × 100 = 1,200,000 tiyin |
| 9–26 | the other lines | from GB-1.02, unchanged |
| 28 | `subtotal := price * int64(sold)` | step 1: the sale total, with `int64(sold)` |
| 29 | `vat := subtotal * vatPercent / 100` | step 2: the VAT (`vat`), first × 12, then / 100. Here `vatPercent` becomes `int64` |
| 30 | `total := subtotal + vat` | step 3: adding with `+`. All three are `int64`, all three in tiyin |
| 31 | `fmt.Println(name, sold, "dona")` | prints the name, the number of items and the word `dona` ("pcs") with spaces |
| 32 | `fmt.Println("jami:", total/tiyinPerSom, "soʻm", total%tiyinPerSom, "tiyin")` | prints the total (`jami`), split into soʻm and tiyin |

Line 32 has two new operations:

- **`/` is integer division.** When a whole number is divided by a whole number, the fractional part of the result is
  dropped, not rounded: `250 / 100` = `2`. So `total/tiyinPerSom` is the whole soʻm.
- **`%` is the remainder**: what is left over after division. `250 % 100` = `50`. So `total%tiyinPerSom` is the
  tiyin left over.

The calculation steps for the apples:

| Step | Code | Value (tiyin) |
|---|---|---|
| 1 | `subtotal = 1_200_000 * 3` | 3,600,000 |
| 2 | `vat = 3_600_000 * 12 / 100` = `43_200_000 / 100` | 432,000 |
| 3 | `total = 3_600_000 + 432_000` | 4,032,000 |
| soʻm | `4_032_000 / 100` | 40,320 |
| tiyin | `4_032_000 % 100` | 0 |

The calculation mixes `int64` variables and untyped constants. What does `go run .` print on the last line?

**A)** `jami: 40320 soʻm 0 tiyin` · **B)** `jami: 40320.00000000001 soʻm` · **C)** a compile error:
`vatPercent` is not `int64`

<details>
<summary>Answer</summary>

**A.** No error, and no extra digit at the end.

```console
$ go run .
bozor ishga tushdi
versiya: 0.1.0
 0 false
olma 1200000 true 40 1.5
olma 37
olma 3 dona
jami: 40320 soʻm 0 tiyin
```

- If you chose **B**, you thought there is a fractional number in the calculation. Every value is a whole number, in
  tiyin.
- If you chose **C**, you thought `vatPercent` is an `int`. It is untyped, so when it is multiplied by `subtotal` it
  takes the type `int64`.

The first five lines are as in GB-1.02 (on the fourth, the price is now in tiyin). The last two are new.

</details>

## Going deeper (optional): conversion from `float64` to `int64`

What if an outside system sends the price in soʻm, with a fraction? For example, 19.99 soʻm. It lands in a `float64`
variable named `som`, and we want to turn it into tiyin:

```go filename="misollar/kesish/main.go" showLineNumbers
package main

import "fmt"

func main() {
	som := 19.99
	fmt.Println(int64(som * 100))
}
```

| Line | Code | What it does |
|---|---|---|
| 6 | `som := 19.99` | `float64`, because the number has a point in it |
| 7 | `int64(som * 100)` | first a `float64` product, then its conversion to `int64` |

```console
$ go run ./misollar/kesish
1998
```

Not 1999 but 1998: one tiyin was lost. The reason, in two steps:

| Step | Value |
|---|---|
| `som * 100` (`float64`) | `1998.9999999999998`: 19.99 is not exact in memory either |
| `int64(…)` | `1998`: a conversion from `float64` to an integer **drops** the fraction; it does not round |

The Go specification says the same: when a floating-point number is converted to an integer, the fraction is
discarded (truncation towards zero).

The rule: accept money from outside as a whole number of tiyin right away, and keep every calculation inside in
`int64`. Turning text into a whole number comes in [GB-1.07](/lab/youtube/gb#gb-1-07).

**How we saw the values in memory.** This program is not in the course folder; we ran it separately. `fmt.Printf`
and `%.30f` ("30 digits after the point") are explained in the next lesson, [GB-1.04](/lab/youtube/gb/gb-1-04/en).

```go
package main

import "fmt"

func main() {
	fmt.Printf("%.30f\n", 1.12)
	fmt.Println(12000.0 * 1.12)
	som := 19.99
	fmt.Println(som * 100)
}
```

```console
$ go run .
1.120000000000000106581410364015
13440
1998.9999999999998
```

Look at the second line: here `12000.0 * 1.12` printed exactly `13440`. Both numbers are constants; Go computes a
constant expression exactly at compile time and writes only the final result into a `float64`. `misollar/float` uses
the variable `price`, so there the calculation happens in `float64`. In a real program, a price always arrives in a
variable.

## Common mistakes

**1. The VAT becomes zero: `(vatPercent / 100)`.** The most common mistake in money calculations. We compute the
percentage separately first, then multiply `subtotal` by it. On paper this is the same formula. Line 29 of
`main.go`:

```go
	vat := subtotal * (vatPercent / 100)
```

Apples, 3 items, 12 % VAT. What is on the last line?

**A)** `jami: 40320 soʻm 0 tiyin` · **B)** `jami: 36000 soʻm 0 tiyin` · **C)** a compile error

<details>
<summary>Answer</summary>

**B: 36,000 soʻm.** No VAT was added at all, and no error appeared.

```console
$ go run .
bozor ishga tushdi
versiya: 0.1.0
 0 false
olma 1200000 true 40 1.5
olma 37
olma 3 dona
jami: 36000 soʻm 0 tiyin
```

12 and 100 are both whole-number constants. Integer division `12 / 100` gives `0`, and a total multiplied by zero is
zero. `*` and `/` have the same precedence and run from left to right. So without parentheses,
`subtotal * vatPercent / 100` first multiplies (43,200,000) and then divides (432,000).

- If you chose **A**, you thought `12 / 100` is 0.12. With whole numbers, the fraction is dropped.
- If you chose **C**, you thought the compiler catches this. The result 0 has the right type and is a valid value, so
  there is no error.

</details>

**Fix:** remove the parentheses, so the division comes last: `vat := subtotal * vatPercent / 100`.

**2. `int64` and `int` mixed.** `price * sold` → `invalid operation: price * sold (mismatched types int64 and int)`.
The full analysis is in the "When types mix" section. **Fix:** `price * int64(sold)`.

**3. Putting a constant into a variable with `:=`.** In the task, if you write `const deliverySom = 15_000` for the
delivery price and put it into a separate variable:

```go
	delivery := deliverySom * tiyinPerSom
	total := subtotal + vat + delivery
```

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:32:11: invalid operation: subtotal + vat + delivery (mismatched types int64 and int)
```

`:=` gave the untyped constant its default type, `int`, while `subtotal` is `int64`. Line 32, column 11 is where
`subtotal` starts. (This example is not in the video; we ran it in a copy of the solution file.) **Fix:** write the
type explicitly (`var delivery int64 = deliverySom * tiyinPerSom`) or put the constant straight into the expression
(`subtotal + vat + deliverySom*tiyinPerSom`).

**4. Silent overflow.** In `int32`, 1,500,000,000 × 2 → `-1294967296`, with no error (the "Overflow" section).
**Fix:** always use `int64` for money.

**5. Converting a fractional number to an integer.** `int64(19.99 * 100)` → `1998` (the "Going deeper" section).
**Fix:** accept money from the start in tiyin, as a whole number.

## Check yourself

Answer first, then open.

**1.** What do you get if you multiply 1,500,000,000 by 2 in `int32`?

<details>
<summary>Answer</summary>

A negative number, `-1294967296`: overflow. Neither the compiler nor the program reports an error.

</details>

**2.** Why is a price stored in tiyin as an `int64`, and not as a `float64`?

<details>
<summary>Answer</summary>

`float64` is a binary fraction and cannot store 1.12 exactly: `12000.0 * 1.12` → `13440.000000000002`. `int64`
counts tiyin exactly and, unlike `int`, is 8 bytes on every server.

</details>

**3.** What does this program print? (It is not in the course folder; we ran it separately.)

```go
package main

import "fmt"

func main() {
	total := 1999 * 3
	fmt.Println(total/100, total%100)
	fmt.Println(total*12/100, total*(12/100))
}
```

**A)** `59.97 97` and `719.64 0` · **B)** `59 97` and `719 0` · **C)** `60 97` and `720 0`

<details>
<summary>Answer</summary>

**B.** `total` = 5997, an `int`. `5997 / 100` = `59` (the fraction is dropped), `5997 % 100` = `97`.
`5997 * 12 / 100` = `71964 / 100` = `719`, while `12 / 100` is `0`, so the second expression is `0`.

```console
$ go run .
59 97
719 0
```

If you chose **A**, you thought integer division gives a fraction. If you chose **C**, you thought it rounds.

</details>

**4.** With `var a int64` and `b := 5`, why does `a + b` not build, and how do you fix it?

<details>
<summary>Answer</summary>

Through `:=`, `b` takes the default type `int`, while `a` is `int64`: `mismatched types int64 and int`. Fix:
`a + int64(b)`, or declare `b` as `var b int64 = 5` from the start.

</details>

**5.** From GB-1.01: what does `go build` create?
