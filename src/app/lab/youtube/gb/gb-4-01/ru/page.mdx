## Что вы узнаете

Каталог bozor теперь живёт на сервере. Мобильное приложение запросило товар с номером 99 и вместо ответа получило ошибку. Причина записана в двух текстах, которыми
приложение и сервер обменялись. Сегодня мы эти два текста прочитаем.

**Одна идея:** HTTP-обмен — это два текста. Клиент отправляет текст запроса, сервер возвращает текст ответа. У обоих одна форма: первая строка, заголовки вида `имя: значение`,
пустая строка, тело. Первая строка запроса — `метод путь версия`, первая строка ответа — `версия код-статуса причина`. Первая цифра кода статуса называет класс: `2xx` — успех,
`4xx` — ошибка в запросе, `5xx` — ошибка на сервере. `Content-Type` говорит, в каком формате тело, `Content-Length` — какой оно длины в **байтах**.

К концу урока вы:

- прочитаете в выводе `curl -v` метод, путь и заголовки запроса, а также код статуса, заголовки и тело ответа;
- отправите тот же запрос вручную через `printf` и `nc`: curl отправляет именно этот текст;
- объясните, почему `Content-Length` считает байты, а не символы, и почему без `-H` сервер возвращает `415`;
- напишете на Go функции `parseRequestLine` (разбирает строку запроса) и `statusClass` (называет класс статуса) и добьётесь, чтобы `go test` прошёл.

Три главных новых слова урока:

| Слово | Простой смысл | По-английски |
|---|---|---|
| запрос и ответ (HTTP-обмен) | текст, который отправляет клиент, и текст, который возвращает сервер | HTTP exchange (request, response) |
| код статуса | трёхзначное число в первой строке ответа: чем закончился запрос | status code |
| заголовок | дополнительная строка вида `имя: значение`: говорит, как читать тело | header |

Вспомогательные слова: **клиент** и **сервер**, **тело** (body — основная часть сообщения), `curl` (программа, которая отправляет запросы из терминала), `printf` и `nc` (отправка запроса вручную).

## Клиент, сервер и адрес

Сервер каталога — программа, которая принимает запросы и возвращает ответы. Она работает на этом же компьютере. Сторона, которая отправляет запрос (например, мобильное приложение), называется **клиентом** (client).
Правила их разговора — **протокол HTTP**: они определяют, как записываются запрос и ответ.

Адрес сервера — одна строка: `http://localhost:8765/products/1`.

| Часть | Смысл |
|---|---|
| `http://` | протокол: клиент и сервер говорят по правилам HTTP |
| `localhost` | этот же компьютер |
| `:8765` | **порт**: сетевой номер одной программы на компьютере; сервер слушает этот номер |
| `/products/1` | **путь** (path): что нужно — товар с номером 1 (`products` — «товары») |

## Первый запрос: curl -v

Отправим ему запрос через `curl`. `curl` — клиентская программа, которая отправляет HTTP-запросы из терминала. Флаг `-v` (verbose, «подробно») показывает и отправленные, и полученные строки.
В этом терминале, против сервера (я сам запустил его, воспользовался и остановил):

```console
$ curl -v http://localhost:8765/products/1
* Host localhost:8765 was resolved.
* IPv6: ::1
* IPv4: 127.0.0.1
*   Trying [::1]:8765...
* connect to ::1 port 8765 from ::1 port 45334 failed: Connection refused
*   Trying 127.0.0.1:8765...
* Established connection to localhost (127.0.0.1 port 8765) from 127.0.0.1 port 41116 
* using HTTP/1.x
> GET /products/1 HTTP/1.1
> Host: localhost:8765
> User-Agent: curl/8.22.0
> Accept: */*
> 
* Request completely sent off
< HTTP/1.1 200 OK
< Content-Type: application/json
< Date: Fri, 27 Nov 2026 07:22:46 GMT
< Content-Length: 49
< 
* Connection #0 to host localhost:8765 left intact
{"id":1,"name":"olma","price":1200000,"stock":40}
```

В выводе три вида строк:

| Начало строки | Что это |
|---|---|
| `*` | сведения о соединении (адрес найден, соединение открыто): не сам HTTP-текст |
| `>` | строка **запроса**, который отправил curl |
| `<` | строка **ответа** сервера; в конце строка без метки — тело, сам товар |

Здесь сервер слушает только IPv4-адрес (`127.0.0.1`): curl сначала попробовал `::1` (IPv6), получил отказ и перешёл на `127.0.0.1`. Строки `*` зависят от машины, поэтому дальше я
убираю их (и строки curl `[N bytes data]`); в видео они тоже скрыты. Остальное не изменено. Значение `Date` каждый раз другое: в видео `06:37:46`, в моём запуске `07:22:46` GMT.
Все шаги выполнились за одну секунду, поэтому в последовательных командах `Date` выглядит одинаково.

## Текст запроса строка за строкой

Только строки `>` — это сам запрос:

```http
GET /products/1 HTTP/1.1
Host: localhost:8765
User-Agent: curl/8.22.0
Accept: */*

```

Первая строка — **строка запроса**. В ней три части, разделённые одним пробелом:

| Часть | Значение | Смысл |
|---|---|---|
| **метод** (method) | `GET` | что сделать: здесь «получить» |
| путь | `/products/1` | что именно нужно |
| версия протокола | `HTTP/1.1` | HTTP, один точка один |

Дальше идут **заголовки** (header): каждый — имя, двоеточие, значение.

| Строка | Смысл |
|---|---|
| `Host: localhost:8765` | какому серверу адресован запрос |
| `User-Agent: curl/8.22.0` | кто отправил запрос: curl и его версия |
| `Accept: */*` | какой тип ответа клиент готов принять: звёздочка, слеш, звёздочка — любой |

В конце стоит **пустая строка**: она означает «заголовки закончились». В этом запросе тела нет, поэтому после пустой строки ничего нет.

## Текст ответа строка за строкой

Теперь ответ — строки `<` и товар под ними:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Date: Fri, 27 Nov 2026 07:22:46 GMT
Content-Length: 49

{"id":1,"name":"olma","price":1200000,"stock":40}
```

Первая строка — **строка статуса**. Она тоже из трёх частей:

| Часть | Значение | Смысл |
|---|---|---|
| версия протокола | `HTTP/1.1` | HTTP, один точка один |
| **код статуса** | `200` | трёхзначное число: чем закончился запрос |
| текст причины | `OK` | пояснение для человека; программа смотрит на код, а текст игнорирует |

Заголовки такие же, как в запросе: имя, двоеточие, значение.

| Строка | Смысл |
|---|---|
| `Content-Type: application/json` | в каком формате тело: `application/json` — JSON |
| `Date: …` | когда сервер сформировал ответ, по гринвичскому времени (GMT) |
| `Content-Length: 49` | сколько в теле **байт**: 49 |

Затем пустая строка: заголовки закончились, начинается тело. Тело — сам товар: `{"id":1,"name":"olma","price":1200000,"stock":40}`. `price` — число без кавычек:
ответ на прошлый вопрос виден прямо здесь.

## Два текста, одна форма

У запроса и ответа одна форма:

| Часть | В запросе | В ответе |
|---|---|---|
| первая строка | `GET /products/1 HTTP/1.1` (метод, путь, версия) | `HTTP/1.1 200 OK` (версия, код статуса, причина) |
| заголовки | `Host: …`, `User-Agent: …`, `Accept: …` | `Content-Type: …`, `Date: …`, `Content-Length: …` |
| пустая строка | заголовки закончились | заголовки закончились |
| тело | в этом запросе нет | `{"id":1,…}` |

Отличается только первая строка: в запросе метод и путь, в ответе код статуса. Получатель опирается на эту форму: читает заголовки до пустой строки, затем читает
столько байт тела, сколько указано в `Content-Length`. Тела может и не быть.

## Пишем вручную: printf и nc

curl всего лишь отправляет этот текст. Проверим это вручную, одной командой из трёх частей:

1. `printf` — команда терминала: выводит заданный текст. `\r\n` внутри текста — конец строки: в HTTP каждая строка заканчивается этими двумя байтами (CR и LF).
2. `|` (вертикальная черта) — передаёт вывод левой команды правой.
3. `nc` (netcat) — подключается к указанному хосту и порту, отправляет полученный текст и выводит ответ.

```console
$ printf 'GET /products/1 HTTP/1.1\r\nHost: localhost:8765\r\nConnection: close\r\n\r\n' | nc localhost 8765
HTTP/1.1 200 OK
Content-Type: application/json
Date: Fri, 27 Nov 2026 07:22:38 GMT
Content-Length: 49
Connection: close

{"id":1,"name":"olma","price":1200000,"stock":40}
```

Текст в одинарных кавычках передаётся команде как один аргумент. В нём три строки и пустая строка в конце: строка запроса, `Host` и `Connection: close`
(закрой соединение после ответа). Результат — тот самый ответ, который показал curl, только добавилась строка `Connection: close` от сервера. Никакого curl, только текст.

Зачем нужен `Connection: close`? Без него сервер оставляет соединение открытым, и `nc` ждёт даже после ответа. Я это проверил: с `timeout 3` (останавливает программу через 3 секунды)
ответ выводится, а затем команда прерывается с кодом выхода 124. Этой команды в папке курса нет, я запустил её сам:

```console
$ printf 'GET /products/1 HTTP/1.1\r\nHost: localhost:8765\r\n\r\n' | timeout 3 nc localhost 8765; echo " chiqish kodi: $?"
HTTP/1.1 200 OK
Content-Type: application/json
Date: Fri, 27 Nov 2026 07:23:58 GMT
Content-Length: 49

{"id":1,"name":"olma","price":1200000,"stock":40} chiqish kodi: 124
```

Программы `nc` бывают разные: здесь OpenBSD netcat, а у GNU-варианта флаги могут отличаться.

## Код статуса: на чьей стороне ошибка

**Код статуса** — трёхзначное число в первой строке ответа. Его первая цифра называет **класс**:

| Класс | Смысл | Примеры |
|---|---|---|
| `2xx` | успех | `200 OK` — запрошенное возвращено; `201 Created` — создано новое |
| `4xx` | ошибка **в запросе** | `400 Bad Request` — запрос составлен неверно (например, битый JSON); `404 Not Found` — сервер не нашёл такой вещи |
| `5xx` | ошибка **на сервере** | `500 Internal Server Error` |

Есть и классы `1xx` и `3xx`; их вы увидите в задании.

Предскажите. Приложение запросило товар 99, а в bozor только два товара. Запрос составлен правильно. Что будет в первой строке ответа?

**A)** `HTTP/1.1 200 OK`, тело пустое · **B)** `HTTP/1.1 404 Not Found` · **C)** `HTTP/1.1 400 Bad Request`

<details>
<summary>Ответ</summary>

**B: `404 Not Found`.** Запрос составлен правильно, поэтому не `400`: такого товара просто нет. Если вы выбрали **C**, вы приняли «запросили несуществующее» за «запрос сломан»;
`400` приходит, когда неверен сам запрос. Если вы выбрали **A**, вы смешали класс «успех» с ошибкой: для несуществующей вещи мы не отдаём `2xx`.

</details>

Вот этот запрос: в конце 99.

```console
$ curl -v http://localhost:8765/products/99
> GET /products/99 HTTP/1.1
> Host: localhost:8765
> User-Agent: curl/8.22.0
> Accept: */*
> 
< HTTP/1.1 404 Not Found
< Content-Type: application/json
< Date: Fri, 27 Nov 2026 07:22:38 GMT
< Content-Length: 30
< 
{"error":"mahsulot topilmadi"}
```

Тело тоже JSON: под ключом `error` текст ошибки (`"mahsulot topilmadi"` — «товар не найден»), приложение берёт его отсюда. Ошибка из начала урока была такой же. В работе ваше приложение ведёт себя так:
сначала смотрит на код статуса, потом читает тело. Если код — успех, тело содержит нужные данные. Если ошибка — тело содержит текст ошибки.

Короткий вопрос. Приложение увидело в первой строке ответа `503`. На чьей стороне ошибка?

**A)** в запросе: клиент ошибся · **B)** на сервере · **C)** сказать нельзя

<details>
<summary>Ответ</summary>

**B: на сервере.** Код `5xx` говорит: сервер допустил ошибку или не смог выполнить запрос (`503` — «Service Unavailable», сервис сейчас не может ответить). Первая цифра показывает, на чьей стороне ошибка,
а точный код — что произошло. **A** — это класс `4xx`; **C** — сказать можно, именно для этого и есть класс.

</details>

У сервера есть и другой ответ. Каталог знает только `GET /products/{id}` и `POST /products`. Если спросить другим методом, сервер вернёт `405`. В видео этого нет,
это есть в README курса; я тоже запустил (`-X` — вы сами называете метод):

```console
$ curl -v -X DELETE http://localhost:8765/products/1
> DELETE /products/1 HTTP/1.1
> Host: localhost:8765
> User-Agent: curl/8.22.0
> Accept: */*
> 
< HTTP/1.1 405 Method Not Allowed
< Allow: GET, HEAD
< Content-Type: text/plain; charset=utf-8
< X-Content-Type-Options: nosniff
< Date: Fri, 27 Nov 2026 07:24:01 GMT
< Content-Length: 19
< 
Method Not Allowed
```

`405` тоже из класса `4xx`: ошибка в запросе (путь есть, но не с этим методом). Заголовок `Allow` говорит, какие методы допустимы.

## Отправляем тело: POST и Content-Length

Теперь тело находится в самом запросе. Чтобы добавить новый товар, метод — `POST`: он передаёт серверу тело, и сервер создаёт из него новый товар. Это тело — JSON товара.
Формат тела и его размер в байтах задают два заголовка: `Content-Type` и `Content-Length`.

Вот тело:

```json
{"name":"oʻrik","price":3500000,"stock":5}
```

Это 42 символа: изогнутый знак (`ʻ`) в букве `oʻ` слова `oʻrik` («слива») — тоже один символ. Предскажите. В заголовке запроса есть `Content-Length`: это длина тела в **байтах**.
Тело — 42 символа. Чему равен `Content-Length`?

**A)** 42 · **B)** 43 · **C)** 44

<details>
<summary>Ответ</summary>

**B: 43.** `Content-Length` считает байты, а не символы, а `ʻ` в UTF-8 занимает два байта ([GB-2.10](/lab/youtube/gb/gb-2-10/ru)). Если вы выбрали **A**, вы приравняли символы к байтам;
**C** — двухбайтовый только один символ, не все. Проверим (этой команды в папке курса нет; `wc -m` в UTF-8-локали считает символы, `wc -c` — байты):

```console
$ printf '{"name":"oʻrik","price":3500000,"stock":5}' | wc -m -c
     42      43
```

</details>

Вот запрос. `-d` передаёт тело, `-H` добавляет заголовок: что тело — JSON, сообщает `Content-Type`. Двойные кавычки тоже оборачивают один аргумент. Сервер вернул `201 Created`:

```console
$ curl -v -d '{"name":"oʻrik","price":3500000,"stock":5}' -H "Content-Type: application/json" http://localhost:8765/products
> POST /products HTTP/1.1
> Host: localhost:8765
> User-Agent: curl/8.22.0
> Accept: */*
> Content-Type: application/json
> Content-Length: 43
> 
< HTTP/1.1 201 Created
< Content-Type: application/json
< Location: /products/3
< Date: Fri, 27 Nov 2026 07:22:38 GMT
< Content-Length: 50
< 
{"id":3,"name":"oʻrik","price":3500000,"stock":5}
```

В запросе: первая строка теперь `POST /products HTTP/1.1`, два новых заголовка (`Content-Type`, `Content-Length: 43`), а после пустой строки идёт тело (curl не показывает его с `>`).
В ответе: `201 Created` — новый товар создан. Заголовок `Location` называет путь нового товара: `/products/3`. В теле товар теперь с `id`: его выдал сам сервер.
`Content-Length: 50` в ответе: и здесь есть `oʻ`, 49 символов и 50 байт. В видео `id` равен 3, потому что на сервере было два товара.

## Классическая ошибка: забыли Content-Type

Предскажите. Отправим тот же `POST` без `-H`: заголовка нет, тело то же JSON. Что вернёт сервер?

**A)** `201 Created` · **B)** `4xx`: ошибка в запросе · **C)** `5xx`: ошибка на сервере

<details>
<summary>Ответ</summary>

**B: `4xx`.** Тело было верным, заголовок — неверным: сервер не знает, в каком формате пришли данные. Если вы выбрали **A**, вы решили, что сервер сам догадается — а он смотрит на `Content-Type`.
**C** — сервер в своей работе не ошибся, ошибся запрос.

</details>

```console
$ curl -v -d '{"name":"oʻrik","price":3500000,"stock":5}' http://localhost:8765/products
> POST /products HTTP/1.1
> Host: localhost:8765
> User-Agent: curl/8.22.0
> Accept: */*
> Content-Length: 43
> Content-Type: application/x-www-form-urlencoded
> 
< HTTP/1.1 415 Unsupported Media Type
< Content-Type: application/json
< Date: Fri, 27 Nov 2026 07:22:38 GMT
< Content-Length: 57
< 
{"error":"Content-Type application/json boʻlishi kerak"}
```

Без `-H` curl сам подставляет `Content-Type`: `application/x-www-form-urlencoded` — формат отправки полей формы в виде `имя=значение`, не JSON. Сервер возвращает `415`: тип тела
не поддерживается. Код начинается с `4`, значит, ошибка в запросе: тело было верным, заголовок — нет. В теле ответа сервер написал причину.

Исправление — `Content-Type: application/json` через `-H`. Теперь сервер возвращает `201`. Сервер запомнил предыдущий успешный `POST`, поэтому в этот раз `id` равен 4, а `Location: /products/4`:

```console
$ curl -v -d '{"name":"oʻrik","price":3500000,"stock":5}' -H "Content-Type: application/json" http://localhost:8765/products
> POST /products HTTP/1.1
> Host: localhost:8765
> User-Agent: curl/8.22.0
> Accept: */*
> Content-Type: application/json
> Content-Length: 43
> 
< HTTP/1.1 201 Created
< Content-Type: application/json
< Location: /products/4
< Date: Fri, 27 Nov 2026 07:22:38 GMT
< Content-Length: 50
< 
{"id":4,"name":"oʻrik","price":3500000,"stock":5}
```

## Частые ошибки

**1. «Ответ пришёл, значит, всё хорошо».** Даже если ошибка `4xx` или `5xx`, сервер отправляет корректный HTTP-ответ: соединение сработало, текст пришёл. Для curl это успех:
на `404` он тоже завершается с кодом выхода 0. Только с флагом `-f` (`--fail`) curl при коде статуса-ошибке возвращает код выхода 22. Я запустил оба варианта:

```console
$ curl -s http://localhost:8765/products/99; echo " chiqish kodi: $?"
{"error":"mahsulot topilmadi"} chiqish kodi: 0
$ curl -sf http://localhost:8765/products/99; echo "chiqish kodi: $?"
chiqish kodi: 22
```

(`-s` — тихий режим: curl не выводит свои промежуточные сообщения.) Вывод: смотрите на код статуса, а не на код выхода и не на «пришёл ли ответ».

**2. Забыть `-H "Content-Type: application/json"`.** Результат — `415 Unsupported Media Type`; как это читать и исправлять, показано выше, в разделе «Классическая ошибка: забыли Content-Type».

**3. Считать `Content-Length` числом символов.** В товаре `oʻrik` 42 символа, но `Content-Length: 43`: разбор — выше, в разделе «Отправляем тело: POST и Content-Length».

**4. Забыть `Connection: close` в `printf | nc`.** `nc` ждёт даже после ответа; в примере с `timeout 3` выше код выхода 124.

**5. Забыть `\r\n` в конце строки в Go.** Строка HTTP заканчивается на `\r\n`. `strings.Split` их не убирает, поэтому `Proto` остаётся `"HTTP/1.1\r\n"`. Вот
неверный вариант `parseRequestLine`: из функции в `solution/main.go` убрана одна строка — `line = strings.TrimRight(line, "\r\n")`; остальная часть файла (`Request`, `statusClass`, `main`) та же. Этой папки нет
в курсовом репозитории, я создал её отдельно (`go.mod` и `tekshiruv_test.go` — те же, что в курсе):

```go
func parseRequestLine(line string) (Request, error) {
	parts := strings.Split(line, " ")
	if len(parts) != 3 {
		return Request{}, fmt.Errorf("soʻrov qatori uch qismdan iborat boʻlishi kerak, hozir %d: %q", len(parts), line)
	}
	method, path, proto := parts[0], parts[1], parts[2]
	if method == "" {
		return Request{}, errors.New("method boʻsh")
	}
	if !strings.HasPrefix(path, "/") {
		return Request{}, fmt.Errorf("yoʻl / bilan boshlanishi kerak: %q", path)
	}
	if !strings.HasPrefix(proto, "HTTP/") {
		return Request{}, fmt.Errorf("versiya HTTP/ bilan boshlanishi kerak: %q", proto)
	}
	return Request{Method: method, Path: path, Proto: proto}, nil
}
```

```go filename="solution/main.go" showLineNumbers
package main

import (
	"errors"
	"fmt"
	"strings"
)

// Request — HTTP soʻrovning birinchi qatoridan olingan uch qism (curl -v'dagi "> GET /products/1 HTTP/1.1").
type Request struct {
	Method string // "GET"
	Path   string // "/products/1"
	Proto  string // "HTTP/1.1"
}

// parseRequestLine "GET /products/1 HTTP/1.1" kabi qatorni qismlarga ajratadi (TASK.md, 1-qadam).
func parseRequestLine(line string) (Request, error) {
	line = strings.TrimRight(line, "\r\n") // HTTP qatori \r\n bilan tugaydi
	parts := strings.Split(line, " ")
	if len(parts) != 3 {
		return Request{}, fmt.Errorf("soʻrov qatori uch qismdan iborat boʻlishi kerak, hozir %d: %q", len(parts), line)
	}
	method, path, proto := parts[0], parts[1], parts[2]
	if method == "" {
		return Request{}, errors.New("method boʻsh")
	}
	if !strings.HasPrefix(path, "/") {
		return Request{}, fmt.Errorf("yoʻl / bilan boshlanishi kerak: %q", path)
	}
	if !strings.HasPrefix(proto, "HTTP/") {
		return Request{}, fmt.Errorf("versiya HTTP/ bilan boshlanishi kerak: %q", proto)
	}
	return Request{Method: method, Path: path, Proto: proto}, nil
}

// statusClass status kodi qaysi sinfga kirishini aytadi (TASK.md, 2-qadam).
func statusClass(code int) string {
	switch {
	case code >= 100 && code < 200:
		return "axborot"
	case code >= 200 && code < 300:
		return "muvaffaqiyat"
	case code >= 300 && code < 400:
		return "yoʻnaltirish"
	case code >= 400 && code < 500:
		return "mijoz xatosi"
	case code >= 500 && code < 600:
		return "server xatosi"
	}
	return "nomaʼlum"
}

func main() {
	req, err := parseRequestLine("GET /products/1 HTTP/1.1")
	if err != nil {
		fmt.Println("xato:", err)
		return
	}
	fmt.Println(req.Method, req.Path, req.Proto)
	fmt.Println(404, statusClass(404))
}
```

Новые строки:

| Строка | Код | Что делает |
|---|---|---|
| 18 | `line = strings.TrimRight(line, "\r\n")` | убирает `\r` и `\n` в конце строки: строка HTTP заканчивается на `\r\n` |
| 19 | `parts := strings.Split(line, " ")` | делит строку по пробелу |
| 20–22 | `if len(parts) != 3 { … }` | если частей не ровно три — ошибка: пустая строка, две и четыре части и два пробела ловятся здесь |
| 23 | `method, path, proto := parts[0], parts[1], parts[2]` | раскладывает три части по именованным переменным |
| 24–26 | `if method == "" { … }` | ошибка, если метод пуст |
| 27–29 | `if !strings.HasPrefix(path, "/") { … }` | ошибка, если путь не начинается с `/` |
| 30–32 | `if !strings.HasPrefix(proto, "HTTP/") { … }` | ошибка, если версия не начинается с `HTTP/` |
| 33 | `return Request{…}, nil` | всё в порядке: три части и ошибка `nil` |
| 38–50 | `switch { case code >= 100 && code < 200: … }` | `switch` без выражения: первое подошедшее условие возвращает название класса; если не подошло ни одно — последний `return "nomaʼlum"` |
