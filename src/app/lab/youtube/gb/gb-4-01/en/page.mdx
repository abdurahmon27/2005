## What you will learn

The bozor catalog now lives on a server. A phone app asked for product number 99 and got an error instead of an answer. The reason is written in the two texts that the app
and the server exchanged. Today we read those two texts.

**One idea:** an HTTP exchange is two texts. The client sends the request text, the server returns the response text. Both have the same shape: a first line, headers of the form `name: value`,
an empty line, a body. The first line of a request is `method path version`; the first line of a response is `version status-code reason`. The first digit of the status code names the class:
`2xx` — success, `4xx` — the error is in the request, `5xx` — the error is on the server. `Content-Type` says what format the body has, `Content-Length` says how long it is, in **bytes**.

By the end of the lesson you will:

- read a request's method, path and headers, and a response's status code, headers and body in `curl -v` output;
- send the same request by hand with `printf` and `nc`: curl sends exactly this text;
- explain why `Content-Length` counts bytes, not characters, and why the server returns `415` when `-H` is missing;
- write two Go functions, `parseRequestLine` (splits a request line) and `statusClass` (names a status class), and make `go test` pass.

Three core new words today:

| Word | Plain meaning | English term |
|---|---|---|
| request and response (HTTP exchange) | the text the client sends and the text the server returns | HTTP exchange (request, response) |
| status code | the three-digit number on the first line of a response: how the request ended | status code |
| header | an extra line of the form `name: value`: it says how to read the body | header |

Helper words: **client** and **server**, **body** (the main part of a message), `curl` (a program that sends requests from the terminal), `printf` with `nc` (sending a request by hand).

## Client, server and address

The catalog server is a program that accepts requests and returns responses. It runs on this same computer. The side that sends a request (for example, a phone app) is called the **client**.
The rules of their conversation are the **HTTP protocol**: they define how a request and a response are written.

The server's address is one line: `http://localhost:8765/products/1`.

| Part | Meaning |
|---|---|
| `http://` | the protocol: client and server talk by HTTP rules |
| `localhost` | this same computer |
| `:8765` | the **port**: the network number of one program on the computer; the server listens on this number |
| `/products/1` | the **path**: what is wanted — product number 1 (`products` — "products") |

## The request text, line by line

Only the `>` lines are the request itself:

```http
GET /products/1 HTTP/1.1
Host: localhost:8765
User-Agent: curl/8.22.0
Accept: */*

```

The first line is the **request line**. It has three parts separated by a single space:

| Part | Value | Meaning |
|---|---|---|
| **method** | `GET` | what to do: here "get" |
| path | `/products/1` | what exactly is wanted |
| protocol version | `HTTP/1.1` | HTTP, one point one |

After it come the **headers**: each is a name, a colon, a value.

| Line | Meaning |
|---|---|
| `Host: localhost:8765` | which server the request is addressed to |
| `User-Agent: curl/8.22.0` | who sent the request: curl and its version |
| `Accept: */*` | what kind of response it accepts: star, slash, star — any |

At the end there is an **empty line**: it means "the headers are over". This request has no body, so nothing follows the empty line.

## The response text, line by line

Now the response — the `<` lines and the product below them:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Date: Fri, 27 Nov 2026 07:22:46 GMT
Content-Length: 49

{"id":1,"name":"olma","price":1200000,"stock":40}
```

The first line is the **status line**. It also has three parts:

| Part | Value | Meaning |
|---|---|---|
| protocol version | `HTTP/1.1` | HTTP, one point one |
| **status code** | `200` | a three-digit number: how the request ended |
| reason text | `OK` | a note for people; a program looks at the code and ignores the text |

The headers are like in the request: name, colon, value.

| Line | Meaning |
|---|---|
| `Content-Type: application/json` | the format of the body: `application/json` — JSON |
| `Date: …` | when the server made the response, in Greenwich time (GMT) |
| `Content-Length: 49` | how many **bytes** the body has: 49 |

Then an empty line: the headers are over, the body begins. The body is the product itself: `{"id":1,"name":"olma","price":1200000,"stock":40}`. `price` is a number without quotes:
the answer to the earlier question is visible right here.

## Two texts, one shape

The request and the response have the same shape:

| Part | In the request | In the response |
|---|---|---|
| first line | `GET /products/1 HTTP/1.1` (method, path, version) | `HTTP/1.1 200 OK` (version, status code, reason) |
| headers | `Host: …`, `User-Agent: …`, `Accept: …` | `Content-Type: …`, `Date: …`, `Content-Length: …` |
| empty line | the headers are over | the headers are over |
| body | none in this request | `{"id":1,…}` |

Only the first line differs: method and path in the request, status code in the response. The receiver relies on this shape: it reads headers up to the empty line, then reads as many
bytes of body as `Content-Length` says. A body may also be absent.

## Writing it by hand: printf and nc

curl only sends this text. We check that by hand, with one command of three parts:

1. `printf` — a terminal command: prints the given text. `\r\n` inside the text is the line end: in HTTP every line ends with these two bytes (CR and LF).
2. `|` (vertical bar) — passes the output of the left command to the command on the right.
3. `nc` (netcat) — connects to the given host and port, sends the text it receives and prints the response.

```console
$ printf 'GET /products/1 HTTP/1.1\r\nHost: localhost:8765\r\nConnection: close\r\n\r\n' | nc localhost 8765
HTTP/1.1 200 OK
Content-Type: application/json
Date: Fri, 27 Nov 2026 07:22:38 GMT
Content-Length: 49
Connection: close

{"id":1,"name":"olma","price":1200000,"stock":40}
```

The text inside single quotes goes to the command as one argument. It has three lines and an empty line at the end: the request line, `Host` and `Connection: close`
(close the connection after the response). The result is the very response curl showed, with the server's `Connection: close` line added. No curl, only text.

Why is `Connection: close` needed? Without it the server keeps the connection open, and `nc` keeps waiting even after the response. I checked this: with `timeout 3` (stops the program after 3 seconds)
the response is printed, and then the command is stopped with exit code 124. This command is not in the course folder; I ran it myself:

```console
$ printf 'GET /products/1 HTTP/1.1\r\nHost: localhost:8765\r\n\r\n' | timeout 3 nc localhost 8765; echo " chiqish kodi: $?"
HTTP/1.1 200 OK
Content-Type: application/json
Date: Fri, 27 Nov 2026 07:23:58 GMT
Content-Length: 49

{"id":1,"name":"olma","price":1200000,"stock":40} chiqish kodi: 124
```

`nc` programs differ: this is OpenBSD netcat, and the GNU variant may have different flags.

## Status code: on whose side is the error

The **status code** is the three-digit number on the first line of a response. Its first digit names the **class**:

| Class | Meaning | Examples |
|---|---|---|
| `2xx` | success | `200 OK` — the requested thing came back; `201 Created` — something new was created |
| `4xx` | the error is **in the request** | `400 Bad Request` — the request is malformed (for example, broken JSON); `404 Not Found` — the server found no such thing |
| `5xx` | the error is **on the server** | `500 Internal Server Error` |

There are also classes `1xx` and `3xx`; you will see them in the task.

Predict. The app asked for product 99, but bozor has only two products. The request is well formed. What is on the first line of the response?

**A)** `HTTP/1.1 200 OK`, empty body · **B)** `HTTP/1.1 404 Not Found` · **C)** `HTTP/1.1 400 Bad Request`

<details>
<summary>Answer</summary>

**B: `404 Not Found`.** The request is well formed, so not `400`: there is simply no such product. If you chose **C**, you took "asked for something that does not exist" for "the request is broken";
`400` comes when the request itself is wrong. If you chose **A**, you mixed the success class with an error: we do not return `2xx` for a thing that does not exist.

</details>

Here is that request: 99 at the end.

```console

> Host: localhost:8765
> User-Agent: curl/8.22.0
> Accept: */*
>

< Content-Type: application/json
< Date: Fri, 27 Nov 2026 07:22:38 GMT
< Content-Length: 30
```

The body is JSON too: under the `error` key is the error text (`"mahsulot topilmadi"` — "product not found"); the app takes it from here. The error from the start of the lesson was the same one. At work your app behaves like this:
first it looks at the status code, then it reads the body. If the code is a success, the body is the data you need. If it is an error, the body is the error text.

A short question. The app saw `503` on the first line of the response. On whose side is the error?

**A)** in the request: the client made a mistake · **B)** on the server · **C)** cannot tell

**B: on the server.** A `5xx` code says: the server made a mistake or could not carry out the request (`503` — "Service Unavailable", the service cannot answer right now). The first digit shows on whose side the error is,
and the exact code shows what happened. **A** is the `4xx` class; **C** — you can tell, that is exactly what the class is for.

## Sending a body: POST and Content-Length

Now the body is in the request itself. To add a new product the method is `POST`: it gives the server a body, and the server creates a new product from it. This body is the product's JSON.
Two headers tell the body's format and its size in bytes: `Content-Type` and `Content-Length`.

Here is the body:

```json
{"name":"oʻrik","price":3500000,"stock":5}
```

That is 42 characters: the curved mark (`ʻ`) in the letter `oʻ` of the word `oʻrik` ("plum") is also one character. Predict. The request header has `Content-Length`: it is the length of the body in **bytes**.
The body is 42 characters. What will `Content-Length` be?

**A)** 42 · **B)** 43 · **C)** 44

<details>
<summary>Answer</summary>

**B: 43.** `Content-Length` counts bytes, not characters, and `ʻ` takes two bytes in UTF-8 ([GB-2.10](/lab/youtube/gb/gb-2-10/en)). If you chose **A**, you treated characters and bytes as the same;
**C** — only one character is two bytes, not all of them. Let us check (this command is not in the course folder; `wc -m` counts characters in a UTF-8 locale, `wc -c` counts bytes):

```console
$ printf '{"name":"oʻrik","price":3500000,"stock":5}' | wc -m -c
     42      43
```

</details>

Here is the request. `-d` gives the body, `-H` adds a header: `Content-Type` says the body is JSON. Double quotes also wrap one argument. The server returned `201 Created`:

```console
$ curl -v -d '{"name":"oʻrik","price":3500000,"stock":5}' -H "Content-Type: application/json" http://localhost:8765/products
> POST /products HTTP/1.1
> Host: localhost:8765
> User-Agent: curl/8.22.0
> Accept: */*
> Content-Type: application/json
> Content-Length: 43
> 
< HTTP/1.1 201 Created
< Content-Type: application/json
< Location: /products/3
< Date: Fri, 27 Nov 2026 07:22:38 GMT
< Content-Length: 50
< 
{"id":3,"name":"oʻrik","price":3500000,"stock":5}
```

In the request: the first line is now `POST /products HTTP/1.1`, there are two new headers (`Content-Type`, `Content-Length: 43`), and after the empty line comes the body (curl does not show it with `>`).
In the response: `201 Created` — a new product was created. The `Location` header names the new product's path: `/products/3`. In the body the product now has an `id`: the server gave it itself.
The response's `Content-Length: 50`: there is `oʻ` here too, 49 characters and 50 bytes. In the video the `id` is 3, because the server had two products.

## The classic mistake: Content-Type forgotten

Predict. We send the same `POST` without `-H`: no header, the same JSON body. What does the server return?

**A)** `201 Created` · **B)** `4xx`: the error is in the request · **C)** `5xx`: the error is on the server

<details>
<summary>Answer</summary>

**B: `4xx`.** The body was right, the header was wrong: the server does not know which format arrived. If you chose **A**, you thought the server would guess — but it looks at `Content-Type`.
**C** — the server made no mistake in its own work, the request was wrong.

</details>

```console
$ curl -v -d '{"name":"oʻrik","price":3500000,"stock":5}' http://localhost:8765/products
> POST /products HTTP/1.1
> Host: localhost:8765
> User-Agent: curl/8.22.0
> Accept: */*
> Content-Length: 43
> Content-Type: application/x-www-form-urlencoded
> 
< HTTP/1.1 415 Unsupported Media Type
< Content-Type: application/json
< Date: Fri, 27 Nov 2026 07:22:38 GMT
< Content-Length: 57
< 
{"error":"Content-Type application/json boʻlishi kerak"}
```

Without `-H`, curl puts in a `Content-Type` itself: `application/x-www-form-urlencoded` — a format for sending form fields as `name=value`, not JSON. The server returns `415`: the body type
is not supported. It starts with `4`, so the error is in the request: the body was right, the header was not. In the response body the server wrote the reason.

The fix is `Content-Type: application/json` with `-H`. Now the server returns `201`. The server remembers the previous successful `POST`, so this time the `id` is 4 and `Location: /products/4`:

```console
$ curl -v -d '{"name":"oʻrik","price":3500000,"stock":5}' -H "Content-Type: application/json" http://localhost:8765/products
> POST /products HTTP/1.1
> Host: localhost:8765
> User-Agent: curl/8.22.0
> Accept: */*
> Content-Type: application/json
> Content-Length: 43
> 
< HTTP/1.1 201 Created
< Content-Type: application/json
< Location: /products/4
< Date: Fri, 27 Nov 2026 07:22:38 GMT
< Content-Length: 50
< 
{"id":4,"name":"oʻrik","price":3500000,"stock":5}
```

## Common mistakes

**1. "A response came back, so everything is fine."** Even if the error is `4xx` or `5xx`, the server sends a correct HTTP response: the connection worked, the text arrived. For curl this is a success:
it ends with exit code 0 even on `404`. Only with the `-f` (`--fail`) flag does curl return exit code 22 when the status code is an error. I ran both:

```console
$ curl -s http://localhost:8765/products/99; echo " chiqish kodi: $?"
{"error":"mahsulot topilmadi"} chiqish kodi: 0
$ curl -sf http://localhost:8765/products/99; echo "chiqish kodi: $?"
chiqish kodi: 22
```

(`-s` is silent mode: curl does not print its own progress messages.) The conclusion: look at the status code, not at the exit code or at "did a response come".

**2. Forgetting `-H "Content-Type: application/json"`.** The result is `415 Unsupported Media Type`; how to read and fix it is shown above, in the section "The classic mistake: Content-Type forgotten".

**3. Taking `Content-Length` for a character count.** The `oʻrik` product has 42 characters, but `Content-Length: 43`: the explanation is above, in the section "Sending a body: POST and Content-Length".

**4. Forgetting `Connection: close` in `printf | nc`.** `nc` keeps waiting even after the response; in the `timeout 3` example above the exit code is 124.

**5. Forgetting the line-ending `\r\n` in Go.** An HTTP line ends with `\r\n`. `strings.Split` does not remove them, so `Proto` stays `"HTTP/1.1\r\n"`. Here is the
wrong version of `parseRequestLine`: one line was removed from the function in `solution/main.go` — `line = strings.TrimRight(line, "\r\n")`; the rest of the file (`Request`, `statusClass`, `main`) is the same. This folder is not
in the course repository; I created it separately (`go.mod` and `tekshiruv_test.go` are the same as in the course):

```go
func parseRequestLine(line string) (Request, error) {
	parts := strings.Split(line, " ")
	if len(parts) != 3 {
		return Request{}, fmt.Errorf("soʻrov qatori uch qismdan iborat boʻlishi kerak, hozir %d: %q", len(parts), line)
	}
	method, path, proto := parts[0], parts[1], parts[2]
	if method == "" {
		return Request{}, errors.New("method boʻsh")
	}
	if !strings.HasPrefix(path, "/") {
		return Request{}, fmt.Errorf("yoʻl / bilan boshlanishi kerak: %q", path)
	}
	if !strings.HasPrefix(proto, "HTTP/") {
		return Request{}, fmt.Errorf("versiya HTTP/ bilan boshlanishi kerak: %q", proto)
	}
	return Request{Method: method, Path: path, Proto: proto}, nil
}
```

```go filename="solution/main.go" showLineNumbers
package main

import (
	"errors"
	"fmt"
	"strings"
)

// Request — HTTP soʻrovning birinchi qatoridan olingan uch qism (curl -v'dagi "> GET /products/1 HTTP/1.1").
type Request struct {
	Method string // "GET"
	Path   string // "/products/1"
	Proto  string // "HTTP/1.1"
}

// parseRequestLine "GET /products/1 HTTP/1.1" kabi qatorni qismlarga ajratadi (TASK.md, 1-qadam).
func parseRequestLine(line string) (Request, error) {
	line = strings.TrimRight(line, "\r\n") // HTTP qatori \r\n bilan tugaydi
	parts := strings.Split(line, " ")
	if len(parts) != 3 {
		return Request{}, fmt.Errorf("soʻrov qatori uch qismdan iborat boʻlishi kerak, hozir %d: %q", len(parts), line)
	}
	method, path, proto := parts[0], parts[1], parts[2]
	if method == "" {
		return Request{}, errors.New("method boʻsh")
	}
	if !strings.HasPrefix(path, "/") {
		return Request{}, fmt.Errorf("yoʻl / bilan boshlanishi kerak: %q", path)
	}
	if !strings.HasPrefix(proto, "HTTP/") {
		return Request{}, fmt.Errorf("versiya HTTP/ bilan boshlanishi kerak: %q", proto)
	}
	return Request{Method: method, Path: path, Proto: proto}, nil
}

// statusClass status kodi qaysi sinfga kirishini aytadi (TASK.md, 2-qadam).
func statusClass(code int) string {
	switch {
	case code >= 100 && code < 200:
		return "axborot"
	case code >= 200 && code < 300:
		return "muvaffaqiyat"
	case code >= 300 && code < 400:
		return "yoʻnaltirish"
	case code >= 400 && code < 500:
		return "mijoz xatosi"
	case code >= 500 && code < 600:
		return "server xatosi"
	}
	return "nomaʼlum"
}

func main() {
	req, err := parseRequestLine("GET /products/1 HTTP/1.1")
	if err != nil {
		fmt.Println("xato:", err)
		return
	}
	fmt.Println(req.Method, req.Path, req.Proto)
	fmt.Println(404, statusClass(404))
}
```

| 20–22 | `if len(parts) != 3 { … }` | if there are not exactly three parts — an error: the empty line, two and four parts and two spaces are caught here |
| 23 | `method, path, proto := parts[0], parts[1], parts[2]` | puts the three parts into named variables |
| 24–26 | `if method == "" { … }` | an error if the method is empty |
| 27–29 | `if !strings.HasPrefix(path, "/") { … }` | an error if the path does not start with `/` |
| 30–32 | `if !strings.HasPrefix(proto, "HTTP/") { … }` | an error if the version does not start with `HTTP/` |
| 33 | `return Request{…}, nil` | all fine: the three parts and a `nil` error |
| 38–50 | `switch { case code >= 100 && code < 200: … }` | a `switch` without an expression: the first condition that matches returns the class name; if none matches, the last `return "nomaʼlum"` |
