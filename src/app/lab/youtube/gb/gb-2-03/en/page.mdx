## What you will learn

In the first module, a product in bozor was three separate variables:

```go
name := "olma"
price := int64(1_200_000) // tiyin
stock := 40
```

Add a second product and three more appear:

```go
name2 := "non"
price2 := int64(400_000)
stock2 := 100
```

Only the digit `2` in the name says that `name2` and `price2` belong to one product. The compiler does not know about this link. How
do you gather one product into one value?

**The one idea:** a **struct** is a type whose fields sit side by side inside one value. A field that you leave out of a literal
gets the zero value of its type, and `q := p` copies every field: `q` is a separate value.

By the end of the lesson you will:

- declare a struct type with `type Product struct { … }`, read a field as `p.Name` and write it as `p.Stock = 40`;
- fill a struct value by field names (a struct literal) and print it with field names using `%+v`;
- say in advance what an omitted field becomes, and why changing `q` after `q := p` does not touch `p`;
- write an order status with `type OrderStatus int` and `iota`.

Today's three core new words:

| Word | Plain meaning | English term |
|---|---|---|
| struct | a type that gathers several named fields into one value: `type Product struct { … }` | struct |
| struct literal | writing a struct value in code with field names: `Product{Name: "non"}`; an omitted field gets its zero value | struct literal |
| iota | the line number inside a `const ( … )` block: it starts at 0 and grows by 1 on each line | iota |

Two helper ideas: `%+v` (prints a struct with field names) and `type OrderStatus int` (a new type based on `int`).

This lesson introduces new types: `Product`, `OrderItem`, `Order` and `OrderStatus`. They are the **domain types** of bozor, that is,
the concepts of a shop. The next lessons build on them.

## The problem: three variables are not one product

The six variables above are not connected to each other. With ten products you track thirty variables, thirty names and the digits
at the end of the names yourself. To pass a product to a function, you write three parameters for three values. What you need is to
gather the name, the price and the stock into **one** value.

Today we do three things:

1. **struct** — a type that gathers several named fields into one value;
2. **struct literal and zero value** — filling a value by field names;
3. **iota** — consecutively numbered constants for order statuses.

## Struct: named fields, one value

There is a keyword `type` for declaring a new type. `type Product struct { … }` reads: "a new type `Product`, its shape is a list
of fields". A **field** is a name and its type. The first program (`_video/01-product/main.go`):

```go filename="_video/01-product/main.go" showLineNumbers
package main

import "fmt"

// Product — katalogdagi bitta mahsulot.
type Product struct {
	ID    int64
	Name  string
	Price int64 // tiyin
	Stock int
}

func main() {
	p := Product{ID: 1, Name: "olma", Price: 1_200_000, Stock: 40}
	fmt.Println(p.Name, p.Price)
	fmt.Printf("%+v\n", p)
}
```

Lines 1–3 are familiar from GB-1.01 (`package main`, `import "fmt"`), line 13 is `func main()`. The new lines:

| Line | Code | What it does |
|---|---|---|
| 5 | `// Product — katalogdagi bitta mahsulot.` | a comment (GB-1.03) that says what the type is ("`Product` — one product of the catalog") |
| 6 | `type Product struct {` | `type` declares a new type named `Product`. `struct` is the shape of the type: a list of fields inside curly braces. It ends with the `}` on line 11 |
| 7 | `ID    int64` | a field: first the **name** (`ID`, the product number), then the **type** (`int64`, GB-1.03) |
| 8 | `Name  string` | `Name` is the product name, text |
| 9 | `Price int64 // tiyin` | `Price` is the price, in tiyin as in GB-1.03 |
| 10 | `Stock int` | `Stock` is the quantity in the warehouse |
| 14 | `p := Product{ID: 1, Name: "olma", Price: 1_200_000, Stock: 40}` | a **struct literal**: `Product`, then inside curly braces `Field: value` pairs separated by commas. The result goes into the variable `p` (`:=`, GB-1.02) |
| 15 | `fmt.Println(p.Name, p.Price)` | `p.Name` reads the `Name` field of `p`: the dot selects a field. `tc.name` in GB-1.08 worked the same way. `Println` prints two values separated by a space |
| 16 | `fmt.Printf("%+v\n", p)` | `%+v` prints the whole struct; the `+` flag adds the field name before each value |

Two notes. First: the columns (`ID    int64`, `Name  string`) are aligned by `go fmt` (GB-1.01); the alignment means nothing to Go.
Second: the names of the type and of the fields start with a capital letter. The reason is explained by
[GB-2.06 · Paketlar: katta harf, internal/ va loyiha tuzilishi](/lab/youtube/gb/gb-2-06/en); for now, just write them this way.

## An omitted field: zero value

Now in the variable `n` we do not write two fields: bread, price 400 000 tiyin. `ID` and `Stock` are missing

<details>
<summary>Answer</summary>

**A.** The code compiles and all four fields are printed. A field omitted from the literal gets the **zero value** of its type:

## In memory: a struct is one value, `q := p` is a copy

Let us follow the code in memory (`_video/03-nusxa/main.go`, the body of `main`):

```go
p := Product{ID: 1, Name: "olma", Price: 1_200_000}
p.Stock = 40
q := p
q.Stock = 0
fmt.Println(p.Stock, q.Stock)
```

When the literal has run, the label `p` is attached to **one** value with four fields. The fields sit side by side inside that value;
they are not separate variables. `Stock` is omitted, so it is `0`.

```text
p ──▶ ┌───────────────────┐
      │ ID     1          │
      │ Name   "olma"     │
      │ Price  1200000    │
      │ Stock  0          │
      └───────────────────┘   ← one value, four fields
```

The second line **writes** one field through the dot: `p.Stock = 40`; the other three fields do not change. Then `q := p`: `:=`
declares a new variable (GB-1.02). After that the `Stock` of `q` becomes `0`. Which two numbers appear on the screen?

**A)** `0 0` · **B)** `40 0` · **C)** `40 40`

<details>
<summary>Answer</summary>

**B: `40 0`.** `q := p` **copies the whole struct**: `q` gets its own separate value with four fields. `q.Stock = 0` changes
only `q`, and `p` keeps `40`. If you chose **A**, you thought `q` and `p` are two names of one value: no, after the copy there are
two values. If you chose **C**, you thought the line `q.Stock = 0` did not work at all: it worked, in `q`.

</details>

Memory after each line:

| Line | Code | `p` | `q` | Screen |
|---|---|---|---|---|
| 1 | `p := Product{ID: 1, Name: "olma", Price: 1_200_000}` | `{ID:1 Name:olma Price:1200000 Stock:0}` | — | |
| 2 | `p.Stock = 40` | `{ID:1 Name:olma Price:1200000 Stock:40}` | — | |
| 3 | `q := p` | `{… Stock:40}` | `{ID:1 Name:olma Price:1200000 Stock:40}` — a **new** value, a copy of four fields | |
| 4 | `q.Stock = 0` | `{… Stock:40}` | `{… Stock:0}` | |
| 5 | `fmt.Println(p.Stock, q.Stock)` | | | `40 0` |

```console
$ ./_video/run.sh 03-nusxa go run .
40 0
```

When a struct is passed to a function as an argument, it is copied in the same way: the function works with its own copy
([Go spec: Calls](https://go.dev/ref/spec#Calls), [Go FAQ: pass by value](https://go.dev/doc/faq#pass_by_value)). If one product
must be changed from several places, you need a pointer: it is explained by
[GB-2.04 · Pointer: nusxa yoki umumiy qiymat](/lab/youtube/gb/gb-2-04/en).

**One caution.** If a field is a slice, `=` copies only the **header** of the slice (the length, the capacity and the reference to
the array); the elements stay in the shared array, as in GB-2.01. Let us check: the next program is **not** in the course folder,
we ran it in a separate folder (`Order` is shortened here; it is written in full in the next section):

```go
package main

import "fmt"

// OrderItem — buyurtmadagi bitta qator.
type OrderItem struct {
	ProductID int64
	Price     int64 // tiyin, buyurtma paytidagi narx
	Quantity  int
}

// Order — bitta buyurtma.
type Order struct {
	ID    int64
	Items []OrderItem
}

func main() {
	a := Order{ID: 1, Items: []OrderItem{{ProductID: 1, Price: 1_200_000, Quantity: 3}}}
	b := a
	b.ID = 2
	b.Items[0].Quantity = 99
	fmt.Println(a.ID, b.ID)
	fmt.Println(a.Items[0].Quantity, b.Items[0].Quantity)
}
```

```console
$ go run .
1 2
99 99
```

The field `ID` was copied: `1 2`. But `b.Items[0].Quantity = 99` changed `a` too, because `a.Items` and `b.Items` look at one array:
`99 99`. The rule: a struct is copied, but the elements of a slice inside it are not.

## The order types: `OrderItem` and `Order`

Each line of an order is an `OrderItem`: which product, how many, and at what price.

```go
// OrderItem — buyurtmadagi bitta qator.
type OrderItem struct {
	ProductID int64
	Price     int64 // tiyin, buyurtma paytidagi narx
	Quantity  int
}
```

- `ProductID` is the **ID** of the product, not the product itself. The line holds no `Product` value, only the number that points to it.
- `Price` is the price of **this line**. This is a decision of bozor: the price is copied from the product at the moment of the order.
  If the product price changes later, the total of the old order does not change.
- `Quantity` is the number of units on this line.

`Order` has three fields:

```go
// Order — bitta buyurtma.
type Order struct {
	ID     int64
	Items  []OrderItem
	Status OrderStatus
}
```

- `ID` is the order number;
- `Items` has the type `[]OrderItem`: a slice of `OrderItem` (GB-2.01). The type of a field can be a slice or another struct;
- `Status` has the type `OrderStatus`: we write it right now.

`Order` comes **before** `OrderStatus`, yet the code compiles: the order of file-level declarations does not matter to Go
([Go spec: Declarations and scope](https://go.dev/ref/spec#Declarations_and_scope)). The `main.go` in the folder has exactly this order.

## Status: `type OrderStatus int` and `iota`

An order has four statuses: new, paid, shipped and cancelled. We store them as numbers and write them in code as names:

```go
// OrderStatus — buyurtma holati.
type OrderStatus int

const (
	StatusNew OrderStatus = iota
	StatusPaid
	StatusShipped
	StatusCancelled
)
```

| Line | Code | What it does |
|---|---|---|
| 1 | `// OrderStatus — buyurtma holati.` | a comment ("`OrderStatus` — the order status") |
| 2 | `type OrderStatus int` | a **new type** based on `int`: inside it is an ordinary number, and the name says the number is a status |
| 4 | `const (` | `const` with parentheses (GB-1.03) declares several constants in one block |
| 5 | `StatusNew OrderStatus = iota` | `iota` is the line number inside this block, counted **from zero**. `StatusNew` has the type `OrderStatus` and the value `0` |
| 6–8 | `StatusPaid` and the rest | on a line without an expression, both the type and `= iota` are **repeated**, only `iota` grows by 1 |

The result:

| Constant | `iota` | Value |
|---|---|---|
| `StatusNew` | 0 | `0` |
| `StatusPaid` | 1 | `1` |
| `StatusShipped` | 2 | `2` |
| `StatusCancelled` | 3 | `3` |

This is a Go rule: [Go spec: Iota](https://go.dev/ref/spec#Iota) and [Constant declarations](https://go.dev/ref/spec#Constant_declarations)
(a line without an expression repeats the previous one).

**`OrderStatus` is a separate type.** A **variable** of type `int` cannot be used in place of `OrderStatus`. We checked this: the next
program is **not** in the course folder, we ran it in a separate folder.

```go
package main

import "fmt"

// OrderStatus — buyurtma holati.
type OrderStatus int

const (
	StatusNew OrderStatus = iota
	StatusPaid
	StatusShipped
	StatusCancelled
)

func main() {
	n := 1
	var s OrderStatus = n
	fmt.Println(s)
}
```

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:17:22: cannot use n (variable of type int) as OrderStatus value in variable declaration
```

The error: line 17, column 22, `n` (a variable of type `int`) cannot be used as an `OrderStatus` value. But a **constant** is
accepted by the compiler, even `99`, which is not in the list. Replace the `main` function of the program above with the following one
(we ran it this way):

```go
func main() {
	var s OrderStatus = 99
	fmt.Println(s, s == StatusCancelled)
}
```

```console
$ go run .
99 false
```

So this type does not reject an invalid status: the type is a name and a checked variable, not a list of values
([Go spec: Assignability](https://go.dev/ref/spec#Assignability)). We write the check of the value ourselves in later lessons.

## Putting it together: we build an order

Now in `main` we build an order in three steps. This is the `main.go` of the folder: its lines 1–49 are identical to `_video/04-order/main.go`.

<details>
<summary>Answer</summary>

**A: `true 0`.** An `Order` with the zero value is a new order, because `StatusNew` equals zero. `Items` is a nil slice: its length
is `0`, and there is no panic ([Go spec: The zero value](https://go.dev/ref/spec#The_zero_value),
[Length and capacity](https://go.dev/ref/spec#Length_and_capacity)). If you chose **B**, you thought `Status` is a "not chosen" status:
in Go it is `0`, the first constant of the list. **C** — taking the length of a nil slice does not panic; a panic would come from

</details>

In the first line, `Items` is the only element of the slice inside square brackets, with its own curly braces. `Status:0`: `%+v`
writes the number of the status; printing the name (the `String()` method) comes in

the zero value is a meaningful status, a new order.

| Field | Value in `empty` | Why |
|---|---|---|
| `ID` | `0` | the zero value of `int64` |
| `Items` | `nil`, `len` 0 | the zero value of a slice |
| `Status` | `0` = `StatusNew` | the base of `OrderStatus` is `int`, whose zero value is `0` |

## Going deeper (optional): inserting a value in the middle of an `iota` list

Statuses are stored as numbers: they are written to a file or a database (we do this in modules 3 and 5). Imagine that someone added
a new status after `StatusNew`: `StatusReserved`, "reserved" (`_video/06-iota/main.go`):

```go
const (
	StatusNew OrderStatus = iota
	StatusReserved
	StatusPaid
	StatusShipped
	StatusCancelled
)

func main() {
	fmt.Println(StatusPaid, StatusShipped)
}
```

What are `StatusPaid` and `StatusShipped` equal to now?

**A)** `1 2`, as before · **B)** `2 3` · **C)** a compile error

<details>
<summary>Answer</summary>

**B: `2 3`.** `iota` is the line number, so `StatusReserved` took 1, and every constant after it moved up by one.
If you chose **A**, you thought a constant keeps its number together with its name: the number is counted from the place in the list.
**C** — the code is valid, and the compiler does not treat this change as an error.

</details>

```console
$ ./_video/run.sh 06-iota go run .
2 3
```

The consequence: a "paid" order stored in the database as `1` is now read as "reserved". The compiler and `go vet` are silent.
The rule: **a new value is added to a stored `iota` list only at the end.** Other ways: write the number explicitly on each constant
(`StatusPaid OrderStatus = 1`) or store the name of the status in the database. In the course folder, `TestHolatRaqamlari` in
`tekshiruv_test.go` pins the numbers `0, 1, 2, 3` for this reason: if you insert a value in the middle of the list, the test fails.

## Common mistakes

**1. A literal without field names.** A literal can also be written without names: the values go into the fields in the order of the
declaration. Here there are three values and `Stock` is missing (`_video/05-xato/main.go`, line 14):

```go
p := Product{1, "olma", 1_200_000}
```

```console
$ ./_video/run.sh 05-xato go run .
# github.com/abdurahmon27/bozor
./main.go:14:35: too few values in struct literal of type Product
```

How to read it: `./main.go:14:35` is file, line, column. Line 14, column 35 is the closing `}` of the literal. The message: `too few values in
struct literal of type Product`. In a literal without names, **every** field must be written, in order
([Go spec: Composite literals](https://go.dev/ref/spec#Composite_literals)).

If you write four values, the code compiles: replace line 14 in `_video/05-xato/main.go` with the following (we ran it this way):

```go
p := Product{1, "olma", 1_200_000, 40}
```

```console
$ go run .
{ID:1 Name:olma Price:1200000 Stock:40}
```

But on the day a fifth field (`Category string`) is added to `Product`, every such line breaks. A literal with field names does not
change: the new field gets its zero value. The next program shows both side by side (it is not in the course folder):

```go
package main

import "fmt"

// Product — katalogdagi bitta mahsulot.
type Product struct {
	ID       int64
	Name     string
	Price    int64 // tiyin
	Stock    int
	Category string
}

func main() {
	p := Product{1, "olma", 1_200_000, 40}
	fmt.Printf("%+v\n", p)
	q := Product{ID: 1, Name: "olma", Price: 1_200_000, Stock: 40}
	fmt.Printf("%+v\n", q)
}
```

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:15:39: too few values in struct literal of type Product
```

Line 15 (`p := …`) broke, and line 17 (`q := …`) is fine. So write the field names.

**2. `q := p` is two values, not two names.** The most common wrong picture: after `q := p`, changing `q` changes `p` too. No: look at
the table in the section "In memory: a struct is one value, `q := p` is a copy", it gives `40 0`. Here the program does not crash,
the result is simply different from the expected one. If one value must be changed from two places, you need a pointer
([GB-2.04](/lab/youtube/gb/gb-2-04/en)). Also remember that the elements of a slice are not copied (`99 99`).

**3. Reading the zero value as "no value was given".** The zero value of `Stock` is `0`, not "unknown". A struct does not tell a
product with `Stock: 0` written from a product with `Stock` omitted: both have `0`. For a new product this is meaningful, but not
for every field: check yourself that the zero value of a field is meaningful in your domain. This is why `StatusNew` is placed on `0`
in `OrderStatus`.

<summary>Hints and explanation of the answer</summary>

Hints (from TASK.md):

- `o.Items` is a slice: `for _, it := range o.Items { … }` gives each line to `it` (like `for _, tc := range tests` in GB-1.08).
- `it.Price` is `int64`, `it.Quantity` is `int`: convert with `int64(it.Quantity)` before multiplying (GB-1.07). For the sum use
  `var total int64` and `+=` (GB-1.06).
- `canCancel` is written with one `return`: two `==` comparisons and `||` (GB-1.05).

The answer (`solution/main.go`, two functions):

```go
func orderTotal(o Order) int64 {
	var total int64
	for _, it := range o.Items {
		total += it.Price * int64(it.Quantity)
	}
	return total
}

func canCancel(o Order) bool {
	return o.Status == StatusNew || o.Status == StatusPaid
}
```

Explanation: on each line `orderTotal` multiplies the price by the quantity and adds it to `total`. `Quantity` is `int` and `Price` is
`int64`; Go does not mix types by itself, so `int64(it.Quantity)`. In an order without lines the loop does not run and `total` stays at
its zero value, that is `0`. `canCancel` compares `Status` with two constants using `==`; `||` means "or". For an order with the zero
value, `Status` is `StatusNew`, so the result is `true`. You can check the answer from the folder itself:
