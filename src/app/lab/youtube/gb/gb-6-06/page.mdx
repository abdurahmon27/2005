## Nimani oʻrganasiz

Dilnoza login qildi va `GET /orders/41` bilan oʻz buyurtmasini oldi. Yoʻldagi `41`ni `42`ga almashtirsa, server kimning buyurtmasini qaytaradi?

**Bitta gʻoya:** login faqat **kim** soʻrayotganini aytadi. **Ruxsat** alohida savol, va buyurtmaga tegadigan **har** soʻrov uni oʻzi berishi kerak. Obyekt darajasida javob SQL shartining oʻzida: `WHERE id = $1 AND user_id = $2`. `$1` mijozdan keladi (yoʻldagi ID), `$2` serverdan (session egasi). Funksiya darajasida javob — rol: `requireAdmin`.

Dars oxirida siz:

- login qilgan foydalanuvchi begona buyurtmani olishini qayta yaratib, yopasiz;
- begona va mavjud boʻlmagan buyurtmaga bir xil `404` qaytarasiz, toʻliq sababni esa faqat server logiga yozdirasiz;
- shu xatoni ushlaydigan testni eski kodda FAIL, yangi kodda ok qilib koʻrasiz;
- `users.role` ustuni va `requireAdmin` middlewareʼi bilan admin yoʻlini yopasiz, `PATCH /orders/{id}`dagi shu xatoni oʻzingiz tuzatasiz.

| Soʻz | Oddiy maʼnosi | Inglizcha |
|---|---|---|
| avtorizatsiya | «shu amalga ruxsatingiz bormi?» tekshiruvi | authorization |
| BOLA | aynan shu buyurtmaga (obyektga) ruxsat tekshirilmagan xato | Broken Object Level Authorization |
| rol | foydalanuvchiga ochiq amallar guruhi (`xaridor`, `admin`) | role |

Yordamchi soʻzlar shu yerning oʻzida izohlanadi: **autentifikatsiya** (authentication), **BFLA** (funksiya darajasidagi xato), **mass assignment**.

## Kimsiz? Va shu ishga ruxsatingiz bormi? — ikki savol

Birinchi savol — **autentifikatsiya** (authentication): «siz kimsiz?». bozorda uni `requireUser` beradi: cookie → session → foydalanuvchi context'da. Javob topilmasa, `401 Unauthorized`.

Ikkinchi savol — **avtorizatsiya** (authorization): «shu ishga ruxsatingiz bormi?». Ruxsat boʻlmasa, odatda `403 Forbidden`. Login qilgan foydalanuvchiga hamma narsa ruxsat degani emas. bozor ikkinchi savolni hozircha hech qayerda bermaydi.

| Qadam | Savol | Yoʻq boʻlsa | Kim beradi |
|---|---|---|---|
| 1 | session yaroqlimi? (kim?) | `401` | `requireUser` (GB-6.04) |
| 2 | bu buyurtma siznikimi? | `404` | SQL sharti, bugun yoziladi |
| 3 | bu amal sizning rolingizga ochiqmi? | `403` | `requireAdmin`, bugun yoziladi |

## Muammo: egasi bazada bor, soʻrovda yoʻq

Har buyurtmaning egasi bazada allaqachon yozilgan: oltinchi migratsiya `orders` jadvaliga `user_id` ustunini qoʻshdi. Mana shu fayl (`--` bilan boshlanadigan qatorlar — izoh, `+goose Up` va `+goose Down` — goosening qoʻllash va qaytarish boʻlimlari):

```sql filename="migrations/00006_orders_owner.sql" showLineNumbers
-- +goose Up
-- Har buyurtmaning egasi bor (GB-6.06): orders.user_id → users.id. Avvalgi customer matni kerak emas:
-- buyurtma kimniki ekanini endi session aytadi, mijoz yozgan ism emas.
-- NOT NULL default'siz qoʻshish faqat boʻsh jadvalda ishlaydi (laboratoriyada orders boʻsh, seed.sql keyin
-- toʻldiradi). Qatorlari bor bazada: avval ustun NULL bilan, eski qatorlarga egasi yoziladi, keyin SET NOT NULL.
ALTER TABLE orders
    ADD COLUMN user_id bigint NOT NULL REFERENCES users (id),
    DROP COLUMN customer;
-- "Shu foydalanuvchining buyurtmalari" (WHERE user_id = …) jadvalni oxirigacha oʻqimasin.
CREATE INDEX orders_user_id_idx ON orders (user_id);

-- +goose Down
DROP INDEX orders_user_id_idx;
ALTER TABLE orders
    ADD COLUMN customer text NOT NULL DEFAULT '',
    DROP COLUMN user_id;
```

| Qator | Nima qiladi |
|---|---|
| 6–8 | bitta `ALTER TABLE`da vergul bilan ikki amal: `user_id` qoʻshadi (`NOT NULL`, `users.id`ga tashqi kalit — GB-5.04), eski `customer` matnini oʻchiradi: kim ekanini endi session aytadi |
| 10 | `CREATE INDEX` `user_id` boʻyicha indeks yaratadi: bitta foydalanuvchining buyurtmalari jadvalni toʻliq oʻqimay topiladi |
| 12–16 | `Down`: indeksni oʻchiradi, `customer`ni boʻsh matn bilan qaytaradi (eski matn tiklanmaydi) |

`NOT NULL`ni `DEFAULT`siz qoʻshish faqat **boʻsh** jadvalda ishlaydi — GB-5.06dagi xato shu edi. Laboratoriyada `orders` boʻsh, `seed.sql` keyin toʻldiradi. Ishlab turgan bazada bu bir fayl emas, bir necha reliz: avval ustun `NULL` bilan va `NOT VALID` tashqi kalit bilan qoʻshiladi, keyin cheklov tasdiqlanadi; eski qatorlarga egasini biznes qarori bilan yozasiz (erkin `customer` matnini `users.id`ga avtomatik moslab boʻlmaydi); `SET NOT NULL` tasdiqlangan `CHECK` orqali; indeks `CREATE INDEX CONCURRENTLY` bilan; eski ustun keyingi relizda oʻchadi. Bosqichlar dars papkasining README faylida.

```go

func (a *api) getOrder(w http.ResponseWriter, r *http.Request) {
```

Birinchi qator: `GET /orders/{id}` yoʻli `getOrder`ga ulangan, tashqi `requireUser` cookiesiz soʻrovni handlerga yetkazmaydi (GB-5.10). `pathID` yoʻldagi `{id}`ni songa aylantiradi, son boʻlmasa `400` (GB-4.08). Oxirgi qator storedan shu IDʼli buyurtmani oladi. Store soʻrovi:

```sql
SELECT user_id, status, note FROM orders
WHERE id = $1
```

Birinchi qator `user_id`, `status`, `note` ustunlarini tanlaydi; `note` — yetkazish izohi, odatda uy manzili. Ikkinchi qator shart: `id` `$1`ga teng. Soʻrovchi kimligi shartda yoʻq.

Dilnoza login qilgan, uning ID'si 1. U `GET /orders/42` yuboradi; 42-buyurtma Jasurniki. Javob qanday? **A)** `401`: avval login qiling · **B)** `403`: ruxsat yoʻq · **C)** `200`: Jasurning buyurtmasi.

<details>
<summary>Javob</summary>

**C.** Cookie bor, session tirik, `requireUser` Dilnozani oʻtkazdi: `401` kimlik tekshiruvidan chiqardi, bu yerda kimlik toʻgʻri. `403` uchun kodda ruxsat tekshiruvi boʻlishi kerak edi — u yoʻq. Qator bazada bor, shartga mos, demak qaytadi.

</details>

Ikkinchi javob — `200`: Jasurning buyurtmasi, uy manzili va jami summa (tiyinda) bilan. Bu xato. Har qadam nimani tekshirdi:

| Qadam | Nima boʻldi | Tekshirilmadi |
|---|---|---|
| `requireUser` | cookie → session → Dilnoza context'ga | buyurtma kimniki |
| `getOrder` | yoʻldagi `42` → store | soʻrovchining ID'si |
| `WHERE id = $1` | 42 topildi → javob | 42 kimniki? |

OWASP API Security Top 10 (2023) roʻyxatida bu **birinchi** band: **Broken Object Level Authorization**, qisqacha **BOLA**. OWASP Authorization Cheat Sheet uni Insecure Direct Object Reference (**IDOR**)ning bir koʻrinishi deydi. ID'lar ketma-ket: hujumchi 43, 44 va keyingilarini ham sinaydi. OWASP qoidasi: mijozdan kelgan ID bilan bazadagi yozuvga tegadigan **har** funksiya foydalanuvchining shu amalga ruxsatini tekshirsin, va buni testlar bilan mahkamlansin.

## Tuzatish: egalik sharti SQLʼning oʻzida

Serverni toʻxtating va saqlangan tuzatilgan fayllarni qaytaring:

```bash
cp handlers.fixed cmd/api/handlers.go
cp orders.fixed internal/store/orders.go
```

Tuzatish soʻrovning oʻzida, bitta yangi qator:

```sql
SELECT user_id, status, note FROM orders
WHERE id = $1
  AND user_id = $2
```

`AND` ikkala shart ham rost boʻlsagina qator topiladi. `$1` — mijoz yuborgan ID (yoʻldan), `$2` — soʻrovchining, ya'ni session egasining ID'si (serverdan). Mijoz `$2`ni tanlay olmaydi. Mana store metodi:

```go
func (s *Store) Order(ctx context.Context, id, userID int64) (Order, error) {
	o := Order{ID: id, Items: []OrderItem{}}
	var note *string // orders.note NULL boʻlishi mumkin: NULL → nil
	err := s.pool.QueryRow(ctx, `
		SELECT user_id, status, note FROM orders
		WHERE id = $1
		  AND user_id = $2`,
		id, userID).Scan(&o.UserID, &o.Status, &note)
	if errors.Is(err, pgx.ErrNoRows) {
		return Order{}, fmt.Errorf("buyurtma %d, foydalanuvchi %d: %w", id, userID, ErrOrderNotFound)
	}
	if err != nil {
		return Order{}, err
	}
	if note != nil {
		o.Note = *note
	}
	rows, err := s.pool.Query(ctx,
		"SELECT product_id, quantity, unit_price FROM order_items WHERE order_id = $1 ORDER BY id", id)
	if err != nil {
		return Order{}, err
	}
	defer rows.Close()
	for rows.Next() {
		var it OrderItem
		if err := rows.Scan(&it.ProductID, &it.Quantity, &it.UnitPrice); err != nil {
			return Order{}, err
		}
		o.Items = append(o.Items, it)
		o.Total += it.UnitPrice * int64(it.Quantity)
	}
	if err := rows.Err(); err != nil {
		return Order{}, err
	}
	return o, nil
}
```

| Qator | Nima qiladi |
|---|---|
| 1 | metod `id` va `userID`ni oladi; `int64` ikkalasiga bir marta yozilgan (`id, userID int64`) |
| 2 | `o` — qaytariladigan buyurtma |
| 3 | `note` — `*string`: ustun `NULL` boʻlsa `nil` qoladi (GB-2.04) |
| 4–8 | `QueryRow` soʻrovni bajaradi (GB-5.05): shart — yuqoridagi `WHERE id = $1 AND user_id = $2`; `$1` ← `id`, `$2` ← `userID`; `Scan` ustunlarni `o` va `note`ga yozadi |
| 9–11 | qator topilmasa `pgx.ErrNoRows`; uni `ErrOrderNotFound`ga oʻraymiz (`%w`, GB-5.10). Begona buyurtmada ham xuddi shu: shart yolgʻon, qator yoʻq |
| 12–14 | boshqa xato — oʻz holicha qaytadi |
| 15–36 | oldingi darslardagidek: `note` bor boʻlsa koʻchiradi, buyurtma qatorlarini oʻqib jami summani hisoblaydi |

Handler egani `currentUser`dan oladi (GB-6.04):

```go
func (a *api) getOrder(w http.ResponseWriter, r *http.Request) {
	id, ok := pathID(w, r)
	if !ok {
		return
	}
	o, err := a.st.Order(r.Context(), id, currentUser(r).ID)
	if err != nil {
		writeError(w, err)
		return
	}
	writeJSON(w, http.StatusOK, o)
}
```

6-qator oʻzgardi: `currentUser(r).ID` — session egasi. ID mijozdan keladi (2-qator, yoʻldan), ega esa sessiondan: mijoz uni tanlay olmaydi. Store endi egasiz chaqirilmaydi: imzo `userID`ni talab qiladi. Lekin ikkala parametr ham `int64`, ularning tartibini almashtirib yozish kompilyatsiya xatosi emas — tartibni test tekshiradi.

Serverni qayta ishga tushiring. Dilnoza ikki soʻrov yuboradi: Jasurning 42-buyurtmasi va umuman yoʻq 999-buyurtma. Javoblar qanday farq qiladi? **A)** `42` → `403`, `999` → `404` · **B)** ikkalasi bir xil `404` · **C)** `42` → `404`, `999` → `400`.

<details>
<summary>Javob</summary>

**B.** Ikkala soʻrovda ham shartga mos qator yoʻq, store ikkalasida `ErrOrderNotFound` qaytaradi. A javobni tanlasangiz, «bor, lekin sizniki emas» (`403`) deb oʻyladingiz — pastda nega bu xavfli ekani. C: `999` toʻgʻri son, `pathID` uni qabul qiladi, shuning uchun `400` emas.

</details>

Ikkalasi `404 Not Found`, bir xil matn «bunday buyurtma yoʻq»; farq faqat `request_id`da (har soʻrovga alohida beriladi, GB-6.01).

**Nega `403` emas?** `403` «bu buyurtma bor, lekin sizniki emas» deydi. Shunda hujumchi ID'larni birma-bir sinab, qaysi buyurtmalar borligini bilib oladi. [RFC 9110 §15.5.4](https://www.rfc-editor.org/rfc/rfc9110#name-403-forbidden) buni aniq aytadi: resurs borligini yashirmoqchi boʻlgan server `403` oʻrniga `404` qaytarishi mumkin («MAY»). Bu bozorning tanlovi, hamma API uchun majburiy qoida emas. Shuni ham bilib qoʻying: ketma-ket ID'lar buyurtmalar *sonini* baribir ochadi — `404` buni yashirmaydi (Chuqurroq boʻlimiga qarang).

Tafsilot esa server logida (birinchi terminal): qaysi buyurtmani qaysi foydalanuvchi soʻraganini koʻrasiz. Bu GB-6.02dagi ikki yoʻl: mijozga xavfsiz matn, logga toʻliq xato. Faqat `xato` qatorlarini olamiz:

```console

2026/11/28 11:15:22 BBSKMXA7MJX34EUFPSDY4XARRX xato 404: "buyurtma 999, foydalanuvchi 1: buyurtma topilmadi"
```

`buyurtma` — order, `foydalanuvchi` — user, `topilmadi` — not found. Log «foydalanuvchi 1 buyurtma 42ni soʻradi» deydi; u begona buyurtma bilan yoʻq buyurtmani oʻzicha ajratmaydi, ikkala qator bir xil shaklda.

## Rol: ruxsatning ikkinchi qavati

Obyekt darajasi «bu buyurtma sizniki?»ni hal qildi. Ikkinchi qavat — funksiya darajasi: baʼzi amallar faqat admin uchun. Yettinchi migratsiya `users`ga `role` ustunini qoʻshadi:

```sql filename="migrations/00007_users_role.sql" showLineNumbers
-- +goose Up
-- Rol (GB-6.06): oddiy xaridor yoki admin. Yangi foydalanuvchi har doim xaridor: eng kam huquq
-- (OWASP Authorization Cheat Sheet, "Enforce Least Privileges"). Admin'ni faqat baza egasi tayinlaydi.
ALTER TABLE users
    ADD COLUMN role text NOT NULL
    DEFAULT 'xaridor'
    CHECK (role IN ('xaridor', 'admin'));

-- +goose Down
ALTER TABLE users DROP COLUMN role;
```

| Qator | Nima qiladi |
|---|---|
| 4–7 | `ALTER TABLE users` majburiy matn ustuni `role`ni qoʻshadi; `DEFAULT 'xaridor'` mavjud va yangi foydalanuvchiga `xaridor` beradi; `CHECK (role IN ('xaridor', 'admin'))` faqat shu ikki qiymatga ruxsat beradi |
| 9–10 | `Down`: ustunni oʻchiradi |

Yangi roʻyxatdan oʻtgan foydalanuvchi har doim `xaridor`: OWASP buni eng kam huquq (least privilege) deydi. Admin faqat bazada tayinlanadi. `store.User`da endi `Role` maydoni bor, `UserBySession` uni ham oʻqiydi. Yangi `cmd/api/authz.go`:

```go filename="cmd/api/authz.go" showLineNumbers
package main

// Authorization — «nima qila olasiz» (GB-6.06). Authentication (requireUser, auth.go) faqat kim ekaningizni
// aniqlaydi. Ruxsatning ikki qavati:
//
//	obyekt   «bu buyurtma sizniki?» — har store metodida, SQL shartida: WHERE id = $1 AND user_id = $2.
//	         Begona buyurtma → 404, xuddi yoʻq buyurtma kabi (RFC 9110 §15.5.4: mavjudligini yashirish).
//	funksiya «bu amal sizning rolingizga ochiq?» — requireAdmin middleware'i, /admin/… route'larida → 403.
//
// OWASP API Security Top 10 2023: API1 Broken Object Level Authorization, API5 Broken Function Level Authorization.

import (
	"errors"
	"net/http"

	"github.com/abdurahmon27/bozor/internal/store"
)

// errForbidden — foydalanuvchi kim ekani maʼlum, lekin bu amal uning roliga ruxsat etilmagan (problemFor → 403).
var errForbidden = errors.New("bu amal uchun ruxsat yoʻq")

// requireAdmin — faqat admin rolidagi foydalanuvchini oʻtkazadi, qolganlarga 403.
// requireUser'ning ICHIDA turishi shart: foydalanuvchini context'ga requireUser qoʻyadi.
// Tashqarida tursa currentUser panic qiladi → 500 (GB-6.04): jim oʻtkazib yuborishdan xavfsizroq.
func requireAdmin(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if currentUser(r).Role != store.RoleAdmin {
			writeError(w, errForbidden)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

| Qator | Nima qiladi |
|---|---|
| 1 | `package main` — `cmd/api`dagi boshqa fayllar bilan bir paket |
| 3–10 | izoh: ruxsatning ikki qavati va OWASP bandlari |
| 12–17 | importlar: `errors`, `net/http` va `store` paketi (rol konstantasi uchun) |
| 19–20 | `errForbidden` — oddiy xato qiymati; `problemFor` (GB-6.02) uni `403 Forbidden`ga aylantiradi |
| 22–24 | izoh: `requireAdmin` `requireUser`ning **ichida** turishi shart |
| 25 | `requireAdmin` — GB-6.01dagi middleware shakli: handler oladi, handler qaytaradi |
| 26 | qaytariladigan handler funksiyasi (closure) |
| 27 | `currentUser(r).Role` admin emasmi? `store.RoleAdmin` qiymati `"admin"` |
| 28–30 | admin emas: `errForbidden` yoziladi va `return` |
| 31 | admin: `next.ServeHTTP` keyingi handlerni chaqiradi |
| 32–33 | ikkala funksiya yopiladi |

## Chuqurroq (ixtiyoriy): body'dagi `user_id` va ketma-ket ID

Dilnoza `POST /orders` bodyʼsiga `"user_id":2` qoʻshib, buyurtmani Jasur nomidan yozmoqchi. Nima boʻladi? **A)** buyurtma Jasurniki · **B)** buyurtma Dilnozaniki · **C)** `400`: nomaʼlum kalit.

<details>
<summary>Javob</summary>

**C.** Asosiy himoya: kirish struct'ida `user_id` maydoni yoʻq — egani yozadigan maydon umuman mavjud emas. `decodeJSON`dagi `DisallowUnknownFields` nomaʼlum kalitni jim tashlamay, ochiq `400` qiladi. Kalitsiz soʻrovda ega — session egasi, ya'ni Dilnoza.

</details>

```go
type orderInput struct {
	Items []itemInput `json:"items"`
	Note  string      `json:"note"`
}
```

`orderInput` — `POST /orders` bodyʼsi qabul qiladigan maydonlar; faqat `items` va `note`. Bu **mass assignment** himoyasi: mijoz oʻzi bermasligi kerak boʻlgan maydonni yuborishi (OWASP API3:2023, Broken Object Property Level Authorization; eski nomi *Mass Assignment*). Haqiqiy soʻrovlar:


Ikkinchi javobda `"user_id":1` — Dilnoza, sessiondan. Yangi buyurtma `43` boʻldi. Bu 43 ta buyurtma borligini bildirmaydi: seed hisobni 41dan boshlaydi. Lekin ketma-ket ID umumiy hajmni baribir ochadi: ikki vaqtda ikkita buyurtma yaratgan hujumchi oraliqda nechta buyurtma boʻlganini hisoblaydi. OWASP tasodifiy, taxmin qilib boʻlmaydigan ID'ni (masalan UUID) qoʻshimcha qatlam sifatida tavsiya qiladi. Lekin Authorization Cheat Sheet aniq aytadi: bunday yashirish «generally not sufficient by itself» — tekshiruv har soʻrovda kerak.

Yana ikki eslatma. Egalik — munosabatga asoslangan qoida («bu buyurtma shu foydalanuvchiniki»), rol esa RBAC (rolga asoslangan boshqaruv). OWASP murakkab tizimlar uchun atribut va munosabatga asoslangan modellarni (ABAC, ReBAC) afzal koʻradi. ## Koʻp uchraydigan xatolar

**1. «Login yetarli».** Eng koʻp uchraydigan tasavvur: `requireUser` bor, demak xavfsiz. Lekin `WHERE id = $1` begona buyurtmani muvaffaqiyatli qaytaradi, kompilyator ham, server ham xato bermaydi — jim xato (yuqoridagi «Muammo» boʻlimi). **2. Middleware yozilgan, lekin ulanmagan.** `requireAdmin` bor, route'da yoʻq: `/admin/users`ni xaridor oldi (yuqoridagi «Rol» boʻlimi). Tuzatish: har himoyalanishi kerak route'da `requireUser(requireAdmin(…))`.

**3. Tartib teskari.** `requireAdmin(requireUser(…))` — admin ham `500` oladi; log: `panic: currentUser: route requireUser bilan oʻralmagan`. Tuzatish: tashqarida `requireUser` (kim?), ichkarida `requireAdmin` (admin'mi?).

**4. Faqat `GET`ni tuzatish.** `PATCH`, `DELETE` va eksport route'lari ham yozuvga tegadi, har birida oʻz egalik tekshiruvi kerak. Starterdagi `PATCH /orders/{id}` hali xato — uy vazifasi shuni yopadi. Yarim tuzatish ham xato beradi: store imzosini oʻzgartirib handlerni unutsangiz, `go vet` darhol koʻrsatadi. ## Uy vazifasi

🟡 **`PATCH /orders/{id}` faqat oʻz buyurtmangizni oʻzgartirsin.** Papkada yana bir route bor: `PATCH /orders/{id}`. **PATCH** — resursning bir qismini oʻzgartiradigan HTTP metod (RFC 5789); bu yerda u buyurtmaning yetkazish izohini (`note`) oʻzgartiradi. Uning `UPDATE`ida bugungi xato: egasi tekshirilmaydi.

```go
func (s *Store) UpdateNote(ctx context.Context, id int64, note string) error {
	tag, err := s.pool.Exec(ctx,
		"UPDATE orders SET note = $2 WHERE id = $1",
		id, note)
```

Bu metodning boshi (`internal/store/orders.go`). Jasur Dilnozaning 41-buyurtmasiga oʻz manzilini yozib koʻradi (Jasur sifatida login qiling, `jasur-login.json` yuqorida yaratilgan):



```console
$ docker compose exec db psql -c "SELECT id, user_id, note FROM orders WHERE id = 41"

----+---------+-------------------
 41 |       1 | Jasurning manzili
(1 row)
```

`-X PATCH` HTTP metodni tanlaydi, `-d` bodyʼni beradi, `| head -1` javobning faqat birinchi qatorini (statusni) qoldiradi. `204 No Content` — oʻzgardi, javob bodysiz; baza Dilnozaning buyurtmasida Jasurning matnini saqlab qoʻydi. Vazifa:

1. **Store.** `UpdateNote(ctx context.Context, id, userID int64, note string) error` qiling va egasini SQL shartiga qoʻying: `UPDATE orders SET note = $3 WHERE id = $1 AND user_id = $2`. Raqamlar argument tartibiga mos: `$1` ← `id`, `$2` ← `userID`, `$3` ← `note`. Begona yoki yoʻq buyurtmada hech qator oʻzgarmaydi (`tag.RowsAffected() == 0`) → `ErrOrderNotFound` (`%w` bilan, hozirgidek).
2. **Handler.** `cmd/api/handlers.go`dagi `updateNote`da store'ga `currentUser(r).ID`ni bering. Egani bodyʼdan yoki yoʻldan olmang.
3. `cmd/api/tekshiruv_test.go`ni oʻzgartirmang. Test uch narsani tekshiradi: Jasur → `404` va izoh oʻzgarmaydi; Dilnoza oʻz buyurtmasiga → `204` va izoh oʻzgaradi; yoʻq `999` → `404`.

```go
func (s *Store) UpdateNote(ctx context.Context, id, userID int64, note string) error {
	tag, err := s.pool.Exec(ctx,
		"UPDATE orders SET note = $3 WHERE id = $1 AND user_id = $2",
		id, userID, note)

		return err
	}
```
