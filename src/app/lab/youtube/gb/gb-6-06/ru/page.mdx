## Что вы узнаете

Дилноза вошла в систему и запросила свой заказ: `GET /orders/41`. Если она заменит в пути `41` на `42`, чей заказ вернёт сервер?

**Главная идея:** вход говорит только о том, **кто** отправил запрос. **Разрешение** — отдельный вопрос, и каждый запрос, который касается заказа, должен задавать его сам. На уровне объекта ответ лежит в самом SQL-условии: `WHERE id = $1 AND user_id = $2`. `$1` приходит от клиента (ID из пути), `$2` — от сервера (владелец сессии). На уровне функции ответ — роль: `requireAdmin`.

К концу урока вы:

- воспроизведёте и закроете ошибку, при которой вошедший пользователь получает чужой заказ;
- вернёте одинаковый `404` на чужой и несуществующий заказ, а полную причину запишете только в лог сервера;
- увидите тест, который ловит эту ошибку: FAIL на старом коде, ok на новом;
- закроете админ-маршрут колонкой `users.role` и middleware `requireAdmin`, а ту же ошибку в `PATCH /orders/{id}` исправите сами.

| Слово | Простое значение | Английский термин |
|---|---|---|
| авторизация | проверка «есть ли у вас разрешение на это действие?» | authorization |
| BOLA | не проверено разрешение на конкретный заказ (объект) | Broken Object Level Authorization |
| роль | группа действий, доступных пользователю (`xaridor`, `admin`) | role |

Вспомогательные слова объясняются по ходу: **аутентификация** (authentication), **BFLA** (ошибка на уровне функции), **mass assignment**.

## Кто вы? И есть ли разрешение на это? — два вопроса

Первый вопрос — **аутентификация** (authentication): «кто вы?». В bozor на него отвечает `requireUser`: cookie → сессия → пользователь в контексте. Нет ответа — `401 Unauthorized`.

Второй вопрос — **авторизация** (authorization): «есть ли у вас разрешение на это?». Нет разрешения — обычно `403 Forbidden`. Вошедшему пользователю разрешено не всё. Этот второй вопрос bozor пока нигде не задаёт.

| Шаг | Вопрос | Если нет | Кто отвечает |
|---|---|---|---|
| 1 | сессия действительна? (кто?) | `401` | `requireUser` (GB-6.04) |
| 2 | этот заказ ваш? | `404` | SQL-условие, пишем сегодня |
| 3 | это действие доступно вашей роли? | `403` | `requireAdmin`, пишем сегодня |

## Проблема: владелец в базе есть, в запросе — нет

Владелец каждого заказа уже записан в базе: шестая миграция добавила в `orders` колонку `user_id`. Вот этот файл (строки с `--` — комментарии, `+goose Up` и `+goose Down` — разделы применения и отката goose):

```sql filename="migrations/00006_orders_owner.sql" showLineNumbers
-- +goose Up
-- Har buyurtmaning egasi bor (GB-6.06): orders.user_id → users.id. Avvalgi customer matni kerak emas:
-- buyurtma kimniki ekanini endi session aytadi, mijoz yozgan ism emas.
-- NOT NULL default'siz qoʻshish faqat boʻsh jadvalda ishlaydi (laboratoriyada orders boʻsh, seed.sql keyin
-- toʻldiradi). Qatorlari bor bazada: avval ustun NULL bilan, eski qatorlarga egasi yoziladi, keyin SET NOT NULL.
ALTER TABLE orders
    ADD COLUMN user_id bigint NOT NULL REFERENCES users (id),
    DROP COLUMN customer;
-- "Shu foydalanuvchining buyurtmalari" (WHERE user_id = …) jadvalni oxirigacha oʻqimasin.
CREATE INDEX orders_user_id_idx ON orders (user_id);

-- +goose Down
DROP INDEX orders_user_id_idx;
ALTER TABLE orders
    ADD COLUMN customer text NOT NULL DEFAULT '',
    DROP COLUMN user_id;
```

| Строка | Что делает |
|---|---|
| 6–8 | в одном `ALTER TABLE` через запятую два действия: добавляет `user_id` (`NOT NULL`, внешний ключ на `users.id`, GB-5.04) и удаляет старый текст `customer`: теперь, кто вы, говорит сессия |
| 10 | `CREATE INDEX` создаёт индекс по `user_id`: заказы одного пользователя находятся без полного чтения таблицы |
| 12–16 | `Down`: удаляет индекс и возвращает `customer` пустой строкой (старый текст не восстановить) |

`NOT NULL` без `DEFAULT` добавляется только в **пустую** таблицу — это была ошибка из GB-5.06. В лаборатории `orders` пуста, `seed.sql` заполняет её позже. В работающей базе это не один файл, а несколько релизов: сначала колонка с `NULL` и внешний ключ `NOT VALID`, потом проверка ограничения; владельцев старых строк вы проставляете по бизнес-решению (свободный текст `customer` нельзя автоматически сопоставить с `users.id`); `SET NOT NULL` — через проверенный `CHECK`; индекс — `CREATE INDEX CONCURRENTLY`; старая колонка удаляется в следующем релизе. Шаги описаны в README папки урока.

Подключённый маршрут и начало обработчика:

```go
	mux.Handle("GET /orders/{id}", a.requireUser(http.HandlerFunc(a.getOrder)))

func (a *api) getOrder(w http.ResponseWriter, r *http.Request) {
	id, ok := pathID(w, r)
	if !ok {
		return
	}
	o, err := a.st.Order(r.Context(), id)
```

Первая строка: путь `GET /orders/{id}` подключён к `getOrder`, внешний `requireUser` не пропускает запрос без cookie до обработчика (GB-5.10). `pathID` превращает `{id}` из пути в число; не число — `400` (GB-4.08). Последняя строка просит у store заказ с этим ID. SQL-запрос store:

```sql
SELECT user_id, status, note FROM orders
WHERE id = $1
```

Первая строка выбирает колонки `user_id`, `status`, `note`; `note` — заметка к доставке, обычно в ней домашний адрес. Вторая строка — условие: `id` равен `$1`. О том, кто спрашивает, в условии ничего нет.

Дилноза вошла, её ID — 1. Она отправляет `GET /orders/42`; заказ 42 принадлежит Жасуру. Какой ответ? **A)** `401`: сначала войдите · **B)** `403`: нет разрешения · **C)** `200`: заказ Жасура.

<details>
<summary>Ответ</summary>

**C.** Cookie есть, сессия жива, `requireUser` пропустил Дилнозу: `401` выдаёт проверка личности, а здесь личность верна. Для `403` в коде должна быть проверка разрешения — её нет. Строка в базе есть и подходит под условие, значит, вернётся.

</details>

Второй ответ — `200`: заказ Жасура с домашним адресом и общей суммой (в тийинах). Это ошибка. Что проверил каждый шаг:

| Шаг | Что произошло | Не проверено |
|---|---|---|
| `requireUser` | cookie → сессия → Дилноза в контекст | чей заказ |
| `getOrder` | `42` из пути → store | ID спрашивающего |
| `WHERE id = $1` | 42 найден → ответ | чей 42? |

В списке OWASP API Security Top 10 (2023) это **первый** пункт: **Broken Object Level Authorization**, коротко **BOLA**. OWASP Authorization Cheat Sheet называет это формой Insecure Direct Object Reference (**IDOR**). ID идут подряд: атакующий попробует и 43, 44 и дальше. Правило OWASP: **каждая** функция, которая по ID от клиента обращается к записи в базе, должна проверять разрешение пользователя на это действие, и это нужно закрепить тестами.

## Исправление: условие владельца в самом SQL

Остановите сервер и верните сохранённые исправленные файлы:

```bash
cp handlers.fixed cmd/api/handlers.go
cp orders.fixed internal/store/orders.go
```

Исправление в самом запросе, одна новая строка:

```sql
SELECT user_id, status, note FROM orders
WHERE id = $1
  AND user_id = $2
```

`AND`: строка находится, только если истинны оба условия. `$1` — ID от клиента (из пути), `$2` — ID спрашивающего, то есть владельца сессии (от сервера). Выбрать `$2` клиент не может. Вот метод store:

```go
func (s *Store) Order(ctx context.Context, id, userID int64) (Order, error) {
	o := Order{ID: id, Items: []OrderItem{}}
	var note *string // orders.note NULL boʻlishi mumkin: NULL → nil
	err := s.pool.QueryRow(ctx, `
		SELECT user_id, status, note FROM orders
		WHERE id = $1
		  AND user_id = $2`,
		id, userID).Scan(&o.UserID, &o.Status, &note)
	if errors.Is(err, pgx.ErrNoRows) {
		return Order{}, fmt.Errorf("buyurtma %d, foydalanuvchi %d: %w", id, userID, ErrOrderNotFound)
	}
	if err != nil {
		return Order{}, err
	}
	if note != nil {
		o.Note = *note
	}
	rows, err := s.pool.Query(ctx,
		"SELECT product_id, quantity, unit_price FROM order_items WHERE order_id = $1 ORDER BY id", id)
	if err != nil {
		return Order{}, err
	}
	defer rows.Close()
	for rows.Next() {
		var it OrderItem
		if err := rows.Scan(&it.ProductID, &it.Quantity, &it.UnitPrice); err != nil {
			return Order{}, err
		}
		o.Items = append(o.Items, it)
		o.Total += it.UnitPrice * int64(it.Quantity)
	}
	if err := rows.Err(); err != nil {
		return Order{}, err
	}
	return o, nil
}
```

| Строка | Что делает |
|---|---|
| 1 | метод принимает `id` и `userID`; `int64` записан один раз для обоих (`id, userID int64`) |
| 2 | `o` — возвращаемый заказ |
| 3 | `note` — `*string`: если в колонке `NULL`, остаётся `nil` (GB-2.04) |
| 4–8 | `QueryRow` выполняет запрос (GB-5.05): условие — то самое `WHERE id = $1 AND user_id = $2`; `$1` ← `id`, `$2` ← `userID`; `Scan` записывает колонки в `o` и `note` |
| 9–11 | нет строки — `pgx.ErrNoRows`; оборачиваем его в `ErrOrderNotFound` (`%w`, GB-5.10). У чужого заказа то же самое: условие ложно, строки нет |
| 12–14 | любая другая ошибка возвращается как есть |
| 15–36 | как в прошлых уроках: переносит `note`, если он есть, читает строки заказа и считает общую сумму |

Обработчик берёт владельца из `currentUser` (GB-6.04):

```go
func (a *api) getOrder(w http.ResponseWriter, r *http.Request) {
	id, ok := pathID(w, r)
	if !ok {
		return
	}
	o, err := a.st.Order(r.Context(), id, currentUser(r).ID)
	if err != nil {
		writeError(w, err)
		return
	}
	writeJSON(w, http.StatusOK, o)
}
```

Изменилась строка 6: `currentUser(r).ID` — владелец сессии. ID приходит от клиента (строка 2, из пути), а владелец — из сессии: клиент его не выбирает. Вызвать store без владельца теперь нельзя: сигнатура требует `userID`. Но оба параметра — `int64`, и перепутанный порядок аргументов не будет ошибкой компиляции — порядок проверяет тест.

Перезапустите сервер. Дилноза отправляет два запроса: заказ Жасура 42 и вообще несуществующий заказ 999. Чем отличаются ответы? **A)** `42` → `403`, `999` → `404` · **B)** оба одинаковые `404` · **C)** `42` → `404`, `999` → `400`.

<details>
<summary>Ответ</summary>

**B.** В обоих запросах нет строки под условие, store в обоих случаях возвращает `ErrOrderNotFound`. Если вы выбрали A, вы думали «есть, но не ваш» (`403`) — ниже о том, чем это опасно. C: `999` — корректное число, `pathID` его принимает, поэтому не `400`.

</details>

Оба — `404 Not Found` с одинаковым текстом «bunday buyurtma yoʻq» («такого заказа нет»); различается только `request_id` (он свой у каждого запроса, GB-6.01).

**Почему не `403`?** `403` говорит «такой заказ есть, но не ваш». Тогда атакующий переберёт ID один за другим и узнает, какие заказы существуют. [RFC 9110 §15.5.4](https://www.rfc-editor.org/rfc/rfc9110#name-403-forbidden) прямо допускает это: сервер, который хочет скрыть существование ресурса, может вернуть `404` вместо `403` («MAY»). Это выбор bozor, а не обязательное правило для любого API. Заметьте также: подряд идущие ID всё равно раскрывают *количество* заказов — `404` этого не скрывает (см. раздел «Глубже»).

Подробности — в логе сервера (первый терминал): видно, какой пользователь какой заказ запрашивал. Это два пути из GB-6.02: клиенту безопасный текст, в лог — полная ошибка. Берём только строки `xato`:

```console
$ grep ' xato ' server.log
2026/11/28 11:15:22 KNBI4DSAZOBX2A7LIZSPLVVBGK xato 404: "buyurtma 42, foydalanuvchi 1: buyurtma topilmadi"
2026/11/28 11:15:22 BBSKMXA7MJX34EUFPSDY4XARRX xato 404: "buyurtma 999, foydalanuvchi 1: buyurtma topilmadi"
```

`buyurtma` — заказ, `foydalanuvchi` — пользователь, `topilmadi` — не найден. Лог говорит «пользователь 1 запросил заказ 42»; чужой и несуществующий заказ он сам не различает, обе строки одной формы.

## Роль: второй слой разрешения

Уровень объекта решил «этот заказ ваш?». Второй слой — уровень функции: некоторые действия только для администратора. Седьмая миграция добавляет в `users` колонку `role`:

```sql filename="migrations/00007_users_role.sql" showLineNumbers
-- +goose Up
-- Rol (GB-6.06): oddiy xaridor yoki admin. Yangi foydalanuvchi har doim xaridor: eng kam huquq
-- (OWASP Authorization Cheat Sheet, "Enforce Least Privileges"). Admin'ni faqat baza egasi tayinlaydi.
ALTER TABLE users
    ADD COLUMN role text NOT NULL
    DEFAULT 'xaridor'
    CHECK (role IN ('xaridor', 'admin'));

-- +goose Down
ALTER TABLE users DROP COLUMN role;
```

| Строка | Что делает |
|---|---|
| 4–7 | `ALTER TABLE users` добавляет обязательную текстовую колонку `role`; `DEFAULT 'xaridor'` даёт `xaridor` существующим и новым пользователям; `CHECK (role IN ('xaridor', 'admin'))` допускает только эти два значения |
| 9–10 | `Down`: удаляет колонку |

Новый зарегистрированный пользователь всегда `xaridor`: OWASP называет это принципом наименьших привилегий (least privilege). Администратора назначают только в базе. В `store.User` теперь есть поле `Role`, `UserBySession` читает и его. Новый `cmd/api/authz.go`:

```go filename="cmd/api/authz.go" showLineNumbers
package main

// Authorization — «nima qila olasiz» (GB-6.06). Authentication (requireUser, auth.go) faqat kim ekaningizni
// aniqlaydi. Ruxsatning ikki qavati:
//
//	obyekt   «bu buyurtma sizniki?» — har store metodida, SQL shartida: WHERE id = $1 AND user_id = $2.
//	         Begona buyurtma → 404, xuddi yoʻq buyurtma kabi (RFC 9110 §15.5.4: mavjudligini yashirish).
//	funksiya «bu amal sizning rolingizga ochiq?» — requireAdmin middleware'i, /admin/… route'larida → 403.
//
// OWASP API Security Top 10 2023: API1 Broken Object Level Authorization, API5 Broken Function Level Authorization.

import (
	"errors"
	"net/http"

	"github.com/abdurahmon27/bozor/internal/store"
)

// errForbidden — foydalanuvchi kim ekani maʼlum, lekin bu amal uning roliga ruxsat etilmagan (problemFor → 403).
var errForbidden = errors.New("bu amal uchun ruxsat yoʻq")

// requireAdmin — faqat admin rolidagi foydalanuvchini oʻtkazadi, qolganlarga 403.
// requireUser'ning ICHIDA turishi shart: foydalanuvchini context'ga requireUser qoʻyadi.
// Tashqarida tursa currentUser panic qiladi → 500 (GB-6.04): jim oʻtkazib yuborishdan xavfsizroq.
func requireAdmin(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if currentUser(r).Role != store.RoleAdmin {
			writeError(w, errForbidden)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

| Строка | Что делает |
|---|---|
| 1 | `package main` — тот же пакет, что и остальные файлы `cmd/api` |
| 3–10 | комментарий: два слоя разрешения и пункты OWASP |
| 12–17 | импорты: `errors`, `net/http` и пакет `store` (для константы роли) |
| 19–20 | `errForbidden` — обычное значение ошибки; `problemFor` (GB-6.02) превращает его в `403 Forbidden` |
| 22–24 | комментарий: `requireAdmin` обязан стоять **внутри** `requireUser` |
| 25 | `requireAdmin` — форма middleware из GB-6.01: принимает handler, возвращает handler |
| 26 | возвращаемая функция-обработчик (closure) |
| 27 | роль `currentUser(r).Role` не admin? Значение `store.RoleAdmin` — `"admin"` |
| 28–30 | не admin: пишется `errForbidden` и `return` |
| 31 | admin: `next.ServeHTTP` вызывает следующий handler |
| 32–33 | закрываются обе функции |

Выбираем `403`: что админ-раздел существует, не секрет, а пользователь знает, кто он.

## Глубже (необязательно): `user_id` в теле и подряд идущие ID

Дилноза добавляет в тело `POST /orders` поле `"user_id":2`, чтобы записать заказ от имени Жасура. Что будет? **A)** заказ будет Жасура · **B)** заказ будет Дилнозы · **C)** `400`: неизвестный ключ.

<details>
<summary>Ответ</summary>

**C.** Главная защита: в структуре входных данных нет поля `user_id` — поля, которое записывало бы владельца, просто не существует. `DisallowUnknownFields` в `decodeJSON` не отбрасывает неизвестный ключ молча, а превращает его в явный `400`. В запросе без ключа владелец — владелец сессии, то есть Дилноза.

</details>

```go
type orderInput struct {
	Items []itemInput `json:"items"`
	Note  string      `json:"note"`
}
```

`orderInput` — поля, которые принимает тело `POST /orders`: только `items` и `note`. Это защита от **mass assignment**: клиент присылает поле, которое сам задавать не должен (OWASP API3:2023, Broken Object Property Level Authorization; прежнее название — *Mass Assignment*). Настоящие запросы:

```console
$ curl -s -b jar.txt localhost:8765/orders -H "Content-Type: application/json" -d '{"user_id":2,"items":[{"product_id":3,"quantity":1}]}'
{"type":"about:blank","title":"Bad Request","status":400,"detail":"body bitta JSON obyekt boʻlsin, faqat maʼlum kalitlar bilan","request_id":"MDQKKJMQOKGIVIVYJKIIZFUEEP"}
```

```console
$ curl -s -b jar.txt localhost:8765/orders -H "Content-Type: application/json" -d '{"items":[{"product_id":3,"quantity":1}]}'
{"id":43,"user_id":1,"status":"yangi","items":[{"product_id":3,"quantity":1,"unit_price":2500000}],"total":2500000}
```

Во втором ответе `"user_id":1` — Дилноза, из сессии. Новый заказ получил номер `43`. Это не значит, что заказов 43: seed начинает счёт с 41. Но подряд идущие ID всё равно раскрывают общий объём: атакующий, создавший два заказа в разное время, посчитает, сколько заказов появилось между ними. OWASP советует случайные, не угадываемые ID (например, UUID) как дополнительный слой. Но Authorization Cheat Sheet говорит прямо: такое сокрытие «generally not sufficient by itself» — проверка нужна в каждом запросе.

Ещё два замечания. Владение — правило, основанное на отношении («этот заказ принадлежит этому пользователю»), а роль — это RBAC (управление доступом по ролям). Для сложных систем OWASP предпочитает модели на атрибутах и отношениях (ABAC, ReBAC). Следующий шаг (GB-6.08): обернуть каждый админ-маршрут по отдельности легко забыть; надёжнее отдельный `ServeMux` для `/admin/`, подключённый один раз через `requireUser(requireAdmin(…))`.

## Частые ошибки

**1. «Входа достаточно».** Самое частое заблуждение: `requireUser` есть, значит, безопасно. Но `WHERE id = $1` успешно возвращает чужой заказ, и ни компилятор, ни сервер не жалуются — это тихая ошибка (раздел «Проблема» выше). Признак: `200` и чужой `user_id`. Исправление: владельца берите из сессии и ставьте в SQL-условие; и при чтении, и при изменении.

**2. Middleware написан, но не подключён.** `requireAdmin` есть, в маршруте его нет: `/admin/users` отдал список покупателю (раздел «Роль» выше). Исправление: на каждом маршруте, который нужно защитить, `requireUser(requireAdmin(…))`.

**3. Порядок обратный.** `requireAdmin(requireUser(…))` — `500` получает даже администратор; в логе: `panic: currentUser: route requireUser bilan oʻralmagan`. Исправление: снаружи `requireUser` (кто?), внутри `requireAdmin` (админ ли?).

**4. Исправить только `GET`.** `PATCH`, `DELETE` и экспорт тоже трогают запись, и в каждом нужна своя проверка владельца. `PATCH /orders/{id}` в starter всё ещё с ошибкой — домашнее задание закрывает именно её. Даже половинчатое исправление даёт ошибку: если поменять сигнатуру store и забыть handler, `go vet` сразу покажет. Дополнительный эксперимент, которого нет в папке урока: starter-обработчик с новой сигнатурой `UpdateNote` (функция полностью приведена в ответе к домашнему заданию):

```console

# [github.com/abdurahmon27/bozor/cmd/api]
vet: cmd/api/handlers.go:247:53: not enough arguments in call to a.st.UpdateNote
	have (context.Context, int64, string)
	want (context.Context, int64, int64, string)
```

`vet:` — сообщение vet; `cmd/api/handlers.go:247:53` — файл, строка, столбец; `not enough arguments` — не хватает аргументов, `have` — передано, `want` — нужно. Сигнатура заставляет передать владельца: добавьте в handler `currentUser(r).ID`.

## Проверьте себя

**1.** На какие вопросы отвечают аутентификация и авторизация?

<details>
<summary>Ответ</summary>

Аутентификация — «кто вы?» (в bozor `requireUser`, нет ответа — `401`). Авторизация — «есть ли у вас разрешение на это действие?» (объект: SQL-условие; функция: `requireAdmin`, нет разрешения — `403`).

</details>

**2.** Почему на чужой заказ отвечаем `404`, а не `403`?

<details>
<summary>Ответ</summary>

`403` говорит «такой заказ есть, но не ваш»; атакующий перебирает ID и узнаёт, какие заказы существуют. RFC 9110 §15.5.4 разрешает `404`, чтобы скрыть существование ресурса. Это не заменяет проверку: условие владельца остаётся в SQL, а `404` — его ответ.

</details>

**3. Предскажите.** Для Дилнозы (ID 1) вызов `Order(ctx, id, 1)` с `id` равным `41`, `42`, `999` — какие HTTP-статусы? **A)** `200`, `404`, `404` · **B)** `200`, `403`, `404` · **C)** все три `200`.

<details>
<summary>Ответ</summary>

**A.** Оба условия выполняются только для `41`: `id = 41 AND user_id = 1`. У `42` `user_id` равен 2, условие ложно; `999` не существует. В обоих случаях строки нет → `ErrOrderNotFound` → `404`. B — `403` мы не используем (вопрос 2). C — это результат старого кода, а здесь исправленный.

</details>

**4. GB-6.03.** Почему пароль хранят с argon2id, а не с SHA?

<details>
<summary>Ответ</summary>

Argon2id намеренно медленный и требует памяти: каждая догадка стоит дорого. Быстрый хеш (SHA) такого барьера не создаёт, атакующий делает огромное число догадок в секунду.

</details>

## Домашнее задание

🟡 **`PATCH /orders/{id}` должен менять только ваш заказ.** В папке есть ещё один маршрут: `PATCH /orders/{id}`. **PATCH** — HTTP-метод, который изменяет часть ресурса (RFC 5789); здесь он меняет заметку к доставке (`note`). В его `UPDATE` сегодняшняя ошибка: владелец не проверяется.

```go
		"UPDATE orders SET note = $2 WHERE id = $1",
		id, note)
```

2. **Handler.** В `updateNote` из `cmd/api/handlers.go` передайте store `currentUser(r).ID`. Не берите владельца из тела или пути.
