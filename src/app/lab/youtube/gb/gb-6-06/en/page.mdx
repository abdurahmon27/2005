## What you will learn

Dilnoza signed in and fetched her own order with `GET /orders/41`. If she changes `41` to `42` in the path, whose order does the server return?

**The one idea:** login only says **who** sent the request. **Permission** is a separate question, and **every** request that touches an order must ask it itself. At object level the answer is in the SQL condition: `WHERE id = $1 AND user_id = $2`. `$1` comes from the client (the ID in the path), `$2` from the server (the session owner). At function level the answer is a role: `requireAdmin`.

By the end you will:

- reproduce and close the bug where a signed-in user receives another user's order;
- return the same `404` for a foreign order and a missing order, and write the full reason only to the server log;
- see a test that catches the bug: FAIL on the old code, ok on the new code;
- protect an admin route with a `users.role` column and a `requireAdmin` middleware, and fix the same bug in `PATCH /orders/{id}` yourself.

| Word | Plain meaning | English term |
|---|---|---|
| authorization | the check «may you do this action?» | authorization |
| BOLA | the permission for this specific order (object) was not checked | Broken Object Level Authorization |
| role | a group of actions open to a user (`xaridor`, `admin`) | role |

Helper words are explained where they appear: **authentication**, **BFLA** (a function-level bug), **mass assignment**.

## Who are you? And may you do this? — two questions

The first question is **authentication**: «who are you?». In bozor `requireUser` answers it: cookie → session → user in the context. No answer — `401 Unauthorized`.

The second question is **authorization**: «may you do this?». No permission — usually `403 Forbidden`. A signed-in user is not allowed everything. bozor does not ask this second question anywhere yet.

| Step | Question | If not | Who answers |
|---|---|---|---|
| 1 | is the session valid? (who?) | `401` | `requireUser` (GB-6.04) |
| 2 | is this order yours? | `404` | the SQL condition, written today |
| 3 | is this action open to your role? | `403` | `requireAdmin`, written today |

## The problem: the owner is in the database, not in the query

Every order's owner is already stored: the sixth migration added a `user_id` column to `orders`. Here is the file (lines starting with `--` are comments; `+goose Up` and `+goose Down` are goose's apply and rollback sections):

```sql filename="migrations/00006_orders_owner.sql" showLineNumbers
-- +goose Up
-- Har buyurtmaning egasi bor (GB-6.06): orders.user_id → users.id. Avvalgi customer matni kerak emas:
-- buyurtma kimniki ekanini endi session aytadi, mijoz yozgan ism emas.
-- NOT NULL default'siz qoʻshish faqat boʻsh jadvalda ishlaydi (laboratoriyada orders boʻsh, seed.sql keyin
-- toʻldiradi). Qatorlari bor bazada: avval ustun NULL bilan, eski qatorlarga egasi yoziladi, keyin SET NOT NULL.
ALTER TABLE orders
    ADD COLUMN user_id bigint NOT NULL REFERENCES users (id),
    DROP COLUMN customer;
-- "Shu foydalanuvchining buyurtmalari" (WHERE user_id = …) jadvalni oxirigacha oʻqimasin.
CREATE INDEX orders_user_id_idx ON orders (user_id);

-- +goose Down
DROP INDEX orders_user_id_idx;
ALTER TABLE orders
    ADD COLUMN customer text NOT NULL DEFAULT '',
    DROP COLUMN user_id;
```

| Line | What it does |
|---|---|
| 6–8 | one `ALTER TABLE` with two actions separated by a comma: adds `user_id` (`NOT NULL`, a foreign key to `users.id`, GB-5.04) and drops the old `customer` text: who you are is now told by the session |
| 10 | `CREATE INDEX` builds an index on `user_id`: one user's orders are found without reading the whole table |
| 12–16 | `Down`: drops the index and restores `customer` as an empty string (the old text cannot come back) |

`NOT NULL` without a `DEFAULT` works only on an **empty** table — that was the error in GB-5.06. In the lab `orders` is empty and `seed.sql` fills it later. On a running database this is not one file but several releases: first the column with `NULL` and a `NOT VALID` foreign key, then validate the constraint; you fill the owners of old rows by a business decision (free-text `customer` cannot be mapped to `users.id` automatically); `SET NOT NULL` through a validated `CHECK`; the index with `CREATE INDEX CONCURRENTLY`; the old column is dropped in a later release. The steps are in the lesson folder's README.

The connected route and the start of the handler:

```go
	mux.Handle("GET /orders/{id}", a.requireUser(http.HandlerFunc(a.getOrder)))

func (a *api) getOrder(w http.ResponseWriter, r *http.Request) {
	id, ok := pathID(w, r)
	if !ok {
		return
	}
	o, err := a.st.Order(r.Context(), id)
```

First line: the path `GET /orders/{id}` is connected to `getOrder`; the outer `requireUser` keeps a request without a cookie from reaching the handler (GB-5.10). `pathID` turns `{id}` from the path into a number; not a number — `400` (GB-4.08). The last line asks the store for the order with this ID. The store's SQL query:

```sql
SELECT user_id, status, note FROM orders
WHERE id = $1
```

The first line selects the columns `user_id`, `status` and `note`; `note` is the delivery note, usually with a home address. The second line is the condition: `id` equals `$1`. Who is asking appears nowhere in the condition.

Dilnoza is signed in; her ID is 1. She sends `GET /orders/42`; order 42 is Jasur's. What is the response? **A)** `401`: sign in first · **B)** `403`: no permission · **C)** `200`: Jasur's order.

<details>
<summary>Answer</summary>

**C.** The cookie is there, the session is alive, `requireUser` let Dilnoza through: `401` comes from the identity check, and here the identity is correct. For `403` the code would need a permission check — there is none. The row exists in the database and matches the condition, so it is returned.

</details>

```console
{"id":41,"user_id":1,"status":"yangi","note":"Chilonzor 9-kvartal, 12-uy","items":[{"product_id":1,"quantity":2,"unit_price":1200000},{"product_id":2,"quantity":3,"unit_price":400000}],"total":3600000}
```

```console
$ curl -s -b jar.txt localhost:8765/orders/42
{"id":42,"user_id":2,"status":"yangi","note":"Yunusobod 4-kvartal, 17-uy, ertalab","items":[{"product_id":4,"quantity":1,"unit_price":3500000},{"product_id":3,"quantity":1,"unit_price":2500000}],"total":6000000}
```

The second response is `200`: Jasur's order with his home address and the total (in tiyin). That is the bug. What each step checked:

| Step | What happened | Not checked |
|---|---|---|
| `requireUser` | cookie → session → Dilnoza into the context | whose order |
| `getOrder` | `42` from the path → store | the asker's ID |
| `WHERE id = $1` | 42 found → response | whose is 42? |

In the OWASP API Security Top 10 (2023) this is the **first** item: **Broken Object Level Authorization**, **BOLA** for short. The OWASP Authorization Cheat Sheet calls it a form of Insecure Direct Object Reference (**IDOR**). IDs are sequential: an attacker will also try 43, 44 and onwards. The OWASP rule: **every** function that uses an ID from the client to reach a record in the database must check that the user may perform that action, and you should pin this down with tests.

## The fix: the ownership condition in the SQL itself

Stop the server and put back the saved fixed files:

```bash
cp handlers.fixed cmd/api/handlers.go
cp orders.fixed internal/store/orders.go
```

The fix is in the query itself, one new line:

```sql
SELECT user_id, status, note FROM orders
WHERE id = $1
  AND user_id = $2
```

`AND`: a row is found only if both conditions are true. `$1` is the ID the client sent (from the path), `$2` is the ID of the asker, that is the session owner (from the server). The client cannot choose `$2`. Here is the store method:

```go
func (s *Store) Order(ctx context.Context, id, userID int64) (Order, error) {
	o := Order{ID: id, Items: []OrderItem{}}
	var note *string // orders.note NULL boʻlishi mumkin: NULL → nil
	err := s.pool.QueryRow(ctx, `
		SELECT user_id, status, note FROM orders
		WHERE id = $1
		  AND user_id = $2`,
		id, userID).Scan(&o.UserID, &o.Status, &note)
	if errors.Is(err, pgx.ErrNoRows) {
		return Order{}, fmt.Errorf("buyurtma %d, foydalanuvchi %d: %w", id, userID, ErrOrderNotFound)
	}
	if err != nil {
		return Order{}, err
	}
	if note != nil {
		o.Note = *note
	}
	rows, err := s.pool.Query(ctx,
		"SELECT product_id, quantity, unit_price FROM order_items WHERE order_id = $1 ORDER BY id", id)
	if err != nil {
		return Order{}, err
	}
	defer rows.Close()
	for rows.Next() {
		var it OrderItem
		if err := rows.Scan(&it.ProductID, &it.Quantity, &it.UnitPrice); err != nil {
			return Order{}, err
		}
		o.Items = append(o.Items, it)
		o.Total += it.UnitPrice * int64(it.Quantity)
	}
	if err := rows.Err(); err != nil {
		return Order{}, err
	}
	return o, nil
}
```

| Line | What it does |
|---|---|
| 1 | the method takes `id` and `userID`; `int64` is written once for both (`id, userID int64`) |
| 2 | `o` is the order to return |
| 3 | `note` is a `*string`: if the column is `NULL`, it stays `nil` (GB-2.04) |
| 4–8 | `QueryRow` runs the query (GB-5.05): the condition is the same `WHERE id = $1 AND user_id = $2`; `$1` ← `id`, `$2` ← `userID`; `Scan` writes the columns into `o` and `note` |
| 9–11 | no row — `pgx.ErrNoRows`; we wrap it in `ErrOrderNotFound` (`%w`, GB-5.10). A foreign order gives exactly the same: the condition is false, there is no row |
| 12–14 | any other error is returned as it is |
| 15–36 | as in earlier lessons: copies `note` if present, reads the order's rows and computes the total |

The handler takes the owner from `currentUser` (GB-6.04):

```go
func (a *api) getOrder(w http.ResponseWriter, r *http.Request) {
	id, ok := pathID(w, r)
	if !ok {
		return
	}
	o, err := a.st.Order(r.Context(), id, currentUser(r).ID)
	if err != nil {
		writeError(w, err)
		return
	}
	writeJSON(w, http.StatusOK, o)
}
```

Line 6 changed: `currentUser(r).ID` is the session owner. The ID comes from the client (line 2, from the path) and the owner from the session: the client does not choose it. The store can no longer be called without an owner: the signature requires `userID`. But both parameters are `int64`, so swapping the arguments is not a compile error — a test checks the order.

Restart the server. Dilnoza sends two requests: Jasur's order 42 and the order 999, which does not exist. How do the responses differ? **A)** `42` → `403`, `999` → `404` · **B)** both the same `404` · **C)** `42` → `404`, `999` → `400`.

<details>
<summary>Answer</summary>

**B.** In both requests no row matches the condition, so the store returns `ErrOrderNotFound` in both. If you chose A, you thought «it exists, but it is not yours» (`403`) — below is why that is dangerous. C: `999` is a valid number, `pathID` accepts it, so it is not `400`.

</details>

Both are `404 Not Found` with the same text «bunday buyurtma yoʻq» («no such order»); only the `request_id` differs (each request gets its own, GB-6.01).

**Why not `403`?** `403` says «this order exists, but it is not yours». Then an attacker tries IDs one by one and learns which orders exist. [RFC 9110 §15.5.4](https://www.rfc-editor.org/rfc/rfc9110#name-403-forbidden) says it plainly: a server that wants to hide the existence of a resource MAY answer `404` instead of `403`. This is bozor's choice, not a mandatory rule for every API. Note also: sequential IDs still reveal the *number* of orders — `404` does not hide that (see the «Going deeper» section).

The detail is in the server log (first terminal): which user asked for which order. These are the two paths from GB-6.02: a safe text for the client, the full error in the log. We take only the `xato` («error») lines:

```console
$ grep ' xato ' server.log
2026/11/28 11:15:22 KNBI4DSAZOBX2A7LIZSPLVVBGK xato 404: "buyurtma 42, foydalanuvchi 1: buyurtma topilmadi"
2026/11/28 11:15:22 BBSKMXA7MJX34EUFPSDY4XARRX xato 404: "buyurtma 999, foydalanuvchi 1: buyurtma topilmadi"
```

`buyurtma` is order, `foydalanuvchi` is user, `topilmadi` is not found. The log says «user 1 asked for order 42»; it does not tell a foreign order from a missing one by itself, both lines have the same form.

## The test: FAIL on the old code, ok on the new code

OWASP also recommends pinning this down with tests («Write tests …»). The test is in `cmd/api/api_test.go`:

```go
func TestOrderOwner(t *testing.T) {
	h, _ := testAPI(t)
	dilnoza := login(t, h, dilnozaLogin)
	for id, want := range map[string]int{"41": 200, "42": 404, "999": 404} {
		rec := send(h, "GET", "/orders/"+id, "", dilnoza.Value)
		if rec.Code != want {
			t.Errorf("Dilnoza GET /orders/%s: %d, kutilgan %d", id, rec.Code, want)
		}
	}
}
```

| Line | What it does |
|---|---|
| 1 | a test function (GB-1.08) |
| 2 | `testAPI` prepares a real Postgres with a fresh schema and the seed; `h` is the ready handler |
| 3 | `login` signs in with the JSON `dilnozaLogin` and returns the cookie |
| 4 | `map[string]int`: ID → expected status; `range` walks all three pairs. Her own (`41`) — `200`, the others — `404` |
| 5 | `send` gives the request to the handler: method, path, empty body and the cookie value |
| 6–8 | if the status is not the expected one, `t.Errorf` fails the test: `%s` is the ID, `%d` are both statuses |

First we run this test on the old, unfixed code. Which of the three IDs fail? **A)** only `42` · **B)** `42` and `999` · **C)** none: the test passes.

<details>
<summary>Answer</summary>

**A.** `41` is Dilnoza's, `200` on the old code too. `999` is a missing order on the old code too, that is `404`. Only `42` gets `200` instead of `404` on the old code. If you chose B, you thought the old code also fails on `999`; it does not — the bug here is for `42`.

</details>

## The role: the second layer of permission

Object level settled «is this order yours?». The second layer is function level: some actions are for admins only. The seventh migration adds a `role` column to `users`:

```sql filename="migrations/00007_users_role.sql" showLineNumbers
-- +goose Up
-- Rol (GB-6.06): oddiy xaridor yoki admin. Yangi foydalanuvchi har doim xaridor: eng kam huquq
-- (OWASP Authorization Cheat Sheet, "Enforce Least Privileges"). Admin'ni faqat baza egasi tayinlaydi.
ALTER TABLE users
    ADD COLUMN role text NOT NULL
    DEFAULT 'xaridor'
    CHECK (role IN ('xaridor', 'admin'));

-- +goose Down
ALTER TABLE users DROP COLUMN role;
```

| Line | What it does |
|---|---|
| 4–7 | `ALTER TABLE users` adds a required text column `role`; `DEFAULT 'xaridor'` gives `xaridor` to existing and new users; `CHECK (role IN ('xaridor', 'admin'))` allows only these two values |
| 9–10 | `Down`: drops the column |

A newly registered user is always `xaridor`: OWASP calls this least privilege. An admin is assigned only in the database. `store.User` now has a `Role` field, and `UserBySession` reads it too. The new `cmd/api/authz.go`:

```go filename="cmd/api/authz.go" showLineNumbers
package main

// Authorization — «nima qila olasiz» (GB-6.06). Authentication (requireUser, auth.go) faqat kim ekaningizni
// aniqlaydi. Ruxsatning ikki qavati:
//
//	obyekt   «bu buyurtma sizniki?» — har store metodida, SQL shartida: WHERE id = $1 AND user_id = $2.
//	         Begona buyurtma → 404, xuddi yoʻq buyurtma kabi (RFC 9110 §15.5.4: mavjudligini yashirish).
//	funksiya «bu amal sizning rolingizga ochiq?» — requireAdmin middleware'i, /admin/… route'larida → 403.
//
// OWASP API Security Top 10 2023: API1 Broken Object Level Authorization, API5 Broken Function Level Authorization.

import (
	"errors"
	"net/http"

	"github.com/abdurahmon27/bozor/internal/store"
)

// errForbidden — foydalanuvchi kim ekani maʼlum, lekin bu amal uning roliga ruxsat etilmagan (problemFor → 403).
var errForbidden = errors.New("bu amal uchun ruxsat yoʻq")

// requireAdmin — faqat admin rolidagi foydalanuvchini oʻtkazadi, qolganlarga 403.
// requireUser'ning ICHIDA turishi shart: foydalanuvchini context'ga requireUser qoʻyadi.
// Tashqarida tursa currentUser panic qiladi → 500 (GB-6.04): jim oʻtkazib yuborishdan xavfsizroq.
func requireAdmin(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if currentUser(r).Role != store.RoleAdmin {
			writeError(w, errForbidden)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

| Line | What it does |
|---|---|
| 1 | `package main` — the same package as the other files in `cmd/api` |
| 3–10 | comment: the two layers of permission and the OWASP items |
| 12–17 | imports: `errors`, `net/http` and the `store` package (for the role constant) |
| 19–20 | `errForbidden` is a plain error value; `problemFor` (GB-6.02) turns it into `403 Forbidden` |
| 22–24 | comment: `requireAdmin` must stand **inside** `requireUser` |
| 25 | `requireAdmin` — the middleware shape from GB-6.01: takes a handler, returns a handler |
| 26 | the returned handler function (a closure) |
| 27 | is the role `currentUser(r).Role` not admin? The value of `store.RoleAdmin` is `"admin"` |
| 28–30 | not admin: `errForbidden` is written and `return` |
| 31 | admin: `next.ServeHTTP` calls the next handler |
| 32–33 | both functions close |

We choose `403`: that an admin section exists is no secret, and the user knows who they are.

## Going deeper (optional): `user_id` in the body and sequential IDs

Dilnoza adds `"user_id":2` to the body of `POST /orders` to write an order in Jasur's name. What happens? **A)** the order is Jasur's · **B)** the order is Dilnoza's · **C)** `400`: unknown key.

<details>
<summary>Answer</summary>

**C.** The main defense: the input struct has no `user_id` field — a field that would write the owner does not exist at all. `DisallowUnknownFields` in `decodeJSON` does not drop the unknown key silently but turns it into an explicit `400`. In a request without the key the owner is the session owner, that is Dilnoza.

</details>

```go
type orderInput struct {
	Items []itemInput `json:"items"`
	Note  string      `json:"note"`
}
```

`orderInput` lists the fields the body of `POST /orders` accepts: only `items` and `note`. This is the defense against **mass assignment**: the client sends a field it must not set itself (OWASP API3:2023, Broken Object Property Level Authorization; its earlier name was *Mass Assignment*). The real requests:

```console
$ curl -s -b jar.txt localhost:8765/orders -H "Content-Type: application/json" -d '{"user_id":2,"items":[{"product_id":3,"quantity":1}]}'
{"type":"about:blank","title":"Bad Request","status":400,"detail":"body bitta JSON obyekt boʻlsin, faqat maʼlum kalitlar bilan","request_id":"MDQKKJMQOKGIVIVYJKIIZFUEEP"}
```

```console
$ curl -s -b jar.txt localhost:8765/orders -H "Content-Type: application/json" -d '{"items":[{"product_id":3,"quantity":1}]}'
{"id":43,"user_id":1,"status":"yangi","items":[{"product_id":3,"quantity":1,"unit_price":2500000}],"total":2500000}
```

In the second response `"user_id":1` is Dilnoza, from the session. The new order got number `43`. That does not mean there are 43 orders: the seed starts counting at 41. But sequential IDs still reveal the overall volume: an attacker who creates two orders at different times counts how many orders appeared between them. OWASP recommends random, unpredictable IDs (for example UUIDs) as an extra layer. But the Authorization Cheat Sheet says it plainly: such hiding is «generally not sufficient by itself» — the check is needed on every request.

Two more notes. Ownership is a relationship-based rule («this order belongs to this user»), while a role is RBAC (role-based access control). For complex systems OWASP prefers attribute- and relationship-based models (ABAC, ReBAC). The next step (GB-6.08): wrapping each admin route one by one is easy to forget; a safer shape is a separate `ServeMux` for `/admin/`, connected once through `requireUser(requireAdmin(…))`.

## Common mistakes

**1. «Login is enough».** The most common belief: `requireUser` is there, so it is safe. But `WHERE id = $1` happily returns another user's order, and neither the compiler nor the server complains — a silent bug (the «The problem» section above). Sign: `200` and another user's `user_id`. Fix: take the owner from the session and put it into the SQL condition; for reads and for changes.

**2. Middleware written but not connected.** `requireAdmin` exists, the route does not use it: `/admin/users` gave the list to a customer (the «The role» section above). Fix: `requireUser(requireAdmin(…))` on every route that must be protected.

**3. Order reversed.** `requireAdmin(requireUser(…))` — even the admin gets `500`; in the log: `panic: currentUser: route requireUser bilan oʻralmagan`. Fix: `requireUser` outside (who?), `requireAdmin` inside (is it an admin?).

**4. Fixing only `GET`.** `PATCH`, `DELETE` and exports touch the record too, and each needs its own owner check. `PATCH /orders/{id}` in the starter is still broken — the homework closes exactly that. Even a half fix gives an error: if you change the store signature and forget the handler, `go vet` shows it at once. An extra experiment that is not in the lesson folder: the starter handler with the new `UpdateNote` signature (the function is given in full in the homework answer):

```console
$ go vet ./...
# github.com/abdurahmon27/bozor/cmd/api
# [github.com/abdurahmon27/bozor/cmd/api]
vet: cmd/api/handlers.go:247:53: not enough arguments in call to a.st.UpdateNote
	have (context.Context, int64, string)
	want (context.Context, int64, int64, string)
```

`vet:` is the vet message; `cmd/api/handlers.go:247:53` is file, line, column; `not enough arguments` — an argument is missing, `have` — what was passed, `want` — what is needed. The signature forces the owner to be passed: add `currentUser(r).ID` in the handler.

## Check yourself

**1.** Which questions do authentication and authorization answer?

<details>
<summary>Answer</summary>

Authentication — «who are you?» (in bozor `requireUser`, no answer — `401`). Authorization — «may you do this action?» (object: the SQL condition; function: `requireAdmin`, no permission — `403`).

</details>

**2.** Why `404`, not `403`, for another user's order?

<details>
<summary>Answer</summary>

`403` says «this order exists, but it is not yours»; an attacker tries IDs and learns which orders exist. RFC 9110 §15.5.4 allows `404` to hide the existence of a resource. This does not replace the check: the ownership condition stays in SQL, and `404` is its response.

</details>

**3. Predict.** For Dilnoza (ID 1), what HTTP statuses do the calls `Order(ctx, id, 1)` give for `id` equal to `41`, `42`, `999`? **A)** `200`, `404`, `404` · **B)** `200`, `403`, `404` · **C)** all three `200`.

<details>
<summary>Answer</summary>

**A.** Only `41` matches both conditions: `id = 41 AND user_id = 1`. For `42` the `user_id` is 2, the condition is false; `999` does not exist. In both cases there is no row → `ErrOrderNotFound` → `404`. B — we do not use `403` (question 2). C — that is the old code's result, and this is the fixed code.

</details>

**4. GB-6.03.** Why is a password stored with argon2id and not with SHA?

<details>
<summary>Answer</summary>

Argon2id is deliberately slow and needs memory: every guess is expensive. A fast hash (SHA) gives no such barrier, and an attacker makes a huge number of guesses per second.

</details>
