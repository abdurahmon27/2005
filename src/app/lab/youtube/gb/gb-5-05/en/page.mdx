## What you will learn

`products` already exists. How does Go read a product from it? Where do we limit waiting if the database does not respond?

**The one idea:** Go is a Postgres client. A query borrows a connection from a pool, sends SQL and parameters separately, and reads the response with `Scan`. A context bounds waiting.

After this lesson you can:

- run `Get` and `ListActive` queries through `pgxpool`;
- distinguish a missing row from a `NULL` sum;
- bound waiting and find results that keep a connection borrowed;
- implement `ByName` and `Cheapest` until the tests pass.

| Word | Plain meaning | English term |
|---|---|---|
| connection pool | open connections kept for reuse | connection pool |
| row scanning | copying a `QueryRow` or `Query` response into Go values with `Scan` | row scanning |
| context deadline | a bound on how long a query may wait | context deadline |

## Connection: address and pool

A Postgres client sends SQL: previously `psql`, now Go. `pgx` handles the protocol; `pgxpool` reuses connections. Each connection is served by a Postgres process. Do not create a new pool for every HTTP request.

| Step | Pool | Postgres |
|---|---|---|
| before query | a connection is idle | waiting for SQL |
| `QueryRow` / `Query` | connection borrowed | executing SQL |
| result closed | connection returned | waiting for another command |

Run these commands inside the copy. `export` sets an **environment variable** inherited by programs. `CGO_ENABLED=0` disables C integration; `GOTOOLCHAIN` selects Go. `up -d --wait` starts the database in the background and waits for readiness. If `5475` is busy, use the same free port in the copied `ports` setting and URL.

## One row: QueryRow and Scan

`Product` is one product row. `ID`, `Price`: `bigint` → `int64`; `Name`: `text` → `string`; `Stock`: `integer` → `int`. Prices are in tiyin. We do not select `active`. `Store` holds the pool address; `*pgxpool.Pool` is a pointer type.

```go filename="_video/stages/02-store.go" showLineNumbers
package main

import (
	"context"

	"github.com/jackc/pgx/v5/pgxpool"
)

type Product struct {
	ID    int64
	Name  string
	Price int64
	Stock int
}

type Store struct {
	pool *pgxpool.Pool
}

func (s *Store) Get(ctx context.Context, id int64) (Product, error) {
	var p Product
	err := s.pool.QueryRow(ctx,
		"SELECT id, name, price, stock FROM products WHERE id = $1", id).
		Scan(&p.ID, &p.Name, &p.Price, &p.Stock)
	return p, err
}
```

| Lines | What they do |
|---|---|
| 1–7 | package and required imports |
| 9–14 | `Product` struct with four fields |
| 16–18 | the `pool` field in `Store` |
| 20 | receiver `s *Store`; inputs `ctx`, `id`; results `Product`, `error` |
| 21 | zero-valued `p` for the result |
| 22–24 | `QueryRow` expects one row; `Scan` writes columns to addresses |
| 25–26 | return the product and error to the caller |

`$1` is the first parameter position; the following `id` argument supplies its value separately from SQL. This prevents SQL injection: input text cannot change the query structure. Do not interpolate user values with `fmt.Sprintf`. `&p.ID` is a field address; `Scan` arguments follow the `SELECT` order. The trailing dot continues the method call on the next line.

| State | `p.ID` | `p.Name` | `p.Price` | `p.Stock` |
|---|---|---|---|---|
| `var p Product` | 0 | `""` | 0 | 0 |
| after `Scan` | 1 | `"olma"` | 1200000 | 40 |

Keep the caller independent of the driver error. Translate it to a sentinel from GB-2.08: a predefined error value:

```go
var ErrNotFound = errors.New("mahsulot topilmadi")

// QueryRow(...).Scan(...) dan keyin:
if errors.Is(err, pgx.ErrNoRows) {
	return Product{}, ErrNotFound
}
return p, err
```

`errors.Is` checks for a match; on a match return zero `Product{}` and `ErrNotFound`. Other errors pass through. The caller can choose HTTP 404 using `errors.Is(err, ErrNotFound)`.

## Multiple rows: Query, Next, Close and Err

`ListActive` returns active products ordered by `id`. `Query` returns `Rows`: rows read in sequence. Here is the main body of the method:

```go
	rows, err := s.pool.Query(ctx,
		"SELECT id, name, price, stock FROM products WHERE active ORDER BY id")
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	out := []Product{}
	for rows.Next() {
		var p Product
		if err := rows.Scan(&p.ID, &p.Name, &p.Price, &p.Stock); err != nil {
			return nil, err
		}
		out = append(out, p)
	}
	return out, rows.Err()
```

Lines 1–5 issue the query and check its error; `WHERE active` keeps true values. Line 6 defers `rows.Close()`, including early returns. Line 7 creates an empty, non-nil slice. Line 8 advances with `Next()`. Lines 9–12 scan into a fresh `p` and return on error. Line 13 uses `append` to add the product. Line 15 returns the slice and `rows.Err()`.

| Action | Current row | `out` | Connection |
|---|---|---|---|
| `Query` | none yet | `[]` | borrowed |
| `Next` → `Scan` | olma | `[olma]` | borrowed |
| next three rows | non, choy, oʻrik | `[olma non choy oʻrik]` | borrowed |
| `Next` → false | finished | unchanged | returned |

`non` means “bread”, `choy` “tea”, and `oʻrik` “apricot”. `Next() == false` can mean normal completion or a read error; `rows.Err()` distinguishes them. Reading to the end closes the result automatically. Deferred `Close` also covers early returns and returns the connection to the pool.

## Order total: SUM, NULL and COALESCE

Now call the SQL from GB-5.04 through Go. `quantity * unit_price` multiplies quantity by unit price. `SUM(bigint)` returns `numeric`, an exact decimal type. pgx can scan an integral value that fits `int64`; fractions and out-of-range values return errors.

```go
func (s *Store) OrderTotal(ctx context.Context, orderID int64) (int64, error) {
	var total int64
	err := s.pool.QueryRow(ctx,
		"SELECT SUM(quantity*unit_price) FROM order_items WHERE order_id = $1", orderID).
		Scan(&total)
	return total, err
}
```

`orderID` is the order number; `total` holds the sum. Line 2 creates a zero variable; lines 3–5 scan into its address; line 6 returns the number and error. An aggregate without `GROUP BY` returns one result row. With no input rows, its value is `NULL`.

Order 99 does not exist. What does `SUM` return? **A)** 0 · **B)** `NULL` · **C)** `pgx.ErrNoRows`.

<details>
<summary>Answer</summary>

**B.** There is a result row, but its value is `NULL`. `int64` cannot represent a missing value. Order 1 totals `2*1200000 + 3*400000 = 3600000`. Zero and “no row” confuse different cases.

</details>

## Deadline: context.WithTimeout

`context.Background()` has no deadline. `WithTimeout` derives `qctx` and a `cancel` function that releases resources. This complete video stage deliberately runs a slow query:

```go filename="_video/stages/06-main-slow.go" showLineNumbers
package main

import (
	"context"
	"fmt"
	"os"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

func main() {
	ctx := context.Background()
	pool, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
	if err != nil {
		fmt.Fprintln(os.Stderr, "pool:", err)
		os.Exit(1)
	}
	defer pool.Close()

	qctx, cancel := context.WithTimeout(ctx, 2*time.Second)
	defer cancel()
	start := time.Now()
	_, err = pool.Exec(qctx, "SELECT pg_sleep(5)")
	fmt.Println("xato:", err, time.Since(start).Round(time.Second))
}
```

New lines 21–25: `2*time.Second` is two seconds; deferred `cancel()` releases resources. `time.Now()` records the start. `Exec` does not read result rows; `_` discards the command result while `err` is kept. `pg_sleep(5)` waits five seconds in Postgres. `time.Since(start)` measures elapsed time; `Round(time.Second)` rounds it to seconds.

What happens? **A)** 5 seconds, no error · **B)** about 2 seconds, deadline error · **C)** immediate 0.

<details>
<summary>Answer</summary>

**B.** `qctx` expires before the five-second query completes. Keep `cancel()` even when a deadline will eventually expire.

</details>

```console
$ cp _video/stages/06-main-slow.go main.go
$ go run .
xato: timeout: context deadline exceeded 2s
```

`timeout: context deadline exceeded` means the context deadline expired. Both the video and this rerun report a rounded 2s: about 40% of the 5s wait. Load and scheduling affect exact timing. The context bounded waiting rather than the database sleep; compilation is outside this measurement.

| Time | `qctx` | Go waiting |
|---|---|---|
| 0s | active | inside the query |
| about 2s | expired | error returned |
| afterwards | done | another query with this context also fails |

## Going deeper (optional): did the server query stop?

On this error path, pgx v5.13.0 closes the connection and asynchronously sends `CancelRequest`. In a separate 30s sleep probe, the call returned in 2.001s. An observer connection saw 0 active sleep queries immediately, 0.5s later and 1s later. These are our rerun measurements. Cancellation is not guaranteed: “usually” matters; an error return does not prove SQL stopped immediately.

```go
	if err != nil {
		panic(err)
	}
	defer victim.Close()
	qctx, cancel := context.WithTimeout(ctx, 2*time.Second)
	defer cancel()
	start := time.Now()
	_, err = victim.Exec(qctx, "SELECT pg_sleep(30)")
	fmt.Printf("timeout elapsed=%.3fs err=%v\n", time.Since(start).Seconds(), err)
	for _, wait := range []time.Duration{0, 500 * time.Millisecond, 500 * time.Millisecond} {
		time.Sleep(wait)
		var n int
		err := observer.QueryRow(ctx, "SELECT count(*) FROM pg_stat_activity WHERE application_name='gb505_timeout_probe' AND state='active' AND query LIKE '%pg_sleep%'").Scan(&n)
		fmt.Println("active sleepers:", n, err)
	}
	fmt.Println("default MaxConns:", observer.Config().MaxConns)
}
```

`pg_typeof(... )::text` reads the SQL type name as text. Two additional SQL statements probe fractional `numeric` and an out-of-range value. `%v` prints the error; `%.3f` prints seconds to three decimal places. `pool.Config().MaxConns` was 12 on this machine. The default is the larger of 4 and `runtime.NumCPU()`; that is not a sizing recommendation.


`numeric <nil>` reports the SQL type and no error. `cannot convert … to integer` means a fraction cannot be scanned as an integer. `out of range for int64` means even an integral value exceeded the range. `active sleepers: 0` means this program had no active sleep at observation time. These observations do not guarantee every future cancellation.

## Common mistakes

**1. Forgetting `rows.Close` when leaving results early.** This is the lesson’s main mistake. This complete program returns after the first name. `firstName` reads the first product name:

```go filename="_video/leak/main.go" showLineNumbers
package main

import (
	"context"
	"fmt"
	"os"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

// firstName: birinchi mahsulotning nomi
func firstName(ctx context.Context, pool *pgxpool.Pool) (string, error) {
	rows, err := pool.Query(ctx, "SELECT name FROM products ORDER BY id")
	if err != nil {
		return "", err
	}
	if !rows.Next() {
		return "", rows.Err()
	}
	var name string
	err = rows.Scan(&name)
	return name, err
}

func main() {
	ctx := context.Background()
	pool, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
	if err != nil {
		fmt.Fprintln(os.Stderr, "pool:", err)
		os.Exit(1)
	}
	qctx, cancel := context.WithTimeout(ctx, 2*time.Second)
	defer cancel()
	for i := 1; i <= 2; i++ {
		start := time.Now()
		name, err := firstName(qctx, pool)
		fmt.Println(i, name, err, time.Since(start).Round(time.Second))
	}
}
```

New lines: `!rows.Next()` in `firstName` means there is no next row, so return `rows.Err()`. `err = rows.Scan(&name)` changes the existing variable. The `for` in `main` makes and times two calls. This broken experiment omits `pool.Close()`: it would wait for the borrowed connection. Close the pool too after fixing the leak.

Limit the pool to one connection. What does the second call do? **A)** finishes quickly · **B)** waits for an idle connection, then hits its deadline · **C)** opens another connection.

<details>
<summary>Answer</summary>

**B.** The first `Rows` remains open and holds the only connection. `pool_max_conns=1` prevents a second one. This call waits to acquire a connection rather than to execute SQL.

</details>

`?pool_max_conns=1` in the URL sets the pool limit. Single quotes stop the shell interpreting `?`. `mkdir -p` prepares the working `leak` folder:

```console
$ mkdir -p leak
$ cp _video/leak/main.go leak/main.go
$ export DATABASE_URL='postgres://bozor:bozor-lab@localhost:5475/bozor?pool_max_conns=1'
$ go run ./leak
1 olma <nil> 0s
2  context deadline exceeded 2s
```

The second line has two spaces because the name is empty. `context deadline exceeded` means the deadline expired. Both video and rerun give 0s/2s; 0s is rounded, not literally zero. Without a deadline, the call would keep waiting.

The fix is one line after checking the `Query` error:

```go
defer rows.Close()
```

What does the second call do after the fix? **A)** returns `olma` without error · **B)** deadline error at 2s · **C)** panic.

<details>
<summary>Answer</summary>

**A.** On the first function’s return, `defer` closes the result and returns the only connection.

</details>

```console
$ cp _video/leak-fixed/main.go leak/main.go
$ go run ./leak
1 olma <nil> 0s
2 olma <nil> 0s
```

| Version | After first call | Second call |
|---|---|---|
| no `Close` | connection borrowed | wait, error at 2s |
| deferred `Close` | connection idle | olma, 0s |

**2. Treating `Next == false` as unconditional success.** Return `rows.Err()` as in `ListActive` so network and deadline errors are preserved.

**3. Treating the 0 after `NULL` as a total.** Check the real `Scan` error in the order-total section. Define the zero rule with SQL `COALESCE`.

**4. Concatenating SQL instead of using `$1`.** Pass `name` and `n` as separate arguments after SQL. A parameter replaces a value, not a table or column name.

**5. Reusing an expired `qctx`.** All calls share the same expiry time. Derive a new context for the next independent operation.

**1.** What does the caller receive when `Get` cannot find the id?

**2.** What happens to the pool when you leave rows unread and forget `rows.Close`?

<details>
<summary>Answer</summary>

The connection remains borrowed. Once idle connections run out, other queries wait; a context deadline makes them return an error.

</details>

**3.** From GB-5.02: what does the left number in `5475:5432` mean?

The host port. The right-hand `5432` is the container port; Go on the host connects to `5475`.

**C.** A row exists with a `NULL` value that `int64` cannot accept. With `COALESCE`, B becomes correct.
