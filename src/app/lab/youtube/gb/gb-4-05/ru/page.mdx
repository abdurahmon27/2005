## Что вы узнаете

В каталоге bozor у каждого товара есть ID, и клиент запрашивает его в пути: `/products/1`, `/products/3`. Писать отдельный паттерн под каждый ID нельзя.
Вопрос: как одно правило принимает все ID? И кто отвечает `404` на несуществующий товар и `405` на неверный метод: mux или наш обработчик?

**Одна идея:** для каждого запроса `ServeMux` сначала ищет паттерн, у которого совпадают **и метод, и путь**. Если находит, он записывает значение вроде `{id}` в запрос (`r.PathValue("id")`, строка) и вызывает обработчик.
Если не находит: при совпавшем пути без метода mux сам пишет `405` + `Allow`, а если нет даже пути, mux сам пишет `404 page not found`.
Поэтому обработчику остаются только его собственные ошибки: `ParseInt` → `400`, `findProduct` → наш `404`. Если вызвать обработчик без mux, `PathValue` пуст.
А паттерн `"/"` без метода подходит ко всем путям и методам и поглощает `404` и `405`; `"GET /{$}"` его ограничивает.

К концу урока вы:

- пишете метод в паттерне (`"GET /products/{id}"`) и по выводу `curl` отличаете `200`, свои `404`/`400` и `404`/`405` от mux;
- читаете часть пути через `r.PathValue("id")`, превращаете её в число через `strconv.ParseInt` и находите товар через `findProduct`;
- собираете маршруты в функцию `newMux()` и тестируете их без сервера через `newMux().ServeHTTP(rec, req)`;
- объясняете, почему паттерн `"/"` отвечает `200` и на неверный путь, и на неверный метод, и исправляете его через `"GET /{$}"`;
- сами пишете в `TASK.md` маршрут `GET /products/{id}/stock`, пока `go test .` не пройдёт.

Три основные новые идеи сегодня:

| Слово | Простой смысл | По-английски |
|---|---|---|
| паттерн = `МЕТОД путь` | первый аргумент `mux.HandleFunc`: для какого метода и пути он подходит. Если не подошёл, ответ пишет mux: `404` или `405` + `Allow` | pattern (method + path) |
| `{id}` + `r.PathValue("id")` | переменная часть пути, подходящая под один сегмент; значение записывает в запрос mux, обработчик читает его как строку | wildcard, `PathValue` |
| `"/"` и `"GET /{$}"` | `"/"` — паттерн для всех путей (и, без метода, для всех методов); `{$}` значит «путь заканчивается здесь» | catch-all pattern, `{$}` |

Вспомогательные имена: `http.Error(w, сообщение, код)` и `newMux()`. Остальным новым именам я даю по одной фразе по ходу текста.

## Метод пишется в паттерне

В GB-4.03 `catalogHandler` сам проверял метод:

```go
func catalogHandler(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodGet {
		w.Header().Set("Allow", http.MethodGet)
		w.WriteHeader(http.StatusMethodNotAllowed)
		return
	}
	// … catalog'ni JSON qilib yozish (GB-4.03)
}
```

Пять строк ради одного: если метод не `GET`, написать `405` + `Allow` и выйти. В каждом обработчике это пришлось бы повторять. С Go 1.22 ([примечания к Go 1.22](https://go.dev/doc/go1.22#enhanced_routing_patterns)) эту проверку делает сам паттерн: метод пишется перед путём.

```text
МЕТОД  ПУТЬ
GET    /products
HEAD   /products   (его принимает паттерн GET)
```

Правило: метод, пробел, затем путь. `GET /products` значит «запрос `GET` **и** ровно этот путь». Паттерн без метода (`/products`) принимает любой метод.
Паттерн `GET` принимает и запрос `HEAD`: `HEAD` просит тот же ответ, что и `GET`, но без тела ([RFC 9110, HEAD](https://www.rfc-editor.org/rfc/rfc9110#name-head)).

Две строки в `newServer` меняются так: в первый аргумент добавляется метод, второй аргумент — обработчик — остаётся тем же:

```go
func newServer(addr string) *http.Server {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", healthHandler)
	mux.HandleFunc("GET /products", catalogHandler)
```

Теперь убираем из `catalogHandler` проверку `r.Method`: запрос, который не `GET` и не `HEAD`, до обработчика уже не дойдёт.

```go
func catalogHandler(w http.ResponseWriter, r *http.Request) {
	products := catalog
	if products == nil {
		products = []Product{}
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(products)
}
```

Остальное — само задание GB-4.03: даже при пустом `catalog` JSON должен быть `[]` (а не `null`), затем `Content-Type`, затем `Encode`. Полный файл — позже, в разделе «Полный код из папки».

**Предсказание.** `POST /products`: какие статус и `Allow`?

**A)** `405` и `Allow: GET` · **B)** `405` и `Allow: GET, HEAD` · **C)** `404` и без `Allow`

<details>
<summary>Ответ</summary>

**B.** Путь совпал, метод нет: mux пишет `405 Method Not Allowed` и кладёт в `Allow` методы, которые этот путь принимает. Паттерн `GET` принимает и `HEAD`, поэтому `GET, HEAD`.
Если вы выбрали **A**, вы вспомнили `Allow: GET`, написанный вручную в GB-4.03: там `HEAD` мы не добавляли. **C** — путь существует, поэтому не `404`.

</details>

```console
$ curl -i -X POST http://localhost:8765/products
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:02:14 GMT
Content-Length: 19

Method Not Allowed
```

Строка за строкой:

| Строка | Что это |
|---|---|
| `HTTP/1.1 405 Method Not Allowed` | строка статуса ([GB-4.01](/lab/youtube/gb/gb-4-01/ru)): `405` — путь есть, метод неверный |
| `Allow: GET, HEAD` | методы, которые принимает этот путь; в ответе `405` этот заголовок обязателен ([RFC 9110, 405](https://www.rfc-editor.org/rfc/rfc9110#name-405-method-not-allowed)) |
| `Content-Type`, `X-Content-Type-Options` | простой текст в UTF-8; `nosniff` говорит браузеру не угадывать тип |
| `Date`, `Content-Length: 19` | время и размер тела: `Method Not Allowed` + последний перевод строки = 19 байт |
| `Method Not Allowed` | тело |

Этот ответ написал **не обработчик, а mux**: `catalogHandler` не вызывался.

А путь, для которого нет вообще ни одного паттерна, — это собственный `404` mux ([GB-4.04](/lab/youtube/gb/gb-4-04/ru)):

```console
$ curl -i http://localhost:8765/narsalar
HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:02:14 GMT
Content-Length: 19

404 page not found
```

### Правило mux

Теперь соберём в одном месте, как mux принимает решение:

```text
запрос: МЕТОД + ПУТЬ
   │
   ├─ есть паттерн с подходящими и методом, и путём ──► вызывается handler(w, r)
   │
   ├─ подходит только путь ───────────────────────────► mux сам: 405 + Allow
   │
   └─ путь тоже не подходит ──────────────────────────► mux сам: 404 page not found
```

Наш код работает только в первом из трёх исходов. Остальные два пишет mux: в обработчике нет ни `405`, ни «путь не найден».

## `{id}`: переменная часть пути

Теперь один товар. В паттерне переменная часть пути берётся в фигурные скобки: `{id}` — это **wildcard**. Он принимает **один сегмент**: одну часть между двумя слешами.

```text
GET /products/{id}
/products/3          id = "3"
/products/abc        id = "abc"
/products/3/stock    не подходит
```

| Путь | Результат | Причина |
|---|---|---|
| `/products/3` | `id = "3"` | `3` — один сегмент |
| `/products/abc` | `id = "abc"` | паттерн **не проверяет**, что это число: подходит любая строка |
| `/products/3/stock` | не подходит | `3/stock` — два сегмента, а `{id}` берёт один |

Важно: `id` — всегда **строка** (`string`). Превратить её в число — наша задача.

Перепишем `productHandler`: в GB-4.04 он всегда отдавал яблоко.

```go
func productHandler(w http.ResponseWriter, r *http.Request) {
	id, err := strconv.ParseInt(r.PathValue("id"), 10, 64)
	if err != nil {
		http.Error(w, "id butun son boʻlishi kerak", http.StatusBadRequest)
		return
	}
```

| Строка | Код | Что делает |
|---|---|---|
| 1 | `func productHandler(w http.ResponseWriter, r *http.Request) {` | сигнатура обработчика из GB-4.03 |
| 2 | `r.PathValue("id")` | возвращает значение, которое mux нашёл в пути, как **строку**. Имя в скобках должно совпадать с `{id}` в паттерне |
| 2 | `strconv.ParseInt(…, 10, 64)` | превращает строку в число ([GB-3.06](/lab/youtube/gb/gb-3-06/ru)): `10` — десятичная система, `64` — `int64`. Возвращает два значения: число и ошибку (`id`, `err`) |
| 3 | `if err != nil {` | если ошибка (`abc` не число), входим в блок |
| 4 | `http.Error(w, "id butun son boʻlishi kerak", http.StatusBadRequest)` | пишет ответ: `Content-Type` — простой текст, затем статус `400`, затем сообщение (`id butun son boʻlishi kerak` — «id должен быть целым числом»). Порядок как в GB-4.03: заголовки → статус → тело |
| 5 | `return` | выход из обработчика. `http.Error` **не останавливает** обработчик: без `return` код пойдёт дальше (ниже, в «Частых ошибках», это видно) |

`StatusBadRequest` — это `400`: сам запрос неверен. Дальше: число есть, ищем товар. `findProduct` — та самая функция из GB-2.04:

```go
func findProduct(products []Product, id int64) *Product {
	for i := range products {
		if products[i].ID == id {
			return &products[i]
		}
	}
	return nil
}
```

Если товар найден, возвращается указатель на товар внутри слайса (`&products[i]`), если нет — `nil`. Продолжение обработчика:

```go
	p := findProduct(catalog, id)
	if p == nil {
		http.Error(w, "mahsulot topilmadi", http.StatusNotFound)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(p)
}
```

`p` — это `*Product`. Если `nil`: `StatusNotFound` (`404`), сообщение `mahsulot topilmadi` («товар не найден»), `return`. Если найден: как в GB-4.03, `Content-Type`, затем `Encode`.

Последний шаг — маршрут. Вместо `"/products/1"`:

```go
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", healthHandler)
	mux.HandleFunc("GET /products", catalogHandler)
	mux.HandleFunc("GET /products/{id}", productHandler)
```

**Маршрут (route)** = паттерн плюс его обработчик. Перезапускаем сервер (в первом терминале `go run .`) и из второго отправляем три запроса.

```console
$ curl -i http://localhost:8765/products/3
HTTP/1.1 200 OK
Content-Type: application/json
Date: Fri, 27 Nov 2026 12:02:14 GMT
Content-Length: 51

{"id":3,"name":"oʻrik","price":3500000,"stock":5}
```

`200`, в теле абрикос (`oʻrik`); цена в тиынах ([GB-1.03](/lab/youtube/gb/gb-1-03/ru)). `PathValue` вернул строку `"3"`, `ParseInt` превратил её в число, `findProduct` нашёл абрикос.

```console
$ curl -i http://localhost:8765/products/99
HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:02:14 GMT
Content-Length: 19

mahsulot topilmadi
```

`99` нет: снова `404`, но тело другое: `mahsulot topilmadi`. Это **наш** `404`: путь подошёл, обработчик сработал.

```console
$ curl -i http://localhost:8765/products/abc
HTTP/1.1 400 Bad Request
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:02:14 GMT
Content-Length: 29

id butun son boʻlishi kerak
```

`abc` подходит под паттерн, но `ParseInt` не может его прочитать: `400 Bad Request`. (`Content-Length: 29`: символ `ʻ` занимает два байта, [GB-2.10](/lab/youtube/gb/gb-2-10/ru).)

Значит, `404` бывает двух видов. Это главное различение урока:

| Запрос | Статус | Кто написал | Тело |
|---|---|---|---|
| `GET /narsalar` | `404` | mux: пути нет | `404 page not found` |
| `GET /products/99` | `404` | обработчик (наш код): путь есть, товара нет | `mahsulot topilmadi` |
| `GET /products/abc` | `400` | обработчик: id не число | `id butun son boʻlishi kerak` |
| `POST /products` | `405` | mux: путь есть, метода нет | `Method Not Allowed` + `Allow: GET, HEAD` |

`{id}` берёт только **один** сегмент. Поэтому и путь со слешем в конце, и путь из трёх сегментов получают `404` от mux:

```console
$ curl -i http://localhost:8765/products/3/
HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:02:14 GMT
Content-Length: 19

404 page not found
$ curl -i http://localhost:8765/products/3/stock
HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:02:14 GMT
Content-Length: 19

404 page not found
```

(`/products/3/stock` — маршрут, который вы напишете в задании; пока его никто не принимает. `/products/3/` в видео нет, он есть в README папки: я перезапустил и его.)

Паттерн `GET` принимает и `HEAD`. `curl -I` отправляет `HEAD` и показывает только заголовки:


Теперь тест, в форме из GB-4.03: запрос `/products/3`, recorder и прямой вызов `productHandler`. Ожидаем статус `200`.

Ответ: `PathValue` **заполняет mux**. Когда запрос подходит под паттерн, mux записывает значение `id = "3"` в сам запрос (в `r`) и только потом вызывает обработчик. Мы вызвали обработчик без mux: в запросе нет `id`, `PathValue` вернул пустую строку (`""`), `ParseInt("")` дал ошибку ([Request.PathValue](https://pkg.go.dev/net/http#Request.PathValue): `""`, если запрос не сопоставлялся с паттерном).

```text

прямой вызов:
тест ──► productHandler(rec, req)          (mux нет, в r нет id)
                                           r.PathValue("id") → ""  →  ParseInt: ошибка  →  400
```

Исправление: пропустим через mux и тест. Для этого вынесем маршруты из `newServer` в отдельную функцию `newMux`. Она создаёт mux, добавляет маршруты и возвращает его. Тип результата — `*http.ServeMux`: именно этот указатель возвращает `http.NewServeMux()`.

```go
func newMux() *http.ServeMux {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", healthHandler)
	mux.HandleFunc("GET /products", catalogHandler)
	mux.HandleFunc("GET /products/{id}", productHandler)
	return mux
}
```

Теперь `newServer` передаёт в поле `Handler` вызов `newMux()`. Остальное как в GB-4.04: адрес и `ReadHeaderTimeout`.

```go
func newServer(addr string) *http.Server {
	return &http.Server{
		Addr:              addr,
		Handler:           newMux(),
		ReadHeaderTimeout: 5 * time.Second,
	}
}
```

В тесте меняется одна строка: вместо `productHandler(rec, req)` — `newMux().ServeHTTP(rec, req)`. `ServeHTTP` — метод интерфейса `Handler` из GB-4.03: **mux тоже `Handler`**. Он выбирает паттерн, записывает `id` и вызывает обработчик.

## Паттерн `"/"` поглощает всё

Теперь главная страница. `homeHandler` пишет на пути `/` название API:

```go
func homeHandler(w http.ResponseWriter, r *http.Request) {
	fmt.Fprintln(w, "bozor API")
}

// newMux ichida:
	mux.HandleFunc("/", homeHandler)
```

Во многих примерах паттерн главной страницы именно такой: только `/`, без метода. Перезапускаем сервер. Клиент ошибся в пути: вместо `products` написал `produkts`. Такого пути в таблице нет.

```bash
curl -i http://localhost:8765/produkts/3
```

**Предсказание.** Паттерн `"/"` есть. Что вернёт `GET /produkts/3`?

**A)** `404 page not found` · **B)** `200` и `bozor API` · **C)** `400 Bad Request`

<details>
<summary>Ответ</summary>

**B: `200` и `bozor API`.** Правило GB-4.04: паттерн со слешем в конце принимает **все** пути, которые с него начинаются. А с `/` начинаются все пути. Если вы выбрали **A**, вы решили, что `produkts` в таблице нет; но паттерн `/` подходит и ему. **C** — `400` пишет только `productHandler`, этот запрос до него не доходит.

</details>

```console
$ curl -i http://localhost:8765/produkts/3
HTTP/1.1 200 OK
Date: Fri, 27 Nov 2026 12:02:15 GMT
Content-Length: 10
Content-Type: text/plain; charset=utf-8

bozor API
$ curl -i http://localhost:8765/products/3
HTTP/1.1 200 OK
Content-Type: application/json
Date: Fri, 27 Nov 2026 12:02:15 GMT
Content-Length: 51

{"id":3,"name":"oʻrik","price":3500000,"stock":5}
```

`/produkts/3` — `200` и `bozor API`. А `/products/3` идёт в `productHandler`: если подходят два паттерна, выигрывает **более точный** (что значит «точнее», — в разделе «Глубже»).

**Предсказание.** Теперь `POST /products/3`. `"/"` всё ещё на месте.

```bash
curl -i -X POST http://localhost:8765/products/3
```

**A)** `405 Method Not Allowed` · **B)** `200` и `bozor API` · **C)** `404 page not found`

<details>
<summary>Ответ</summary>

**B: `200`.** Вспомните правило mux: сначала ищется паттерн, у которого совпадают **и метод, и путь**. У `"/"` метода нет, поэтому он принимает и `POST`, и этот путь. Подходящий паттерн найден, до `405` mux не доходит.
Если вы выбрали **A**, вы решили: «путь есть в `GET /products/{id}`, метода нет». Но раз подошёл и `"/"`, случая «совпал только путь» не возникает.

</details>

```console
$ curl -i -X POST http://localhost:8765/products/3
HTTP/1.1 200 OK
Date: Fri, 27 Nov 2026 12:02:15 GMT
Content-Length: 10
Content-Type: text/plain; charset=utf-8

bozor API
```

Итог: и неверный адрес, и неверный метод получают `200`. Клиент не видит своей ошибки, и такая ошибка долго остаётся незамеченной.

| Запрос | С `"/"` | Должно быть |
|---|---|---|
| `GET /produkts/3` | `200` `bozor API` | `404` |
| `POST /products/3` | `200` `bozor API` | `405` |

Исправление: ограничим паттерн. `{$}` значит «путь заканчивается здесь». `"GET /{$}"` принимает только ровно путь `/` и только `GET`:

```go
// newMux ichida:
	mux.HandleFunc("GET /{$}", homeHandler)
```

| Часть | Смысл |
|---|---|
| `GET` | только `GET` (и `HEAD`) |
| `/` | путь начинается с `/` … |
| `{$}` | … и на этом заканчивается: других сегментов нет |

Перезапускаем сервер:

```console
$ curl -i http://localhost:8765/produkts/3

Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:02:15 GMT
Content-Length: 19

404 page not found
$ curl -i -X POST http://localhost:8765/products/3
```

Неверный путь снова даёт `404`, `POST` снова даёт `405`. Сама главная страница по-прежнему работает (`curl -i http://localhost:8765/` — `200` и `bozor API`; это я тоже запускал, и оно проверяется в `TestHome` из папки).

## Глубже (необязательно): приоритет и конфликт

Если под один запрос подходят два паттерна, mux выбирает **более точный**. «Точнее» значит: каждый запрос точного паттерна принимает и второй, но не наоборот ([ServeMux, Precedence](https://pkg.go.dev/net/http#ServeMux)). Поэтому, когда рядом стоят `"/"` и `GET /products/{id}`, `/products/3` идёт в `productHandler`. Порядок регистрации не важен.

А если оба паттерна принимают одни и те же запросы и ни один не точнее? Добавим такой же паттерн с другим именем wildcard:

```go
	mux.HandleFunc("GET /products/{id}", productHandler)
	mux.HandleFunc("GET /products/{name}", productHandler)
```

Оба принимают одни и те же запросы. В первом терминале `go run .`:

```console
$ go run .

goroutine 1 [running]:
```

## Частые ошибки

### 1. «`{id}` проверяет, что это число»

`{id}` принимает любой один сегмент: `/products/abc` тоже подходит (мы видели выше). Проверка — в обработчике: `ParseInt` → `400`. Если довериться паттерну и использовать `PathValue` без проверки, `abc` внутри обработчика станет неожиданным случаем.
Ещё про `ParseInt`: он читает и `+3`, и `03` как `3` (несколько URL на один товар), а слишком большое число, не помещающееся в `int64`, получает `400` (пометка из README; эти два случая я не перезапускал). В боевом API можно отвергать и `id < 1`; в этом уроке этого нет ради простоты.

### 2. `"/"` — паттерн, который поглощает всё

Вы видели это в середине урока: `mux.HandleFunc("/", homeHandler)` — `200` и на неверный путь, и на неверный метод. Это **тихая** ошибка: никакой ошибки нет, ответ неверный. Исправление — `"GET /{$}"` (раздел выше «Паттерн `"/"` поглощает всё»).

### 3. Забыть `return` после `http.Error`

`http.Error` пишет ответ, но не останавливает обработчик. Уберём `return` (в блоке `400` функции `productHandler` удалите строку `return`; я сделал это в копии папки, в самой папке курса такого изменения нет):

```go
func productHandler(w http.ResponseWriter, r *http.Request) {
	id, err := strconv.ParseInt(r.PathValue("id"), 10, 64)
	if err != nil {
		http.Error(w, "id butun son boʻlishi kerak", http.StatusBadRequest)
	}
	p := findProduct(catalog, id)
	if p == nil {
		http.Error(w, "mahsulot topilmadi", http.StatusNotFound)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(p)
}
```

Остальная часть файла такая же, как в `main.go`. Запускаем сервер и запрашиваем `abc`:

```console
$ curl -i http://localhost:8765/products/abc
HTTP/1.1 400 Bad Request
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:03:01 GMT
Content-Length: 48

id butun son boʻlishi kerak
mahsulot topilmadi
```

В статусе `400`, но в теле **два** сообщения. Причина: при ошибке `ParseInt` значение `id` — `0`; `return` нет, код пошёл дальше, `findProduct(catalog, 0)` вернул `nil`, и `http.Error` вызвался второй раз. Первый ответ уже ушёл, поэтому статус `404` второго вызова был проигнорирован, а текст просто дописался. Терминал с сервером пишет об этом в лог:

```text
2026/11/27 17:03:01 http: superfluous response.WriteHeader call from main.productHandler (main.go:67)
```

(Это строка из лога сервера; время — по местным часам. `superfluous response.WriteHeader call` — «лишний вызов `WriteHeader`»: статус пытались записать второй раз, `main.go:67` — этот вызов.) Исправление: после `http.Error` всегда пишите `return`. `tekshiruv_test.go` из папки тоже сравнивает тело точно и ловит это.

### 4. Имя в `PathValue` не совпадает с именем в паттерне

В паттерне `{id}`, а в обработчике `r.PathValue("product")` — имя в скобках должно быть тем же. В копии папки я заменил ровно одну строку: вместо `r.PathValue("id")` — `r.PathValue("product")`.

```console
$ curl -i http://localhost:8765/products/3
HTTP/1.1 400 Bad Request
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:03:02 GMT
Content-Length: 29

id butun son boʻlishi kerak
```

В пути есть `3`, а ответ `400`. Ни компилятор, ни mux ошибки не показывают: `PathValue("product")` просто возвращает пустую строку, как и в тесте без mux. Признак: «`400` на верный id». Проверьте: совпадают ли имя внутри `{…}` и `PathValue("…")`.

### 5. Слеш в конце и `{id}`

`/products/3/` — это `404` от mux: `{id}` — только один сегмент, а слеш начинает новый (пустой) сегмент (результат `curl` выше). Просите клиента писать `/products/3`; не «исправляйте» `{id}`, добавляя слеш.

## Проверьте себя

**1.** Есть только паттерн `GET /products/{id}`. Пришёл `POST /products/3`: какие статус и заголовок? Кто их пишет?

<details>
<summary>Ответ</summary>

`405 Method Not Allowed` и `Allow: GET, HEAD`. Ответ пишет mux: есть паттерн с подходящим путём, но метод не подходит. Обработчик не вызывается.

</details>

**2.** Вы вызвали `productHandler(rec, req)` в тесте напрямую. Почему `PathValue("id")` пуст?

<details>
<summary>Ответ</summary>

`PathValue` заполняет **mux**, выбравший паттерн: он записывает `id = "3"` в запрос и только потом вызывает обработчик. При прямом вызове mux нет, в запросе нет `id`, поэтому `""`. Исправление: пропустить тест через `newMux().ServeHTTP(rec, req)`.

</details>

</details>

**4.** Предсказание: есть только эти маршруты: `GET /{$}`, `GET /health`, `GET /products`, `GET /products/{id}`. Что вернёт `curl -i http://localhost:8765/products/1/stock`?

`404 page not found` от mux: `{id}` берёт один сегмент, а `/products/1/stock` — три сегмента, ни один паттерн не подходит. Я перезапустил это на `main.go` с нерешённым заданием:

</details>

**5.** Есть `"/"` и `GET /products/3`. В какой обработчик пойдёт `GET /products/3` и почему?

<details>
<summary>Ответ</summary>

В `productHandler`. Оба паттерна подходят, но `GET /products/{id}` точнее: каждый его запрос принимает и `"/"`, но не наоборот. Выигрывает более точный; порядок не важен (в `curl` выше `/products/3` — JSON).

</details>
