## What you will learn

Every product in the bozor catalog has an ID, and the client asks for it in the path: `/products/1`, `/products/3`. You cannot write a separate pattern for every ID.
The question: how does one rule accept every ID? And who answers `404` for a missing product and `405` for a wrong method: the mux or our handler?

**One idea:** for every request, `ServeMux` first looks for a pattern where **both the method and the path** match. If it finds one, it writes the value of a wildcard such as `{id}` into the request (`r.PathValue("id")`, a string) and calls the handler.
If it finds none: when a pattern matches the path, the mux itself writes `405` + `Allow`; when no pattern matches even the path, the mux itself writes `404 page not found`.
So the handler is left with only the errors it alone knows about: `ParseInt` → `400`, `findProduct` → our own `404`. If a handler is called without the mux, `PathValue` is empty.
And a pattern `"/"` with no method matches every path and every method, so it swallows the `404` and the `405`; `"GET /{$}"` limits it.

By the end of the lesson you can:

- write the method in a pattern (`"GET /products/{id}"`) and use `curl` to tell `200`, your own `404`/`400`, and the mux's `404`/`405` apart;
- read the part of the path with `r.PathValue("id")`, turn it into a number with `strconv.ParseInt`, and find the product with `findProduct`;
- collect the routes in a `newMux()` function and test them without a server using `newMux().ServeHTTP(rec, req)`;
- explain why the `"/"` pattern answers `200` to a wrong path and to a wrong method, and fix it with `"GET /{$}"`;
- write the `GET /products/{id}/stock` route yourself in `TASK.md`, until `go test .` passes.

Today's three core new ideas:

| Word | Plain meaning | English term |
|---|---|---|
| pattern = `METHOD path` | the first argument of `mux.HandleFunc`: which method and which path it matches. If nothing matches, the mux writes the answer: `404` or `405` + `Allow` | pattern (method + path) |
| `{id}` + `r.PathValue("id")` | a variable part of the path that matches one segment; the mux writes its value into the request, the handler reads it as a string | wildcard, `PathValue` |
| `"/"` and `"GET /{$}"` | `"/"` is a pattern for every path (and, with no method, every method); `{$}` means "the path ends here" | catch-all pattern, `{$}` |

Helper names: `http.Error(w, message, code)` and `newMux()`. I give every other new name one sentence where it appears.

## The method goes in the pattern

In GB-4.03, `catalogHandler` checked the method itself:

```go
func catalogHandler(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodGet {
		w.Header().Set("Allow", http.MethodGet)
		w.WriteHeader(http.StatusMethodNotAllowed)
		return
	}
	// … catalog'ni JSON qilib yozish (GB-4.03)
}
```

Five lines for one thing: if the method is not `GET`, write `405` + `Allow` and leave. Every handler would have to repeat this. Since Go 1.22 ([Go 1.22 release notes](https://go.dev/doc/go1.22#enhanced_routing_patterns)) the pattern does this check itself: the method is written in front of the path.

```text
METHOD  PATH
GET     /products
HEAD    /products   (the GET pattern takes it)
```

The rule: method, space, then path. `GET /products` means "a `GET` request **and** exactly this path". A pattern with no method (`/products`) takes every method.
A `GET` pattern also takes a `HEAD` request: `HEAD` asks for the same response as `GET`, but without a body ([RFC 9110, HEAD](https://www.rfc-editor.org/rfc/rfc9110#name-head)).

Two lines in `newServer` change like this: the method is added to the first argument, and the second argument — the handler — stays the same:

```go
func newServer(addr string) *http.Server {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", healthHandler)
	mux.HandleFunc("GET /products", catalogHandler)
```

Now we remove the `r.Method` check from `catalogHandler`: a request that is neither `GET` nor `HEAD` no longer reaches the handler.

```go
func catalogHandler(w http.ResponseWriter, r *http.Request) {
	products := catalog
	if products == nil {
		products = []Product{}
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(products)
}
```

The rest is the GB-4.03 task itself: even if `catalog` is empty, the JSON is `[]` (not `null`), then `Content-Type`, then `Encode`. The whole file comes later, in "The full code from the folder".

### The mux rule

Now we put in one place how the mux decides:

```text
request: METHOD + PATH
   │
   ├─ a pattern matches both the method and the path ──► handler(w, r) is called
   │
   ├─ a pattern matches only the path ────────────────► mux itself: 405 + Allow
   │
   └─ not even the path matches ──────────────────────► mux itself: 404 page not found
```

Only in the first of the three outcomes does our code run. The mux writes the other two: the handler contains neither a `405` nor a "path not found".

## `{id}`: a variable part of the path

Now one product. In a pattern, the variable part of the path is put in curly braces: `{id}` is a **wildcard**. It matches **one segment**: one part between two slashes.

```text
GET /products/{id}
/products/3          id = "3"
/products/abc        id = "abc"
/products/3/stock    no match
```

| Path | Result | Reason |
|---|---|---|
| `/products/3` | `id = "3"` | `3` is one segment |
| `/products/abc` | `id = "abc"` | the pattern does **not check** that it is a number: any string matches |
| `/products/3/stock` | no match | `3/stock` is two segments, and `{id}` takes one |

Important: `id` is always a **string** (`string`). Turning it into a number is our job.

We rewrite `productHandler`: in GB-4.04 it always returned the apple.

```go
func productHandler(w http.ResponseWriter, r *http.Request) {
	id, err := strconv.ParseInt(r.PathValue("id"), 10, 64)
	if err != nil {
		http.Error(w, "id butun son boʻlishi kerak", http.StatusBadRequest)
		return
	}
```

| Line | Code | What it does |
|---|---|---|
| 1 | `func productHandler(w http.ResponseWriter, r *http.Request) {` | the handler signature from GB-4.03 |
| 2 | `r.PathValue("id")` | returns the value the mux found in the path, as a **string**. The name in the parentheses must be the same as `{id}` in the pattern |
| 2 | `strconv.ParseInt(…, 10, 64)` | turns the string into a number ([GB-3.06](/lab/youtube/gb/gb-3-06/en)): `10` is base ten, `64` is `int64`. It returns two values: the number and an error (`id`, `err`) |
| 3 | `if err != nil {` | if there is an error (`abc` is not a number), we enter the block |
| 4 | `http.Error(w, "id butun son boʻlishi kerak", http.StatusBadRequest)` | writes the response: `Content-Type` plain text, then status `400`, then the message (`id butun son boʻlishi kerak` means "id must be a whole number"). The order is as in GB-4.03: headers → status → body |
| 5 | `return` | leaves the handler. `http.Error` does **not stop** the handler: without `return` the code goes on (you see it below, in "Common mistakes") |

`StatusBadRequest` is `400`: the request itself is wrong. Next: we have a number, now we find the product. `findProduct` is the same function from GB-2.04:

```go
func findProduct(products []Product, id int64) *Product {
	for i := range products {
		if products[i].ID == id {
			return &products[i]
		}
	}
	return nil
}
```

If the product is found, it returns a pointer to the product inside the slice (`&products[i]`); if not, `nil`. The rest of the handler:

```go
	p := findProduct(catalog, id)
	if p == nil {
		http.Error(w, "mahsulot topilmadi", http.StatusNotFound)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(p)
}
```

`p` is a `*Product`. If it is `nil`: `StatusNotFound` (`404`), the message `mahsulot topilmadi` ("product not found"), `return`. If it is found: as in GB-4.03, `Content-Type`, then `Encode`.

The last step: the route. Instead of `"/products/1"`:

```go
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", healthHandler)
	mux.HandleFunc("GET /products", catalogHandler)
	mux.HandleFunc("GET /products/{id}", productHandler)
```

A **route** is a pattern plus its handler. We restart the server (`go run .` in the first terminal) and send three requests from the second.

`200`, the apricot (`oʻrik`) in the body; the price is in tiyin ([GB-1.03](/lab/youtube/gb/gb-1-03/en)). `PathValue` returned the string `"3"`, `ParseInt` turned it into a number, `findProduct` found the apricot.

```console
$ curl -i http://localhost:8765/products/99
HTTP/1.1 404 Not Found

X-Content-Type-Options: nosniff

Content-Length: 19

mahsulot topilmadi
```

There is no `99`: `404` again, but the body is different: `mahsulot topilmadi`. This is **our** `404`: the path matched, the handler ran.

```console
$ curl -i http://localhost:8765/products/abc
HTTP/1.1 400 Bad Request
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:02:14 GMT
Content-Length: 29
```

`abc` matches the pattern, but `ParseInt` cannot read it: `400 Bad Request`. (`Content-Length: 29`: the character `ʻ` is two bytes, [GB-2.10](/lab/youtube/gb/gb-2-10/en).)

So there are two kinds of `404`. This is the main distinction of the lesson:

| Request | Status | Who wrote it | Body |
|---|---|---|---|
| `GET /narsalar` | `404` | the mux: no such path | `404 page not found` |
| `GET /products/99` | `404` | the handler (our code): the path exists, the product does not | `mahsulot topilmadi` |
| `GET /products/abc` | `400` | the handler: id is not a number | `id butun son boʻlishi kerak` |
| `POST /products` | `405` | the mux: the path exists, the method does not | `Method Not Allowed` + `Allow: GET, HEAD` |

`{id}` takes only **one** segment. That is why both a path with a trailing slash and a three-segment path get the mux's `404`:

## In a test, `PathValue` is empty

Now a test, in the shape from GB-4.03: the request `/products/3`, a recorder, and a direct call of `productHandler`. We expect status `200`.

```go filename="_video/02-test-direct/handler_test.go" showLineNumbers
package main

import (

func TestProduct(t *testing.T) {
	req := httptest.NewRequest(http.MethodGet, "/products/3", nil)
	rec := httptest.NewRecorder()
	productHandler(rec, req)
	if rec.Code != http.StatusOK {
		t.Errorf("status %d, kutilgan %d: %s", rec.Code, http.StatusOK, rec.Body.String())

```

| Line | Code | What it does |
|---|---|---|
| 10 | `httptest.NewRequest(http.MethodGet, "/products/3", nil)` | builds the request `GET /products/3` (GB-4.03) |
| 11 | `httptest.NewRecorder()` | a `w` that keeps the response |
| 12 | `productHandler(rec, req)` | we call the handler like an ordinary function |
| 13–15 | `if rec.Code != http.StatusOK { t.Errorf(…) }` | if the status is not `200`, the test fails and prints the status and the body (`%d` — a number, `%s` — a string) |

**Predict.** What does `go test` say?

**A)** `PASS`: status `200` · **B)** `FAIL`: status `404` · **C)** `FAIL`: status `400`

<details>
<summary>Answer</summary>

**C: `400`.** The output is below. If you chose **A**, you thought the path has `3`, so `id = "3"`. **B** — that `id = "3"` but `findProduct` will not find the product: it would find `3`. But the handler does not even get that far: `3` never arrives at `ParseInt`.

</details>

```console
$ go test
--- FAIL: TestProduct (0.00s)
    handler_test.go:14: status 400, kutilgan 200: id butun son boʻlishi kerak
FAIL
exit status 1
FAIL	github.com/abdurahmon27/bozor	0.002s
```

We read it: `handler_test.go:14` is the `t.Errorf` on line 14; the end of the message is the body: `id butun son boʻlishi kerak`, that is, `ParseInt` returned an error, `id` is not a number. But the path had `3`. Why?

The answer: **the mux fills in** `PathValue`. When a request matches a pattern, the mux writes the value `id = "3"` into the request itself (into `r`) and only then calls the handler. We called the handler without the mux: the request has no `id`, `PathValue` returned an empty string (`""`), and `ParseInt("")` gave an error ([Request.PathValue](https://pkg.go.dev/net/http#Request.PathValue): `""` if the request was not matched against a pattern).

```text
through the mux:
GET /products/3 ──► mux: pattern matches ──► id = "3" is written into r ──► productHandler(w, r)
                                                                            r.PathValue("id") → "3"

direct call:
test ──► productHandler(rec, req)          (no mux, no id in r)
                                           r.PathValue("id") → ""  →  ParseInt error  →  400
```

The fix: we send the test through the mux too. For that we move the routes out of `newServer` into a separate function, `newMux`. It creates a mux, adds the routes and returns it. The result type is `*http.ServeMux`: that is the pointer `http.NewServeMux()` returns.

```go
func newMux() *http.ServeMux {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", healthHandler)
	mux.HandleFunc("GET /products", catalogHandler)
	mux.HandleFunc("GET /products/{id}", productHandler)
	return mux
}
```

`newServer` now gives the `Handler` field the call `newMux()`. The rest is the same as in GB-4.04: the address and `ReadHeaderTimeout`.

```go
func newServer(addr string) *http.Server {
	return &http.Server{
		Addr:              addr,
		Handler:           newMux(),
		ReadHeaderTimeout: 5 * time.Second,
	}
}
```

In the test one line changes: instead of `productHandler(rec, req)`, `newMux().ServeHTTP(rec, req)`. `ServeHTTP` is the method of the `Handler` interface from GB-4.03: **the mux is a `Handler` too**. It picks the pattern, writes `id` and calls the handler.

## The `"/"` pattern swallows everything

Now the home page. `homeHandler` writes the name of the API on the path `/`:

```go

// newMux ichida:
	mux.HandleFunc("/", homeHandler)
```

In many examples the pattern of the home page is exactly this: only `/`, no method. We restart the server. A client made a mistake in the path: `produkts` instead of `products`. There is no such path in the table.

**A)** `404 page not found` · **B)** `200` and `bozor API` · **C)** `400 Bad Request`

## Going deeper (optional): precedence and conflict

When two patterns match one request, the mux picks the **more specific** one. "More specific" means: every request of the specific pattern is also matched by the other one, but not the other way round ([ServeMux, Precedence](https://pkg.go.dev/net/http#ServeMux)). That is why, with `"/"` and `GET /products/{id}` side by side, `/products/3` goes to `productHandler`. The order of registration does not matter.

What if both patterns match the same requests and neither is more specific? We add the same pattern with a different wildcard name:

```go
	mux.HandleFunc("GET /products/{id}", productHandler)
	mux.HandleFunc("GET /products/{name}", productHandler)
```

Both match the same requests. In the first terminal, `go run .`:

```console
$ go run .
panic: pattern "GET /products/{name}" (registered at …/bozor/main.go:82) conflicts with pattern "GET /products/{id}" (registered at …/bozor/main.go:81):
	GET /products/{name} matches the same requests as GET /products/{id}

goroutine 1 [running]:
net/http.(*ServeMux).register(...)

net/http.(*ServeMux).HandleFunc(0x101013ebe74e560?, {0x6f75d0?, 0x7c3ebe75a2e8?}, 0x70?)
	$GOMODCACHE/golang.org/toolchain@v0.0.1-go1.27.4.linux-amd64/src/net/http/server.go:2955 +0x5e

	…/bozor/main.go:82 +0xb0
```

(`…/bozor` is the path of my temporary folder and `$GOMODCACHE` is the Go module cache: I shortened them; `_video/chiqishlar.txt` does the same. The `0x…` addresses in the stack differ on every run.)

Reading it: the program fails with a `panic` right at startup. `conflicts with` means the two patterns clash. The second line gives the reason: the `{name}` pattern matches **the same requests** as `{id}`, neither is more specific, and the mux cannot choose. The stack line `main.newMux()` points to line 82 of your `newMux`.
This is good: the error appears **at startup**, not at request time, before any client sees it.

## Common mistakes

### 1. Thinking "`{id}` checks that it is a number"

`{id}` matches any single segment: `/products/abc` matches too (we saw it above). The check is in the handler: `ParseInt` → `400`. If you trust the pattern and use `PathValue` without checking, `abc` becomes an unexpected case inside the handler.
More about `ParseInt`: it reads `+3` and `03` as `3` too (several URLs for one product), and a number too large for `int64` gets `400` (a note from the README; I did not re-run these two). In a production API you can also reject `id < 1`; this lesson leaves it out for simplicity.

### 2. `"/"` — the pattern that swallows everything

You saw this in the middle of the lesson: `mux.HandleFunc("/", homeHandler)` gives `200` to a wrong path and to a wrong method. This is a **silent** bug: there is no error, and the answer is wrong. The fix is `"GET /{$}"` (see the section above, "The `"/"` pattern swallows everything").

### 3. Forgetting `return` after `http.Error`

`http.Error` writes the response, but does not stop the handler. We remove `return` (in the `400` block of `productHandler`, delete the `return` line; I did this in a copy of the folder, so the course folder has no such change):

```go
func productHandler(w http.ResponseWriter, r *http.Request) {
	id, err := strconv.ParseInt(r.PathValue("id"), 10, 64)
	if err != nil {
		http.Error(w, "id butun son boʻlishi kerak", http.StatusBadRequest)
	}
	p := findProduct(catalog, id)
	if p == nil {
		http.Error(w, "mahsulot topilmadi", http.StatusNotFound)
		return
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(p)
}
```

The rest of the file is the same as `main.go`. We start the server and request `abc`:

```console
$ curl -i http://localhost:8765/products/abc
HTTP/1.1 400 Bad Request
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:03:01 GMT
Content-Length: 48

id butun son boʻlishi kerak
mahsulot topilmadi
```

The status is `400`, but the body has **two** messages. The reason: when `ParseInt` fails, `id` is `0`; there is no `return`, the code went on, `findProduct(catalog, 0)` returned `nil`, and `http.Error` was called a second time. The first response had already gone out, so the `404` status of the second call was ignored and only its text was added. The terminal where the server runs writes this to the log:

```text
2026/11/27 17:03:01 http: superfluous response.WriteHeader call from main.productHandler (main.go:67)
```

(This is a line from the server log; the time is by the local clock. `superfluous response.WriteHeader call` means an extra `WriteHeader` call: someone tried to write the status a second time, and `main.go:67` is that call.) The fix: always write `return` after `http.Error`. `tekshiruv_test.go` in the folder compares the body exactly and catches this too.

### 4. The name in `PathValue` does not match the name in the pattern

The pattern says `{id}` and the handler says `r.PathValue("product")` — the name in the parentheses must be the same. In a copy of the folder I replaced exactly one line: `r.PathValue("product")` instead of `r.PathValue("id")`.

```console
$ curl -i http://localhost:8765/products/3

Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Fri, 27 Nov 2026 12:03:02 GMT
Content-Length: 29

id butun son boʻlishi kerak
```

The path has `3`, and the response is `400`. Neither the compiler nor the mux reports an error: `PathValue("product")` simply returns an empty string, just as in the test without the mux. The symptom: "`400` for a valid id". Check whether the name inside `{…}` and `PathValue("…")` are the same.

### 5. A trailing slash and `{id}`

`/products/3/` gets the mux's `404`: `{id}` is only one segment, and the slash starts a new (empty) segment (see the `curl` result above). Ask the client to write `/products/3`; do not "fix" `{id}` by adding a slash.
