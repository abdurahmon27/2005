## What you will learn

The order was inserted, apple stock decreased, but there was not enough bread. The function returned an error. Is half an order left in the database?

**The one idea:** a **transaction** groups changes across tables: either they all commit, or the table changes are rolled back. In Go every statement goes through one `tx`.

After this lesson you will:

- find a partial order left without a transaction, using SQL;
- distinguish `BEGIN`, `COMMIT`, `ROLLBACK` and an aborted transaction;
- write `PlaceOrder` with `pool.Begin`, `defer tx.Rollback(ctx)` and `tx.Commit(ctx)`;
- find a statement sent through the pool instead of `tx`, and check the homework against real Postgres.

| Word | Plain meaning | English term |
|---|---|---|
| transaction | a group of statements committed or rolled back together | transaction |
| aborted transaction | a state in which ordinary statements are rejected after a SQL error | aborted transaction |
| pgx transaction | `tx`, which manages a transaction on one connection acquired from the pool | pgx transaction |

Two helper concepts: `UPDATE … SET` changes a value in an existing row. **SQLSTATE** is Postgres's five-character code for an error category.

## SQL: BEGIN and ROLLBACK

A **transaction** groups these writes. `BEGIN` starts it; the same connection sees its own new values. Other connections do not see uncommitted table changes. `COMMIT` saves them; `ROLLBACK` cancels them.

| Stage | This connection | Another connection |
|---|---|---|
| before `BEGIN` | apple `38` | apple `38` |
| after `UPDATE … - 2` | apple `36` | committed apple `38` |
| after `ROLLBACK` | apple `38` | apple `38` |
| with a successful `COMMIT` instead | apple `36` | a later read can see `36` |

This table assumes ordinary separate queries. A long-lived read snapshot in another transaction is outside this lesson.

```sql filename="bekor.sql" showLineNumbers
BEGIN;
UPDATE products SET stock = stock - 2 WHERE id = 1;
SELECT stock FROM products WHERE id = 1;
ROLLBACK;
SELECT stock FROM products WHERE id = 1;
```

Line 1 begins, line 2 decreases stock, line 3 reads the internal value. Line 4 rolls back; line 5 reads again. `;` ends a SQL statement.

What does the last `SELECT` print? **A)** `38` · **B)** `36` · **C)** `40`.

<details>
<summary>Answer</summary>

**A: `38`.** `ROLLBACK` undoes only this transaction's decrease. **B** ignores rollback. **C** assumes it also undoes the earlier order placed without a transaction.

</details>

```console
$ docker compose exec db psql -t -f /lab/bekor.sql
BEGIN
UPDATE 1
    36

ROLLBACK
    38
```

`-t` hides headings and `(N rows)`, but retains `BEGIN`, `UPDATE 1` and `ROLLBACK`. `UPDATE 1` means one row was updated. Inside the transaction stock is `36`; after rollback it is `38`.

What if the program stops before COMMIT? **A)** UPDATE remains · **B)** it rolls back when the connection is lost · **C)** the database waits forever.

<details>
<summary>Answer</summary>

**B.** Postgres rolls back an unfinished transaction when it detects that the connection has closed. **A** equates UPDATE with COMMIT. **C** does not describe the state after detecting disconnection. Detecting a network disconnection can take time after the process stops.

</details>

## SQL errors: an aborted transaction

`xato.sql` tries to reduce bread stock from `3` to `-2`. `SELECT 1` is a simple query that returns `1` on success.

```sql filename="xato.sql" showLineNumbers
BEGIN;
UPDATE products SET stock = stock - 5 WHERE id = 2;
SELECT 1;
COMMIT;
```

How much bread remains at the end? **A)** `3` · **B)** `-2` · **C)** `0`.

<details>
<summary>Answer</summary>

**A.** `CHECK` rejects negative stock; table changes in this transaction do not commit. **B** ignores the constraint; **C** assumes a change to zero that the statement never requests.

</details>

```console
$ docker compose exec db psql -f /lab/xato.sql
BEGIN
psql:/lab/xato.sql:2: ERROR:  new row for relation "products" violates check constraint "products_stock_check"
DETAIL:  Failing row contains (2, non, 400000, -2, t).
psql:/lab/xato.sql:3: ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
```

- `/lab/xato.sql:2` identifies line 2 of the SQL file. `Failing row` in `DETAIL` lists rejected values, not a stored row.
- `current transaction is aborted` means the transaction has failed; ordinary queries are rejected until the block ends. That is why even `SELECT 1` does not run.
- The final `COMMIT` returned `ROLLBACK` in this state. The transaction block ended without saving the changes.

This lab has no savepoints. A savepoint is a position inside a transaction to which you can roll back; using one is a separate topic. An ordinary Go error does not itself abort a Postgres transaction. For example, `pgx.ErrNoRows` is not a SQL error; Go code must still perform the rollback after it.

## Go: one tx for every statement

`pool.Begin(ctx)` acquires one connection from the pool and sends `BEGIN`. The returned `tx` is not the connection itself: it manages the transaction on that connection. Every `QueryRow`/`Exec` goes through this `tx`.

| Go path | Postgres | Pool |
|---|---|---|
| `pool.Begin` | transaction starts | one connection acquired |
| `tx.QueryRow` / `tx.Exec` | writes in that transaction | connection stays acquired |
| early `return` → deferred `Rollback` | table changes rolled back | healthy connection released |
| successful `Commit` | writes committed | connection released |
| subsequent deferred `Rollback` | no new ROLLBACK sent | transaction already closed |

The complete `store.go` is below; lines 1–96 are retained from GB-5.05. The new parts start at line 98.

<details>
<summary>Complete store.go</summary>

```go filename="store.go" showLineNumbers
package main

import (
	"context"
	"errors"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

// Product — products jadvalidagi bitta qator (narx tiyinda, GB-1.03).
type Product struct {
	ID    int64
	Name  string
	Price int64
	Stock int
}

// ErrNotFound — jadvalda bunday mahsulot yoʻq (GB-2.08: chaqiruvchi errors.Is bilan tekshiradi).
var ErrNotFound = errors.New("mahsulot topilmadi")

// Store — products jadvaliga Go'dan kirish. pool bir vaqtda koʻp goroutine'dan ishlatilishi mumkin.
type Store struct {
	pool *pgxpool.Pool
}

// Get id boʻyicha bitta mahsulotni oʻqiydi; yoʻq boʻlsa ErrNotFound.
func (s *Store) Get(ctx context.Context, id int64) (Product, error) {
	var p Product
	err := s.pool.QueryRow(ctx,
		"SELECT id, name, price, stock FROM products WHERE id = $1", id).
		Scan(&p.ID, &p.Name, &p.Price, &p.Stock)
	if errors.Is(err, pgx.ErrNoRows) {
		return Product{}, ErrNotFound
	}
	return p, err
}

// ListActive faol mahsulotlarni id tartibida oʻqiydi.
func (s *Store) ListActive(ctx context.Context) ([]Product, error) {
	rows, err := s.pool.Query(ctx,
		"SELECT id, name, price, stock FROM products WHERE active ORDER BY id")
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	out := []Product{}
	for rows.Next() {
		var p Product
		if err := rows.Scan(&p.ID, &p.Name, &p.Price, &p.Stock); err != nil {
			return nil, err
		}
		out = append(out, p)
	}
	return out, rows.Err()
}

// OrderTotal bitta buyurtmaning jami summasini (tiyinda) hisoblaydi. Buyurtma yoʻq boʻlsa SUM NULL beradi: COALESCE uni nolga aylantiradi.
func (s *Store) OrderTotal(ctx context.Context, orderID int64) (int64, error) {
	var total int64
	err := s.pool.QueryRow(ctx,
		"SELECT COALESCE(SUM(quantity*unit_price), 0) FROM order_items WHERE order_id = $1", orderID).
		Scan(&total)
	return total, err
}

// ByName nom boʻyicha bitta mahsulotni oʻqiydi; yoʻq boʻlsa ErrNotFound.
func (s *Store) ByName(ctx context.Context, name string) (Product, error) {
	var p Product
	err := s.pool.QueryRow(ctx,
		"SELECT id, name, price, stock FROM products WHERE name = $1", name).
		Scan(&p.ID, &p.Name, &p.Price, &p.Stock)
	if errors.Is(err, pgx.ErrNoRows) {
		return Product{}, ErrNotFound
	}
	return p, err
}

// Cheapest eng arzon n ta faol mahsulotni narx boʻyicha oʻsish tartibida oʻqiydi.
func (s *Store) Cheapest(ctx context.Context, n int) ([]Product, error) {
	rows, err := s.pool.Query(ctx,
		"SELECT id, name, price, stock FROM products WHERE active ORDER BY price, id LIMIT $1", n)
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	out := []Product{}
	for rows.Next() {
		var p Product
		if err := rows.Scan(&p.ID, &p.Name, &p.Price, &p.Stock); err != nil {
			return nil, err
		}
		out = append(out, p)
	}
	return out, rows.Err()
}

// ErrNotEnoughStock — omborda yetarli qoldiq yoʻq. VAZIFA (TASK.md, 1-qadam): PlaceOrder shu xatoni qaytarsin.
var ErrNotEnoughStock = errors.New("qoldiq yetarli emas")

// ErrInvalidQuantity — miqdor noldan katta boʻlishi kerak. VAZIFA (TASK.md, 3-qadam).
var ErrInvalidQuantity = errors.New("miqdor noldan katta boʻlishi kerak")

// OrderItem — buyurtmadagi bitta qator: qaysi mahsulot va nechta.
type OrderItem struct {
	ProductID int64
	Quantity  int
}

// PlaceOrder buyurtmani bitta transaction'da yozadi: orders qatori, har mahsulot uchun products.stock kamayishi
// va order_items qatori. Biror qadam xato bersa, hech narsa yozilmaydi.
func (s *Store) PlaceOrder(ctx context.Context, customer string, items []OrderItem) (int64, error) {
	tx, err := s.pool.Begin(ctx)
	if err != nil {
		return 0, err
	}
	defer tx.Rollback(ctx)

	var orderID int64
	err = tx.QueryRow(ctx,
		"INSERT INTO orders (customer) VALUES ($1) RETURNING id", customer).Scan(&orderID)
	if err != nil {
		return 0, err
	}
	for _, it := range items {
		var price int64
		err = tx.QueryRow(ctx,
			"UPDATE products SET stock = stock - $1 WHERE id = $2 RETURNING price",
			it.Quantity, it.ProductID).Scan(&price)
		if errors.Is(err, pgx.ErrNoRows) {
			return 0, ErrNotFound
		}
		if err != nil {
			return 0, err
		}
		_, err = tx.Exec(ctx,
			"INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ($1, $2, $3, $4)",
			orderID, it.ProductID, it.Quantity, price)
		if err != nil {
			return 0, err
		}
	}
	if err := tx.Commit(ctx); err != nil {
		return 0, err
	}
	return orderID, nil
}

// Restock tovar qabul qilishni yozadi: har mahsulotning qoldigʻi Quantity ga oshadi.
// Hammasi bitta transaction'da: bitta mahsulot topilmasa, hech birining qoldigʻi oʻzgarmaydi. VAZIFA (TASK.md, 2-qadam).
func (s *Store) Restock(ctx context.Context, items []OrderItem) error {
	return errors.New("Restock hali yozilmagan")
}
```

</details>

| Line | Code | What it does |
|---|---|---|
| 98–108 | errors and `OrderItem` | two sentinel errors for the homework; a struct with product id and quantity |
| 110–116 | `PlaceOrder`, `pool.Begin` | the same signature; returns `0, err` if beginning fails |
| 117 | `defer tx.Rollback(ctx)` | attempts rollback when the function returns if the transaction is still open |
| 119–124 | `tx.QueryRow` | creates the order in this transaction; `=` because `err` already exists |
| 125–129 | loop, `UPDATE` | the same SQL, now through `tx`; the order item needs the price |
| 130–135 | `errors.Is(err, pgx.ErrNoRows)` | if UPDATE finds no row, `Scan` returns this error; maps it to `ErrNotFound` and exits; other errors pass through |
| 136–142 | `tx.Exec`, error check | writes the order item in the same transaction |
| 143–147 | `tx.Commit(ctx)` | checks the error; returns `orderID, nil` only on success |
| 149–153 | `Restock` | homework stub: currently returns «hali yozilmagan» ("not implemented yet") |

Rollback after Commit returns `pgx.ErrTxClosed` (`tx is closed`) and does not change the committed row. The deferred call's return value is discarded. This makes the pattern safe on the success path too.

`defer` does not run on forced process termination or `os.Exit`. If the connection is lost, Postgres rolls back the unfinished transaction. Cancelling the `Begin` context does not trigger automatic rollback in pgx: you still need `Commit` or `Rollback`. If rollback fails for another reason, pgx closes the connection; only a healthy connection returns to the pool.

## Going deeper (optional): identify a Postgres error by its code

The homework maps `23514` to `ErrNotEnoughStock`. `*pgconn.PgError` is pgx's Postgres error type. `errors.As` extracts it; `&pgErr` is the variable's address. `Code` is SQLSTATE; `ConstraintName` names the failed constraint.

This complete stage file also shows the `errors` and `pgconn` imports:

```go filename="_video/stages/05-main-pgerr.go" showLineNumbers
package main

import (
	"context"
	"errors"
	"fmt"
	"os"
	"time"

	"github.com/jackc/pgx/v5/pgconn"
	"github.com/jackc/pgx/v5/pgxpool"
)

func main() {
	ctx := context.Background()
	pool, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
	if err != nil {
		fmt.Fprintln(os.Stderr, "pool:", err)
		os.Exit(1)
	}
	defer pool.Close()

	store := &Store{pool: pool}
	qctx, cancel := context.WithTimeout(ctx, 5*time.Second)
	defer cancel()

	_, err = store.PlaceOrder(qctx, "Aziza", []OrderItem{{ProductID: 2, Quantity: 5}})
	var pgErr *pgconn.PgError
	if errors.As(err, &pgErr) {
		fmt.Println(pgErr.Code, pgErr.ConstraintName)
	}
}
```

New lines compared with the earlier `main`: 5 and 10 add imports; 27 orders 5 bread units; 28–31 extract the error and print two fields. `pgErr` is a pointer; we read its fields only if `errors.As` succeeds.

If you call `tx.Commit` despite the SQL error, pgx returns `pgx.ErrTxCommitRollback`: `commit unexpectedly resulted in rollback`. This example's `PlaceOrder` exits on the error first. It therefore returns the original `23514` error.

Commit can also return an error after a connection failure. `0, err` is this function's return convention; after a disconnection, it does not by itself prove the server did not commit. ## Common mistakes

**Using the pool after Begin.** This incorrect line compiles because the pool also has `Exec`.

```go
		_, err = s.pool.Exec(ctx,
			"INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ($1, $2, $3, $4)",
			orderID, it.ProductID, it.Quantity, price)
```

`tx` holds one connection. The pool acquires another; it cannot see the `orders` row that the transaction has not committed. In this example the foreign key check fails.

**A)** the order commits · **B)** foreign key error · **C)** only the apple change remains.

<details>
<summary>Answer</summary>

**B.** The new order id does not yet exist for the other connection. **A** treats two connections as one transaction. **C** overlooks deferred rollback.

</details>

**Assuming an error return undoes everything.** Look at the result without a transaction: `0, err` did not clean the database. Distinguish SQL errors from ordinary Go errors and arrange rollback on every exit path.

**Ignoring the Commit error.** Do not call `tx.Commit(ctx)` and unconditionally report success afterwards. Lines 143–146 above check the error.

## Check yourself

1. If CHECK fails in this lesson's transaction without savepoints, does the earlier UPDATE commit?

<details>
<summary>Answer</summary>

No. The transaction aborts; ordinary statements are rejected. ROLLBACK ends the block; COMMIT also results in rollback in this state. Earlier table changes do not commit.

</details>

2. Why does deferred Rollback after Commit not erase the committed order?

<details>
<summary>Answer</summary>

`tx` is closed. pgx returns `ErrTxClosed` without sending a new ROLLBACK to the database.

</details>

3. Apple stock starts at `40`. A read after `BEGIN; UPDATE products SET stock = stock - 2 WHERE id = 1; ROLLBACK;` returns: **A)** `38` · **B)** `40` · **C)** an error?

<details>
<summary>Answer</summary>

**B: `40`.** Only this transaction's change was undone. Getting `38` would require a successful COMMIT.

</details>

4. GB-5.04: why does `WHERE note = NULL` return no rows?

<details>
<summary>Answer</summary>

Ordinary comparison with `NULL` produces unknown; WHERE keeps only true. Use `WHERE note IS NULL`.

</details>
