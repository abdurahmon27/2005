## Что вы узнаете

Заказ записан, остаток яблок уменьшился, но хлеба не хватило. Функция вернула ошибку. Останется ли в базе половина заказа?

**Одна идея:** **транзакция** объединяет изменения в нескольких таблицах: сохраняются либо все изменения, либо изменения таблиц отменяются. В Go все команды идут через один `tx`.

После урока вы:

- найдёте через SQL частичный заказ, оставшийся без транзакции;
- различите `BEGIN`, `COMMIT`, `ROLLBACK` и прерванную транзакцию;
- напишете `PlaceOrder` с `pool.Begin`, `defer tx.Rollback(ctx)` и `tx.Commit(ctx)`;
- найдёте команду, отправленную через пул вместо `tx`, и проверите задание на настоящем Postgres.

| Слово | Простой смысл | Английский термин |
|---|---|---|
| транзакция | группа команд, сохраняемых или отменяемых вместе | transaction |
| прерванная транзакция | состояние, в котором после SQL-ошибки отклоняются обычные команды | aborted transaction |
| транзакция pgx | `tx`, управляющий транзакцией на одном соединении из пула | pgx transaction |

Два вспомогательных понятия: `UPDATE … SET` меняет значение в существующей строке. **SQLSTATE** — код категории ошибки Postgres из пяти символов.

## Без транзакции: ошибка не удаляет половину заказа

`bozor.sql` заново создаёт три таблицы из прошлых уроков. `DROP TABLE` удаляет и существующие строки: выполняйте его в этой лаборатории. В нашей копии таблицы уже существовали:

```console
$ docker compose exec db psql -f /lab/bozor.sql
DROP TABLE
CREATE TABLE
INSERT 0 4
CREATE TABLE
CREATE TABLE
INSERT 0 3
INSERT 0 4
```

В новой базе сначала появятся ещё три предупреждения `NOTICE … does not exist, skipping`. `CREATE TABLE` создаёт таблицу, `INSERT 0 n` добавляет `n` строк. В видео скрыты `DROP TABLE`, предупреждения и некоторые количества строк; здесь приведены повторно полученные результаты.

| Таблица | Начальное состояние | Роль в заказе |
|---|---|---|
| `products` | яблоко (`olma`): `id=1`, остаток `40`; хлеб (`non`): `id=2`, остаток `3`; ещё чай и абрикосы | уменьшить остаток |
| `orders` | 3 заказа | строка заказа клиента |
| `order_items` | 4 строки | товар, количество и цена на момент заказа |

`price`/`unit_price` указаны в тийинах: яблоко `1200000`, хлеб `400000`. Для `products.stock` есть `CHECK (stock >= 0)`.

Новый входной тип из `store.go`:

```go
type OrderItem struct {
	ProductID int64
	Quantity  int
}
```

`ProductID` определяет товар, `Quantity` — количество. `[]OrderItem` — слайс значений этой структуры. `Store` содержит пул соединений из прошлого урока.

Сначала полный файл с неправильным подходом:

```go filename="notx.go" showLineNumbers
package main

import "context"

// PlaceOrderNoTx — videodagi XATO versiya: shu PlaceOrder, lekin transaction'siz.
// Har buyruq pool orqali alohida yuboriladi, shuning uchun xatodan keyin yarim yozilgan buyurtma qoladi.
// Faqat koʻrsatish uchun: ishlatmang.
func (s *Store) PlaceOrderNoTx(ctx context.Context, customer string, items []OrderItem) (int64, error) {
	var orderID int64
	err := s.pool.QueryRow(ctx,
		"INSERT INTO orders (customer) VALUES ($1) RETURNING id", customer).Scan(&orderID)
	if err != nil {
		return 0, err
	}
	for _, it := range items {
		var price int64
		err = s.pool.QueryRow(ctx,
			"UPDATE products SET stock = stock - $1 WHERE id = $2 RETURNING price",
			it.Quantity, it.ProductID).Scan(&price)
		if err != nil {
			return 0, err
		}
		_, err = s.pool.Exec(ctx,
			"INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ($1, $2, $3, $4)",
			orderID, it.ProductID, it.Quantity, price)
		if err != nil {
			return 0, err
		}
	}
	return orderID, nil
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1–7 | `package`, `import`, комментарии | пакет `main`, тип context и предупреждение о неправильной версии |
| 8 | `PlaceOrderNoTx(…) (int64, error)` | метод Store: получает context, клиента и позиции заказа, возвращает id и ошибку |
| 9–11 | `QueryRow(…).Scan(&orderID)` | добавляет строку в `orders`; `$1` — клиент; записывает `RETURNING id` по адресу |
| 12–14 | `if err != nil` | при ошибке возвращает `0, err`; сам по себе не отменяет предыдущие результаты SQL |
| 15–16 | `for _, it := range items` | цикл по элементам; `_` отбрасывает индекс, `it` — текущая позиция; `price` хранит цену |
| 17–19 | `UPDATE … RETURNING price` | `SET` присваивает новое значение: из остатка вычитается количество `$1`; `$2` выбирает товар; цена читается в `price` |
| 20–22 | `return 0, err` | выходит при нарушении ограничения остатка; `err` уже существует, поэтому в строке 17 стоит `=` |
| 23–25 | `Exec` | добавляет строку в `order_items` с четырьмя параметрами; `_` отбрасывает результат команды |
| 26–31 | проверка ошибки, `return` | выходит при ошибке, а после успешного цикла возвращает id и `nil` |

## SQL: BEGIN и ROLLBACK

**Транзакция** объединяет эти записи. `BEGIN` начинает её; то же соединение видит собственные новые значения. Другие соединения не видят несохранённых изменений таблиц. `COMMIT` сохраняет, `ROLLBACK` отменяет.

| Этап | Это соединение | Другое соединение |
|---|---|---|
| до `BEGIN` | яблок `38` | яблок `38` |
| после `UPDATE … - 2` | яблок `36` | сохранённый остаток `38` |
| после `ROLLBACK` | яблок `38` | яблок `38` |
| если вместо этого успешный `COMMIT` | яблок `36` | последующее чтение может увидеть `36` |

Таблица предполагает обычные отдельные запросы. Долгоживущий снимок чтения в другой транзакции выходит за рамки урока.

```sql filename="bekor.sql" showLineNumbers
BEGIN;
UPDATE products SET stock = stock - 2 WHERE id = 1;
SELECT stock FROM products WHERE id = 1;
ROLLBACK;
SELECT stock FROM products WHERE id = 1;
```

Строка 1 начинает транзакцию, 2 уменьшает остаток, 3 читает значение внутри неё. Строка 4 отменяет изменения, 5 читает снова. `;` завершает SQL-команду.

Что выведет последний `SELECT`? **A)** `38` · **B)** `36` · **C)** `40`.

<details>
<summary>Ответ</summary>

**A: `38`.** `ROLLBACK` отменяет только уменьшение в этой транзакции. **B** игнорирует откат. **C** предполагает, что отменится и предыдущий заказ без транзакции.

</details>

```console
$ docker compose exec db psql -t -f /lab/bekor.sql
BEGIN
UPDATE 1
    36

ROLLBACK
    38
```

`-t` скрывает заголовки и `(N rows)`, но оставляет `BEGIN`, `UPDATE 1`, `ROLLBACK`. `UPDATE 1` — обновлена одна строка. Внутри остаток `36`, после отката — `38`.

А если программа остановится до COMMIT? **A)** UPDATE останется · **B)** откатится при разрыве соединения · **C)** база будет ждать вечно.

<details>
<summary>Ответ</summary>

**B.** Postgres откатывает незавершённую транзакцию, обнаружив закрытие соединения. **A** приравнивает UPDATE к COMMIT. **C** не описывает состояние после обнаружения разрыва. Между остановкой процесса и обнаружением сетевого разрыва может пройти время.

</details>

## SQL-ошибка: прерванная транзакция

`xato.sql` пытается уменьшить остаток хлеба с `3` до `-2`. `SELECT 1` — простой запрос, который при успехе возвращает `1`.

```sql filename="xato.sql" showLineNumbers
BEGIN;
UPDATE products SET stock = stock - 5 WHERE id = 2;
SELECT 1;
COMMIT;
```

Сколько хлеба останется в конце? **A)** `3` · **B)** `-2` · **C)** `0`.

<details>
<summary>Ответ</summary>

**A.** `CHECK` запрещает отрицательный остаток; изменения таблиц в этой транзакции не сохраняются. **B** игнорирует ограничение; **C** предполагает обнуление, которого команда не запрашивает.

</details>

```console
$ docker compose exec db psql -f /lab/xato.sql
BEGIN
psql:/lab/xato.sql:2: ERROR:  new row for relation "products" violates check constraint "products_stock_check"
DETAIL:  Failing row contains (2, non, 400000, -2, t).
psql:/lab/xato.sql:3: ERROR:  current transaction is aborted, commands ignored until end of transaction block
ROLLBACK
```

- `/lab/xato.sql:2` — вторая строка SQL-файла. `Failing row` в `DETAIL` содержит отклонённые значения, а не сохранённую строку.
- `current transaction is aborted` — транзакция прервана; обычные запросы отклоняются до завершения блока. Поэтому даже `SELECT 1` не выполняется.
- Последний `COMMIT` в этом состоянии ответил `ROLLBACK`. Блок транзакции завершился без сохранения изменений.

В этой лаборатории нет точек сохранения. Точка сохранения, savepoint, — место внутри транзакции, к которому можно откатиться; это отдельная тема. Обычная ошибка Go сама по себе не переводит транзакцию Postgres в прерванное состояние. Например, `pgx.ErrNoRows` — не SQL-ошибка; после неё откат всё равно должен выполнить код Go.

## Go: один tx для всех команд

`pool.Begin(ctx)` получает из пула одно соединение и отправляет `BEGIN`. Возвращённый `tx` — не само соединение, а значение, управляющее транзакцией на нём. Все `QueryRow`/`Exec` идут через этот `tx`.

| Путь Go | Postgres | Пул |
|---|---|---|
| `pool.Begin` | начинается транзакция | одно соединение занято |
| `tx.QueryRow` / `tx.Exec` | записи в той же транзакции | соединение остаётся занятым |
| ранний `return` → отложенный `Rollback` | изменения таблиц отменены | исправное соединение возвращается |
| успешный `Commit` | записи сохранены | соединение возвращается |
| последующий отложенный `Rollback` | новый ROLLBACK не отправляется | транзакция уже закрыта |

Ниже полный `store.go`; строки 1–96 остались из GB-5.05. Новые части начинаются со строки 98.

<details>
<summary>Полный store.go</summary>

```go filename="store.go" showLineNumbers
package main

import (
	"context"
	"errors"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

// Product — products jadvalidagi bitta qator (narx tiyinda, GB-1.03).
type Product struct {
	ID    int64
	Name  string
	Price int64
	Stock int
}

// ErrNotFound — jadvalda bunday mahsulot yoʻq (GB-2.08: chaqiruvchi errors.Is bilan tekshiradi).
var ErrNotFound = errors.New("mahsulot topilmadi")

// Store — products jadvaliga Go'dan kirish. pool bir vaqtda koʻp goroutine'dan ishlatilishi mumkin.
type Store struct {
	pool *pgxpool.Pool
}

// Get id boʻyicha bitta mahsulotni oʻqiydi; yoʻq boʻlsa ErrNotFound.
func (s *Store) Get(ctx context.Context, id int64) (Product, error) {
	var p Product
	err := s.pool.QueryRow(ctx,
		"SELECT id, name, price, stock FROM products WHERE id = $1", id).
		Scan(&p.ID, &p.Name, &p.Price, &p.Stock)
	if errors.Is(err, pgx.ErrNoRows) {
		return Product{}, ErrNotFound
	}
	return p, err
}

// ListActive faol mahsulotlarni id tartibida oʻqiydi.
func (s *Store) ListActive(ctx context.Context) ([]Product, error) {
	rows, err := s.pool.Query(ctx,
		"SELECT id, name, price, stock FROM products WHERE active ORDER BY id")
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	out := []Product{}
	for rows.Next() {
		var p Product

// PlaceOrder buyurtmani bitta transaction'da yozadi: orders qatori, har mahsulot uchun products.stock kamayishi
// va order_items qatori. Biror qadam xato bersa, hech narsa yozilmaydi.
func (s *Store) PlaceOrder(ctx context.Context, customer string, items []OrderItem) (int64, error) {
	tx, err := s.pool.Begin(ctx)
	if err != nil {
		return 0, err
	}
	defer tx.Rollback(ctx)

	var orderID int64
	err = tx.QueryRow(ctx,
		"INSERT INTO orders (customer) VALUES ($1) RETURNING id", customer).Scan(&orderID)
	if err != nil {
		return 0, err
	}
	for _, it := range items {
		var price int64
		err = tx.QueryRow(ctx,
			"UPDATE products SET stock = stock - $1 WHERE id = $2 RETURNING price",
			it.Quantity, it.ProductID).Scan(&price)
		if errors.Is(err, pgx.ErrNoRows) {
			return 0, ErrNotFound
		}
		if err != nil {
			return 0, err
		}
		_, err = tx.Exec(ctx,
			"INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ($1, $2, $3, $4)",
			orderID, it.ProductID, it.Quantity, price)
		if err != nil {
			return 0, err
		}
	}
	if err := tx.Commit(ctx); err != nil {
		return 0, err
	}
	return orderID, nil
}
```

| 119–124 | `tx.QueryRow` | создаёт заказ в этой транзакции; `=` потому, что `err` уже есть |
| 125–129 | цикл, `UPDATE` | прежний SQL, теперь через `tx`; цена нужна для позиции заказа |
| 130–135 | `errors.Is(err, pgx.ErrNoRows)` | если UPDATE не нашёл строку, `Scan` возвращает эту ошибку; преобразует в `ErrNotFound` и выходит; прочие ошибки не меняет |
| 136–142 | `tx.Exec`, проверка ошибки | записывает позицию заказа в той же транзакции |
| 143–147 | `tx.Commit(ctx)` | проверяет ошибку; возвращает `orderID, nil` только при успехе |
| 149–153 | `Restock` | заглушка задания: пока возвращает «hali yozilmagan» («ещё не реализовано») |

Rollback после Commit возвращает `pgx.ErrTxClosed` (`tx is closed`) и не меняет сохранённую запись. Возвращаемое значение отложенного вызова отбрасывается. Поэтому этот шаблон безопасен и на успешном пути.

`defer` не выполняется при принудительном завершении процесса или `os.Exit`. При разрыве соединения незавершённую транзакцию откатывает Postgres. Отмена context, переданного в `Begin`, не вызывает автоматический rollback в pgx: всё равно нужен `Commit` или `Rollback`. Если rollback не удаётся по другой причине, pgx закрывает соединение; в пул возвращается только исправное.

## Частые ошибки

**Пул после Begin.** Неправильная строка компилируется: у пула тоже есть `Exec`.

```go

			"INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES ($1, $2, $3, $4)",
			orderID, it.ProductID, it.Quantity, price)
```

## Проверьте себя

1. Если CHECK нарушен внутри транзакции этого урока без savepoint, сохранится ли предыдущий UPDATE?

<details>
<summary>Ответ</summary>

Нет. Транзакция прерывается; обычные команды отклоняются. ROLLBACK завершает блок; COMMIT в этом состоянии тоже приводит к откату. Предыдущие изменения таблиц не сохраняются.

</details>

2. Почему отложенный Rollback после Commit не удаляет сохранённый заказ?

<details>
<summary>Ответ</summary>

`tx` закрыт. pgx возвращает `ErrTxClosed`, не отправляя базе новый ROLLBACK.

</details>

3. Вначале яблок `40`. Чтение после `BEGIN; UPDATE products SET stock = stock - 2 WHERE id = 1; ROLLBACK;` вернёт: **A)** `38` · **B)** `40` · **C)** ошибку?

<details>
<summary>Ответ</summary>

**B: `40`.** Отменено только изменение этой транзакции. Для `38` нужен был успешный COMMIT.

</details>

4. GB-5.04: почему `WHERE note = NULL` не возвращает строк?

<details>

Обычное сравнение с `NULL` даёт неизвестное значение; WHERE сохраняет только истину. Нужно `WHERE note IS NULL`.
