## Что вы узнаете

В SQL неверно назван столбец. `go build` и `go vet` прошли. Почему программа падает только при обращении к базе?

**Одна идея:** SQL пишете вы; **sqlc** читает схему и запросы, затем создаёт обычный Go-код для проверенных запросов.
При этой конфигурации он не подключается к базе. Неизвестный столбец обнаруживается при `sqlc generate`; ошибки выполнения всё равно нужно обрабатывать.

После урока вы:

- напишете комментарии в `query.sql` и конфигурацию `sqlc.yaml`;
- прочитаете типы, `QueryRow`, `Scan` и цикл строк в `db/`;
- переведёте `Store.Get`, `ListActive` и `PlaceOrder` на сгенерированные методы;
- различите устаревший `db/`, забытый generate и ошибки типов выражений.

| Термин | Простой смысл | Английский термин |
|---|---|---|
| аннотация запроса | имя Go-метода и форма результата в SQL-комментарии | query annotation |
| сгенерированный код | Go-файлы, созданные sqlc из SQL и схемы | generated code |
| ошибка при генерации | ошибка, найденная при проверке SQL до запуска программы | generation-time error |

```go filename="_video/stages/01-store-qolda.go" showLineNumbers
package main

import (
	"context"
	"errors"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

// Videoning boshidagi holat: GB-5.05'dagi qoʻlda yozilgan Get, ustun nomida xato bilan (stock → qoldiq).
type Product struct {
	ID    int64
	Name  string
	Price int64
	Stock int
}

var ErrNotFound = errors.New("mahsulot topilmadi")

type Store struct {
	pool *pgxpool.Pool
}

func (s *Store) Get(ctx context.Context, id int64) (Product, error) {
	var p Product
	err := s.pool.QueryRow(ctx,
		"SELECT id, name, price, qoldiq FROM products WHERE id = $1", id).
		Scan(&p.ID, &p.Name, &p.Price, &p.Stock)
	if errors.Is(err, pgx.ErrNoRows) {
		return Product{}, ErrNotFound
	}
	return p, err
}
```

```go filename="_video/stages/01-main.go" showLineNumbers
package main

import (
	"context"
	"fmt"
	"os"
	"time"

	"github.com/jackc/pgx/v5/pgxpool"
)

func main() {
	ctx := context.Background()
	pool, err := pgxpool.New(ctx, os.Getenv("DATABASE_URL"))
	if err != nil {
		fmt.Fprintln(os.Stderr, "pool:", err)
		os.Exit(1)
	}
	defer pool.Close()

	store := &Store{pool: pool}
	qctx, cancel := context.WithTimeout(ctx, 5*time.Second)
	defer cancel()

	p, err := store.Get(qctx, 1)
	fmt.Println(p, err)
}
```

Пустые строки служат читаемости. `qoldiq` означает «остаток», но настоящий SQL-столбец называется `stock`.

Какая команда найдёт ошибку? **A)** `go build` · **B)** `go vet .` · **C)** `go run .`.

<details>
<summary>Ответ</summary>

**C.** Для компилятора Go SQL — обычная строка. `go vet` тоже не знает эту таблицу. A и B предполагают проверку SQL-схемы.

</details>

```console
$ go build
$ go vet .
$ go run .
{0  0 0} ERROR: column "qoldiq" does not exist (SQLSTATE 42703)
```

Первые две команды ничего не напечатали и завершились с кодом `0`. `column … does not exist` означает «такого столбца нет».

## query.sql и sqlc.yaml

Повторяющиеся `QueryRow` и `Scan` для каждого запроса поручим инструменту. `sqlc generate` создаёт этот повторяющийся Go-код.
Сначала установите инструмент. `cmd/sqlc` — пакет команды, `@v1.31.1` — выбранная версия.
Каталог Go bin должен быть в `PATH`, как в GB-3.03:

```console
$ go install github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1
$ sqlc version
v1.31.1
```

Установка у нас ничего не напечатала. В исследовании видео холодная установка заняла около четырёх минут, наша повторная установка с кэшем — три секунды.
Это разные условия, сравнивать скорость по ним нельзя. C-компилятор не понадобился: с `CGO_ENABLED=0` sqlc использует WebAssembly-вариант парсера.
Это заранее собранный код парсера; PostgreSQL-сервер он не запускает.

Пока поместим в `query.sql` только два запроса (`_video/stages/02-query.sql`):

```sql filename="_video/stages/02-query.sql" showLineNumbers
-- name: GetProduct :one
SELECT id, name, price, stock FROM products
WHERE id = $1;

-- name: ListActiveProducts :many
SELECT id, name, price, stock FROM products
WHERE active
ORDER BY id;
```

```bash
cp _video/stages/02-query.sql query.sql
```

`--` начинает SQL-комментарий. **Аннотация запроса** через `name:` задаёт имя Go-метода; `:one` возвращает одно значение и ошибку.
`GetProduct` ищет по `id = $1`. Значение `$1` передаётся отдельным аргументом.
`:many` возвращает слайс и ошибку. `ListActiveProducts` получает активные строки в порядке ID.
Для команды без возвращаемых строк `:exec` возвращает только ошибку; применим его в транзакции.

Полный `sqlc.yaml`:

```yaml filename="sqlc.yaml" showLineNumbers
version: "2"
sql:
  - engine: postgresql
    schema: migrations
    queries: query.sql
    gen:
      go:
        package: db
        out: db
        sql_package: pgx/v5
```

| Строка | Значение |
|---|---|
| 1 | `version: "2"` — формат конфигурации, не версия sqlc; кавычки делают его строкой. |
| 2–3 | `sql` — список; `-` — один элемент; `engine` выбирает синтаксис Postgres. |
| 4 | `schema` читает структуру таблиц из `migrations/`, пропуская goose `Down`. |
| 5 | `queries` — источник запросов. |
| 6–7 | `gen.go` включает генерацию Go-кода. |
| 8 | `package` — имя создаваемого пакета. |
| 9 | `out` — папка для файлов. |
| 10 | `sql_package: pgx/v5` выбирает API pgx v5. |

Файлы читаются по именам; поэтому важен порядок `00001_…`. sqlc не применяет миграции к базе: это работа goose.

| До | Действие | После |
|---|---|---|
| `migrations/` + `query.sql` | `sqlc generate` | созданы `db/*.go` |
| Go-программа + `db/*.go` | `go run .` | SQL отправлен через pgx в Postgres |

Что выведет успешный generate? **A)** ничего · **B)** список файлов · **C)** `OK` и число запросов.

<details>
<summary>Ответ</summary>

**A.** Успешная команда молчит. Для B нужен `ls db`; C путает её с выводом goose.

</details>

```console
$ sqlc generate
$ ls db
db.go
models.go
query.sql.go
```

`generate` ничего не напечатал, `ls db` перечислил файлы. `0.9 s` — цитата из исследования видео; новое измерение — `0.755 s`.
Отношение примерно `1.2`; это не гарантия времени даже для маленькой схемы. Существенно то, что проверка прошла до запуска программы.
Парсер Postgres разбирает SQL; отсутствующий столбец sqlc находит по собственному каталогу схемы. База при этой конфигурации не участвует.

## models.go: типы из схемы

Какой Go-тип соответствует `stock integer NOT NULL`? **A)** `int` · **B)** `int32` · **C)** `int64`.

<details>
<summary>Ответ</summary>

**B.** Postgres `integer` занимает четыре байта; sqlc для pgx создаёт `int32`. A — наш доменный выбор, C соответствует `bigint`.

</details>

```go filename="db/models.go" showLineNumbers
// Code generated by sqlc. DO NOT EDIT.
// versions:
//   sqlc v1.31.1

package db

import (
	"github.com/jackc/pgx/v5/pgtype"
)

type Order struct {
	ID       int64
	Customer string
	Note     pgtype.Text
	Status   string
}

type OrderItem struct {
	ID        int64
	OrderID   int64
	ProductID int64
	Quantity  int32
	UnitPrice int64
}

type Product struct {
	ID     int64
	Name   string
	Price  int64
	Stock  int32
	Active bool
}
```

1–3 маркер сгенерированного файла и версия sqlc; 5 пакет; 7–9 импорт `pgtype`.
11–16 `Order`: ID из `bigint`, `Customer` и `Status` из `text`, `Note` из nullable `text`.
18–24 `OrderItem`: три ID и цена `int64`, количество `int32`.
26–32 `Product`: ID и цена `int64`, имя `string`, остаток `int32`, активность `bool`.

Для `Note` нужен **`pgtype.Text`**: Go `string` не представляет SQL `NULL`.
Его поле `String` хранит строку, а `Valid` показывает наличие значения. `Valid: false` — `NULL`; `Valid: true, String: ""` — пустая строка.
`Status` появился из третьей миграции. `DO NOT EDIT` означает «не редактировать вручную»: следующий generate перезапишет файл.

## db.go и query.sql.go: обычный Go

```go filename="db/db.go" showLineNumbers
// Code generated by sqlc. DO NOT EDIT.
// versions:
//   sqlc v1.31.1

package db

import (
	"context"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgconn"
)

type DBTX interface {
	Exec(context.Context, string, ...interface{}) (pgconn.CommandTag, error)
	Query(context.Context, string, ...interface{}) (pgx.Rows, error)
	QueryRow(context.Context, string, ...interface{}) pgx.Row
}

func New(db DBTX) *Queries {
	return &Queries{db: db}
}

type Queries struct {
	db DBTX
}

func (q *Queries) WithTx(tx pgx.Tx) *Queries {
	return &Queries{
		db: tx,
	}
}
```

1–3 маркер файла; 5 пакет; 7–12 импорты. 14–18 интерфейс `DBTX` требует три метода.
`Exec` возвращает `pgconn.CommandTag` и ошибку; `Query` — `pgx.Rows` и ошибку; `QueryRow` — `pgx.Row`.
Имена параметров в интерфейсе необязательны. `...interface{}` — это `...any`: произвольное число аргументов.
20–22 `New` помещает переданный DBTX в новый `Queries`; `&` возвращает его адрес. 24–26 `Queries.db` хранит этот DBTX.
28–32 `WithTx` создаёт новый `Queries` с `tx` в поле `db`.
И pool, и `pgx.Tx` имеют три метода; оба удовлетворяют этому интерфейсу.

Теперь два полных фрагмента из `db/query.sql.go`. Это не весь файл:

```go
const getProduct = `-- name: GetProduct :one
SELECT id, name, price, stock FROM products
WHERE id = $1
`

type GetProductRow struct {
	ID    int64
	Name  string
	Price int64
	Stock int32
}

func (q *Queries) GetProduct(ctx context.Context, id int64) (GetProductRow, error) {
	row := q.db.QueryRow(ctx, getProduct, id)
	var i GetProductRow
	err := row.Scan(
		&i.ID,
		&i.Name,
		&i.Price,
		&i.Stock,
	)
	return i, err
}
```

```go
const listActiveProducts = `-- name: ListActiveProducts :many
SELECT id, name, price, stock FROM products
WHERE active
ORDER BY id
`

type ListActiveProductsRow struct {
	ID    int64
	Name  string
	Price int64
	Stock int32
}

func (q *Queries) ListActiveProducts(ctx context.Context) ([]ListActiveProductsRow, error) {
	rows, err := q.db.Query(ctx, listActiveProducts)
	if err != nil {
		return nil, err
	}
	defer rows.Close()
	var items []ListActiveProductsRow
	for rows.Next() {
		var i ListActiveProductsRow
		if err := rows.Scan(
			&i.ID,
			&i.Name,
			&i.Price,
			&i.Stock,
		); err != nil {
			return nil, err
		}
		items = append(items, i)
	}
	if err := rows.Err(); err != nil {
		return nil, err
	}
	return items, nil
}
```

## Имена параметров и WithTx

Для транзакции остаются прежние три SQL-запроса. Начальный вариант (`_video/stages/03-query-dollar.sql`) выглядит так:

```sql filename="_video/stages/03-query-dollar.sql" showLineNumbers
-- name: GetProduct :one
SELECT id, name, price, stock FROM products
WHERE id = $1;

-- name: ListActiveProducts :many
SELECT id, name, price, stock FROM products
WHERE active
ORDER BY id;

-- name: CreateOrder :one
INSERT INTO orders (customer) VALUES ($1)
RETURNING id;

-- name: DecrementStock :one
UPDATE products SET stock = stock - $1
WHERE id = $2
RETURNING price;

-- name: AddOrderItem :exec
INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES ($1, $2, $3, $4);
```

У `CreateOrder` есть `RETURNING id`, поэтому `:one`; `DecrementStock` возвращает цену, поэтому тоже `:one`.
`AddOrderItem` записывает четыре параметра без строки результата: `:exec`.
При этой конфигурации для нескольких параметров sqlc создаёт структуру `Params`. Имена он выводит из столбцов.
Как назовётся поле для `$1` в `stock = stock - $1`? **A)** `Quantity` · **B)** `Stock` · **C)** `Column1`.

<details>
<summary>Ответ</summary>

**B.** Повторная генерация дала `Stock int32`, `ID int64`. A — нужный нам смысл, но он не записан; C здесь не получился.

</details>

```go
type DecrementStockParams struct {
	Stock int32
	ID    int64
}
```

Здесь `Stock` — вычитаемое количество, а не текущий остаток. Для явного имени заменим `$1` на `@quantity`, `$2` на `@id`.
`@name` — сокращение `sqlc.arg(name)`. SQL, отправляемый Postgres, снова использует `$1`, `$2`.
Полный итоговый `query.sql`:

var ErrNotEnoughStock = errors.New("qoldiq yetarli emas")

// ErrInvalidQuantity — miqdor noldan katta boʻlishi va integer ustuniga (int32) sigʻishi kerak.
var ErrInvalidQuantity = errors.New("miqdor notoʻgʻri: 1 dan 2147483647 gacha boʻlishi kerak")

// OrderItem — buyurtmadagi bitta qator: qaysi mahsulot va nechta.
type OrderItem struct {

```go
func (s *Store) PlaceOrder(ctx context.Context, customer string, items []OrderItem) (int64, error) {
	for _, it := range items {
		if it.Quantity <= 0 || it.Quantity > math.MaxInt32 {
			return 0, ErrInvalidQuantity
		}
	}
	tx, err := s.pool.Begin(ctx)
	if err != nil {
		return 0, err
	}
	defer tx.Rollback(ctx)
	qtx := s.q.WithTx(tx)

	orderID, err := qtx.CreateOrder(ctx, customer)
	if err != nil {
		return 0, err
	}
	for _, it := range items {
		var price int64
		price, err = qtx.DecrementStock(ctx, db.DecrementStockParams{
			Quantity: int32(it.Quantity),
			ID:       it.ProductID,
		})
		if errors.Is(err, pgx.ErrNoRows) {
			return 0, ErrNotFound
		}
		var pgErr *pgconn.PgError
		if errors.As(err, &pgErr) && pgErr.Code == "23514" { // 23514 = check_violation: CHECK (stock >= 0) buzildi
			return 0, ErrNotEnoughStock
		}
		if err != nil {
			return 0, err
		}
		err = qtx.AddOrderItem(ctx, db.AddOrderItemParams{
			OrderID:   orderID,
			ProductID: it.ProductID,
			Quantity:  int32(it.Quantity),
			UnitPrice: price,
		})
		if err != nil {
			return 0, err
		}
	}
	if err := tx.Commit(ctx); err != nil {
		return 0, err
	}
	return orderID, nil
}
```

Объявления: два значения ошибок; `OrderItem` содержит ID товара и количество. `math.MaxInt32` — `2147483647`.
В импорты `store.go` добавлены `math` и `github.com/jackc/pgx/v5/pgconn`.

| Строки метода | Изменение и задача |
|---|---|
| 1–6 | Количество положительное и помещается в `int32`; иначе ошибка до открытия транзакции. `\|\|` — «или». |
| 7–11 | `Begin`, проверка ошибки, `defer Rollback`: правило GB-5.07. |
| 12 | `qtx := s.q.WithTx(tx)` — новый `Queries`, исполнитель запросов — `tx`. |
| 14–17 | `CreateOrder` даёт ID; при ошибке возврат. |
| 18–23 | `range items`, переменная `price`; проверенное количество `int32` и ID товара передаются в `DecrementStockParams`. |
| 24–26 | Преобразование `ErrNoRows` в `ErrNotFound`. |
| 27–30 | `errors.As` извлекает `*pgconn.PgError`; `23514` (`check_violation`) — нарушение CHECK остатка. |
| 31–33 | Возврат другой ошибки. |
| 34–42 | Запись ID заказа, товара, количества и текущей цены через `AddOrderItemParams`; проверка ошибки. |
| 43–48 | Закрытие цикла, проверка ошибки `Commit`, возврат ID и `nil`. |

`price, err =` присваивает значение прежней `err`, не создавая внутреннюю переменную.
`WithTx` не открывает транзакцию и не выполняет commit; это остаётся в `Store`.

| Состояние | `s.q.db` | `qtx.db` | База |
|---|---|---|---|
| до `Begin` | pool | отсутствует | транзакции нет |
| после `WithTx(tx)` | pool | tx | открытая транзакция |
| `qtx.CreateOrder` и остальные | pool | tx | неподтверждённые изменения |
| после `Commit` | pool | завершённый tx | изменения подтверждены |

Если внутри транзакции вызвать `s.q`, запрос может уйти через pool по другому соединению. Все три действия должны использовать `qtx`.

## Глубже (необязательно): db/ и SQL всегда вместе

`db/` обычно коммитят в git. Для сборки программы установка sqlc не обязательна: достаточно Go-файлов.
`sqlc diff` сравнивает файлы, которые должны получиться при генерации, с существующими.
В чистой исходной копии:

```console
$ sqlc diff
```

Вывода нет, exit `0`. Когда мы добавили SQL-запрос без generate, команда показала diff и вернула exit `1`.
Текст различий зависит от файлов; здесь он не воспроизводится. Включение этого правила в автоматическую проверку разбирается в GB-8.05.

Тип вычисляемого столбца — предположение sqlc. Мы повторно сгенерировали три варианта в отдельной копии:

| Выражение OrderTotal | Результат sqlc v1.31.1 | Ограничение |
|---|---|---|
| `COALESCE(SUM(quantity * unit_price), 0)` | `interface{}` | не подходит Go-методу, ожидающему `int64` |
| `SUM(quantity * unit_price) AS total` | `int64` | без строк Postgres возвращает `NULL` |
| `COALESCE(SUM(quantity * unit_price), 0)::bigint AS total` | `int64` | пустой результат `0`, тип задан в SQL |

Для `SUM(bigint)` Postgres возвращает `numeric`. `COALESCE` выбирает первое значение, отличное от `NULL`.
`::bigint` преобразует SQL-тип; `AS total` именует столбец результата. Читать сигнатуру sqlc и тестировать с настоящей базой всё равно нужно.
Конфигурация страницы проверяет без базы; sqlc также поддерживает анализ с базой при других настройках.

## Частые ошибки

**1. «Build прошёл, значит новый SQL правильный».** В опыте с `qoldiq` выше остался старый `db/`.
Исправление: поправьте столбец, проверьте exit generate, затем `sqlc diff`. Компилятор найдёт забытую генерацию только при использовании нового метода.

**2. Исправлять `db/*.go` вручную.** Следующий generate уничтожит изменение. Исправьте SQL или `sqlc.yaml`, затем генерируйте снова.

**3. Использовать pool вместо транзакции.** `s.q` привязан к pool. После `qtx := s.q.WithTx(tx)` отправляйте все три запроса через `qtx`.

**4. Не проверять тип SUM.** В копии решения мы убрали `::bigint` из `OrderTotal`.

Исправление: `COALESCE(…)::bigint AS total`, затем generate.

Полностью убирать `COALESCE` тоже нельзя. Следующий неверный вариант при генерации дал `int64`:

```sql
-- name: OrderTotal :one
SELECT SUM(quantity * unit_price) AS total
FROM order_items
WHERE order_id = $1;
```

```console
$ go test -run TestOrderTotal .
--- FAIL: TestOrderTotal (0.05s)
    store_test.go:262: OrderTotal(3): can't scan into dest[0] (col: total): cannot scan NULL into *int64
FAIL
FAIL	github.com/abdurahmon27/bozor	0.055s
FAIL
```

`store_test.go:262` — строка проверки. `cannot scan NULL into *int64` означает, что нельзя записать `NULL` по адресу `int64`.
У заказа `3` нет позиций. Исправление: ноль через `COALESCE`, явный тип через `::bigint`.

**5. Преобразовывать количество в `int32` без проверки.** `int32(it.Quantity)` обрезает слишком большое число. Сначала проверьте границы `1 … math.MaxInt32`.
**6. Всегда ждать пустой слайс от `:many`.** При этой настройке возможен `nil`. В доменном методе используйте `make([]Product, 0, len(rows))`.
Другой вариант: `emit_empty_slices: true` в `gen.go`; повторная генерация создаёт `items := []T{}`.
