## What you will learn

bozor compiles, its tests pass and it runs. But an order asks for 50 apples while the stock is 40, and the program still prints "buyurtma qabul qilindi" ("order accepted").
The JSON of the catalog has no price. The compiler is silent and so are the tests. Who finds these bugs?

**One idea:** the compiler checks only the rules of the language. Code that compiles but is wrong is found by **static analysis** tools: they read the code without running it.
Each tool looks at its own layer: `go vet` ships with Go, `staticcheck` adds more checks, `govulncheck` looks for known vulnerabilities in dependencies
and says "affected" only when your code *calls* the vulnerable function. All three chain into one line before a commit with `&&`.

By the end you will:

- find a duplicated JSON tag with `go vet ./...`, fix it and explain why `go test` did not see it;
- install `staticcheck` at an exact version, find an `err` that was overwritten without a check (`SA4006`) and fix it with a short `if`;
- read the `govulncheck` result on three levels (module, package, function), find GO-2022-1059 in `golang.org/x/text v0.3.7` by its trace and close it with `go get`;
- in `TASK.md`, fix the three problems that these three tools find in a teammate's `Rename` PR, until `go test ./...` passes.

Three core new words today:

| Word | Plain meaning | English term |
|---|---|---|
| `go vet` | the code checker that ships with Go: it finds suspicious places without running the code | go vet |
| `staticcheck` | a code checker you install separately: over a hundred checks, most of them not in `go vet` | staticcheck |
| `govulncheck` | compares the versions in `go.mod` with the Go vulnerability database and checks whether your code calls a vulnerable function | govulncheck |

A **vulnerability** is a security bug in a dependency's code that can be exploited from outside. Helper ideas: `go install package@version` (installing a tool) and the `&&` chain (you saw it in GB-1.01).

## The problem: it compiles, the test passes, the program is wrong

The start of the video is the step `_video/00-boshlash`. Its file `cmd/bozor/main.go`:

```go filename="_video/00-boshlash/cmd/bozor/main.go" showLineNumbers

package main

import (
	"encoding/json"
	"fmt"
	"os"

	"github.com/abdurahmon27/bozor/internal/store"
	"golang.org/x/text/language"
	"golang.org/x/text/message"
)

const tiyinPerSom = 100 // 1 soʻm = 100 tiyin

func main() {
	var st store.Store
	st.Add("olma", 1_200_000, 40)
	st.Add("non", 400_000, 100)

	printer := message.NewPrinter(language.Uzbek)
	for _, p := range st.List() {
		printer.Printf("%d. %s: %d soʻm\n", p.ID, p.Name, p.Price/tiyinPerSom)

	err := st.Sell(1, 50)
	err = st.Sell(2, 3)
	if err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	fmt.Println("buyurtma qabul qilindi")

	if err := json.NewEncoder(os.Stdout).Encode(st.List()); err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
}
```

## Three tools, three layers

The compiler (`go build`) checks the rules of the language: spelling, types, an unused import. The two bugs above break no rule, so the compiler is silent.
**Static analysis** tools read the code without running it and say: "this does not break a rule, but it looks suspicious". Today there are three tools, each looking at something different:

| Tool | Where from | What it looks at | Today's finding |
|---|---|---|---|
| `go vet` | ships with Go | suspicious constructs (35 checks) | a duplicated JSON tag |
| `staticcheck` | installed separately | over a hundred checks, many not in `go vet` | an `err` overwritten without a check |
| `govulncheck` | installed separately | known vulnerabilities in dependencies | an old `golang.org/x/text` |

The path of code to a commit:

```text
code ─┬─ go build ......... language rules
      └─ static analysis .. reads the code without running it
             ├─ go vet ........... ships with Go
             ├─ staticcheck ...... more checks
             └─ govulncheck ...... known vulnerabilities
                      │
                   commit  (one line)
```

The `go vet` documentation describes it like this: "examines Go source code and reports suspicious constructs" ([pkg.go.dev/cmd/vet](https://pkg.go.dev/cmd/vet)).

`cmd/bozor` has no test file, and the test of the `store` package passed. The video shows `0.003s`, my run shows `0.002s`: test time differs a little on every run, only `ok` matters.

**A)** nothing: `go test` already ran vet · **B)** an error in `store.go` · **C)** an error in `main.go`

<details>
<summary>Answer</summary>

**B.** The error is in `store.go`, not in `main.go`. If you chose **A**, you thought `go test` runs every vet check: below we see that it runs only 11 of them. **C**: `main.go` has no JSON tags.

</details>

```console
$ go vet ./...
internal/store/store.go:16:2: struct field OldPrice repeats json tag "price" also at store.go:15
```

Reading the message:

- `internal/store/store.go:16:2`: the file, line and column (the `file:line:column` form from GB-1.01);
- `struct field OldPrice repeats json tag "price"`: "the field `OldPrice` repeats the JSON tag `price`";
- `also at store.go:15`: "the same tag is also on line 15 of this file".

The code compiled and the test passed; only vet saw the bug. Lines 12–18 of `store.go`:

```go
type Product struct {
	ID       int64  `json:"id"`
	Name     string `json:"name"`
	Price    int64  `json:"price"` // tiyin
	OldPrice int64  `json:"price"` // chegirmagacha narx, tiyin

```

A teammate added the field `OldPrice` for the price before a discount (line 15 is `Price`, line 16 is `OldPrice`). They copied the `Price` line and did not change the tag.

### Why `go test` did not find it

`go test` does not run every vet check, only **the 11 most reliable ones**: they almost never warn for nothing. `go help test` lists them:

```console
$ go help test | grep -A2 'high-confidence'
binary. Only a high-confidence subset of the default go vet checks are
used. That subset is: atomic, bools, buildtag, directive, errorsas,
ifaceassert, nilfunc, printf, stdversion, stringintconv, and tests.
```

`printf` (GB-1.04) is in this list. `structtag`, which checks tags, is not. `go vet ./...` runs all of them by default; `go tool vet help` lists them, and we can count:

```console
$ go tool vet help | grep -c '^    [a-z]'
35
```

| Command | How many checks | `printf` | `structtag` |
|---|---|---|---|
| `go test ./...` | 11 | yes | no |
| `go vet ./...` | 35 | yes | yes |

In the previous lesson `structtag` found a space inside a tag ([GB-3.02](/lab/youtube/gb/gb-3-02/en)). Today it found another bug.

## A duplicated tag: JSON silently drops both fields

If two fields have the **same** JSON name, `encoding/json` drops both of them and reports no error ([pkg.go.dev/encoding/json#Marshal](https://pkg.go.dev/encoding/json#Marshal):
"all fields are ignored; no error occurs"). That is why the catalog JSON in the video has no `price`. `Unmarshal` does not receive the price either: it silently disappears.
I checked this with a small program. It is not in the course folder; its full code is below (in a separate folder after `go mod init example.com/takror`, then `go run .`):

```go
package main

import (
	"encoding/json"
	"fmt"
)

type Product struct {
	ID       int64 `json:"id"`
	Price    int64 `json:"price"`
	OldPrice int64 `json:"price"`
}

func main() {
	p := Product{ID: 1, Price: 1_200_000, OldPrice: 1_500_000}
	data, err := json.Marshal(p)
	fmt.Println(string(data), err)

	var q Product
	err = json.Unmarshal([]byte(`{"id":1,"price":5}`), &q)
	fmt.Println(q, err)
}
```

```console
$ go run .
{"id":1} <nil>
{1 0 0} <nil>
$ go vet ./...
main.go:11:2: struct field OldPrice repeats json tag "price" also at main.go:10
```

| Action | Result | Why |
|---|---|---|
| `json.Marshal(p)` | `{"id":1}` | both `Price` and `OldPrice` were dropped; `err` is `nil` |
| `json.Unmarshal(…"price":5…)` | `{1 0 0}` | the key `price` was written to no field; `err` is `nil` |
| `go vet ./...` | `struct field OldPrice repeats json tag "price"` | vet points at the line |

The fix: give `OldPrice` its own key, `old_price`. We do not add `omitempty`: the rule from [GB-3.02](/lab/youtube/gb/gb-3-02/en) says not to put `omitempty` on numbers, otherwise a zero and a missing key cannot be told apart.

```go
type Product struct {
	ID       int64  `json:"id"`
	Name     string `json:"name"`
	Price    int64  `json:"price"`     // tiyin
	OldPrice int64  `json:"old_price"` // chegirmagacha narx, tiyin
	Stock    int    `json:"stock"`
}
```

`&&` means "run the next command only if the previous one succeeded" (GB-1.01). If `go vet` is silent, `go run` runs:

```console
$ go vet ./... && go run ./cmd/bozor
1. olma: 12 000 soʻm
2. non: 4 000 soʻm
buyurtma qabul qilindi
[{"id":1,"name":"olma","price":1200000,"old_price":0,"stock":40},{"id":2,"name":"non","price":400000,"old_price":0,"stock":97}]
```

`go vet` was silent, so `go run` ran too. The price is back in the JSON, and `old_price` is zero: there is no discount.

## staticcheck: installing it

The second bug from the video, the order, is still there, and vet is silent. To find it we need `staticcheck`. It is a widely used static analysis tool for Go, run by an independent project
([staticcheck.dev](https://staticcheck.dev/docs/)). It has over a hundred checks: some resemble vet's, many are not in vet. A check name is a group and a number:
the name in parentheses (for example `SA4006`) is the group (`SA`) and the number (`4006`).

The tool does not ship with Go, so we install it with `go install`. The parts of the line:

| Part | What it is |
|---|---|
| `go install` | downloads the module, builds the command in it and puts the binary file into Go's `bin` folder |
| `honnef.co/go/tools/cmd/staticcheck` | `honnef.co/go/tools` is the module; `cmd/staticcheck` is the command folder inside it (GB-2.06) |
| `@2026.2.2` | the version after the at sign: with an exact version, everyone on the team gets the same checks |

```console
$ go install honnef.co/go/tools/cmd/staticcheck@2026.2.2
go: downloading honnef.co/go/tools v0.8.2
go: downloading golang.org/x/tools v0.51.0
go: downloading golang.org/x/exp/typeparams v0.0.0-20231108232855-2478ac86f678
go: downloading github.com/BurntSushi/toml v1.4.1-0.20240526193622-a339e1f7089c
go: downloading golang.org/x/exp v0.0.0-20231110203233-9a3e6036ecaa
go: downloading golang.org/x/sync v0.23.0
go: downloading golang.org/x/mod v0.41.0
```

Above is the complete output with a clean module cache (my run: the cache was empty). The video shows only the first line and hides the rest with `…`.
When the cache is already full, `go install` prints nothing. If it also downloads a Go version for the first time, one more line, `go: downloading go1.27.4`, can appear.
The staticcheck release is named by year (`2026.2.2`); the module version `v0.8.2` is the same release (`staticcheck -version` shows both). `go install` does not touch bozor's `go.mod`.

Now run it. A common error:

```console
$ staticcheck ./...
bash: staticcheck: command not found
```

The shell did not find `staticcheck`: the binary is installed, but Go's `bin` folder is not in **PATH** (PATH is the list of folders where the shell looks for commands). The fix:

```console
$ export PATH="$PATH:$(go env GOPATH)/bin"
```

The command prints nothing. `go env GOPATH` prints Go's home folder (usually `~/go`), and `go install` puts binaries into its `bin` subfolder. `$( … )` puts the result of a command into the line,
and `export` appends it to the end of PATH. This works only in the current terminal. To make it permanent, add the same line to the end of `~/.bashrc` (in zsh, `~/.zshrc`):

```console
$ echo 'export PATH="$PATH:$(go env GOPATH)/bin"' >> ~/.bashrc
```

This one prints nothing as well. Inside single quotes `$` is not expanded now: the line is written to the file as it is. `>>` appends to the end of the file.

## staticcheck: the lost error

The order code (`cmd/bozor/main.go`, lines 26–32):

```go
	err := st.Sell(1, 50)
	err = st.Sell(2, 3)
	if err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	fmt.Println("buyurtma qabul qilindi")
```

The first `Sell` sells 50 apples and writes its error to `err`. The second `Sell` sells 3 loaves and writes its result to `err` again. Then `if err != nil`. Which line does `staticcheck ./...` point at?

**A)** 26: `err := st.Sell(1, 50)` · **B)** 27: `err = st.Sell(2, 3)` · **C)** none: `err` is checked

<details>
<summary>Answer</summary>

**A.** The value from line 26 is overwritten on line 27 before anybody reads it. If you chose **B**: the value on line 27 is read by the `if`, so it is fine. **C**: `err` is checked, but only its *last* value; the first one is lost.

</details>

First run it on the `00-boshlash` step (both bugs are there):

```console
$ staticcheck ./...
cmd/bozor/main.go:26:2: this value of err is never used (SA4006)
```

`cmd/bozor/main.go:26:2`: line 26, column 2: "this value of `err` is never used". In parentheses is the name of the check, `SA4006`. Why:

| Line | Code | What `err` holds |
|---|---|---|
| 26 | `err := st.Sell(1, 50)` | the apple error (stock 40, requested 50) |
| 27 | `err = st.Sell(2, 3)` | the bread result, `nil`; the apple error is gone |
| 28 | `if err != nil {` | `err` is `nil`: the `if` body is skipped |

So nobody checked the apple error and the program said "buyurtma qabul qilindi". This is the first bug from the start of the lesson. Vet did not see it (see the `go vet ./... && go run ./cmd/bozor` line above),
and `staticcheck` found it. The reverse is true as well: in the output above `staticcheck` did not find the duplicated tag; vet found that. The tools complement each other.

If you know the name of a check, `staticcheck -explain` shows its documentation in the terminal:

```console
$ staticcheck -explain SA4006
A value assigned to a variable is never read before being overwritten. Forgotten error check or dead code?

Available since
    2017.1

Online documentation
    https://staticcheck.dev/docs/checks#SA4006
```

The first line: "a value assigned to a variable is never read before being overwritten: a forgotten error check or dead code". Below it is the address of the documentation page. The video hides the "Available since 2017.1" part.

**The fix: a short `if`** ([GB-1.05](/lab/youtube/gb/gb-1-05/en)): `err` lives only inside this `if` and is checked at once. The second `Sell` gets its own `err`: one value can no longer overwrite another.

```go
	if err := st.Sell(1, 50); err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	if err := st.Sell(2, 3); err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
```

```console
$ staticcheck ./... && go run ./cmd/bozor
1. olma: 12 000 soʻm
2. non: 4 000 soʻm
xato: olma: qoldiq 40, soʻralgan 50
exit status 1
```

`staticcheck` is silent, and the program tells the truth: apple stock 40, requested 50. `exit status 1` is the exit code that `os.Exit(1)` returned; `go run` prints it this way (GB-1.07).

## A mid-lesson question: a package without a test file

`cmd/bozor` has no test file. Suppose someone wrote `fmt.Printf("%s\n", p.Name, p.Stock)` in this package: one `%s`, two arguments. `go build` passes. What does `go test ./...` do?

**A)** passes: `[no test files]` · **B)** `FAIL`: a vet `printf` error · **C)** a compile error

<details>
<summary>Answer</summary>

**B.** `go test` runs the same 11 vet checks in every package, even without a test file. `printf` is among them, so the package fails with `build failed`. If you chose **A**,
you thought `go test` skips a package without tests (that line does appear, but only when vet is clean). **C**: `go build` passes, because `printf` arguments are not a rule of the language.
I checked this not on the course folder's `main.go` but on a small separate program (it is not in the course folder; run it in a separate folder after `go mod init example.com/printf`):

```go
package main

import "fmt"

func main() {
	fmt.Printf("%s\n", "olma", 40)
}
```

```console
$ go build ./...
$ go test ./...
# example.com/printf
./main.go:6:2: fmt.Printf call needs 1 arg but has 2 args
FAIL	example.com/printf [build failed]
```

## Going deeper (optional): an old tool after a Go update

Two details; both answer the question "why pin versions and why inside the folder".

**1. It matters which Go built the tool.** A static analysis tool reads Go source with the type checker of the Go that built it. A staticcheck built with the old Go (1.26.8)
failed in a Go 1.27.4 project like this (I built it with `GOTOOLCHAIN=go1.26.8 go install honnef.co/go/tools/cmd/staticcheck@2026.2.2`; the home folder in the output is shortened to `…`):

```console
$ go version
go version go1.27.4 linux/amd64
$ staticcheck ./...
-: …/src/internal/poll/splice_linux.go:237:21: unknown field rfd in struct literal of type splicePipe (compile)
```

The message is not about your code: in the package `internal/poll` of the Go **standard library**, the struct `splicePipe` has no field `rfd`. Go 1.27 uses a new language feature there
(a direct reference to a field of an embedded struct in a struct literal; [staticcheck 2026.2 release notes](https://staticcheck.dev/changes/2026.2/)), and a tool built with the old Go does not know it.
The fix: run `go install …@2026.2.2` again with the new Go, **inside this folder**: in the folder the `go` command switches to the `go 1.27` from `go.mod`, and the tool is built with that Go.

**2. `govulncheck@latest` and the pinned version.** As of 2026-11-27, `govulncheck@latest` (`v1.10.0`, 2026-11-17) could not load the standard library when the older `go` on my machine
automatically switched to Go 1.27 (`internal/poll/splice_linux.go:237:21: use of promoted field … requires go1.27 or later`); if Go 1.27 is installed directly, `v1.10.0` works. `v1.9.0` worked in both cases,
so the lesson pins it. When a new version appears, re-check and raise the number. There is a second reason: so that the whole team sees the same result.

Another way to pin a tool (since Go 1.24): record it in `go.mod` itself. My run (in a copy of the 04-yangilash step):

```console
$ go get -tool honnef.co/go/tools/cmd/staticcheck@2026.2.2
go: added github.com/BurntSushi/toml v1.4.1-0.20240526193622-a339e1f7089c
go: added golang.org/x/exp/typeparams v0.0.0-20231108232855-2478ac86f678
go: added honnef.co/go/tools v0.8.2
$ go tool staticcheck ./...
```

The first command adds the line `tool honnef.co/go/tools/cmd/staticcheck` and `// indirect` dependencies to `go.mod`; the second is silent (no findings). The version is pinned in `go.mod`, and the tool is always built with the current Go.
This lesson used `go install`: `go.mod` keeps only bozor's own dependencies.

## Common mistakes

**1. "It compiled and the test passed, so the code is right."** The whole lesson is against this belief. `go build` checks language rules, `go test` runs only the checks someone wrote plus 11 vet checks.
A duplicated tag, an unchecked `err` and an old dependency all compile and pass the tests. The fix: the four-command line before every commit.

**2. `bash: staticcheck: command not found`.** The command is shown above. How to read it: the shell did not find a command called `staticcheck` in the PATH folders. The cause: `go install` put the binary into `$(go env GOPATH)/bin`, and that folder is not in PATH.
The fix: `export PATH="$PATH:$(go env GOPATH)/bin"`, and to make it permanent, write the line to `~/.bashrc` too.

**3. Installing a tool outside the folder.** If Go is older, the tool is built with the old Go and cannot read the new standard library: `unknown field rfd in struct literal of type splicePipe (compile)`.
How to read it: the error is in `internal/poll`, which is Go's own code, not yours. The fix: run `go install` again inside the lesson folder; reinstall the tools after you update Go as well.

**4. Reading `doesn't appear to call` as "everything is fine".** The exit code is 0 and "affected by 0", but there were vulnerabilities at the package and module levels (GO-2022-1059, GO-2026-6629, GO-2026-5970). A function nobody calls today may be called by new code tomorrow.
The fix: run `go get golang.org/x/text@latest` anyway.
