## Что вы узнаете

bozor компилируется, тесты проходят, программа работает. Но заказ просит 50 штук яблок при остатке 40, а программа всё равно пишет «buyurtma qabul qilindi» («заказ принят»).
А в JSON каталога нет цены. Компилятор молчит, тесты молчат. Кто найдёт эти ошибки?

**Одна идея:** компилятор проверяет только правила языка. Код, который компилируется, но неверен, находят инструменты **статического анализа** (static analysis): они читают код, не запуская его.
Каждый инструмент смотрит на свой слой: `go vet` поставляется вместе с Go, `staticcheck` даёт больше проверок, `govulncheck` ищет известные уязвимости в зависимостях
и говорит «affected» только если ваш код *вызывает* уязвимую функцию. Все три собираются через `&&` в одну строку перед коммитом.

К концу урока вы:

- найдёте дублирующийся JSON-тег через `go vet ./...`, исправите его и объясните, почему `go test` его не увидел;
- установите `staticcheck` точной версии, найдёте `err`, перезаписанный без проверки (`SA4006`), и исправите его коротким `if`;
- прочитаете результат `govulncheck` на трёх уровнях (модуль, пакет, функция), найдёте GO-2022-1059 в `golang.org/x/text v0.3.7` по trace и закроете её через `go get`;
- в `TASK.md` исправите три проблемы из PR коллеги с методом `Rename`, которые находят эти же три инструмента, пока `go test ./...` не пройдёт.

Три главных новых слова сегодня:

| Слово | Простой смысл | По-английски |
|---|---|---|
| `go vet` | анализатор кода, который поставляется вместе с Go: ищет подозрительные места, не запуская код | go vet |
| `staticcheck` | анализатор, который ставится отдельно: больше сотни проверок, большинства нет в `go vet` | staticcheck |
| `govulncheck` | сверяет версии из `go.mod` с базой уязвимостей Go и проверяет, вызывает ли ваш код уязвимую функцию | govulncheck |

**Уязвимость** (vulnerability) — проверяемая снаружи ошибка безопасности в коде зависимости. Вспомогательные понятия: `go install пакет@версия` (установка инструмента) и цепочка `&&` (вы видели её в GB-1.01).

## Проблема: компилируется, тест проходит, программа неверна

Начало видео — шаг `_video/00-boshlash`. Его файл `cmd/bozor/main.go`:

```go filename="_video/00-boshlash/cmd/bozor/main.go" showLineNumbers
// bozor dasturi: katalogni chiqaradi, buyurtmani sotadi va katalogni JSON'da yozadi.
package main

import (
	"encoding/json"
	"fmt"
	"os"

	"github.com/abdurahmon27/bozor/internal/store"
	"golang.org/x/text/language"
	"golang.org/x/text/message"
)

const tiyinPerSom = 100 // 1 soʻm = 100 tiyin

func main() {
	var st store.Store
	st.Add("olma", 1_200_000, 40)
	st.Add("non", 400_000, 100)

	printer := message.NewPrinter(language.Uzbek)
	for _, p := range st.List() {
		printer.Printf("%d. %s: %d soʻm\n", p.ID, p.Name, p.Price/tiyinPerSom)
	}

	err := st.Sell(1, 50)
	err = st.Sell(2, 3)
	if err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	fmt.Println("buyurtma qabul qilindi")

	if err := json.NewEncoder(os.Stdout).Encode(st.List()); err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
}
```

Всё в этом файле вам знакомо по прошлым урокам. Краткое напоминание:

| Строка | Код | Что делает |
|---|---|---|
| 1–2 | комментарий, `package main` | пакет программы (GB-1.01) |
| 4–12 | `import (…)` | стандартная библиотека (`encoding/json`, `fmt`, `os`), пакет `internal/store` проекта bozor и внешний модуль `golang.org/x/text` (GB-2.06) |
| 14 | `const tiyinPerSom = 100` | 1 сум = 100 тийин; цена хранится в тийинах (GB-1.03) |
| 17–19 | `var st store.Store`, два `st.Add` | пустой каталог и два товара: 40 яблок и 100 штук хлеба |
| 21–24 | `printer`, `for … range` | печатает каталог в сумах: цена в тийинах делится на `tiyinPerSom` (GB-2.06) |
| 26–27 | `err := st.Sell(1, 50)`, `err = st.Sell(2, 3)` | продаёт 50 яблок, затем 3 хлеба; `Sell` возвращает `error`, результат пишется в `err` (GB-2.08) |
| 28–31 | `if err != nil { … os.Exit(1) }` | при ошибке пишет в stderr и выходит с кодом 1 (GB-1.07) |
| 32 | `fmt.Println(…)` | «buyurtma qabul qilindi» («заказ принят») |
| 34–37 | `json.NewEncoder(os.Stdout).Encode(st.List())` | пишет каталог в stdout как JSON (GB-3.02) |

Запускаем:

```console
$ go run ./cmd/bozor
1. olma: 12 000 soʻm
2. non: 4 000 soʻm
buyurtma qabul qilindi
[{"id":1,"name":"olma","stock":40},{"id":2,"name":"non","stock":97}]
```

Неверны две вещи:

1. Запрошено 50 яблок, на складе 40, но программа пишет «buyurtma qabul qilindi». Остаток в каталоге остался 40.
2. В JSON каталога нет ключа `price`, хотя в `Product` цена есть.

Третья проблема не в коде, а в зависимости; до неё мы дойдём в разделе про `govulncheck`.

## Три инструмента, три слоя

Компилятор (`go build`) проверяет правила языка: орфографию, типы, неиспользуемый импорт. Две ошибки выше правил не нарушают, поэтому компилятор молчит.
Инструменты **статического анализа** читают код, не запуская его, и говорят: «правилам это не противоречит, но выглядит подозрительно». Сегодня три инструмента, каждый смотрит на своё:

| Инструмент | Откуда | Что проверяет | Сегодняшняя находка |
|---|---|---|---|
| `go vet` | поставляется с Go | подозрительные конструкции (35 проверок) | дублирующийся JSON-тег |
| `staticcheck` | ставится отдельно | больше сотни проверок, многих нет в `go vet` | `err`, перезаписанный без проверки |
| `govulncheck` | ставится отдельно | известные уязвимости в зависимостях | старый `golang.org/x/text` |

Путь кода до коммита:

```text
код ─┬─ go build ......... правила языка
     └─ статический анализ ... читает код, не запуская его
            ├─ go vet ........... поставляется с Go
            ├─ staticcheck ...... больше проверок
            └─ govulncheck ...... известные уязвимости
                     │
                  коммит  (одна строка)
```

Документация `go vet` описывает его так: «examines Go source code and reports suspicious constructs» — читает исходный код Go и сообщает о подозрительных конструкциях ([pkg.go.dev/cmd/vet](https://pkg.go.dev/cmd/vet)).

## go vet: тест прошёл, vet нашёл

Сначала тесты. `./...` значит «эта папка и все пакеты внутри» (GB-1.01):

```console
$ go test ./...
?   	github.com/abdurahmon27/bozor/cmd/bozor	[no test files]
ok  	github.com/abdurahmon27/bozor/internal/store	0.002s
```

В `cmd/bozor` нет файла тестов, тест пакета `store` прошёл. В видео `0.003s`, у меня `0.002s`: время теста каждый раз немного другое, важно только `ok`.
Из GB-1.04 вы знаете: `go test` сам запускает и проверки vet. Теперь запустим сам `go vet ./...` — по всем пакетам. Что выведется?

**A)** ничего: `go test` уже запускал vet · **B)** ошибка в `store.go` · **C)** ошибка в `main.go`

<details>
<summary>Ответ</summary>

**B.** Ошибка в `store.go`, а не в `main.go`. Если вы выбрали **A**, вы решили, что `go test` запускает все проверки vet: ниже увидим, что он запускает только 11. **C** — в `main.go` нет JSON-тегов.

</details>

```console
$ go vet ./...
internal/store/store.go:16:2: struct field OldPrice repeats json tag "price" also at store.go:15
```

Читаем сообщение:

- `internal/store/store.go:16:2` — файл, строка и столбец (`файл:строка:столбец` из GB-1.01);
- `struct field OldPrice repeats json tag "price"` — «поле `OldPrice` повторяет JSON-тег `price`»;
- `also at store.go:15` — «такой же тег есть и в 15-й строке этого файла».

Код компилируется, тест прошёл, а ошибку увидел только vet. Строки 12–18 файла `store.go`:

```go
type Product struct {
	ID       int64  `json:"id"`
	Name     string `json:"name"`
	Price    int64  `json:"price"` // tiyin
	OldPrice int64  `json:"price"` // chegirmagacha narx, tiyin
	Stock    int    `json:"stock"`
}
```

Коллега добавил поле `OldPrice` для цены до скидки (строка 15 — `Price`, строка 16 — `OldPrice`). Он скопировал строку `Price` и не изменил тег.

### Почему `go test` не нашёл

`go test` запускает не все проверки vet, а только **11 самых надёжных**: они почти никогда не предупреждают зря. Их перечисляет `go help test`:

```console
$ go help test | grep -A2 'high-confidence'
binary. Only a high-confidence subset of the default go vet checks are
used. That subset is: atomic, bools, buildtag, directive, errorsas,
ifaceassert, nilfunc, printf, stdversion, stringintconv, and tests.
```

`printf` (GB-1.04) в этом списке есть. А `structtag`, проверяющего теги, нет. `go vet ./...` по умолчанию запускает все; `go tool vet help` их считает:

```console
$ go tool vet help | grep -c '^    [a-z]'
35
```

| Команда | Сколько проверок | `printf` | `structtag` |
|---|---|---|---|
| `go test ./...` | 11 | есть | нет |
| `go vet ./...` | 35 | есть | есть |

В прошлом уроке `structtag` нашёл пробел в теге ([GB-3.02](/lab/youtube/gb/gb-3-02/ru)). Сегодня он нашёл ещё одну ошибку.

## Повторяющийся тег: JSON молча отбрасывает оба поля

Если у двух полей **одинаковое** JSON-имя, `encoding/json` отбрасывает оба и не сообщает об ошибке ([pkg.go.dev/encoding/json#Marshal](https://pkg.go.dev/encoding/json#Marshal):
«all fields are ignored; no error occurs»). Поэтому в JSON каталога из видео нет `price`. `Unmarshal` тоже не получает цену: она молча пропадает.
Я проверил это маленькой программой. Её нет в папке курса; полный код ниже (в отдельной папке после `go mod init example.com/takror`, затем `go run .`):

```go
package main

import (
	"encoding/json"
	"fmt"
)

type Product struct {
	ID       int64 `json:"id"`
	Price    int64 `json:"price"`
	OldPrice int64 `json:"price"`
}

func main() {
	p := Product{ID: 1, Price: 1_200_000, OldPrice: 1_500_000}
	data, err := json.Marshal(p)
	fmt.Println(string(data), err)

	var q Product
	err = json.Unmarshal([]byte(`{"id":1,"price":5}`), &q)
	fmt.Println(q, err)
}
```

```console
$ go run .
{"id":1} <nil>
{1 0 0} <nil>
$ go vet ./...
main.go:11:2: struct field OldPrice repeats json tag "price" also at main.go:10
```

| Действие | Результат | Почему |
|---|---|---|
| `json.Marshal(p)` | `{"id":1}` | отброшены и `Price`, и `OldPrice`; `err` равен `nil` |
| `json.Unmarshal(…"price":5…)` | `{1 0 0}` | ключ `price` не записан ни в одно поле; `err` равен `nil` |
| `go vet ./...` | `struct field OldPrice repeats json tag "price"` | vet указывает на строку |

Исправление: у `OldPrice` свой ключ, `old_price`. `omitempty` не добавляем: правило из [GB-3.02](/lab/youtube/gb/gb-3-02/ru) — к числам `omitempty` не ставят, иначе ноль и отсутствующий ключ не отличить.

```go
type Product struct {
	ID       int64  `json:"id"`
	Name     string `json:"name"`
	Price    int64  `json:"price"`     // tiyin
	OldPrice int64  `json:"old_price"` // chegirmagacha narx, tiyin
	Stock    int    `json:"stock"`
}
```

`&&` значит «запусти следующую команду, только если предыдущая завершилась успешно» (GB-1.01). Если `go vet` молчит, `go run` запускается:

```console
$ go vet ./... && go run ./cmd/bozor
1. olma: 12 000 soʻm
2. non: 4 000 soʻm
buyurtma qabul qilindi
[{"id":1,"name":"olma","price":1200000,"old_price":0,"stock":40},{"id":2,"name":"non","price":400000,"old_price":0,"stock":97}]
```

`go vet` промолчал, поэтому запустился и `go run`. Цена в JSON вернулась, а `old_price` равен нулю: скидки нет.

## staticcheck: установка

Вторая ошибка из видео, заказ, всё ещё на месте, а vet молчит. Чтобы её найти, нужен `staticcheck`. Это распространённый в Go инструмент статического анализа, его ведёт независимый проект
([staticcheck.dev](https://staticcheck.dev/docs/)). Проверок больше сотни: часть похожа на проверки vet, многих в vet нет. Имя проверки состоит из буквы и цифр:
имя в скобках (например `SA4006`) — это группа (`SA`) и номер (`4006`).

В комплект Go инструмент не входит, ставим его через `go install`. Части строки:

| Часть | Что это |
|---|---|
| `go install` | скачивает модуль, собирает из него команду и кладёт бинарный файл в папку `bin` Go |
| `honnef.co/go/tools/cmd/staticcheck` | `honnef.co/go/tools` — модуль; `cmd/staticcheck` — папка команды в нём (GB-2.06) |
| `@2026.2.2` | после знака «собака» версия: если указать точную версию, у всей команды будут одни и те же проверки |

```console
$ go install honnef.co/go/tools/cmd/staticcheck@2026.2.2
go: downloading honnef.co/go/tools v0.8.2
go: downloading golang.org/x/tools v0.51.0
```

Запускаем. Частая ошибка:

```console
$ staticcheck ./...
bash: staticcheck: command not found
```

Shell не нашёл `staticcheck`: бинарный файл установлен, но папки `bin` Go нет в **PATH** (PATH — список папок, где shell ищет команды). Исправление:

```console
$ export PATH="$PATH:$(go env GOPATH)/bin"
```

Команда ничего не выводит. `go env GOPATH` печатает домашнюю папку Go (обычно `~/go`), `go install` кладёт бинарные файлы в её подпапку `bin`. `$( … )` подставляет результат команды в строку,
а `export` дописывает её в конец PATH. Это действует только в текущем терминале. Чтобы сделать постоянно, добавьте ту же строку в конец `~/.bashrc` (в zsh — `~/.zshrc`):

```console
$ echo 'export PATH="$PATH:$(go env GOPATH)/bin"' >> ~/.bashrc
```

И эта команда ничего не выводит. Внутри одинарных кавычек `$` сейчас не раскрывается: в файл строка записывается как есть. `>>` дописывает в конец файла.

## staticcheck: потерянная ошибка

Код заказа (`cmd/bozor/main.go`, строки 26–32):

```go
	err := st.Sell(1, 50)
	err = st.Sell(2, 3)
	if err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	fmt.Println("buyurtma qabul qilindi")
```

Первый `Sell` продаёт 50 яблок и записывает ошибку в `err`. Второй `Sell` продаёт 3 хлеба, результат снова пишется в `err`. Потом `if err != nil`. Какую строку покажет `staticcheck ./...`?

**A)** 26: `err := st.Sell(1, 50)` · **B)** 27: `err = st.Sell(2, 3)` · **C)** никакую: `err` проверен

<details>
<summary>Ответ</summary>

**A.** Значение из строки 26 в строке 27 перезаписывается, не будучи прочитанным. Если вы выбрали **B**: значение из строки 27 читает `if`, поэтому с ним всё в порядке. **C** — `err` проверен, но только его *последнее* значение; первое потеряно.

</details>

Сначала запустим на шаге `00-boshlash` (обе ошибки там):

```console
$ staticcheck ./...
cmd/bozor/main.go:26:2: this value of err is never used (SA4006)
```

`cmd/bozor/main.go:26:2` — строка 26, столбец 2: «это значение `err` никогда не используется». В скобках имя проверки, `SA4006`. Почему:

| Строка | Код | Что лежит в `err` |
|---|---|---|
| 26 | `err := st.Sell(1, 50)` | ошибка по яблокам (остаток 40, запрошено 50) |
| 27 | `err = st.Sell(2, 3)` | результат по хлебу, `nil`; ошибка по яблокам потеряна |
| 28 | `if err != nil {` | `err` равен `nil`: внутрь `if` не заходим |

В итоге ошибку по яблокам никто не проверил, и программа сказала «buyurtma qabul qilindi». Это первая ошибка из начала урока. Vet её не увидел (см. выше строку `go vet ./... && go run ./cmd/bozor`),
а `staticcheck` нашёл. Верно и обратное: в выводе выше `staticcheck` не нашёл дублирующийся тег, его нашёл vet. Инструменты дополняют друг друга.

Если вы знаете имя проверки, `staticcheck -explain` показывает её документацию прямо в терминале:

```console
$ staticcheck -explain SA4006
A value assigned to a variable is never read before being overwritten. Forgotten error check or dead code?

Available since
    2017.1

Online documentation
    https://staticcheck.dev/docs/checks#SA4006
```

Первая строка: «значение, записанное в переменную, не прочитано до перезаписи: забытая проверка ошибки или лишний код». Ниже адрес страницы документации. В видео часть «Available since 2017.1» скрыта.

**Исправление — короткий `if`** ([GB-1.05](/lab/youtube/gb/gb-1-05/ru)): `err` живёт только внутри этого `if` и проверяется сразу. Второй `Sell` получает свой `err`: перезаписать одно значение другим уже нельзя.

```go
	if err := st.Sell(1, 50); err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	if err := st.Sell(2, 3); err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
```

```console
$ staticcheck ./... && go run ./cmd/bozor
1. olma: 12 000 soʻm
2. non: 4 000 soʻm
xato: olma: qoldiq 40, soʻralgan 50
exit status 1
```

`staticcheck` молчит, а программа говорит правду: остаток яблок 40, запрошено 50. `exit status 1` — код выхода, который вернул `os.Exit(1)`; `go run` печатает его так (GB-1.07).

## Промежуточный вопрос: пакет без файла тестов

В `cmd/bozor` нет файла тестов. Допустим, в этом пакете написали `fmt.Printf("%s\n", p.Name, p.Stock)`: `%s` один, аргументов два. `go build` проходит. Что сделает `go test ./...`?

**A)** пройдёт: `[no test files]` · **B)** `FAIL`: ошибка vet `printf` · **C)** ошибка компиляции

<details>
<summary>Ответ</summary>

**B.** `go test` запускает в каждом пакете те же 11 проверок vet, даже если файла тестов нет. `printf` среди них, поэтому пакет падает с `build failed`. Если вы выбрали **A**,
вы решили, что `go test` пропускает пакет без тестов (такая запись появляется, но только когда vet чист). **C** — `go build` проходит: аргументы `printf` не относятся к правилам языка.
Я проверил это не на `main.go` из папки курса, а на маленькой отдельной программе (её нет в папке курса; запускайте в отдельной папке после `go mod init example.com/printf`):

</details>

Третья ошибка не в коде, а в зависимости. В `go.mod` есть `golang.org/x/text` (в [GB-2.06](/lab/youtube/gb/gb-2-06/ru) этот модуль печатал цену в виде `12 000`). В папке урока он намеренно старой версии:

## Когда уязвимая функция вызывается

Теперь PR: пользователь передаёт язык аргументом (`cmd/bozor/main.go`, строки 21–27):

```go
	til := "uz"
	if len(os.Args) > 1 {
		til = os.Args[1]
	}
	matcher := language.NewMatcher([]language.Tag{language.Uzbek, language.Russian})
	tag, _ := language.MatchStrings(matcher, til)
	printer := message.NewPrinter(tag)
```

| Строка | Код | Что делает |
|---|---|---|
| 21 | `til := "uz"` | сначала `til` равен `"uz"` |
| 22–24 | `if len(os.Args) > 1 { til = os.Args[1] }` | если в командной строке есть аргумент, `til` получает его (GB-1.07) |
| 25 | `language.NewMatcher([]language.Tag{…})` | создаёт сопоставитель (`Matcher`) из языков, которые поддерживает bozor: узбекский и русский |
| 26 | `tag, _ := language.MatchStrings(matcher, til)` | превращает введённый текст языка в наиболее подходящий язык из списка; второй результат (индекс совпавшего текста) не нужен, поэтому `_` (GB-1.08) |
| 27 | `message.NewPrinter(tag)` | `printer` теперь работает с этим языковым тегом |

Что делает `MatchStrings`, читаем через `go doc` ([GB-2.07](/lab/youtube/gb/gb-2-07/ru)); он показывает и модули из `go.mod`:

```console
$ go doc language.MatchStrings
package language // import "golang.org/x/text/language"

func MatchStrings(m Matcher, lang ...string) (tag Tag, index int)
    MatchStrings parses and matches the given strings until one of them matches
    the language in the Matcher. A string may be an Accept-Language header as
    handled by ParseAcceptLanguage. The default language is returned if no other
    language matched.
```

- `m Matcher` — сопоставитель, который вернул `NewMatcher`;
- `lang ...string` — три точки: функция принимает несколько строк, мы передаём одну;
- документация: функция разбирает строки и сравнивает их, пока одна не совпадёт с одним из языков `Matcher`;
- третья строка: текст может быть **заголовком Accept-Language**. Его браузер отправляет серверу; в нём языки, которые предпочитает пользователь. HTTP-заголовки разберём в [GB-4.01](/lab/youtube/gb/gb-4-01/ru).

Что теперь скажет `govulncheck`, предположите. Результат:

## Одна строка перед коммитом

Четыре команды в одной строке:

```console
$ go vet ./... && staticcheck ./... && govulncheck ./... && go test ./...
No vulnerabilities found.
?   	github.com/abdurahmon27/bozor/cmd/bozor	[no test files]
ok  	github.com/abdurahmon27/bozor/internal/store	0.002s
```

- если инструмент находит проблему, он завершается с ненулевым кодом, и `&&` останавливает цепочку (`govulncheck` — если ваш код вызывает уязвимую функцию);
- если всё чисто, в конце запускаются тесты: здесь первая строка принадлежит `govulncheck`, две следующие — результат `go test`;
- `go vet` и `staticcheck` молчат, поэтому их строк нет; `govulncheck` берёт базу из интернета, так что интернет нужен;
- время теста: в видео `0.006s`, у меня `0.002s` — время меняется, важно `ok`.

Это проверка перед каждым коммитом. В [GB-8.05](/lab/youtube/gb#gb-8-05) такая проверка будет автоматически запускаться на каждом pull request.

## Глубже (необязательно): старый инструмент после обновления Go

Две подробности, обе отвечают на вопрос «зачем фиксировать версии и почему внутри папки».

**1. Важно, каким Go вы собрали инструмент.** Инструмент статического анализа читает исходный код Go с помощью проверки типов того Go, которым он собран. staticcheck, собранный старым Go (1.26.8),
упал в проекте на Go 1.27.4 так (я собрал его командой `GOTOOLCHAIN=go1.26.8 go install honnef.co/go/tools/cmd/staticcheck@2026.2.2`; домашняя папка в выводе сокращена до `…`):

```console
$ go version
go version go1.27.4 linux/amd64
$ staticcheck ./...
-: …/src/internal/poll/splice_linux.go:237:21: unknown field rfd in struct literal of type splicePipe (compile)
```

Сообщение не про ваш код: в пакете `internal/poll` **стандартной библиотеки** Go в struct `splicePipe` нет поля `rfd`. Там используется новая возможность языка Go 1.27
(прямое обращение к полю вложенного struct в struct-литерале; [staticcheck 2026.2 release notes](https://staticcheck.dev/changes/2026.2/)), а инструмент, собранный старым Go, её не знает.
Решение: заново выполнить `go install …@2026.2.2` новым Go, **внутри этой папки**: в папке команда `go` переключается на `go 1.27` из `go.mod`, и инструмент собирается этим Go.

**2. `govulncheck@latest` и зафиксированная версия.** По состоянию на 2026-11-27 `govulncheck@latest` (`v1.10.0`, 2026-11-17) не смог загрузить стандартную библиотеку, когда более старый `go` на моём компьютере
автоматически переключился на Go 1.27 (`internal/poll/splice_linux.go:237:21: use of promoted field … requires go1.27 or later`); если Go 1.27 установлен напрямую, `v1.10.0` работает. `v1.9.0` работал в обоих случаях,
поэтому урок фиксирует её. Когда выйдет новая версия, перепроверьте и поднимите номер. Есть и вторая причина: чтобы вся команда видела одинаковый результат.

Ещё один способ зафиксировать версию (с Go 1.24): записать инструмент в сам `go.mod`. Мой запуск (в копии шага 04-yangilash):

```console
$ go get -tool honnef.co/go/tools/cmd/staticcheck@2026.2.2
go: added github.com/BurntSushi/toml v1.4.1-0.20240526193622-a339e1f7089c
go: added golang.org/x/exp/typeparams v0.0.0-20231108232855-2478ac86f678
go: added honnef.co/go/tools v0.8.2
$ go tool staticcheck ./...
```

Первая команда добавляет в `go.mod` строку `tool honnef.co/go/tools/cmd/staticcheck` и `// indirect`-зависимости; вторая молчит (ошибок нет). Версия фиксируется в `go.mod`, и инструмент всегда собирается текущим Go.
В этом уроке использован `go install`: `go.mod` хранит только собственные зависимости bozor.

## Частые ошибки

**1. «Скомпилировалось и тест прошёл, значит код верный».** Весь урок против этого убеждения. `go build` проверяет правила языка, `go test` запускает только написанные проверки и 11 проверок vet.
Дублирующийся тег, непроверенный `err` и старая зависимость компилируются и проходят тесты. Исправление: строка из четырёх команд перед коммитом.

**2. `bash: staticcheck: command not found`.** Команда показана выше. Как читать: shell не нашёл команду `staticcheck` в папках из PATH. Причина: `go install` положил бинарный файл в `$(go env GOPATH)/bin`, а этой папки нет в PATH.
Исправление: `export PATH="$PATH:$(go env GOPATH)/bin"`, а чтобы это сохранялось, запишите строку и в `~/.bashrc`.

**3. Установка инструмента вне папки.** Если Go старее, инструмент собирается старым Go и не может прочитать новую стандартную библиотеку: `unknown field rfd in struct literal of type splicePipe (compile)`.
Как читать: ошибка в `internal/poll` — это код самого Go, не ваш. Исправление: заново выполните `go install` внутри папки урока; и после обновления Go переустанавливайте инструменты.

**4. Читать `doesn't appear to call` как «всё в порядке».** Код выхода 0 и «affected by 0», но уязвимости на уровне пакета и модуля были (GO-2022-1059, GO-2026-6629, GO-2026-5970). Функцию, которую сегодня не вызывают, завтра может вызвать новый код.
Исправление: всё равно выполните `go get golang.org/x/text@latest`.

## Проверьте себя

1. Какая команда находит повторяющийся JSON-тег и почему `go test` его не нашёл?

<details>
<summary>Ответ</summary>

`go vet ./...` (проверка `structtag`). `go test` запускает только 11 надёжных проверок vet, `structtag` среди них нет; `go vet ./...` запускает все 35.

</details>

2. Если `govulncheck` пишет «уязвимость есть, но ваш код её не вызывает» (`doesn't appear to call`), каков код выхода? Нужно ли обновлять модуль?

<details>
<summary>Ответ</summary>

Код выхода 0 (если код вызывает уязвимую функцию — 3). Обновить всё равно стоит: функцию, которую сегодня не вызывают, завтра может вызвать новый код, а уязвимости на уровне пакета и модуля тоже закроются.

</details>

3. Из [GB-2.10](/lab/youtube/gb/gb-2-10/ru): чему равно `len("oʻrik")`?

<details>
<summary>Ответ</summary>

6. Символ `ʻ` занимает в UTF-8 2 байта, остальные 4 буквы — по одному: 1 + 2 + 1 + 1 + 1 = 6.

</details>

4. Что запишет `json.Marshal(p)` в программе `takror` выше (`p`: `ID: 1`, `Price: 1_200_000`, `OldPrice: 1_500_000`)?

<details>
<summary>Ответ</summary>

`{"id":1}`. И `Price`, и `OldPrice` отбрасываются, `err` равен `nil`. Это первая строка вывода программы `takror` на этой странице (я запускал её). Если вы написали
`{"id":1,"price":1200000}`, вы решили, что одно из двух полей «победит»; `encoding/json` отбрасывает оба.

</details>

5. В строке `go vet ./... && staticcheck ./... && govulncheck ./... && go test ./...` `staticcheck` нашёл проблему. Запустится ли `govulncheck`?

<details>
<summary>Ответ</summary>

Нет. `staticcheck` завершится с ненулевым кодом, `&&` остановит цепочку: `govulncheck` и `go test` не запустятся.

</details>
