## What you will learn

In GB-6.04, bozor ("market", the course project) looks up a session record on every protected request. A common alternative is the JWT: a token that is verified without touching the database. Which one is right? Today we try both on the same requests.

**One idea:** a JWT is three parts joined by dots, `header.payload.signature`. The signature is a keyed HMAC-SHA256 of the first two parts. The server recomputes it to verify, so it stores nothing. For the same reason logout has nothing to delete: a stolen JWT works until `exp`, while a session dies as soon as its record is deleted. Revoking a JWT (a denylist or a refresh token) brings server state back.

By the end of the lesson you will:

- build a JWT without a library and read its payload without the key;
- verify a token with `golang-jwt/jwt/v5` under four rules and see what a rule-less `Parse` lets through;
- see on your own screen that after logout the old cookie gives `401` while the same JWT gives `200`;
- name the price of revocation, justify the choice for bozor, and write a `jti` denylist until `go test` passes.

| Word | Plain meaning | English term |
|---|---|---|
| JWT | three parts joined by dots: header, payload, signature | JSON Web Token |
| signature | the HMAC of the first two parts, computed with a key | signature |
| token revocation | a mark kept on the server so a token is rejected before it expires | token revocation |

Two helpers: **base64url** turns bytes into text made of letters, digits, `-` and `_`; **HMAC** is a hash computed with a key, so it cannot be computed without the key. Both appear in the code below. A **claim** is a field in the payload: it says who and what the token is about.

## What is inside a JWT

A **JWT** (JSON Web Token, [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)) is three parts joined by dots. Each part is base64url text.

```text
header . payload . signature
```

| Part | Inside | Purpose |
|---|---|---|
| header | `{"alg":"HS256","typ":"JWT"}` | `alg` is the signing algorithm (`HS256` is HMAC with SHA-256), `typ` is the token type |
| payload | claims | who and what the token is about |
| signature | an HMAC result | binds the first two parts to a key |

The payload in this lesson has four claims:

| Claim | English | Meaning | In bozor |
|---|---|---|---|
| `sub` | subject | who the token is about | user ID: `1` |
| `iss` | issuer | who issued it | `bozor` |
| `aud` | audience | who it is for | `bozor-api` |
| `exp` | expiration time | from this moment the token is not accepted | now + 15 minutes |

`exp` is written in Unix time: the number of seconds since 1970-01-01 00:00:00 UTC ([RFC 7519 §2, NumericDate](https://www.rfc-editor.org/rfc/rfc7519#section-2)). The library adds two more claims: `iat` (issued at, the time of issue) and `jti` (JWT ID, a unique ID of the token).

RFC 7519 describes a JWT in two forms: signed (JWS, three parts) and encrypted (JWE, [five parts](https://www.rfc-editor.org/rfc/rfc7516#section-3.1)). This lesson covers only the signed JWT; bozor issues that one.

## Building a JWT by hand

First we build one without a library, so every byte is visible. `cmd/qolda/main.go` builds a token and prints its three parts on separate lines.

```go filename="cmd/qolda/main.go" showLineNumbers
// qolda — HS256 imzoli JWT'ni kutubxonasiz yasaydi va uch qismini alohida qatorda chiqaradi (GB-6.05).
// Token: header.payload.imzo — uchala qism nuqta bilan ulanadi. Kalit har ishga tushishda yangi.
//
//	go run ./cmd/qolda
package main

import (
	"fmt"
	"strings"
	"time"

	"github.com/abdurahmon27/bozor/internal/token"
)

func main() {
	key := token.NewKey()
	exp := time.Now().Add(15 * time.Minute).Unix() // Unix vaqt: 1970-01-01 UTC'dan beri soniyalar (RFC 7519 §2: NumericDate)
	header := `{"alg":"HS256","typ":"JWT"}`
	payload := fmt.Sprintf(`{"sub":"1","iss":"bozor","aud":"bozor-api","exp":%d}`, exp)
	t := token.SignHS256(header, payload, key)

	parts := strings.Split(t, ".")
	fmt.Println("header: ", parts[0])
	fmt.Println("payload:", parts[1])
	fmt.Println("imzo:   ", parts[2])
}
```

| Line | Code | What it does |
|---|---|---|
| 1–4 | `//` comments | say what the program does and how to run it; the compiler does not read them |
| 5–13 | `package main`, `import` | this is a runnable program; the packages it needs: `fmt`, `strings`, `time` and our `internal/token` |
| 16 | `key := token.NewKey()` | `NewKey` from `internal/token` returns 32 random bytes. Anyone who knows the key can issue tokens, so the key is a secret. For HS256 the key must be at least 32 bytes ([RFC 7518 §3.2](https://www.rfc-editor.org/rfc/rfc7518#section-3.2)) |
| 17 | `exp := time.Now().Add(15 * time.Minute).Unix()` | `Now()` is the current moment, `Add` adds 15 minutes, `Unix()` converts the moment to Unix-time seconds |
| 18 | ``header := `\{"alg":"HS256","typ":"JWT"\}` `` | text in backticks is ready-made JSON (GB-3.02); the quotes inside need no `\` escape |
| 19 | `payload := fmt.Sprintf(…, exp)` | `Sprintf` puts the number `exp` in place of `%d` and builds the text (GB-1.04) |
| 20 | `t := token.SignHS256(header, payload, key)` | builds the token from those three values |
| 22 | `parts := strings.Split(t, ".")` | splits the token at the dots into three texts: `parts[0]`, `parts[1]`, `parts[2]` |
| 23–25 | `fmt.Println(…)` | prints each part on its own line |

Now inside `SignHS256`. It lives in `internal/token/qolda.go`. First the helper `b64`: it turns bytes into base64url text.

```go filename="internal/token/qolda.go" showLineNumbers
// Package token — bozor'ning JWT'lari (GB-6.05).
//
// qolda.go: HS256 imzoli JWT'ni kutubxonasiz, qoʻlda yasash — har bayti koʻrinsin deb (RFC 7519, RFC 7515).
// token.go: ishdagi yoʻl — golang-jwt/jwt/v5 bilan yasash va qatʼiy tekshirish (RFC 8725).
package token

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/base64"
)

// b64 — base64url, "="siz (RFC 7515 §2: Base64url Encoding, padding yoʻq).
// Alifbo: A–Z a–z 0–9 - _ ; oddiy base64'dagi + va / oʻrniga - va _, shuning uchun URL va sarlavhada xavfsiz.
func b64(b []byte) string {
	return base64.RawURLEncoding.EncodeToString(b)
}

// SignHS256 — JWT'ni qoʻlda yasaydi: base64url(header) . base64url(payload) . base64url(imzo).
// Imzo — nuqtagacha boʻlgan matnning HMAC-SHA256'i, kalit bilan (RFC 7518 §3.2).
// header va payload — tayyor JSON matnlar; ular shifrlanmaydi, faqat imzolanadi.
func SignHS256(header, payload string, key []byte) string {
	input := b64([]byte(header)) + "." + b64([]byte(payload))
	mac := hmac.New(sha256.New, key)
	mac.Write([]byte(input))
	return input + "." + b64(mac.Sum(nil))
}
```

| Line | Code | What it does |
|---|---|---|
| 5 | `package token` | the `internal/token` folder is a package with this name (GB-2.06) |
| 7–11 | `import` | `crypto/hmac` and `crypto/sha256` are for the signature; `encoding/base64` is for the text |
| 15–17 | `func b64(b []byte) string` | takes bytes, returns text. `RawURLEncoding` is the URL alphabet (`A–Z a–z 0–9 - _`) with no `=` at the end; so the token survives both a URL and a header. `EncodeToString` returns the result as a `string` |
| 22 | `func SignHS256(header, payload string, key []byte) string` | takes two texts and the key bytes, returns the token text |
| 23 | `input := b64([]byte(header)) + "." + b64([]byte(payload))` | `[]byte(…)` turns text into bytes (GB-2.07); `b64` encodes; `+` joins with a dot. This is the text that gets signed |
| 24 | `mac := hmac.New(sha256.New, key)` | a keyed hash calculator. `sha256.New` has no parentheses: the function itself is passed, and `hmac` calls it when needed |
| 25 | `mac.Write([]byte(input))` | feeds the text to be signed into the calculator |
| 26 | `return input + "." + b64(mac.Sum(nil))` | `Sum(nil)` returns the result, 32 bytes, in a new slice. `b64` turns it into text: this is the third part |

This is how the token is computed:

| Step | What | Value |
|---|---|---|
| 1 | `b64(header)` | `eyJhbGci…` |
| 2 | `b64(payload)` | the base64url form of the payload JSON text |
| 3 | `input` | 1 + `.` + 2 |
| 4 | `HMAC-SHA256(key, input)` | 32 bytes |
| 5 | `b64(32 bytes)` | 43 characters: this is the signature |
| 6 | token | `input` + `.` + signature |

Run it:

```console
$ go run ./cmd/qolda
header:  eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
payload: eyJzdWIiOiIxIiwiaXNzIjoiYm96b3IiLCJhdWQiOiJib3pvci1hcGkiLCJleHAiOjE3OTU4NTg0OTh9
imzo:    C1q-jEJddLMip5WA-QKKdF8byGpmxhY4SR4JpBQ51TY
```

Three lines: on screen `header`, `payload` and `imzo` (the signature) are separate, while in the token they are joined with dots. The signature is 43 characters: the base64url form of 32 bytes. Your `payload` and signature will differ: `exp` and the key are different.

A JWT usually starts with `eyJ`. The reason: the header JSON text starts with `{"alg"…`. Its base64url form is `eyJhbGci…`. `eyJ` is `{"` plus the start of the next letter. If a space follows the `{`, the beginning is different. You can see this with `basenc`, a GNU coreutils command; with `--base64url` it encodes. `printf` prints the text without a trailing newline:

```console
$ printf '{"alg"' | basenc --base64url
eyJhbGci
$ printf '{ "alg"' | basenc --base64url
eyAiYWxnIg==
```

`basenc` added `=` padding at the end (`==`). A JWT drops it: that is exactly what `RawURLEncoding` does. `basenc` does not print a newline, so in your terminal the next prompt may start on the same line.

## The payload is not encrypted

Can someone who does not know the key read the payload line? **A)** no: it is encrypted · **B)** yes: it is only base64url · **C)** only if there is a signature too.

<details>
<summary>Answer</summary>

**B.** base64url encoding is not encryption: it reverses without a key. If you chose **A**, you mixed up encoding with encryption. In **C**, the signature does not hide the payload; it only helps check that it has not changed.

</details>

`echo` prints the line, `|` passes it to the next command, and `basenc --base64url -d` decodes with `-d`:

```console
$ echo eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 | basenc --base64url -d
{"alg":"HS256","typ":"JWT"}
$ echo eyJzdWIiOiIxIiwiaXNzIjoiYm96b3IiLCJhdWQiOiJib3pvci1hcGkiLCJleHAiOjE3OTU4NTg0OTh9 | basenc --base64url -d
{"sub":"1","iss":"bozor","aud":"bozor-api","exp":1795858498}
```

No key was needed: the claims are plain text. So you never put secrets in a JWT: no passwords, no personal data. The signature guarantees only this: someone who knows the key wrote the text, and it has not changed. OWASP: an HS256 signature proves only that the token was produced by some holder of the shared secret ([OWASP JWT Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)).

## The server recomputes the signature

To verify, the server repeats the computation from `SignHS256`:

```text
token  =  header . payload . signature
          \_______  _______/    |
                  \/            |
     HMAC-SHA256(server key)     |
                  |              |
        computed signature  ==  signature in the token ?
                  |
     yes → trust the payload, no database visit
     no  → the token is rejected
```

Change one letter and the HMAC comes out completely different. The server looks nothing up: the token itself and the key on the server are enough. The library compares with `hmac.Equal`, in constant time ([golang-jwt/jwt v5.3.1 source](https://github.com/golang-jwt/jwt/blob/v5.3.1/hmac.go)).

## The library and the four rules

At work you do not write verification by hand. [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725), JWT best current practices, lists the usual mistakes: trusting the `alg` in the header, and not checking `iss` and `aud`. We take [golang-jwt/jwt](https://github.com/golang-jwt/jwt/releases), version 5: it is actively maintained. `go get` works as in GB-2.06, with the version written exactly:

```console
$ go get github.com/golang-jwt/jwt/v5@v5.3.1
go: added github.com/golang-jwt/jwt/v5 v5.3.1
```

This output was taken in a new, empty module. In the lesson folder the line is already there, so a repeated `go get` prints nothing. The line in `go.mod`:

```console
$ grep jwt go.mod
	github.com/golang-jwt/jwt/v5 v5.3.1
```

Verification is in the `Parse` function in `internal/token/token.go`:

```go
func Parse(s string, key []byte) (Claims, error) {
	rc := &jwt.RegisteredClaims{}
	_, err := jwt.ParseWithClaims(s, rc, func(*jwt.Token) (any, error) {
		return key, nil
	},
		jwt.WithValidMethods([]string{"HS256"}),
		jwt.WithIssuer(Issuer),
		jwt.WithAudience(Audience),
		jwt.WithExpirationRequired(),
	)
	if err != nil {
		return Claims{}, err
	}
	id, err := strconv.ParseInt(rc.Subject, 10, 64)
	if err != nil {
		return Claims{}, fmt.Errorf("token: sub son emas: %w", err)
	}
	c := Claims{UserID: id, JTI: rc.ID}
	if rc.ExpiresAt != nil { // WithExpirationRequired bilan doim bor; nil'ga baribir tayanmaymiz
		c.Expires = rc.ExpiresAt.Time
	}
	return c, nil
}
```

| Line | What it does |
|---|---|
| 1 | `Parse` takes the token text `s` and the key; it returns `Claims` and an `error` |
| 2 | `jwt.RegisteredClaims` is a struct from the library: it has fields for the standard claims (`sub`, `iss`, `aud`, `exp`…). `&…{}` gives its address (GB-2.04) |
| 3–5 | `jwt.ParseWithClaims` splits the token, reads the payload into `rc` and verifies the signature. The third argument is an anonymous function: the library asks it for the key, and we hand over that same `key` (GB-2.09). Its parameter `*jwt.Token` is not needed, so it has no name. `any` is any type (GB-2.07) |
| 6–9 | the four rules: each is an option whose name starts with `With`. A table follows |
| 11–13 | if verification returned an error, an empty `Claims{}` and the error are returned |
| 14–17 | `strconv.ParseInt(rc.Subject, 10, 64)` turns the `sub` text into an `int64` number; if it is not a number, it is an error (wrapped with `%w`, GB-2.08) |
| 18–22 | our `Claims`: `UserID` (`sub`), `JTI`, `Expires` (`exp`, if present) and `return c, nil` |

`Claims` is our struct, at the top of `token.go`:

```go
type Claims struct {
	UserID  int64     // sub
	JTI     string    // jti: shu tokenning noyob ID'si (RFC 7519 §4.1.7) — denylist kaliti
	Expires time.Time // exp
}
```

The four rules:

| Option | What it rejects | Why |
|---|---|---|
| `WithValidMethods([]string{"HS256"})` | another `alg` in the header: `none`, `HS512`… | the server chooses the algorithm, not the token ([RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725#section-3.1)) |
| `WithIssuer(Issuer)` | `iss` is not `bozor` | checks who issued the token ([§3.8](https://www.rfc-editor.org/rfc/rfc8725#section-3.8)); `Issuer` is a package constant |
| `WithAudience(Audience)` | `bozor-api` is not in `aud` | a token issued for another service must not fit this API ([§3.9](https://www.rfc-editor.org/rfc/rfc8725#section-3.9)) |
| `WithExpirationRequired()` | no `exp` | a token without `exp` never dies; in the library `exp` is optional by default |

If `exp` is present, the library always checks it: by [RFC 7519 §4.1.4](https://www.rfc-editor.org/rfc/rfc7519#section-4.1.4) the token is not accepted after that moment. **Requiring** `exp` is our own rule.

`cmd/tekshir` runs the hand-built token through `Parse`, then tries seven cases. The list of cases:

```go
	cases := []struct{ name, tok string }{
		{"qoʻlda yasalgan", good},
		// payload'da sub 1 → 2, imzo eski: header va imzo oʻsha, faqat oʻrtadagi qism yangi.
		{"sub 1 → 2, imzo eski", parts[0] + "." + b64([]byte(claims("2", "bozor-api", exp))) + "." + parts[2]},
		// alg "none": imzo boʻsh (RFC 7519 §6: unsecured JWT).
		{"alg none, imzo yoʻq", b64([]byte(`{"alg":"none","typ":"JWT"}`)) + "." + parts[1] + "."},
		{"exp yoʻq", token.SignHS256(hs256, claims("1", "bozor-api", 0), key)},
		{"aud boshqa xizmat", token.SignHS256(hs256, claims("1", "hisobot-api", exp), key)},
		{"muddati oʻtgan", token.SignHS256(hs256, claims("1", "bozor-api", time.Now().Add(-time.Minute).Unix()), key)},
		// alg HS512, imzo shu kalit bilan TOʻGʻRI hisoblangan: algoritmni token emas, server tanlaydi.
		{"alg HS512, imzo toʻgʻri", signHS512(claims("1", "bozor-api", exp), key)},
	}
```

Each case is a name and a token text. The first is the whole token. The second is a copy: `parts[0]` and `parts[2]` (header and signature) are old, the middle payload is new: `sub` is two instead of one. The `alg none` token has an empty signature ([RFC 7519 §6](https://www.rfc-editor.org/rfc/rfc7519#section-6): an unsecured JWT). The last one is signed with `HS512`, and the signature was computed correctly with the same key.

Two questions, then we run it.

**Prediction 1:** in the copy `sub` is 2 instead of 1, with the old header and signature. `Parse`? **A)** `ok, sub=2` · **B)** rejected: the signature is wrong · **C)** rejected: the payload cannot be opened.

<details>
<summary>Answer</summary>

**B.** The server computes the HMAC of the changed payload, and the result does not match the old signature. If you chose **A**, you thought the signature is not checked. In **C**, opening the payload does not depend on the key: it was plain text.

</details>

**Prediction 2:** `alg` is `HS512`, and the signature is correct for the same key. `Parse`? **A)** ok: the signature is correct · **B)** rejected: this algorithm is not allowed · **C)** rejected: the key is short.

<details>
<summary>Answer</summary>

**B.** `WithValidMethods` allows only `HS256`. Even with a correct signature, the server chooses the algorithm, not the token. **C** is wrong: the key is 32 bytes, which is accepted for `HS512` too.

</details>

```console
$ go run ./cmd/tekshir
qoʻlda yasalgan:         ok, sub=1
sub 1 → 2, imzo eski:    token signature is invalid: signature is invalid
alg none, imzo yoʻq:     token signature is invalid: signing method none is invalid
exp yoʻq:                token has invalid claims: token is missing required claim: exp claim is required
aud boshqa xizmat:       token has invalid claims: token has invalid audience
muddati oʻtgan:          token has invalid claims: token is expired
alg HS512, imzo toʻgʻri: token signature is invalid: signing method HS512 is invalid
```

Read the result. The library error has two layers: first the kind of error, and after the colon the reason (wrapping with `%w`, GB-2.08).

| Case | Result | Who rejected it |
|---|---|---|
| built by hand | `ok, sub=1` | same format, correct signature |
| `sub` 1 → 2, old signature | `signature is invalid` | the HMAC did not match |
| `alg none` | `signing method none is invalid` | `WithValidMethods` |
| no `exp` | `missing required claim: exp claim is required` | `WithExpirationRequired` |
| `aud` of another service | `token has invalid audience` | `WithAudience` |
| expired | `token is expired` | the `exp` check |
| `alg HS512`, correct signature | `signing method HS512 is invalid` | `WithValidMethods` |

`iss` does not appear in this table. `TestParseRadEtadi` in `internal/token/token_test.go` checks it: it tries another `iss`, another key, `HS384`, a non-numeric `sub` and other cases.

## The classic mistake: Parse without rules

The most common mistake: calling `Parse` without the four options. For an experiment, we temporarily remove the four option lines. I tried it with the ready copy in the lesson folder: `_video/stages/token-qoidasiz.go`, the rule-less variant of `internal/token/token.go`. In your own copy, comment out the option lines, try it, and then put them back:

**Prediction:** which tokens get through a rule-less `Parse`? **A)** none: a signature is required · **B)** no `exp`, another `aud`, `HS512` · **C)** only `alg none`.

<details>
<summary>Answer</summary>

**B.** The signature is still checked, so **A** is partly right: a token with a broken signature does not pass. But in the library's default settings `exp` is optional, `aud` is not checked and the algorithm comes from the header. **C** is wrong: the library rejects `none` itself.

</details>


- The library rejected `alg none` itself: `token is unverifiable: 'none' signature type is not allowed`. v5 accepts `none` only with the key `jwt.UnsafeAllowNoneSignatureType`.
- The expired token was rejected too: if `exp` is present, it is always checked.
- **The token without `exp` passed:** it never dies.
- **The token issued for another service passed:** `aud` was not checked.
- **`HS512` passed:** the token chooses the algorithm.

The fix: put the four options back. With a single HMAC key, `HS512` passing is not yet an attack. But with public-key algorithms it turns into "alg confusion" (below, in the "Going deeper" section).

## The server: authenticate with two paths

`requireUser` from GB-6.04 now calls `authenticate`. It has two paths: if the `Authorization: Bearer <token>` header is present, it is a JWT; otherwise a cookie.

```go
func (a *api) authenticate(r *http.Request) (store.User, error) {
	if s, ok := bearer(r); ok {
		c, err := token.Parse(s, a.jwtKey)
		if err != nil {
			return store.User{}, fmt.Errorf("%w: %w", errBadToken, err)
		}
		// VAZIFA (TASK.md, 3-qadam): c.JTI denylist'da boʻlsa (a.st.TokenRevoked) — errBadToken.
		return store.User{ID: c.UserID}, nil
	}
	// aks holda: session cookie'si (GB-6.04)
	cookie, err := r.Cookie(sessionCookie)
	if err != nil {
		return store.User{}, err // http.ErrNoCookie → 401
	}
	return a.st.UserBySession(r.Context(), hashToken(cookie.Value))
}
```

| Line | What it does |
|---|---|
| 1 | `authenticate` takes the request and returns a `store.User` or an error |
| 2 | `bearer(r)` extracts the token after the word `Bearer` from the `Authorization` header. If a token is present, `ok` is `true` (the comma-ok form from GB-2.02) |
| 3–6 | `token.Parse` verifies the token with the server key `a.jwtKey`. On error we wrap it in `errBadToken` (`%w` twice, GB-6.02); `problemFor` turns that into `401` |
| 7 | a comment: in the task, the denylist check is added here |
| 8 | the user ID comes from the token's `sub`. **There is no store access** |
| 10–15 | if there is no Bearer, the GB-6.04 path: `r.Cookie` gets the cookie (if missing, an error, `401`), `hashToken` hashes it, `UserBySession` looks it up in the store |

A **Bearer** token is one that any party in possession of it can use ([RFC 6750 §1.2](https://www.rfc-editor.org/rfc/rfc6750#section-1.2)). The header looks like `Authorization: Bearer <token>`. The `bearer` function parses that header:

```go
func bearer(r *http.Request) (string, bool) {
	scheme, rest, ok := strings.Cut(r.Header.Get("Authorization"), " ")
	if !ok || !strings.EqualFold(scheme, "Bearer") {
		return "", false
	}
	t := strings.TrimLeft(rest, " ")
	return t, t != ""
}
```

`strings.Cut` splits the text at the first space into two parts: the scheme name and the rest. `EqualFold` compares the scheme name ignoring case ([RFC 9110 §11.1](https://www.rfc-editor.org/rfc/rfc9110#section-11.1)). `TrimLeft` removes extra spaces before the token.

## Why the JWT keeps working after logout

| | session | JWT |
|---|---|---|
| what the server holds | token hash → user, expiry | only the key |
| what logout does | deletes the row | nothing to delete |
| next request | lookup: no row → `401` | signature valid, `exp` not passed → `200` |
| a stolen copy | dies at once | works until `exp`: 15 minutes for us |

The proof is in the token itself: with a valid signature and an `exp` that has not passed, it is valid. For the server to "forget" it, something about it would have had to be stored. With a stolen token, an attacker uses it until `exp`.

## The price of revocation

There are two usual fixes. Each one brings state back to the server.

1. **A denylist** is a list of revoked `jti` values. It must be checked on every request, which is again a lookup. OWASP writes: with a denylist, user sessions are no longer fully **stateless** (the server keeps no state), so you may consider a plain session system ([OWASP JWT Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html)).
2. **A short `exp` + a refresh token.** The access token lives a few minutes, and a new one is obtained with a **refresh token**. The refresh token is stored on the server and revoked there, which is again a session.
3. **Changing the key** is a way without a database, but it kills everyone's tokens.

**Size.** A JWT travels with every request and grows with every claim. `printf %s` prints the token without a trailing newline, `wc -c` counts bytes. We take the cookie value from the `jar.txt` format: a cookie file has tab-separated columns, and the seventh is the value (`cut -f7`); `tr -d` removes the newline:

```console
$ printf %s "$T" | wc -c
233
$ grep session eski.txt | cut -f7 | tr -d '\n' | wc -c
43
```

The JWT is 233 characters, the session token is 43. This is a lab value: every added claim makes the token bigger.

## The choice for bozor

- **bozor: session.** One API and one Postgres: requests go to the database anyway, and the session lookup is a single `SELECT` by primary key (GB-6.04). It is usually cheap; it was not measured in this lesson. Logout and blocking must take effect at once.
- **A JWT fits between services:** one service gives another a short-lived token, and the service that accepts the token does not connect to the database.

This is a choice for bozor's conditions, not a general rule. If the conditions change, the choice changes: what matters is knowing the price of both paths. At work tomorrow: when you see a JWT, check the four rules and what logout does.

**Alg confusion** (not re-run here; a paraphrase of [RFC 8725 §2.1](https://www.rfc-editor.org/rfc/rfc8725#section-2.1)). The defence is for the server to set the allowed algorithms, that is, `WithValidMethods`. In our system with a single HMAC key this attack does not exist; so it is mentioned here only as a rule.

## Common mistakes

**1. `Parse` without rules.** There is no error message: the token simply passes. A token without `exp` lives forever, a token for another service is accepted, and the token still chooses the algorithm. The full analysis is in the "The classic mistake: Parse without rules" section above. The fix: the four options.

**2. Secrets in a JWT.** We read the payload without a key using `basenc` (the "The payload is not encrypted" section above). Do not put a password or personal data in a claim. If you need the email, read it from the database by `sub`; that is why `/me` on the JWT path returned only `id`.

**3. Believing that "logout kills the JWT too".** Logout deletes the session row; for a JWT there is nothing to delete (the "The same requests" section: old cookie `401`, JWT `200`). The fix: a denylist (the task) or accepting a short `exp`.

```go
	s.mu.Lock()
```

```go
	n := 0
```

```text
2026/11/28 14:24:46 LJSWE4HDPBQKF7MGYGZKTMR52C POST "/logout" 204 130.945µs
2026/11/28 14:24:46 3KI6N4F622SNZQNQVFNBUVW7TB xato 401: "JWT yaroqsiz: jti O2BZPFBFFHJDBB4PCKXKAVGYFC bekor qilingan"
2026/11/28 14:24:46 3KI6N4F622SNZQNQVFNBUVW7TB GET "/me" 401 366.966µs
```

Here is the price: every JWT request does one lookup in the store, just like a session. What is left of the JWT compared with a session? Signature verification and a "who is this" answer without the database; killing a stolen token at once still depends on server state.
