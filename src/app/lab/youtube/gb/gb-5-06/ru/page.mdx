## Что вы узнаете

`orders.sql` уже создал таблицы. Что произойдёт, если выполнить его при следующем обновлении сервера? Как обновить схему, сохранив данные?

**Одна идея:** каждое изменение схемы хранится в SQL-файле с номером. База хранит применённые версии в `goose_db_version`; goose применяет недостающие файлы.
Обычно каждый файл выполняется в одной транзакции: при ошибке изменения этого файла откатываются.

После урока вы:

- установите goose и выполните `status`, `up`, `down`;
- прочитаете состояние базы из таблицы версий;
- исправите ошибку добавления столбца в заполненную таблицу с помощью `DEFAULT`;
- напишете четвёртую миграцию и проверите её тестами.

| Слово | Простой смысл | Английский термин |
|---|---|---|
| файл миграции | SQL-файл с номером, изменяющий схему | migration file |
| goose | инструмент, сравнивающий файлы с применёнными версиями в базе | goose |
| неудачная миграция | невыполненное изменение, откатившееся в обычной транзакции | failed migration |

**ALTER TABLE** меняет структуру существующей таблицы. **`\dt`** выводит список таблиц в psql.
Здесь схема означает структуру таблиц; `public` — именованная схема, в которой находятся таблицы.

## Файлы миграций и goose

Каждое изменение — отдельный **файл миграции**. Номер задаёт порядок; goose сравнивает файлы с версиями в базе.

| До | Действие | После |
|---|---|---|
| файлы 1, 2; в базе начальная 0 | `goose up` | 1, 2 применены; версия 2 |
| файлы 1, 2; в базе 1, 2 | `goose up` | без изменений |
| файлы 1, 2, 3; в базе 1, 2 | `goose up` | выполняется только 3 |

Установите точную версию goose. В пути модуля `v3` — старшая версия, `cmd/goose` — пакет команды, `@v3.30.2` — устанавливаемая версия.
`go install` записывает исполняемый файл в `GOBIN`, а если он не задан — обычно в `~/go/bin`. Эта папка должна быть в `PATH`.

```console
$ go install github.com/pressly/goose/v3/cmd/goose@v3.30.2
```

```console
$ goose -version
goose version: v3.30.2
```

При этом повторном запуске установка ничего не вывела; первый запуск может печатать сообщения о загрузке. `-version` показывает установленную версию.
Goose нужны три значения: `GOOSE_DRIVER` — тип базы; `GOOSE_DBSTRING` — адрес подключения; `GOOSE_MIGRATION_DIR` — папка файлов.
Один `export` может задать несколько значений.

```bash
export GOOSE_DRIVER=postgres GOOSE_MIGRATION_DIR=migrations
export GOOSE_DBSTRING=postgres://bozor:bozor-lab@localhost:5486/bozor
export DATABASE_URL=postgres://bozor:bozor-lab@localhost:5486/bozor
```

`DATABASE_URL` читают последующие Go-тесты; goose использует свой `GOOSE_DBSTRING`.
Части URL: `bozor` — пользователь, `bozor-lab` — пароль лаборатории, `localhost:5486` — адрес и порт, последний `bozor` — имя базы.
`ls migrations` перечисляет файлы:

```console
$ ls migrations
00001_products.sql
00002_orders.sql
```

```sql filename="migrations/00001_products.sql" showLineNumbers
-- +goose Up
CREATE TABLE products (
    id     bigint
           GENERATED ALWAYS AS IDENTITY
           PRIMARY KEY,
    name   text    NOT NULL UNIQUE CHECK (name <> ''),
    price  bigint  NOT NULL CHECK (price > 0),
    stock  integer NOT NULL DEFAULT 0 CHECK (stock >= 0),
    active boolean NOT NULL DEFAULT true
);

-- +goose Down
DROP TABLE products;
```

| Строка | Что делает |
|---|---|
| 1 | В SQL `--` — комментарий; для goose `-- +goose Up` начинает раздел применения |
| 2 | `CREATE TABLE products (` открывает определение таблицы и столбцов |
| 3–5 | `id` — большое целое число; база выдаёт номер; первичный ключ делает его уникальным |
| 6 | `name` — текст; NULL, повторы и пустой текст запрещены |
| 7 | `price` — большое целое число в тийинах; NULL и неположительные значения запрещены |
| 8 | `stock` — целое число, по умолчанию 0; отрицательное значение и NULL запрещены |
| 9 | `active` — логическое значение, по умолчанию true; NULL запрещён |
| 10 | `);` завершает определение таблицы и SQL-команду |
| 12–13 | `Down` начинает раздел отката; `DROP TABLE` удаляет таблицу |

`<>` означает «не равно»; `''` — пустой текст. Второй файл создаёт связанные таблицы:

```sql filename="migrations/00002_orders.sql" showLineNumbers
-- +goose Up
CREATE TABLE orders (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer text   NOT NULL,
    note     text
);
CREATE TABLE order_items (
    id         bigint  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id   bigint  NOT NULL REFERENCES orders (id),
    product_id bigint  NOT NULL REFERENCES products (id),
    quantity   integer NOT NULL CHECK (quantity > 0),
    unit_price bigint  NOT NULL CHECK (unit_price > 0)
);

-- +goose Down
DROP TABLE order_items;
DROP TABLE orders;
```

Строки 2–6: `orders` хранит заказы; `customer` — имя клиента, `note` — необязательная заметка.
Строки 7–13: `order_items` хранит позиции; `order_id` и `product_id` — внешние ключи, задающие ссылки на заказы и товары.
Количество `quantity` и цена единицы `unit_price` должны быть положительными.
Строки 15–17: сначала удаляется ссылающаяся таблица `order_items`, затем `orders`. Первая миграция откатывается после второй.

## Состояние, Up и таблица версий

`goose status` показывает состояние каждого файла. `Applied At` — время применения; `Migration` — файл.
`Pending` означает «ещё не применён». Все блоки console ниже выполнены заново; префиксы даты сохранены точно.

```console
$ goose status
2026/11/27 20:34:28     Applied At                  Migration
2026/11/27 20:34:28     =======================================
2026/11/27 20:34:28     Pending                  -- 00001_products.sql
2026/11/27 20:34:28     Pending                  -- 00002_orders.sql
```

`goose up` выполняет неприменённые файлы по номерам. Какие выполнятся в этой пустой базе?
**A)** только 2 · **B)** сначала 1, затем 2 · **C)** ни один.

<details>
<summary>Ответ</summary>

**B.** Оба имеют статус `Pending`. Последний номер обозначает новейшую версию, а не указание выполнить только этот файл.

</details>

```console
$ goose up
2026/11/27 20:34:28 OK   00001_products.sql (8.94ms)
2026/11/27 20:34:28 OK   00002_orders.sql (9.83ms)
2026/11/27 20:34:28 goose: successfully migrated database to version: 2
```

`OK` означает, что файл применён; в скобках длительность, `ms` — миллисекунды. Последняя строка сообщает текущую версию базы: `2`.
`psql -c` выполняет одну команду. `\dt` перечисляет таблицы:

```console
$ docker compose exec db psql -c '\dt'
              List of tables
 Schema |       Name       | Type  | Owner 
--------+------------------+-------+-------
 public | goose_db_version | table | bozor
 public | order_items      | table | bozor
 public | orders           | table | bozor
 public | products         | table | bozor
(4 rows)
```

`Schema` — именованная группа (`public`); `Name` — имя таблицы; `Type` — `table` («таблица»); `Owner` — владелец.
Есть три таблицы проекта и таблица goose `goose_db_version`. `(4 rows)` — четыре строки результата.
Прочитайте версии, упорядочив записи по `id`:

```console
$ docker compose exec db psql -c 'SELECT id, version_id, is_applied FROM goose_db_version ORDER BY id'
 id | version_id | is_applied 
----+------------+------------
  1 |          0 | t
  2 |          1 | t
  3 |          2 | t
(3 rows)
```

`id` — ключ записи; `version_id` — номер миграции; `t` в `is_applied` означает true, «применена».
`0` — начальная запись goose, а не файл миграции. Поэтому двум файлам соответствуют три записи.

Повторите тот же `goose up`. **A)** ошибка существующей таблицы · **B)** без изменений · **C)** таблицы пересоздадутся.

<details>
<summary>Ответ</summary>

**B.** Goose видит, что обе версии применены. Ответ A относится к повторному SQL-файлу вручную; C означал бы потерю данных.

</details>

```console
$ goose up
2026/11/27 20:34:28 goose: no migrations to run. current version: 2
```

`no migrations to run` означает, что новых файлов нет. При таком управлении схемой `up` можно повторять при каждом deploy.
Это не гарантирует исправление схемы, изменённой вручную, или координацию нескольких одновременных deploy.

## Ошибка NOT NULL в заполненной таблице

`seed.sql` добавляет четыре товара, три заказа и четыре позиции заказов:

```console
$ docker compose exec db psql -f /lab/seed.sql
INSERT 0 4
INSERT 0 3
INSERT 0 4
```

`N` в каждом `INSERT 0 N` — число записанных строк.
Заказу нужен статус. `goose create` создаёт шаблон; `-s` выбирает последовательный номер, `orders_status` — имя, `sql` — тип файла.
Без `-s` имя начинается с метки времени; выберите один способ для проекта.

```console
$ goose create -s orders_status sql
2026/11/27 20:34:28 Created new file: migrations/00003_orders_status.sql
```

```console
$ ls migrations
00001_products.sql
00002_orders.sql
00003_orders_status.sql
```

`Created new file` означает, что новый файл создан. Замените примерные `SELECT` в шаблоне. Сначала намеренно ошибочный вариант:

```sql
-- +goose Up
ALTER TABLE orders ADD COLUMN status text NOT NULL;

-- +goose Down
ALTER TABLE orders DROP COLUMN status;
```

Строка 1 — Up. Строка 2: `ALTER TABLE orders` меняет существующую таблицу; `ADD COLUMN` добавляет текстовый столбец `status`.
`NOT NULL` запрещает NULL. Строки 4–5 — Down; `DROP COLUMN` удаляет столбец.
Если не задать `DEFAULT`, существующие строки получают NULL в новом столбце. NULL отличается от пустого текста.

Уже есть три заказа. Что произойдёт? **A)** статус станет `''` · **B)** база откажет · **C)** NULL будет принят.

<details>
<summary>Ответ</summary>

**B.** Три существующие строки получили бы NULL, что запрещено `NOT NULL`. Для A пустой текст нигде не задан; C противоречит ограничению.

</details>

```console
$ goose up
2026/11/27 20:34:28 goose run: ERROR 00003_orders_status.sql: failed to run SQL migration: failed to execute SQL query "ALTER TABLE orders ADD COLUMN status text NOT NULL;": ERROR: column "status" of relation "orders" contains null values (SQLSTATE 23502)
```

Код выхода goose — `1`. `ERROR 00003_orders_status.sql` называет файл; далее показан невыполненный SQL.
`column "status" of relation "orders" contains null values` означает, что столбец status таблицы orders содержит NULL.
`SQLSTATE 23502` — код Postgres `not_null_violation`, нарушение NOT NULL.

**Транзакция** сохраняет либо все свои команды, либо ни одной. Подробнее в [GB-5.07](/lab/youtube/gb/gb-5-07/ru).
Обычно goose выполняет каждый файл в одной транзакции. Это не одна транзакция на все файлы одного `up`.

| Этап | Файлы 1–2 | Файл 3 | orders.status |
|---|---|---|---|
| до ошибки | сохранены | не начат | отсутствует |
| ошибка | сохранены | откатывается | отсутствует |
| следующая попытка | не выполняются снова | выполняется снова | зависит от успеха |

Промежуточный вопрос: что с `orders` после ошибки? **A)** status есть с NULL · **B)** status отсутствует · **C)** таблица изменена частично.

<details>
<summary>Ответ</summary>

**B.** Изменение этого файла не сохранено. Здесь `ALTER TABLE` тоже выполняется атомарно; в файле с несколькими командами транзакция откатывает и предыдущие команды.

</details>

```console
$ docker compose exec db psql -c 'SELECT * FROM orders LIMIT 1'
 id | customer | note 
----+----------+------
  1 | Dilnoza  | 
(1 row)
```

```console
$ goose status
2026/11/27 20:34:28     Applied At                  Migration
2026/11/27 20:34:28     =======================================
2026/11/27 20:34:28     Fri Nov 27 15:34:28 2026 -- 00001_products.sql
2026/11/27 20:34:28     Fri Nov 27 15:34:28 2026 -- 00002_orders.sql
2026/11/27 20:34:28     Pending                  -- 00003_orders_status.sql
```

Есть только `id`, `customer`, `note`. `00003` остаётся `Pending`.
Дата `Applied At` зависит от часового пояса базы, префикс строки — от окружения CLI; здесь они отличаются.
С `-- +goose NO TRANSACTION` обычная гарантия не действует: команды до ошибки могут сохраниться.
В файлах этого урока такой аннотации нет.

## Исправляем неприменённый файл

Правило: не меняйте миграцию, уже применённую к любой базе. Goose не проверяет изменение содержимого и сам не выполнит её заново.
Иначе разные базы получат разные схемы под одним номером. Для изменения создавайте новый файл с новым номером.
Этот третий файл ещё ни к одной базе не применён, поэтому исправим его:

```sql filename="migrations/00003_orders_status.sql" showLineNumbers
-- +goose Up
ALTER TABLE orders
    ADD COLUMN status text NOT NULL DEFAULT 'yangi' CHECK (status <> '');

-- +goose Down
ALTER TABLE orders DROP COLUMN status;
```

Новое — строка 3. `DEFAULT 'yangi'` задаёт значение и существующим заказам, и новым записям без явно указанного статуса.
`yangi` означает «новый». `CHECK (status <> '')` запрещает пустой текст; это отдельное от `NOT NULL` правило.
Сколько файлов теперь применится? **A)** все три · **B)** только 3 · **C)** ни одного.

<details>
<summary>Ответ</summary>

**B.** Первые два файла сохранены. Третий после ошибки остался неприменённым; исправление позволяет повторить попытку.

</details>

```console
$ goose up
2026/11/27 20:34:28 OK   00003_orders_status.sql (4.12ms)
2026/11/27 20:34:28 goose: successfully migrated database to version: 3
```

```console
$ docker compose exec db psql -c 'SELECT id, customer, status FROM orders'
 id | customer | status 
----+----------+--------
  1 | Dilnoza  | yangi
  2 | Jasur    | yangi
  3 | Malika   | yangi
(3 rows)
```

У всех трёх существующих заказов статус `yangi`. Этот запрос не гарантирует порядок: если он нужен, добавьте `ORDER BY id`.

Времена из видео ниже **цитируются**; рядом измерения, повторённые для этой страницы.

| Действие | Видео, ms | Этот запуск, ms | Этот / видео |
|---|---|---|---|
| Up 00001 | 10.27 | 8.94 | 0.87× |
| Up 00002 | 7.37 | 9.83 | 1.33× |
| Up 00003 | 7.18 | 4.12 | 0.57× |
| Down 00003 | 5.05 | 4.71 | 0.93× |

На загруженном компьютере миллисекунды меняются. Отношения показывают различие одного запуска, а не гарантию производительности.
Существенно поведение: выполнен только нужный файл, ошибка не сохранила изменение, повторная попытка сработала.

## Down: откат последней миграции

`goose down` выполняет раздел `Down` последней применённой миграции. Сколько файлов откатится при версии 3?
**A)** все · **B)** последний · **C)** ни одного.

<details>
<summary>Ответ</summary>

**B.** Только `DROP COLUMN status` из файла 3. `docker compose down -v` удаляет всю экспериментальную базу; goose down выполняет этот SQL.

</details>

```console
$ goose down
2026/11/27 20:34:28 OK   00003_orders_status.sql (4.71ms)
```

```console
$ docker compose exec db psql -c 'SELECT * FROM orders LIMIT 1'
 id | customer | note 
----+----------+------
  1 | Dilnoza  | 
(1 row)
```

`status` отсутствует, прежние три столбца на месте. `DROP COLUMN` удаляет и данные статуса; Down не заменяет резервную копию.
В рабочей базе часто пишут новую исправляющую миграцию. Down удобен при разработке и тестировании.
Повторите `up`: файл 3 применится снова, статусы снова получат DEFAULT.

```console
$ goose up
2026/11/27 20:34:28 OK   00003_orders_status.sql (4.02ms)
2026/11/27 20:34:28 goose: successfully migrated database to version: 3
```

## Глубже (необязательно): SQL внутри binary

На сервере может не быть отдельной команды goose. Go умеет включать файлы в binary при компиляции.
Фрагмент `migrate.go`; это не отдельная программа:

```go
//go:embed migrations/*.sql
var files embed.FS
```

Строка 1 — директива `//go:embed`. `migrations/*.sql` выбирает SQL-файлы этой папки; `*` — переменная часть имени.
Строка 2 объявляет переменную `files` типа `embed.FS` через `var`. Этот тип позволяет читать встроенные файлы; полный файл импортирует `embed`.

SQL-файлы с номерами распространяются вместе с binary. При изменении файла binary нужно пересобрать.
`NewProvider` из папки использует goose как библиотеку и координирует несколько экземпляров с помощью сессионной блокировки Postgres.
API библиотеки и вызов при deploy разбираются в [GB-8.06](/lab/youtube/gb#gb-8-06); сейчас готовый `migrate.go` используется через тесты.

## Частые ошибки

1. **Редактировать применённый файл.** Goose видит версию, а не изменение содержимого. Второй `up` выше не обнаружит новую работу. Исправление: новый файл с новым номером.
2. **NOT NULL без DEFAULT в заполненной таблице.** Полная ошибка `23502` показана выше; `DEFAULT 'yangi'` в `00003` задаёт значение существующим строкам.
3. **Считать NULL и пустой текст одинаковыми.** `NOT NULL` не запрещает `''`. Добавьте `CHECK (status <> '')`.
4. **Ожидать восстановления данных от Down.** `DROP COLUMN` удаляет прежние статусы. Повторный Up восстанавливает только DEFAULT.
5. **Считать ошибку одного файла откатом всех файлов.** После ошибки файла 3 файлы 1 и 2 остаются применёнными. Граница транзакции — один файл.

## Проверьте себя

**1.** Где goose хранит применённые версии? Почему двум файлам соответствуют три записи?

<details>
<summary>Ответ</summary>

В `goose_db_version`. `0` — начальная запись, `1` и `2` — версии файлов.

</details>

**2.** Почему неудачная миграция не оставляет таблицу изменённой частично? Каково исключение?

<details>
<summary>Ответ</summary>

Обычно один файл выполняется в одной транзакции. При ошибке откатывается этот файл. `NO TRANSACTION` отключает защиту.

</details>

**3.** Версия 3. `goose down`, затем `goose up`. **A)** заново выполняются 1–3 · **B)** откатывается и применяется только 3 · **C)** up выдаёт ошибку.

<details>
<summary>Ответ</summary>

**B.** Down откатывает последний файл; Up снова видит неприменённый файл 3. Прежние данные статуса не возвращаются.

</details>

**4.** Из GB-5.03: сохранится ли строка с ценой `0` при `CHECK (price > 0)`?

<details>
<summary>Ответ</summary>

Нет. Условие ложно; база отклонит строку с ошибкой нарушения CHECK.

</details>
