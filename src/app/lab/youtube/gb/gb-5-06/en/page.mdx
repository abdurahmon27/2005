## What you will learn

`orders.sql` has created the tables once. What happens if you run it during the next server update? How can you update the schema while keeping the data?

**The one idea:** each schema change lives in a numbered SQL file. The database records applied versions in `goose_db_version`; goose applies the missing files.
Normally, each file runs in one transaction: if it fails, that file's changes roll back.

After this lesson you will:

- install goose and run `status`, `up`, and `down`;
- read the database state from its version table;
- fix a column addition on a populated table with `DEFAULT`;
- write the fourth migration and check it with tests.

| Word | Plain meaning | English term |
|---|---|---|
| migration file | a numbered SQL file that changes the schema | migration file |
| goose | a tool that compares files with applied versions in the database | goose |
| failed migration | an unsuccessful change rolled back within the usual transaction | failed migration |

**ALTER TABLE** changes an existing table's structure. **`\dt`** lists tables in psql.
Here, schema means the structure of tables; `public` is the named schema containing the tables.

## Migration files and goose

Each change is a separate **migration file**. Its number gives the order; goose compares files with database versions.

| Before | Action | After |
|---|---|---|
| files 1, 2; database at initial 0 | `goose up` | 1, 2 applied; version 2 |
| files 1, 2; database has 1, 2 | `goose up` | no change |
| files 1, 2, 3; database has 1, 2 | `goose up` | only 3 runs |

Install a specific goose version. In the module path, `v3` is the major version, `cmd/goose` is the command package, and `@v3.30.2` selects the version.
`go install` writes the executable to `GOBIN`, or usually `~/go/bin` when unset. Put that folder in `PATH`.

```console
$ go install github.com/pressly/goose/v3/cmd/goose@v3.30.2
```

```console
$ goose -version
goose version: v3.30.2
```

Installation printed nothing in this repeat run; a first run may print download messages. `-version` shows the installed version.
Goose needs three values: `GOOSE_DRIVER` selects the database type; `GOOSE_DBSTRING` is the connection address; `GOOSE_MIGRATION_DIR` selects the file directory.
One `export` can set several values.

```bash
export GOOSE_DRIVER=postgres GOOSE_MIGRATION_DIR=migrations
export GOOSE_DBSTRING=postgres://bozor:bozor-lab@localhost:5486/bozor
export DATABASE_URL=postgres://bozor:bozor-lab@localhost:5486/bozor
```

Later Go tests read `DATABASE_URL`; goose uses its own `GOOSE_DBSTRING`.
The URL contains user `bozor`, lab password `bozor-lab`, host and port `localhost:5486`, and database name `bozor` at the end.
`ls migrations` lists the files:

```console
$ ls migrations
00001_products.sql
00002_orders.sql
```

```sql filename="migrations/00001_products.sql" showLineNumbers
-- +goose Up
CREATE TABLE products (
    id     bigint
           GENERATED ALWAYS AS IDENTITY
           PRIMARY KEY,
    name   text    NOT NULL UNIQUE CHECK (name <> ''),
    price  bigint  NOT NULL CHECK (price > 0),
    stock  integer NOT NULL DEFAULT 0 CHECK (stock >= 0),
    active boolean NOT NULL DEFAULT true
);

-- +goose Down
DROP TABLE products;
```

| Line | What it does |
|---|---|
| 1 | In SQL, `--` starts a comment; goose reads `-- +goose Up` as the apply-section marker |
| 2 | `CREATE TABLE products (` opens the table and column definition |
| 3–5 | `id` is a large integer; the database assigns its number; the primary key makes it unique |
| 6 | `name` is text; NULL, duplicates, and empty text are rejected |
| 7 | `price` is a large integer in tiyin; NULL and nonpositive values are rejected |
| 8 | `stock` is an integer, defaulting to 0; negatives and NULL are rejected |
| 9 | `active` is a boolean, defaulting to true; NULL is rejected |
| 10 | `);` closes the table definition and SQL statement |
| 12–13 | `Down` begins the rollback section; `DROP TABLE` deletes the table |

`<>` means not equal; `''` is empty text. The second file creates related tables:

```sql filename="migrations/00002_orders.sql" showLineNumbers
-- +goose Up
CREATE TABLE orders (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer text   NOT NULL,
    note     text
);
CREATE TABLE order_items (
    id         bigint  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id   bigint  NOT NULL REFERENCES orders (id),
    product_id bigint  NOT NULL REFERENCES products (id),
    quantity   integer NOT NULL CHECK (quantity > 0),
    unit_price bigint  NOT NULL CHECK (unit_price > 0)
);

-- +goose Down
DROP TABLE order_items;
DROP TABLE orders;
```

Lines 2–6: `orders` stores orders; `customer` is the customer name, and `note` is an optional note.
Lines 7–13: `order_items` stores order lines; `order_id` and `product_id` are foreign keys.
The `quantity` and `unit_price` must be positive.
Lines 15–17: the referencing `order_items` table is dropped before `orders`. The first migration rolls back after the second.

`Pending` means not applied yet. All console blocks below were rerun; date prefixes are preserved exactly.

```console
$ goose status
2026/11/27 20:34:28     Applied At                  Migration
2026/11/27 20:34:28     =======================================
2026/11/27 20:34:28     Pending                  -- 00001_products.sql
2026/11/27 20:34:28     Pending                  -- 00002_orders.sql
```

`goose up` runs unapplied files in numeric order. Which files run in this empty database?
**A)** only 2 · **B)** 1 followed by 2 · **C)** neither.

<details>
<summary>Answer</summary>

**B.** Both are `Pending`. The highest number identifies the newest version; it does not mean only that file should run.

</details>

```console
$ goose up
2026/11/27 20:34:28 OK   00001_products.sql (8.94ms)
2026/11/27 20:34:28 OK   00002_orders.sql (9.83ms)
2026/11/27 20:34:28 goose: successfully migrated database to version: 2
```

`OK` means the file was applied; parentheses contain the duration, and `ms` means milliseconds. The last line reports current database version `2`.
`psql -c` executes one command. `\dt` lists tables:

$ docker compose exec db psql -c '\dt'

</details>

## A NOT NULL error on a populated table

`seed.sql` inserts four products, three orders, and four order lines:

```console
$ docker compose exec db psql -f /lab/seed.sql
INSERT 0 4
INSERT 0 3
INSERT 0 4
```

`N` in each `INSERT 0 N` counts inserted rows.
Orders need a status. `goose create` creates a template; `-s` selects sequential numbering, `orders_status` is the name, and `sql` is the file type.
Without `-s`, the name starts with a timestamp; choose one numbering scheme per project.

```console
$ goose create -s orders_status sql
2026/11/27 20:34:28 Created new file: migrations/00003_orders_status.sql
```

```console
$ ls migrations
00001_products.sql
00002_orders.sql
00003_orders_status.sql
```

`Created new file` confirms file creation. Replace the template's example `SELECT` statements. Start with this deliberately broken version:

```sql
-- +goose Up
ALTER TABLE orders ADD COLUMN status text NOT NULL;

-- +goose Down
ALTER TABLE orders DROP COLUMN status;
```

Line 1 starts Up. Line 2: `ALTER TABLE orders` changes the existing table; `ADD COLUMN` adds a text column named `status`.
`NOT NULL` forbids NULL. Lines 4–5 form Down; `DROP COLUMN` removes the column.
Without a `DEFAULT`, existing rows receive NULL in the new column. NULL differs from empty text.

Three orders already exist. What happens? **A)** status becomes `''` · **B)** the database rejects it · **C)** NULL is accepted.

<details>
<summary>Answer</summary>

**B.** The three existing rows would receive NULL, which `NOT NULL` forbids. A has no empty-text value configured; C violates the constraint.

</details>

```console
$ goose up
2026/11/27 20:34:28 goose run: ERROR 00003_orders_status.sql: failed to run SQL migration: failed to execute SQL query "ALTER TABLE orders ADD COLUMN status text NOT NULL;": ERROR: column "status" of relation "orders" contains null values (SQLSTATE 23502)
```

Goose has exit code `1`. `ERROR 00003_orders_status.sql` identifies the file; the unsuccessful SQL follows.
`column "status" of relation "orders" contains null values` explains the conflicting values.
`SQLSTATE 23502` is Postgres's `not_null_violation` code: a NOT NULL violation.

A **transaction** saves either all its commands or none. [GB-5.07](/lab/youtube/gb/gb-5-07/en) explains it further.
Goose normally executes each file in one transaction. This does not mean one transaction covers every file in one `up`.

| Stage | Files 1–2 | File 3 | orders.status |
|---|---|---|---|
| before failure | committed | not started | absent |
| failure | committed | rolled back | absent |
| next attempt | not executed again | executed again | depends on success |

Midway question: what is `orders` like after failure? **A)** status exists with NULL · **B)** status is absent · **C)** the table is partly changed.

<details>
<summary>Answer</summary>

**B.** This file's change was not committed. This `ALTER TABLE` is itself atomic; in a file with several commands, the transaction also rolls back earlier commands.

</details>

```console
$ docker compose exec db psql -c 'SELECT * FROM orders LIMIT 1'
 id | customer | note 
----+----------+------
  1 | Dilnoza  | 
(1 row)
```

```console
$ goose status
2026/11/27 20:34:28     Applied At                  Migration
2026/11/27 20:34:28     =======================================
2026/11/27 20:34:28     Fri Nov 27 15:34:28 2026 -- 00001_products.sql
2026/11/27 20:34:28     Fri Nov 27 15:34:28 2026 -- 00002_orders.sql
2026/11/27 20:34:28     Pending                  -- 00003_orders_status.sql
```

Only `id`, `customer`, and `note` exist. `00003` remains `Pending`.
The `Applied At` date depends on the database time zone; line prefixes depend on the CLI environment. They differ in this output.
A file containing `-- +goose NO TRANSACTION` opts out of the usual guarantee: commands before an error may remain committed.
This lesson's files do not contain that annotation.

## Fixing an unapplied file

Rule: do not edit a migration already applied to any database. Goose does not check content changes or automatically rerun it.
Otherwise different databases can have different schemas under the same number. Write a new numbered file for a change.
This third file has not been applied to any database, so we can fix it:

```sql filename="migrations/00003_orders_status.sql" showLineNumbers
-- +goose Up
ALTER TABLE orders
    ADD COLUMN status text NOT NULL DEFAULT 'yangi' CHECK (status <> '');

-- +goose Down
ALTER TABLE orders DROP COLUMN status;
```

The change is line 3. `DEFAULT 'yangi'` gives existing orders a value and applies to new rows when status is omitted.
`yangi` means “new”. `CHECK (status <> '')` rejects empty text; this is separate from `NOT NULL`.
How many files now apply? **A)** all three · **B)** only 3 · **C)** none.

<details>
<summary>Answer</summary>

**B.** The first two files are committed. The third remained unapplied after failure; we fix it and retry.

</details>

```console
$ goose up
2026/11/27 20:34:28 OK   00003_orders_status.sql (4.12ms)
2026/11/27 20:34:28 goose: successfully migrated database to version: 3
```

```console
$ docker compose exec db psql -c 'SELECT id, customer, status FROM orders'
 id | customer | status 
----+----------+--------
  1 | Dilnoza  | yangi
  2 | Jasur    | yangi
  3 | Malika   | yangi
(3 rows)
```

All three existing orders have status `yangi`. This query does not guarantee ordering: add `ORDER BY id` when order matters.

## Down: rolling back the latest migration

`goose down` executes the `Down` section of the latest applied migration. At version 3, how many files roll back?
**A)** all · **B)** the latest · **C)** none.

<details>
<summary>Answer</summary>

**B.** Only `DROP COLUMN status` from file 3. `docker compose down -v` removes the entire experiment database; goose down executes that SQL.

</details>

```console
$ goose down
2026/11/27 20:34:28 OK   00003_orders_status.sql (4.71ms)
```

```console
$ docker compose exec db psql -c 'SELECT * FROM orders LIMIT 1'
 id | customer | note 
----+----------+------
  1 | Dilnoza  | 
(1 row)
```

`status` is absent; the original three columns remain. `DROP COLUMN` also deletes status data; Down is not a backup.
Production changes often use a new corrective migration. Down is useful in development and tests.
Run `up` again: file 3 applies again, and status values return to the DEFAULT.

```console
$ goose up
2026/11/27 20:34:28 OK   00003_orders_status.sql (4.02ms)
2026/11/27 20:34:28 goose: successfully migrated database to version: 3
```

## Going deeper (optional): SQL inside the binary

The server may have no separate goose command. Go can include files in the binary at compilation.
This is an excerpt from `migrate.go`, not a standalone program:

```go
//go:embed migrations/*.sql
var files embed.FS
```

Line 1 is the `//go:embed` directive. `migrations/*.sql` selects SQL files in that folder; `*` matches the variable part of each name.
Line 2 uses `var` to declare `files` with type `embed.FS`. That type reads embedded files; the complete file imports `embed`.

Numbered SQL files travel with the binary. Changing a file requires rebuilding the binary.
The folder's `NewProvider` uses goose as a library and coordinates multiple instances with a Postgres session lock.
[GB-8.06](/lab/youtube/gb#gb-8-06) covers the library API and deployment calls; for now, tests use the supplied `migrate.go`.

## Common mistakes

1. **Editing an applied file.** Goose sees the version, not content changes. The second `up` above will not discover new work. Fix: a new numbered file.
2. **NOT NULL without DEFAULT on a populated table.** The full `23502` error appears above; `DEFAULT 'yangi'` in `00003` supplies values for existing rows.
3. **Treating NULL and empty text as equivalent.** `NOT NULL` does not forbid `''`. Also use `CHECK (status <> '')`.
4. **Expecting Down to restore data.** `DROP COLUMN` removes old statuses. Repeating Up restores only the DEFAULT.
5. **Thinking one failed file rolls back every file.** Files 1 and 2 remain applied after file 3 fails. The transaction boundary is one file.

</details>
