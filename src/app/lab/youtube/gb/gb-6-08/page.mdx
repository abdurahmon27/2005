## Nimani oʻrganasiz

6-modulda bozor'ga beshta qoida qoʻshildi: parol, session, buyurtma egasi, admin roli va rate limit. Ertaga kimdir yangi route qoʻshib, bitta qoidani buzsa, buni kim aytadi?

**Bitta gʻoya:** qoida faqat uni **buzishga urinadigan** foydalanuvchi bilan tekshirilganda isbotlangan hisoblanadi. Spetsifikatsiya jadval boʻladi: «kim · soʻrov · kutilgan status». Har qator butun middleware zanjiri orqali, haqiqiy Postgres'da yuboriladi. Jadvalda **ikki xaridor** bor: biri ikkinchisining buyurtmasini soʻraydi. Bitta foydalanuvchi bilan yozilgan test begona buyurtmani hech qachon soʻramaydi, shuning uchun BOLA'ni koʻrmaydi.

Dars oxirida siz:

- himoyalangan bozor'ning spetsifikatsiyasini oʻqib, uni bitta toʻliq `curl` sessiyasida koʻrasiz: `401`, `403`, `404` va `429`;
- qoidalarni `rule{who, method, path, body, want}` jadvaliga yozib, `go test` bilan haqiqiy Postgres'da isbotlaysiz;
- bitta foydalanuvchili test BOLA'li kodda ham oʻtishini, ikki xaridorli jadval esa uni ushlashini oʻz koʻzingiz bilan koʻrasiz;
- `GET /orders` va `GET /admin/orders` route'larini yozib, ularning qatorlarini jadvalga qoʻshasiz.

| Soʻz | Oddiy maʼnosi | Inglizcha |
|---|---|---|
| himoya jadvali | spetsifikatsiya jadval shaklida: har qator — kim, qaysi soʻrov, kutilgan status | access table |
| bitta oʻram | `/admin/` ostidagi hamma route bitta mux'da, mux esa bir marta oʻralgan: unutib boʻlmaydi | one wrap for a route group |
| ikki foydalanuvchili test | begona obyektni soʻraydigan ikkinchi xaridor bilan yozilgan test | two-user test |

Yordamchi soʻzlar shu yerning oʻzida izohlanadi: Postgres'ning `left(matn, n)` funksiyasi va `go test -run`dagi regexp (`|`, `$`).

## Spetsifikatsiya: kim nima qila oladi

Qoidani isbotlash uchun avval uni aniq yozish kerak. Himoyalangan bozor'ning spetsifikatsiyasi uch guruh va yana uch qoida:

```text
ochiq        GET /products, GET /products/{id}
             POST /users · POST /login · POST /logout
login kerak  GET /me · POST /orders
             GET, PATCH /orders/{id}            yoʻq session → 401
             begona buyurtma = yoʻq buyurtma    → 404
admin        GET /admin/users · POST /admin/products
             DELETE /admin/products/{id}        xaridorga → 403
```

| Guruh | Kim kira oladi | Yoʻq boʻlsa | Qaysi dars |
|---|---|---|---|
| ochiq | hamma: katalog, roʻyxatdan oʻtish, login, logout | — | GB-5.10, GB-6.03, GB-6.04 |
| login kerak | session bor foydalanuvchi: buyurtmalar va `GET /me` | `401 Unauthorized`: kimligingiz nomaʼlum | GB-6.04 |
| buyurtma | faqat egasi: `WHERE id = $1 AND user_id = $2` | `404 Not Found`: begona buyurtma yoʻq buyurtma bilan bir xil | GB-6.06 |
| admin | `admin` roli: foydalanuvchilar va katalogni oʻzgartirish | `403 Forbidden`: kimligingiz maʼlum, roli yetmaydi | GB-6.06 |

Begona buyurtmaga `403` emas, `404` qaytadi: `403` «bunday buyurtma bor, lekin sizniki emas» degan maʼnoni beradi. RFC 9110 §15.5.4 shunday ruxsat beradi: mavjudligini yashirmoqchi boʻlgan server `403` oʻrniga `404` qaytarishi **mumkin**.

Yana uch qoida:

- **Parol** bazada hech qachon ochiq turmaydi: faqat GB-6.03'dagi argon2id satri.
- **Login** soʻrovlariga limit: bitta IP'dan 5 urinish, bitta email'ga 10 urinish. Keyin `429 Too Many Requests` va `Retry-After` sarlavhasi.
- **Har xato javobi** GB-6.02'dagi `application/problem+json` shaklida.

## Middleware zanjiri tashqaridan ichkariga

`newHandler` (`cmd/api/middleware.go`) har soʻrovni shu qavatlar orqali oʻtkazadi. Har qavat keyingisini oʻraydi: tashqi qavat birinchi koʻradi.

```go
func newHandler(st *store.Store) http.Handler {
	return requestID(
		logRequests(
			recoverPanic(
				cors(
					protectCSRF(
						muxErrors(newMux(st)))))))
}
```

| Qator | Kod | Nima qiladi |
|---|---|---|
| 1 | `func newHandler(st *store.Store) http.Handler {` | butun API'ning bitta handler'ini yasaydi (GB-6.01) |
| 2 | `requestID(` | har soʻrovga `X-Request-Id` beradi (GB-6.01) |
| 3 | `logRequests(` | har soʻrovga log qatori yozadi (GB-6.01) |
| 4 | `recoverPanic(` | panic'ni `500` javobga aylantiradi (GB-6.01) |
| 5 | `cors(` | CORS sarlavhalarini qoʻshadi (GB-6.07) |
| 6 | `protectCSRF(` | begona origin'dan kelgan oʻzgartiruvchi soʻrovga `403` beradi (GB-6.07) |
| 7 | `muxErrors(newMux(st))` | mux'ning oʻz `404` va `405` javoblarini problem shaklida beradi (GB-6.01); `newMux` route'larni yasaydi |

Qatorlarning oxiridagi koʻp `)` — yetti ochilgan qavsning yopilishi. Soʻrov `requestID`dan `muxErrors`ga qarab ichkariga kiradi, javob esa teskari yoʻldan chiqadi.

Route'larning oʻz qavatlari ham bor. Bu `newMux` ichidan (`cmd/api/handlers.go`, 35–48-qatorlar):

```go
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", healthHandler)
	mux.HandleFunc("GET /products", a.listProducts)
	mux.HandleFunc("GET /products/{id}", a.getProduct)
	mux.Handle("POST /users", requireJSON(http.HandlerFunc(a.register))) // GB-6.03
	mux.Handle("POST /login", a.loginIP.limitByIP(requireJSON(http.HandlerFunc(a.login))))
	mux.HandleFunc("POST /logout", a.logout) // requireUser'siz: eskirgan cookie ham tozalansin (GB-6.04)

	mux.Handle("GET /me", a.requireUser(http.HandlerFunc(a.me)))
	mux.Handle("POST /logout-all", a.requireUser(http.HandlerFunc(a.logoutAll)))
	// VAZIFA (TASK.md, 2-qadam): GET /orders — faqat oʻz buyurtmalari (requireUser bilan)
	mux.Handle("POST /orders", a.requireUser(requireJSON(http.HandlerFunc(a.createOrder))))
	mux.Handle("GET /orders/{id}", a.requireUser(http.HandlerFunc(a.getOrder)))
	mux.Handle("PATCH /orders/{id}", a.requireUser(requireJSON(http.HandlerFunc(a.updateNote))))
```

| Qator | Nima qiladi |
|---|---|
| 1 | `mux := http.NewServeMux()` — yoʻl → handler jadvali (GB-4.04) |
| 2–4 | `GET /health`, `GET /products`, `GET /products/{id}`: oʻramsiz, ochiq |
| 5 | `POST /users` — roʻyxatdan oʻtish: ochiq, faqat `requireJSON` (JSON boʻlmagan body'ga `415`, GB-6.01) |
| 6 | `POST /login` — `limitByIP` (GB-6.07) `requireJSON`ni oʻraydi: limit eng birinchi |
| 7 | `POST /logout` — `requireUser`siz: eskirgan cookie ham tozalansin (GB-6.04) |
| 9–10 | `GET /me`, `POST /logout-all` — `requireUser` bilan: session boʻlmasa `401` |
| 11 | vazifa izohi: `GET /orders` shu yerga qoʻshiladi |
| 12–14 | buyurtma route'lari `requireUser` bilan; `PATCH`da `requireJSON` uning **ichida**: avval kimligingiz (`401`), keyin body (`415`) |

## Admin route'lari: bitta mux, bitta oʻram

GB-6.06'da har admin route alohida oʻralardi. Birini unutsangiz, oddiy xaridor unga kirardi: bu OWASP API5:2023 (BFLA). OWASP yagona, tekshirish oson ruxsat moduli tavsiya qiladi va hamma narsani sukut boʻyicha rad etishni aytadi. Bugungi yechim: admin route'lari **alohida mux**da, mux esa **bir marta** oʻraladi.

```go
	admin := http.NewServeMux()
	admin.HandleFunc("GET /admin/users", a.listUsers)
	// VAZIFA (TASK.md, 2-qadam): GET /admin/orders — hamma buyurtmalar
	admin.Handle("POST /admin/products", requireJSON(http.HandlerFunc(a.createProduct)))
	admin.HandleFunc("DELETE /admin/products/{id}", a.deleteProduct)
	mux.Handle("/admin/",
		a.requireUser(requireAdmin(muxErrors(admin))))
```

| Qator | Nima qiladi |
|---|---|
| 1 | `admin := http.NewServeMux()` — yana bitta yoʻl → handler jadvali, faqat admin uchun |
| 2 | `GET /admin/users` — yoʻl toʻliq yoziladi: soʻrovdagi yoʻl oʻzgarmaydi |
| 3 | vazifa izohi: `GET /admin/orders` shu yerga qoʻshiladi |
| 4 | `POST /admin/products` — katalogga yozish endi shu yerda (`POST /products`dan koʻchdi); `requireJSON` bilan |
| 5 | `DELETE /admin/products/{id}` — mahsulotni oʻchirish, `{id}` — GB-4.05 |
| 6–7 | admin mux'ni asosiy mux'ga ulaydi va oʻraydi: `requireUser`ning ichida `requireAdmin`, uning ichida `muxErrors` va admin mux |

`"/admin/"` pattern'i slash bilan tugaydi va metodsiz. Ikkala xususiyat [`net/http.ServeMux`](https://pkg.go.dev/net/http#ServeMux) hujjatida yozilgan: slash bilan tugaydigan pattern shu yoʻl ostidagi **hamma** yoʻlga mos keladi, metodsiz pattern **har** metodga mos keladi. Demak `/admin/` ostidagi har soʻrov — hozirgi va kelajakdagi, mavjud va mavjud boʻlmagan — avval shu ikki oʻramdan oʻtadi:

```text
GET /admin/…  →  requireUser  →  requireAdmin  →  muxErrors  →  admin mux
                 session yoʻq    rol xaridor       admin mux      handler yoki
                 → 401           → 403             javoblari      404 / 405
```

Admin mux'ga qoʻshilgan har yangi route oʻzi himoyalangan: oʻram yozish kerak emas, unutib ham boʻlmaydi. Tashqi `muxErrors` `/admin/` pattern'ini topadi, shuning uchun ichki mux'ning oʻz `404` va `405` javoblari uchun `muxErrors(admin)` alohida kerak.

## Bitta curl sessiyasi: har qoida

Endi spetsifikatsiyaning har bandini bitta sessiyada koʻramiz. Hamma chiqish shu kompyuterda, Go 1.27.4, PostgreSQL 18 va curl 8.22.0 bilan olingan. Ikki eslatma:

- Men `curl -i`ni `curl -s -i` bilan ishga tushirdim: chiqish faylga ketgani uchun `-s` progress qatorini yashiradi. Terminalda `curl -i` aynan shu qatorlarni chiqaradi.
- `X-Request-Id` va `Date` har yurishda boshqa. Qolgan hamma qator bir xil chiqadi.

### 1. Baza, migratsiyalar, seed va server

Birinchi terminalda Postgres'ni ishga tushiramiz:

```console
$ docker compose up -d --wait
…
 Container gb608-db-1 Waiting
 Container gb608-db-1 Healthy
```

Port `5518`, konteyner nomi `gb608-db-1`: boshi `compose.yaml`dagi loyiha nomi (`gb608`). `…` bilan compose'ning tarmoq va konteyner yaratish qatorlarini qisqartirdim. Endi ulanish satri (konteynerdan olinadi, ekranga chiqmaydi) va goose:

```bash
export DATABASE_URL="$(docker compose exec -T db sh -c 'printf "postgres://%s:%s@localhost:5518/%s" "$POSTGRES_USER" "$POSTGRES_PASSWORD" "$POSTGRES_DB"')"
export GOOSE_DRIVER=postgres GOOSE_MIGRATION_DIR=migrations
export GOOSE_DBSTRING="$DATABASE_URL"
```

```console
$ goose up

OK   00003_orders_status.sql (2.88ms)
OK   00004_users.sql (5.94ms)
```

goose har qator boshiga sana va vaqt yozadi; ixchamlik uchun olib tashladim. Yettita migratsiya qoʻllandi (GB-5.06). Keyin `seed.sql`:


Server shu terminalda ishlab turadi; qolgan buyruqlarni ikkinchi terminalda yozasiz. (Serverning birinchi qatorini men `go run ./cmd/api` bilan tekshirdim; keyingi sessiyada esa xuddi shu kodni `go build` bilan qurib ishlatdim: chiqish bir xil.)

### 2. Roʻyxatdan oʻtish: rolni baza beradi

Ikkinchi terminalda yangi foydalanuvchi Aziza roʻyxatdan oʻtadi: `POST /users`, email va kamida 15 belgili parol (GB-6.03):

```console

HTTP/1.1 201 Created
Content-Type: application/json
Vary: Origin
X-Request-Id: GVAN7GMVLZRFTRELEHFJ4H7PG6
```

Birinchi qator `201 Created`. Body'da yangi foydalanuvchining `id`si — 4 va `"role":"xaridor"`. Rolni mijoz yubormaydi: u bazadagi ustunning sukut qiymati (GB-6.06, eng kam huquq).

### 3. Bazada nima turibdi

Parol bazada ochiq turmasligi kerak. Tekshiramiz: `psql -c` bitta SQL buyruqni bajaradi, Postgres'ning `left(matn, n)` funksiyasi matnning birinchi `n` belgisini oladi. Bu yerda — `password_hash`ning birinchi 31 belgisi:

```console
$ docker compose exec db psql -c "SELECT id, email, left(password_hash, 31) FROM users WHERE id = 4"
 id |      email       |              left
----+------------------+---------------------------------
  4 | aziza@bozor.test | $argon2id$v=19$m=47104,t=1,p=1$
(1 row)
```

Birinchi 31 belgi: `$argon2id$` (algoritm), `v=19$` (versiya), `m=47104,` (xotira, KiB), `t=1,` (oʻtishlar soni), `p=1$` (parallellik). Parolning oʻzi hech qayerda yoʻq; qolgani — salt va kalit — keyingi belgilarda, biz ularni chop etmaymiz (GB-6.03).

### Bashorat: umuman yoʻq admin yoʻli

Endi hech qayerda roʻyxatdan oʻtmagan yoʻl: cookie'siz `GET /admin/yoq`. Javob qanday? **A)** `404 Not Found` · **B)** `401 Unauthorized` · **C)** `403 Forbidden`.

<details>
<summary>Javob</summary>

**B.** `"/admin/"` pattern'i bu yoʻlni ham ushlaydi, birinchi qavat — `requireUser`: cookie yoʻq, demak `401`. Agar A deb oʻylagan boʻlsangiz, mux «bunday route yoʻq» deb avval oʻzi javob beradi deb tasavvur qilgansiz; lekin `/admin/` ostidagi yoʻl mux'ning oʻzigacha yetmaydi. C — `403` faqat kimligi maʼlum, roli yetmaydigan foydalanuvchiga.

</details>

### 7. Login limiti

Oxirgi qoida. Bir qatorda olti login: beshta notoʻgʻri parol, oltinchisi — Azizaning toʻgʻri paroli. Buyruq terminalda bir qator; mana u, tushunarli boʻlishi uchun boʻlib yozilgan:

## Testlar: qoidalarning isboti

Qoidalar koʻrinib turibdi. Lekin ertaga kimdir yangi route qoʻshib, bittasini buzsa, `curl` buni aytmaydi. Buni test aytadi. Testlar `cmd/api/himoya_test.go`da; ularning mock'i yoʻq: har test oʻz sxemasida, haqiqiy Postgres'da ishlaydi (`internal/pgtest`, GB-5.10).

### Jadvalning bir qatori

```go
// Jadvaldagi body'lar.
const (
	orderBody   = `{"items":[{"product_id":3,"quantity":1}]}`
	productBody = `{"name":"anor","price":1800000,"stock":5}`
	noteBody    = `{"note":"Jasurning manzili"}`
)

// rule — jadvalning bir qatori: kim, qaysi soʻrov, qaysi status kutiladi.
type rule struct {
	who                string // "anonim" (cookie'siz), "dilnoza", "jasur", "admin"
	method, path, body string
	want               int
}
```

| Qator | Kod | Nima qiladi |
|---|---|---|
| 1–6 | `const ( … )` | jadvalda ishlatiladigan uch tayyor body: buyurtma, mahsulot va izoh (GB-1.03) |
| 9 | `type rule struct {` | `rule` — jadvalning bir qatorini tavsiflovchi struct (GB-2.03) |
| 10 | `who string` | kim: `"anonim"` (cookie'siz), `"dilnoza"`, `"jasur"` yoki `"admin"` |
| 11 | `method, path, body string` | soʻrov: metod, yoʻl va body (bir qatorda uch `string` maydon) |
| 12 | `want int` | kutilgan status kodi |

Jadvalning oʻzi — spetsifikatsiya (`accessRules`; bu starter, vazifaning qatorlari hali yoʻq):

```go
// accessRules — kim nima qila oladi (README, «Spetsifikatsiya»). Ikki xaridor shart: bitta foydalanuvchi
// bilan yozilgan test begona buyurtmani hech qachon soʻramaydi va BOLA'ni koʻrmaydi.
var accessRules = []rule{
	{"anonim", "GET", "/products", "", 200},
	{"anonim", "GET", "/orders/41", "", 401},
	{"anonim", "POST", "/orders", orderBody, 401},
	{"anonim", "POST", "/admin/products", productBody, 401},
	{"dilnoza", "GET", "/orders/41", "", 200},
	{"dilnoza", "GET", "/orders/42", "", 404},
	{"jasur", "GET", "/orders/41", "", 404},
	{"jasur", "PATCH", "/orders/41", noteBody, 404},
	{"admin", "GET", "/orders/41", "", 404}, // /orders/{id} — «mening buyurtmam»: admin uchun ham
	{"dilnoza", "POST", "/admin/products", productBody, 403},
	{"jasur", "GET", "/admin/users", "", 403},
	{"dilnoza", "GET", "/admin/yoq", "", 403}, // yoʻq admin yoʻli ham 403: ichida nima borligi bilinmaydi
	{"admin", "GET", "/admin/yoq", "", 404},
	{"admin", "GET", "/admin/users", "", 200},
	{"admin", "POST", "/admin/products", productBody, 201},
	{"admin", "DELETE", "/admin/products/1", "", 409}, // olma buyurtmalarda bor
	// VAZIFA (TASK.md, 3-qadam): GET /orders va GET /admin/orders uchun qatorlar
}
```

Har qator — shu darsning bitta qoidasi. `{"anonim", "GET", "/orders/41", "", 401}` — «cookie'siz `GET /orders/41` — `401`». `{"jasur", "GET", "/orders/41", "", 404}` — begona buyurtma, `404`. `{"dilnoza", "POST", "/admin/products", productBody, 403}` — xaridor admin yoʻlida, `403`. `dilnoza … /orders/42` va `jasur … /orders/41` qatorlari — ikki xaridor: Dilnoza va Jasur bir-birining buyurtmasini soʻraydi. `{"admin", "DELETE", "/admin/products/1", "", 409}` — 1-mahsulot (`olma`) buyurtmalarda bor, shuning uchun oʻchirib boʻlmaydi: `409 Conflict`.

## Oʻzingizni tekshiring

1. Nega admin route'lari alohida mux'da?

<details>
<summary>Javob</summary>

Mux bir marta oʻralgan: `requireUser(requireAdmin(muxErrors(admin)))`. `/admin/` ostidagi har route — keyin qoʻshilgani ham — shu oʻramdan oʻtadi, shuning uchun yangi admin route'ni himoyasiz qoldirib boʻlmaydi. Har route alohida oʻralganda esa bittasini unutish mumkin edi (GB-6.06, OWASP API5).

</details>

2. Nega himoya testida ikki xaridor shart?

<details>
<summary>Javob</summary>

Begona buyurtmani soʻraydigan ikkinchi foydalanuvchi boʻlmasa, BOLA koʻrinmaydi: bitta foydalanuvchi oʻzinikini va yoʻq buyurtmani soʻraydi, begonasini hech kim soʻramaydi. Buzilgan store ham bunday testdan oʻtib ketadi.

</details>

3. (GB-6.05) Logout darhol ishlashi uchun bozor nimani tanladi va nega?

<details>
<summary>Javob</summary>

Session'ni. Logout bazadagi session qatorini oʻchiradi va eski cookie keyingi soʻrovda `401` oladi. JWT'da serverda yozuv yoʻq: u `exp` (muddat)gacha yaroqli qoladi, agar alohida denylist boʻlmasa.

</details>

4. Bashorat. Jadvalga qator qoʻshdik: `{"admin", "GET", "/orders/42", "", ?}`. 42-buyurtma Jasurniki. Qanday status kutiladi?

<details>
<summary>Javob</summary>

`404`. `/orders/{id}` — «mening buyurtmam»: egasi SQL shartida, admin uchun ham. 42-buyurtma admin'niki emas. Bu jadvaldagi `{"admin", "GET", "/orders/41", "", 404}` qatorining oʻzi, faqat boshqa ID bilan.

</details>

<summary>Yechim va izoh</summary>

Javob — `solution/` papkasida. Asosiy qismlari:

`internal/store/orders.go`: ikkala metod bitta yordamchiga tayanadi; farqi faqat `WHERE`da.

```go
func (s *Store) Orders(ctx context.Context, userID int64) ([]OrderSummary, error) {
	return s.summaries(ctx, `
		SELECT o.id, o.user_id, o.status, COALESCE(sum(i.quantity * i.unit_price), 0)::bigint
		FROM orders o
		LEFT JOIN order_items i ON i.order_id = o.id
		WHERE o.user_id = $1
		GROUP BY o.id
		ORDER BY o.id`, userID)
}
```

`LEFT JOIN` qatorsiz buyurtmani ham chiqaradi; `COALESCE(…, 0)` bunday buyurtmaning jamini `NULL` oʻrniga `0` qiladi (GB-5.04); `sum(bigint)` Postgres'da `numeric` qaytaradi, `::bigint` uni `int64`ga sigʻadigan turga qaytaradi. `summaries` ichida roʻyxat `[]OrderSummary{}` bilan boshlanadi: buyurtma boʻlmasa JSON'da `[]` chiqadi, `null` emas.

`cmd/api/handlers.go`:

```go
	mux.Handle("GET /orders", a.requireUser(http.HandlerFunc(a.listOrders)))
	…
	admin.HandleFunc("GET /admin/orders", a.allOrders)
```

`listOrders` egasini `currentUser(r).ID`dan oladi: mijoz uni yoʻlda ham, body'da ham bera olmaydi. `allOrders`da rol tekshiruvi yoʻq: uni admin mux bir marta oʻragan. Agar `GET /admin/orders`ni asosiy mux'ga qoʻysangiz, oʻram yoʻq va Dilnoza `403` oʻrniga `200` koʻradi — test shuni ushlaydi.
