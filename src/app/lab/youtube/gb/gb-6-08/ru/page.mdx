## Что вы узнаете

В модуле 6 в bozor добавили пять правил: пароль, сессия, владелец заказа, роль админа и rate limit. Завтра кто-то добавит новый маршрут и нарушит одно из правил. Кто вам об этом скажет?

**Главная идея:** правило считается доказанным только тогда, когда его проверили пользователем, который пытается его **нарушить**. Спецификация становится таблицей: «кто · запрос · ожидаемый статус». Каждая строка отправляется через всю цепочку middleware на настоящем Postgres. В таблице **два покупателя**: один просит заказ другого. Тест с одним пользователем никогда не просит чужой заказ, поэтому не видит BOLA.

К концу урока вы:

- прочитаете спецификацию защищённого bozor и увидите её в одной полной сессии `curl`: `401`, `403`, `404` и `429`;
- запишете правила в таблицу `rule{who, method, path, body, want}` и докажете их через `go test` на настоящем Postgres;
- своими глазами увидите, что тест с одним пользователем проходит и на коде с BOLA, а таблица с двумя покупателями его ловит;
- напишете маршруты `GET /orders` и `GET /admin/orders` и добавите их строки в таблицу.

| Слово | Простой смысл | По-английски |
|---|---|---|
| таблица доступа | спецификация в виде таблицы: каждая строка — кто, какой запрос, ожидаемый статус | access table |
| одна обёртка | все маршруты под `/admin/` лежат в одном mux, а mux обёрнут один раз: забыть нельзя | one wrap for a route group |
| тест с двумя пользователями | тест, где второй покупатель просит чужой объект | two-user test |

Вспомогательные слова объясняются на месте: функция Postgres `left(текст, n)` и регулярное выражение в `go test -run` (`|`, `$`).

## Спецификация: кто что может

Чтобы доказать правило, его сначала нужно чётко записать. Спецификация защищённого bozor — три группы и ещё три правила:

```text
открытые     GET /products, GET /products/{id}
             POST /users · POST /login · POST /logout
нужен login  GET /me · POST /orders
             GET, PATCH /orders/{id}            нет сессии → 401
             чужой заказ = нет заказа           → 404
админ        GET /admin/users · POST /admin/products
             DELETE /admin/products/{id}        покупателю → 403
```

| Группа | Кто входит | Если нельзя | Какой урок |
|---|---|---|---|
| открытые | все: каталог, регистрация, login, logout | — | GB-5.10, GB-6.03, GB-6.04 |
| нужен login | пользователь с сессией: заказы и `GET /me` | `401 Unauthorized`: неизвестно, кто вы | GB-6.04 |
| заказ | только владелец: `WHERE id = $1 AND user_id = $2` | `404 Not Found`: чужой заказ неотличим от несуществующего | GB-6.06 |
| админ | роль `admin`: пользователи и изменение каталога | `403 Forbidden`: вы известны, но роли не хватает | GB-6.06 |

На чужой заказ отвечают `404`, а не `403`: `403` говорит «такой заказ есть, но он не ваш». RFC 9110 §15.5.4 это разрешает: сервер, который хочет скрыть существование ресурса, **может** ответить `404` вместо `403`.

Ещё три правила:

- **Пароль** в базе никогда не лежит открытым текстом: только строка argon2id из GB-6.03.
- **Лимит на login**: 5 попыток с одного IP, 10 попыток на один email. Дальше `429 Too Many Requests` и заголовок `Retry-After`.
- **Каждый ответ с ошибкой** — в формате `application/problem+json` из GB-6.02.

## Цепочка middleware снаружи внутрь

`newHandler` (`cmd/api/middleware.go`) пропускает каждый запрос через эти слои. Каждый слой оборачивает следующий: внешний видит запрос первым.

```go
func newHandler(st *store.Store) http.Handler {
	return requestID(
		logRequests(
			recoverPanic(
				cors(
					protectCSRF(
						muxErrors(newMux(st)))))))
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1 | `func newHandler(st *store.Store) http.Handler {` | собирает один handler для всего API (GB-6.01) |
| 2 | `requestID(` | выдаёт каждому запросу `X-Request-Id` (GB-6.01) |
| 3 | `logRequests(` | пишет строку лога на каждый запрос (GB-6.01) |
| 4 | `recoverPanic(` | превращает panic в ответ `500` (GB-6.01) |
| 5 | `cors(` | добавляет заголовки CORS (GB-6.07) |
| 6 | `protectCSRF(` | отвечает `403` на изменяющий запрос с чужого origin (GB-6.07) |
| 7 | `muxErrors(newMux(st))` | отдаёт собственные `404` и `405` mux в виде problem (GB-6.01); `newMux` создаёт маршруты |

Много `)` в конце — закрытие семи открытых скобок. Запрос идёт внутрь от `requestID` к `muxErrors`, ответ возвращается обратным путём.

У маршрутов есть и собственные слои. Это кусок `newMux` (`cmd/api/handlers.go`, строки 35–48):

```go
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", healthHandler)
	mux.HandleFunc("GET /products", a.listProducts)
	mux.HandleFunc("GET /products/{id}", a.getProduct)
	mux.Handle("POST /users", requireJSON(http.HandlerFunc(a.register))) // GB-6.03
	mux.Handle("POST /login", a.loginIP.limitByIP(requireJSON(http.HandlerFunc(a.login))))
	mux.HandleFunc("POST /logout", a.logout) // requireUser'siz: eskirgan cookie ham tozalansin (GB-6.04)

	mux.Handle("GET /me", a.requireUser(http.HandlerFunc(a.me)))
	mux.Handle("POST /logout-all", a.requireUser(http.HandlerFunc(a.logoutAll)))
	// VAZIFA (TASK.md, 2-qadam): GET /orders — faqat oʻz buyurtmalari (requireUser bilan)
	mux.Handle("POST /orders", a.requireUser(requireJSON(http.HandlerFunc(a.createOrder))))
	mux.Handle("GET /orders/{id}", a.requireUser(http.HandlerFunc(a.getOrder)))
	mux.Handle("PATCH /orders/{id}", a.requireUser(requireJSON(http.HandlerFunc(a.updateNote))))
```

| Строка | Что делает |
|---|---|
| 1 | `mux := http.NewServeMux()` — таблица «путь → handler» (GB-4.04) |
| 2–4 | `GET /health`, `GET /products`, `GET /products/{id}`: без обёрток, открыты |
| 5 | `POST /users` — регистрация: открыта, только `requireJSON` (`415` на body не в JSON, GB-6.01) |
| 6 | `POST /login` — `limitByIP` (GB-6.07) оборачивает `requireJSON`: лимит самый первый |
| 7 | `POST /logout` — без `requireUser`: чтобы очищалась и устаревшая cookie (GB-6.04) |
| 9–10 | `GET /me`, `POST /logout-all` — с `requireUser`: без сессии `401` |
| 11 | комментарий к заданию: `GET /orders` добавится сюда |
| 12–14 | маршруты заказов с `requireUser`; в `PATCH` `requireJSON` стоит **внутри**: сначала кто вы (`401`), потом body (`415`) |

## Маршруты админа: один mux, одна обёртка

В GB-6.06 каждый маршрут админа оборачивался отдельно. Забыли один — и обычный покупатель заходит: это OWASP API5:2023 (BFLA). OWASP советует единый модуль авторизации, который легко проверить, и запрет всего по умолчанию. Решение на сегодня: маршруты админа лежат в **отдельном mux**, а mux оборачивается **один раз**.

```go
	admin := http.NewServeMux()
	admin.HandleFunc("GET /admin/users", a.listUsers)
	// VAZIFA (TASK.md, 2-qadam): GET /admin/orders — hamma buyurtmalar
	admin.Handle("POST /admin/products", requireJSON(http.HandlerFunc(a.createProduct)))
	admin.HandleFunc("DELETE /admin/products/{id}", a.deleteProduct)
	mux.Handle("/admin/",
		a.requireUser(requireAdmin(muxErrors(admin))))
```

| Строка | Что делает |
|---|---|
| 1 | `admin := http.NewServeMux()` — ещё одна таблица «путь → handler», только для админа |
| 2 | `GET /admin/users` — путь записывается полностью: путь в запросе не меняется |
| 3 | комментарий к заданию: `GET /admin/orders` добавится сюда |
| 4 | `POST /admin/products` — запись в каталог теперь здесь (переехала с `POST /products`); с `requireJSON` |
| 5 | `DELETE /admin/products/{id}` — удаление товара, `{id}` — GB-4.05 |
| 6–7 | подключает admin mux к основному и оборачивает его: `requireUser`, внутри `requireAdmin`, внутри `muxErrors` и admin mux |

Pattern `"/admin/"` заканчивается слэшем и без метода. Оба свойства описаны в документации [`net/http.ServeMux`](https://pkg.go.dev/net/http#ServeMux): pattern со слэшем на конце подходит ко **всем** путям под ним, pattern без метода — к **любому** методу. Значит, каждый запрос под `/admin/` — нынешний и будущий, существующий и несуществующий — сначала проходит две обёртки:

```text
GET /admin/…  →  requireUser  →  requireAdmin  →  muxErrors  →  admin mux
                 нет сессии      роль покупателя   ответы         handler или
                 → 401           → 403             admin mux      404 / 405
```

Любой новый маршрут, добавленный в admin mux, защищён сам: обёртку писать не нужно, забыть её нельзя. Внешний `muxErrors` находит pattern `/admin/`, поэтому для собственных `404` и `405` внутреннего mux нужен отдельный `muxErrors(admin)`.

### 2. Регистрация: роль выдаёт база

Во втором терминале новый пользователь Азиза регистрируется: `POST /users`, email и пароль не короче 15 символов (GB-6.03):

```console
$ curl -i localhost:8765/users -H "Content-Type: application/json" -d '{"email":"aziza@bozor.test","password":"anor-behi-yongoq-uzum-5"}'
HTTP/1.1 201 Created
Content-Type: application/json
Vary: Origin
X-Request-Id: GVAN7GMVLZRFTRELEHFJ4H7PG6
Date: Sat, 28 Nov 2026 09:43:17 GMT
Content-Length: 53

{"id":4,"email":"aziza@bozor.test","role":"xaridor"}
```

Первая строка — `201 Created`. В теле — `id` нового пользователя, 4, и `"role":"xaridor"` (`xaridor` — «покупатель»). Роль клиент не присылает: это значение колонки по умолчанию в базе (GB-6.06, наименьшие привилегии).

### 3. Что лежит в базе

Пароль не должен лежать в базе открытым. Проверяем: `psql -c` выполняет одну SQL-команду, а функция Postgres `left(текст, n)` берёт первые `n` символов текста. Здесь это первые 31 символ `password_hash`:

```console
$ docker compose exec db psql -c "SELECT id, email, left(password_hash, 31) FROM users WHERE id = 4"
 id |      email       |              left
----+------------------+---------------------------------
  4 | aziza@bozor.test | $argon2id$v=19$m=47104,t=1,p=1$
(1 row)
```

Первые 31 символ: `$argon2id$` (алгоритм), `v=19$` (версия), `m=47104,` (память, КиБ), `t=1,` (число проходов), `p=1$` (параллелизм). Самого пароля нигде нет; остальное — соль и ключ — в следующих символах, мы их не показываем (GB-6.03).

### 4. Login, чужой заказ и путь админа

Азиза входит. `-c aziza.txt` (cookie jar) записывает cookie, которую выдал сервер, в файл `aziza.txt`:

```console
$ curl -s -c aziza.txt localhost:8765/login -H "Content-Type: application/json" -d '{"email":"aziza@bozor.test","password":"anor-behi-yongoq-uzum-5"}'
{"id":4,"email":"aziza@bozor.test","role":"xaridor"}
```

Теперь заказ 41 Дилнозы. `-b aziza.txt` читает cookie из файла и добавляет её в запрос:

```console
$ curl -i -b aziza.txt localhost:8765/orders/41
HTTP/1.1 404 Not Found
Cache-Control: no-store
Content-Type: application/problem+json
Vary: Origin
X-Request-Id: VYB4UICCKXU5IOQQISOJJUHOBE
Date: Sat, 28 Nov 2026 09:43:17 GMT
Content-Length: 131

{"type":"about:blank","title":"Not Found","status":404,"detail":"bunday buyurtma yoʻq","request_id":"VYB4UICCKXU5IOQQISOJJUHOBE"}
```

`404 Not Found`, `detail` — «нет такого заказа» (`bunday buyurtma yoʻq`). Несуществующий заказ (например, `/orders/999`) получает именно этот текст: Азиза не может узнать, существует ли заказ 41. Теперь Азиза пытается добавить товар по пути админа:

```console
$ curl -i -b aziza.txt localhost:8765/admin/products -H "Content-Type: application/json" -d '{"name":"anor","price":1800000,"stock":5}'
HTTP/1.1 403 Forbidden
Cache-Control: no-store
Content-Type: application/problem+json
Vary: Origin
X-Request-Id: 7SD2LKSDG4XJ7DOSAFAO3NLPI3
Date: Sat, 28 Nov 2026 09:43:17 GMT
Content-Length: 136

{"type":"about:blank","title":"Forbidden","status":403,"detail":"bu amal uchun ruxsat yoʻq","request_id":"7SD2LKSDG4XJ7DOSAFAO3NLPI3"}
```

### Предсказание: путь админа, которого нет

### 7. Лимит на login

Последнее правило. Шесть login в одной строке: пять неверных паролей, шестой — верный пароль Азизы. В терминале это одна строка; здесь она разбита, чтобы читалось:

```bash
for p in x1 x2 x3 x4 x5 anor-behi-yongoq-uzum-5; do
  curl -s -o /dev/null -w "%{http_code} " localhost:8765/login \
    -H "Content-Type: application/json" \
    -d '{"email":"aziza@bozor.test","password":"'$p'"}'
done; echo
```

| Строка | Код | Что делает |
|---|---|---|
| 1 | `for p in … ; do` | переменная `p` по очереди принимает `x1` … `x5`, затем верный пароль: шесть оборотов |
| 2 | `curl -s -o /dev/null -w "%{http_code} " …` | `-o /dev/null` выбрасывает тело, `-w` печатает только код статуса и пробел; `\` в конце строки продолжает команду на следующей |
| 3 | `-H "Content-Type: application/json" \` | сообщает, что это JSON |
| 4 | `-d '{"email":…,"password":"'$p'"}'` | `'$p'` подставляет `p` внутрь JSON: часть в кавычках закрывается, `$p` раскрывается, снова начинается часть в кавычках |
| 5 | `done; echo` | цикл закончился; `echo` печатает в конце перевод строки |

### Предсказание: шестая попытка

С login Азизы прошло больше 12 секунд: корзина снова полна (5 токенов, по одному добавляется каждые 12 секунд, GB-6.07). Пять раз неверный пароль, шестой раз — верный. Каким будет шестой ответ? **A)** `200`: пароль верный · **B)** `401`: все · **C)** `429`: слишком много попыток.

<details>
<summary>Ответ</summary>

**C.** Пять попыток забрали пять токенов; на шестую токена не осталось, поэтому сервер даже не проверяет пароль. Лимит не знает, верен пароль или нет: он считает попытки. Выбравшие A решили, что верный пароль важнее всего; выбравшие B забыли про лимит.

</details>

```console
$ for p in x1 x2 x3 x4 x5 anor-behi-yongoq-uzum-5; do curl -s -o /dev/null -w "%{http_code} " localhost:8765/login -H "Content-Type: application/json" -d '{"email":"aziza@bozor.test","password":"'$p'"}'; done; echo
401 401 401 401 401 429

Пять `401`, затем `429`. Посмотрим шестой ответ целиком:

`429 Too Many Requests`, `Content-Type: application/problem+json` (GB-6.02) и `Retry-After: 12`: через 12 секунд откроется ещё одна попытка. Остановлен и верный пароль: иначе атакующий увидел бы разницу между `401` и `200` и продолжил бы подбор. В цифрах: с одного IP 5 попыток, потом по одной каждые 12 секунд; на один email 10 попыток, потом по одной в минуту. Лимит на email работает, даже если атакующий меняет IP: после первых 10 попыток на один аккаунт нельзя подбирать больше одного пароля в минуту.

### Вопрос: админ и чужой заказ

Админ входит и отправляет `GET /orders/41`: это заказ Дилнозы. Какой будет ответ? **A)** `200`: админ видит всё · **B)** `403`: неподходящая роль · **C)** `404`: заказ не его.

<summary>Ответ</summary>

Это и есть сегодняшнее задание.

</details>

func TestPasswordNotStored(t *testing.T) {

	if rec.Code != http.StatusCreated || strings.Contains(rec.Body.String(), "argon2id") {
		t.Fatalf("POST /users: %d %s; kutilgan 201, javobda hash yoʻq", rec.Code, rec.Body)
	}
	var hash string

		"SELECT password_hash FROM users WHERE email = $1", "aziza@bozor.test").Scan(&hash)
	if err != nil {
		t.Fatalf("users qatori oʻqilmadi: %v", err)
	}
	if strings.Contains(hash, pw) || !strings.HasPrefix(hash, "$argon2id$") {
		t.Errorf("password_hash = %q: parol ochiq turibdi yoki argon2id emas", hash)

| Строка | Что делает |
|---|---|
| 2 | `h, pool := testAPI(t)` — теперь нужно и второе значение: `pool` (пул соединений) подключён прямо к базе |
| 3 | `const pw = "…"` — пароль Азизы (GB-1.03) |
| 4 | записывает Азизу через `POST /users`; JSON собирают строка в обратных кавычках и `+pw+` (GB-3.02) |

	err := s.pool.QueryRow(ctx, `
		SELECT user_id, status, note FROM orders
		WHERE id = $1
		  AND user_id = $2`,
		id, userID).Scan(&o.UserID, &o.Status, &note)
```

Сломанная версия (`_video/stages/bola/orders.go`):

Владелец больше не проверяется: строка находится, чей бы ни был `id`. В копии папки урока подменяем так (верный файл сохраняется в `orders.fixed`):

**Предсказание.** Что скажет тест с одним пользователем на сломанном store? **A)** FAIL: 41 окажется чужим · **B)** ok: тест проходит · **C)** FAIL: 999 → `200`.

<details>
<summary>Ответ</summary>

**B.** Тест просит три вещи: свой заказ Дилнозы (41), несуществующий заказ (999) и запрос без cookie. На сломанном store все три отрабатывают верно: 41 действительно принадлежит Дилнозе, 999 нет в базе, запрос без cookie останавливает `requireUser`. Выбравшие A решили, что 41 окажется «чужим», но тест просит от имени Дилнозы — 41 её. C: 999 нет в базе, и без условия владельца строка не найдётся.

</details>

| Дилноза | 999 (нет такого) | `404` ✓ | — |
| аноним | 41 | `401` ✓ | `401` ✓ |
| Дилноза | 42 (Жасура) | **никто не просит** | ожидалось `404`, пришло `200` ✗ |
| Жасур | 41 (Дилнозы) | **никто не просит** | ожидалось `404`, пришло `200` ✗ |

## Проверьте себя

1. Почему маршруты админа лежат в отдельном mux?

<details>
<summary>Ответ</summary>

Mux обёрнут один раз: `requireUser(requireAdmin(muxErrors(admin)))`. Каждый маршрут под `/admin/` — в том числе добавленный позже — проходит эту обёртку, поэтому новый маршрут админа нельзя оставить без защиты. Когда каждый маршрут оборачивался отдельно, один можно было забыть (GB-6.06, OWASP API5).

</details>

2. Почему в тесте защиты обязательны два покупателя?

<details>
<summary>Ответ</summary>

Без второго пользователя, который просит чужой заказ, BOLA не видна: один пользователь просит свой заказ и несуществующий, чужой не просит никто. Даже сломанный store проходит такой тест.

</details>

3. (GB-6.05) Что выбрал bozor, чтобы logout действовал сразу, и почему?

<details>
<summary>Ответ</summary>

Сессию. Logout удаляет строку сессии в базе, и старая cookie на следующем запросе получает `401`. У JWT записи на сервере нет: он действителен до `exp` (срока), если нет отдельного denylist.

</details>

4. Предсказание. В таблицу добавили строку `{"admin", "GET", "/orders/42", "", ?}`. Заказ 42 принадлежит Жасуру. Какой статус ожидается?

<details>
<summary>Ответ</summary>

`404`. `/orders/{id}` — «мой заказ»: владелец проверяется в SQL, и для админа тоже. Заказ 42 админу не принадлежит. Это та же строка, что `{"admin", "GET", "/orders/41", "", 404}` в таблице, только с другим ID.

</details>

5. Предсказание. Что выведет `go test -run 'TestAccess' ./cmd/api` (без `$`) на starter? **A)** всё ok · **B)** FAIL, потому что падает `TestAccess` · **C)** FAIL, но падает другой тест.

<summary>Решение и пояснение</summary>

Ответ лежит в папке `solution/`. Главные части:

`internal/store/orders.go`: оба метода опираются на один вспомогательный; разница только в `WHERE`.

```go
func (s *Store) Orders(ctx context.Context, userID int64) ([]OrderSummary, error) {
	return s.summaries(ctx, `
		SELECT o.id, o.user_id, o.status, COALESCE(sum(i.quantity * i.unit_price), 0)::bigint
		FROM orders o
		LEFT JOIN order_items i ON i.order_id = o.id
		WHERE o.user_id = $1
		GROUP BY o.id
		ORDER BY o.id`, userID)
}
```

`LEFT JOIN` выводит и заказ без строк; `COALESCE(…, 0)` делает сумму такого заказа `0`, а не `NULL` (GB-5.04); `sum(bigint)` в Postgres возвращает `numeric`, а `::bigint` возвращает тип, помещающийся в `int64`. Внутри `summaries` список начинается с `[]OrderSummary{}`: если заказов нет, в JSON будет `[]`, а не `null`.

`cmd/api/handlers.go`:

```go
	mux.Handle("GET /orders", a.requireUser(http.HandlerFunc(a.listOrders)))
	…
	admin.HandleFunc("GET /admin/orders", a.allOrders)
```

`listOrders` берёт владельца из `currentUser(r).ID`: клиент не может передать его ни в пути, ни в body. В `allOrders` проверки роли нет: admin mux уже обернул его один раз. Если поставить `GET /admin/orders` в основной mux, обёртки не будет, и Дилноза увидит `200` вместо `403` — тест это поймает.

Три новые строки в `cmd/api/himoya_test.go`:

	{"anonim", "GET", "/admin/orders", "", 401},
	{"jasur", "GET", "/admin/orders", "", 403},
