## What you will learn

Module 6 added five rules to bozor: the password, the session, the order owner, the admin role and the rate limit. Tomorrow someone adds a new route and breaks one rule. Who tells you?

**The one idea:** a rule counts as proven only when a user who tries to **break** it has tested it. The specification becomes a table: "who · request · expected status". Every row is sent through the whole middleware chain on real Postgres. The table has **two buyers**: one asks for the other's order. A test with one user never asks for someone else's order, so it cannot see BOLA.

By the end of the lesson you will:

- read the specification of the protected bozor and see it in one full `curl` session: `401`, `403`, `404` and `429`;
- write the rules as a `rule{who, method, path, body, want}` table and prove them with `go test` on real Postgres;
- see for yourself that a one-user test passes even on code with BOLA, while a two-buyer table catches it;
- write the routes `GET /orders` and `GET /admin/orders` and add their rows to the table.

| Word | Plain meaning | English term |
|---|---|---|
| access table | the specification as a table: each row is who, which request, expected status | access table |
| one wrap | every route under `/admin/` lives in one mux, and the mux is wrapped once: nothing to forget | one wrap for a route group |
| two-user test | a test where a second buyer asks for an object that is not theirs | two-user test |

Helper words are explained where they appear: the Postgres function `left(text, n)` and the regular expression in `go test -run` (`|`, `$`).

## The specification: who can do what

To prove a rule you first have to write it down exactly. The specification of the protected bozor is three groups and three more rules:

```text
open         GET /products, GET /products/{id}
             POST /users · POST /login · POST /logout
login needed GET /me · POST /orders
             GET, PATCH /orders/{id}            no session → 401
             someone else's order = no order    → 404
admin        GET /admin/users · POST /admin/products
             DELETE /admin/products/{id}        for a buyer → 403
```

| Group | Who gets in | If not | Which lesson |
|---|---|---|---|
| open | everyone: catalog, registration, login, logout | — | GB-5.10, GB-6.03, GB-6.04 |
| login needed | a user with a session: orders and `GET /me` | `401 Unauthorized`: it is not known who you are | GB-6.04 |
| order | the owner only: `WHERE id = $1 AND user_id = $2` | `404 Not Found`: someone else's order looks the same as a missing one | GB-6.06 |
| admin | the `admin` role: users and catalog changes | `403 Forbidden`: you are known, but your role is not enough | GB-6.06 |

Someone else's order gets `404`, not `403`: `403` says "such an order exists, but it is not yours". RFC 9110 §15.5.4 allows this: a server that wants to hide the existence of a resource **may** answer `404` instead of `403`.

Three more rules:

- **The password** never sits in the database as plain text: only the argon2id string from GB-6.03.
- **Login limit**: 5 attempts from one IP, 10 attempts for one email. After that, `429 Too Many Requests` and a `Retry-After` header.
- **Every error response** has the `application/problem+json` shape from GB-6.02.

## The middleware chain, outside in

`newHandler` (`cmd/api/middleware.go`) passes every request through these layers. Each layer wraps the next: the outer layer sees the request first.

```go
func newHandler(st *store.Store) http.Handler {
	return requestID(
		logRequests(
			recoverPanic(
				cors(
					protectCSRF(
						muxErrors(newMux(st)))))))
}
```

| Line | Code | What it does |
|---|---|---|
| 1 | `func newHandler(st *store.Store) http.Handler {` | builds the one handler for the whole API (GB-6.01) |
| 2 | `requestID(` | gives each request an `X-Request-Id` (GB-6.01) |
| 3 | `logRequests(` | writes a log line for each request (GB-6.01) |
| 4 | `recoverPanic(` | turns a panic into a `500` response (GB-6.01) |
| 5 | `cors(` | adds the CORS headers (GB-6.07) |
| 6 | `protectCSRF(` | answers `403` to a state-changing request from a foreign origin (GB-6.07) |
| 7 | `muxErrors(newMux(st))` | turns the mux's own `404` and `405` into problem responses (GB-6.01); `newMux` builds the routes |

The many `)` at the end close the seven opened parentheses. A request goes inward from `requestID` to `muxErrors`; the response comes back the other way.

The routes have their own layers too. This is a piece of `newMux` (`cmd/api/handlers.go`, lines 35–48):

```go
	mux := http.NewServeMux()
	mux.HandleFunc("GET /health", healthHandler)
	mux.HandleFunc("GET /products", a.listProducts)
	mux.HandleFunc("GET /products/{id}", a.getProduct)
	mux.Handle("POST /users", requireJSON(http.HandlerFunc(a.register))) // GB-6.03
	mux.Handle("POST /login", a.loginIP.limitByIP(requireJSON(http.HandlerFunc(a.login))))
	mux.HandleFunc("POST /logout", a.logout) // requireUser'siz: eskirgan cookie ham tozalansin (GB-6.04)

	mux.Handle("GET /me", a.requireUser(http.HandlerFunc(a.me)))
	mux.Handle("POST /logout-all", a.requireUser(http.HandlerFunc(a.logoutAll)))
	// VAZIFA (TASK.md, 2-qadam): GET /orders — faqat oʻz buyurtmalari (requireUser bilan)
	mux.Handle("POST /orders", a.requireUser(requireJSON(http.HandlerFunc(a.createOrder))))
	mux.Handle("GET /orders/{id}", a.requireUser(http.HandlerFunc(a.getOrder)))
	mux.Handle("PATCH /orders/{id}", a.requireUser(requireJSON(http.HandlerFunc(a.updateNote))))
```

| Line | What it does |
|---|---|
| 1 | `mux := http.NewServeMux()` — a table "path → handler" (GB-4.04) |
| 2–4 | `GET /health`, `GET /products`, `GET /products/{id}`: no wrapper, open |
| 5 | `POST /users` — registration: open, only `requireJSON` (`415` for a body that is not JSON, GB-6.01) |
| 6 | `POST /login` — `limitByIP` (GB-6.07) wraps `requireJSON`: the limit comes first |
| 7 | `POST /logout` — without `requireUser`, so that even a stale cookie gets cleared (GB-6.04) |
| 9–10 | `GET /me`, `POST /logout-all` — with `requireUser`: no session means `401` |
| 11 | the homework comment: `GET /orders` goes here |
| 12–14 | the order routes with `requireUser`; in `PATCH`, `requireJSON` is **inside**: first who you are (`401`), then the body (`415`) |

## Admin routes: one mux, one wrap

In GB-6.06 every admin route was wrapped separately. Forget one and an ordinary buyer gets in: this is OWASP API5:2023 (BFLA). OWASP recommends one authorization module that is easy to analyze, and denying everything by default. Today's solution: the admin routes live in a **separate mux**, and that mux is wrapped **once**.

```go
	admin := http.NewServeMux()
	admin.HandleFunc("GET /admin/users", a.listUsers)
	// VAZIFA (TASK.md, 2-qadam): GET /admin/orders — hamma buyurtmalar
	admin.Handle("POST /admin/products", requireJSON(http.HandlerFunc(a.createProduct)))
	admin.HandleFunc("DELETE /admin/products/{id}", a.deleteProduct)
	mux.Handle("/admin/",
		a.requireUser(requireAdmin(muxErrors(admin))))
```

| Line | What it does |
|---|---|
| 1 | `admin := http.NewServeMux()` — one more "path → handler" table, only for the admin |
| 2 | `GET /admin/users` — the path is written in full: the request path does not change |
| 3 | the homework comment: `GET /admin/orders` goes here |
| 4 | `POST /admin/products` — writing to the catalog now happens here (moved from `POST /products`); with `requireJSON` |
| 5 | `DELETE /admin/products/{id}` — deletes a product, `{id}` is from GB-4.05 |
| 6–7 | mounts the admin mux on the main mux and wraps it: `requireUser`, inside it `requireAdmin`, inside it `muxErrors` and the admin mux |

The pattern `"/admin/"` ends with a slash and has no method. Both properties are in the [`net/http.ServeMux`](https://pkg.go.dev/net/http#ServeMux) documentation: a pattern that ends in a slash matches **every** path under it, and a pattern without a method matches **every** method. So every request under `/admin/` — present or future, existing or not — passes the two wrappers first:

```text
GET /admin/…  →  requireUser  →  requireAdmin  →  muxErrors  →  admin mux
                 no session      buyer role        admin mux      handler or
                 → 401           → 403             responses      404 / 405
```

Any new route added to the admin mux is protected by itself: there is no wrapper to write and none to forget. The outer `muxErrors` finds the `/admin/` pattern, so the inner mux's own `404` and `405` need their own `muxErrors(admin)`.

### 3. What is in the database

The password must not sit in the database as plain text. We check: `psql -c` runs one SQL command, and the Postgres function `left(text, n)` takes the first `n` characters of the text. Here, the first 31 characters of `password_hash`:

```console
$ docker compose exec db psql -c "SELECT id, email, left(password_hash, 31) FROM users WHERE id = 4"
 id |      email       |              left
----+------------------+---------------------------------
  4 | aziza@bozor.test | $argon2id$v=19$m=47104,t=1,p=1$
(1 row)
```

The first 31 characters: `$argon2id$` (the algorithm), `v=19$` (the version), `m=47104,` (memory, KiB), `t=1,` (number of passes), `p=1$` (parallelism). The password itself is nowhere; the rest — the salt and the key — is in the following characters, and we do not print them (GB-6.03).

### 7. The login limit

The last rule. Six logins in one line: five wrong passwords, the sixth is Aziza's correct password. In a terminal this is one line; here it is split so that it reads well:

```bash
for p in x1 x2 x3 x4 x5 anor-behi-yongoq-uzum-5; do
  curl -s -o /dev/null -w "%{http_code} " localhost:8765/login \
    -H "Content-Type: application/json" \
    -d '{"email":"aziza@bozor.test","password":"'$p'"}'
done; echo
```

| Line | Code | What it does |
|---|---|---|
| 1 | `for p in … ; do` | the variable `p` takes `x1` … `x5` in turn, then the correct password: six rounds |
| 2 | `curl -s -o /dev/null -w "%{http_code} " …` | `-o /dev/null` throws the body away, `-w` prints only the status code and a space; the `\` at the end of the line continues the command on the next line |
| 3 | `-H "Content-Type: application/json" \` | says that this is JSON |
| 4 | `-d '{"email":…,"password":"'$p'"}'` | `'$p'` puts `p` inside the JSON: the quoted part closes, `$p` is expanded, a quoted part starts again |
| 5 | `done; echo` | the loop is over; `echo` prints a newline at the end |

### Predict: the sixth attempt

More than 12 seconds have passed since Aziza's login: the bucket is full again (5 tokens, one is added every 12 seconds, GB-6.07). Five wrong passwords, and the sixth with the correct password. What is the sixth response? **A)** `200`: the password is correct · **B)** `401`: all of them · **C)** `429`: too many attempts.

<details>
<summary>Answer</summary>

**C.** Five attempts took five tokens; no token is left for the sixth, so the server does not even check the password. The limit does not know whether the password is right: it counts attempts. If you chose A, you thought a correct password beats everything; if you chose B, you forgot the limit.

</details>

```console
$ for p in x1 x2 x3 x4 x5 anor-behi-yongoq-uzum-5; do curl -s -o /dev/null -w "%{http_code} " localhost:8765/login -H "Content-Type: application/json" -d '{"email":"aziza@bozor.test","password":"'$p'"}'; done; echo
401 401 401 401 401 429
```

Date: Sat, 28 Nov 2026 09:43:30 GMT
Content-Length: 166

{"type":"about:blank","title":"Too Many Requests","status":429,"detail":"urinishlar koʻp: keyinroq qayta urinib koʻring","request_id":"PTMASP33DYC6MG2AABT4RKPXTS"}
```

`429 Too Many Requests`, `Content-Type: application/problem+json` (GB-6.02) and `Retry-After: 12`: in 12 seconds one more attempt opens. The correct password is stopped too: otherwise an attacker would see the difference between `401` and `200` and keep guessing. In numbers: from one IP, 5 attempts, then one every 12 seconds; for one email, 10 attempts, then one per minute. The email limit works even if the attacker changes IP: after the first 10 attempts, one account cannot be guessed at more than once per minute.

### Question: the admin and someone else's order

The admin logs in and sends `GET /orders/41`: this is Dilnoza's order. What is the response? **A)** `200`: the admin sees everything · **B)** `403`: wrong role · **C)** `404`: the order is not theirs.

<details>
<summary>Answer</summary>

**C.** `GET /orders/{id}` means "my order": the query has a `user_id` condition, for the admin too. The order does not belong to the admin, so it "does not exist". If you chose A, you thought the role opens everything; if you chose B, you assumed this route checks the role: it does not look at the role. We need a separate path where the admin sees all orders: `GET /admin/orders`. That is today's homework.

</details>

## The tests: proof of the rules

The rules are visible. But if someone adds a new route tomorrow and breaks one, `curl` will not tell you. A test will. The tests are in `cmd/api/himoya_test.go`; they have no mocks: each test runs in its own schema on real Postgres (`internal/pgtest`, GB-5.10).

|---|---|---|

| 9 | `type rule struct {` | `rule` — a struct that describes one row of the table (GB-2.03) |
| 10 | `who string` | who: `"anonim"` (anonymous, no cookie), `"dilnoza"`, `"jasur"` or `"admin"` |

func TestAccess(t *testing.T) {

		"anonim":  "",

		if rec.Code != r.want {
			t.Errorf("%s %s %s: %d, kutilgan %d", r.who, r.method, r.path, rec.Code, r.want)
		}
	}

```

|---|---|---|
| 1 | `func TestAccess(t *testing.T) {` | the test function (GB-1.08) |
| 2 | `h, _ := testAPI(t)` | a fresh schema and the **whole chain**: `h` is `newHandler` (GB-5.10); the second value (`pool`) is not needed in this test, and `_` discards it |
| 3–8 | `cookies := map[string]string{ … }` | a `map`: the key is the user, the value is their session cookie (GB-2.02) |

| 9 | `for _, r := range accessRules {` | for every row of the table |
| 10 | `rec := send(h, r.method, r.path, r.body, cookies[r.who])` | sends the request into the chain; the cookie comes from the map by `r.who` (GB-5.10) |
| 11 | `if rec.Code != r.want {` | if the status is not what was expected… |
| 12 | `t.Errorf(…)` | …records an error, but the test **goes on**: the following rows are checked too, so all errors show up in one run |

### The password test

```go
func TestPasswordNotStored(t *testing.T) {
	h, pool := testAPI(t)
	const pw = "anor-behi-yongoq-uzum-5"
	rec := send(h, "POST", "/users", `{"email":"aziza@bozor.test","password":"`+pw+`"}`, "")
	if rec.Code != http.StatusCreated || strings.Contains(rec.Body.String(), "argon2id") {
		t.Fatalf("POST /users: %d %s; kutilgan 201, javobda hash yoʻq", rec.Code, rec.Body)
	}
	var hash string
	err := pool.QueryRow(context.Background(),
		"SELECT password_hash FROM users WHERE email = $1", "aziza@bozor.test").Scan(&hash)
	if err != nil {
		t.Fatalf("users qatori oʻqilmadi: %v", err)
	}
	if strings.Contains(hash, pw) || !strings.HasPrefix(hash, "$argon2id$") {
		t.Errorf("password_hash = %q: parol ochiq turibdi yoki argon2id emas", hash)
	}
	login(t, h, `{"email":"aziza@bozor.test","password":"`+pw+`"}`) // hash'dan parolni tekshirish ishlaydi
}
```

| Line | What it does |
|---|---|
| 2 | `h, pool := testAPI(t)` — now the second value is needed too: `pool` (a connection pool) is connected straight to the database |
| 3 | `const pw = "…"` — Aziza's password (GB-1.03) |
| 4 | registers Aziza with `POST /users`; the JSON is assembled from a backtick string and `+pw+` (GB-3.02) |
| 5–7 | if the status is not `201` or the response contains `argon2id` (a hash) — `t.Fatalf`: the test stops here, because the next step depends on this |
| 8–13 | `var hash string`, then `pool.QueryRow(…).Scan(&hash)` reads `password_hash` from the database; if that fails — `t.Fatalf` again (GB-5.05) |
| 14–16 | `strings.Contains(hash, pw)` — is the password inside the hash; `!strings.HasPrefix(hash, "$argon2id$")` — does the string fail to start with argon2id (GB-3.01). If either is true — `t.Errorf` |
| 17 | `login(…)`: login with this password works, so the password is checked against the hash |

Without this test, if someone removes the `Hash` call, the API keeps working, but the password reaches the database as plain text and no error is visible.

## Common mistakes

**The most common mistake is writing the protection test with one user.** Such a test is green while the code has a hole.

`TestOrdersOneUser` uses only Dilnoza: her own order gives `200`, a missing order gives `404`, no cookie gives `401`. This file is not in the lesson folder: a wrong test must not live in the starter. It is under `_video/stages/bola/`:

## Check yourself

1. Why are the admin routes in a separate mux?

<details>
<summary>Answer</summary>

The mux is wrapped once: `requireUser(requireAdmin(muxErrors(admin)))`. Every route under `/admin/` — including one added later — passes this wrapper, so a new admin route cannot be left unprotected. When each route was wrapped separately, one could be forgotten (GB-6.06, OWASP API5).

</details>

2. Why does the protection test need two buyers?

<details>
<summary>Answer</summary>

Without a second user who asks for someone else's order, BOLA is invisible: one user asks for their own order and for a missing one, and nobody asks for someone else's. Even a broken store passes such a test.

</details>

3. (GB-6.05) What did bozor choose so that logout works immediately, and why?

<details>
<summary>Answer</summary>

The session. Logout deletes the session row in the database, and the old cookie gets `401` on the next request. A JWT has no record on the server: it stays valid until `exp` (the expiry time), unless there is a separate denylist.

</details>

4. Predict. We add the row `{"admin", "GET", "/orders/42", "", ?}` to the table. Order 42 belongs to Jasur. What status is expected?

<details>
<summary>Answer</summary>

`404`. `/orders/{id}` means "my order": the owner is checked in SQL, for the admin too. Order 42 does not belong to the admin. This is the same row as `{"admin", "GET", "/orders/41", "", 404}` in the table, only with another ID.

</details>

The first three failures are `GET /orders`: `405 Method Not Allowed` (this path has only `POST` so far); then `GET /admin/orders` — `404` (the admin mux has no such route); the last one — the table is missing three rows. Work until everything is `ok`; when you finish, run `docker compose down -v`.

<details>
<summary>Solution and explanation</summary>

The answer is in the `solution/` folder. The main parts:

`internal/store/orders.go`: both methods rely on one helper; the difference is only in `WHERE`.

```go
func (s *Store) Orders(ctx context.Context, userID int64) ([]OrderSummary, error) {
	return s.summaries(ctx, `
		SELECT o.id, o.user_id, o.status, COALESCE(sum(i.quantity * i.unit_price), 0)::bigint
		FROM orders o
		LEFT JOIN order_items i ON i.order_id = o.id
		WHERE o.user_id = $1
		GROUP BY o.id
		ORDER BY o.id`, userID)
}
```

`LEFT JOIN` also returns an order with no items; `COALESCE(…, 0)` makes the total of such an order `0` instead of `NULL` (GB-5.04); `sum(bigint)` returns `numeric` in Postgres, and `::bigint` turns it back into a type that fits `int64`. Inside `summaries` the list starts as `[]OrderSummary{}`: with no orders the JSON is `[]`, not `null`.

`cmd/api/handlers.go`:

```go
	mux.Handle("GET /orders", a.requireUser(http.HandlerFunc(a.listOrders)))
	…
	admin.HandleFunc("GET /admin/orders", a.allOrders)
```

`listOrders` takes the owner from `currentUser(r).ID`: the client cannot give it in the path or in the body. `allOrders` has no role check: the admin mux already wraps it once. If you put `GET /admin/orders` on the main mux, there is no wrapper and Dilnoza sees `200` instead of `403` — the test catches that.

The three new rows in `cmd/api/himoya_test.go`:

```go
	{"anonim", "GET", "/orders", "", 401},
	{"anonim", "GET", "/admin/orders", "", 401},
	{"jasur", "GET", "/admin/orders", "", 403},
```
