## Что вы узнаете

Дилноза вошла в bozor. Потом на чужой странице на другом порту нажала кнопку «Sovgʻani olish» («Получить подарок»). Это нажатие отменило заказ 41 в bozor, хотя session cookie было `SameSite=Lax`. Почему защита не сработала?

**Одна идея:** браузер добавляет cookie к запросу **сам**, независимо от того, какая страница запрос начала. Атрибуты cookie управляют только тем, «когда добавлять», а `SameSite` смотрит на *site*: порт и поддомен site не меняют. Поэтому на запросе, меняющем состояние, сервер сам проверяет, **откуда** пришёл запрос. CORS управляет только тем, можно ли **прочитать** ответ: запрос всё равно выполняется. А login ограничивают числом попыток.

К концу урока вы:

- увидите в настоящем Chrome, что делает каждый атрибут `Set-Cookie` (`__Host-`, `Max-Age`, `HttpOnly`, `Secure`, `SameSite`);
- воспроизведёте отмену заказа Дилнозы обычной HTML-формой с другой страницы и превратите её в `403` с помощью `http.CrossOriginProtection`;
- настроите CORS через allow-list и `Vary: Origin` и своими глазами увидите ошибку «вернуть `Origin` без проверки»;
- поставите на `POST /login` token bucket лимит по IP (`429` и `Retry-After`), а второй, по email, напишете сами в домашнем задании.

| Слово | Простой смысл | По-английски |
|---|---|---|
| `SameSite` | атрибут: добавлять ли cookie к запросу, начатому с **другого site** | SameSite |
| CSRF | страница чужого сайта отправляет запрос через браузер пользователя, с его cookie | cross-site request forgery |
| token bucket | ограниченный запас токенов для каждого ключа (IP, email): каждая попытка забирает один | token bucket |

Два вспомогательных понятия: заголовки `Sec-Fetch-Site` и `Origin` (кто начал запрос) и **CORS** (правило браузера на чтение). Остальные слова объясняются там, где встречаются впервые.

Эта атака называется **CSRF** (cross-site request forgery): чужой сайт подделывает запрос через собственный браузер пользователя. Сегодня мы воспроизведём её и закроем. План: атрибуты cookie, проверка на сервере, откуда пришёл запрос, чем CORS не является и rate limit на login, то есть ограничение числа попыток.

## Атрибуты cookie: правила для браузера

Хранить cookie и решать, к какому запросу его добавить, будет браузер. Сервер задаёт ему правила только **атрибутами** в заголовке `Set-Cookie`. Посмотрим ответ на login целиком (`-i` выводит и заголовки ответа, `-c jar.txt` сохраняет cookie в файл). Запустите сервер из папки `final` и выполните curl в той же папке:

```console
$ curl -s -i -c jar.txt localhost:8765/login -H "Content-Type: application/json" --data-binary @login.json | mask
HTTP/1.1 200 OK
Cache-Control: no-store
Content-Type: application/json
Set-Cookie: __Host-session=[redacted]; Path=/; Max-Age=86400; HttpOnly; Secure; SameSite=Lax
Vary: Origin
X-Request-Id: GLYOPBEPBDRKAICL3Q3V6FD3N7
Date: Sat, 28 Nov 2026 09:24:10 GMT
Content-Length: 38

{"id":1,"email":"[email]"}
```

ID запроса, дата и токен при каждом запуске другие. Вместо токена стоит `[redacted]`: его подставил `mask`. `Cache-Control: no-store` знаком по GB-6.04; `Content-Type`, `Content-Length`, `Date` — обычные HTTP-заголовки (GB-4.01). `Vary: Origin` добавлен в этом уроке, объясню его в разделе про CORS. Смотрим на строку `Set-Cookie`. По сравнению с GB-6.04 изменились два места: перед именем появился префикс `__Host-`, а вместо `Expires` стоит `Max-Age`. Остальные атрибуты те же.

| Часть | Что делает браузер |
|---|---|
| `__Host-session` | cookie с именем, начинающимся на `__Host-`, браузер принимает, только если выполнены три условия (см. ниже) |
| `Path=/` | cookie добавляется ко всем путям сайта |
| `Max-Age=86400` | браузер хранит cookie 86400 секунд, то есть 24 часа |
| `HttpOnly` | скрипт на странице не может прочитать cookie через `document.cookie` |
| `Secure` | cookie отправляется только по HTTPS; `http://localhost` — исключение |
| `SameSite=Lax` | ограничивает добавление cookie к запросам, начатым с другого site (в следующих разделах) |

Так эти атрибуты записаны в `setSessionCookie`:

```go
func setSessionCookie(w http.ResponseWriter, token string) {
	http.SetCookie(w, &http.Cookie{
		Name:     sessionCookie,
		Value:    token,
		Path:     "/",
		MaxAge:   int(sessionTTL.Seconds()),
		HttpOnly: true,
		Secure:   true,
		SameSite: http.SameSiteLaxMode,
	})
	w.Header().Set("Cache-Control", "no-store")
}
```

| Код | Что делает |
|---|---|
| `Name: sessionCookie` | имя cookie; значение этой константы — `"__Host-session"` |
| `MaxAge: int(sessionTTL.Seconds())` | `sessionTTL` — это `24 * time.Hour`; `Seconds()` переводит её в секунды (`86400`), `int` делает целое число |
| `HttpOnly: true`, `Secure: true` | записывают соответствующие атрибуты |
| `SameSite: http.SameSiteLaxMode` | записывает `SameSite=Lax`; в GB-6.04 он только назывался |
| `w.Header().Set("Cache-Control", "no-store")` | ответ не должен оставаться в кэше (GB-6.04) |

**`Max-Age`** — *относительный* срок в секундах: браузер прибавляет его к своему текущему времени. `Expires` — точная дата, браузер сверяет её со своими часами, и при неверных часах срок сдвигается. Если указаны оба, главным считается `Max-Age` (RFC 6265bis §4.1.2.2). Браузер может и сократить срок, поэтому основным остаётся срок сессии на сервере (`sessionTTL`, GB-6.04).

**Префикс `__Host-`** ставит браузеру условие: cookie должно быть `Secure`, иметь `Path=/` и не иметь атрибута `Domain`. Cookie без `Domain` — *host-only*: оно возвращается только тому host, который его выдал, а не поддоменам. Итог: `blog.bozor.uz` не может перезаписать `__Host-session` для bozor. Ограничение относится к host, а не к порту: RFC 6265bis прямо говорит, что порты — единственная часть модели origin, которую `__Host-` cookie игнорируют.

Как curl сохранил это cookie? Последняя строка `jar.txt`:

```console
$ tail -1 jar.txt | mask
#HttpOnly_localhost	FALSE	/	TRUE	1795944250	__Host-session	[redacted]
```

В строке семь столбцов, разделённых табами: домен (пометка `#HttpOnly_` — cookie `HttpOnly`), принимают ли его поддомены (`FALSE` — нет, `Domain` не было), путь, `Secure` (`TRUE`), время окончания (в секундах epoch: curl превратил `Max-Age` в абсолютное время), имя, значение. Curl сохраняет и возвращает `Secure` cookie для `http://localhost`: localhost — исключение (MDN, Set-Cookie).

### HttpOnly: в настоящем браузере

`HttpOnly` с помощью curl не показать: у curl нет скрипта страницы. Поэтому нужен настоящий Chrome. Он работает без окна (**headless**), а управляет им Go-программа в `_video/brauzer` через библиотеку **chromedp**. Сама программа не тема урока: она управляет браузером и печатает результат. Команда `httponly` входит в bozor на странице bozor как Дилноза (браузер сам сохраняет cookie), затем скриптом страницы делает два дела. Сервер запущен из `final`, команда в папке браузера:

```console
$ go run . httponly | mask
login: 200 {"id":1,"email":"[email]"}
document.cookie: ""
fetch /me: 200 {"id":1,"email":"[email]"}
```

1. `login: 200 …` — вход удался, в браузере есть cookie.
2. `document.cookie: ""` — скрипт читает cookie через `document.cookie` и получает пустую строку: так работает `HttpOnly`.
3. `fetch /me: 200 …` — `fetch` это функция браузера для запросов. Она шлёт запрос на `/me`, браузер сам добавляет cookie: ответ `200`.

Вывод: вредоносный скрипт на странице **не может украсть** токен, но пока страница открыта, может отправлять запросы от имени Дилнозы. `HttpOnly` защищает от первого, но не от второго.

## Origin и site: когда cookie считается «пришедшим из другого места»

Чтобы понять `SameSite`, нужно точно знать, что значит «из другого места». Есть два понятия.

**Origin** — схема, host и порт вместе: `http://localhost:8765`. Если отличается хотя бы одно, origin другой.

**Site** — схема и *регистрируемый домен* (registrable domain): запись из Public Suffix List и одна часть перед ней, например `bozor.uz`. **Порт не учитывается.** У `localhost` и IP-адресов регистрируемого домена нет: там должен совпасть весь host (HTML Standard, «same site»). Схема тоже учитывается: в правилах cookie `http://` и `https://` — разные site (MDN, Site).

| Одна страница | Другая страница | Origin | Site |
|---|---|---|---|
| `http://localhost:8765` | `http://localhost:8765/me` | тот же | тот же |
| `http://localhost:8765` | `http://localhost:9090` | **другой** (порт) | **тот же** (порт не учитывается) |
| `https://app.bozor.uz` | `https://blog.bozor.uz` | другой (host) | **тот же** (`bozor.uz`) |
| `http://localhost:8765` | `http://127.0.0.1:9090` | другой | **другой** (host другой) |
| `http://localhost` | `https://localhost` | другой | другой (схема другая) |

Чужой сайт в лаборатории открывается с одного сервера под двумя именами: `http://localhost:9090` (**тот же site**, что и bozor, но другой origin) и `http://127.0.0.1:9090` (**другой site**). Первый моделирует соседний сервис внутри сети (сосед по порту или поддомен), второй — обычный чужой сайт.

## SameSite: когда cookie добавляется

`SameSite` определяет, добавлять ли cookie к запросу, **начатому с другого site**. Значений три. Внутри одного site cookie уходит во всех трёх случаях при любом типе запроса.

| Запрос, начатый с другого site | `Strict` | `Lax` | `None` (нужен `Secure`) |
|---|---|---|---|
| страница, открытая по ссылке (навигация верхнего уровня, `GET`) | не уходит | **уходит** | уходит |
| `POST` через форму | не уходит | не уходит | уходит |
| `iframe` (страница внутри страницы) или `fetch` | не уходит | не уходит | уходит |

`Lax` — значение cookie этого урока. Его правило: с другого site уходит только при навигации верхнего уровня с безопасным методом (`GET`) (RFC 6265bis §4.1.2.7). По этой таблице предскажите: если чужая страница на другом site, что получит `POST`-форма?

## CSRF: форма на чужой странице

Страница атаки лежит в константе `formaPage` в `cmd/begona`: обычная HTML-форма, скрипта нет.

```html
<form method="post" action="http://localhost:8765/orders/41/cancel">
  <button>Sovgʻani olish</button>
</form>
```

| Строка | Что делает |
|---|---|
| `<form method="post" action="…">` | при отправке формы браузер шлёт `POST`-запрос; `action` — куда: путь отмены заказа в bozor |
| `<button>Sovgʻani olish</button>` | кнопка; при нажатии браузер отправляет форму |
| `</form>` | форма закончилась |

Отправляя форму, браузер **сам** добавляет cookie bozor, если `SameSite` позволяет. У этого маршрута нет тела, поэтому нет и `requireJSON` (GB-6.01): обычная форма тоже может до него дойти. Вот маршрут `cancelOrder`:

```go
	mux.Handle("POST /orders/{id}/cancel", a.requireUser(http.HandlerFunc(a.cancelOrder)))
```

| Шаг | Кто | Что |
|---|---|---|
| 1 | Дилноза | входит в bozor; браузер сохраняет cookie |
| 2 | Дилноза | открывает чужую страницу |
| 3 | Дилноза | нажимает «Sovgʻani olish» |
| 4 | браузер | отправляет форму как `POST /orders/41/cancel` и (если разрешено) сам добавляет cookie |
| 5 | bozor | cookie верное, владелец верный: заказ отменён |

### Два новых поля в логе сервера

Чтобы видеть, кто начал запрос, в `logRequests` добавлены два поля:

```go
		_, err := r.Cookie(sessionCookie)
		log.Printf("%s %s %q %d %s site=%q cookie=%t", w.Header().Get("X-Request-Id"),
			r.Method, r.URL.Path, rec.status, time.Since(start), r.Header.Get("Sec-Fetch-Site"), err == nil)
```

`site=` — заголовок `Sec-Fetch-Site`: браузер сам добавляет его к каждому запросу на HTTPS или localhost-адреса, и в нём записано, какая страница начала запрос. Значения: `same-origin`, `same-site`, `cross-site`, `none` (адрес набран в адресной строке или открыт из закладки). `cookie=` — пришло ли session cookie (`true`/`false`). `r.Header.Get` читает заголовок, `err == nil` означает, что cookie есть (GB-6.04).

### Предскажите: форма с другого site

Откроем чужую страницу теперь через `127.0.0.1`, то есть на **другом site**. Cookie `SameSite=Lax`. Что будет при нажатии «Sovgʻani olish»? **A)** `200`, заказ отменён · **B)** `401`, cookie не пришло · **C)** `403`, нет прав.

## Защита на сервере: http.CrossOriginProtection

Сервер сам проверяет, **откуда** пришёл запрос, меняющий состояние. С Go 1.25 для этого в стандартной библиотеке есть `http.CrossOriginProtection`; OWASP CSRF Prevention Cheat Sheet называет его прямо. Он опирается на два заголовка, которые шлёт браузер: `Sec-Fetch-Site` (видели выше) и `Origin` (origin страницы, начавшей запрос; браузер добавляет его к `POST`).

```go
var allowedOrigins = []string{"http://localhost:3000"}

// errCrossOrigin — soʻrov boshqa origin'dagi sahifadan kelgan (problemFor → 403).
var errCrossOrigin = errors.New("boshqa saytdan kelgan soʻrov")

// protectCSRF — Go 1.25'dan beri standart kutubxonadagi http.CrossOriginProtection bilan:
//   - GET, HEAD, OPTIONS — har doim oʻtadi (ular holatni oʻzgartirmasligi kerak);
//   - Sec-Fetch-Site: same-origin yoki none (manzil qatoriga yozilgan) — oʻtadi; boshqa qiymat — rad;
//   - Sec-Fetch-Site yoʻq, Origin bor — Origin'ning host'i Host sarlavhasiga teng boʻlsa oʻtadi;
//   - ikkalasi ham yoʻq — Go buni brauzer emas deb hisoblaydi (curl, mobil ilova, boshqa server): oʻtadi (fail-open);
//   - AddTrustedOrigin'dagi origin'lar — oʻtadi.
//
// Origin ↔ Host solishtiruvida sxema (http/https) koʻrilmaydi: production'da HTTPS + HSTS (GB-8.06).
//
// Brauzer bo'lmagan mijozda begona cookie yoʻq: CSRF — aynan brauzer cookie'ni oʻzi qoʻshgani uchun xavf.
// Rad sababi (Check'ning xatosi) log'ga, mijozga — bizning matn (GB-6.02).
func protectCSRF(next http.Handler) http.Handler {
	cop := http.NewCrossOriginProtection()
	for _, o := range allowedOrigins {
		if err := cop.AddTrustedOrigin(o); err != nil {
			panic(err) // roʻyxat kodimizda: notoʻgʻri yozilgan boʻlsa server ishga tushmasin
		}
	}
```

| Код | Что делает |
|---|---|
| `var allowedOrigins = []string{…}` | список разрешённых origin: собственное веб-приложение bozor, `http://localhost:3000` |
| `func protectCSRF(next http.Handler) http.Handler` | middleware (форма из GB-6.01) |
| `cop := http.NewCrossOriginProtection()` | создаёт объект-проверяющий |
| `for _, o := range allowedOrigins` | для каждого origin из списка |
| `cop.AddTrustedOrigin(o)` | добавляет его в **доверенные** origin; если запись неверна (нет схемы, есть путь), возвращает ошибку |
| `panic(err)` | список в нашем коде: при ошибке сервер не должен запускаться (GB-2.09) |

Главная часть — возвращаемый handler:

```go
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if err := cop.Check(r); err != nil {
			writeError(w, fmt.Errorf("%w: %w", errCrossOrigin, err))
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

| Код | Что делает |
|---|---|
| `cop.Check(r)` | проверяет запрос; при отказе возвращает ошибку |
| `fmt.Errorf("%w: %w", errCrossOrigin, err)` | объединяет две ошибки: наш текст и причину от `Check` (GB-6.02) |
| `writeError(w, …)` | пишет `403` в виде problem: клиенту наш текст, причина идёт в лог |
| `next.ServeHTTP(w, r)` | проверка пройдена, handler работает |

Правила `Check` (исходник Go 1.27.4, `net/http/csrf.go`):

1. `GET`, `HEAD`, `OPTIONS` — **всегда проходят**: эти методы не должны менять состояние. Поэтому не меняйте состояние в GET.
2. `Sec-Fetch-Site: same-origin` или `none` — проходит. Другое значение (`same-site`, `cross-site`) — **отказ**, если только `Origin` не в списке доверенных или путь не исключён через `AddInsecureBypassPattern`.
3. `Sec-Fetch-Site` нет, `Origin` есть — проходит, если host в `Origin` (с портом) равен заголовку `Host`, иначе отказ. Схема не сравнивается.
4. Нет ни того, ни другого — считается, что запрос не из браузера или из того же origin, и он **проходит**.

Место в цепочке: `requestID → logRequests → recoverPanic → cors → protectCSRF → muxErrors → mux` (`cmd/api/middleware.go`, `newHandler`).

## CORS: правило на чтение ответа

**CORS** (cross-origin resource sharing) — правило браузера на **чтение**. Страница с другого origin может отправить запрос серверу, но чтобы прочитать ответ, сервер должен указать именно этот origin в заголовке `Access-Control-Allow-Origin`. Если не указал, браузер не отдаст ответ странице. Для запроса с cookie нужен ещё `Access-Control-Allow-Credentials: true`. Это правило сервер **не защищает**: запрос всё равно выполняется. Опыт ниже это показывает.

`oqishPage` в `cmd/begona` — страница со скриптом:

```html
<pre id="natija">kutilmoqda…</pre>
<script>
fetch("http://localhost:8765/me", {credentials: "include"})
  .then(r => r.text())
  .then(t => { natija.textContent = "oʻqildi: " + t })
  .catch(e => { natija.textContent = "oʻqib boʻlmadi: " + e })
</script>
```

| Строка | Что делает |
|---|---|
| `<pre id="natija">kutilmoqda…</pre>` | место, куда пишется результат («kutilmoqda» — «ожидается») |
| `fetch("http://localhost:8765/me", {credentials: "include"})` | запрашивает `/me` у bozor; `credentials: "include"` отправляет и cookie |
| `.then(r => r.text())` | когда ответ получен, берёт его текст |
| `.then(t => { natija.textContent = "oʻqildi: " + t })` | записывает текст на страницу («oʻqildi» — «прочитано») |
| `.catch(e => { … "oʻqib boʻlmadi: " + e })` | если чтение отклонено, записывает ошибку («oʻqib boʻlmadi» — «прочитать не удалось») |

Сервер `final`, чужой сайт на `localhost:9090`. Программа-браузер открывает страницу и ждёт текст результата:

```console
$ go run . cors http://localhost:9090 | mask
```

Страница не смогла прочитать ответ: `fetch` завершился с `TypeError: Failed to fetch`. Браузер намеренно не говорит скрипту причину (подробности только в консоли браузера). Но посмотрите в лог сервера:


`GET "/me" 200`, `cookie=true`: запрос **выполнен**. Так как это `GET`, он прошёл и `CrossOriginProtection` (правило 1). CORS лишь не отдал ответ странице. Значит, CORS не защита сервера: запрос, меняющий состояние, останавливает проверка CSRF.

### Частая ошибка: вернуть Origin как есть

Разработчики хотят всё разрешить и вместо списка возвращают сам `Origin` из запроса, вместе с `Allow-Credentials: true`. Это код из копии `aks`:

```go
func cors(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		// XATO (video): roʻyxat oʻrniga soʻrovdagi Origin'ni oʻzini qaytarish — har qanday sahifa javobni oʻqiydi.
		w.Header().Set("Access-Control-Allow-Origin", r.Header.Get("Origin"))
		w.Header().Set("Access-Control-Allow-Credentials", "true")
		next.ServeHTTP(w, r)
	})
}
```

`r.Header.Get("Origin")` читает `Origin` из запроса, `Set` записывает его в ответ: любой странице говорится «вам можно». А `Allow-Credentials: true` разрешает читать и ответы с cookie. `Origin` ничем не проверяется.

**Предскажите.** С этим кодом снова запускается страница чтения (`localhost:9090/oqish`). Результат? **A)** страница читает email Дилнозы · **B)** `TypeError: Failed to fetch` · **C)** `403`, останавливает `protectCSRF`.

<details>
<summary>Ответ</summary>

### Как правильно: allow-list

Список разрешённых origin (**allow-list**) — тот же `allowedOrigins`, которым пользуется `protectCSRF`. Вот middleware `cors` (итоговый код):

```go
func cors(next http.Handler) http.Handler {
	allowed := map[string]bool{}
	for _, o := range allowedOrigins {
		allowed[o] = true
	}
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Add("Vary", "Origin")
		origin := r.Header.Get("Origin")
		if !allowed[origin] {
			next.ServeHTTP(w, r)
			return
		}
		w.Header().Set("Access-Control-Allow-Origin", origin)
		w.Header().Set("Access-Control-Allow-Credentials", "true")
		// Preflight: brauzer haqiqiy soʻrovdan oldin OPTIONS bilan ruxsat soʻraydi (JSON body, PATCH, DELETE…).
		if r.Method == http.MethodOptions && r.Header.Get("Access-Control-Request-Method") != "" {
			w.Header().Set("Access-Control-Allow-Methods", "POST, PATCH, DELETE")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
			w.Header().Set("Access-Control-Max-Age", "600") // brauzer javobni 10 daqiqa eslab qoladi
			w.WriteHeader(http.StatusNoContent)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

| Код | Что делает |
|---|---|
| `allowed := map[string]bool{}` и `for … allowed[o] = true` | превращает список в `map` для быстрой проверки |
| `w.Header().Add("Vary", "Origin")` | говорит кэшу: «ответ зависит от `Origin`» (`Add` **добавляет** значение к заголовку, `Set` заменяет) |
| `if !allowed[origin] { next.ServeHTTP(w, r); return }` | если origin нет в списке, CORS-заголовки **не добавляются**; запрос выполняется как обычно |
| `Access-Control-Allow-Origin` = `origin` | если origin в списке, возвращает именно его |
| `Access-Control-Allow-Credentials: true` | разрешает читать ответ с cookie |
| `if r.Method == http.MethodOptions && …` | ветка preflight (ниже) |

### Preflight

Перед необычным запросом (JSON-тело, `PATCH`, `DELETE`, нестандартный заголовок) браузер сначала шлёт запрос `OPTIONS` и спрашивает разрешение: в `Access-Control-Request-Method` и `Access-Control-Request-Headers` пишет, что ему нужно. Это **preflight**. Если ответ разрешения не даёт, браузер настоящий запрос **вообще не отправляет**. Preflight с разрешённым origin:

## Rate limit на login: token bucket

Каждая попытка входа считает argon2id: в GB-6.03 мы видели, что одна попытка занимает 46 MiB памяти и заметное время CPU. В моём прогоне одна строка `POST "/login"` в логе показала `82.523656ms`. Без ограничения `POST /login` открыт для подбора паролей и это дешёвый способ загрузить сервер. Bozor до урока (`himoyasiz`): подряд восемь неверных login с одного IP. Bash-цикл `for i in $(seq 8)` повторяет команду восемь раз; в curl `-o /dev/null` отбрасывает тело, `-w "%{http_code} "` печатает только код статуса, `echo` завершает строку:

```console
$ for i in $(seq 8); do curl -s -o /dev/null -w "%{http_code} " localhost:8765/login -H "Content-Type: application/json" --data-binary @wrong.json; done; echo
401 401 401 401 401 401 401 401
```

Восемь `401`: подбор безграничен. Решение — **token bucket** («ведро с токенами»). Для каждого ключа (сейчас это IP) есть ведро: в нём не больше 5 токенов, в начале оно полное. Каждая попытка забирает один токен. В ведро каждые 12 секунд возвращается один токен. Если токенов нет — `429 Too Many Requests` и `Retry-After`: через сколько секунд можно попробовать снова.

| Попытка | В ведре до | Результат | В ведре после |
|---|---|---|---|
| 1 | 5 | `401` (пароль неверный, но попытка разрешена) | 4 |
| 2 | 4 | `401` | 3 |
| 3 | 3 | `401` | 2 |
| 4 | 2 | `401` | 1 |
| 5 | 1 | `401` | 0 |
| 6, 7, 8 | 0 | `429`, `Retry-After` | 0 (токен не берётся) |
| через 12 секунд | 0 → 1 | следующая попытка `401` | 0 |

Код — в пакете `golang.org/x/time/rate`: token bucket от команды Go (добавлен через `go get golang.org/x/time/rate`, GB-2.06; в `go.mod` `v0.16.0`). Полный `cmd/api/ratelimit.go`:

```go filename="cmd/api/ratelimit.go" showLineNumbers
package main

// Login'ga rate limit (GB-6.07). Har login urinishi argon2id hisoblaydi (GB-6.03: 46 MiB xotira):
// cheklovsiz POST /login — parol taxmin qilish uchun ochiq eshik va serverni band qilishning arzon yoʻli.
//
// golang.org/x/time/rate — Go jamoasining token bucket'i: chelakda eng koʻpi `burst` ta token,
// har `every` vaqtda bittadan toʻladi; har soʻrov bitta token oladi; token yoʻq — 429 Too Many Requests
// (RFC 6585 §4) va Retry-After: necha soniyadan keyin qayta urinish mumkin (RFC 9110 §10.2.3).

import (
	"math"
	"net"
	"net/http"
	"strconv"
	"sync"
	"time"

	"golang.org/x/time/rate"
)

// limiters — har kalit (IP yoki email) uchun alohida chelak. Map bir vaqtda koʻp soʻrovdan
// ishlatiladi, shuning uchun mutex (GB-4.07). Kalitlar oʻchirilmaydi: uzoq ishlaydigan serverda
// map oʻsib boradi — tozalash 🟡 ixtiyoriy vazifada (TASK.md, sweep).
type limiters struct {
	mu    sync.Mutex
	m     map[string]*rate.Limiter
	every rate.Limit
	burst int
}

// newLimiters — har kalitga: boshida burst ta urinish, keyin har every'da bittadan.
func newLimiters(every time.Duration, burst int) *limiters {
	return &limiters{m: map[string]*rate.Limiter{}, every: rate.Every(every), burst: burst}
}

// get — kalitning chelagi; birinchi murojaatda yangisi (toʻla) yaratiladi.
func (l *limiters) get(key string) *rate.Limiter {
	l.mu.Lock()
	defer l.mu.Unlock()
	lim, ok := l.m[key]
	if !ok {
		lim = rate.NewLimiter(l.every, l.burst)
		l.m[key] = lim
	}
	return lim
}

// wait — 0: urinish mumkin (token olindi). Aks holda — keyingi token qancha vaqtdan keyin.
// Reserve navbat oladi, Delay — shu navbatgacha kutish; biz kutmaymiz: Cancel tokenni qaytaradi.
func (l *limiters) wait(key string) time.Duration {
	res := l.get(key).Reserve()
	d := res.Delay()
	if d > 0 {
		res.Cancel()
	}
	return d
}

// limitByIP — middleware (GB-6.01 shakli): kalit — mijozning IP manzili. r.RemoteAddr — TCP ulanishning
// manzili («IP:port»), uni mijoz soxtalashtira olmaydi. X-Forwarded-For sarlavhasiga ishonmaymiz: uni
// har kim yozadi. Server proksi (Caddy, GB-8.06) ortida boʻlsa, RemoteAddr — proksining manzili: hamma mijoz bitta
// chelakka tushadi. U holda IP'ni faqat ishonchli proksi yozgan sarlavhadan olish kerak (GB-8.06).
// net/http serveri RemoteAddr'ni doim «IP:port» qiladi, shuning uchun SplitHostPort xatosi bu yerda kutilmaydi.
// Eslatma: IPv6'da bitta foydalanuvchida odatda butun /64 tarmoq boʻladi — production'da kalitni /64 boʻyicha olish mumkin.
func (l *limiters) limitByIP(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		ip, _, _ := net.SplitHostPort(r.RemoteAddr)
		if d := l.wait(ip); d > 0 {
			tooManyRequests(w, d)
			return
		}
		next.ServeHTTP(w, r)
	})
}

// tooManyRequests — 429 problem va Retry-After butun soniyalarda, yuqoriga yaxlitlangan.
func tooManyRequests(w http.ResponseWriter, d time.Duration) {
	w.Header().Set("Retry-After", strconv.Itoa(int(math.Ceil(d.Seconds()))))
	writeProblem(w, newProblem(http.StatusTooManyRequests, "urinishlar koʻp: keyinroq qayta urinib koʻring"))
}
```

| Строки | Что делает |
|---|---|
| 10–19 | `import`; `rate` — `golang.org/x/time/rate` |
| 24–29 | `limiters`: `m` — ключ (IP или email) → одно ведро (`*rate.Limiter`); `mu` — mutex, потому что `map` одновременно использует много запросов (GB-4.07); `every` — интервал между токенами (тип `rate.Limit`), `burst` — размер ведра |
| 32–34 | `newLimiters`: `rate.Every(every)` создаёт скорость «один токен каждые `every`» |
| 37–46 | `get`: ведро ключа; для нового ключа `rate.NewLimiter` создаёт полное ведро |
| 50–57 | `wait`: `Reserve` занимает очередь (токен берётся), `Delay` — время ожидания до этой очереди (`time.Duration`). Ждать мы не будем: при `d > 0` `Cancel` возвращает токен. Функция возвращает `0` (можно) или время ожидания |
| 65–74 | `limitByIP`: middleware (форма из GB-6.01). `r.RemoteAddr` — адрес TCP-соединения, `"IP:port"`; `net.SplitHostPort` выделяет IP, порт и ошибка отбрасываются в `_`. Если `wait(ip) > 0` — `429`, `return` |
| 77–80 | `tooManyRequests`: пишет `Retry-After` целым числом секунд: `math.Ceil` округляет вверх (`11.9` → `12`), `strconv.Itoa` превращает целое число в текст. Ответ — problem JSON из GB-6.02 |

Зачем нужен `Cancel`? `Reserve` занимает очередь, даже если токенов не хватает (берёт будущий токен «в долг»). Чтобы отклонённая попытка не опустошала ведро ещё сильнее, `Cancel` отменяет её эффект (документация пакета: «насколько возможно»). Иначе каждая отклонённая попытка отодвигала бы следующее разрешение.

`limitByIP` оборачивает в маршруте `requireJSON`, поэтому срабатывает **до** argon2id:

```go
	mux.Handle("POST /login", a.loginIP.limitByIP(requireJSON(http.HandlerFunc(a.login))))
```

А `api.loginIP` создаётся в `newMux`: `newLimiters(12*time.Second, 5)` — пять попыток, потом по одной каждые 12 секунд (`handlers.go`, `loginIP: newLimiters(12*time.Second, 5)`).

## Глубже (необязательно): границы

- **Запрос без заголовков проходит (fail-open).** Из-за правила 4 в `Check` запрос без `Sec-Fetch-Site` и без `Origin` проходит: чтобы работали curl и мобильные приложения. OWASP для чувствительных endpoint рекомендует обратное (fail-safe: заголовка нет — отказ). Современные браузеры шлют `Sec-Fetch-Site` с 2023 года (OWASP), поэтому для браузера это решение не опасно.
- **При сравнении `Origin` и `Host` схема не учитывается.** Запрос между origin с HTTP на HTTPS правило 3 отличить не может. Комментарий в исходнике Go называет решение: HTTPS и HSTS (GB-8.06).
- **Fetch Metadata шлётся только на надёжные адреса:** `https`, `wss`, `file`, `localhost` и `127.0.0.0/8` (OWASP). В production HTTPS обязателен; на обычном HTTP остаётся только проверка `Origin`.
- **Cookie без `SameSite`.** RFC 6265bis: если атрибута нет или он неизвестен, режим по умолчанию равен `Lax`. Браузер (`MAY`) может ещё применить к недавно созданному cookie режим `Lax-allowing-unsafe`: отправлять его на `POST` верхнего уровня с другого site; RFC рекомендует возраст cookie не более 2 минут. Поэтому всегда пишите атрибут явно.
- **CSRF-токен** (synchronizer или signed double-submit) — классический путь. OWASP называет `Sec-Fetch-Site` основным сигналом политики Fetch Metadata, а если заголовка нет, советует проверку `Origin` и при необходимости токен.
- **XSS побеждает любую защиту от CSRF** (OWASP): скрипт, попавший на страницу, шлёт запросы с того же origin. `HttpOnly` останавливает только кражу токена.
- **Лимиты в памяти** и относятся к одному процессу. Если экземпляров сервера несколько, нужен общий счётчик (например, Redis). Ключи приходят от клиента (IP, email), и `map`, который не очищают, растёт: `sweep` из домашнего задания его чистит.
- **Границы ключа-IP.** Много пользователей за одним NAT делят одно ведро. В IPv6 у одного клиента обычно целая сеть `/64` (в production ключ можно брать по `/64`).
- **DoS через блокировку.** Лимит по email позволяет злоумышленнику заблокировать и Дилнозу (OWASP, «Account Lockout»). Поэтому лимит по email мягче, чем по IP: 10 попыток, затем одна в минуту.

## Частые ошибки

**1. «Поставил `SameSite=Lax`, CSRF закрыт».** Мы видели выше: `Lax` останавливает `POST` с **другого site**, но не соседний порт или поддомен внутри одного site. А при `None` cookie уходит отовсюду. Итог: `200`, заказ отменён (таблица, три строки). Правильно: оставьте `Lax` **и** включите на сервере `protectCSRF` (`CrossOriginProtection`).

**2. Считать CORS защитой сервера.** Реальный вывод: чужая страница получила `TypeError: Failed to fetch`, но в логе была строка `GET "/me" 200 … cookie=true`: запрос выполнен. Ошибка видна в браузере, а сервер отработал. Правильно: запрос, меняющий состояние, останавливает `protectCSRF`, а чтение данных защищают аутентификация (`requireUser`) и проверка владельца (GB-6.06).

**3. Возвращать `Origin` без проверки.** Реальный вывод: страница прочитала данные Дилнозы (`oʻqildi: {"id":1,…}`). Причина: `Allow-Origin` взят из `Origin` запроса и добавлен `Allow-Credentials: true`. Правильно: список `allowedOrigins`, проверка `if !allowed[origin]` в коде `cors`, `Vary: Origin` в каждом ответе. `Allow-Origin: *` вместе с `Allow-Credentials` использовать нельзя: браузер отклонит такой ответ (OWASP).

**4. `X-Forwarded-For` как ключ IP.** Этого нет в папке, это мой дополнительный опыт: в `limitByIP` добавлены три строки (в копии для опыта; код в папке не менялся).

```go
func (l *limiters) limitByIP(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		ip, _, _ := net.SplitHostPort(r.RemoteAddr)
		if xff := r.Header.Get("X-Forwarded-For"); xff != "" {
			ip = xff // XATO: sarlavhani mijoz yozadi
		}
		if d := l.wait(ip); d > 0 {
			tooManyRequests(w, d)
			return
		}
		next.ServeHTTP(w, r)
	})
}
```

Атакующий меняет заголовок в каждом запросе (`-H "X-Forwarded-For: 203.0.113.$i"`):

```console
$ for i in $(seq 8); do curl -s -o /dev/null -w "%{http_code} " -H "X-Forwarded-For: 203.0.113.$i" localhost:8765/login -H "Content-Type: application/json" --data-binary @wrong.json; done; echo
401 401 401 401 401 401 401 401
```

Восемь раз `401`: лимит не сработал, каждому значению заголовка выдали новое полное ведро. В настоящем коде (ключ — `RemoteAddr`) та же команда упирается в лимит:


## Проверьте себя

**1.** Почему страница на `localhost:9090` получила `Lax` cookie, хотя cookie `Lax`?

<details>
<summary>Ответ</summary>

Порт site не меняет: `localhost:9090` с bozor (`localhost:8765`) — **один site**. `SameSite` ограничивает только запросы, начатые с другого site, внутри одного site cookie уходит при любом запросе. Поэтому на сервере нужно проверять `Sec-Fetch-Site` и `Origin`: `Sec-Fetch-Site: same-site` в `CrossOriginProtection` отклоняется.

</details>

**2.** Почему CORS не защита сервера?

<details>
<summary>Ответ</summary>

CORS управляет только **чтением** ответа. Запрос доходит до сервера и выполняется: в логе была строка `GET "/me" 200 … cookie=true`, а страница всё равно получила `Failed to fetch`. Запрос, меняющий состояние, останавливает `protectCSRF`.

</details>

**3. GB-6.04.** Почему старая копия cookie после logout получает `401`?

<details>
<summary>Ответ</summary>

Logout удалил запись сессии на сервере. Сервер при каждом запросе ищет запись по хешу токена из cookie и не находит: `requireUser` отвечает `401`. Само cookie (в браузере или в `jar.txt`) ничего не доказывает.

</details>

**4. Предскажите.** На сервере `final` Дилноза входит с **верным** паролем с одного IP шесть раз подряд. Какие статусы?

<details>
<summary>Ответ</summary>

`200 200 200 200 200 429`. Лимит считает попытки, а не верность пароля: в маршруте `limitByIP` стоит перед `login`. На шестую попытку токена не хватает. Вывод «Лимит считает все попытки» выше это показывает.

</details>

**5. Предскажите.** `curl -X POST -b jar.txt -H 'Origin: http://localhost:9090' localhost:8765/orders/41/cancel` (без `Sec-Fetch-Site`): результат?

<details>
<summary>Ответ</summary>

`403`. `Sec-Fetch-Site` нет, поэтому правило 3: host в `Origin` (`localhost:9090`) отличается от заголовка `Host` (`localhost:8765`), отказ. Причина в логе: `cross-origin request detected, and/or browser is out of date: Sec-Fetch-Site is missing, and Origin does not match Host`.

</details>

`sweep` (🟡):

```go
func (l *limiters) sweep(now time.Time) int {
	l.mu.Lock()
	defer l.mu.Unlock()
	n := 0
	for key, lim := range l.m {
		if lim.TokensAt(now) >= float64(l.burst) {
			delete(l.m, key) // range ichida delete mumkin (Go spec: For statements with range clause)
			n++
		}
	}
	return n
}
```

`sweep` берёт `mu` (`map` одновременно используют другие запросы), и если `TokensAt(now)` показывает у ведра ключа полное ведро, удаляет ключ через `delete` (внутри `range` `delete` допустим). Удалять полное ведро безопасно: новое всё равно создаётся полным. На сервере её нужно вызывать периодически (горутиной с `time.Ticker`, GB-7.01).
