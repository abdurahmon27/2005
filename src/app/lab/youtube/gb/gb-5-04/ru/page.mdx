## Что вы узнаете

bozor нужен отчёт с итоговой суммой каждого заказа. Сумма не хранится в столбце: позиции заказа находятся в другой таблице. Как вычислить её, сохранив заказ без позиций?

**Одна идея:** соедините строки связанных таблиц, сгруппируйте пары по заказу и вычислите сумму каждой группы. Сохраните заказы без пар и явно обработайте отсутствующие значения.

К концу урока вы сможете:

- связать `orders` и `order_items` через `REFERENCES`;
- построить отчёт с `JOIN`, `LEFT JOIN`, `GROUP BY` и `SUM`;
- объяснить, почему `note = NULL` ничего не находит, и правильно использовать `IS NULL` и `COALESCE`;
- написать два SQL-запроса и проверить их командой `go test`.

| Слово | Простое значение | Английский термин |
|---|---|---|
| `JOIN` / `LEFT JOIN` | соединение строк таблиц в пары; левое соединение сохраняет и строки слева без пары | join / left join |
| `GROUP BY` + `SUM` | создание групп и вычисление одной суммы для каждой | grouping / aggregate |
| `NULL` | отсутствующее или неизвестное значение; обычное сравнение может дать неизвестный результат | NULL / three-valued logic |

Два вспомогательных понятия: **внешний ключ** (`REFERENCES`, foreign key) требует существования строки, на которую указывает ссылка. **COALESCE** возвращает первое значение среди аргументов, отличное от NULL.

Заказу нужен необязательный комментарий. Каждая позиция должна ссылаться на существующие заказ и товар. Полный `orders.sql`:

```sql filename="orders.sql" showLineNumbers
CREATE TABLE orders (
    id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer text   NOT NULL,
    note     text
);
CREATE TABLE order_items (
    id         bigint  GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    order_id   bigint  NOT NULL REFERENCES orders (id),
    product_id bigint  NOT NULL REFERENCES products (id),
    quantity   integer NOT NULL CHECK (quantity > 0),
    unit_price bigint  NOT NULL CHECK (unit_price > 0)
);
```

| Строка | Код | Что делает |
|---|---|---|
| 1 | `CREATE TABLE orders (` | начинает таблицу заказов и список её столбцов |
| 2 | `id ... PRIMARY KEY` | идентификатор `bigint`, выдаваемый базой; первичный ключ определяет одну строку |
| 3 | `customer text NOT NULL,` | обязательное имя клиента; запятая разделяет столбцы |
| 4 | `note text` | необязательный комментарий: требования `NOT NULL` нет |
| 5 | `);` | закрывает список столбцов и завершает команду |
| 6 | `CREATE TABLE order_items (` | начинает таблицу позиций заказа |
| 7 | `id ... PRIMARY KEY,` | выдаваемый базой идентификатор каждой позиции |
| 8 | `order_id ... REFERENCES orders (id),` | обязательный идентификатор заказа; указанный заказ должен существовать |
| 9 | `product_id ... REFERENCES products (id),` | обязательный идентификатор товара; указанный товар должен существовать |
| 10 | `quantity ... CHECK (quantity > 0),` | обязательное положительное целое количество |
| 11 | `unit_price ... CHECK (unit_price > 0)` | обязательная положительная цена единицы в тийинах на момент покупки |
| 12 | `);` | завершает определение второй таблицы |

`unit_price` — снимок цены. Последующее изменение `products.price` не должно менять сумму старого заказа. Внешний ключ проверяет существование строки, но не копирует цену.

## JOIN: одна строка результата на пару

Для каждой позиции нужен клиент. Создайте `sorov.sql` и запишите в него этот полный запрос. Для каждого следующего запроса заменяйте содержимое файла, а не добавляйте запрос в конец.

```sql
SELECT orders.customer, order_items.quantity
FROM orders
JOIN order_items ON order_items.order_id = orders.id;
```

| Строка | Код | Что делает |
|---|---|---|
| 1 | `SELECT orders.customer, order_items.quantity` | выбирает два столбца; `таблица.столбец` указывает источник каждого |
| 2 | `FROM orders` | начинает с таблицы заказов |
| 3 | `JOIN order_items ON ...` | образует пары при `order_items.order_id = orders.id`; `ON` задаёт условие соответствия |

Одному заказу могут соответствовать несколько позиций. Состояние соединения до выбора выводимых столбцов:

| Заказ | Количества в подходящих позициях | Строк результата JOIN |
|---|---|---|
| 1, Dilnoza | 2, 3 | 2 |
| 2, Jasur | 1, 1 | 2 |
| 3, Malika | подходящих позиций нет | 0 |

**Предскажите:** сколько строк вернёт JOIN?
**A)** 3 заказа · **B)** 4 пары · **C)** 5 строк, включая Malika

<details>
<summary>Ответ</summary>

**B: 4.** `JOIN` означает `INNER JOIN`: остаются только совпавшие пары. A считает заказы вместо пар. Для C нужно сохранить и заказ без пары.

</details>

```console
$ docker compose exec db psql -f /lab/sorov.sql
 customer | quantity 
----------+----------
 Dilnoza  |        2
 Dilnoza  |        3
 Jasur    |        1
 Jasur    |        1
(4 rows)
```

Malika отсутствует. В начальном запросе нет `ORDER BY`: показанный порядок наблюдался, но не гарантирован. Далее запросы отчёта задают порядок явно.

## GROUP BY и SUM: одна сумма на заказ

Для каждой позиции умножим количество на сохранённую цену единицы. Здесь `*` — умножение; в `SELECT *` он выбирал все столбцы. **SUM** — агрегат: объединяет входные значения в одно. `AS jami` называет столбец результата `jami` («итого»).

Сначала замените `sorov.sql` этой незавершённой попыткой:

```sql
SELECT orders.id, orders.customer,
       SUM(order_items.quantity * order_items.unit_price) AS jami
FROM orders
JOIN order_items ON order_items.order_id = orders.id;
```

**Предскажите:** можно ли вывести агрегат вместе с отдельными столбцами заказа без группировки?
**A)** да, сумма по заказу · **B)** да, общая сумма · **C)** ошибка GROUP BY

<details>
<summary>Ответ</summary>

**C.** Запрос не указывает, какие строки относятся к каждой сумме. A предполагает автоматическую группировку. B не определяет, какой `orders.id` показать рядом с общей суммой.

</details>

```console
$ docker compose exec db psql -f /lab/sorov.sql
psql:/lab/sorov.sql:4: ERROR:  column "orders.id" must appear in the GROUP BY clause or be used in an aggregate function
LINE 1: SELECT orders.id, orders.customer,
               ^
```

`psql:/lab/sorov.sql:4` указывает файл и строку завершения команды. `LINE 1` и `^` указывают проблемное выражение. “Must appear in the GROUP BY clause or be used in an aggregate function” означает требование к `orders.id`: столбец должен быть в GROUP BY или внутри агрегата.

Добавьте `GROUP BY orders.id`, чтобы образовать группу для каждого идентификатора заказа. `ORDER BY orders.id` задаст определённый порядок по возрастанию:

```sql
SELECT orders.id, orders.customer,
       SUM(order_items.quantity * order_items.unit_price) AS jami
FROM orders
JOIN order_items ON order_items.order_id = orders.id
GROUP BY orders.id
ORDER BY orders.id;
```

Строки 1–4 по-прежнему выбирают поля заказа, вычисляют сумму и соединяют таблицы. Строка 5 создаёт группы; строка 6 сортирует результат и завершает команду. `SUM(...)` вычисляет выражение в скобках для каждой входной строки и складывает значения внутри группы.

| Группа | Суммы позиций в тийинах | SUM |
|---|---|---|
| заказ 1 | `2 × 1200000 + 3 × 400000` | 3600000 |
| заказ 2 | `1 × 3500000 + 1 × 1200000` | 4700000 |

Почему в GROUP BY нет `orders.customer`? `orders.id` — первичный ключ таблицы, поэтому каждому идентификатору соответствует ровно один клиент. PostgreSQL распознаёт эту зависимость здесь. Это не разрешение выбирать любые несгруппированные столбцы.

**Предскажите:** сколько строк останется в результате?
**A)** 3 · **B)** 2 · **C)** 4

<details>
<summary>Ответ</summary>

**B: 2.** Четыре соединённые строки образуют две группы. A считает Malika, хотя JOIN её исключил. C считает строки до группировки.

</details>

```console
$ docker compose exec db psql -f /lab/sorov.sql
 id | customer |  jami   
----+----------+---------
  1 | Dilnoza  | 3600000
  2 | Jasur    | 4700000
(2 rows)
```

Суммы равны 3 600 000 и 4 700 000 тийинов. `SUM(bigint)` возвращает `numeric`, точный числовой тип PostgreSQL, даже для этих целых сумм. Чтение в Go разбирается в [GB-5.05 · Go → Postgres: pgx](/lab/youtube/gb/gb-5-05/ru).

## LEFT JOIN и NULL: сохранить пропавший заказ

Отчёту нужен каждый заказ. **LEFT JOIN** сохраняет все строки левой таблицы, здесь `orders`. Для строки без пары он выдаёт NULL в столбцах правой таблицы. Новую строку в `order_items` он не вставляет.

Замените `sorov.sql`:

```sql
SELECT orders.customer, order_items.quantity
FROM orders
LEFT JOIN order_items ON order_items.order_id = orders.id;
```

Изменилась только строка 3: `LEFT` сохраняет заказ без пары. Ожидайте четыре совпавшие пары и строку Malika с количеством NULL:

```console
$ docker compose exec db psql -f /lab/sorov.sql
 customer | quantity 
----------+----------
 Dilnoza  |        2
 Dilnoza  |        3
 Jasur    |        1
 Jasur    |        1
 Malika   |         
(5 rows)
```

**NULL** означает отсутствующее или неизвестное значение. Это не ноль и не `''`. Обычные сравнения `=` и `<>` с NULL дают NULL, то есть неизвестный результат. Это **трёхзначная логика**: истина, ложь, неизвестно. `WHERE` оставляет только истину.

| `note` | `note = NULL` | WHERE оставит? | `note IS NULL` |
|---|---|---|---|
| `NULL` | неизвестно (`NULL`) | нет | истина |
| `'ertalab yetkazing'` | неизвестно (`NULL`) | нет | ложь |
| `''` | неизвестно (`NULL`) | нет | ложь |

Пустая строка в таблице иллюстрирует правило; это не дополнительная запись в seed.

**Предскажите:** у двух заказов комментарий NULL. Сколько строк вернёт `WHERE note = NULL`?
**A)** 2 · **B)** 0 · **C)** синтаксическая ошибка

<details>
<summary>Ответ</summary>

**B: 0.** Условие для каждой строки неизвестно, а не истинно. A считает NULL обычным сравнимым значением. C неверно: запрос допустим и молча возвращает пустой результат.

</details>

```console
$ docker compose exec db psql -c 'SELECT id, customer FROM orders WHERE note = NULL'
 id | customer 
----+----------
(0 rows)
```

Проверяйте отсутствие значения через **IS NULL**. Он всегда возвращает истину или ложь; `IS NOT NULL` проверяет обратное. Ожидайте Dilnoza и Malika:

```console
$ docker compose exec db psql -c 'SELECT id, customer FROM orders WHERE note IS NULL'
 id | customer 
----+----------
  1 | Dilnoza
  3 | Malika
(2 rows)
```

В этих двух демонстрационных фильтрах нет `ORDER BY`; показанный порядок строк не гарантирован. Запрос домашнего задания добавляет сортировку.

## COALESCE: ноль вместо отсутствующей суммы

Теперь сохраним все заказы в сгруппированном отчёте. В предыдущем запросе с группировкой замените только `JOIN` на `LEFT JOIN`:

```sql
SELECT orders.id, orders.customer,
       SUM(order_items.quantity * order_items.unit_price) AS jami
FROM orders
LEFT JOIN order_items ON order_items.order_id = orders.id
GROUP BY orders.id
ORDER BY orders.id;
```

`SUM` пропускает входные NULL. В группе Malika одна строка результата, её количество и цена равны NULL. Умножение тоже даёт NULL; складывать нечего, значений кроме NULL нет.

**Промежуточный вопрос:** чему равен SUM для Malika?
**A)** 0 · **B)** NULL · **C)** ошибка

<details>
<summary>Ответ</summary>

**B: NULL.** Если нет входных значений, отличных от NULL, SUM возвращает NULL. A предполагает автоматический ноль; C считает отсутствие значения ошибкой SQL.

</details>

```console
$ docker compose exec db psql -f /lab/sorov.sql
 id | customer |  jami   
----+----------+---------
  1 | Dilnoza  | 3600000
  2 | Jasur    | 4700000
  3 | Malika   |        
(3 rows)
```

Пустая сумма означает NULL. Чтобы отчёт показывал ноль, замените строку 2 на `COALESCE(SUM(...), 0) AS jami`. Полный запрос:

```sql
SELECT orders.id, orders.customer,
       COALESCE(SUM(order_items.quantity * order_items.unit_price), 0) AS jami
FROM orders
LEFT JOIN order_items ON order_items.order_id = orders.id
GROUP BY orders.id
ORDER BY orders.id;
```

**COALESCE** рассматривает разделённые запятыми аргументы по порядку и возвращает первый, отличный от NULL. Внутренние скобки содержат выражение SUM; внешние — результат SUM и запасной ноль. Остальные строки прежние.

| Заказ | Подходящих позиций | SUM | COALESCE(SUM, 0) |
|---|---|---|---|
| 1 | 2 | 3600000 | 3600000 |
| 2 | 2 | 4700000 | 4700000 |
| 3 | 0 | `NULL` | 0 |

Ожидайте три заказа с суммами 3600000, 4700000 и 0:

```console
$ docker compose exec db psql -f /lab/sorov.sql
 id | customer |  jami   
----+----------+---------
  1 | Dilnoza  | 3600000
  2 | Jasur    | 4700000
  3 | Malika   |       0
(3 rows)
```

`LEFT JOIN` сохраняет заказ; `COALESCE` заменяет отсутствующую сумму. Нужны оба: COALESCE не возвращает строку, уже исключённую INNER JOIN.

## Глубже (необязательно): неравенство с NULL

`<>` означает «не равно», но сравнение комментария NULL с текстом снова даёт неизвестно. Предскажите результат для комментариев, отличных от `'ertalab yetkazing'`: строк не останется. У Jasur сравнение ложно, у остальных двух неизвестно.

```console
$ docker compose exec db psql -c "SELECT id, customer FROM orders WHERE note <> 'ertalab yetkazing'"
 id | customer 
----+----------
(0 rows)
```

**IS DISTINCT FROM** сравнивает значения, считая NULL сравнимым отсутствующим значением. NULL и этот текст различны, поэтому Dilnoza и Malika теперь остаются. Два NULL считались бы неразличными.

```console
$ docker compose exec db psql -c "SELECT id, customer FROM orders WHERE note IS DISTINCT FROM 'ertalab yetkazing'"
 id | customer 
----+----------
  1 | Dilnoza
  3 | Malika
(2 rows)
```

Здесь тоже нет `ORDER BY`. Используйте это условие, когда правило требует «отличается, включая отсутствие значения», а не обычного SQL-неравенства.

## Частые ошибки

1. **`WHERE note = NULL`.** Допустимый SQL, пустой результат. В разделе «LEFT JOIN и NULL» есть полный ошибочный запрос и реальный вывод. Используйте `WHERE note IS NULL`; `''` — отдельное значение.
2. **Ожидание автоматической группировки от SUM.** Запрос из четырёх строк в разделе «GROUP BY и SUM» даёт реальную ошибку `must appear in the GROUP BY clause`. Добавьте `GROUP BY orders.id`, сохраните `ORDER BY` для определённого порядка.
3. **INNER JOIN в отчёте обо всех заказах.** Запрос работает, но исключает Malika. Используйте LEFT JOIN и COALESCE для суммы; одна замена NULL не восстановит строку.
4. **Фильтр правой таблицы после LEFT JOIN.** `WHERE order_items.quantity > 0` снова отбрасывает строку с добавленными NULL. Если нужно сохранить каждую левую строку, поместите ограничение позиций в `ON` или уберите его.
5. **Сортировка NULL-суммы через DESC.** По умолчанию PostgreSQL ставит NULL первым при убывании. Заданию нужен числовой ноль: примените COALESCE до сортировки.

Внешний ключ также не создаёт автоматически индекс на ссылающемся столбце. Выбор индекса и проверка связи — отдельные задачи.

## Проверьте себя

1. Чем JOIN и LEFT JOIN отличаются для заказа без позиций?

<details>
<summary>Ответ</summary>

JOIN исключает заказ. LEFT JOIN сохраняет одну строку результата с NULL в правых столбцах. Совпавшие пары ведут себя одинаково в обоих вариантах.

</details>

2. Почему `WHERE note = NULL` не возвращает строки?

<details>
<summary>Ответ</summary>

Обычное равенство с NULL даёт неизвестно; WHERE требует истину. `IS NULL` проверяет отсутствие и возвращает логическое значение.

</details>

3. Предскажите сумму Malika после `LEFT JOIN`, `GROUP BY` и `COALESCE(SUM(...), 0)`: **A)** NULL · **B)** 0 · **C)** строки нет.

<details>
<summary>Ответ</summary>

**B.** LEFT JOIN сохраняет заказ; SUM не получает суммы, отличной от NULL, и возвращает NULL; COALESCE заменяет его на 0. A забывает COALESCE, C описывает INNER JOIN.

</details>

4. Из GB-5.01: что возможно, если два процесса одновременно обновляют один JSON-файл?

<details>
<summary>Ответ</summary>

Обновление может потеряться, а файл — повредиться. База координирует доступ; нескольким изменениям, которые должны выполниться вместе, нужна транзакция. Она рассматривается в GB-5.07.

</details>
