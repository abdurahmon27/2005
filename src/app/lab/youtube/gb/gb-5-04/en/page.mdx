## What you will learn

bozor needs a report with a total for every order. The total is not stored in a column: its items live in another table. How do you calculate it without losing an order that has no items?

**One idea:** pair rows from related tables, group the pairs by order, and calculate each total. Preserve unmatched orders and handle their missing values explicitly.

By the end, you can:

- connect `orders` and `order_items` with `REFERENCES`;
- use `JOIN`, `LEFT JOIN`, `GROUP BY`, and `SUM` to build the report;
- explain why `note = NULL` finds nothing and use `IS NULL` and `COALESCE` correctly;
- write two SQL queries and check them with `go test`.

| Word | Plain meaning | English term |
|---|---|---|
| `JOIN` / `LEFT JOIN` | pair table rows; the left variant also preserves unmatched left rows | join / left join |
| `GROUP BY` + `SUM` | form groups and calculate one sum per group | grouping / aggregate |
| `NULL` | a missing or unknown value; ordinary comparisons can produce an unknown result | NULL / three-valued logic |

Two helpers: a **foreign key** (`REFERENCES`) requires a referenced row to exist. **COALESCE** returns the first non-NULL value from its arguments.

| Line | Code | What it does |

## JOIN: one result row per pair

We need the customer for each item. Replace the contents of a new `sorov.sql` file with this complete query. Replace that file again for each later query on this page; do not append queries.

```sql
SELECT orders.customer, order_items.quantity
FROM orders
JOIN order_items ON order_items.order_id = orders.id;
```

| Line | Code | What it does |
|---|---|---|
| 1 | `SELECT orders.customer, order_items.quantity` | select two columns; `table.column` identifies which table supplies each one |
| 2 | `FROM orders` | start from the order table |
| 3 | `JOIN order_items ON ...` | pair rows where `order_items.order_id = orders.id`; `ON` specifies the matching condition |

The same order can match several items. Here is the pairing state, before projecting the selected columns:

| Order | Matching item quantities | JOIN result rows |
|---|---|---|
| 1, Dilnoza | 2, 3 | 2 |
| 2, Jasur | 1, 1 | 2 |
| 3, Malika | no matching item | 0 |

**Predict:** how many rows will this JOIN return?
**A)** 3 orders · **B)** 4 pairs · **C)** 5 rows, including Malika

<details>
<summary>Answer</summary>

**B: 4.** `JOIN` means `INNER JOIN`: only matching pairs survive. A counts orders rather than pairs. C would require preserving the unmatched order.

</details>

$ docker compose exec db psql -f /lab/sorov.sql

----------+----------

 Dilnoza  |        3

Malika is absent. There is no `ORDER BY` in this introductory query: the displayed order is observed, not guaranteed. Later report queries specify their order explicitly.

## GROUP BY and SUM: one total per order

For each item, multiply quantity by its recorded unit price. `*` is multiplication here; it selected every column in `SELECT *`. **SUM** is an aggregate: it combines input values into one value. `AS jami` names the output column `jami` (“total”).

First replace `sorov.sql` with this incomplete attempt:

```sql
SELECT orders.id, orders.customer,
       SUM(order_items.quantity * order_items.unit_price) AS jami
FROM orders
JOIN order_items ON order_items.order_id = orders.id;
```

**Predict:** will mixing an aggregate with individual order columns work without grouping?
**A)** yes, one total per order · **B)** yes, one total for all orders · **C)** a GROUP BY error

<details>
<summary>Answer</summary>

**C.** The query does not state which rows belong to each total. A assumes grouping happens automatically. B leaves no single `orders.id` to show beside the overall sum.

</details>

```console
$ docker compose exec db psql -f /lab/sorov.sql
psql:/lab/sorov.sql:4: ERROR:  column "orders.id" must appear in the GROUP BY clause or be used in an aggregate function
LINE 1: SELECT orders.id, orders.customer,
               ^
```

`psql:/lab/sorov.sql:4` identifies the file and the line where the statement ends. `LINE 1` and `^` point to the offending expression. “Must appear in the GROUP BY clause or be used in an aggregate function” states the missing rule for `orders.id`.

Add `GROUP BY orders.id` to form one group per order identifier. Add `ORDER BY orders.id` for predictable ascending order:

```sql
SELECT orders.id, orders.customer,
       SUM(order_items.quantity * order_items.unit_price) AS jami
FROM orders
JOIN order_items ON order_items.order_id = orders.id
GROUP BY orders.id
ORDER BY orders.id;
```

Lines 1–4 still select the order fields, calculate the sum, and join the tables. Line 5 forms the groups; line 6 sorts the result and ends the statement. `SUM(...)` evaluates its parenthesized expression for each input row, then adds the values within that group.

| Group | Item amounts in tiyin | SUM |
|---|---|---|
| order 1 | `2 × 1200000 + 3 × 400000` | 3600000 |
| order 2 | `1 × 3500000 + 1 × 1200000` | 4700000 |

Why is `orders.customer` absent from `GROUP BY`? `orders.id` is the table's primary key, so each identifier determines exactly one customer. PostgreSQL recognizes that dependency here. It is not permission to select arbitrary ungrouped columns.

**Predict:** how many result rows remain?
**A)** 3 · **B)** 2 · **C)** 4

<details>
<summary>Answer</summary>

**B: 2.** The four joined rows form two groups. A counts Malika even though JOIN removed her. C counts inputs before grouping.

</details>

```console
$ docker compose exec db psql -f /lab/sorov.sql
 id | customer |  jami   
----+----------+---------
  1 | Dilnoza  | 3600000
  2 | Jasur    | 4700000
(2 rows)
```

The amounts are 3 600 000 and 4 700 000 tiyin. `SUM(bigint)` returns `numeric`, PostgreSQL's exact numeric type, even for these integer amounts. Reading it into Go is covered in [GB-5.05 · Go to Postgres: pgx](/lab/youtube/gb/gb-5-05/en).

## LEFT JOIN and NULL: preserve the missing order

The report needs every order. **LEFT JOIN** preserves all rows from the left table, here `orders`. For an unmatched row it supplies NULL values for the right table's columns. It does not insert a row into `order_items`.

Replace `sorov.sql` with:

```sql
SELECT orders.customer, order_items.quantity
FROM orders
LEFT JOIN order_items ON order_items.order_id = orders.id;
```

Only line 3 changed: `LEFT` now preserves the unmatched order. Expect four matching pairs and one row for Malika, whose quantity is NULL:

```console
$ docker compose exec db psql -f /lab/sorov.sql
 customer | quantity 
----------+----------
 Dilnoza  |        2
 Dilnoza  |        3
 Jasur    |        1
 Jasur    |        1
 Malika   |         
(5 rows)
```

**NULL** means a missing or unknown value. It is neither zero nor `''`. Ordinary `=` and `<>` comparisons with NULL produce NULL, an unknown result. This is **three-valued logic**: true, false, unknown. `WHERE` keeps only true.

| `note` | `note = NULL` | Kept by WHERE? | `note IS NULL` |
|---|---|---|---|
| `NULL` | unknown (`NULL`) | no | true |
| `'ertalab yetkazing'` | unknown (`NULL`) | no | false |
| `''` | unknown (`NULL`) | no | false |

The empty-string row illustrates the rule; it is not an extra row in this seed.

**Predict:** two orders have NULL notes. How many rows does `WHERE note = NULL` return?
**A)** 2 · **B)** 0 · **C)** syntax error

<details>
<summary>Answer</summary>

**B: 0.** The predicate is unknown for every row, never true. A treats NULL as an ordinary comparable value. C is wrong: the query is valid and silently returns nothing.

</details>

```console
$ docker compose exec db psql -c 'SELECT id, customer FROM orders WHERE note = NULL'
 id | customer 
----+----------
(0 rows)
```

Use **IS NULL** to ask whether a value is missing. It always returns true or false; `IS NOT NULL` asks the opposite. Expect Dilnoza and Malika:

```console
$ docker compose exec db psql -c 'SELECT id, customer FROM orders WHERE note IS NULL'
 id | customer 
----+----------
  1 | Dilnoza
  3 | Malika
(2 rows)
```

These two demonstration filters have no `ORDER BY`; their displayed row order is not guaranteed. The homework query adds it.

## COALESCE: replace a missing total with zero

Now preserve all orders in the grouped report. Replace only `JOIN` with `LEFT JOIN` in the earlier grouped query:

```sql
SELECT orders.id, orders.customer,
       SUM(order_items.quantity * order_items.unit_price) AS jami
FROM orders
LEFT JOIN order_items ON order_items.order_id = orders.id
GROUP BY orders.id
ORDER BY orders.id;
```

`SUM` ignores NULL inputs. Malika's group contains one result row, whose quantity and unit price are NULL. Multiplication therefore gives NULL; there are no non-NULL amounts to add.

**Mid-lesson check:** what is Malika's SUM?
**A)** 0 · **B)** NULL · **C)** error

<details>
<summary>Answer</summary>

**B: NULL.** With no non-NULL input, SUM returns NULL. A assumes the aggregate supplies zero automatically; C assumes missing input is a SQL error.

</details>

```console
$ docker compose exec db psql -f /lab/sorov.sql
 id | customer |  jami   
----+----------+---------
  1 | Dilnoza  | 3600000
  2 | Jasur    | 4700000
  3 | Malika   |        
(3 rows)
```

The blank total is NULL. To make the report show zero, replace line 2 with `COALESCE(SUM(...), 0) AS jami`. The full query is:

```sql
SELECT orders.id, orders.customer,
       COALESCE(SUM(order_items.quantity * order_items.unit_price), 0) AS jami
FROM orders
LEFT JOIN order_items ON order_items.order_id = orders.id
GROUP BY orders.id
ORDER BY orders.id;
```

**COALESCE** considers its comma-separated arguments in order and returns the first non-NULL one. The inner parentheses enclose SUM's expression; the outer parentheses hold SUM's result and the fallback zero. Other lines are unchanged.

| Order | Matching items | SUM | COALESCE(SUM, 0) |
|---|---|---|---|
| 1 | 2 | 3600000 | 3600000 |
| 2 | 2 | 4700000 | 4700000 |
| 3 | 0 | `NULL` | 0 |

Expect three orders with totals 3600000, 4700000, and 0:

```console
$ docker compose exec db psql -f /lab/sorov.sql
 id | customer |  jami   
----+----------+---------
  1 | Dilnoza  | 3600000
  2 | Jasur    | 4700000
  3 | Malika   |       0
(3 rows)
```

`LEFT JOIN` preserves the order; `COALESCE` replaces its missing total. Both are needed: COALESCE cannot restore a row already removed by INNER JOIN.

## Going deeper (optional): inequality with NULL

`<>` means “not equal,” but comparing a NULL note with text still gives unknown. Predict the result for notes different from `'ertalab yetkazing'`: no rows survive. Jasur's comparison is false; the other two are unknown.

```console
$ docker compose exec db psql -c "SELECT id, customer FROM orders WHERE note <> 'ertalab yetkazing'"
 id | customer 
----+----------
(0 rows)
```

**IS DISTINCT FROM** compares values while treating NULL as a comparable missing value. NULL and that text are distinct, so Dilnoza and Malika now survive. Two NULL values would be considered not distinct.

```console
$ docker compose exec db psql -c "SELECT id, customer FROM orders WHERE note IS DISTINCT FROM 'ertalab yetkazing'"
 id | customer 
----+----------
  1 | Dilnoza
  3 | Malika
(2 rows)
```

These filters also omit `ORDER BY`. Use this predicate when the business rule needs “different, including a missing value,” rather than ordinary SQL inequality.

## Common mistakes

1. **`WHERE note = NULL`.** Valid SQL, empty result. The “LEFT JOIN and NULL” section shows the complete failing query and its real output. Use `WHERE note IS NULL`; `''` is a separate value.
2. **Expecting SUM to group automatically.** The four-line query in “GROUP BY and SUM” produces the real `must appear in the GROUP BY clause` error. Add `GROUP BY orders.id`; keep `ORDER BY` for deterministic order.
3. **INNER JOIN in an all-orders report.** The query runs but drops Malika. Use LEFT JOIN, then COALESCE for the total; replacing NULL alone cannot recover her row.
4. **Filtering the right table after LEFT JOIN.** `WHERE order_items.quantity > 0` rejects the NULL-extended row again. If the intended rule is to keep every left row, put an item restriction in `ON` instead, or omit it.
5. **Sorting a NULL sum with DESC.** By default PostgreSQL puts NULL first in descending order. The homework needs a numeric zero: apply COALESCE before ordering.

A foreign key also does not automatically create an index on its referencing column. Choosing an index is separate from enforcing the relationship.
