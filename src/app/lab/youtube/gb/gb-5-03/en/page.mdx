## What you will learn

The `bozor.json` file cannot prevent an empty name or a negative price from being written. Only our Go code checks those rules.
If another program also writes data, where should the rules live?

**The one idea:** a table's schema—its columns, types and rules—is a contract the database checks on every write.
When a rule is broken, Postgres returns an error and does not store the invalid row.

By the end of the lesson you will:

- create the bozor `products` table with `CREATE TABLE`;
- add rows with `INSERT`, then select them with `SELECT`, `WHERE`, `AND`, `ORDER BY` and `LIMIT`;
- get the new database-generated `id` with `RETURNING`;
- read `NOT NULL`, `UNIQUE` and `CHECK` errors, then add a rule against empty names.

| Word | Plain meaning | English term |
|---|---|---|
| table | columns with names and types; each row is one product record | table |
| `INSERT` / `SELECT` | write a new row / read existing rows | insert / select |
| constraint | a rule that rejects invalid rows inside the database | constraint |

## INSERT: write four products

Map each product's values to its columns. **`INSERT INTO`** specifies the destination table and columns.
We omit `id`: the database generates it. Here is the complete course file `seed.sql`:

```sql filename="seed.sql" showLineNumbers
INSERT INTO products (name, price, stock, active)
VALUES ('olma', 1200000, 40, true),
       ('non', 400000, 3, true),
       ('choy', 2500000, 8, true),
       ('oʻrik', 3500000, 2, true);
```

Line 1 sets the column order. Line 2 starts with `VALUES`; each group of parentheses contains one row in that order.
Lines 3–5 supply the remaining products; commas separate rows, and the final `;` ends the statement.
`'olma'` is single-quoted text, the numbers are tiyin, and `true` marks an active product.
The names mean apple (`olma`), bread (`non`), tea (`choy`) and apricot (`oʻrik`).

How many rows will executing this file write?

**A)** `1` · **B)** `4` · **C)** `5`, because there are five columns

<details>
<summary>Answer</summary>

**B.** There are four parenthesized groups after `VALUES`. One statement can write several rows; the column count is not the row count.

</details>

```console
$ docker compose exec -T db psql -f /lab/seed.sql
INSERT 0 4
```

In `INSERT 0 4`, `4` is the number of inserted rows. The first `0` is a historical field and is always zero now.
**`SELECT`** reads rows; `*` means all columns, and `FROM products` names the source table.
Which IDs will appear: **A)** all `0` · **B)** `1, 2, 3, 4` · **C)** no `id`?

<details>
<summary>Answer</summary>

**B.** The new table's identity counter supplied the next number for each row. Omitting `id` from `INSERT` does not remove the column.

</details>

```console
$ docker compose exec -T db psql -c 'SELECT * FROM products'
 id | name  |  price  | stock | active 
----+-------+---------+-------+--------
  1 | olma  | 1200000 |    40 | t
  2 | non   |  400000 |     3 | t
  3 | choy  | 2500000 |     8 | t
  4 | oʻrik | 3500000 |     2 | t
(4 rows)
```

The first line gives column names; the separators draw the table; `(4 rows)` gives the row count.
`t` in `active` means `true`. State change: zero rows → four products.

## SELECT: filter, sort and limit

We need names and prices rather than the whole table. `SELECT name, price` returns only those two columns.
`WHERE stock < 5` keeps only rows with stock below five; `<` means strictly less than.

**A)** olma, choy · **B)** non, oʻrik · **C)** every product?

<details>
<summary>Answer</summary>

**B.** non has stock `3`, and oʻrik has `2`; olma with `40` and choy with `8` fail the condition.

</details>

```console
$ docker compose exec -T db psql -c 'SELECT name, price FROM products WHERE stock < 5'
 name  |  price  
-------+---------
 non   |  400000
 oʻrik | 3500000
(2 rows)
```

`AND` requires both conditions to be true. What remains if we add `price > 1000000`?
`>` means strictly greater than.

**A)** non · **B)** oʻrik · **C)** non and oʻrik

<details>
<summary>Answer</summary>

**B.** non costs `400000`, so it fails the new condition. oʻrik costs `3500000`; both conditions are true.

</details>

```console
$ docker compose exec -T db psql -c 'SELECT name, price FROM products WHERE stock < 5 AND price > 1000000'
 name  |  price  
-------+---------
 oʻrik | 3500000
(1 row)
```

`ORDER BY price DESC` sorts by decreasing price; omitting `DESC` gives ascending order.
Without `ORDER BY`, Postgres does not guarantee the order of rows.

```sql
SELECT name, price
FROM products
WHERE stock < 5
ORDER BY price DESC;
```

Which rows will appear, and in what order?

**A)** non, oʻrik · **B)** oʻrik, non · **C)** olma, choy

<details>
<summary>Answer</summary>

**B.** The filter is unchanged: oʻrik and non remain. `DESC` puts `3500000` before `400000`.
A uses ascending order; C ignores the filter.

</details>

```console
$ docker compose exec -T db psql -c 'SELECT name, price FROM products WHERE stock < 5 ORDER BY price DESC'
 name  |  price  
-------+---------
 oʻrik | 3500000
 non   |  400000
(2 rows)
```

`LIMIT 2` allows at most two result rows.
This time there is no `WHERE`: which are the two most expensive products in the whole table?

**A)** oʻrik, choy · **B)** olma, non · **C)** oʻrik, non

<details>
<summary>Answer</summary>

**A.** Decreasing prices are `3500000`, `2500000`, `1200000`, `400000`.
`LIMIT` takes the first two rows of the sorted result; C incorrectly keeps the earlier filter.

</details>

```console
$ docker compose exec -T db psql -c 'SELECT name, price FROM products ORDER BY price DESC LIMIT 2'
 name  |  price  
-------+---------
 oʻrik | 3500000
 choy  | 2500000
(2 rows)
```

| Step | Rows or result |
|---|---|
| `FROM products` | four products |
| `WHERE stock < 5` | non and oʻrik |
| `ORDER BY price DESC` | oʻrik, non |
| `SELECT name, price` | only name and price in each row |

This table explains the result; in SQL text, `SELECT` is written first.
When prices tie, add a second key for a stable order: `ORDER BY price, id`.

## Quotes: text or column name

SQL text uses single quotes: `'olma'`. Double quotes delimit a name: `"olma"` is a column name.
The outer shell quotes pass the SQL text as one argument; they are separate from SQL quoting.

```sql
SELECT name FROM products WHERE name = "olma";
```

What will this broken query do? `=` tests equality in SQL.

**A)** find the apple · **B)** look for an `olma` column and fail · **C)** return every row

<details>
<summary>Answer</summary>

**B.** The table has a `name` column, but no `olma` column. A confuses a text value with a column name.

</details>

```console
$ docker compose exec -T db psql -c 'SELECT name FROM products WHERE name = "olma"'
ERROR:  column "olma" does not exist
LINE 1: SELECT name FROM products WHERE name = "olma"
                                               ^
```

`column … does not exist` says the requested column is absent. `LINE 1` identifies the query line, and `^` marks the error position.
The fix uses `'olma'` inside SQL and double quotes outside for the shell.
Now one apple row is returned:

```console
$ docker compose exec -T db psql -c "SELECT name FROM products WHERE name = 'olma'"
 name 
------
 olma
(1 row)
```

## RETURNING: a new id and a missing rule

We need to know which `id` the database assigned to a new product immediately.
**`RETURNING id`** returns `id` from the inserted row. Using it from Go comes in GB-5.05.
What ID will `sut` (milk) receive: **A)** `4` · **B)** `5` · **C)** no result?

<details>
<summary>Answer</summary>

**B.** The four previous rows received `1`–`4`. `RETURNING` does not cancel the insert: `INSERT 0 1` below also confirms one inserted row.

</details>

```console
$ docker compose exec -T db psql -c "INSERT INTO products (name, price) VALUES ('sut', 900000) RETURNING id"
 id 
----
  5
(1 row)

INSERT 0 1
```

But a type does not check a business rule. `''` is text of length zero; `-5` is also a valid `bigint` value.
`RETURNING *` returns all columns of the new row. What happens?

**A)** the database rejects it · **B)** the row is inserted · **C)** the negative price becomes `0`

<details>
<summary>Answer</summary>

**B.** So far `name` and `price` have only types. Those types forbid neither empty text nor a negative number; there is no automatic correction.

</details>

```console
$ docker compose exec -T db psql -c "INSERT INTO products (name, price) VALUES ('', -5) RETURNING *"
 id | name | price | stock | active 
----+------+-------+-------+--------
  6 |      |    -5 |       | 
(1 row)

INSERT 0 1
```

The blank `stock` and `active` cells are `NULL` here: no values were supplied, and there is no `DEFAULT`.
But `name` is `''`, not `NULL`. Plain `psql` output can display both as blank cells.
State change: five valid rows → six rows, one breaking the business rules.

## Constraints: the database rejects invalid rows

The price must be positive regardless of which program writes it.
A **constraint** keeps that requirement in the table. Now use the main `products.sql`:

```sql filename="products.sql" showLineNumbers
DROP TABLE IF EXISTS products;
CREATE TABLE products (
    id     bigint
           GENERATED ALWAYS AS IDENTITY
           PRIMARY KEY,
    name   text    NOT NULL UNIQUE,
    price  bigint  NOT NULL CHECK (price > 0),
    stock  integer NOT NULL DEFAULT 0 CHECK (stock >= 0),
    active boolean NOT NULL DEFAULT true
);
```

| Line | New rule | Result |
|---|---|---|
| 1 | `DROP TABLE IF EXISTS products` | removes the table and all its rows if it exists |
| 2–5 | `CREATE TABLE`, identity, `PRIMARY KEY` | a new table and primary key, as before |
| 6 | `NOT NULL UNIQUE` | the name cannot be `NULL` or duplicated |
| 7 | `NOT NULL CHECK (price > 0)` | price must be present and above zero |
| 8 | `NOT NULL DEFAULT 0 CHECK (stock >= 0)` | omitted stock becomes `0`; negative stock is rejected |
| 9 | `NOT NULL DEFAULT true` | omitted active status becomes `true`; explicit `NULL` is rejected |
| 10 | `);` | ends the table definition |

`>=` means greater than or equal to. `DEFAULT` supplies an omitted column's value; it does not replace an explicit `NULL`.
`CHECK (condition)` rejects a row when the condition is false; a `NULL` result passes.
That is why required values also need `NOT NULL`. `PRIMARY KEY` supplies that requirement for `id`.

| Write path | What is checked | If a rule is broken |
|---|---|---|
| value type | compatibility with `bigint`, `text`, `integer`, `boolean` | error |
| `NOT NULL` | missing value | error |
| `CHECK` | condition is false | error |
| `UNIQUE` | duplicate of an existing row's value | error |
| storage | every requirement passed | new row |

This is the path observed on PostgreSQL 18.7; the order of checks is not a guarantee applications should rely on.
An error does not leave half an invalid row stored; do not expect the first message to list every problem.

Changing tables without dropping them comes in [GB-5.06](/lab/youtube/gb#gb-5-06).
What happens to the `('', -5)` row now?

**A)** a `NOT NULL` error for the empty name · **B)** a `CHECK` error for the price · **C)** both errors

<details>
<summary>Answer</summary>

**B.** `''` is a present value, so it passes `NOT NULL`. But price `-5` violates `price > 0`.
C assumes one error message lists every broken rule.

</details>

```console
$ docker compose exec -T db psql -c "INSERT INTO products (name, price) VALUES ('', -5)"
ERROR:  new row for relation "products" violates check constraint "products_price_check"
DETAIL:  Failing row contains (5, , -5, 0, t).
```

`new row for relation … violates check constraint` says the table's new row broke its CHECK rule.
Here `relation` means table; `products_price_check` is the rule's name.
`DETAIL` shows the rejected row: `id=5`, empty text for the name, price `-5`, stock `0` and active status `t`.
`DEFAULT` supplied the last two values. The table still contains four rows.

To reject empty text too, add this to line 6; you will do it in the homework:

```sql
name   text    NOT NULL UNIQUE CHECK (name <> ''),
```

`<>` means not equal. `''` is two adjacent single quotes: empty text.
This rule does not check names consisting of spaces; today's task concerns exactly empty text.

Mid-lesson question: the table already has `choy`. What happens when another `choy` is inserted at a different price?

**A)** a second row is added · **B)** the old price is updated · **C)** a `UNIQUE` error

<details>
<summary>Answer</summary>

**C.** The rule applies to the name, not the price. `INSERT` tries to add a new row; it does not update an existing row's price.

</details>

```console
$ docker compose exec -T db psql -c "INSERT INTO products (name, price) VALUES ('choy', 2600000)"
ERROR:  duplicate key value violates unique constraint "products_name_key"
DETAIL:  Key (name)=(choy) already exists.
```

`duplicate key value` means a repeated key value; `already exists` identifies the value already present.
`products_name_key` is the uniqueness rule for the name. No row was added.

How is an explicit `NULL` name checked?

**A)** `NOT NULL` rejects it · **B)** `DEFAULT` creates a name · **C)** it is the same as empty text

<details>
<summary>Answer</summary>

**A.** `NULL` is an absent value; `''` is present text. There is no `DEFAULT` for `name` either.
A `CHECK` alone is not enough to reject `NULL`.

</details>

```console
$ docker compose exec -T db psql -c "INSERT INTO products (name, price) VALUES (NULL, 900000)"
ERROR:  null value in column "name" of relation "products" violates not-null constraint
DETAIL:  Failing row contains (7, null, 900000, 0, t).
```

`null value in column "name" … violates not-null constraint` says `NULL` in `name` broke the NOT NULL rule.
The row in `DETAIL` was not stored either. Four products remain in the table.

## Going deeper (optional): gaps between IDs

An identity number is allocated before the row is checked. Rejecting the row does not reclaim that number.
Three `INSERT` statements were rejected. What appears when we insert `sut` and request its `id` now?

**A)** `5` · **B)** `8` · **C)** `4`

<details>
<summary>Answer</summary>

**B.** Those attempts received `5`, `6` and `7` from the identity counter before constraint checking.
Rejecting a row does not move the counter back. A confuses the row count with the next `id`.

</details>

```console
$ docker compose exec -T db psql -c "INSERT INTO products (name, price) VALUES ('sut', 900000) RETURNING id"
 id 
----
  8
(1 row)

INSERT 0 1
```

| Action | ID allocated | Rows in the table |
|---|---|---|
| initial products | `1`–`4` | `4` |
| invalid price | `5` | `4` |
| duplicate name | `6` | `4` |
| `NULL` name | `7` | `4` |
| sut | `8` | `5` |

`id` identifies a row; it is neither a product count nor a gapless position number.
Do not rely on consecutive IDs. This behavior comes from the sequence counter used by identity.

## Common mistakes

1. **“NOT NULL also rejects empty names.”** In the `VALUES ('', -5)` experiment, `CHECK` rejected the price; the name passed `NOT NULL`.
   Fix: add `CHECK (name <> '')` to `name` and keep `NOT NULL` for `NULL`.
2. **Double-quoting text.** The Quotes section showed the `WHERE name = "olma"` error.
   `column "olma" does not exist` means the database looked for a column. Fix: `WHERE name = 'olma'`.
3. **Expecting INSERT to update an old row.** The duplicate `choy` caused a `UNIQUE` error; its old price stayed unchanged.
   Use `INSERT` to add new rows.
4. **Relying on the displayed order.** Without `ORDER BY`, order is unspecified. State the required column and add `id` to break ties.
5. **Expecting recreation to preserve data.** `DROP TABLE` removes the rows too.
   This lab reloaded `seed.sql`; changing a system with existing data is the topic of GB-5.06.

```sql filename="solution/arzon.sql" showLineNumbers
SELECT name, price
FROM products
WHERE active AND price < 3000000
ORDER BY price, id
LIMIT 2;
```

Line 1 selects the columns; line 2 names the source table; line 3 checks active status and price together.
Line 4 sorts by ascending price, using `id` to break ties; line 5 limits the result.
The test catalog also contains active `qand` (sugar, `1100000`) and inactive `sut` (milk, `900000`).
Its expected answer is therefore `non|400000`, then `qand|1100000`.
The second dataset compares prices `2999999`, `3000000`, `3000001`: the boundary value `3000000` is excluded.
