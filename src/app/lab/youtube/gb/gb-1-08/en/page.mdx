## What you will learn

In the last lesson bozor accepted an apple priced at one hundred quadrillion soʻm and printed a negative price on the
receipt:

```console
$ ./_video/run.sh 00-gb107 bash -c 'go build && ./bozor add olma 100000000000000000 1'
bozor ishga tushdi
versiya: 0.1.0
 0 false
olma -8446744073709551616 true 40 1.5
olma 39
olma, 1 dona   -84467440737095516.-16
QQS            -912720851596686.-13
yetkazish          15000.00
jami           -85380161588677202.-29
```

The price, the VAT (`QQS`) and the total (`jami`) are negative, and there is a minus even after the decimal point. The
code checked every command, but nobody had tried an input like this. How do you find this bug with a program instead of
by hand, and how do you make sure it never comes back?

**The one idea:** `go test` compiles your package together with its `_test.go` files into a separate **test binary** and
calls every `TestXxx(t)` function. `t.Errorf` only puts a "failed" mark on `t`, and the function goes on; `t.Fatalf`
stops this test function. If the mark is there at the end, the binary prints `FAIL` and exits with code 1.

By the end of the lesson you will:

- write a test for a Go function and run it with `go test` and `go test -v`;
- read a failed test's message line by line: which test, which file and line, what came back, what was expected;
- write a table-driven test: the cases are data, the checking code is written once, and each row runs as a separate
  subtest through `t.Run`;
- find and fix two real bugs in bozor with a test, and run a single subtest on its own with `-run`.

Today's three core new words:

| Word | Plain meaning | English term |
|---|---|---|
| test file and `go test` | a file whose name ends in `_test.go`; `go test` calls its `func TestXxx(t *testing.T)` functions in a separate test binary, while `go build` leaves the file out of the binary | test file, `go test` |
| `t.Errorf` | writes a message and marks the test as "failed", but the function goes on | `t.Errorf` |
| table-driven test | a list of cases (`name`, `in`, `want`, `wantErr`) and code that checks them in one loop; each row is a separate **subtest** | table-driven test, subtest |

Two helper words: **`t.Fatalf`** writes a message like `t.Errorf`, but stops this test function (or subtest) at once;
**`-v` and `-run`** are `go test` flags: `-v` prints the name of every test, `-run` runs only the tests whose name
matches a pattern.

## Where the bug is: not in Atoi, in the multiplication

The `100000000000000000` (10¹⁷) from the start of the lesson is a valid number for `Atoi`: `int` is 8 bytes on this
machine, so its maximum is 9 223 372 036 854 775 807 (about nine quintillion), and 10¹⁷ fits. The problem is the last line
of `parsePrice`: `int64(som) * tiyinPerSom` (*som* is the price in soʻm; 1 soʻm = 100 tiyin). The result should be 10¹⁹.
That is past the `int64` limit, and as in GB-1.03 the excess wraps around and the number turns negative
([Go spec: Integer overflow](https://go.dev/ref/spec#Integer_overflow)):

| Step | Value |
|---|---|
| `s` (the input text) | `"100000000000000000"` |
| `som, err := strconv.Atoi(s)` | `som` = 100 000 000 000 000 000, `err` = `nil`: the number fits in `int` |
| `int64(som) * tiyinPerSom`, the result we need | 10 000 000 000 000 000 000 = 10¹⁹ > 9 223 372 036 854 775 807 |
| `int64(som) * tiyinPerSom`, the real result | 10¹⁹ − 2⁶⁴ = **−8 446 744 073 709 551 616**: overflow |

The first line of the receipt is this negative tiyin amount divided into soʻm: `-84467440737095516.-16`.

Today you will find this bug with a test and fix it. You need three things:

1. a test file and the `go test` command;
2. `t.Errorf`, that is, reporting that a test failed: what failed and why;
3. a table-driven test: many cases checked by one piece of code.

## The test file and the test function

A **test** is ordinary Go code in a separate file. You choose the start of the file name, here `price`, but it must end
in `_test.go`. `go build` does not put such a file into the bozor binary; `go test` finds it
([pkg.go.dev/testing](https://pkg.go.dev/testing): "excluded from regular package builds but will be included when the
"go test" command is run"). The first test checks two cases (`_video/01-test/price_test.go`):

```go filename="_video/01-test/price_test.go" showLineNumbers
package main

import "testing"

func TestParsePrice(t *testing.T) {
	got, err := parsePrice("12000")
	if err != nil || got != 1_200_000 {
		t.Errorf("parsePrice(%q) = %d, %v; kutilgan %d, xatosiz", "12000", got, err, 1_200_000)
	}
	got, err = parsePrice("500")
	if err != nil || got != 50_000 {
		t.Errorf("parsePrice(%q) = %d, %v; kutilgan %d, xatosiz", "500", got, err, 50_000)
	}
}
```

| Line | Code | What it does |
|---|---|---|
| 1 | `package main` | the same package as `main.go`: that is why the test can call `parsePrice` directly |
| 3 | `import "testing"` | the test package from the standard library |
| 5 | `func TestParsePrice(t *testing.T) {` | the test function: its name starts with `Test`, and the next letter must not be lowercase. The parameter is `t`, its type is `testing.T`: you report the result through this `t`. The star `*` in the type means **pointer**; we open it in [GB-2.04](/lab/youtube/gb/gb-2-04/en) |
| 6 | `got, err := parsePrice("12000")` | an ordinary call: 12 000 soʻm, the results go to `got` and `err` |
| 7 | `if err != nil \|\| got != 1_200_000 {` | the condition: there is an error, **or** the result is not 1 200 000 tiyin. `\|\|` means "or" (GB-1.05) |
| 8 | `t.Errorf(…)` | writes a message with a Printf template and marks the test as failed. `%q` prints a string in quotes (GB-1.04). The Uzbek words in the message: *kutilgan* = "expected", *xatosiz* = "without an error" |
| 9 | `}` | the end of the `if`. Note: there is no `return` after `Errorf` |
| 10 | `got, err = parsePrice("500")` | the second case: 500 soʻm = 50 000 tiyin. `got` and `err` already exist, so it is `=` without the colon (GB-1.02) |
| 11–13 | `if …` / `t.Errorf(…)` / `}` | the same check as the first one |
| 14 | `}` | the end of the test function |

The order of the message is the usual one in Go: **what was called, what came back, what was expected**:
`parsePrice("12000") = …; kutilgan …`
([Go Code Review Comments: Useful Test Failures](https://go.dev/wiki/CodeReviewComments#useful-test-failures)). Whoever
reads a failed test's message understands what happened without opening the code.

## See the test fail once

To trust a test, see it fail once: a test that has never failed may be checking nothing. We remove the multiplication
by one hundred from the last line of `parsePrice`, as if someone thought the price was already in tiyin
(`_video/02-buzuq/main.go`, line 23; *buzuq* = "broken"; `price_test.go` is unchanged):

```go
// parsePrice soʻmdagi narx matnini tiyinga oʻgiradi.
func parsePrice(s string) (int64, error) {
	som, err := strconv.Atoi(s)
	if err != nil {
		return 0, err
	}
	if som <= 0 {
		return 0, fmt.Errorf("narx musbat boʻlishi kerak, keldi %d", som)
	}
	return int64(som), nil
}
```

Both cases now give a wrong result. How many error lines does `go test` print?

**A)** 1: it stops at the first error · **B)** 2: both cases · **C)** a compile error

<details>
<summary>Answer</summary>

**B: two lines.** `t.Errorf` does not stop the test, the following lines keep running: the second call on line 10 runs
too and writes its own message. If you chose **A**, you thought `t.Errorf` stops the test: the one that stops it is
`t.Fatalf`, which we will see in the table. **C**: the code compiles, `int64(som)` is still an `int64`, the
function type did not change.

</details>

```console
$ ./_video/run.sh 02-buzuq go test
--- FAIL: TestParsePrice (0.00s)
    price_test.go:8: parsePrice("12000") = 12000, <nil>; kutilgan 1200000, xatosiz
    price_test.go:12: parsePrice("500") = 500, <nil>; kutilgan 50000, xatosiz
FAIL
exit status 1
FAIL	github.com/abdurahmon27/bozor	0.003s
```

| Line | What it says |
|---|---|
| `--- FAIL: TestParsePrice (0.00s)` | which test failed, and its time |
| `price_test.go:8: …` | before the message, the file and the line number: `t.Errorf` was called on line 8. The message: 12 000 came back, 1 200 000 was expected. `err` is `nil`, and `%v` printed it as `<nil>` in angle brackets |
| `price_test.go:12: …` | the second case, line 12: 500 came back, 50 000 was expected |
| `FAIL` | the test binary failed |
| `exit status 1` | the test binary exited with code 1 (like `os.Exit(1)` in GB-1.07) |
| `FAIL	github.com/abdurahmon27/bozor	0.003s` | the last line: the package failed |

## What happens inside `go test`

Where did `exit status 1` come from? `go test` builds a temporary **test binary** from `main.go` and `price_test.go`. The
binary calls `TestParsePrice` and gives it `t`. `t.Errorf` only puts a "failed" mark on `t`. When the function ends, the
binary sees the mark, prints `FAIL` and exits with code 1
([go help test](https://pkg.go.dev/cmd/go#hdr-Test_packages): "compiles the package sources and tests found in the
current directory and then runs the resulting test binary"):

```text
 main.go + price_test.go        (one package main)
            │  go test compiles
            ▼
 test binary ──► TestParsePrice(t)
                     │ line 8:  t.Errorf → t: "failed" ✗, the function goes on
                     │ line 12: t.Errorf → t: "failed" ✗ (another message)
                     ▼
            the function ended: t has the mark
                     ▼
 FAIL  →  exit status 1  →  go test: FAIL github.com/abdurahmon27/bozor
```

The documentation says it like this: "Errorf is equivalent to Logf followed by Fail": write a message and set the mark,
nothing else ([pkg.go.dev/testing](https://pkg.go.dev/testing)). We put the multiplication back and move on to the table.

## The table-driven test

Now we want to add the huge input from the start, a text with a letter, zero and the limits. Copying three lines for
every case invites mistakes: you change a number in one place and forget the other. The usual way in Go is a
**table-driven test**: the cases are written as data, and the checking code is written once
([Go wiki: TableDrivenTests](https://go.dev/wiki/TableDrivenTests)). This is `price_test.go` in the folder:

```go filename="price_test.go" showLineNumbers
package main

import "testing"

func TestParsePrice(t *testing.T) {
	tests := []struct {
		name    string
		in      string
		want    int64
		wantErr bool
	}{
		{"oddiy", "12000", 1_200_000, false},
		{"chegara", "10000000", 1_000_000_000, false},
		{"harf", "12k", 0, true},
		{"nol", "0", 0, true},
		{"ortiq", "10000001", 0, true},
		{"ulkan", "100000000000000000", 0, true},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got, err := parsePrice(tc.in)
			if (err != nil) != tc.wantErr {
				t.Fatalf("parsePrice(%q) = %d, %v; xato kutilgan: %v", tc.in, got, err, tc.wantErr)
			}
			if got != tc.want {
				t.Errorf("parsePrice(%q) = %d; kutilgan %d", tc.in, got, tc.want)
			}
		})
	}
}
```

**The table (lines 6–18):**

| Line | Code | What it does |
|---|---|---|
| 6 | `tests := []struct {` | a variable named `tests`. A **`struct`** groups several named fields into one value (in detail in [GB-2.03](/lab/youtube/gb/gb-2-03/en)). The `[]` in front means a list of such values, a **slice** (the next lesson, [GB-2.01](/lab/youtube/gb/gb-2-01/en)) |
| 7 | `name    string` | the case name (it becomes the subtest name) |
| 8 | `in      string` | the input text |
| 9 | `want    int64` | the expected result, in tiyin |
| 10 | `wantErr bool` | whether an error is expected: `true` or `false` |
| 11 | `}{` | `}` closes the struct type, `{` opens the list of rows |
| 12 | `{"oddiy", "12000", 1_200_000, false},` | each row: the fields in order (`name`, `in`, `want`, `wantErr`) inside curly braces, with a comma at the end. *oddiy* = "plain" |
| 13 | `{"chegara", "10000000", 1_000_000_000, false},` | *chegara* = "limit": 10 million soʻm must **pass** under the GB-1.05 rule |
| 14–17 | `harf`, `nol`, `ortiq`, `ulkan` | must give an error (`true`): *harf* ("letter") `12k`, *nol* ("zero") `0`, *ortiq* ("over") one soʻm above the limit (10 000 001), and *ulkan* ("huge"), the number from the start |
| 18 | `}` | the end of the list |

The last comma (on line 17 too) is required: when a line ends in `}`, Go inserts a hidden semicolon there, and the comma
prevents that ([Go spec: Semicolons](https://go.dev/ref/spec#Semicolons)). Bugs often sit exactly at a limit, so both
10 000 000 and 10 000 001 are in the table. Such a value on either side of a limit is a **boundary value**.

**The loop (lines 19–29):**

| Line | Code | What it does |
|---|---|---|
| 19 | `for _, tc := range tests {` | in GB-1.06 `range` counted up to a number. Over a list it gives two values: the index and the row itself. We do not need the index; the underscore `_` throws it away. The row goes into a variable named `tc` (*test case*) |
| 20 | `t.Run(tc.name, func(t *testing.T) {` | **`t.Run`** runs each row as a separate **subtest**. The first argument is its name: `tc.name`, where the dot reads a field of the row. The second is an **anonymous function**: `func`, a parameter and a body, written without a name and passed directly as an argument. Its `t` is a different `t`, the subtest's |
| 21 | `got, err := parsePrice(tc.in)` | the call with this row's input |
| 22 | `if (err != nil) != tc.wantErr {` | `err != nil` in brackets is a `bool`: "is there an error?". If it is not equal to `wantErr`, the error is not as expected |
| 23 | `t.Fatalf(…)` | **`t.Fatalf`** writes a message just like `Errorf`, but stops this subtest at once. If an error came when none was expected (or did not come when one was), checking `got` makes no sense. *xato kutilgan* = "error expected" |
| 25–26 | `if got != tc.want {` / `t.Errorf(…)` | compares `got` with `want`; here a plain `Errorf` |
| 28 | `})` | `}` closes the anonymous function, `)` closes the `t.Run` call |
| 29–30 | `}` / `}` | the end of the loop and of `TestParsePrice` |

The documentation of `t.Fatalf`: "Fatalf is equivalent to Logf followed by FailNow". `FailNow` stops this test
function, while the other subtests keep running ([pkg.go.dev/testing#T.Fatalf](https://pkg.go.dev/testing#T.Fatalf),
[T.Run](https://pkg.go.dev/testing#T.Run), [Go blog: Using Subtests](https://go.dev/blog/subtests)).

## What the table found

The code is still as in the last lesson (`_video/03-jadval/main.go` = GB-1.07's `solution/main.go`; *jadval* =
"table"): `parsePrice` has no upper limit; the limit is only in `main`, **after** the multiplication:

```go
	if price > 10_000_000*tiyinPerSom { // price <= 0 endi parsePrice ichida
		fmt.Printf("xato: narx notoʻgʻri: %d tiyin\n", price)
		return
	}
```

Which of the six subtests fail?

**A)** only `ulkan` · **B)** `harf`, `nol` and `ulkan` · **C)** `ortiq` and `ulkan`

<details>
<summary>Answer</summary>

**C: two of them, `ortiq` and `ulkan`.** `ortiq` (10 000 001 soʻm) should give an error, but `parsePrice` only checks
from below: it has no upper limit. `ulkan` returns a negative number because of the overflow, without an error. If you
chose **A**, you thought the limit was inside `parsePrice`. **B**: GB-1.07's code already rejects `harf` and `nol`, with
the `Atoi` error and the `som <= 0` check.

</details>

## Mid-lesson question: `Errorf` instead of `Fatalf`

If the first check (line 23) used `t.Errorf` instead of `t.Fatalf`, how many messages would the `ulkan` subtest print?
This is `_video/06-errorf/price_test.go`: that one word is the only difference.

**A)** 1 · **B)** 0 · **C)** 2

<details>
<summary>Answer</summary>

**C: two.** After `Errorf` the subtest goes on, the second check runs too and says again that the negative number is not
equal to `want` (0). **A** is what `Fatalf` would give. **B**: the subtest fails anyway, `Errorf` sets the mark too.

</details>

```console
$ ./_video/run.sh 06-errorf go test
--- FAIL: TestParsePrice (0.00s)
    --- FAIL: TestParsePrice/ortiq (0.00s)
        price_test.go:23: parsePrice("10000001") = 1000000100, <nil>; xato kutilgan: true
```

```go filename="main.go" showLineNumbers
func parsePrice(s string) (int64, error) {
	som, err := strconv.Atoi(s)
	if err != nil {
		return 0, err
	}

		return 0, fmt.Errorf("narx musbat boʻlishi kerak, keldi %d", som)

		return 0, err
	}

		return 0, fmt.Errorf("miqdor kamida 1 boʻlishi kerak, keldi %d", n)
	}
	return n, nil

		return

	fmt.Println(name, stock)
```

## Running one case: `-run`

To run one case on its own there is the **`-run`** flag. Its value is a **regular expression**, a search pattern; the
slash `/` separates the test name from the subtest name
([go help testflag](https://pkg.go.dev/cmd/go#hdr-Testing_flags): "split by unbracketed slash (/) characters into a
sequence of regular expressions"):

```console
$ ./_video/run.sh 04-tuzat go test -v -run TestParsePrice/ulkan
=== RUN   TestParsePrice
=== RUN   TestParsePrice/ulkan
--- PASS: TestParsePrice (0.00s)
    --- PASS: TestParsePrice/ulkan (0.00s)
PASS
ok  	github.com/abdurahmon27/bozor	0.003s
```

A subtest runs inside its parent test, so `TestParsePrice` shows `RUN` too, but only `ulkan` was called inside it. It is
enough for the pattern to match **any part** of the name: `ol` may be in the middle of a name. Of the six names, only
`nol` contains `ol`:

```console
$ ./_video/run.sh 04-tuzat go test -v -run TestParsePrice/ol
=== RUN   TestParsePrice
=== RUN   TestParsePrice/nol
--- PASS: TestParsePrice (0.00s)
    --- PASS: TestParsePrice/nol (0.00s)
PASS
ok  	github.com/abdurahmon27/bozor	0.005s
```

For exactly one name, anchor the pattern on both sides: `^` is the start of the name, `$` the end. Put the pattern in
single quotes: `$` and `^` are special characters for the terminal too, and the quotes pass them to Go unchanged:

```console

=== RUN   TestParsePrice
=== RUN   TestParsePrice/nol
--- PASS: TestParsePrice (0.00s)
    --- PASS: TestParsePrice/nol (0.00s)
PASS
ok  	github.com/abdurahmon27/bozor	0.005s
```

The result is the same here, but in another table `-run nol` would also run `nolinchi` or `manfiy_nol`; `^…$` runs only
`nol` itself.

```go filename="solution/sold_test.go" showLineNumbers
package main

import "testing"

func TestParseSold(t *testing.T) {
	tests := []struct {
		name    string
		in      string
		want    int
		wantErr bool
	}{
		{"oddiy", "5", 5, false},
		{"eng_kam", "1", 1, false},
		{"chegara", "1000", 1000, false},
		{"nol", "0", 0, true},
		{"manfiy", "-1", 0, true},
		{"ortiq", "1001", 0, true},
		{"harf", "besh", 0, true},
	}
	for _, tc := range tests {
		t.Run(tc.name, func(t *testing.T) {
			got, err := parseSold(tc.in)
			if (err != nil) != tc.wantErr {
				t.Fatalf("parseSold(%q) = %d, %v; xato kutilgan: %v", tc.in, got, err, tc.wantErr)
			}
			if got != tc.want {
				t.Errorf("parseSold(%q) = %d; kutilgan %d", tc.in, got, tc.want)
			}
		})
	}
}
```
