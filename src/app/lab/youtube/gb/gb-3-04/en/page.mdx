## What you will learn

In bozor, `go run` prints two lists: products that are running low and paid orders. The bodies of the two functions that select them are identical, letter for letter; only the types differ.
A third type means a third copy. Can we write the body once and choose the type at the call?

**One idea:** a **type parameter** is a parameter of a function for a *type*. It is declared in square brackets after the function name and before the ordinary parameters: `[T any]`.
The function body is checked **once**, against the constraint: the constraint says which types `T` can be, and therefore which operations on `T` are allowed in the body.
At each call the compiler infers `T` from the arguments and checks only the call: does the type fit the constraint, do the arguments agree.

By the end of the lesson you will:

- replace the two copies `filterProducts` and `filterOrders` with one `Filter[T any]`;
- write the sum for `int` and `int64` as one function, `Sum[N Number]`, and pick `comparable` when you need `==`;
- read the compiler's generic errors: `cannot use … as []any`, `does not match inferred type`, `operator + not defined … constrained by any`, `cannot infer E`;
- remove the type parameter where only a method is called (`writeTotal`) and read the square brackets in `errors.AsType[*StockError](err)`.

Today's three core new words:

| Word | Plain meaning | In Go |
|---|---|---|
| type parameter | a name in square brackets after the function name (`T`): the call chooses which type the function works with | type parameter |
| constraint | an interface that says which types `T` can be and which operations exist for it | constraint |
| type inference | the compiler finds `T` itself from the arguments of the call | type inference |

Helper words are explained in one sentence where they appear: **generic function**, **type argument**, **instantiation**, **type set**, the tilde `~`.

## The problem: two functions with the same body

The starting program of the lesson is `_video/00-takror/main.go`. It is a complete program; `Product`, `OrderItem`, `OrderStatus` and `Order` are the types from GB-2.03.

```go filename="_video/00-takror/main.go" showLineNumbers
package main

import (
	"fmt"
)

// Product — katalogdagi bitta mahsulot (GB-2.03).
type Product struct {
	ID    int64
	Name  string
	Price int64 // tiyin
	Stock int
}

// OrderItem — buyurtmadagi bitta qator (GB-2.03).
type OrderItem struct {
	ProductID int64
	Price     int64 // tiyin
	Quantity  int
}

// OrderStatus — buyurtma holati (GB-2.03).
type OrderStatus int

const (
	StatusNew OrderStatus = iota
	StatusPaid
)

// Order — bitta buyurtma (GB-2.03).
type Order struct {
	ID     int64
	Items  []OrderItem
	Status OrderStatus
}

func filterProducts(ps []Product, keep func(Product) bool) []Product {
	var out []Product
	for _, p := range ps {
		if keep(p) {
			out = append(out, p)
		}
	}
	return out
}

func filterOrders(orders []Order, keep func(Order) bool) []Order {
	var out []Order
	for _, o := range orders {
		if keep(o) {
			out = append(out, o)
		}
	}
	return out
}

func main() {
	products := []Product{
		{ID: 1, Name: "olma", Price: 1_200_000, Stock: 40},
		{ID: 2, Name: "non", Price: 400_000, Stock: 3},
		{ID: 3, Name: "choy", Price: 2_500_000, Stock: 0},
	}
	orders := []Order{
		{ID: 7, Status: StatusPaid, Items: []OrderItem{{ProductID: 1, Price: 1_200_000, Quantity: 3}}},
		{ID: 8, Status: StatusNew, Items: []OrderItem{{ProductID: 2, Price: 400_000, Quantity: 5}}},
		{ID: 9, Status: StatusPaid, Items: []OrderItem{{ProductID: 2, Price: 400_000, Quantity: 2}}},
	}

	low := filterProducts(products, func(p Product) bool { return p.Stock < 5 })
	paid := filterOrders(orders, func(o Order) bool { return o.Status == StatusPaid })
	for _, p := range low {
		fmt.Println("kam qolgan:", p.Name, p.Stock)
	}
	for _, o := range paid {
		fmt.Println("toʻlangan buyurtma:", o.ID)
	}
}
```

| Line | Code | What it does |
|---|---|---|
| 1–35 | `package main`, `import`, `Product`, `OrderItem`, `OrderStatus`, `Order` | the types from GB-2.03: a product, an order line, an order status and an order |
| 37 | `func filterProducts(ps []Product, keep func(Product) bool) []Product {` | the first parameter `ps` is a slice of products; the second, `keep`, has a **function** type: it takes a `Product` and returns a `bool`; the result is `[]Product` |
| 38 | `var out []Product` | `out` is a nil slice (GB-2.01): empty for now |
| 39–41 | `for _, p := range ps { if keep(p) { out = append(out, p) } }` | `keep(p)` is called for each `p`; if it returns `true`, `p` is added to `out` |
| 44 | `return out` | the selected products are returned |
| 47–55 | `func filterOrders(orders []Order, keep func(Order) bool) []Order { … }` | the second function: the body is the same seven lines again, with `o` in place of `p` |
| 58–67 | `products := …`, `orders := …` | the data: products olma (40), non (3), choy (0); orders 7 (paid), 8 (new), 9 (paid) |
| 69 | `low := filterProducts(products, func(p Product) bool { return p.Stock < 5 })` | a function literal (GB-1.08) in place of `keep`: it takes `p` and returns `true` if the stock is below 5. The result is stored in `low` |
| 70 | `paid := filterOrders(orders, func(o Order) bool { return o.Status == StatusPaid })` | `true` if `Status` is `StatusPaid` (paid); the result is stored in `paid` |
| 71–76 | two `for` loops | print the elements of `low` and `paid` |

`keep func(Product) bool` differs from `fn func()` in GB-2.09: this function has both a parameter and a result. That is why the condition is given at the call, not fixed in the body.

Run the program:

```console
$ ./_video/run.sh 00-takror go run .
kam qolgan: non 3
kam qolgan: choy 0
toʻlangan buyurtma: 7
toʻlangan buyurtma: 9
```

`non` (3) and `choy` (0) are low; orders 7 and 9 are paid. Now the difference between the two functions:

| | `filterProducts` | `filterOrders` |
|---|---|---|
| 1st parameter | `ps []Product` | `orders []Order` |
| type of `keep` | `func(Product) bool` | `func(Order) bool` |
| type of `out` | `[]Product` | `[]Order` |
| loop variable | `p` | `o` |
| result type | `[]Product` | `[]Order` |
| everything else | `var out`, `for`, `if keep`, `append`, `return` | the same |

The difference is only in type names. The logic, "go through the elements and collect those for which `keep` returned `true`", does not depend on the type at all. A third type (say `Customer`) would need one more copy.

Ian Lance Taylor of the Go team describes exactly this case: the same code is written many times, and the copies differ only in the types they use. Then it is worth thinking about a type parameter.
But first we try the simple solution.

## First attempt: one function with `any`

You know from GB-2.07 that `any` is an interface with no methods, and any value fits into it. So can we write one function that takes `[]any`? Its body is the same (`_video/01-any/main.go`):

```go
func filterAny(items []any, keep func(any) bool) []any {
	var out []any
	for _, x := range items {
		if keep(x) {
			out = append(out, x)
		}
	}
	return out
}
```

At the call, inside `keep`, the value has to be turned back into a `Product`: `x.(Product)` is the type assertion from GB-2.07, which takes the `Product` out of the interface.

```go
low := filterAny(products, func(x any) bool { return x.(Product).Stock < 5 })
```

A `Product` fits into `any`. Does a `[]Product` slice fit into a `[]any` slice? What does `go build` say?

**A)** the build succeeds · **B)** a compile error · **C)** the build succeeds, then `panic`

<details>
<summary>Answer</summary>

**B: a compile error.** The type of `products` is `[]Product`, the parameter is `[]any`; Go does not convert such a slice for you. If you chose **A**, you thought that since `Product` fits into `any`, the slice fits too.
If you chose **C**, you expected the error while the program runs: this error is found before the program starts.

```console
$ ./_video/run.sh 01-any go build
# github.com/abdurahmon27/bozor
./main.go:59:19: cannot use products (variable of type []Product) as []any value in argument to filterAny
```

</details>

Read the message. `./main.go:59:19` is the file, line 59, column 19: the `products` argument. `cannot use products (variable of type []Product) as []any value in argument to filterAny` means
"`products` (type `[]Product`) cannot be used as a `[]any` value in the argument of `filterAny`". The first line, `# github.com/abdurahmon27/bozor`, is the module name.

Why? The reason is in memory. Let us measure the sizes with `unsafe.Sizeof` (`_video/01b-olcham/main.go`; the body of `main` is this line):

```go
fmt.Println(unsafe.Sizeof(Product{}), unsafe.Sizeof(any(nil)))
```

```console
$ ./_video/run.sh 01b-olcham go run .
40 16
```

`Product` is **40 bytes**, `any` (an interface value, GB-2.07) is **16 bytes**: pointers to the type and to the value. On this platform (`linux/amd64`) that is how it is.

```text
[]Product  (3 elements):  | Product: 40 bytes | Product: 40 bytes | Product: 40 bytes |   the struct itself, side by side
[]any      (3 elements):  | type + value: 16  | type + value: 16  | type + value: 16  |   each one is pointers
```

The elements of the two slices lie differently in memory, so one cannot be passed in place of the other. The other way is to copy every element into a new `[]any` slice. Then:

| Step | What happens |
|---|---|
| 1 | `[]Product` → a new `[]any`: every element is copied |
| 2 | `filterAny` returns `[]any` |
| 3 | every time, the type has to be restored with `x.(Product)` |
| 4 | if the type is wrong, the assertion stops the running program with `panic` ([Go spec](https://go.dev/ref/spec#Type_assertions)) |

As a result the code is longer and riskier, and a type error shows up not at compile time but while the program runs. The Go FAQ says the same: the two types do not have the same representation in memory.

## Type parameter: one `Filter`

Go's solution is the **type parameter**. It is declared after the function name, before the ordinary parameters, in square brackets. A function with a type parameter is called a **generic function** (`_video/02-filter/main.go`):

```go
func Filter[T any](items []T, keep func(T) bool) []T {
	var out []T
	for _, x := range items {
		if keep(x) {
			out = append(out, x)
		}
	}
	return out
}
```

| Line | Code | What it does |
|---|---|---|
| 1 | `[T any]` | the list of type parameters: `T` is a name for a type, and the caller chooses it. The `any` after `T` is the constraint: it says which type `T` can be; `any` means any type |
| 1 | `items []T`, `keep func(T) bool`, `[]T` | `T` is used like an ordinary type: `items` is a slice of `T`, `keep` is a function that takes `T`, the result is a slice of `T` |
| 2 | `var out []T` | `out` is also a slice of `T`, nil |
| 3–5 | `for _, x := range items { if keep(x) { out = append(out, x) } }` | `x` is each element (type `T`); if `keep` returns `true`, the element is added to `out` |
| 8 | `return out` | a `[]T` is returned |

`Filter` is one body in place of `filterProducts` and `filterOrders`. Now the calls in `main` (we do not write `T`):

```go
low := Filter(products, func(p Product) bool { return p.Stock < 5 })
paid := Filter(orders, func(o Order) bool { return o.Status == StatusPaid })
```

We did not write `T`: the compiler infers it from the arguments. This is **type inference**.

| Call | First argument | The compiler concludes | The type of `keep` becomes |
|---|---|---|---|
| `Filter(products, …)` | `[]Product` | `T = Product` | `func(Product) bool` |
| `Filter(orders, …)` | `[]Order` | `T = Order` | `func(Order) bool` |

One function instead of two. The output must match the one from the start:

```console
$ ./_video/run.sh 02-filter go run .
kam qolgan: non 3
kam qolgan: choy 0
toʻlangan buyurtma: 7
toʻlangan buyurtma: 9
```

Now a wrong call: `Filter` gets `orders`, but `keep` is a function that takes a `Product` (`_video/04-mos-emas/main.go`):

```go
low := Filter(orders, func(p Product) bool { return p.Stock < 5 })
```

What happens?

**A)** it works: an empty slice is returned · **B)** a compile error · **C)** `panic` at run time

<details>
<summary>Answer</summary>

**B: a compile error.** The compiler inferred `T` from the first argument: `Order`. So `keep` had to be a function that takes an `Order`, but a function that takes a `Product` came.
If you chose **A**, you thought Go accepts types that are "similar enough". If you chose **C**, you expected the error while the program runs: a type error in a generic call is found before the program starts.

```console
$ ./_video/run.sh 04-mos-emas go build
# github.com/abdurahmon27/bozor
./main.go:59:24: in call to Filter, type func(p Product) bool of func(p Product) bool {…} does not match inferred type func(Order) bool for func(T) bool
```

</details>

Read the message: `in call to Filter` means the error is in the `Filter` call; `type func(p Product) bool of func(p Product) bool {…}` is the type of the argument that was passed (`{…}` is how the compiler abbreviates a function body);
`does not match inferred type func(Order) bool for func(T) bool` means "the type inferred for `func(T) bool` is `func(Order) bool`, and the argument does not match it". The error was found before the program ran.

We can write `T` ourselves too, in square brackets (`_video/03-tur/main.go`; the body of `main`):

```go
fmt.Printf("%T\n", Filter[Product])
fmt.Printf("%T\n", Filter[Order])
```

Here `Product` is the **type argument**: the concrete type that is put in place of `T`. `%T` prints the type of a value (GB-2.08).

```console
$ ./_video/run.sh 03-tur go run .
func([]main.Product, func(main.Product) bool) []main.Product
func([]main.Order, func(main.Order) bool) []main.Order
```

`main.Product` is the `Product` of package `main`. The result is an ordinary function type: it takes a `[]Product` and a function, and returns a `[]Product`. Putting the type argument in place of `T` is called **instantiation**.
You cannot pass `Filter` without square brackets to `Printf`: there is nowhere to infer `T` from. This example is not in the course folder: in the `main` of `_video/03-tur/main.go` I changed the first `Filter[Product]` to `Filter`; everything else is the same.

```go
fmt.Printf("%T\n", Filter)
fmt.Printf("%T\n", Filter[Order])
```

```console
$ go build
# github.com/abdurahmon27/bozor
./main.go:48:12: in call to fmt.Printf, cannot infer T (declared at ./main.go:37:13)
```

`cannot infer T` means "`T` could not be inferred"; the parentheses show where `T` is declared: line 37, column 13, that is the `[T any]` of `Filter`.

## Constraint: which operations are possible on a type

The second copy: the sum. Stocks are `int`, sums are `int64`; we want one `Sum` for both. The type parameter is `N`, and the constraint is `any` again (`_video/05-sum-any/main.go`):

```go
func Sum[N any](nums []N) N {
	var total N
	for _, n := range nums {
		total += n
	}
	return total
}
```

| Line | Code | What it does |
|---|---|---|
| 1 | `func Sum[N any](nums []N) N` | `N` is a type parameter; `nums` is a slice of numbers of type `N`; the result is also `N` |
| 2 | `var total N` | a variable of type `N`, at first the zero value |
| 3–5 | `for _, n := range nums { total += n }` | each `n` is added to `total` |
| 6 | `return total` | the sum is returned |

For now `Sum` is called only with `int` and `int64`: `Sum([]int{…})`, `Sum([]int64{…})`. Does this code compile?

**A)** yes, it works with both types · **B)** no: `+` is not defined for `N` · **C)** an error only with `string`

<details>
<summary>Answer</summary>

**B.** The body of a generic function is checked **once**, not per call. About `N` the compiler knows only what the constraint says, here `any`. `any` includes `struct` and `bool`, and they have no `+`.
If you chose **A**, you thought the compiler checks `Sum` with the `int` from the call. If you chose **C**, you expected only the type from the call: the error is against the body, not the call.

```console
$ ./_video/run.sh 05-sum-any go build
# github.com/abdurahmon27/bozor
./main.go:40:3: invalid operation: operator + not defined on total (variable of type N constrained by any)
```

</details>

The message: `./main.go:40:3` is line 40 (`total += n`); `operator + not defined on total` means "the `+` operation is not defined for `total`"; `(variable of type N constrained by any)` means
"`total` is a variable of type `N`, and the constraint of `N` is `any`". **The rule:** the body may use only operations that exist for **all** types in the constraint. The set of types a constraint allows is called its **type set**; for `any` it is all types.
This is a frequent mistake.

The fix: we write the constraint ourselves (`_video/06-sum/main.go`). `Number` is also an interface, but instead of methods it holds a **list of types**. The vertical bar `|` reads as "or":

```go
type Number interface {
	int | int64
}

func Sum[N Number](nums []N) N {
```

Now `N` can only be `int` or `int64`; both have `+`, so the compiler agrees. The body is the same; only the first line of `Sum` changed. Such an interface can only be a constraint, not the type of a variable ([Go spec](https://go.dev/ref/spec#General_interfaces)).
In `main` there are two calls:

```go
fmt.Println(Sum([]int{40, 3, 0}), Sum([]int64{3_600_000, 800_000}))
```

```console
$ ./_video/run.sh 06-sum go run .
43 4400000
```

| Call | `N` | Calculation | Result |
|---|---|---|---|
| `Sum([]int{40, 3, 0})` | `int` | 40 + 3 + 0 | `43` |
| `Sum([]int64{3_600_000, 800_000})` | `int64` | 3,600,000 + 800,000 | `4400000` (tiyin) |

An intermediate question. `Contains` checks whether `x` is in the slice: it compares each `v` with `x` using `==`. The constraint is `any`. What does `go build` say? (`_video/07-contains/main.go`)

```go
func Contains[T any](items []T, x T) bool {
	for _, v := range items {
		if v == x {
			return true
		}
	}
	return false
}
```

**A)** the build succeeds · **B)** a compile error · **C)** it works only with `string`

<details>
<summary>Answer</summary>

**B.** `==` does not exist for every type: slices, maps and functions cannot be compared with `==` ([Go spec](https://go.dev/ref/spec#Comparison_operators)), and the type set of `any` includes them. The same rule as for `Sum`: the body must use an operation that exists for all the types.
If you chose **A**, you thought `==` works on any type. If you chose **C**, you missed that the error is aimed at the body, not the call.

```console
$ ./_video/run.sh 07-contains go build
# github.com/abdurahmon27/bozor
./main.go:39:6: invalid operation: v == x (incomparable types in type set)
```

</details>

`incomparable types in type set` means "there are types in the type set that cannot be compared". The fix is a constraint that Go declares in advance: **`comparable`**, the types that can be compared with `==` (`_video/07b-comparable/main.go`):

```go
func Contains[T comparable](items []T, x T) bool {
```

```go
fmt.Println(Contains([]string{"olma", "non"}, "non"), Contains([]int64{1, 2}, 3))
```

```console
$ ./_video/run.sh 07b-comparable go run .
true false
```

`"non"` is in the list: `true`; `3` is not in `[]int64{1, 2}`: `false`. In the standard library, `slices.Contains` is declared exactly like this (`[S ~[]E, E comparable]`; we read the `~[]E` part in GB-3.05). The output is again cut to the first 4 lines:

```console
$ go doc slices.Contains | head -4
package slices // import "slices"

func Contains[S ~[]E, E comparable](s S, v E) bool
    Contains reports whether v is present in s.
```

## Where a type parameter is not needed: only a method is called

Now the opposite case. A teammate wrote `writeTotal` as a generic function (`_video/08-writer/main.go`):

```go
func writeTotal[W io.Writer](w W, total int64) error {
	_, err := fmt.Fprintf(w, "jami: %d tiyin\n", total)
	return err
}
```

Here `W` is a type parameter with the constraint `io.Writer`: an ordinary interface with a method can be a constraint too, and `W` must have a `Write` method. `total` is the sum to write. `main` calls it like this:

```go
if err := writeTotal(os.Stdout, 4_400_000); err != nil { … }
```

```console
$ ./_video/run.sh 08-writer go run .
jami: 4400000 tiyin
```

The program works correctly. But `W` appears in the signature **once**: only as the type of `w`. It does not tie any other type to it. The function does one thing with `w`: it calls the `Write` method (through `Fprintf`).
For that, the ordinary `io.Writer` parameter from GB-2.07 is enough (`_video/08b-writer/main.go`):

```go
func writeTotal(w io.Writer, total int64) error {
```

The body is the same, there is no `[W io.Writer]`, and `w io.Writer` replaces `w W`.

```console
$ ./_video/run.sh 08b-writer go run .
jami: 4400000 tiyin
```

The output is letter for letter the same, and the code is simpler. Taylor's rules ([When To Use Generics](https://go.dev/blog/when-generics)):

| Situation | What to use |
|---|---|
| the same code is repeated, differing only in the type | a type parameter (`Filter`, `Sum`) |
| only a method is called on the value | an interface (`io.Writer`) |
| `T` ties the input type to the output type | a type parameter: in `Filter[T]` a `[]T` goes in and a `[]T` comes out; remove `T` and the result type (`[]Product`) is lost |
| the method's implementation differs for each type | give each type its own method and call it through an interface |

Taylor's own example: instead of `func ReadSome[T io.Reader](r T) ([]byte, error)`, write `func ReadSome(r io.Reader) ([]byte, error)`. He says: *"Omitting the type parameter makes the function easier to write, easier to read, and the execution time will likely be the same."*
Do not replace an interface with a type parameter for speed. In code review, rely on these rules.

## Reading the square brackets in `errors.AsType`

In GB-2.08 we left the square brackets of `errors.AsType` for this lesson. Now we can read its declaration (`| head -4` cuts the output to the first 4 lines):

```console
$ go doc errors.AsType | head -4
package errors // import "errors"

func AsType[E error](err error) (E, bool)
    AsType finds the first error in err's tree that matches the type E, and if
```

`func AsType[E error](err error) (E, bool)`: `E` is a type parameter with the constraint `error`, so `E` must have an `Error()` method. There is one ordinary parameter: `err`, of type `error`. `E` appears only in the **result**: the error that was found, and a `bool`.

What if we do not write the brackets? We have `err`; can the compiler infer the type itself, as with `Filter`? Two lines of code (`_video/09-astype/main.go`; `err` holds a `*StockError`):

```go
err := fmt.Errorf("buyurtma 7: %w", &StockError{Name: "olma", Stock: 40, Want: 41})
if se, ok := errors.AsType(err); ok {
```

**A)** `E = error` · **B)** an error: `E` cannot be determined · **C)** `E = *StockError` is found

<details>
<summary>Answer</summary>

**B.** In a call, `E` is inferred only from the types of the arguments; which variable the result is assigned to is not taken into account. The type of `err` is `error`, and it has no `E` in it.
If you chose **A**, you thought the compiler puts `error` in place of `E`: `error` is the type of the argument, and `E` is not inferred from it. If you chose **C**, you thought the compiler sees the `*StockError` inside `err`: the type of `err` is `error`, and what is inside is known only while the program runs.

```console
$ ./_video/run.sh 09-astype go build
# github.com/abdurahmon27/bozor
./main.go:51:28: in call to errors.AsType, cannot infer E (declared at $GOROOT/src/errors/wrap.go:167:13)
```

</details>

`cannot infer E` means "`E` could not be inferred". The parentheses show where `E` is declared; `$GOROOT` is the folder where Go is installed. So we write the type ourselves (`_video/10-astype-ok/main.go`):

```go
if se, ok := errors.AsType[*StockError](err); ok {
	fmt.Printf("%T %s %d\n", se, se.Name, se.Stock)
}
```

```console
$ ./_video/run.sh 10-astype-ok go run .
*main.StockError olma 40
```

The `*StockError` in square brackets is the **type argument**, and `E` is the type parameter. In GB-2.08 we called it a "type parameter"; the correct name is type argument. In this lab `StockError` is in package `main`, so `%T` prints `*main.StockError`.
The type of `se` is `*StockError`, so its fields (`se.Name`, `se.Stock`) are read directly.

## Going deeper (optional): `~int64` and `type Tiyin int64`

Let us make a separate type for money: `type Tiyin int64` is a new type whose **underlying type** is `int64`, like `OrderStatus` (GB-2.03). It is only an example: in bozor, money stays a plain `int64`.
We pass a slice of `Tiyin` to `Sum` (`_video/11-tilde/main.go`):

```go
type Tiyin int64
```

```go
fmt.Println(Sum([]Tiyin{1_200_000, 400_000}))
```

```console
$ ./_video/run.sh 11-tilde go build
# github.com/abdurahmon27/bozor
./main.go:53:17: Tiyin does not satisfy Number (possibly missing ~ for int64 in Number)
```

`Tiyin does not satisfy Number` means "`Tiyin` does not satisfy `Number`". The hint: `possibly missing ~ for int64 in Number` means "perhaps a `~` is missing before `int64` in `Number`".
The list `int | int64` contains exactly `int64`, and `Tiyin` is a different type. The fix is the tilde (`_video/12-tilde-ok/main.go`):

```go
type Number interface {
	~int | ~int64
}
```

`~int64` is not one type but **all** types whose underlying type is `int64`; `~int` means all whose underlying type is `int`.

```console
$ ./_video/run.sh 12-tilde-ok go run .
1600000
```

`1,200,000 + 400,000 = 1,600,000`. The tilde is common in the declarations of package `slices`, for example:

```console
$ go doc slices.Clone | head -4
package slices // import "slices"

func Clone[S ~[]E, E any](s S) S
    Clone returns a copy of the slice. The elements are copied using assignment,
```

Generics have been in the language since Go 1.18 ([Go 1.18 release notes](https://go.dev/doc/go1.18#generics)).

## Common mistakes

All of these appeared on this page; here they are short, with the fix.

**1. "`any` is any type, so any operation works in the body."** No: the body may use only operations that exist for **all** types in the constraint (see the "Constraint" section).
`total += n` in `Sum[N any]` → `operator + not defined on total (variable of type N constrained by any)`. The fix: narrow the constraint (`Number`). If you need `==`, use `comparable`.

**2. Passing a `[]Product` to a `[]any` parameter.** The two slices are laid out differently in memory (40 and 16 bytes), hence `cannot use products (variable of type []Product) as []any value`. The fix: a type parameter instead of `any` (`Filter[T any]`).

**3. Writing `errors.AsType(err)` without square brackets.** `E` is only in the result and cannot be inferred from the arguments: `cannot infer E`. The fix: `errors.AsType[*StockError](err)`.

**4. A type that is not in the list.** `Number` is only `int | int64`: pass a `float64` or a `Tiyin` and you get `does not satisfy Number`. For `Tiyin` use `~int64` (the "Going deeper" section); for `float64`, add `float64` to the constraint.

**5. Arguments that do not agree with each other.** `Filter(orders, func(p Product) bool {…})` → `does not match inferred type func(Order) bool for func(T) bool`: `T` was inferred from the first argument, and `keep` has to match it.

**6. A type parameter everywhere.** `writeTotal[W io.Writer](w W, …)` works, but `W` ties nothing: `w io.Writer` is enough and the code is simpler (see the "Where a type parameter is not needed" section).

```go
func SumBy[T any, N Number](items []T, value func(T) N) N {
	var total N
	for _, x := range items {
		total += value(x)
	}
	return total
}
```

The body is like `Sum`: `value(x)` in place of `n`.

**Step 2.**

```go
func paidTotal(orders []Order) int64 {
	paid := Filter(orders, func(o Order) bool { return o.Status == StatusPaid })

}
```

In `Filter`, `T = Order` (from `orders`). In `SumBy`, `T = Order` (from `paid`) and `N = int64` from the result of the `value` function. Both are type inference.
