## Что вы узнаете

В bozor `go run` печатает два списка: товары с малым остатком и оплаченные заказы. Тела двух функций, которые их отбирают, совпадают буква в букву, различаются только типы.
Появится третий тип — придётся писать третью копию. Нельзя ли написать тело один раз, а тип выбирать при вызове?

**Главная идея:** **параметр типа** — это параметр функции для *типа*. Он объявляется в квадратных скобках после имени функции и перед обычными параметрами: `[T any]`.
Тело функции проверяется **один раз**, по constraint: constraint определяет, какими типами может быть `T`, а значит, какие операции с `T` допустимы в теле.
При каждом вызове компилятор выводит `T` из аргументов и проверяет только сам вызов: подходит ли тип под constraint и согласованы ли аргументы.

К концу урока вы:

- замените две копии `filterProducts` и `filterOrders` одним `Filter[T any]`;
- напишете сумму для `int` и `int64` одной функцией `Sum[N Number]` и выберете `comparable`, когда нужен `==`;
- прочитаете generic-ошибки компилятора: `cannot use … as []any`, `does not match inferred type`, `operator + not defined … constrained by any`, `cannot infer E`;
- уберёте параметр типа там, где вызывается только метод (`writeTotal`), и прочитаете квадратные скобки в `errors.AsType[*StockError](err)`.

Три главных новых слова сегодня:

| Слово | Простой смысл | По-английски |
|---|---|---|
| параметр типа | имя в квадратных скобках после имени функции (`T`): с каким типом работает функция, выбирает вызов | type parameter |
| ограничение (constraint) | интерфейс, который определяет, какими типами может быть `T` и какие операции для него есть | constraint |
| вывод типов (type inference) | компилятор сам находит `T` по аргументам вызова | type inference |

Вспомогательные слова объясняются одной фразой там, где встречаются: **generic-функция**, **аргумент типа**, **инстанцирование**, **набор типов (type set)**, тильда `~`.

## Проблема: две функции с одинаковым телом

Исходная программа урока — `_video/00-takror/main.go`. Это полная программа; `Product`, `OrderItem`, `OrderStatus` и `Order` — типы из GB-2.03.

```go filename="_video/00-takror/main.go" showLineNumbers
package main

import (
	"fmt"
)

// Product — katalogdagi bitta mahsulot (GB-2.03).
type Product struct {
	ID    int64
	Name  string
	Price int64 // tiyin
	Stock int
}

// OrderItem — buyurtmadagi bitta qator (GB-2.03).
type OrderItem struct {
	ProductID int64
	Price     int64 // tiyin
	Quantity  int
}

// OrderStatus — buyurtma holati (GB-2.03).
type OrderStatus int

const (
	StatusNew OrderStatus = iota
	StatusPaid
)

// Order — bitta buyurtma (GB-2.03).
type Order struct {
	ID     int64
	Items  []OrderItem
	Status OrderStatus
}

func filterProducts(ps []Product, keep func(Product) bool) []Product {
	var out []Product
	for _, p := range ps {
		if keep(p) {
			out = append(out, p)
		}
	}
	return out
}

func filterOrders(orders []Order, keep func(Order) bool) []Order {
	var out []Order
	for _, o := range orders {
		if keep(o) {
			out = append(out, o)
		}
	}
	return out
}

func main() {
	products := []Product{
		{ID: 1, Name: "olma", Price: 1_200_000, Stock: 40},
		{ID: 2, Name: "non", Price: 400_000, Stock: 3},
		{ID: 3, Name: "choy", Price: 2_500_000, Stock: 0},
	}
	orders := []Order{
		{ID: 7, Status: StatusPaid, Items: []OrderItem{{ProductID: 1, Price: 1_200_000, Quantity: 3}}},
		{ID: 8, Status: StatusNew, Items: []OrderItem{{ProductID: 2, Price: 400_000, Quantity: 5}}},
		{ID: 9, Status: StatusPaid, Items: []OrderItem{{ProductID: 2, Price: 400_000, Quantity: 2}}},
	}

	low := filterProducts(products, func(p Product) bool { return p.Stock < 5 })
	paid := filterOrders(orders, func(o Order) bool { return o.Status == StatusPaid })
	for _, p := range low {
		fmt.Println("kam qolgan:", p.Name, p.Stock)
	}
	for _, o := range paid {
		fmt.Println("toʻlangan buyurtma:", o.ID)
	}
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1–35 | `package main`, `import`, `Product`, `OrderItem`, `OrderStatus`, `Order` | типы из GB-2.03: товар, строка заказа, статус заказа и заказ |
| 37 | `func filterProducts(ps []Product, keep func(Product) bool) []Product {` | первый параметр `ps` — слайс товаров; второй `keep` — параметр типа **функция**: принимает `Product`, возвращает `bool`; результат — `[]Product` |
| 38 | `var out []Product` | `out` — nil-слайс (GB-2.01): пока пустой |
| 39–41 | `for _, p := range ps { if keep(p) { out = append(out, p) } }` | для каждого `p` вызывается `keep(p)`; если вернул `true`, `p` добавляется в `out` |
| 44 | `return out` | возвращаются отобранные товары |
| 47–55 | `func filterOrders(orders []Order, keep func(Order) bool) []Order { … }` | вторая функция: тело снова те же семь строк, вместо `p` — `o` |
| 58–67 | `products := …`, `orders := …` | данные: товары olma (40), non (3), choy (0); заказы 7 (оплачен), 8 (новый), 9 (оплачен) |
| 69 | `low := filterProducts(products, func(p Product) bool { return p.Stock < 5 })` | вместо `keep` — анонимная функция (GB-1.08): принимает `p`, возвращает `true`, если остаток меньше 5. Результат записывается в `low` |
| 70 | `paid := filterOrders(orders, func(o Order) bool { return o.Status == StatusPaid })` | `true`, если `Status` равен `StatusPaid` (оплачен); результат записывается в `paid` |
| 71–76 | два цикла `for` | выводят элементы `low` и `paid` |

`keep func(Product) bool` отличается от `fn func()` из GB-2.09: у этой функции есть и параметр, и результат. Поэтому условие передаётся при вызове, а не зашито в теле.

Запускаем программу:

```console
$ ./_video/run.sh 00-takror go run .
kam qolgan: non 3
kam qolgan: choy 0
toʻlangan buyurtma: 7
toʻlangan buyurtma: 9
```

Мало осталось у `non` (3) и `choy` (0), оплачены заказы 7 и 9. Теперь разница между двумя функциями:

| | `filterProducts` | `filterOrders` |
|---|---|---|
| 1-й параметр | `ps []Product` | `orders []Order` |
| тип `keep` | `func(Product) bool` | `func(Order) bool` |
| тип `out` | `[]Product` | `[]Order` |
| переменная цикла | `p` | `o` |
| тип результата | `[]Product` | `[]Order` |
| всё остальное | `var out`, `for`, `if keep`, `append`, `return` | то же самое |

Разница только в названиях типов. Логика — «обойти элементы и собрать те, для которых `keep` вернул `true`» — от типа вообще не зависит. Появится третий тип (например, `Customer`) — понадобится ещё одна копия.

Ian Lance Taylor из команды Go описывает именно этот случай: один и тот же код пишется много раз, и копии различаются только используемым типом. Тогда стоит подумать о параметре типа.
Но сначала попробуем простое решение.

## Первая попытка: одна функция с `any`

Из GB-2.07 вы знаете: `any` — интерфейс без методов, ему подходит любое значение. Значит, можно написать одну функцию, принимающую `[]any`? Её тело то же (`_video/01-any/main.go`):

```go
func filterAny(items []any, keep func(any) bool) []any {
	var out []any
	for _, x := range items {
		if keep(x) {
			out = append(out, x)
		}
	}
	return out
}
```

При вызове внутри `keep` значение нужно снова превратить в `Product`: `x.(Product)` — это type assertion из GB-2.07, он достаёт `Product` из интерфейса.

```go
low := filterAny(products, func(x any) bool { return x.(Product).Stock < 5 })
```

`Product` подходит под `any`. А слайс `[]Product` подойдёт под слайс `[]any`? Что скажет `go build`?

**A)** сборка пройдёт · **B)** ошибка компиляции · **C)** сборка пройдёт, потом `panic`

<details>
<summary>Ответ</summary>

**B: ошибка компиляции.** Тип `products` — `[]Product`, а параметр — `[]any`; Go сам такой слайс не преобразует. Если вы выбрали **A**, вы решили, что раз `Product` подходит под `any`, то и слайс подойдёт.
Если выбрали **C**, вы ждали ошибку во время работы: эта ошибка находится до запуска программы.

```console
$ ./_video/run.sh 01-any go build
# github.com/abdurahmon27/bozor
./main.go:59:19: cannot use products (variable of type []Product) as []any value in argument to filterAny
```

</details>

Прочитайте сообщение. `./main.go:59:19` — файл, строка 59, столбец 19: аргумент `products`. `cannot use products (variable of type []Product) as []any value in argument to filterAny` —
«нельзя использовать `products` (тип `[]Product`) как значение `[]any` в аргументе `filterAny`». Первая строка `# github.com/abdurahmon27/bozor` — имя модуля.

Почему? Причина в памяти. Измерим размеры через `unsafe.Sizeof` (`_video/01b-olcham/main.go`; тело `main` — эта строка):

```go
fmt.Println(unsafe.Sizeof(Product{}), unsafe.Sizeof(any(nil)))
```

```console
$ ./_video/run.sh 01b-olcham go run .
40 16
```

`Product` — **40 байт**, `any` (значение интерфейса, GB-2.07) — **16 байт**: указатели на тип и на значение. На этой платформе (`linux/amd64`) так.

```text
[]Product  (3 элемента):  | Product: 40 байт | Product: 40 байт | Product: 40 байт |   сама структура, подряд
[]any      (3 элемента):  | тип + знач.: 16  | тип + знач.: 16  | тип + знач.: 16  |   каждый — указатели
```

Элементы двух слайсов лежат в памяти по-разному, поэтому один нельзя передать вместо другого. Другой путь — скопировать каждый элемент в новый слайс `[]any`. Дальше:

| Шаг | Что происходит |
|---|---|
| 1 | `[]Product` → новый `[]any`: каждый элемент копируется |
| 2 | `filterAny` возвращает `[]any` |
| 3 | каждый раз тип нужно восстанавливать через `x.(Product)` |
| 4 | при ошибке в типе assertion останавливает работающую программу через `panic` ([спецификация Go](https://go.dev/ref/spec#Type_assertions)) |

В итоге код длиннее и опаснее, а ошибка типа обнаруживается не при компиляции, а во время работы. Об этом пишет и Go FAQ: у этих двух типов нет одинакового представления в памяти.

## Параметр типа: один `Filter`

Решение Go — **параметр типа** (type parameter). Он объявляется после имени функции, перед обычными параметрами, в квадратных скобках. Функция с параметром типа называется **generic-функцией** (`_video/02-filter/main.go`):

```go
func Filter[T any](items []T, keep func(T) bool) []T {
	var out []T
	for _, x := range items {
		if keep(x) {
			out = append(out, x)
		}
	}
	return out
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1 | `[T any]` | список параметров типа: `T` — имя для типа, его выбирает вызывающий. `any` после `T` — constraint: он говорит, каким типом может быть `T`; `any` — любым |
| 1 | `items []T`, `keep func(T) bool`, `[]T` | `T` используется как обычный тип: `items` — слайс `T`, `keep` — функция, принимающая `T`, результат — слайс `T` |
| 2 | `var out []T` | `out` — тоже слайс `T`, nil |
| 3–5 | `for _, x := range items { if keep(x) { out = append(out, x) } }` | `x` — каждый элемент (тип `T`); если `keep` вернул `true`, элемент добавляется в `out` |
| 8 | `return out` | возвращается `[]T` |

`Filter` — одно тело вместо `filterProducts` и `filterOrders`. Теперь вызовы в `main` (`T` мы не пишем):

```go
low := Filter(products, func(p Product) bool { return p.Stock < 5 })
paid := Filter(orders, func(o Order) bool { return o.Status == StatusPaid })
```

`T` мы не написали: компилятор выводит его из аргументов. Это **вывод типов** (type inference).

| Вызов | Первый аргумент | Вывод компилятора | Тип `keep` получается |
|---|---|---|---|
| `Filter(products, …)` | `[]Product` | `T = Product` | `func(Product) bool` |
| `Filter(orders, …)` | `[]Order` | `T = Order` | `func(Order) bool` |

Одна функция вместо двух. Вывод должен совпасть с тем, что было в начале:

```console
$ ./_video/run.sh 02-filter go run .
kam qolgan: non 3
kam qolgan: choy 0
toʻlangan buyurtma: 7
toʻlangan buyurtma: 9
```

Теперь неверный вызов: в `Filter` передаётся `orders`, а `keep` — функция, принимающая `Product` (`_video/04-mos-emas/main.go`):

```go
low := Filter(orders, func(p Product) bool { return p.Stock < 5 })
```

Что будет?

**A)** заработает: вернётся пустой слайс · **B)** ошибка компиляции · **C)** `panic` при запуске

<details>
<summary>Ответ</summary>

**B: ошибка компиляции.** Компилятор вывел `T` из первого аргумента: `Order`. Значит, `keep` должна принимать `Order`, а пришла функция, принимающая `Product`.
Если вы выбрали **A**, вы решили, что Go считает типы «достаточно похожими». Если выбрали **C**, вы ждали ошибку во время работы: ошибка типов в generic-вызове находится до запуска программы.

```console
$ ./_video/run.sh 04-mos-emas go build
# github.com/abdurahmon27/bozor
./main.go:59:24: in call to Filter, type func(p Product) bool of func(p Product) bool {…} does not match inferred type func(Order) bool for func(T) bool
```

</details>

Читаем сообщение: `in call to Filter` — ошибка в вызове `Filter`; `type func(p Product) bool of func(p Product) bool {…}` — тип переданного аргумента (`{…}` — так компилятор сокращает тело функции);
`does not match inferred type func(Order) bool for func(T) bool` — «для `func(T) bool` выведен тип `func(Order) bool`, и он не совпадает». Ошибка найдена до запуска программы.

`T` можно написать и самим, в квадратных скобках (`_video/03-tur/main.go`; тело `main`):

```go
fmt.Printf("%T\n", Filter[Product])
fmt.Printf("%T\n", Filter[Order])
```

Здесь `Product` — **аргумент типа** (type argument): конкретный тип, который подставляется вместо `T`. `%T` печатает тип значения (GB-2.08).


`main.Product` — `Product` из пакета `main`. Результат — обычный тип функции: принимает `[]Product` и функцию, возвращает `[]Product`. Подстановка аргумента типа вместо `T` называется **инстанцированием** (instantiation).
Передать `Filter` без квадратных скобок в `Printf` нельзя: нигде вывести `T`. Этого примера в папке курса нет: в `main` из `_video/03-tur/main.go` я заменил первый `Filter[Product]` на `Filter`, всё остальное то же.

```go

```

## Constraint: какие операции возможны с типом

Вторая копия: сумма. Остатки — `int`, суммы — `int64`; для обоих хотим одну `Sum`. Параметр типа `N`, constraint снова `any` (`_video/05-sum-any/main.go`):

```go
func Sum[N any](nums []N) N {
	var total N
	for _, n := range nums {
		total += n
	}
	return total
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1 | `func Sum[N any](nums []N) N` | `N` — параметр типа; `nums` — слайс чисел типа `N`; результат тоже `N` |
| 2 | `var total N` | переменная типа `N`, вначале нулевое значение (zero value) |
| 3–5 | `for _, n := range nums { total += n }` | каждый `n` прибавляется к `total` |
| 6 | `return total` | возвращается сумма |

Пока `Sum` вызывается только с `int` и `int64`: `Sum([]int{…})`, `Sum([]int64{…})`. Скомпилируется ли этот код?

**A)** да, работает с обоими типами · **B)** нет: `+` не определён для `N` · **C)** ошибка только со `string`

<details>
<summary>Ответ</summary>

**B.** Тело generic-функции проверяется **один раз**, а не по вызовам. Про `N` компилятор знает только то, что говорит constraint — здесь `any`. Под `any` попадают и `struct`, и `bool`, а у них нет `+`.
Если вы выбрали **A**, вы решили, что компилятор проверяет `Sum` с `int` из вызова. Если выбрали **C**, вы ждали только типа из вызова: ошибка относится не к вызову, а к телу.

```console
$ ./_video/run.sh 05-sum-any go build
# github.com/abdurahmon27/bozor
./main.go:40:3: invalid operation: operator + not defined on total (variable of type N constrained by any)
```

</details>

Сообщение: `./main.go:40:3` — строка 40 (`total += n`); `operator + not defined on total` — «операция `+` не определена для `total`»; `(variable of type N constrained by any)` —
«`total` — переменная типа `N`, constraint у `N` — `any`». **Правило:** тело может использовать только те операции, которые есть у **всех** типов из constraint. Множество типов, которые разрешает constraint, называется **набором типов** (type set); у `any` это все типы.
Это частая ошибка.

Исправление: пишем constraint сами (`_video/06-sum/main.go`). `Number` — тоже интерфейс, но вместо методов в нём **список типов**. Вертикальная черта `|` читается как «или»:

```go
type Number interface {
	int | int64
}

func Sum[N Number](nums []N) N {
```

Теперь `N` может быть только `int` или `int64`; у обоих есть `+`, компилятор согласен. Тело то же, изменилась только первая строка `Sum`. Такой интерфейс может быть только constraint, но не типом переменной ([спецификация Go](https://go.dev/ref/spec#General_interfaces)).
В `main` два вызова:

```go
fmt.Println(Sum([]int{40, 3, 0}), Sum([]int64{3_600_000, 800_000}))
```

```console
$ ./_video/run.sh 06-sum go run .
43 4400000
```

| Вызов | `N` | Вычисление | Результат |
|---|---|---|---|
| `Sum([]int{40, 3, 0})` | `int` | 40 + 3 + 0 | `43` |
| `Sum([]int64{3_600_000, 800_000})` | `int64` | 3 600 000 + 800 000 | `4400000` (тийин) |

Промежуточный вопрос. `Contains` проверяет, есть ли `x` в слайсе: каждый `v` сравнивается с `x` через `==`. Constraint — `any`. Что скажет `go build`? (`_video/07-contains/main.go`)

```go
func Contains[T any](items []T, x T) bool {
	for _, v := range items {
		if v == x {
			return true
		}
	}
	return false
}
```

**A)** сборка пройдёт · **B)** ошибка компиляции · **C)** работает только со `string`

<details>
<summary>Ответ</summary>

**B.** `==` есть не у всех типов: слайсы, map и функции через `==` сравнивать нельзя ([спецификация Go](https://go.dev/ref/spec#Comparison_operators)), а в наборе типов `any` они есть. То же правило, что у `Sum`: тело должно использовать операцию, которая есть у всех типов.
Если вы выбрали **A**, вы решили, что `==` работает с любым типом. Если выбрали **C**, вы пропустили, что ошибка направлена на тело, а не на вызов.

```console
$ ./_video/run.sh 07-contains go build
# github.com/abdurahmon27/bozor
./main.go:39:6: invalid operation: v == x (incomparable types in type set)
```

</details>

`incomparable types in type set` — «в наборе типов есть несравнимые типы». Исправление — заранее объявленный в Go constraint **`comparable`**: типы, которые можно сравнивать через `==` (`_video/07b-comparable/main.go`):

```go
func Contains[T comparable](items []T, x T) bool {
```

```go
fmt.Println(Contains([]string{"olma", "non"}, "non"), Contains([]int64{1, 2}, 3))
```

```console
$ ./_video/run.sh 07b-comparable go run .
true false
```

`"non"` в списке есть — `true`; `3` в `[]int64{1, 2}` нет — `false`. Стандартная библиотека: `slices.Contains` объявлен именно так (`[S ~[]E, E comparable]`; часть `~[]E` разберём в GB-3.05). Вывод снова обрезан до первых 4 строк:

```console
$ go doc slices.Contains | head -4
package slices // import "slices"

func Contains[S ~[]E, E comparable](s S, v E) bool
    Contains reports whether v is present in s.
```

## Где параметр типа не нужен: вызывается только метод

Теперь обратный случай. Коллега написал `writeTotal` как generic (`_video/08-writer/main.go`):

```go
func writeTotal[W io.Writer](w W, total int64) error {
	_, err := fmt.Fprintf(w, "jami: %d tiyin\n", total)
	return err
}
```

Здесь `W` — параметр типа с constraint `io.Writer`: обычный интерфейс с методом тоже может быть constraint, у `W` обязан быть метод `Write`. `total` — записываемая сумма. `main` вызывает функцию так:

```go
if err := writeTotal(os.Stdout, 4_400_000); err != nil { … }
```

```console
$ ./_video/run.sh 08-writer go run .
jami: 4400000 tiyin
```

Программа работает правильно. Но `W` встречается в сигнатуре **один раз**: только как тип `w`. Другие типы он не связывает. Функция делает с `w` одно — вызывает метод `Write` (через `Fprintf`).
Для этого хватает обычного параметра `io.Writer` из GB-2.07 (`_video/08b-writer/main.go`):

```go
func writeTotal(w io.Writer, total int64) error {
```

Тело то же, `[W io.Writer]` нет, вместо `w W` — `w io.Writer`.

```console
$ ./_video/run.sh 08b-writer go run .
jami: 4400000 tiyin
```

Вывод буква в букву тот же, а код проще. Правила Taylor ([When To Use Generics](https://go.dev/blog/when-generics)):

| Ситуация | Что взять |
|---|---|
| один и тот же код повторяется, различаясь только типом | параметр типа (`Filter`, `Sum`) |
| со значением вызывается только метод | интерфейс (`io.Writer`) |
| `T` связывает тип входа и тип выхода | параметр типа: в `Filter[T]` входит `[]T`, выходит `[]T`; убрав `T`, потеряем тип результата (`[]Product`) |
| реализация метода у каждого типа своя | своему типу — свой метод, вызов через интерфейс |

Собственный пример Taylor: вместо `func ReadSome[T io.Reader](r T) ([]byte, error)` пишите `func ReadSome(r io.Reader) ([]byte, error)`. Он говорит: *"Omitting the type parameter makes the function easier to write, easier to read, and the execution time will likely be the same."*
Не заменяйте интерфейс параметром типа ради скорости. В код-ревью опирайтесь на эти правила.

## Читаем квадратные скобки в `errors.AsType`

В GB-2.08 мы отложили квадратные скобки в `errors.AsType` на этот урок. Теперь можно прочитать его объявление (`| head -4` обрезает вывод до первых 4 строк):

```console
$ go doc errors.AsType | head -4
package errors // import "errors"

func AsType[E error](err error) (E, bool)
    AsType finds the first error in err's tree that matches the type E, and if
```

`func AsType[E error](err error) (E, bool)`: `E` — параметр типа, constraint `error`, то есть у `E` обязан быть метод `Error()`. Обычный параметр один: `err`, тип `error`. А `E` встречается только в **результате**: найденная ошибка и `bool`.

А если скобки не писать? `err` есть — сумеет ли компилятор вывести тип сам, как у `Filter`? Две строки кода (`_video/09-astype/main.go`; внутри `err` лежит `*StockError`):

```go
err := fmt.Errorf("buyurtma 7: %w", &StockError{Name: "olma", Stock: 40, Want: 41})
if se, ok := errors.AsType(err); ok {
```

**A)** получится `E = error` · **B)** ошибка: `E` не определяется · **C)** найдётся `E = *StockError`

<details>
<summary>Ответ</summary>

**B.** При вызове `E` выводится только из типов аргументов; в какую переменную пишется результат, не учитывается. Тип `err` — `error`, в нём `E` нет.
Если вы выбрали **A**, вы решили, что компилятор подставит `error` вместо `E`: `error` — тип аргумента, а `E` из него не выводится. Если выбрали **C**, вы решили, что компилятор видит `*StockError` внутри `err`: тип `err` — `error`, а то, что внутри, становится известно только во время работы.

```console
$ ./_video/run.sh 09-astype go build
# github.com/abdurahmon27/bozor
./main.go:51:28: in call to errors.AsType, cannot infer E (declared at $GOROOT/src/errors/wrap.go:167:13)
```

</details>

`cannot infer E` — «не удалось вывести `E`». В скобках указано место, где объявлен `E`; `$GOROOT` — папка, куда установлен Go. Поэтому тип пишем сами (`_video/10-astype-ok/main.go`):

```go
if se, ok := errors.AsType[*StockError](err); ok {
	fmt.Printf("%T %s %d\n", se, se.Name, se.Stock)
}
```

```console
$ ./_video/run.sh 10-astype-ok go run .
*main.StockError olma 40
```

`*StockError` в квадратных скобках — **аргумент типа**, а `E` — параметр типа. В GB-2.08 мы назвали это «параметром типа»; правильно — аргумент типа. В этой лаборатории `StockError` лежит в пакете `main`, поэтому `%T` печатает `*main.StockError`.
Тип `se` — `*StockError`, поэтому его поля (`se.Name`, `se.Stock`) читаются напрямую.

## Глубже (необязательно): `~int64` и `type Tiyin int64`

Заведём отдельный тип для денег: `type Tiyin int64` — новый тип, у которого **базовый тип** (underlying type) `int64`, как у `OrderStatus` (GB-2.03). Это только пример: в bozor деньги остаются обычным `int64`.
Передадим в `Sum` слайс `Tiyin` (`_video/11-tilde/main.go`):

```go
type Tiyin int64
```

```go
fmt.Println(Sum([]Tiyin{1_200_000, 400_000}))
```

```console
$ ./_video/run.sh 11-tilde go build
# github.com/abdurahmon27/bozor
./main.go:53:17: Tiyin does not satisfy Number (possibly missing ~ for int64 in Number)
```

`Tiyin does not satisfy Number` — «`Tiyin` не удовлетворяет `Number`». Подсказка: `possibly missing ~ for int64 in Number` — «возможно, в `Number` перед `int64` не хватает `~`».
В списке `int | int64` стоит именно `int64`, а `Tiyin` — другой тип. Исправление — тильда (`_video/12-tilde-ok/main.go`):

```go
type Number interface {
	~int | ~int64
}
```

`~int64` — это не один тип, а **все** типы с базовым типом `int64`; `~int` — все с базовым типом `int`.

```console
$ ./_video/run.sh 12-tilde-ok go run .
1600000
```

`1 200 000 + 400 000 = 1 600 000`. В объявлениях пакета `slices` тильда встречается часто, например:

```console
$ go doc slices.Clone | head -4
package slices // import "slices"

func Clone[S ~[]E, E any](s S) S
    Clone returns a copy of the slice. The elements are copied using assignment,
```

Generics есть в языке с Go 1.18 ([Go 1.18 release notes](https://go.dev/doc/go1.18#generics)).

## Частые ошибки

Всё это уже встречалось на странице; здесь коротко, с исправлением.

**1. «`any` — любой тип, значит, в теле работает любая операция».** Нет: тело может использовать только операции, которые есть у **всех** типов из constraint (см. раздел «Constraint»).
`total += n` в `Sum[N any]` → `operator + not defined on total (variable of type N constrained by any)`. Исправление: сузьте constraint (`Number`). Нужен `==` — `comparable`.

**2. Передать `[]Product` в параметр `[]any`.** В памяти эти два слайса устроены по-разному (40 и 16 байт), поэтому `cannot use products (variable of type []Product) as []any value`. Исправление: параметр типа вместо `any` (`Filter[T any]`).

**3. Написать `errors.AsType(err)` без квадратных скобок.** `E` есть только в результате и не выводится из аргументов: `cannot infer E`. Исправление: `errors.AsType[*StockError](err)`.

**4. Тип, которого нет в списке.** `Number` — только `int | int64`: передадите `float64` или `Tiyin` — получите `does not satisfy Number`. Для `Tiyin` — `~int64` (раздел «Глубже»); для `float64` — добавьте `float64` в constraint.

**5. Аргументы не согласованы между собой.** `Filter(orders, func(p Product) bool {…})` → `does not match inferred type func(Order) bool for func(T) bool`: `T` вывелся из первого аргумента, и `keep` должна ему соответствовать.

**6. Параметр типа везде.** `writeTotal[W io.Writer](w W, …)` работает, но `W` ничего не связывает: хватает `w io.Writer`, и код проще (см. раздел «Где параметр типа не нужен»).

```go
func paidTotal(orders []Order) int64 {
	paid := Filter(orders, func(o Order) bool { return o.Status == StatusPaid })
	return SumBy(paid, func(o Order) int64 { return o.Total() })
}
```

В `Filter` `T = Order` (из `orders`). В `SumBy` `T = Order` (из `paid`), `N = int64` — из результата функции `value`. Оба случая — вывод типов.
