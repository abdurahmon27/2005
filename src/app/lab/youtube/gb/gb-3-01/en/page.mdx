## What you will learn

Until now the bozor catalog was written inside `main.go`: when a price changes, you rebuild the program. Now the catalog comes from a file.
Each line has an ID, a name, the price in som and the stock, separated by semicolons:

```console
$ cat katalog.txt
1;olma;12000;40
2;oʻrik;35000;5
3;non;4000;100
4;choy;25000;8
```

How does the program read this file? And why must one `loadCatalog` function read the catalog the same way from a file, from text typed in the terminal
and from text inside a test?

**The one idea:** `io.Reader` is an interface with one method. The caller gives `Read` a byte slice `p` that serves as the buffer; the Reader writes
at most `len(p)` bytes into it and returns in `n` how many it wrote; when the data is over it returns `io.EOF`. An open file hands out bytes in **chunks**
and knows nothing about lines or character boundaries. `bufio.Scanner` collects bytes from any `io.Reader` into its own buffer, builds lines
from them and tells you through `Err()` why it stopped. So one function that accepts an `io.Reader` instead of a file name works with a file,
with standard input and with test text.

By the end of the lesson you will:

- open the catalog with `os.Open` and `defer f.Close()` and read the `Read` contract in `go doc io.Reader`;
- call `f.Read` yourself, see in which chunks a file hands out its bytes, and read the file line by line with `bufio.Scanner`;
- run one `loadCatalog(r io.Reader)` function with a file, with `cat katalog.txt | go run .` and with `strings.NewReader`;
- see with your own eyes how data disappears **silently** when `sc.Err()` is not checked, and fix it; in the homework you teach `loadCatalog` to skip
  comments and to name the line with an error, until `go test` passes.

Today's three core new words:

| Word | Plain meaning | English term |
|---|---|---|
| `io.Reader` | an interface with one method: `Read(p)` fills your buffer with bytes and returns `io.EOF` at the end | io.Reader |
| `bufio.Scanner` | a reader that builds lines from bytes that arrive in chunks from a Reader | bufio.Scanner |
| accepting a Reader | a function takes an `io.Reader`, not a file name: one code for a file, stdin and a test | accept an io.Reader |

Helper ideas are explained in one sentence when they first appear: **standard input** (stdin) and the **vertical bar** (pipe), `strings.Split`,
the **offset** and the **buffer**.

## `os.Open`: opening the file

To reach the bytes of a file on disk, the program first has to **open** it. The starting code is the `run() error` and `main` shape from [GB-2.09](/lab/youtube/gb/gb-2-09/en),
and inside it only opens the file (`_video/01-open/main.go`):

```go filename="_video/01-open/main.go" showLineNumbers
// Video, 01-open: katalog.txt'ni oʻqish uchun ochadi (hali hech narsa oʻqimaydi).
package main

import (
	"fmt"
	"os"
)

func run() error {
	f, err := os.Open("katalog.txt")
	if err != nil {
		return err
	}
	defer f.Close()
	// … f'dan oʻqiymiz
	return nil
}

func main() {
	if err := run(); err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
}
```

| Line | Code | What it does |
|---|---|---|
| 1 | `// Video, 01-open: …` | a comment: Go does not read it |
| 2 | `package main` | this file is an executable program (GB-1.01) |
| 4–7 | `import ( "fmt"  "os" )` | `fmt` is for output, `os` is for working with the operating system: `Open` lives in this package |
| 9 | `func run() error {` | `run` is the function that does the work; its result is an `error` (GB-2.09) |
| 10 | `f, err := os.Open("katalog.txt")` | opens `katalog.txt` **for reading only**; returns two values: `f` (type `*os.File`, an open file) and `err` |
| 11–13 | `if err != nil { return err }` | if the file did not open, we return the error to whoever called `run` (GB-1.07) |
| 14 | `defer f.Close()` | closes the file when `run` ends; written right after the check (GB-2.09) |
| 15 | `// … f'dan oʻqiymiz` | a placeholder ("we read from `f`"): in the next sections we add code here |
| 16 | `return nil` | no error |
| 19–24 | `func main() { … }` | if `run` returns an error, `main` writes it to stderr and ends the program with `os.Exit(1)` (GB-2.09) |

Two remarks.

- `os.Open` opens the file **for reading only**. The difference from `os.Create` ([GB-2.07](/lab/youtube/gb/gb-2-07/en)): it does not create the file and does not empty it.
  If the file does not exist, it returns an error (we will see it in the mistakes section).
- For a file that was written, an error from `Close` could mean lost data, so in GB-2.09 we wrote `return f.Close()`. A file that was only read has nothing to lose,
  so a plain `defer f.Close()` is enough ([close(2)](https://man7.org/linux/man-pages/man2/close.2.html):
  deferred errors concern written data).

## `io.Reader`: one method

To read the file we need a method of `f`. Which method, and what does it guarantee? `go doc` ([GB-2.07](/lab/youtube/gb/gb-2-07/en)) tells us. Here is the start of the documentation
(the whole text is long; `head -n 5` takes only the first five lines):

```console
$ go doc io.Reader | head -n 5
package io // import "io"

type Reader interface {
	Read(p []byte) (n int, err error)
}
```

This is an interface with one method, like `Writer` in [GB-2.07](/lab/youtube/gb/gb-2-07/en). Its parts:

| Part | What it is |
|---|---|
| `Read` | the method name |
| `p []byte` | the **buffer** that the caller gives: room for bytes (`[]byte` is a slice of bytes) |
| `n int` | how many bytes `Read` wrote |
| `err error` | an error, or a sign that the data is over |

The rule from the documentation: `Read` writes **at most `len(p)` bytes** into `p` and returns in `n` how many. Always `0 <= n <= len(p)`.

An open file implements this interface without a declaration ([GB-2.07](/lab/youtube/gb/gb-2-07/en)). The `Read` of `*os.File`:

```console
$ go doc os.File.Read
package os // import "os"

func (f *File) Read(b []byte) (n int, err error)
    Read reads up to len(b) bytes from the File and stores them in b. It
    returns the number of bytes read and any error encountered. At end of file,
    Read returns 0, io.EOF.
```

The signature is the same: `Read(b []byte) (n int, err error)` (the parameter name `b` does not matter). From the documentation: "reads up to `len(b)` bytes, returns their number and an error. **At end of file**
it returns `0, io.EOF`." **EOF** means *end of file*. `io.EOF` is a **sentinel error** (like `ErrNotFound` from
[GB-2.08](/lab/youtube/gb/gb-2-08/en)): it is created once in the package, and the caller compares with it. Its own documentation:

```console
$ go doc io.EOF
package io // import "io"

var EOF = errors.New("EOF")
    EOF is the error returned by Read when no more input is available. (Read
    must return EOF itself, not an error wrapping EOF, because callers will test
    for EOF using ==.) Functions should return EOF only to signal a graceful
    end of input. If the EOF occurs unexpectedly in a structured data stream,
    the appropriate error is either ErrUnexpectedEOF or some other error giving
    more detail.
```

Notice: "Read must return EOF itself, **not wrapped**, because callers test for it with `==`". That is why the code below uses
`==` and not `errors.Is`.

## Calling `Read` ourselves

Let us test the contract: the buffer is deliberately small, 20 bytes. The program (`_video/02-read/main.go`):

```go filename="_video/02-read/main.go" showLineNumbers
// Video, 02-read: f.Read'ni oʻzimiz chaqiramiz — 20 baytlik buferga boʻlak-boʻlak.
package main

import (
	"fmt"
	"io"
	"os"
)

func run() error {
	f, err := os.Open("katalog.txt")
	if err != nil {
		return err
	}
	defer f.Close()
	buf := make([]byte, 20)
	for {
		n, err := f.Read(buf)
		fmt.Printf("%d %q\n", n, buf[:n])
		if err == io.EOF {
			break // fayl tugadi
		}
		if err != nil {
			return err
		}
	}
	return nil
}

func main() {
	if err := run(); err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
}
```

The new lines:

| Line | Code | What it does |
|---|---|---|
| 6 | `"io"` | the `io` package, for `io.EOF` |
| 16 | `buf := make([]byte, 20)` | a 20-byte buffer: made with `make`, filled with zeros (GB-2.01) |
| 17 | `for {` | a loop with no condition: runs until `break` or `return` (GB-1.06) |
| 18 | `n, err := f.Read(buf)` | fills `buf` with bytes of the file; `n` is how many bytes, `err` is an error or `io.EOF` |
| 19 | `fmt.Printf("%d %q\n", n, buf[:n])` | prints `n` and **only the written** bytes: `buf[:n]` is the first `n` elements of `buf` (GB-2.01). `%q` means in quotes, with `\n` and similar characters written as escapes (GB-1.04) |
| 20–22 | `if err == io.EOF { break }` | if the file is over, leave the loop. `==`, because `Read` does not wrap `io.EOF` |
| 23–25 | `if err != nil { return err }` | any other error is returned |

Line 19 is **before** line 20: the rule of the documentation is *first n bytes, then err*. `Read` may return bytes together with an error,
and those bytes must not be lost.

The file is 63 bytes, the buffer is 20 bytes. What will `Read` return?

**A)** each `Read` returns one line · **B)** `20, 20, 20, 3`, and `EOF` comes together with the last `Read` · **C)** `20, 20, 20, 3`, then a separate `0` bytes and `EOF`

<details>
<summary>Answer</summary>

**C.** The file has 63 bytes: 20 + 20 + 20 + 3. The fourth `Read` returns the last 3 bytes with no error, and the fifth call returns `0` and `io.EOF`.
If you chose **A**, you thought `Read` knows about lines: it knows only bytes. **B** — other Readers may behave like this
(the documentation allows it), but `*os.File` returns the last bytes without an error and `EOF` on the next call.

</details>

```console
$ ./_video/run.sh 02-read go run .
20 "1;olma;12000;40\n2;o\xca"
20 "\xbbrik;35000;5\n3;non;4"
20 "000;100\n4;choy;25000"
3 ";8\n"
0 ""
```

Let us go through the output step by step. An open file remembers where reading stopped: this is the **offset**, the number of bytes from the start of the file that have been passed. Each `Read`
asks the operating system for up to `len(buf)` bytes from that place and moves the offset forward ([read(2)](https://man7.org/linux/man-pages/man2/read.2.html)):

| `Read` | Bytes of the file (offset) | `n` | `err` | Printed line |
|---|---|---|---|---|
| 1 | 0–19 | 20 | `nil` | `20 "1;olma;12000;40\n2;o\xca"` |
| 2 | 20–39 | 20 | `nil` | `20 "\xbbrik;35000;5\n3;non;4"` |
| 3 | 40–59 | 20 | `nil` | `20 "000;100\n4;choy;25000"` |
| 4 | 60–62 | 3 | `nil` | `3 ";8\n"` |
| 5 | — (offset 63: the file is over) | 0 | `io.EOF` | `0 ""` |

Two conclusions:

- **`Read` does not know about lines.** The first chunk ended in the middle of the second line (`2;o`), the rest is in the next chunk.
- **`Read` does not know about characters either.** The `ʻ` in `oʻrik` was two bytes (`ca bb`, [GB-2.10](/lab/youtube/gb/gb-2-10/en)). The first chunk ended on its first byte (`\xca`),
  and the second byte (`\xbb`) is at the start of the next chunk: `%q` shows an invalid byte as `\x..`.

Putting lines and characters back together from chunks is the job of other code.

## `bufio.Scanner`: lines from chunks

The `bufio` package of the standard library does this (*buffered I/O*, input and output with a buffer). `bufio.NewScanner` takes any `io.Reader`,
collects bytes into its own buffer with `Read` and builds lines from them. The program (`_video/03-scan/main.go`):

```go filename="_video/03-scan/main.go" showLineNumbers
// Video, 03-scan: bufio.Scanner fayldan qatorlarni beradi.
package main

import (
	"bufio"
	"fmt"
	"os"
)

func run() error {
	f, err := os.Open("katalog.txt")
	if err != nil {
		return err
	}
	defer f.Close()
	sc := bufio.NewScanner(f)
	for sc.Scan() {
		fmt.Printf("%q\n", sc.Text())
	}
	if err := sc.Err(); err != nil {
		return err
	}
	return nil
}

func main() {
	if err := run(); err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
}
```

| Line | Code | What it does |
|---|---|---|
| 5 | `"bufio"` | the `bufio` package |
| 16 | `sc := bufio.NewScanner(f)` | creates a Scanner that reads from `f`; `f` is an `io.Reader`. The Scanner calls `f.Read` by itself |
| 17 | `for sc.Scan() {` | `Scan` returns `true` if it found the next line, and `false` if the data is over or an error happened. It is the condition of the `for` ([GB-1.06](/lab/youtube/gb/gb-1-06/en)) |
| 18 | `fmt.Printf("%q\n", sc.Text())` | `sc.Text()` gives the found line as a `string` |
| 20–22 | `if err := sc.Err(); err != nil { return err }` | after the loop: why did `Scan` stop? If `sc.Err()` returned an error, we return it. The short `if` is the form from [GB-1.05](/lab/youtube/gb/gb-1-05/en) |

Now, looking at the previous output, think: how does the second line of the file, `oʻrik`, look in `sc.Text()`?

**A)** `"2;o\xca"`: broken, as in the `Read` chunk · **B)** `"2;oʻrik;35000;5"`: whole · **C)** an error: UTF-8 is broken

<details>
<summary>Answer</summary>

**B.** The Scanner collects bytes in its own buffer and waits for the end of the line, then gives the whole line. The chunk borders of `Read` are not visible to it.
If you chose **A**, you thought the Scanner gives the `Read` chunk; **C** — a broken character never reaches `Text`,
because both bytes of `ʻ` sit next to each other inside the line.

</details>

```console
$ ./_video/run.sh 03-scan go run .
"1;olma;12000;40"
"2;oʻrik;35000;5"
"3;non;4000;100"
"4;choy;25000;8"
```

Four lines, `oʻrik` whole. The final `\n` is removed (and so is `\r\n` in Windows files). Even if the file does not end with `\n`, the last line
is still returned. After the loop `sc.Err()` is `nil`: **end of file is not an error**, so `io.EOF` did not appear.

This is what happens inside the Scanner (each row is one `Scan`):

| `Scan` | What the Scanner does | Result | `sc.Text()` |
|---|---|---|---|
| 1 | the buffer is empty: it calls `f.Read` (63 bytes arrive), looks for the first `\n` | `true` | `"1;olma;12000;40"` |
| 2 | up to the next `\n` in what is left in the buffer | `true` | `"2;oʻrik;35000;5"` |
| 3 | the same | `true` | `"3;non;4000;100"` |
| 4 | the same | `true` | `"4;choy;25000;8"` |
| 5 | the buffer is empty: `f.Read` returns `0` bytes and `io.EOF`; EOF is not an error | `false` | — (`sc.Err()` = `nil`) |

A single line has a limit: the Scanner's buffer grows when needed, but one line must not exceed about **64 KiB** (65,536 bytes; 1 KiB = 1024 bytes).
In the documentation this is `bufio.MaxScanTokenSize = 64 * 1024` ([pkg.go.dev](https://pkg.go.dev/bufio#pkg-constants)). We meet this limit in the mistakes section.

## `parseLine`: from a line to a `Product`

A line is still a plain `string`. `parseLine` turns it into a `Product`. The video shows its body briefly; the full code is in `main.go`:

```go
func parseLine(line string) (Product, error) {
	parts := strings.Split(line, ";")
	if len(parts) != 4 {
		return Product{}, fmt.Errorf("4 ta maydon kerak, bor %d", len(parts))
	}
	id, err := strconv.ParseInt(parts[0], 10, 64)
	if err != nil {
		return Product{}, fmt.Errorf("ID: %w", err)
	}
	name := parts[1]
	if name == "" {
		return Product{}, errors.New("nom boʻsh")
	}
	if !utf8.ValidString(name) {
		return Product{}, errors.New("nom UTF-8 emas") // GB-2.10
	}
	price, err := parsePrice(parts[2])
	if err != nil {
		return Product{}, fmt.Errorf("narx: %w", err)
	}
	stock, err := strconv.Atoi(parts[3])
	if err != nil {
		return Product{}, fmt.Errorf("qoldiq: %w", err)
	}
	if stock < 0 {
		return Product{}, fmt.Errorf("qoldiq manfiy boʻlmasin, keldi %d", stock)
	}
	return Product{ID: id, Name: name, Price: price, Stock: stock}, nil
}
```

| Line | What it does |
|---|---|
| `parts := strings.Split(line, ";")` | `strings.Split` cuts the line at `;` and returns a `[]string`: `"1;olma;12000;40"` → `["1" "olma" "12000" "40"]` |
| `if len(parts) != 4 {…}` | if there are not four fields, an error like `4 ta maydon kerak, bor 1` ("4 fields needed, 1 found") |
| `id, err := strconv.ParseInt(parts[0], 10, 64)` | converts the ID text to an `int64` number (`10` is base ten, `64` is 64 bits); on an error it returns it with the prefix `ID: …` (`%w`, GB-2.08) |
| `name := parts[1]` and two checks | the name is not empty and is valid UTF-8 (`utf8.ValidString`, GB-2.10) |
| `price, err := parsePrice(parts[2])` | the price from som to tiyin: `12000` → `1200000` ([GB-1.07](/lab/youtube/gb/gb-1-07/en)) |
| `stock, err := strconv.Atoi(parts[3])` | the stock as an `int`; it must not be negative |
| `return Product{ID: id, …}, nil` | the finished `Product` (GB-2.03) |

Let us look at the real result of `strings.Split` (this program is not in the course folder; save it and run `go run main.go`):

```go

```

`%q` showed every field in quotes: so far all of it is text. The line `1;olma;12000;40` becomes `Product{ID: 1, Name: "olma", Price: 1200000, Stock: 40}`
(this is exactly what `videoCatalog` in `tekshiruv_test.go` expects).

## `loadCatalog(r io.Reader)`: one function

We move the Scanner loop into a function:

```go
func loadCatalog(r io.Reader) ([]Product, error) {
	var products []Product
	sc := bufio.NewScanner(r)
	for sc.Scan() {
		p, err := parseLine(sc.Text())
		if err != nil {
			return nil, err
		}
		products = append(products, p)
	}
	return products, sc.Err()
}
```

| Line | Code | What it does |
|---|---|---|
| 1 | `func loadCatalog(r io.Reader) ([]Product, error) {` | the parameter type is not `*os.File` but **`io.Reader`**: the Scanner needs only `Read`. The rule from [GB-2.07](/lab/youtube/gb/gb-2-07/en): ask in a parameter only for the method you need |
| 2 | `var products []Product` | an empty slice |
| 3 | `sc := bufio.NewScanner(r)` | the Scanner now reads from `r`: only `r.Read` is called |
| 4 | `for sc.Scan() {` | one turn for every line |
| 5–8 | `p, err := parseLine(sc.Text())` and `if err != nil { return nil, err }` | we turn the line into a `Product`; on an error we return `nil` and the error |
| 9 | `products = append(products, p)` | we add the result to the slice (GB-2.01) |
| 11 | `return products, sc.Err()` | at the end: the products and the Scanner's error (at end of file it is `nil`) |

In `run` we give `f` to `loadCatalog` and print the result with `writeReport` from [GB-2.07](/lab/youtube/gb/gb-2-07/en) to `os.Stdout` (`_video/04-load/main.go`, the file name is inside the code here):

```go
func run() error {
	f, err := os.Open("katalog.txt")
	if err != nil {
		return err
	}
	defer f.Close()
	products, err := loadCatalog(f)
	if err != nil {
		return err
	}
	return writeReport(os.Stdout, products)
}
```

oʻrik   35000 soʻm    5 dona
non      4000 soʻm  100 dona
choy    25000 soʻm    8 dona

Four products, the price in som. `writeReport` did not change: it gets `Price` in tiyin and divides by `tiyinPerSom` to print som.

## Standard input: a file, `os.Stdin` and the vertical bar

Now the file name does not live in the code but comes from the command line; if there is no argument, the program reads **standard input**. `run` from `main.go`:

```go
func run() error {
	var r io.Reader = os.Stdin
	if len(os.Args) > 1 {
		f, err := os.Open(os.Args[1])
		if err != nil {
			return err
		}
		defer f.Close()
		r = f
	}
	products, err := loadCatalog(r)
	if err != nil {
		return err
	}
	return writeReport(os.Stdout, products)
}
```

| Line | Code | What it does |
|---|---|---|
| 2 | `var r io.Reader = os.Stdin` | `r` is a variable of type `io.Reader`, at first holding `os.Stdin`. **Standard input** (stdin) is the input stream of the program; `os.Stdin` is also an `*os.File`, like `os.Stdout` ([GB-2.07](/lab/youtube/gb/gb-2-07/en)) |
| 3 | `if len(os.Args) > 1 {` | is there an argument on the command line? ([GB-1.07](/lab/youtube/gb/gb-1-07/en)) |
| 4 | `f, err := os.Open(os.Args[1])` | we open the file whose name is the first argument |
| 8 | `defer f.Close()` | even though it is written inside the `if`, it runs when `run` ends ([GB-2.09](/lab/youtube/gb/gb-2-09/en)), not when the `if` block ends |
| 9 | `r = f` | we put the file in `r`: the interface value ([GB-2.07](/lab/youtube/gb/gb-2-07/en)) now holds the `*os.File` |
| 11 | `products, err := loadCatalog(r)` | `loadCatalog` did not change: it does not know what is inside `r` |

What is inside `r`:

| Situation | Inside `r` |
|---|---|
| there is an argument (`go run . katalog.txt`) | the open file `*os.File` |
| no argument (`go run .`) | `os.Stdin` |

What does `go run .` do with no argument?

**A)** prints an empty report and ends at once · **B)** waits: the input is the terminal · **C)** an error: no file name

<details>
<summary>Answer</summary>

**B.** Standard input is the terminal itself: `Read` waits for the lines you type, and `Ctrl+D` at the start of a line says that the input is over
([termios(3)](https://man7.org/linux/man-pages/man3/termios.3.html)). I did not re-run this answer: the program is interactive, try it yourself.
If you chose **A**, you thought stdin is empty; **C** — the argument is optional: if it is there a file is opened, if not stdin stays.

</details>

We give the catalog to stdin with a **vertical bar** (pipe): `|` connects the output of the left command to the standard input of the right one
([Bash manual: Pipelines](https://www.gnu.org/software/bash/manual/html_node/Pipelines.html)). With a file name the result is the same:

```console

Both give the same four lines: `loadCatalog` does not know where the bytes came from.

## Accept a `Reader`, not a file name

Which call will not compile?

**A)** `loadCatalog(os.Stdin)` · **B)** `loadCatalog(f)` · **C)** `loadCatalog("katalog.txt")`

<details>
<summary>Answer</summary>

**C.** `os.Stdin` and `f` are `*os.File`, they have `Read`. But `"katalog.txt"` is a `string`, and it has no `Read` method. The real error (in `_video/08-string/main.go`, inside `run`,
`loadCatalog("katalog.txt")` is written instead of `loadCatalog(f)`):

```

How to read it: `./main.go:112:31` is the file, line and column (GB-1.01). `cannot use "katalog.txt" (constant of type string) as io.Reader value in argument to loadCatalog` means
"a string constant in quotes cannot be used as an `io.Reader` in the argument of `loadCatalog`". The reason: `string does not implement io.Reader (missing method Read)` means
"`string` does not implement `io.Reader`: the `Read` method is missing". The first line `# github.com/abdurahmon27/bozor` is the module name (it was shortened in the video).
If you chose **A** or **B**, both calls were fine.

</details>

A file name and a Reader are different things. If a function takes a `Reader`, then **where** to get the bytes from is decided by the caller: a file, stdin or text. That is why `loadCatalog`
knows nothing about whether there is a file, a terminal or a network.

In a test we do not need a file at all. A fragment from `tekshiruv_test.go` (shortened):

Such a test does not touch the disk: it is fast and gives the same result every time. At work, an HTTP request body is also an `io.Reader`: that is in [GB-4.06](/lab/youtube/gb#gb-4-06). Let us run

## Going deeper (optional): how many times does the Scanner call `Read`

This is not in the video, but it is in the README of the course folder (`07-count`). `logReader` is our own Reader that wraps another Reader and prints every `Read`.
It has a `Read` method, so it is an `io.Reader` too:

```go
// logReader boshqa Reader'ni oʻrab, har bir Read chaqiruvini chiqaradi.
type logReader struct {
	r io.Reader
}

func (l logReader) Read(p []byte) (int, error) {
	n, err := l.r.Read(p)
	fmt.Printf("Read: len(p)=%d n=%d err=%v\n", len(p), n, err)
	return n, err
}
```

In `run` one line changed: `loadCatalog(logReader{r: f})`. The Scanner gives `Read` its own 4096-byte buffer, so for a 63-byte file two calls are enough
(in our loop with a 20-byte buffer there were five):

```console
$ ./_video/run.sh 07-count go run . katalog.txt
Read: len(p)=4096 n=63 err=<nil>
Read: len(p)=4033 n=0 err=EOF
4 ta mahsulot
```

The first call brought the whole file (`n=63`), the second returned `EOF`: 4096 − 63 = 4033. The `Scan` table above is built on this measurement.

## Common mistakes

### 1. `sc.Err()` is not checked: data disappears silently

This is the most dangerous mistake, because it reports nothing. A variant seen in code review: after the loop, `nil` is returned instead of `sc.Err()`. It usually works, because at the end of a file
`Err` is `nil` anyway. `katta.txt` is also a catalog of four lines, but the export that wrote it is broken: a long description landed in the third line instead of the name. The fields:

```console
$ cut -c1-40 katta.txt
1;olma;12000;40
2;oʻrik;35000;5
3;non yangi uzilgan issiq non, yangi uzi
4;choy;25000;8
```

(`cut -c1-40` takes the first 40 characters of every line.) The longest line, with `wc -L`:

```console
$ wc -L katta.txt
70014 katta.txt
```

70,014 is longer than the Scanner limit (64 KiB = 65,536). The wrong variant (`_video/06-errsiz/main.go`):

```go
func loadCatalog(r io.Reader) ([]Product, error) {
	var products []Product
	sc := bufio.NewScanner(r)
	for sc.Scan() {
		p, err := parseLine(sc.Text())
		if err != nil {
			return nil, err
		}
		products = append(products, p)
	}
	return products, nil // XATO: sc.Err() tekshirilmadi
}
```

Look at the last line: `return products, nil` — `sc.Err()` is thrown away. What does `go run . katta.txt` print?

**A)** three products: the long line is skipped · **B)** two products, no error · **C)** an error: the line is too long

<details>
<summary>Answer</summary>

**B.** The third line is longer than the Scanner limit: `Scan` returned `false` and the loop ended silently. Our code did not look at `sc.Err()`, so the error was lost:

```console
$ ./_video/run.sh 06-errsiz go run . katta.txt
olma    12000 soʻm   40 dona
oʻrik   35000 soʻm    5 dona
```

Half of the catalog is lost, and the program ended successfully (exit code 0: the script prints it, I removed that line from the block). Nobody notices a mistake like this.
If you chose **A**, you thought the Scanner skips a long line: it stops. **C** — the error **exists**, but we did not read it.

</details>

The fix: return `return products, sc.Err()` at the end. The `main.go` in the folder does this, and the error is visible:

```console
$ go run . katta.txt
xato: bufio.Scanner: token too long
exit status 1
```

`xato:` is the prefix from `main`, `exit status 1` is the message of `go run`: the program ended with code 1. `bufio.Scanner: token too long` means "the line is too long for the Scanner" (in the Scanner documentation one line is called a **token**). Its
sentinel error is `bufio.ErrTooLong` (`go doc bufio.ErrTooLong`), and you check it as in [GB-2.08](/lab/youtube/gb/gb-2-08/en): `errors.Is(err, bufio.ErrTooLong)`. If a line
can really be that long, `sc.Buffer` raises the limit ([pkg.go.dev](https://pkg.go.dev/bufio#Scanner.Buffer)); I did not run it on this page.

### 2. A relative path: the file "does not exist"

`os.Open("katalog.txt")` is a **relative path**: the file is searched for not next to the program file but in the **current folder** of the process
([path_resolution(7)](https://man7.org/linux/man-pages/man7/path_resolution.7.html)). This is not in the video, it is an experiment from the README: `go build` makes a binary, then we run it from one folder up
(`bozor/` is the temporary folder that `run.sh` made; `cd ..` goes one folder up):

```console
$ ./_video/run.sh 01-open sh -c 'go build && cd .. && ./bozor/bozor'
(chiqish kodi: 1)
xato: open katalog.txt: no such file or directory
```

`open katalog.txt: no such file or directory` means "could not open `katalog.txt`: there is no such file or folder". The file is in place, but the program was started from another folder.
The fix: run the program from the folder that has the file, or pass the path to the file as an argument (`go run . katalog.txt`).

## Check yourself

1. `f.Read(buf)` returned `n` and `err`. Which do you use first?

<details>
<summary>Answer</summary>

First `n` bytes (`buf[:n]`), then `err`. A Reader may return data together with an error (the documentation: "Callers should always process the n > 0 bytes returned
before considering the error"), and the bytes must not be lost.

</details>

2. The loop `for sc.Scan() { … }` has ended. What do you check, and why?

<details>
<summary>Answer</summary>

`sc.Err()`. `Scan` returns `false` both on an error and at end of file; only `Err` tells them apart (at end of file it is `nil`). Without the check, in a case like `katta.txt` data disappears silently.

</details>

3. From [GB-2.08](/lab/youtube/gb/gb-2-08/en): how do you find out that an error wrapped with `%w` contains `ErrNotFound`?

<details>
<summary>Answer</summary>

`errors.Is(err, ErrNotFound)`. It looks through the whole chain of wrapped errors from start to end, while `err == ErrNotFound` compares only the outermost layer
([errors.Is](https://pkg.go.dev/errors#Is)).

</details>

4. What does this program print? (It is not in the course folder: save it as `main.go` in an empty folder.)

```go
package main

import (
	"bufio"
	"fmt"
	"strings"
)

func main() {
	sc := bufio.NewScanner(strings.NewReader("a\nb\r\n\nc"))
	for sc.Scan() {
		fmt.Printf("%q\n", sc.Text())
	}
	fmt.Println(sc.Err())
}
```

**A)** `"a"`, `"b"`, `"c"` and `<nil>` · **B)** `"a"`, `"b"`, `""`, `"c"` and `<nil>` · **C)** `"a"`, `"b\r"`, `""`, `"c"` and `<nil>`

<details>
<summary>Answer</summary>

**B.** `"a\nb\r\n\nc"` is four lines: `a`, `b` (the `\r\n` is removed too), an empty line and the last `c` with no `\n`. **A** — the Scanner does not skip empty lines (you do that
yourself in the homework). **C** — the `\r` is removed too. `Err()` is `nil`, and `fmt.Println` prints it as `<nil>`:

```console
$ go run main.go
"a"
"b"
""
"c"
<nil>
```

</details>

5. From [GB-2.09](/lab/youtube/gb/gb-2-09/en): `defer f.Close()` is written inside the block `if len(os.Args) > 1 { … }`. When does `Close` run?

<details>
<summary>Answer</summary>

When the function `run` ends, not when the `if` block ends: `defer` belongs to the function ([Go spec: Defer statements](https://go.dev/ref/spec#Defer_statements)). That is why after `r = f`
`loadCatalog` reads from a file that is still open.

</details>

Hint: `n := 0` before the loop, `n++` at the start of the loop; skip a comment with `continue` **after** `n++`, otherwise the numbers of the following lines shift. You will need `strings.TrimSpace`
and `strings.HasPrefix`.

<details>
<summary>Explanation of the answer (try it yourself first)</summary>

`loadCatalog` from `solution/main.go`:

```go
func loadCatalog(r io.Reader) ([]Product, error) {
	var products []Product
	sc := bufio.NewScanner(r)
	n := 0 // oʻqilgan qatorlar soni, izoh va boʻsh qatorlar ham
	for sc.Scan() {
		n++
		line := strings.TrimSpace(sc.Text())
		if line == "" || strings.HasPrefix(line, "#") {
			continue
		}
		p, err := parseLine(line)
		if err != nil {
			return nil, fmt.Errorf("%d-qator: %w", n, err)
		}
		products = append(products, p)
	}
	if err := sc.Err(); err != nil {
		// Scanner n-qatordan keyingisini oʻqiy olmadi.
		return nil, fmt.Errorf("%d-qator: %w", n+1, err)
	}
	return products, nil
}
```

- `n++` on every line, **before** `continue`: comments and empty lines count too, so the line number in the error matches the number in the file.
- `strings.TrimSpace` removes spaces at the start and at the end; `line == ""` is an empty line, `strings.HasPrefix(line, "#")` is a comment. In both cases `continue`.
- `fmt.Errorf("%d-qator: %w", n, err)`: `%w` keeps the original error inside, and `errors.As` and `errors.Is` will find it. With `%v` the text would be the same, but the chain would break: the test checks this.
- `sc.Err()` is now checked separately and wrapped with `n+1`: the Scanner could not read the line **after** the last line it read. In `katta.txt` two lines were read and the third is too long: `3-qator`.
