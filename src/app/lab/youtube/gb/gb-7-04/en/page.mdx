## What you will learn

The bozor importer updates catalog stock. It fetches stock counts for 1000 products every night. Sequential processing takes about 20 seconds. Starting a goroutine per product makes the lab supplier reject 990 requests. How can you speed up the import and limit concurrent requests?

**One idea:** input size should not determine the number of concurrent requests. A limit you choose and a cancellation signal control the import.

After this lesson, you can:

- measure unbounded work through request counts, goroutine counts, and memory;
- write ten workers reading one channel;
- combine a concurrency limit and the first error with `errgroup`;
- cancel remaining work through the group context and fix context use after `Wait`.

| Term | Plain meaning | English term |
|---|---|---|
| worker pool | persistent goroutines take jobs from one channel | worker pool |
| `errgroup.Group` | waits for functions and returns the first error | errgroup |
| `errgroup.WithContext` | cancels the group context on error or when `Wait` returns | WithContext |

**Bounded concurrency** means at most N tasks are in progress, including tasks waiting for responses. `SetLimit` sets that bound. The helper syntax `errs...` expands slice elements into separate arguments. `golang.org/x/sync` is a Go module outside the standard library.

## Sequential import: the baseline

The supplier is a fake with no network: `supplier.go`. `checkStock(ctx, id)` returns one stock count. ID 1 is `olma` (apple), 40; ID 2 is `non` (bread), 120; ID 3 is `oʻrik` (apricot), 5. Other existing IDs have stock `id % 50`. Only IDs 1…1000 exist.

Each request waits about 20 ms. When more than 10 requests overlap, excess requests receive `ErrTooMany`: `429 too many requests`. This lab limits concurrent work; a rate limit counts requests over time instead. No actual HTTP response is sent. `catalogIDs(n)` builds a slice of IDs 1…n; `saveStocks` only checks its context. Writing to Postgres comes in GB-7.07.

```go filename="_video/01-ketma/main.go" showLineNumbers
package main

import (
	"context"
	"fmt"
	"time"
)

func importStocks(ctx context.Context, ids []int64) ([]int, error) {
	stocks := make([]int, len(ids))
	for i, id := range ids {
		n, err := checkStock(ctx, id)
		if err != nil {
			return nil, fmt.Errorf("mahsulot %d: %w", id, err)
		}
		stocks[i] = n
	}
	return stocks, nil
}

	start := time.Now()

	report(stocks, err, start)
}
```

## A goroutine per ID: no bound

```go filename="_video/02-cheksiz/main.go" showLineNumbers
package main

import (
	"context"
	"errors"
	"sync"
	"time"
)

func importStocks(ctx context.Context, ids []int64) ([]int, error) {
	stocks := make([]int, len(ids))
	errs := make([]error, len(ids))
	var wg sync.WaitGroup
	for i, id := range ids {
		wg.Go(func() {
			stocks[i], errs[i] = checkStock(ctx, id)
		})
	}
	wg.Wait()
	return stocks, errors.Join(errs...)
}

func main() {
	start := time.Now()
	stocks, err := importStocks(context.Background(), catalogIDs(1000))
	report(stocks, err, start)
}
```

Lines 11–12 create separate slices for stock counts and errors. Line 13 creates a `WaitGroup`; 14–18 start `wg.Go` for each ID. Line 16 writes only to its own index `i`. There is no `append`. Line 19 waits for all tasks; 20 joins non-nil errors through `errors.Join(errs...)`. New imports are `errors` and `sync`; `main` is unchanged.

**Predict:** 1000 goroutines; the supplier accepts at most 10 overlapping requests. What do we expect in this rapidly launched experiment? **A)** 0 rejected, an automatic queue · **B)** 12 rejected, matching the CPU count · **C)** 990 rejected.

**C**, in this experiment. `go` does not wait for the called work to finish. CPU count does not bound requests waiting for responses. The language does not guarantee that every goroutine runs immediately together; 990 is this run’s result.

## One jobs channel, ten workers

Build a **worker pool**. `main` sends job indexes; ten persistent goroutines receive them.

| State | main / jobs | Workers and requests |
|---|---|---|
| start | unbuffered `jobs`, no jobs | 10 workers wait to receive |
| 10 busy | next `jobs <- i` waits | at most 10 requests |
| one finishes | a free worker receives the index | it starts the next request |
| sending ends | `close(jobs)`, then `wg.Wait()` | range ends, all workers are awaited |

```go filename="_video/04-worker/main.go" showLineNumbers
package main

import (
	"context"
	"errors"
	"sync"
	"time"
)

const workers = 10

func importStocks(ctx context.Context, ids []int64) ([]int, error) {
	stocks := make([]int, len(ids))
	errs := make([]error, len(ids))
	jobs := make(chan int)
	var wg sync.WaitGroup
	for range workers {
		wg.Go(func() {
			for i := range jobs {
				stocks[i], errs[i] = checkStock(ctx, ids[i])
			}
		})
	}
	for i := range ids {
		jobs <- i
	}
	close(jobs)
	wg.Wait()
	return stocks, errors.Join(errs...)
}

func main() {
	start := time.Now()
	stocks, err := importStocks(context.Background(), catalogIDs(1000))
	report(stocks, err, start)
}
```

Line 10 sets `workers = 10`. Line 15 creates an unbuffered `chan int`: it carries indexes rather than IDs. Lines 17–23 start ten `wg.Go` calls. Lines 19–21 receive indexes until the channel closes and write only to the corresponding result cell.

Lines 24–26 send each index through `jobs <- i`. Without a free worker, the sender waits. Line 27 closes the channel; `for i := range jobs` ends. Line 28 waits for all workers. Line 29 joins errors.

**Predict:** 1000 products, 10 workers, 20 ms per request. Approximate time? **A)** 20 ms · **B)** 2 s · **C)** 20 s.

<details>
<summary>Answer</summary>

**B.** 1000 / 10 × 20 ms = 2 s. A covers one batch of ten; C is sequential. Scheduling and other overhead add to the ideal calculation.

</details>

## errgroup: a limit and the first error

We managed a channel, a worker loop, and an error slice manually. **errgroup** combines waiting for functions with error return. It is a package in `golang.org/x/sync`.

The lesson folder already has this dependency. The following command was rerun in a separate temporary module without that dependency:

```console
$ go get golang.org/x/sync/errgroup
go: added golang.org/x/sync v0.25.0
```

`go: added` means the module was added to `go.mod`; `go.sum` stores checksums. The video also showed `go: downloading`; this run used the module cache, so that line is absent.

```go filename="_video/05-errgroup/main.go" showLineNumbers
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

const workers = 10

func importStocks(ctx context.Context, ids []int64) ([]int, error) {
	stocks := make([]int, len(ids))
	var g errgroup.Group
	g.SetLimit(workers)
	for i, id := range ids {
		g.Go(func() error {
			n, err := checkStock(ctx, id)
			if err != nil {
				return fmt.Errorf("mahsulot %d: %w", id, err)
			}
			stocks[i] = n
			return nil
		})
	}
	if err := g.Wait(); err != nil {
		return nil, err
	}
	return stocks, nil
}

func main() {
	start := time.Now()
	stocks, err := importStocks(context.Background(), catalogIDs(1000))
	report(stocks, err, start)
}
```

Line 8 imports the package. Line 15 creates a zero-value `Group`: ready to use, but with no limit or error cancellation by itself. Line 16 bounds active work using `SetLimit(workers)`.

Line 18 passes `func() error` to `g.Go`. When the limit is full, the caller of `g.Go` waits. These are not ten persistent workers: a goroutine starts for each task, with a bound on active tasks. Lines 19–25 fetch stock, wrap an error with the ID, or write `stocks[i]` and return `nil`.

Lines 27–29 wait for every started function and return the first non-nil error. “First” means the first recorded error, rather than the first ID in input order. Line 30 returns only a successful result.

| State | Caller of `g.Go` | Result |
|---|---|---|
| 0 active | starts the first task | 1 active |
| 10 active | waits to add task 11 | bound holds |
| one finishes | a slot opens and the next task starts | at most 10 active |
| loop ends | `g.Wait()` | all finish, first error or `nil` |

**Predict:** what happens with 1000 valid IDs? **A)** 990 rejections again · **B)** about 2 s, at most 10 active · **C)** only 10 results.

<details>
<summary>Answer</summary>

**B.** `SetLimit` bounds concurrent work rather than total tasks. A ignores the limit; C mistakes it for the total result count.

</details>

Active work is bounded, but the `ids` and `stocks` slices still use memory proportional to list length. This does not promise constant memory for the entire import.

## WithContext: work after an error

First check a plain `Group`. `_video/06-xato/main.go` differs from the previous file only in `main`:

`ids[499]` is element 500; the supplier has no ID 9999. **Predict:** how many total requests? **A)** 1000 · **B)** about 510 · **C)** 500.

```go filename="_video/07-withctx/main.go" showLineNumbers
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

const workers = 10

func importStocks(ctx context.Context, ids []int64) ([]int, error) {
	stocks := make([]int, len(ids))
	g, ctx := errgroup.WithContext(ctx)
	g.SetLimit(workers)
	for i, id := range ids {
		g.Go(func() error {
			n, err := checkStock(ctx, id)
			if err != nil {
				return fmt.Errorf("mahsulot %d: %w", id, err)
			}
			stocks[i] = n
			return nil
		})
	}
	if err := g.Wait(); err != nil {
		return nil, err
	}
	return stocks, nil
}

func main() {
	start := time.Now()
	ids := catalogIDs(1000)
	ids[499] = 9999
	stocks, err := importStocks(context.Background(), ids)
	report(stocks, err, start)
}
```

Line 15 is `g, ctx := errgroup.WithContext(ctx)`. In this function body, `ctx` shares the parameter’s block. `:=` creates only `g` and assigns a new context to the existing `ctx`. Line 19 now passes the group context. The first non-nil error cancels it.

The supplier responds in two places: it checks `ctx.Err()` on entry and watches `ctx.Done()` through `select` while waiting. Cancellation does not forcibly kill a goroutine. If both `select` cases are ready, choosing the cancellation case is not guaranteed.

**Mid-lesson question:** the error for product 9999 triggered cancellation; other functions returned `context canceled`. What does `Wait` return? **A)** the first error about 9999 · **B)** `context canceled` · **C)** every error through `errors.Join`.

<details>
<summary>Answer</summary>

**A.** The group keeps the first error. Later cancellation errors neither replace it nor join it. Before returning, `Wait` waits for all started functions.

</details>

The loop still calls every `g.Go`. A `checkStock` started after cancellation usually returns at its entry check without increasing the supplier counter. Calls already running react to the signal. A `g.Go` blocked on the limit does not itself return automatically on context cancellation; it waits for a slot.

| Event | Group context | Work |
|---|---|---|
| before error | active | at most 10 requests |
| first error | canceled | running calls observe the signal |
| remaining loop | canceled | new functions are called; entry checks return quickly |
| `Wait` | canceled | after every function finishes, first error |

## Which context after Wait?

Now there is no invalid ID. After importing, save the stock counts through `saveStocks`. `g, ctx :=` replaced the parameter’s context. The added part of `_video/08-wait-ctx/main.go` is:

```go
	if err := g.Wait(); err != nil {
		return nil, err
	}
	if err := saveStocks(ctx, stocks); err != nil {
		return nil, err
	}
	return stocks, nil
```

Rule: the context from `WithContext` is canceled on the first error **or when `Wait` returns**. Successful completion also cancels it.

**B.** `Wait` succeeded, but the next `saveStocks` received the canceled group context. A assumes a longer context lifetime; C has no invalid ID to explain it.

</details>

```go filename="_video/09-gctx/main.go" showLineNumbers
package main

import (
	"context"
	"fmt"
	"time"

	"golang.org/x/sync/errgroup"
)

const workers = 10

func importStocks(ctx context.Context, ids []int64) ([]int, error) {
	stocks := make([]int, len(ids))
	g, gctx := errgroup.WithContext(ctx)
	g.SetLimit(workers)
	for i, id := range ids {
		g.Go(func() error {
			n, err := checkStock(gctx, id)
			if err != nil {
				return fmt.Errorf("mahsulot %d: %w", id, err)
			}
			stocks[i] = n
			return nil
		})
	}
	if err := g.Wait(); err != nil {
		return nil, err
	}
	if err := saveStocks(ctx, stocks); err != nil {
		return nil, err
	}
	return stocks, nil
}

func main() {
	start := time.Now()
	stocks, err := importStocks(context.Background(), catalogIDs(1000))
	report(stocks, err, start)
}
```

Line 15 now creates new `g` and `gctx`, preserving the parameter `ctx`. Line 19 uses `checkStock(gctx, id)`; lines 30–32 use `saveStocks(ctx, stocks)`. The outer context’s own deadline or cancellation still applies.

## Going deeper (optional): the channel behind the limit

In the v0.25.0 source, `SetLimit(n)` creates a buffered channel with capacity n. `g.Go` sends to reserve a slot; receiving when a function finishes releases it. This is a version-specific detail; the API promises a bound on active work.

`SetLimit(0)` prevents adding new goroutines. Unless the limit changes, the next `g.Go` remains blocked. If no goroutine can make progress, the runtime may terminate with deadlock. In a server with other work or timers, one blocked call does not guarantee that report. A negative limit removes the bound. Do not change the limit while tasks are active.

`errgroup` does not recover panics. An unrecovered panic terminates the whole program; `Wait` does not convert it into an ordinary `error`.

## Common mistakes

1. **Expecting a plain Group to stop everything on error.** Stage 06 still sent 1000 requests. Use `WithContext`, pass its context into work, and have that work check the signal.
2. **Using the group context after `Wait`.** Stage 08’s `saveStocks(ctx, stocks)` produced the real error `saqlash: context canceled`. Stage 09 separates `gctx` and passes the outer `ctx` to saving.
3. **Calling `append` on a shared slice from every goroutine.** This breaks the separate-index rule. Allocate the result length first, write only `stocks[i]`, and call `Wait` before reading.
4. **Skipping limit validation.** Zero prevents new work; negative values remove the bound. In the task, return `errBadLimit` for `limit < 1` before calling `SetLimit`.
5. **Reading exit code 0 as a successful import.** The lab’s `main` prints errors without calling `os.Exit(1)`. Also read the result line containing `xato` (“error”).

**1.** Why does one goroutine per product create an unbounded import?

<summary>Answer</summary>

Task starts depend on list length. Waiting may not occupy a CPU, but active requests and goroutines still require resources. The code should set the limit.

**2.** What is needed to cancel remaining work on the first error?

<details>
<summary>Answer</summary>

`WithContext(ctx)`, `gctx` inside `g.Go`, and signal checks inside `checkStock`. `SetLimit` bounds concurrent work; it does not itself cancel anything.

</details>

**3. Predict:** `g.SetLimit(2)` and five valid IDs. What is the result length? **A)** 2 · **B)** 5 · **C)** depends on completion order.

<details>
<summary>Answer</summary>

**B.** The bound applies to active tasks. All five IDs are processed, and results are written in `ids` order.

</details>

**4. GB-7.01:** what happens to running goroutines when `main` returns?

<details>
<summary>Answer</summary>

The program exits without waiting for other goroutines. The work’s owner therefore waits using `wg.Wait()` or `g.Wait()`.

</details>

```go
func fetchPrices(ctx context.Context, ids []int64, limit int) ([]int64, error) {
	if limit < 1 {
		return nil, errBadLimit
	}
	prices := make([]int64, len(ids))
	g, gctx := errgroup.WithContext(ctx)
	g.SetLimit(limit)
	for i, id := range ids {
		g.Go(func() error {
			p, err := checkPrice(gctx, id)
			if err != nil {
				return fmt.Errorf("narx %d: %w", id, err)
			}
			prices[i] = p
			return nil
		})
	}
	if err := g.Wait(); err != nil {
		return nil, err
	}
	return prices, nil
}
```

The first three lines reject invalid limits. Then come the result slice, `g` and `gctx`, the limit, and a task per ID. Only `prices[i]` is written. Errors are wrapped with `narx %d: %w`; after `Wait`, return `nil` on error or the complete slice.
