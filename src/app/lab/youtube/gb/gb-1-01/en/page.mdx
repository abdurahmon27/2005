## What you will learn

When you put the bozor backend on a server, what exactly do you copy there: the code, Go itself, or something else?
On this page we start from an empty folder and answer that question in the terminal itself.

**Bozor** ("bazaar") is the backend that grows through the whole course, that is, a program that runs on a server: a
small marketplace that manages products, stock and orders. Today it prints one line. By the end of the course it will
be an API running on a server.

**The one idea:** the source text (`main.go` and `go.mod`) becomes one file through `go build`. The operating system
runs that file directly: it needs neither Go nor `main.go`. But it was built from the code as it was at the last
`go build`.

By the end of the lesson you will:

- create a module in an empty folder with `go mod init` and explain both lines of `go.mod`;
- read every line and every symbol of `main.go`: `package main`, `import "fmt"`, `func main() { … }`,
  `fmt.Println(…)`;
- know the difference between `go run .` and `go build` and avoid the stale binary trap;
- find a compiler error by `file:line:column` and bring code to the standard format with `go fmt ./...`.

Today's three core new words:

| Word | Plain meaning | Term |
|---|---|---|
| module | code that is versioned together under one name; the name and the Go version are in the `go.mod` file | module |
| entry point | where the program starts: the `main` function in the `main` package | entry point (`package main` + `func main`) |
| binary | the executable file `go build` made: machine code, with the Go runtime inside | binary (executable) |

There are also two helper commands: `go run .` (compiles and runs at once) and `go fmt ./...` (brings code to the
standard format).

**A)** none · **B)** the shell looks for `bozor` in the PATH folders, while `./bozor` runs the file in the current

<summary>Answer</summary>

```console

```

| Part | Meaning |
|---|---|
| `go1.26` | major release: Go 1.26 |
| `.8` | the eighth minor release: bugs fixed, the language did not change |
| `linux` | the operating system of this computer |
| `amd64` | the processor architecture: 64-bit Intel or AMD |

You may have a newer version (according to the course README, the newest in November 2026 is `go1.27.4`). Everything

## Module: `go mod init` and `go.mod`

A project needs a name and a Go version. In Go a project is a **module**: code that is versioned together under one
name.

First we create an empty `bozor` folder and enter it. `mkdir` creates the folder, `cd` enters it. Two ampersands
(`&&`) run the second command only if the first one succeeded.

```console
$ mkdir bozor && cd bozor
$ go mod init github.com/abdurahmon27/bozor
go: creating new go.mod: module github.com/abdurahmon27/bozor
```

`mkdir … && cd …` printed nothing. `go mod init` starts a new module. The text at the end is the **module path**,
that is, the full name of the module. Usually it is the address where the code lives: `github.com`, the user name and
the project name. Write your own GitHub name instead of `abdurahmon27`; the address does not have to exist yet.

Go printed one line: "creating new go.mod: module github.com/abdurahmon27/bozor". In the video this long path is
shortened to `…/bozor` on screen; here it is in full.

We look inside the file (`cat` prints a file to the terminal):

```console
$ cat go.mod
module github.com/abdurahmon27/bozor

go 1.26.8
```

| Line | Entry | What it does |
|---|---|---|
| 1 | `module github.com/abdurahmon27/bozor` | the module path: other code refers to this module by this name |
| 2 | (empty) | separates the two entries |
| 3 | `go 1.26.8` | the `go` line: the minimum Go version this module needs (so since Go 1.21) |

The file has two entries. The first word of each (`module`, `go`) is a **directive**: it says what the line is about.
`go mod init` writes the installed version into the `go` line, so your number may differ.

One detail. The Go 1.26 release notes say `go mod init` writes `go 1.25.0`. That is true only for go1.26.0: from
go1.26.1 on it writes the installed version again (source: `cmd/go/internal/modload/init.go`). That is why we have
`go 1.26.8`.

The `go.mod` in the course folder requires `go 1.26.8`. If your Go is older, the README describes two cases (not
re-run here, it needs an old Go): with the default setting (`GOTOOLCHAIN=auto`) Go downloads the needed version
itself; with Go from a Debian/Ubuntu package (`GOTOOLCHAIN=local`) you get the error `go.mod requires go >= 1.26.8`.
The fix: update Go, or run `go mod init` in your own folder.

## `main.go` line by line

Now we create the file `main.go` in this folder. Here is the whole program, 7 lines:

```go filename="main.go" showLineNumbers
package main

import "fmt"

func main() {
	fmt.Println("bozor ishga tushdi")
}
```

| Line | Code | What it does |
|---|---|---|
| 1 | `package main` | the file belongs to the `main` package: the compiler makes a runnable program from it |
| 2 | (empty) | a separator; `go fmt` puts it there (below) |
| 3 | `import "fmt"` | connects the `fmt` package from the standard library to this file |
| 4 | (empty) | a separator |
| 5 | `func main() {` | declares the `main` function and opens its body: the program starts here |
| 6 | `fmt.Println("bozor ishga tushdi")` | calls `Println` from the `fmt` package: writes the text to the terminal |
| 7 | `}` | the function body ends; when `main` ends, the program ends too |

The string `"bozor ishga tushdi"` is Uzbek for "bozor has started". Now each line in detail.

### Line 1: `package main`

Every Go file starts with the word `package` and says which **package** it belongs to. A package is the `.go` files
of one folder that are compiled together. The name `main` is special: from the `main` package the compiler makes a
runnable program. A package with any other name becomes a library: other packages use it, it does not run by itself.

### Line 3: `import "fmt"`

`import` connects another package to this file. `fmt` is a package from the **standard library**, its name comes from
the word "format": it formats and prints text. The standard library comes with Go, you need no download and no
internet for it.

The package path is written in quotes: quotes delimit a text value, that is, a **string**. `"fmt"` is the
three-letter string `fmt`, the path of the package.

### Lines 5 and 7: `func main() { … }`

- `func` declares a function, `main` is its name.
- The empty parentheses `()` mean the function takes no values.
- The curly braces `{` and `}` surround the function body. The opening `{` must be on this same line; if you move it
  to the next line, the compiler reports an error (the real message is in "Common mistakes").

The `main` function in the `main` package is the program's **entry point**. Go calls it itself. The lines of the body
run from top to bottom. When the function ends, the program ends too.

### Line 6: `fmt.Println("bozor ishga tushdi")`

This line is the whole work of the program.

- `fmt.Println`: the dot refers to a name inside the `fmt` package. `fmt.Println` = "`Println` from the `fmt`
  package".
- `( … )`: the parentheses **call** the function. The value inside is an **argument**; here, one string.
- `Println` writes its argument to **standard output**, that is, to the terminal, and adds a newline character at
  the end. The name comes from "print line".
- The capital `P` means the name is visible outside the package. We cover this rule in the course's lesson on packages
  ([GB-2.06](/lab/youtube/gb#gb-2-06)). For now it is enough to know: you cannot write `fmt.println` with a lowercase letter.
- The indentation at the start of the line is one Tab character. You don't need to fix it by hand: `go fmt` puts it
  there.

### What happens when the program runs

| Step | What happens | On screen |
|---|---|---|
| 1 | the operating system starts the program, the Go runtime gets ready | — |
| 2 | Go calls the `main` function of the `main` package (line 5) | — |
| 3 | line 6: `Println` writes `bozor ishga tushdi` and a newline character to standard output | `bozor ishga tushdi` |
| 4 | line 7: `main` ended, the program exits | — |

## `go run .`: compile and run at once

We run the program: we type `go run .`. The dot (`.`) is the package in the current folder. This command compiles
the package and runs the result at once.

How many files are in the folder after the command?

**A)** 2: `go.mod`, `main.go` · **B)** 3: a compiled `bozor` file is added · **C)** 3: a file named `main` appears

<details>
<summary>Answer</summary>

**A: two.** `go run` writes the compiled result not to the project folder but to Go's **build cache** folder and runs
it from there (since Go 1.24 the result also stays there). On Linux this folder is `~/.cache/go-build`; `go env
GOCACHE` tells you yours. If you chose "B", you mixed up `go run` and `go build`: `go build` writes the file into the
folder (next section). "C" has the same mistake, plus the wrong name.

</details>

```console
$ go run .
bozor ishga tushdi
$ ls
go.mod  main.go
```

On screen is the line the program wrote, without quotes: the quotes were only the text boundary in the code. `ls`
showed only `go.mod` and `main.go` in the folder.

You always give `go run` a package, here with the dot. `go run main.go` works too, but it takes only that one file:
once the package has more files, you need `go run .`.

## `go build`: one executable file

`go run` compiles again every time and leaves no result in the folder. `go build` writes the result into the folder
as a file. If no package is given, it builds the package of the current folder.

```console
$ go build
$ ls
bozor  go.mod  main.go
```

A successful `go build` is silent: it printed nothing. `ls` now shows three files. The new file is a **binary**, named
`bozor`. The name comes not from the folder but from the last part of the module path
(`github.com/abdurahmon27/bozor` → `bozor`). On Windows it is `bozor.exe`.

We look at the file in detail and run it:

```console
$ ls -lh bozor
-rwxr-xr-x 1 haywan users 2.3M Nov 27 00:07 bozor
$ ./bozor
bozor ishga tushdi
```

`ls -l` gives a detailed list, `h` writes the size in readable units:

| Column | Value | Meaning |
|---|---|---|
| permissions | `-rwxr-xr-x` | the first `-` = a regular file; the `x` letters mean the file can be run |
| link count | `1` | how many names the file has |
| owner | `haywan` | the user who created the file |
| group | `users` | the owner's group |
| size | `2.3M` | 2.3 MiB (exactly: 2 410 014 bytes) |
| time | `Nov 27 00:07` | the time of the last change |
| name | `bozor` | the file name |

In the video the line shows the time `Nov 26 23:27`; the other columns are the same. Your owner, group and time will
differ. The exact byte count can also differ by a few bytes (the build for the video had 2 410 070 bytes), while
`2.3M` stays the same.

`./bozor` ran it from the current folder: the same line. Why the size is 2.3 MiB, we see in the next section.

## In an environment without Go: `env -i`

Now we copy the `bozor` file to another folder and run it in an empty environment without PATH. There is no `main.go`
next to it, and the terminal cannot find Go. What happens?

**A)** `bozor ishga tushdi` is printed · **B)** error: go not found · **C)** error: no main.go

<details>
<summary>Answer</summary>

**A: the program works.** `bozor` is ready machine code; running it needs neither Go nor `main.go`. If you chose
"B", you thought a Go program needs Go installed to run: Go is needed only to **build**. If you chose "C", you thought
the binary reads `main.go` every time: it does not read the text, the text became machine code during the build.

</details>

```console
$ env -i go version
env: ‘go’: No such file or directory
$ cp bozor /tmp/ && env -i /tmp/bozor
bozor ishga tushdi
```

`env -i` runs the command after it in an empty environment, without PATH. In the first command `env` did not find
`go`: "no such file or directory" (exit code 127). In the second, `cp` copied the file to the `/tmp` folder, and `env`
ran it there: no `main.go` next to it, no PATH, and `bozor` still worked.

One exception (from the README): with no PATH, `env` searches `/bin` and `/usr/bin`. If Go was installed into
`/usr/bin` with `apt install golang-go`, `env -i go version` works. That does not change the fact that `bozor` does
not need Go.

### Why it worked: what is inside `go build`

`go build` puts our code, the `fmt` package and the Go **runtime** into one file. The runtime is code added to every
Go program that manages memory and the work of the program.

```text
main.go + go.mod       our text
      │
      ▼
   go build            compiling + linking
      │
      ▼
    bozor              our code + fmt + runtime
      │                machine code: needs neither Go nor main.go
      ▼
  linux/amd64          this system runs it directly
```

Most of the file is the runtime. Let's measure it: we build a program with an empty `func main() {}`. This example is
not in the course folder; its complete code:

```go
package main

func main() {}
```

```console
$ mkdir bosh && cd bosh
$ go mod init github.com/abdurahmon27/bosh
go: creating new go.mod: module github.com/abdurahmon27/bosh
$ go build
$ stat -c %s bosh
1830036
```

`stat -c %s` prints the size of a file in bytes (`bosh` is Uzbek for "empty"). A program that does nothing is
1 830 036 bytes, and `bozor` is 2 410 014 bytes: 76 % of `bozor` was there before `fmt` was added (the runtime and the
program start-up code). The course research measured 1 830 044 and 2 410 070 bytes on the same Go: the ratio is 76 %
again.

The file is not linked to other system libraries either. `ldd` shows which system libraries a program requires:

```console
$ ldd ./bozor
	not a dynamic executable
```

"not a dynamic executable": `bozor` loads no system library at all. That is why this one file is what you copy to the
server. There is one condition: the server must also be `linux/amd64`. Building for another system comes in the
course's section on deploying to a server.

## Stale binary

Now we change the text on line 6 to `bozor yangilandi` ("bozor has been updated") and save the file:

```go
package main

import "fmt"

func main() {
	fmt.Println("bozor yangilandi")
}
```

```console
$ go run .
bozor yangilandi
```

`go run .` printed the new text: it compiles from the current code every time. But we did not run `go build`.

What does `./bozor` print now?

**A)** `bozor yangilandi` · **B)** `bozor ishga tushdi` · **C)** error: the file is stale

<details>
<summary>Answer</summary>

**B: the old text.** `go run` does not write its result into the folder. The `bozor` file was built from the code as
it was at the last `go build`. If you chose "A", you thought `go run` also updates the `bozor` file. If "C", you
thought the binary knows that `main.go` changed: it never sees `main.go`, and nobody warns you.

</details>

```console
$ ./bozor
bozor ishga tushdi
$ go build && ./bozor
bozor yangilandi
```

| Step | Text in `main.go` | Text inside the `bozor` file | On screen |
|---|---|---|---|
| first `go build` | `bozor ishga tushdi` | `bozor ishga tushdi` | — |
| text changed, `go run .` | `bozor yangilandi` | `bozor ishga tushdi` | `bozor yangilandi` |
| `./bozor` | `bozor yangilandi` | `bozor ishga tushdi` | `bozor ishga tushdi` |
| `go build && ./bozor` | `bozor yangilandi` | `bozor yangilandi` | `bozor yangilandi` |

To update it you need `go build` again. An old file left on a server is a real bug. That is why programs usually
print their version when they start: in the homework you add this to bozor.

Before the next section, put the text back (`bozor ishga tushdi`).

## Reading a compiler error: `file:line:column`

Now we practise reading compiler messages. Make each mistake in `main.go` temporarily, then undo it.

### An unclosed quote

We delete the closing quote on line 6:

```go
package main

import "fmt"

func main() {
	fmt.Println("bozor ishga tushdi)
}
```

One quote character is missing. What does `go run .` say?

**A)** the program runs, treating everything to the end of the line as text · **B)** one error: the string is not
closed · **C)** two errors: both the string and the parenthesis

<details>
<summary>Answer</summary>

**C: two lines of errors.** The first one: the string is not closed. The text ran to the end of the line and
swallowed the closing `)`, so the compiler also sees an unclosed parenthesis. If you chose "A": in Go an ordinary
quoted string cannot go past one line. "B" misses the second error, which is a consequence of the first.

</details>

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:6:34: newline in string
./main.go:6:34: syntax error: unexpected newline in argument list; possibly missing comma or )
```

The first line `# github.com/abdurahmon27/bozor` says which package is being compiled (the video hides this line).
Each of the next two lines starts with `file:line:column`:

| Part | Value | Meaning |
|---|---|---|
| file | `./main.go` | `main.go` in the current folder |
| line | `6` | line 6 |
| column | `34` | byte 34 of the line, counting from 1 |

The **column** is the byte position in the line. On this line every character, the Tab too, is one byte:

| Piece | Bytes | Total |
|---|---|---|
| Tab | 1 | 1 |
| `fmt.Println(` | 12 | 13 |
| `"` | 1 | 14 |
| `bozor ishga tushdi)` | 19 | 33 |
| end of line (newline character) | — | **34** |

Byte 34 is the end of the line: the compiler saw a newline character inside an open string.

- `newline in string`: the line ended before the string was closed.
- `syntax error: unexpected newline in argument list; possibly missing comma or )` is a **syntax error**: the list of
  arguments ended unexpectedly, probably a comma or a `)` is missing. It is a consequence of the first one.

The rule: **fix the first error**. Often the rest go away by themselves. Here, putting the closing `"` back removes
both messages.

### An unused import

We put the quote back. Now we add `import "os"` as line 4. `os` is the standard package for working with the
operating system, but we call nothing from it:

```go
package main

import "fmt"
import "os"

func main() {
	fmt.Println("bozor ishga tushdi")
}
```

What does `go run .` do?

**A)** the program runs and says nothing · **B)** the program runs, but a warning appears · **C)** the program does
not compile at all

<details>
<summary>Answer</summary>

**C.** In Go an unused import is not a warning but an error: the program is not built, and `bozor ishga tushdi` is not
printed either. If you chose "B", you expected a compiler with warnings: the Go compiler has no warnings, only errors.

</details>

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:4:8: "os" imported and not used
```

The location: line 4, column 8. `import ` (with the space) is 7 bytes, byte 8 is where the quoted `"os"` starts.
`imported and not used` means what it says. The fix: delete that line.

Go's official FAQ gives the reason: an unneeded import slows compilation down, and as code grows this becomes
noticeable. That is why Go treats it as an error.

Two notes (from the README). Usually imports are written as one group: `import (` … `"fmt"` … `"os"` … `)`; we will
see this form in later lessons. The Go extension for VS Code removes an unused import by itself when you save the
file: to see this error, save the file with "Save without Formatting".

## `go fmt ./...`: one standard format

The last tool. We wrote `main.go` messily and saved it:

```go
package main
import "fmt"
func main(){
fmt.Println("bozor ishga tushdi")
}
```

This code works, but it has no empty lines, no indentation and no space between `)` and `{`. In Go, how code looks is
fixed by one standard. A program called **gofmt** applies it, and `go fmt` runs it on packages.

```console
$ go fmt ./...
main.go
$ go fmt ./...
```

`./...` means the current folder and the packages in all folders inside it. `go fmt` brings each file to the gofmt
format and prints the names of the files it changed: the first time, `main.go`. The second time it printed nothing:
nothing was left to change.

The file is back to 7 lines:

```go filename="main.go" showLineNumbers
package main

import "fmt"

func main() {
	fmt.Println("bozor ishga tushdi")
}
```

Empty lines at lines 2 and 4, indentation with one Tab on line 6, a space in `main() {` on line 5. All Go code looks
the same, so in code review you discuss the meaning, not the format. Many editors run gofmt by themselves when you
save a file.

## Going deeper (optional): a column is a byte, not a character

The column in an error message is counted in bytes. On the line above every character was one byte, so you could not
see the difference. With an Uzbek letter you can: `ʻ` (U+02BB) is two bytes in UTF-8. This example is not in the
course folder; line 6 has the unclosed text `"oʻrik` ("apricot"):

```go
package main

import "fmt"

func main() {
	fmt.Println("oʻrik)
}
```

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:6:22: newline in string
./main.go:6:22: syntax error: unexpected newline in argument list; possibly missing comma or )
```

Line 6 has 20 characters but 21 bytes (`ʻ` is two bytes). The compiler showed column 22: the end of the line is byte
22. Counting characters would give 21. On lines with Uzbek text the column number can be larger than the number of
characters: the error is still at the reported place, the count is just in bytes.

## Common mistakes

### 1. "`go run .` updates the binary too"

The most common wrong idea in this topic. `go run .` writes its result to the build cache and does not change the
`bozor` file in the folder. There is no error message: the old file quietly keeps running and gives the old result.
The real output is in the "Stale binary" section. The fix: run `go build` again before you copy or run the file, and
let the program print its version at start (the homework).

### 2. The opening `{` on the next line

```go
package main

import "fmt"

func main()
{
	fmt.Println("bozor ishga tushdi")
}
```

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:6:1: syntax error: unexpected semicolon or newline before {
```

Reading it: `main.go`, line 6, column 1, the lonely `{`. The message: an unexpected semicolon or newline before `{`.
The Go compiler puts an invisible semicolon at the end of a line that ends with `)`, so the `func main()` line ends
right there. The fix: put `{` back on the same line as `func main()` (`go fmt` does not fix this: it reports the same
error and leaves the file unchanged).

### 3. `fmt.println` with a lowercase letter

```go
package main

import "fmt"

func main() {
	fmt.println("bozor ishga tushdi")
}
```

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:6:6: undefined: fmt.println (but have Println)
```

Reading it: line 6, column 6, where `println` starts (the Tab and `fmt.` are 5 bytes). `undefined: fmt.println (but
have Println)`: `fmt.println` is not defined, but `Println` exists. A name with a lowercase first letter is not
visible outside its package; the rule is in [GB-2.06](/lab/youtube/gb#gb-2-06). The fix: `Println`.

### 4. `go run` without a package

```console
$ go run
go: no go files listed
```

"no go files listed". Unlike `go build`, `go run` does not take the current folder by itself. The fix: `go run .`.

### 5. Fixing errors from the end

The unclosed quote gave two lines of errors, and the second said "missing comma or `)`". If you trust the second one
and add a `)`, nothing is fixed: the cause is in the first line. Always start with the first message (the "Reading a
compiler error" section).

## Check yourself

**1.** What do the two entries in the `go.mod` file mean?

<details>
<summary>Answer</summary>

`module github.com/abdurahmon27/bozor` is the module path, the full name of the module. `go 1.26.8` is the minimum Go

**2.** What is the difference between `go run .` and `go build`?

<details>
<summary>Answer</summary>

`go run .` compiles and runs at once, keeps the result in the build cache and leaves no file in the project folder.
`go build` makes one executable file (a binary) that works without Go, and does not run it.

</details>

**3.** Where does a message that starts with `./main.go:4:8` point?

<details>
<summary>Answer</summary>

To line 4, column 8 (byte 8, counting from 1) of the file `main.go` in the current folder. In our example this is
where `"os"` starts in `import "os"`.

</details>

**4.** Predict the output. In an empty folder `dukon` ("shop"): `go mod init github.com/abdurahmon27/bozor`, then the
7-line `main.go` from above and `go build`. What does `ls` show?

**A)** `dukon  go.mod  main.go` · **B)** `bozor  go.mod  main.go` · **C)** `go.mod  main  main.go`

<details>
<summary>Answer</summary>

**B.** The binary's name comes not from the folder but from the last part of the module path:

```console
$ go build
$ ls
bozor  go.mod  main.go
```

If you chose "A", you thought the name comes from the folder; "C" takes it from the package name `main`.

</details>

**5.** From the start of the lesson. On another computer `go version` prints `go version go1.26.8 darwin/arm64`. What
does it mean, and will a `bozor` built there run on our `linux/amd64` server?

<details>
<summary>Answer</summary>

Go 1.26.8, the operating system is macOS (`darwin`), the processor is ARM (an Apple chip, `arm64`). A plain
`go build` builds for its own system, so a `bozor` made there does not run on a `linux/amd64` server. Building for
another system comes in the course's section on deploying to a server.

</details>
