## Что вы узнаете

Когда вы выкладываете бэкенд bozor на сервер, что именно вы туда копируете: код, сам Go или что-то другое? На этой
странице мы начнём с пустой папки и ответим на этот вопрос прямо в терминале.

**Bozor** («базар») — бэкенд, который растёт на протяжении всего курса, то есть программа, работающая на сервере:
маленький marketplace, который управляет товарами, остатками и заказами. Сегодня он печатает одну строку. К концу
курса он станет API, работающим на сервере.

**Одна идея:** исходный текст (`main.go` и `go.mod`) через `go build` превращается в один файл. Его напрямую
запускает операционная система: ему не нужны ни Go, ни `main.go`. Но он собран из кода, каким тот был в момент
последнего `go build`.

К концу урока вы:

- создадите модуль в пустой папке через `go mod init` и объясните обе строки `go.mod`;
- прочитаете каждую строку и каждый символ `main.go`: `package main`, `import "fmt"`, `func main() { … }`,
  `fmt.Println(…)`;
- будете знать разницу между `go run .` и `go build` и не попадёте в ловушку устаревшего бинарника;
- найдёте ошибку компилятора по `файл:строка:столбец` и приведёте код к стандартному формату через `go fmt ./...`.

Три главных новых слова сегодня:

| Слово | Простой смысл | По-английски |
|---|---|---|
| модуль | код, который версионируется вместе под одним именем; имя и версия Go лежат в файле `go.mod` | module |
| точка входа | место, где начинается программа: функция `main` в пакете `main` | entry point (`package main` + `func main`) |
| бинарник | исполняемый файл, который собрал `go build`: машинный код, внутри есть и Go runtime | binary (executable) |

Есть и две вспомогательные команды: `go run .` (компилирует и сразу запускает) и `go fmt ./...` (приводит код к
стандартному формату).

## Что нужно знать заранее

Это первый урок курса, предыдущего урока нет. Понадобятся терминал, текстовый редактор и установленный Go.

**Установка Go.** Официальная инструкция: [go.dev/doc/install](https://go.dev/doc/install), загрузка:
[go.dev/dl](https://go.dev/dl). Короткий путь для каждой системы — в
[README](https://github.com/abdurahmon27/go-backend-uz/tree/main/lessons/gb-1-01-birinchi-dastur) папки курса:

- **Linux:** распакуйте архив `.tar.gz` в `/usr/local` и добавьте `/usr/local/go/bin` в PATH.
- **macOS:** откройте файл `.pkg` (на компьютере с чипом Apple — `darwin-arm64`, на Intel — `darwin-amd64`).
- **Windows:** откройте файл `.msi`. В Windows `go build` создаёт файл `bozor.exe`. Команды с этой страницы так же
  работают в WSL и Git Bash; в `cmd` и PowerShell нет `ls -lh` и `env -i`.

**Как запускать код.** Этот урок делайте не в браузерном go.dev/play, а на своём компьютере: ему нужны `go.mod`,
`go build` и файлы в папке. Откройте терминал в пустом месте вне папки курса и вводите команды в порядке страницы.
Папка курса (`lessons/gb-1-01-birinchi-dastur`) — состояние в конце урока: `go.mod`, `main.go` и тест, который
проверяет задание.

Сначала один вопрос из того, что вы знаете о терминале. В текущей папке есть исполняемый файл `bozor`. Чем
отличается ввод `bozor` от ввода `./bozor`?

**A)** ничем · **B)** `bozor` shell ищет в папках из PATH, а `./bozor` запускает файл из текущей папки ·
**C)** `./` даёт файлу право на запуск

<details>
<summary>Ответ</summary>

**B.** Если в имени нет `/`, shell ищет команду в папках из переменной окружения PATH; текущей папки там обычно нет.

</details>

установленную версию Go.

```console
$ go version

```

| Часть | Смысл |
|---|---|
| `go1.26` | основной релиз (major release): Go 1.26 |
| `.8` | восьмой корректирующий релиз (minor release): исправлены ошибки, язык не менялся |

## Модуль: `go mod init` и `go.mod`

Проекту нужны имя и версия Go. В Go проект — это **модуль** (module): код, который версионируется вместе под одним
именем.

Сначала создаём пустую папку `bozor` и заходим в неё. `mkdir` создаёт папку, `cd` переходит в неё. Два амперсанда
(`&&`) выполняют вторую команду, только если первая завершилась успешно.

```console
$ mkdir bozor && cd bozor
$ go mod init github.com/abdurahmon27/bozor
go: creating new go.mod: module github.com/abdurahmon27/bozor
```

`mkdir … && cd …` ничего не вывела. `go mod init` начинает новый модуль. Текст в конце — **путь модуля** (module
path), то есть его полное имя. Обычно это адрес, где лежит код: `github.com`, имя пользователя и имя проекта. Вместо
`abdurahmon27` напишите своё имя на GitHub; адреса пока может и не существовать.

Go написал одну строку: «создаётся новый go.mod: модуль github.com/abdurahmon27/bozor». В видео этот длинный путь на
экране сокращён до `…/bozor`; здесь он полностью.

Смотрим содержимое файла (`cat` выводит файл в терминал):

```console
$ cat go.mod
module github.com/abdurahmon27/bozor

go 1.26.8
```

| Строка | Запись | Что делает |
|---|---|---|
| 1 | `module github.com/abdurahmon27/bozor` | путь модуля: другой код обращается к этому модулю по этому имени |
| 2 | (пустая) | разделяет две записи |
| 3 | `go 1.26.8` | строка `go`: минимальная версия Go, нужная этому модулю (так с Go 1.21) |

В файле две записи. Первое слово каждой (`module`, `go`) — **директива** (directive): она говорит, о чём строка.
`go mod init` пишет в строку `go` установленную версию, у вас число может быть другим.

Одно уточнение. В заметках к релизу Go 1.26 сказано, что `go mod init` пишет `go 1.25.0`. Это верно только для
go1.26.0: начиная с go1.26.1 он снова пишет установленную версию (источник: `cmd/go/internal/modload/init.go`).
Поэтому у нас `go 1.26.8`.

`go.mod` в папке курса требует `go 1.26.8`. Если ваш Go старее, по README возможны два случая (здесь не запускалось,
нужен старый Go): при обычной настройке (`GOTOOLCHAIN=auto`) Go сам скачает нужную версию; у Go из пакета
Debian/Ubuntu (`GOTOOLCHAIN=local`) появится ошибка `go.mod requires go >= 1.26.8`. Решение: обновите Go или сделайте
`go mod init` в своей папке.

## `main.go` построчно

Теперь создаём в этой папке файл `main.go`. Вот вся программа, 7 строк:

```go filename="main.go" showLineNumbers
package main

import "fmt"

func main() {
	fmt.Println("bozor ishga tushdi")
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1 | `package main` | файл относится к пакету `main`: компилятор делает из него запускаемую программу |
| 2 | (пустая) | разделитель; его ставит `go fmt` (ниже) |
| 3 | `import "fmt"` | подключает к файлу пакет `fmt` из стандартной библиотеки |
| 4 | (пустая) | разделитель |
| 5 | `func main() {` | объявляет функцию `main` и открывает её тело: программа начинается здесь |
| 6 | `fmt.Println("bozor ishga tushdi")` | вызывает `Println` из пакета `fmt`: пишет текст в терминал |
| 7 | `}` | тело функции закончилось; когда заканчивается `main`, заканчивается и программа |

Строка `"bozor ishga tushdi"` по-узбекски значит «bozor запустился». Теперь каждая строка подробно.

### Строка 1: `package main`

Каждый файл Go начинается со слова `package` и говорит, к какому **пакету** (package) он относится. Пакет — это
файлы `.go` из одной папки, которые компилируются вместе. Имя `main` особое: из пакета `main` компилятор делает
запускаемую программу. Пакет с другим именем становится библиотекой: его используют другие пакеты, сам он не
запускается.

### Строка 3: `import "fmt"`

`import` подключает к файлу другой пакет. `fmt` — пакет из **стандартной библиотеки** (standard library), имя от
слова «format»: он форматирует и выводит текст. Стандартная библиотека поставляется вместе с Go, скачивать её и
интернет не нужно.

Путь пакета пишется в кавычках: кавычки ограничивают текстовое значение, то есть **строку** (string). `"fmt"` —
строка из трёх букв `fmt`, путь пакета.

### Строки 5 и 7: `func main() { … }`

- `func` объявляет функцию, `main` — её имя.
- Пустые скобки `()` означают, что функция не принимает никаких значений.
- Фигурные скобки `{` и `}` окружают тело функции. Открывающая `{` обязана стоять на этой же строке; если перенести
  её на следующую, компилятор выдаст ошибку (настоящее сообщение — в разделе «Частые ошибки»).

Функция `main` в пакете `main` — **точка входа** (entry point) программы. Go вызывает её сам. Строки тела выполняются
сверху вниз. Когда функция заканчивается, заканчивается и программа.

### Строка 6: `fmt.Println("bozor ishga tushdi")`

Эта строка — вся работа программы.

- `fmt.Println`: точка обращается к имени внутри пакета `fmt`. `fmt.Println` = «`Println` из пакета `fmt`».
- `( … )`: скобки **вызывают** функцию. Значение внутри — **аргумент** (argument); здесь одна строка.
- `Println` пишет свой аргумент в **стандартный вывод** (standard output), то есть в терминал, и добавляет в конце
  символ новой строки. Имя — от «print line».
- Заглавная `P` означает, что имя видно за пределами пакета. Это правило мы разберём в уроке курса о пакетах
  ([GB-2.06](/lab/youtube/gb/gb-2-06/ru)). Сейчас достаточно знать: написать `fmt.println` со строчной буквы нельзя.
- Отступ в начале строки — один символ Tab. Выравнивать его вручную не нужно: его ставит `go fmt`.

### Что происходит при запуске программы

| Шаг | Что происходит | На экране |
|---|---|---|
| 1 | операционная система запускает программу, Go runtime готовится к работе | — |
| 2 | Go вызывает функцию `main` из пакета `main` (строка 5) | — |
| 3 | строка 6: `Println` пишет `bozor ishga tushdi` и символ новой строки в стандартный вывод | `bozor ishga tushdi` |
| 4 | строка 7: `main` закончилась, программа завершается | — |

## `go run .`: скомпилировать и сразу запустить

Запускаем программу: пишем `go run .`. Точка (`.`) — пакет в текущей папке. Эта команда компилирует пакет и сразу
запускает результат.

Сколько файлов будет в папке после команды?

**A)** 2: `go.mod`, `main.go` · **B)** 3: добавится скомпилированный файл `bozor` · **C)** 3: появится файл с именем
`main`

<details>
<summary>Ответ</summary>

**A: два.** `go run` пишет результат компиляции не в папку проекта, а в папку **кэша сборки** Go (build cache) и
запускает его оттуда (с Go 1.24 результат там и сохраняется). В Linux это папка `~/.cache/go-build`; вашу покажет
`go env GOCACHE`. Если вы выбрали «B», вы спутали `go run` с `go build`: файл в папку пишет `go build` (следующий
раздел). В «C» та же ошибка, да ещё и имя неверное.

</details>

```console
$ go run .
bozor ishga tushdi
$ ls
go.mod  main.go
```

На экране строка, которую написала программа, без кавычек: кавычки были лишь границей текста в коде. `ls` показала в
папке только `go.mod` и `main.go`.

Пакет команде `go run` указывают всегда, здесь — точкой. `go run main.go` тоже работает, но берёт только этот один
файл: когда файлов в пакете станет больше, нужен `go run .`.

## `go build`: один исполняемый файл

`go run` каждый раз компилирует заново и не оставляет результат в папке. `go build` же записывает результат в папку
файлом. Если пакет не указан, он собирает пакет текущей папки.

```console
$ go build
$ ls
bozor  go.mod  main.go
```

Успешный `go build` работает молча: ничего не вывел. `ls` теперь показывает три файла. Новый файл — **бинарник**
(binary), он назван `bozor`. Имя берётся не из папки, а из последней части пути модуля
(`github.com/abdurahmon27/bozor` → `bozor`). В Windows это будет `bozor.exe`.

Смотрим файл подробно и запускаем его:

```console
$ ls -lh bozor
-rwxr-xr-x 1 haywan users 2.3M Nov 27 00:07 bozor
$ ./bozor
bozor ishga tushdi
```

`ls -l` даёт подробный список, `h` пишет размер в удобных для чтения единицах:

| Столбец | Значение | Смысл |
|---|---|---|
| права | `-rwxr-xr-x` | первый `-` = обычный файл; буквы `x` означают, что файл можно запускать |
| число ссылок | `1` | сколько у файла имён (жёсткие ссылки) |
| владелец | `haywan` | пользователь, создавший файл |
| группа | `users` | группа владельца |
| размер | `2.3M` | 2,3 MiB (точно: 2 410 014 байт) |
| время | `Nov 27 00:07` | время последнего изменения |
| имя | `bozor` | имя файла |

В видео в строке время `Nov 26 23:27`; остальные столбцы те же. У вас владелец, группа и время будут другими.
Точное число байт тоже может отличаться на несколько байт (при сборке для видео было 2 410 070 байт), а `2.3M`
остаётся тем же.

`./bozor` запустил его из текущей папки: та же строка. Почему размер 2,3 MiB, увидим в следующем разделе.

## В окружении без Go: `env -i`

Теперь скопируем файл `bozor` в другую папку и запустим в пустом окружении без PATH. Рядом нет `main.go`, терминал
не может найти Go. Что произойдёт?

**A)** выведется `bozor ishga tushdi` · **B)** ошибка: go не найден · **C)** ошибка: нет main.go

<details>
<summary>Ответ</summary>

**A: программа работает.** `bozor` — готовый машинный код, для его запуска не нужны ни Go, ни `main.go`. Если вы
выбрали «B», вы думали, что для работы программы на Go нужен установленный Go: Go нужен только для **сборки**. Если
выбрали «C», вы думали, что бинарник каждый раз читает `main.go`: он не читает текст, текст превратился в машинный код
при сборке.

</details>

```console
$ env -i go version
env: ‘go’: No such file or directory
$ cp bozor /tmp/ && env -i /tmp/bozor
bozor ishga tushdi
```

`env -i` запускает следующую за ней команду в пустом окружении, без PATH. В первой команде `env` не нашла `go`: «нет
такого файла или папки» (код выхода 127). Во второй `cp` скопировала файл в папку `/tmp`, а `env` запустила его там:
рядом нет `main.go`, нет PATH, а `bozor` всё равно сработал.

Одно исключение (из README): если PATH нет, `env` ищет в `/bin` и `/usr/bin`. Если Go установлен в `/usr/bin` через
`apt install golang-go`, `env -i go version` сработает. Это не меняет того, что `bozor` не нуждается в Go.

### Почему сработало: что внутри `go build`

`go build` собирает в один файл наш код, пакет `fmt` и **runtime** Go. Runtime — код, который добавляется к каждой
программе на Go и управляет памятью и работой программы.

```text
main.go + go.mod       наш текст
      │
      ▼
   go build            компиляция + сборка
      │
      ▼
    bozor              наш код + fmt + runtime
      │                машинный код: не нужны ни Go, ни main.go
      ▼
  linux/amd64          эта система запускает его напрямую
```

Большая часть файла — runtime. Измерим: соберём программу с пустой `func main() {}`. Этого примера нет в папке курса;
его полный код:

```go
package main

func main() {}
```

```console
$ mkdir bosh && cd bosh
$ go mod init github.com/abdurahmon27/bosh
go: creating new go.mod: module github.com/abdurahmon27/bosh
$ go build
$ stat -c %s bosh
1830036
```

`stat -c %s` выводит размер файла в байтах (`bosh` по-узбекски — «пустой»). Программа, которая ничего не делает, —
1 830 036 байт, а `bozor` — 2 410 014 байт: 76 % файла `bozor` были там ещё до подключения `fmt` (runtime и код
запуска программы). В исследовании курса на том же Go вышло 1 830 044 и 2 410 070 байт: соотношение снова 76 %.

Файл не связан и с другими библиотеками системы. `ldd` показывает, каких системных библиотек требует программа:

```console
$ ldd ./bozor
	not a dynamic executable
```

«не динамический исполняемый файл»: `bozor` не загружает ни одной системной библиотеки. Поэтому на сервер копируют
этот один файл. Условие одно: сервер тоже должен быть `linux/amd64`. Сборку для другой системы разберём в разделе
курса о выкладке на сервер.

## Устаревший бинарник

Теперь меняем текст в строке 6 на `bozor yangilandi` («bozor обновился») и сохраняем файл:

```go
package main

import "fmt"

func main() {
	fmt.Println("bozor yangilandi")
}
```

```console
$ go run .
bozor yangilandi
```

`go run .` вывел новый текст: он каждый раз компилирует из текущего кода. А `go build` мы не запускали.

Что теперь напишет `./bozor`?

**A)** `bozor yangilandi` · **B)** `bozor ishga tushdi` · **C)** ошибка: файл устарел

<details>
<summary>Ответ</summary>

**B: старый текст.** `go run` не пишет результат в папку. А файл `bozor` собран из кода на момент последнего
`go build`. Если вы выбрали «A», вы думали, что `go run` обновляет и файл `bozor`. Если «C», вы думали, что бинарник
знает об изменении `main.go`: он вообще не видит `main.go`, и никто не предупреждает.

</details>

```console
$ ./bozor
bozor ishga tushdi
$ go build && ./bozor
bozor yangilandi
```

| Шаг | Текст в `main.go` | Текст внутри файла `bozor` | На экране |
|---|---|---|---|
| первый `go build` | `bozor ishga tushdi` | `bozor ishga tushdi` | — |
| текст изменён, `go run .` | `bozor yangilandi` | `bozor ishga tushdi` | `bozor yangilandi` |
| `./bozor` | `bozor yangilandi` | `bozor ishga tushdi` | `bozor ishga tushdi` |
| `go build && ./bozor` | `bozor yangilandi` | `bozor yangilandi` | `bozor yangilandi` |

Чтобы обновить, нужен повторный `go build`. Забытый на сервере старый файл — настоящая ошибка. Поэтому программы
обычно при запуске печатают свою версию: в домашнем задании вы добавите это в bozor.

Перед следующим разделом верните текст в исходное состояние (`bozor ishga tushdi`).

## Как читать ошибку компилятора: `файл:строка:столбец`

Теперь потренируемся читать сообщения компилятора. Каждую ошибку сделайте в `main.go` временно, потом верните.

### Незакрытая кавычка

Удаляем закрывающую кавычку в строке 6:

```go
package main

import "fmt"

func main() {
	fmt.Println("bozor ishga tushdi)
}
```

Не хватает одного символа кавычки. Что скажет `go run .`?

**A)** программа работает, текстом считается всё до конца строки · **B)** одна ошибка: строка не закрыта ·
**C)** две ошибки: и строка, и скобка

<details>
<summary>Ответ</summary>

**C: две строки ошибок.** Первая — строка не закрыта. Текст растянулся до конца строки и «проглотил» закрывающую `)`,
поэтому компилятор видит, что и скобка не закрыта. Если вы выбрали «A»: в Go обычная строка в кавычках не может
занимать больше одной строки кода. В «B» не учтена вторая ошибка, она — следствие первой.

</details>

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:6:34: newline in string
./main.go:6:34: syntax error: unexpected newline in argument list; possibly missing comma or )
```

Первая строка `# github.com/abdurahmon27/bozor` — какой пакет компилируется (в видео эта строка скрыта). Каждая из
следующих двух начинается с `файл:строка:столбец`:

| Часть | Значение | Смысл |
|---|---|---|
| файл | `./main.go` | `main.go` в текущей папке |
| строка | `6` | 6-я строка |
| столбец | `34` | 34-й байт в строке, считая с 1 |

**Столбец** (column) — номер байта в строке. В этой строке каждый символ, и Tab тоже, занимает один байт:

| Кусок | Байт | Всего |
|---|---|---|
| Tab | 1 | 1 |
| `fmt.Println(` | 12 | 13 |
| `"` | 1 | 14 |
| `bozor ishga tushdi)` | 19 | 33 |
| конец строки (символ новой строки) | — | **34** |

34-й байт — конец строки: компилятор увидел символ новой строки внутри открытой строки.

- `newline in string` — «перевод строки внутри строки»: строка кончилась, а текст не закрыт.
- `syntax error: unexpected newline in argument list; possibly missing comma or )` — **синтаксическая ошибка**
  (syntax error): «неожиданный перевод строки в списке аргументов; возможно, не хватает запятой или `)`». Это
  следствие первой.

Правило: **исправляйте первую ошибку**. Часто остальные исчезают сами. Здесь возврат закрывающей `"` убирает оба
сообщения.

### Неиспользуемый импорт

Кавычку вернули. Теперь добавим в строку 4 `import "os"`. `os` — стандартный пакет для работы с операционной
системой, но мы из него ничего не вызываем:

```go
package main

import "fmt"
import "os"

func main() {
	fmt.Println("bozor ishga tushdi")
}
```

Что сделает `go run .`?

**A)** программа работает и ничего не говорит · **B)** программа работает, но появится предупреждение ·
**C)** программа вообще не скомпилируется

<details>
<summary>Ответ</summary>

**C.** В Go неиспользуемый импорт — не предупреждение, а ошибка: программа не собирается, и `bozor ishga tushdi` тоже
не выводится. Если вы выбрали «B», вы ждали компилятор с предупреждениями: в компиляторе Go предупреждений нет,
только ошибки.

</details>

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:4:8: "os" imported and not used
```

Адрес: строка 4, столбец 8. `import ` (с пробелом) — 7 байт, 8-й байт — место, где начинается `"os"` в кавычках.
`imported and not used` — «импортирован, но не используется». Исправление: удалить эту строку.

Официальный FAQ Go называет причину: лишний импорт замедляет компиляцию, и по мере роста кода это становится
заметно. Поэтому Go считает его ошибкой.

Два замечания (из README). Обычно импорты пишут одной группой: `import (` … `"fmt"` … `"os"` … `)`; эту форму увидим
в следующих уроках. Расширение Go для VS Code при сохранении файла само удаляет неиспользуемый импорт: чтобы увидеть
эту ошибку, сохраните файл через «Save without Formatting».

## `go fmt ./...`: один стандартный формат

Последний инструмент. Мы записали `main.go` неаккуратно:

```go
package main
import "fmt"
func main(){
fmt.Println("bozor ishga tushdi")
}
```

Этот код работает, но в нём нет пустых строк, нет отступа, нет пробела между `)` и `{`. В Go то, как выглядит код,
определено одним стандартом. Его применяет программа **gofmt**, а `go fmt` запускает её на пакетах.

```console
$ go fmt ./...
main.go
$ go fmt ./...
```

`./...` — текущая папка и пакеты во всех папках внутри неё. `go fmt` приводит каждый файл к формату gofmt и пишет
имена изменённых файлов: в первый раз `main.go`. Во второй раз ничего не вывел: менять было нечего.

Файл снова стал 7-строчным:

```go filename="main.go" showLineNumbers
package main

import "fmt"

func main() {
	fmt.Println("bozor ishga tushdi")
}
```

Пустые строки в строках 2 и 4, отступ одним Tab в строке 6, пробел в `main() {` в строке 5. Весь код на Go выглядит
одинаково, поэтому на ревью кода (code review) вы обсуждаете смысл, а не формат. Многие редакторы сами вызывают gofmt
при сохранении файла.

## Глубже (необязательно): столбец — это байт, а не символ

Столбец в сообщении об ошибке считается в байтах. В строке выше каждый символ был одним байтом, поэтому разницы не
было видно. С узбекской буквой разница видна: `ʻ` (U+02BB) в UTF-8 занимает два байта. Этого примера нет в папке
курса; в строке 6 незакрытый текст `"oʻrik` («урюк»):

```go
package main

import "fmt"

func main() {
	fmt.Println("oʻrik)
}
```

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:6:22: newline in string
./main.go:6:22: syntax error: unexpected newline in argument list; possibly missing comma or )
```

В строке 6 — 20 символов, но 21 байт (`ʻ` — два байта). Компилятор показал столбец 22: конец строки — 22-й байт. При
счёте по символам вышло бы 21. В строках с узбекским текстом номер столбца может быть больше числа символов: ошибка
всё равно в указанном месте, просто счёт идёт в байтах.

## Частые ошибки

### 1. «`go run .` обновляет и бинарник»

Самое частое неверное представление в этой теме. `go run .` пишет результат в кэш сборки и не меняет файл `bozor` в
папке. Сообщения об ошибке нет: старый файл молча продолжает работать и даёт старый результат. Настоящий вывод — в
разделе «Устаревший бинарник». Исправление: повторный `go build` перед копированием или запуском, и пусть программа
при запуске печатает свою версию (домашнее задание).

### 2. Открывающая `{` на следующей строке

```go
package main

import "fmt"

func main()
{
	fmt.Println("bozor ishga tushdi")
}
```

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:6:1: syntax error: unexpected semicolon or newline before {
```

Читаем: `main.go`, строка 6, столбец 1 — одинокая `{`. Сообщение: «неожиданная точка с запятой или перевод строки
перед `{`». Компилятор Go ставит невидимую точку с запятой в конце строки, которая заканчивается на `)`, поэтому
строка `func main()` на этом и заканчивается. Исправление: верните `{` на одну строку с `func main()` (`go fmt` это
не исправит: он выдаёт ту же ошибку и не меняет файл).

### 3. `fmt.println` со строчной буквы

```go
package main

import "fmt"

func main() {
	fmt.println("bozor ishga tushdi")
}
```

```console
$ go run .
# github.com/abdurahmon27/bozor
./main.go:6:6: undefined: fmt.println (but have Println)
```

Читаем: строка 6, столбец 6 — там, где начинается `println` (Tab и `fmt.` = 5 байт). `undefined: fmt.println (but
have Println)` — «`fmt.println` не определён (но есть `Println`)». Имя со строчной буквы не видно за пределами
пакета; правило — в [GB-2.06](/lab/youtube/gb/gb-2-06/ru). Исправление: `Println`.

### 4. `go run` без пакета

```console
$ go run
go: no go files listed
```

«не указано ни одного go-файла». В отличие от `go build`, `go run` сам не берёт текущую папку. Исправление:
`go run .`.

### 5. Исправлять ошибки с конца

Незакрытая кавычка дала две строки ошибок, вторая сказала «не хватает запятой или `)`». Если поверить второй и
добавить `)`, ничего не исправится: причина в первой строке. Всегда начинайте с первого сообщения (раздел «Как читать
ошибку компилятора»).
