## What you will learn

bozor stores prices in som, but customers also want to see the price in dollars. The dollar rate changes every day, so we take it from an external **API**: an API is data that another program serves over HTTP.
It is one call, but there are three places to get it wrong. Today we close all three.

**One idea:** `http.Get` and `client.Get` return an error only when the request **could not be carried out**: the connection dropped, the time ran out, a protocol error, too many redirects.
If the server answered — `404` as well as `503` — then `err` is empty (`nil)` and the outcome sits in `resp.StatusCode`: we check it ourselves. The default client has `Timeout` 0, which means nothing
limits the wait for a response; a silent server stops the program forever, so we pass `&http.Client{Timeout: …}`. `resp.Body` is a stream: after the error check we **write**
`defer resp.Body.Close()` and read the JSON with `Decode`.

By the end of the lesson you will:

- see why the default `http.Get` waits forever for a silent server, and limit the wait with `http.Client{Timeout: 2 * time.Second}`;
- see why `err` is `nil` for a `404` response, and write the `resp.StatusCode != http.StatusOK` check;
- close `resp.Body` with `defer resp.Body.Close()` and see `go vet` catch the mistake of writing `defer` before the error check;
- write `fetchRate`, which reads JSON into the `rateResponse` struct, and meet its third trap (status `200`, but an error in the body);
- harden `fetchRate` against that trap in the homework, with the `*StatusError` type and `io.LimitReader`, and make `go test` pass.

Today's three core new words:

| Word | Plain meaning | English term |
|---|---|---|
| timeout | the longest time a client waits for a response; `0` means no limit | timeout |
| status check | after a response arrives, we compare `resp.StatusCode` ourselves | status check |
| `resp.Body` and `Close` | the main part of the response: read as a stream, then closed | response body, close |

Helper words: the `time.Second` and `&http.Client{…}` notation, and `float64(x)` with `%.2f`/`%.0f` (only for displaying a price).

One question about the previous lesson. The first line of the server's response is `HTTP/1.1 404 Not Found`. What does it mean?

**A)** the server answered: not found · **B)** the connection to the server dropped · **C)** the request text was written wrongly

<details>
<summary>Answer</summary>

**A.** The server answered, and the answer itself is `404`: what was asked for was not found. The connection did not drop, and the request text was read ([GB-4.01](/lab/youtube/gb/gb-4-01/en)).

| What happened | Where it shows in Go |
|---|---|
| the request was not carried out (no connection, time ran out) | `err != nil`, no `resp` |
| the server answered: `200`, `404`, `503` | `err == nil`, the code is in `resp.StatusCode` |

## The first silent failure: a server that does not answer

The default client has `Timeout` 0, and zero means **there is no limit on waiting for the response**. More precisely: the default transport gives 30 seconds to open the connection and 10 seconds for the TLS handshake,
but puts no limit on waiting for the response headers. If the server accepts the connection and stays silent, the program keeps waiting.

To see this we need a server that does not answer. In a second terminal, the `nc` command:

```console
$ nc -l 8089
```

`nc` prints nothing: it stands and waits. `nc` (netcat) is a simple network program, `-l` (listen) means "listen". `8089` is a **port**: the network number of one program on this computer.
`nc` accepts the connection on that port but writes nothing: it is a "silent server". (`nc` programs differ: this is the LibreSSL/OpenBSD variant; in GNU netcat it is `nc -l -p 8089`.)

We point the program at this server. The address is `http://localhost:8089`: `localhost` is this computer itself, `8089` is the port. `_video/02-sukut/main.go` differs from the previous one in two places
(the other lines are the same):

```go
	fmt.Println("soʻrov yuborildi")
	resp, err := http.Get("http://localhost:8089")
```

The first line prints text before `Get`, so we can see that the request went out. In the second, the address is the silent `nc`. What is the result?

**A)** an error at once · **B)** an error after 30 seconds · **C)** no error: the program waits

<details>
<summary>Answer</summary>

**C.** `http.Get` is called with the default client, `Timeout` 0: the wait is unlimited. The connection opened (`nc` accepted it), so there is no connection error either; and the response does not come.
**A** would happen if nobody listened on the port ("connection refused"). **B** — 30 seconds is the limit only for *opening* the connection; it is already open.

</details>

We start `nc` in one terminal and the program in another. In the video the program was stopped with Control C. To make the run repeatable, I sent the same signal with `timeout` after 6 seconds:

```console
$ cd _video/02-sukut && timeout -s INT 6 go run .
soʻrov yuborildi
signal: interrupt
```

`soʻrov yuborildi` ("request sent") was printed, then nothing for 6 seconds. `signal: interrupt` — the program was interrupted (`interrupt` is the signal that Control C sends). When you press Control C in the video, the terminal shows `^C` itself
(`^Csignal: interrupt`); with `timeout` no `^C` appears, the rest is the same. Six seconds is not chance: I stopped the program myself; had I not, it would still be waiting after 30 seconds.
If the server never answers, our program never continues either.

## The fix: http.Client and Timeout

The fix is our own **client**. `http.Client` is a struct with fields; we give the `Timeout` field the wait limit. `_video/03-timeout/main.go`:

```go filename="_video/03-timeout/main.go" showLineNumbers
package main

import (
	"fmt"
	"net/http"
	"os"
	"time"
)

func main() {
	client := &http.Client{Timeout: 2 * time.Second}
	resp, err := client.Get("http://localhost:8089")
	if err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	fmt.Println(resp.Status)
}
```

| Line | Code | What it does |
|---|---|---|
| 7 | `"time"` | `time` is the standard package for working with time |
| 11 | `client := &http.Client{Timeout: 2 * time.Second}` | `http.Client{…}` is the `Client` struct with its `Timeout` field; `time.Second` is one second, `2 * time.Second` is two seconds; `&` takes the **address** of the struct ([GB-2.04](/lab/youtube/gb/gb-2-04/en)), so one client is used in every call |
| 12 | `resp, err := client.Get("http://localhost:8089")` | now `client.Get`: not `http.Get`, but our own client. The address is the silent `nc` again |

The server is still silent. What is printed?

**A)** an error after 2 seconds · **B)** an error at once · **C)** it still waits

<details>
<summary>Answer</summary>

**A.** `Timeout` is the limit of the wait. When it is exceeded, the client aborts the request and `Get` returns an error. **C** — that is the behaviour of a client with `Timeout` 0 (the default). **B** — there is no reason to fail before `Timeout`.

</details>

We start a new `nc` (it ends after one connection) and run the program:

```console
$ cd _video/03-timeout && go run .
xato: Get "http://localhost:8089": context deadline exceeded (Client.Timeout exceeded while awaiting headers)
exit status 1
```

The parts of the message: `Get "http://localhost:8089"` — which call and which address; `context deadline exceeded` — "the deadline passed"; in parentheses, the cause: `Client.Timeout exceeded while awaiting headers`,
that is, `Timeout` was exceeded and the response headers did not arrive. We open the word `context` in the message in [GB-7.03 · `select` and `context`](/lab/youtube/gb#gb-7-03); for now read it as "deadline".
`exit status 1` comes from `os.Exit(1)` ([GB-1.07](/lab/youtube/gb/gb-1-07/en)). Now the wait is limited and the program does not hang.

The diagram:

| Time | What happens |
|---|---|
| 0 s | the program calls `client.Get`, the request goes out; the client starts a 2-second timer |
| 0–2 s | the server (`nc`) stays silent |
| 2 s | the timer expires; `Get` returns an error: `deadline exceeded` |

I measured these 2 seconds. The number in the video is "2 seconds" (that is how the code is written). I built a binary, started a new `nc` and timed it with `time` (this measurement is not in the video):

```console
$ go build -o kurs .
```

`go build` printed nothing: a new file `kurs` appeared (delete it if you do not need it).

```console
$ time ./kurs
xato: Get "http://localhost:8089": context deadline exceeded (Client.Timeout exceeded while awaiting headers)

real	0m2.003s
user	0m0.000s
sys	0m0.003s
```

`real` is wall-clock time: 2.003 seconds, almost exactly `Timeout: 2 * time.Second` (the second run also gave 2.003). If the machine is busy, hundredths of a second may be added; what matters is the ratio:
**the client's wait equals the `Timeout` value, not the speed of the machine**. `user` and `sys` are processor time: while it waits, the program does almost nothing. (The `time` output looks different in other shells: this is bash.)

## The second silent failure: 404 is not an error

The second case: the server answers, but not as we expected. We send a request to an address that does not exist: `/v6/nothing`. `_video/04-404/main.go`:

```go filename="_video/04-404/main.go" showLineNumbers
package main

import (
	"fmt"
	"net/http"
	"os"
	"time"
)

func main() {
	client := &http.Client{Timeout: 2 * time.Second}
	resp, err := client.Get("https://open.er-api.com/v6/nothing")
	if err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	fmt.Println("err:", err)
	fmt.Println(resp.Status, resp.StatusCode)
}
```

New lines: 12 — the address `/v6/nothing` ("nothing": no such path); 17 — prints the value of `err` itself (we only get here when `err == nil`); 18 — the status. What does `Get` return?

**A)** `err != nil`, no `resp` · **B)** `err` is nil, status `404` · **C)** panic

<details>
<summary>Answer</summary>

**B.** The server answered, so the request was **carried out**: `err` is nil, and `404` is inside `resp`. **A** — that is what a connection problem would give (previous section). **C** — `Get` does not panic; a panic comes later, if you use a `resp` that does not exist.

</details>

```console
$ cd _video/04-404 && go run .
err: <nil>
404 Not Found 404
```

`err: <nil>` — there is no error (`nil`, which prints as `<nil>`, [GB-1.07](/lab/youtube/gb/gb-1-07/en)); `404 Not Found 404` — `Status` and `StatusCode`. The `Get` documentation says it plainly:
*"A non-2xx response doesn't cause an error"* — a response whose code does not start with `2xx` does not produce an error. `Get` returns an error if the request was not carried out: a connection, deadline or protocol error, too many redirects.
**Checking the status is our job.**

We wrap this in a function that bozor calls from elsewhere. `fetchRate`: it takes a client, an address and a currency code, and returns a rate and an error.

```go
func fetchRate(client *http.Client, url, code string) (float64, error) {
	resp, err := client.Get(url)
	if err != nil {
		return 0, err
	}
	// …
}
```

`url, code string` — both parameters are `string` (short for `url string, code string`); `client *http.Client` is a **pointer** to `Client` ([GB-2.04](/lab/youtube/gb/gb-2-04/en)): `&http.Client{…}` gives exactly this type.
The results are `(float64, error)`: the rate (a fractional number) and an error ([GB-1.07](/lab/youtube/gb/gb-1-07/en)). `Get` is now called on the client itself. On an error we return zero and `err`.

The status check:

```go
	resp, err := client.Get(url)
	if err != nil {
		return 0, err
	}
	if resp.StatusCode != http.StatusOK {
		return 0, fmt.Errorf("kurs soʻrovi: javob %s", resp.Status)
	}
	// …
```

`http.StatusOK` is the name of the number `200` (a constant in the package). If `StatusCode` is not equal to it, we create the error ourselves: `fmt.Errorf` ([GB-1.07](/lab/youtube/gb/gb-1-07/en)). We added `resp.Status` to the message so it is visible what happened
(for example `kurs soʻrovi: javob 404 Not Found`). For now this is plain text: in the homework you replace it with your own type.

Now we gather all three cases in one table:

| Case | `err` | `resp.StatusCode` | What we do |
|---|---|---|---|
| no connection, time ran out | `!= nil` | no `resp` either | return `err` |
| the server answered, but not `200` | `nil` | `404`, `503`, … | check it ourselves and create an error |
| the server answered `200` | `nil` | `200` | read the body |

## resp.Body: a stream, Close and JSON

Third — the body. A response comes in two parts:

```text
client.Get(url)
   │
   ▼
server ──► status line and headers ──► resp.Status, resp.StatusCode   arrives at once
       └─► body                    ──► resp.Body                      a stream: read, then closed
```

The status and headers sit in `resp` at once. The **body** is a **stream**: we read data from it ourselves with `Decode`. The type of `resp.Body` is `io.ReadCloser`: it is a `Reader`
(the `io.Reader` from [GB-2.07](/lab/youtube/gb/gb-2-07/en), which you read from) and a `Close` method. `Close` closes the body.

Why close it? The documentation: if the body is not read to the end and **not closed**, the connection opened to the server may not be reused by the next request (*"may not reuse"*). That is why, right after the error check, we write
`defer resp.Body.Close()`: like `defer f.Close()` in [GB-2.09](/lab/youtube/gb/gb-2-09/en). The documentation adds: when `err == nil`, `resp.Body` is never `nil`.

A type that takes only the needed fields from the response:

```go
type rateResponse struct {
	Result   string             `json:"result"`
	BaseCode string             `json:"base_code"`
	Rates    map[string]float64 `json:"rates"`
}
```

`rateResponse` is a struct: `Result`, `BaseCode`, `Rates`. The tags ([GB-3.02](/lab/youtube/gb/gb-3-02/en)) bind the fields to JSON keys: the key `base_code` lands in the field `BaseCode`.
`Rates` is a map ([GB-2.02](/lab/youtube/gb/gb-2-02/en)): the key is the currency code (`string`), the value is the rate (`float64`).

The program that puts it all together is `_video/05-decode/main.go`:

```go filename="_video/05-decode/main.go" showLineNumbers
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"os"
	"time"
)

type rateResponse struct {
	Result   string             `json:"result"`
	BaseCode string             `json:"base_code"`
	Rates    map[string]float64 `json:"rates"`
}

func main() {
	client := &http.Client{Timeout: 5 * time.Second}
	resp, err := client.Get("https://open.er-api.com/v6/latest/USD")
	if err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	defer resp.Body.Close()
	var data rateResponse
	if err := json.NewDecoder(resp.Body).Decode(&data); err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	fmt.Println(data.BaseCode, data.Rates["UZS"])
}
```

| Line | Code | What it does |
|---|---|---|
| 18 | `client := &http.Client{Timeout: 5 * time.Second}` | 5 seconds in this program: the real API may answer slower than two seconds |
| 24 | `defer resp.Body.Close()` | **after** the error check; when the function ends, the body is closed |
| 25 | `var data rateResponse` | an empty struct that the JSON will fill |
| 26 | `json.NewDecoder(resp.Body).Decode(&data)` | `resp.Body` is the source; `Decode` reads the JSON and writes it into the struct at `&data`; on a failure, `err` ([GB-3.02](/lab/youtube/gb/gb-3-02/en)) |
| 30 | `fmt.Println(data.BaseCode, data.Rates["UZS"])` | which currency the count starts from, and the som rate: from the map by the key `"UZS"` |

```console
$ cd _video/05-decode && go run .
USD 11966.840025
```

`USD` is `base_code`, `11966.840025` is `UZS` in `rates`. This number is the API's **value for today**: on 2026-11-27 both the video and my run gave exactly this. The API refreshes it once a day
(the response has `cache-control: max-age=3600`), so you will get a different number. This is not a mistake: the checks below ("12000 som is about 1 dollar") rely on the ratio, not on the rate.

## Plugging it into bozor: the price in dollars

Now we add `fetchRate` to the bozor code. This is `main.go` in the folder; the homework also starts from this file. It gathers everything in one place:

```go filename="main.go" showLineNumbers
package main

import (
	"encoding/json"
	"fmt"
	"net/http"
	"os"
	"time"
)

const tiyinPerSom = 100 // 1 soʻm = 100 tiyin (GB-1.03)

// rateURL — ochiq kurs API'si: 1 USD necha valyutaga teng (kalitsiz, bepul).
const rateURL = "https://open.er-api.com/v6/latest/USD"

// Product — katalogdagi mahsulot (GB-2.03); narx tiyinda.
type Product struct {
	ID    int64  `json:"id"`
	Name  string `json:"name"`
	Price int64  `json:"price"` // tiyin
	Stock int    `json:"stock"`
}

// rateResponse — kurs API'si javobining bizga kerak qismi.
type rateResponse struct {
	Result   string             `json:"result"`
	BaseCode string             `json:"base_code"`
	Rates    map[string]float64 `json:"rates"`

// StatusError — server 200 dan boshqa status bilan javob bergani.
```

## The third trap: status 200, but an error

If the API does not know the currency code, it answers with status `200`, and the body looks like this (the API's own error type):

```json
{
  "result": "error",
  "error-type": "unsupported-code"
}
```

`result` is `"error"`, `error-type` is the API's error type. The status is `200` ("the request went through"), but there is no data. This case comes from the address `…/latest/XXX` (`XXX` is a currency code that does not exist)
(we observed the value `unsupported-code` on this API on 2026-11-27; the documentation has `result` and `error-type`). We point the video's `fetchRate` at this address — `_video/07-xato200/main.go`:


## Going deeper (optional): reusing the client, Timeout and LimitReader

This part is not needed for the main idea, but it appears in working code. Three rules:

1. **Do not create a client on every call.** Reuse one client: the connections opened to the server are kept inside it and reused. The documentation says so
   (*"Clients should be reused instead of created as needed"*) and also calls calling it from several places at once safe. That is why `run` creates one `client` and passes it to `fetchRate`.
2. **`Timeout` is a limit on the whole request.** According to the documentation it includes the connection, redirects and **reading the response body**. A separate deadline for each request is given with `context`, in [GB-7.03](/lab/youtube/gb#gb-7-03).
3. **Do not trust the response size of an external server.** `io.LimitReader` reads from the body at most the given number of bytes:

```go
	body := io.LimitReader(resp.Body, 1<<20) // 1 MB
	if err := json.NewDecoder(body).Decode(&data); err != nil {
```

`1<<20` shifts one 20 bits to the left: `1048576` bytes, that is, 1 megabyte. `io.LimitReader(resp.Body, 1<<20)` is `resp.Body` itself, but after the first megabyte it says "end".
`Decode` now reads from `body`. If the JSON value itself is longer than one megabyte, `Decode` cannot read it to the end and returns an error: the code will not fill memory with an endlessly large response.
You apply this in step 3 of the homework.

## Common mistakes

**1. "`err == nil` means the response is a success."** The most widespread misconception. We saw above: even for a `404 Not Found` response, `err` is `nil` (the section "The second silent failure" above).
`err` only says the request was not carried out; it says nothing about the content of the response. Fix: after the `err` check, check `resp.StatusCode` too.

**2. `defer resp.Body.Close()` before the error check.** The most common mistake in code. The broken version is `_video/06-vet/main.go`:

```go filename="_video/06-vet/main.go" showLineNumbers
package main

import (
	"fmt"
	"net/http"
	"os"
	"time"
)

func main() {
	client := &http.Client{Timeout: 5 * time.Second}
	resp, err := client.Get("https://open.er-api.com/v6/latest/USD")
	defer resp.Body.Close()
	if err != nil {
		fmt.Fprintln(os.Stderr, "xato:", err)
		os.Exit(1)
	}
	fmt.Println(resp.Status)
}
```

In line 13, `defer resp.Body.Close()` comes **before** the `if err != nil` of line 14. If `Get` returns an error, `resp` is `nil`, and reading `Body` from `nil` crashes the program with a panic.
`go vet` ([GB-1.04](/lab/youtube/gb/gb-1-04/en)) finds it before the program even runs. Think first: what does `go vet` say?

<details>
<summary>Answer</summary>

It names the line with the mistake and the reason: `main.go:13:8` — line 13, column 8 (the `resp` in `resp.Body`), the reason: `resp` was used without checking the error. The exact words are below.

</details>

```console
$ cd _video/06-vet && go vet .
main.go:13:8: using resp before checking for errors
```

`main.go:13:8` — file, line, column; `using resp before checking for errors` — "`resp` was used before checking for errors". Fix: write `defer` **after** the `if err != nil { … }` block,
as in `fetchRate`.
