## What you will learn

A handler panics before writing a response. The client receives a closed connection, and the server log makes the request hard to identify. How can every request get an ID, a status and an access log entry?

**The one idea:** middleware takes an `http.Handler` and returns another `http.Handler`. Its returned function remembers `next`; code before and after `next.ServeHTTP` surrounds the wrapped handler. Code after `next` runs only if that call returns normally.

By the end, you will:

- write a handler wrapper and record method, path, status and duration;
- recover a handler panic into a 500 JSON response before the response starts;
- add a request ID and build the chain in the order that preserves the access log.

| Word | Plain meaning | English term |
|---|---|---|
| middleware | a function that adds work around another handler | middleware |
| panic recovery | stopping a panic in the current request and producing a controlled response | panic recovery |
| chain order | which wrapper runs before which handler, and where normal execution resumes | middleware chain |

Two helper terms appear when needed: **embedding** is a field declared using its type without a separate name. A **request ID** identifies one request in the response and server log.

## A panic before the response

For the demonstration only, insert this after `pathID` succeeds in `getProduct` in `cmd/api/handlers.go`. `id == 13` selects the test request; `panic` interrupts normal execution. The runner does this in a copy.

```go

		panic("sinov: 13-mahsulotda bug")
	}
```

Without our recovery layer, `net/http` recovers a panic from `ServeHTTP`, writes a **stack trace** showing the active function calls, and closes an HTTP/1 connection. HTTP/2 resets the stream. This does not mean the entire server process stops. See the [Handler contract](https://pkg.go.dev/net/http#Handler).

Predict `/products/13`, then `/products/1`: **A)** 500 JSON, then a product · **B)** empty reply, then a product · **C)** both connections fail.

<details>
<summary>Answer</summary>

**B.** There is no application recovery yet. The server handles the failed request, but it does not invent our JSON error response. **A** assumes that recovery already writes it; **C** confuses the active request with the server process.

</details>

## The middleware shape and a closure

We need the same request logging around every route. This first version is the complete `_video/v1-log/middleware.go` file. To inspect it manually, use it as `cmd/api/middleware.go` in a copy of the course folder. The runner already makes that copy.

```go filename="_video/v1-log/middleware.go" showLineNumbers
package main

// _video/v1-log: birinchi logRequests — status hali yoʻq (video: shakl-kod).

import (
	"log"
	"net/http"
	"time"

	"github.com/abdurahmon27/bozor/internal/store"
)

func newHandler(st *store.Store) http.Handler {
	return logRequests(newMux(st))
}

func logRequests(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)
		log.Printf("%s %q %s", r.Method, r.URL.Path, time.Since(start))
	})
}
```

| Line | Code | What it does |
|---|---|---|
| 1, 3 | `package main`, `// …` | joins the executable's package; the comment names the demonstration step |
| 5–11 | `import (…)` | imports logging, HTTP, time and the existing internal store package |
| 13–15 | `newHandler(st *store.Store)` | receives the store pointer, builds a mux, returns the wrapped handler |
| 17 | `func logRequests(next http.Handler) http.Handler` | receives the wrapped handler as `next`; returns a handler |
| 18 | `return http.HandlerFunc(func(…) {` | converts the anonymous function to `HandlerFunc`, whose `ServeHTTP` method satisfies `http.Handler`; `w` writes the response and `r` points to the request |
| 19 | `start := time.Now()` | creates a local variable holding this request's start time |
| 20 | `next.ServeHTTP(w, r)` | runs the wrapped handler synchronously, with this writer and request |
| 21 | `log.Printf(…)` | writes method (`%s`), quoted path (`%q`) and elapsed duration (`%s`); `time.Since(start)` measures the interval |
| 22–23 | `})`, `}` | closes the anonymous function, conversion call and outer function |

The anonymous function is a **closure**: it keeps access to `next` after `logRequests` returns. Building a wrapper and serving a request happen at different times.

| Moment | State | Action |
|---|---|---|
| server construction | `next = mux` | `logRequests(mux)` returns a handler once |
| first request | a new local `start` | returned handler runs `start → next → log` |
| next request | another local `start`, same `next` | returned handler runs again |

`newServer` assigns `Handler: newHandler(st)` in `cmd/api/main.go`. Merely defining middleware does not connect it to the server.

**A.** The format string has only three fields. `ResponseWriter` has no method for asking which status was sent. **B** requires recording it ourselves; **C** is wrong because a 404 handler returns normally.

</details>

## Recording status and the zero trap

The video starts with this simpler writer wrapper:

```go
type statusRecorder struct {
	http.ResponseWriter
	status int
}

func (rec *statusRecorder) WriteHeader(code int) {
	rec.status = code
	rec.ResponseWriter.WriteHeader(code)
}
```

`http.ResponseWriter` is an embedded field. Its field name is `ResponseWriter`; methods such as `Header` and `Write` are promoted to the outer type. Our own `WriteHeader` takes precedence. Its pointer receiver `rec *statusRecorder` modifies the same struct, so we pass `&statusRecorder{…}`. The resulting `*statusRecorder` satisfies `http.ResponseWriter`.

`rec.status = code` remembers the status. `rec.ResponseWriter.WriteHeader(code)` calls the inner writer's method and sends the status onward. Calling `rec.WriteHeader(code)` there would recurse into the same method.

The first attempt leaves `status` at its zero value:

```go
rec := &statusRecorder{ResponseWriter: w}
next.ServeHTTP(rec, r)
log.Printf("%s %q %d %s", r.Method, r.URL.Path, rec.status, time.Since(start))
```

Predict the access-log status for `/health`, whose handler only calls `Fprintln`: **A)** 200 · **B)** 0 · **C)** 404.

<details>
<summary>Answer</summary>

**B: 0 in this historical wrapper.** The promoted `Write` calls the inner writer. That writer supplies an implicit 200; it never calls our outer `WriteHeader`. **A** is the client's status, but not the saved field; **C** would mean a missing route.

</details>

```console
$ curl -sS -s localhost:8765/health
ok
```

Fresh logs from `_video/v3-nol`:

```text
2026/11/27 22:04:42 GET "/products/99" 404 155.427µs
```

| Step in the simple wrapper | `rec.status` | Client response |
|---|---|---|
| create `rec` | 0 | not started |
| `/health` calls promoted `Write` | still 0 | inner writer selects 200 |
| `/products/99` calls our `WriteHeader(404)` | 404 | inner writer sends 404 |


## Panic recovery and the wrong order

This is the recovery function from `_video/v4-tartib`, before the folder's additional guards:

```go
func recoverPanic(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		defer func() {
			if v := recover(); v != nil {
				log.Printf("panic: %v\n%s", v, debug.Stack())
				writeError(w, http.StatusInternalServerError, apiError{Code: "internal", Message: "ichki xato"})
			}
		}()
		next.ServeHTTP(w, r)
	})
}
```

Line 1 keeps the middleware shape. Line 2 returns the request handler. Line 3 registers a deferred anonymous function. Line 4 calls `recover` directly inside it and assigns the panic value to `v`; without a panic, `v` is `nil`. Lines 5–6 log the value and write a generic 500 JSON error. `%v` formats the panic value, `\n` inserts a newline, and `debug.Stack()` from `runtime/debug` returns this goroutine's stack trace. `ichki xato` means “internal error”. The final `}()` calls the deferred function when unwinding; `next.ServeHTTP` runs the inner handler.

The panic text stays in the server log. The client gets the existing `apiError` shape, not the stack. Recovery applies to the current goroutine: it cannot catch a panic in a goroutine started by the handler.

First try the wrong order:

```go
return recoverPanic(logRequests(newMux(st)))
```

`recoverPanic` is outside `logRequests`. The logger writes its access entry after `next` returns normally. Predict `/products/13`: **A)** panic trace and access entry · **B)** panic trace only · **C)** access entry only.

<details>
<summary>Answer</summary>

**B.** Panic unwinds through the logger before the outer recovery stops it. Execution does not return to the line after `next` inside the unwound logger. **A** needs recovery inside logging; **C** ignores our explicit panic log.

</details>

```console
$ curl -sS -i localhost:8765/products/13

Content-Type: application/json
Date: Fri, 27 Nov 2026 17:04:43 GMT
Content-Length: 53

{"error":{"code":"internal","message":"ichki xato"}}
```

Fresh shortened log, with no access entry:

```text
2026/11/27 22:04:43 panic: sinov: 13-mahsulotda bug
goroutine 21 [running]:
…
main.logRequests.func1(…)
…
main.recoverPanic.func1(…)

```

| Order | Panic path | Code after the logger's `next` |
|---|---|---|
| `recoverPanic(logRequests(mux))` | handler → mux → logger → recovery | skipped |
| `logRequests(recoverPanic(mux))` | handler → mux → recovery; recovery returns to logger | runs, records 500 |

`main.logRequests.func1` is the anonymous function created inside `logRequests`. A stack trace shows active calls; read the caller relationship from the inner frame toward the outer one.

## One request ID across the response and logs

To find both entries for one failed request, add an ID before running the other middleware:

```go
func requestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("X-Request-Id", rand.Text())
		next.ServeHTTP(w, r)
	})
}
```

Line 3 generates a new value with `crypto/rand.Text()` and sets the response header. Line 4 calls `next`. In Go 1.27.4 the generated text has 26 base32 characters; the API guarantees at least 128 bits of randomness and permits longer output in future versions. `Text` was added in Go 1.24. This is a correlation ID, not an authentication credential. See [rand.Text](https://pkg.go.dev/crypto/rand#Text).

The server generates the ID instead of trusting an incoming client value. Both logging functions read `w.Header().Get("X-Request-Id")`. The wrapper's promoted `Header()` accesses the same header map as the inner writer.

| Stage | Header map | Use |
|---|---|---|
| `requestID` | sets `X-Request-Id` | creates the request's ID |
| `recoverPanic` | reads the same map | prefixes the panic entry |
| `logRequests` | reads the same map | prefixes the access entry |
| response | sends that header | client can report the same ID |

Keep the header stable in downstream handlers. Passing the ID into handler logs through `context` is taught in [GB-8.02 · structured logs and request IDs](/lab/youtube/gb#gb-8-02).

<details>
<summary>Answer</summary>

**B.** Construction is `newMux → recoverPanic → logRequests → requestID`. A request enters from the outside: `requestID → logRequests → recoverPanic → mux → route handler`. **A** mixes construction with serving; **C** skips the wrappers.

```go filename="cmd/api/middleware.go" showLineNumbers
package main

// Middleware (GB-6.01). Har biri bitta shaklda: http.Handler oladi (next) va uni oʻragan yangi
// http.Handler qaytaradi. Qaytgan handler oʻz ishini qiladi va next.ServeHTTP'ni chaqiradi:
// chaqiruvdan oldingi kod soʻrov handler'ga yetguncha, keyingi kod javob yozilgandan keyin ishlaydi.

import (
	"crypto/rand"
	"log"
	"net/http"
	"runtime/debug"
	"time"

	"github.com/abdurahmon27/bozor/internal/store"
)

// newHandler — server'ga beriladigan butun zanjir. Tashqaridan ichkariga:
// requestID → logRequests → recoverPanic → mux → handler.
// Tartib muhim: recoverPanic logRequests'ning ichida boʻlsin, aks holda panic boʻlgan soʻrov
// log'ga tushmaydi (panic logRequests'ning log qatoridan oʻtib ketadi).
func newHandler(st *store.Store) http.Handler {
	// VAZIFA (TASK.md, 1-qadam): requireJSON'ni shu zanjirga qoʻshing.
	return requestID(logRequests(recoverPanic(newMux(st))))
}

// requestID har soʻrovga tasodifiy ID beradi va uni javobning X-Request-Id sarlavhasiga yozadi.
// Mijoz xato haqida shu ID bilan xabar beradi, biz log'dan aynan shu soʻrovni topamiz.
// Mijoz yuborgan X-Request-Id'ga ishonmaymiz: ID'ni har doim server oʻzi yasaydi.
func requestID(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("X-Request-Id", rand.Text())
		next.ServeHTTP(w, r)
	})
}

// statusRecorder — ResponseWriter'ni oʻrab, handler yozgan status kodni eslab qoladi.
// http.ResponseWriter maydon nomisiz (embedding): Header ichkaridagi writer'niki.
// Birinchi yakuniy status esda qoladi: WriteHeader orqali yoki Write'dagi yashirin 200.
type statusRecorder struct {
	http.ResponseWriter
	status      int
	wroteHeader bool
}

func (rec *statusRecorder) WriteHeader(code int) {
	if rec.wroteHeader {
		// net/http ortiqcha WriteHeader haqida oʻzi ogohlantiradi; status oʻzgarmaydi.
		rec.ResponseWriter.WriteHeader(code)
		return
	}
	rec.ResponseWriter.WriteHeader(code)
	if code >= 100 && code < 200 && code != http.StatusSwitchingProtocols {
		return // 1xx vaqtinchalik javob; yakuniy status hali keladi.
	}
	rec.status = code
	rec.wroteHeader = true
}

func (rec *statusRecorder) Write(b []byte) (int, error) {
	if !rec.wroteHeader {
		rec.status = http.StatusOK
		rec.wroteHeader = true
	}
	return rec.ResponseWriter.Write(b) // ichki Write 200 va Content-Type'ni oʻzi tanlaydi.
}

// Unwrap ichkaridagi asl writer'ni qaytaradi: http.ResponseController (Flush va boshqalar)
// oʻralgan writer orqali ham ishlashi uchun (go doc net/http.NewResponseController).
func (rec *statusRecorder) Unwrap() http.ResponseWriter {
	return rec.ResponseWriter
}

// logRequests har soʻrovdan keyin bitta qator yozadi: ID, metod, yoʻl, status, vaqt.
// status 200'dan boshlanadi: handler WriteHeader'ni chaqirmay Write qilsa, javob 200 boʻladi (GB-4.03),
// Write birinchi yashirin 200'ni ham eslab qoladi (videodagi soddaroq variantdan farqi).
// Yoʻl %q bilan: mijoz yoʻlga yangi qator (%0A) yashirib, log'ga soxta qator qoʻsha olmaydi.
func logRequests(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
		next.ServeHTTP(rec, r)
		log.Printf("%s %s %q %d %s", w.Header().Get("X-Request-Id"),
			r.Method, r.URL.Path, rec.status, time.Since(start))
	})
}

// recoverPanic — GB-2.09'dagi safely, har soʻrov uchun: handler'dagi panic'ni toʻxtatadi,
// stack'ni log'ga yozadi va mijozga 500 + bizning JSON xato shaklini qaytaradi.
// Videodagidan ikki farq (README, «recoverPanic: videodan tashqari ikki himoya»):
//   - http.ErrAbortHandler — "javobni ataylab uz" degan panic (go doc net/http.ErrAbortHandler):
//     uni toʻxtatmaymiz, net/http'ning oʻziga qaytaramiz;
//   - handler javobni yozishni boshlagan boʻlsa (status yoki body ketgan), 500'ni yuborib boʻlmaydi:
//     yarim javob oxiriga JSON qoʻshilib qoladi. Shunda panic'ni log'ga yozib, javobni ErrAbortHandler
//     bilan uzamiz: mijoz buzuq 200 emas, uzilgan javob oladi. Bu holda logRequests qatori yozilmaydi,
//     panic qatori esa ID bilan logda bor.
//
// Eslatma: handler oʻzi ishga tushirgan goroutine'dagi panic'ni bu middleware ushlamaydi (u boshqa
// goroutine'ning stack'ida; recover faqat panic qilgan goroutine'da ishlaydi) — bunday panic butun serverni yiqitadi.
func recoverPanic(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		sw := &startWriter{ResponseWriter: w}
		defer func() {
			if v := recover(); v != nil {
				if v == http.ErrAbortHandler {
					panic(v)
				}
				log.Printf("%s panic: %v\n%s", w.Header().Get("X-Request-Id"), v, debug.Stack())
				if sw.started {
					panic(http.ErrAbortHandler)
				}
				writeError(w, http.StatusInternalServerError, apiError{Code: "internal", Message: "ichki xato"})
			}
		}()
		next.ServeHTTP(sw, r)
	})
}

// startWriter javob boshlanganini (WriteHeader yoki Write chaqirilganini) eslab qoladi: recoverPanic uchun.
type startWriter struct {
	http.ResponseWriter
	started bool
}

func (sw *startWriter) WriteHeader(code int) {
	sw.started = true
	sw.ResponseWriter.WriteHeader(code)
}

func (sw *startWriter) Write(b []byte) (int, error) {
	sw.started = true
	return sw.ResponseWriter.Write(b)
}

func (sw *startWriter) Unwrap() http.ResponseWriter {
	return sw.ResponseWriter
}

// requireJSON — VAZIFA (TASK.md, 1-qadam): POST soʻrovida Content-Type application/json
// boʻlmasa — 415 va bizning xato shaklimiz. Hozircha hech narsa tekshirmaydi.
func requireJSON(next http.Handler) http.Handler {
	return next
}

// muxErrors — 🟡 ixtiyoriy (TASK.md, 2-qadam): mux'ning oʻz 404/405 javoblarini JSON qilish.
// Hozircha mux'ni oʻzgarishsiz qaytaradi.
func muxErrors(mux *http.ServeMux) http.Handler {
	return mux
}
```

Only the additions to the earlier examples need explanation:

| Lines | What changes |
|---|---|
| 8, 11 | import `crypto/rand` and `runtime/debug` for IDs and stack traces |
| 21–34 | connect the full chain; set the ID before `next` |
| 39–64 | `wroteHeader` is a boolean recording the first final status. `WriteHeader` forwards but does not replace an existing status. `Write` records an implicit 200, then delegates directly so content detection still works |
| 52–54 | 100–199 are informational responses, so they do not finish status recording; 101 switches protocols and is treated as committed |
| 69–70 | `Unwrap` exposes the inner writer to `http.NewResponseController` |
| 79–83 | create a fresh recorder per request, pass it to `next`, log ID, method, quoted path, status and elapsed time |
| 101–114 | `sw` is a `startWriter`; `defer` recovers, preserves `ErrAbortHandler`, logs the panic, checks whether writing started, then writes 500 only when possible |
| 119–135 | `started` begins as `false`; `WriteHeader` and `Write` set it to `true` and delegate. `[]byte`, `(int, error)` and the returned pair follow the writer contract |
| 140–147 | `requireJSON` and `muxErrors` currently return their inputs unchanged; implementing and connecting them is the task |

`http.ErrAbortHandler` is the special panic value that tells `net/http` to abort the response without another stack log. If a response already started, a new 500 cannot replace its status or body. The folder logs the panic and aborts instead of appending error JSON to a partial response. On that path, and on a deliberate abort, the access-log line is skipped. The normal 500-and-access-log result above applies to a panic before the response starts.

`Unwrap` supports `ResponseController` operations such as flushing; embedding the `ResponseWriter` interface does not automatically preserve optional interfaces such as `http.Flusher`.

## Common mistakes

**Assuming a writer's status field follows the network automatically.** The zero-status run above is a silent logging bug: HTTP succeeds with 200, but the saved field is 0. Initialize the default and record the first explicit or implicit status, as in the full folder file. Repeated `WriteHeader` does not change the first status already sent.

**Putting recovery outside logging.** The wrong-order experiment above returns 500 but loses the access entry. Put `recoverPanic` inside `logRequests` so normal execution returns to the logger.

**Calling the request header field as a method.** This complete extra program is outside the course folder. Save it as `header-error.go` in a separate scratch folder:

```go
package main

import "net/http"

func main() {
	r, _ := http.NewRequest("GET", "http://localhost/health", nil)
	_ = r.Header().Get("Content-Type")
}
```

```console
$ go run header-error.go
# command-line-arguments
./header-error.go:7:6: invalid operation: cannot call r.Header (variable of map type http.Header): http.Header is not a function
```

`./header-error.go:7:6` identifies file, line and column. “Cannot call” means that `r.Header` is a map field, not a function. `# command-line-arguments` labels the temporary package built from the named file. Fix line 7 to `_ = r.Header.Get("Content-Type")`. `w.Header()` is a method on a response writer; `r.Header` is a request field. `_` discards a value; the successful request construction here does not require using its error result.

**Writing an error, then continuing.** In `requireJSON`, return after writing 415. Otherwise the inner handler also writes a response; the first status stays, and `net/http` can report `superfluous response.WriteHeader call` (“an extra call”). Do not try to repair a response that already started by appending a second JSON object.
