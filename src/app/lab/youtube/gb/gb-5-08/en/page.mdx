## What you will learn

One apricot remains. Two buyers click Buy, and both receive success. The database reports stock `0`, with no error. Where did the second decrement go?

**The one idea:** a transaction alone does not protect a separate read, check and write from another buyer. Put the stock condition in the `UPDATE`, or lock the row before reading it for a decision.

By the end you will:

- reproduce a **lost update** in two database connections;
- combine the stock check and decrement in one conditional `UPDATE`;
- use `SELECT … FOR UPDATE` through `tx` and explain who waits;
- verify concurrent buyers and fix the coupon exercise.

| Word | Plain meaning | English term |
|---|---|---|
| lost update | two buyers calculate from the same old stock; one decrement disappears | lost update |
| conditional UPDATE | check and change a row in one SQL statement | conditional UPDATE |
| row lock | conflicting writes and locking reads wait for the transaction to finish | row-level lock |

**Overselling** means accepting more purchases than the available stock. `CommandTag` is the result description returned by `Exec`; `RowsAffected()` reads its row count.

Open `docker compose exec db psql` in two terminals in the lab folder. Each is a separate database connection, called a session. In the transcript, `[A]` and `[B]` identify the session; do not type these prefixes into SQL.

| Step | A | B | Committed stock |
|---|---|---|---|
| 1 | `BEGIN`; read `1` | | `1` |
| 2 | | `BEGIN`; read `1` | `1` |
| 3 | writes the calculated `0`; `COMMIT` | still remembers `1` | `0` |
| 4 | | writes its calculated `0`; `COMMIT` | `0` |

Both applications decide that one unit is available. A commits before B writes. What does B's `UPDATE products SET stock = 0 WHERE id = 4` return?

**A)** error because the row changed · **B)** `UPDATE 1` · **C)** waits for A.

<details>
<summary>Answer</summary>

**B.** The row still matches `id=4`, and assigning zero is valid. There is no condition testing the previously read stock. A has already committed, so B does not wait for A. Option A assumes an automatic stale-read check that this statement does not request.

</details>

## Why BEGIN does not fix the read-check-write sequence

Postgres defaults to **READ COMMITTED**, the isolation level governing visibility between transactions. An ordinary `SELECT` sees other transactions' data committed before that query began. It also sees earlier writes from its own transaction.

B read before A committed. Its next `UPDATE` is a new statement, but `SET stock = 0` still writes the value computed from B's old Go variable. It never recomputes the decrement from the database value. In READ COMMITTED, a conflicting updater can wait and then process a newer row version; we use that rule in the next section.

This is a lost update in the database, related to GB-4.07's lost update in memory. It is not evidence of a Go memory data race: Go's race detector does not check this SQL business rule.

The shipped demonstration is the complete `naive.go`. It is part of package `bozor`, alongside `Store` and its error values in `store.go`; it is not a standalone `main` program.

```go filename="naive.go" showLineNumbers
package bozor

import (
	"context"
	"errors"

	"github.com/jackc/pgx/v5"
)

// buyNaive — videoning birinchi, XATO versiyasi: transaction bor, lekin oʻqish va yozish orasida qulf yoʻq.
// Ikki xaridor bir xil eski qoldiqni oʻqib, ikkalasi ham yozadi (lost update). Faqat koʻrsatish uchun (naive_test.go): ishlatmang.
func (s *Store) buyNaive(ctx context.Context, id int64, qty int) error {
	tx, err := s.pool.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx)

	var stock int
	err = tx.QueryRow(ctx,
		"SELECT stock FROM products WHERE id = $1", id).Scan(&stock)
	if errors.Is(err, pgx.ErrNoRows) {
		return ErrNotFound
	}
	if err != nil {
		return err
	}
	if stock < qty {
		return ErrNotEnoughStock
	}
	_, err = tx.Exec(ctx,
		"UPDATE products SET stock = $1 WHERE id = $2", stock-qty, id)
	if err != nil {
		return err
	}
	return tx.Commit(ctx)
}
```

| Line | Code | What it does |
|---|---|---|
| 1, 3–8 | `package`, `import` | joins package `bozor`; imports context, error inspection and pgx |
| 10–12 | comment and `buyNaive` | demonstration method; `s *Store` is the receiver, `id` the product, `qty` the number of units |
| 13–17 | `Begin`, error branch, deferred rollback | reserves one connection for `tx`; returns a begin error; schedules rollback for every exit |
| 19–21 | `var stock int`; `QueryRow(...).Scan(&stock)` | reads one stock value into the address `&stock`; `$1` is `id` |
| 22–27 | `errors.Is`; `if err != nil` | maps no row to `ErrNotFound`; returns any other read error |
| 28–30 | `stock < qty` | returns `ErrNotEnoughStock` if the remembered stock is insufficient |
| 31–32 | `_, err = tx.Exec(...)` | discards the command tag with `_`; writes `stock-qty` as `$1`, `id` as `$2` |
| 33–36 | error branch; `tx.Commit(ctx)` | returns a write error or commits; commit errors reach the caller |

Blank lines and `//` comments have no runtime effect. `:=` creates variables; `=` assigns existing ones. Dots select methods; parentheses call them, braces enclose blocks, and `return` leaves the method. These spellings come from the prerequisite lessons.

`buyNaive` deliberately demonstrates positive purchases only; it lacks the `qty <= 0` guard. Both final methods reject invalid quantities. A transaction makes this buyer's writes succeed or roll back together; it does not reserve the previously read stock for that buyer.

## Fix 1: check and decrement in one UPDATE

The rule fits one SQL condition:

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 4 AND stock >= 1;
```

`SET` calculates from the row's current stock. `AND` requires both the matching id and at least one unit. An `UPDATE` holds a row lock against conflicting writers until its transaction finishes. An unmatched row is not updated.

Reset stock to one. A begins and decrements, but leaves its transaction open. B submits the same conditional statement and waits. After A commits, what does B report?

**A)** `UPDATE 1`, stock `-1` · **B)** `UPDATE 0` · **C)** CHECK error.

<details>
<summary>Answer</summary>

**B.** After waiting, Postgres rechecks `WHERE` against the updated row. Stock is zero, so `stock >= 1` is false. Nothing is decremented. A ignores the condition; C assumes the decrement happens before the row qualifies.

</details>

The Go method from `store.go`, shown as a fragment:

```go
func (s *Store) Buy(ctx context.Context, id int64, qty int) error {
	if qty <= 0 {
		return ErrInvalidQuantity
	}
	tag, err := s.pool.Exec(ctx,
		"UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1", qty, id)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 0 {
		return ErrNotEnoughStock
	}
	return nil
}
```

`qty <= 0` returns `ErrInvalidQuantity` before SQL. `Exec` returns `tag`, a `CommandTag`, and `err`. Return SQL errors first; then inspect `tag.RowsAffected()`. Zero means no row was updated. Here we assume the product exists and return `ErrNotEnoughStock`; an unknown id also gives zero.

`$1` occurs twice but is one parameter, `qty`. `$2` is `id`. `nil` reports success. This single statement already runs in an implicit transaction, so no explicit `Begin` is needed for this isolated stock decrement. A full order with several writes still needs the transaction from GB-5.07.

## Fix 2: SELECT FOR UPDATE inside tx

If a decision requires reading the row into Go first, lock it during that read:

```sql
SELECT stock FROM products WHERE id = 4 FOR UPDATE;
```

`FOR UPDATE` locks the selected row. Another transaction's writes or conflicting locking reads wait. An **ordinary SELECT remains allowed** and reads visible committed data. The lock does not make every reader wait.

| Step | A | B |
|---|---|---|
| 1 | `BEGIN`; locking read returns `1` | `BEGIN` |
| 2 | holds row lock | `SELECT … FOR UPDATE` waits |
| 3 | writes `0`; `COMMIT` | waits until A ends |
| 4 | finished | locks the updated row and reads `0`; rejects purchase |

Predict B's locking read after A commits: **A)** old `1` · **B)** current `0` · **C)** always an error.

<details>
<summary>Answer</summary>

**B** in this READ COMMITTED experiment. The read waits and then returns the updated row. The Go check sees insufficient stock. With different isolation levels, a concurrent change can instead require retrying the transaction.

</details>

Here is the complete final `store.go`, including both approaches. Its original comment on line 45 says another buyer cannot read the row. Read that as “cannot perform the conflicting locking read”: ordinary SELECT is allowed.

```go filename="store.go" showLineNumbers
package bozor

import (
	"context"
	"errors"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

// ErrNotFound — jadvalda bunday mahsulot yoʻq (GB-2.08, GB-5.05).
var ErrNotFound = errors.New("mahsulot topilmadi")

// ErrNotEnoughStock — omborda yetarli qoldiq yoʻq (GB-5.07).
var ErrNotEnoughStock = errors.New("qoldiq yetarli emas")

// ErrInvalidQuantity — miqdor noldan katta boʻlishi kerak (GB-5.07: manfiy miqdor qoldiqni oshirib yuborar edi).
var ErrInvalidQuantity = errors.New("miqdor noldan katta boʻlishi kerak")

// Store — Postgres'dagi bozor jadvallariga Go'dan kirish (GB-5.05).
type Store struct {
	pool *pgxpool.Pool
}

// Buy id mahsulotdan qty dona sotadi. Tekshiruv va kamaytirish bitta UPDATE buyrugʻida:
// "WHERE stock >= $1" shart bajarilmasa qator oʻzgarmaydi va RowsAffected() nol boʻladi.
// Bu darsda id mavjud deb faraz qilinadi: nol qator "qoldiq yetmaydi" degani (mavjud boʻlmagan id ham nol qator beradi;
// ikkisini ajratish uchun alohida SELECT kerak, BuyLocked esa ErrNoRows orqali ErrNotFound beradi).
func (s *Store) Buy(ctx context.Context, id int64, qty int) error {
	if qty <= 0 {
		return ErrInvalidQuantity
	}
	tag, err := s.pool.Exec(ctx,
		"UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1", qty, id)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 0 {
		return ErrNotEnoughStock
	}
	return nil
}

// BuyLocked ham sotadi, lekin boshqacha: avval qatorni FOR UPDATE bilan qulflaydi, qoldiqni Go'da tekshiradi,
// keyin yozadi. Qulf transaction tugaguncha turadi, shuning uchun boshqa xaridorning FOR UPDATE'i yoki UPDATE'i shu qatorni kutadi (oddiy SELECT kutmaydi).
func (s *Store) BuyLocked(ctx context.Context, id int64, qty int) error {
	if qty <= 0 {
		return ErrInvalidQuantity
	}
	tx, err := s.pool.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx)

	var stock int
	err = tx.QueryRow(ctx,
		"SELECT stock FROM products WHERE id = $1 FOR UPDATE", id).Scan(&stock)
	if errors.Is(err, pgx.ErrNoRows) {
		return ErrNotFound
	}
	if err != nil {
		return err
	}
	if stock < qty {
		return ErrNotEnoughStock
	}
	_, err = tx.Exec(ctx,
		"UPDATE products SET stock = $1 WHERE id = $2", stock-qty, id)
	if err != nil {
		return err
	}
	return tx.Commit(ctx)
}
```

The shared declarations on lines 1–23 import the packages, construct three sentinel error values with `errors.New`, and define `Store` with `pool *pgxpool.Pool`. `ErrNotFound` means “product not found”, `ErrNotEnoughStock` means “insufficient stock”, and `ErrInvalidQuantity` requires a positive quantity. Each is one error value that callers recognize with `errors.Is`. Lines 29–42 are the conditional method just explained.

Only the new parts of `BuyLocked`:

| Line | Code | What it does |
|---|---|---|
| 46–49 | method and quantity guard | same inputs and invalid-quantity rule as `Buy` |
| 50–54 | `Begin`; deferred rollback | keeps reading and writing on one transaction connection |
| 56–58 | `tx.QueryRow(... FOR UPDATE).Scan(&stock)` | acquires the lock and reads the stock |
| 59–64 | no-row and other error branches | maps `pgx.ErrNoRows` to `ErrNotFound`; preserves other failures |
| 65–67 | stock check | rejects the purchase while still holding the row lock |
| 68–72 | `tx.Exec`; error check | writes the stock computed under the lock |
| 73 | `tx.Commit(ctx)` | confirms the write and ends the transaction |

Every early return after `Begin` reaches the deferred rollback. A successful commit also ends the transaction; the later deferred rollback returns `ErrTxClosed`, which this pattern ignores.

## Choosing a method and a shared boundary

| Requirement | Choice | Cost or limitation |
|---|---|---|
| rule fits `stock >= qty` | conditional UPDATE | zero rows does not distinguish absent product from insufficient stock |
| read data, decide in Go, write | `FOR UPDATE` in one transaction | holds a lock while Go makes the decision; keep the transaction short |
| write stock and complete an order | put the chosen rule in the order transaction | all related writes must use the same `tx` |

Two application servers each have their own `sync.Mutex`. Does this prevent the database bug? **A)** yes · **B)** only within each process · **C)** only with the race detector.

<details>
<summary>Answer</summary>

**B.** A Go mutex coordinates goroutines sharing that mutex in one process. The other server has a different mutex. The database rule must coordinate both servers. The race detector cannot enforce an SQL stock condition.

</details>

## Common mistakes

**1. Sending FOR UPDATE through the pool.** This is the classic silent bug. After `tx := … Begin`, replace only the read in `BuyLocked` with:

```go
var stock int
err = s.pool.QueryRow(ctx,
	"SELECT stock FROM products WHERE id = $1 FOR UPDATE", id).Scan(&stock)
```

This is the fragment from `_video/stages/04-store-pool-mistake.go`. `pool.QueryRow` uses a separate connection rather than the connection reserved by `tx`. Its implicit transaction ends with that statement; the row lock is released before the later `tx.Exec`. Writing the words `FOR UPDATE` therefore does not protect the whole operation.

Predict the test: **A)** PASS because FOR UPDATE appears · **B)** FAIL, too many successes · **C)** always panic.

<details>
<summary>Answer</summary>

**B** in our run. The statement is valid, so no SQL syntax error or panic is required. The read's lock does not cover the write in the other transaction.

</details>

In the previous fresh stock-test copy replace `store.go` with `_video/stages/04-store-pool-mistake.go` and run:

```console
$ go test

    --- FAIL: TestConcurrentBuyers/BuyLocked (0.12s)
        store_test.go:172: 1-urinish: 20 xaridor, omborda 5 ta: 20 tasiga "olindi" dedik; kutilgan: 5
FAIL
exit status 1
FAIL	github.com/abdurahmon27/bozor	0.397s
```

The assertion at `store_test.go:172` expected five but received 20. The video recorded `0.381s`; this run `0.397s`. **Fix:** both read and write must use `tx`, as in the complete final file. Our tests use a pool of 40 connections; with 20 buyers and a smaller pool, this mistake can also exhaust connections because each buyer holds one and requests another.

**2. Treating BEGIN as a stock reservation.** The naive example already showed this silent failure. Lock before reading, or combine the condition and decrement.

**3. Assuming CHECK alone catches a stale absolute write.** Both buyers assigning zero pass `CHECK (stock >= 0)`. An unguarded *relative* decrement below zero does fail. The helper's `check` scenario first sets stock to zero; its complete output is:

```console
$ python3 _video/sessions.py check

stock 
-------
     1
(1 row)

[A] UPDATE products SET stock = stock - 1 WHERE id = 4;
ERROR:  new row for relation "products" violates check constraint "products_stock_check"
DETAIL:  Failing row contains (4, oʻrik, 3500000, -1, t).

oxirgi: stock

```

`violates check constraint` means the new row breaks the named rule. `DETAIL` shows the rejected row: product 4, apricot, price `3500000` tiyin, stock `-1`, active `t` (true). The failed statement leaves stock zero. Keep the constraint as a final safeguard; use the conditional rule for an expected “insufficient stock” result.

**4. Holding locks during unrelated work.** Finish the transaction promptly; avoid network calls while a stock row is locked. When locking several products, acquire them in a consistent order to reduce deadlocks, where transactions wait on one another. Postgres aborts one deadlocked transaction, so the caller must handle that error.

**1.** What does `RowsAffected() == 0` tell you?

The statement updated zero rows. For this SQL, either the id is absent or the stock condition failed. `Buy` assumes an existing id and returns `ErrNotEnoughStock`; the coupon task asks you to distinguish the reasons.

**2.** When does the FOR UPDATE lock end in `BuyLocked`? Can an ordinary SELECT read meanwhile?

<details>

The lock lasts until the transaction commits or rolls back along these code paths. Ordinary SELECT can read visible committed data while the row lock is held. Conflicting writers and locking readers wait.

```go filename="solution/coupon.go" showLineNumbers
package bozor

import (
	"context"
	"errors"

	"github.com/jackc/pgx/v5"
)

// ErrCouponUsedUp — promo-kodning ishlatish soni tugagan.
var ErrCouponUsedUp = errors.New("promo-kod tugagan")

// ErrCouponNotFound — bunday promo-kod yoʻq.
var ErrCouponNotFound = errors.New("promo-kod topilmadi")

// UseCoupon promo-kodni bir marta ishlatadi: coupons.uses_left bittaga kamayadi.
// Tekshiruv va kamaytirish bitta UPDATE buyrugʻida (WHERE uses_left > 0): parallel chaqiruvlarda ham roppa-rosa uses_left marta oʻtadi.
func (s *Store) UseCoupon(ctx context.Context, code string) error {
	tag, err := s.pool.Exec(ctx,
		"UPDATE coupons SET uses_left = uses_left - 1 WHERE code = $1 AND uses_left > 0", code)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 1 {
		return nil
	}
	// Nol qator: promo-kod yoʻq yoki tugagan. Qaysi biri ekanini alohida oʻqib bilamiz.
	var left int
	err = s.pool.QueryRow(ctx,
		"SELECT uses_left FROM coupons WHERE code = $1", code).Scan(&left)
	if errors.Is(err, pgx.ErrNoRows) {
		return ErrCouponNotFound
	}
	if err != nil {
		return err
	}
	return ErrCouponUsedUp
}

var errUseCouponLockedTODO = errors.New("UseCouponLocked hali yozilmagan")

// UseCouponLocked ham promo-kodni ishlatadi, lekin boshqacha: qatorni FOR UPDATE bilan qulflaydi, Go'da tekshiradi, keyin yozadi.
func (s *Store) UseCouponLocked(ctx context.Context, code string) error {
	tx, err := s.pool.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx)

	var left int
	err = tx.QueryRow(ctx,
		"SELECT uses_left FROM coupons WHERE code = $1 FOR UPDATE", code).Scan(&left)
	if errors.Is(err, pgx.ErrNoRows) {
		return ErrCouponNotFound
	}
	if err != nil {
		return err
	}
	if left == 0 {
		return ErrCouponUsedUp
	}
	_, err = tx.Exec(ctx,
		"UPDATE coupons SET uses_left = $1 WHERE code = $2", left-1, code)
	if err != nil {
		return err
	}
	return tx.Commit(ctx)
}
```

New names: `code` identifies the coupon, `left` holds remaining uses, `ErrCouponUsedUp` means “coupon exhausted”, and `ErrCouponNotFound` means “coupon not found”. Lines 19–26 perform the guarded decrement and return success. Lines 28–37 classify the zero-row result. Lines 44–67 repeat the transaction pattern, with `left == 0` checked under the row lock. Line 40 keeps the original optional-stub error value for the checker; the implemented method no longer returns it.

</details>
