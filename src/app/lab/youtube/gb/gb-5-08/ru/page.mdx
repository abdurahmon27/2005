## Что вы узнаете

Остался один абрикос. Два покупателя нажали «Купить», и оба получили успех. В базе остаток `0`, ошибки нет. Куда исчезло второе уменьшение?

**Одна идея:** сама транзакция не защищает отдельные чтение, проверку и запись от другого покупателя. Добавьте условие остатка в `UPDATE` или заблокируйте строку перед чтением для принятия решения.

После урока вы:

- воспроизведёте **потерянное обновление** (lost update) в двух соединениях с базой;
- объедините проверку и уменьшение остатка в одном условном `UPDATE`;
- примените `SELECT … FOR UPDATE` через `tx` и объясните, кто ждёт;
- проверите параллельных покупателей и исправите задачу с промокодом.

| Слово | Простой смысл | Английский термин |
|---|---|---|
| потерянное обновление | два покупателя вычисляют из одного старого остатка; одно уменьшение исчезает | lost update |
| условный UPDATE | проверка и изменение строки одной командой SQL | conditional UPDATE |
| блокировка строки | конфликтующие записи и чтения с блокировкой ждут завершения транзакции | row-level lock |

**Лишние продажи** (overselling) — принятие большего числа покупок, чем позволяет остаток. `CommandTag` — описание результата, возвращаемое `Exec`; `RowsAffected()` получает из него число строк.


```console
$ docker compose exec db psql -c "SELECT name, stock FROM products WHERE id = 4"

-------+-------
```

`UPDATE … SET` присваивает значение столбцу; `WHERE id = 4` выбирает товар. `UPDATE 1` считает одну обновлённую строку, в том числе строку, которой присвоили её прежнее значение. Это не число проданных единиц. В таблице — название товара, остаток и `(1 row)`, одна строка.

В двух терминалах в папке лаборатории откройте `docker compose exec db psql`. Каждый — отдельное соединение с базой, то есть сеанс. В журнале `[A]` и `[B]` обозначают сеанс; не вводите эти префиксы вместе с SQL.

| Шаг | A | B | Подтверждённый остаток |
|---|---|---|---|
| 1 | `BEGIN`; прочитал `1` | | `1` |
| 2 | | `BEGIN`; прочитал `1` | `1` |
| 3 | записал вычисленный `0`; `COMMIT` | ещё помнит `1` | `0` |
| 4 | | записал свой вычисленный `0`; `COMMIT` | `0` |

Оба приложения решают, что одна единица доступна. A подтверждает запись раньше B. Что вернёт команда B `UPDATE products SET stock = 0 WHERE id = 4`?

**A)** ошибку, потому что строка изменилась · **B)** `UPDATE 1` · **C)** будет ждать A.

<details>
<summary>Ответ</summary>

**B.** Строка по-прежнему соответствует `id=4`, а записать ноль допустимо. Условия проверки ранее прочитанного остатка нет. A уже завершил транзакцию, поэтому B его не ждёт. Вариант A предполагает автоматическую проверку устаревшего чтения, которую эта команда не запрашивает.

</details>

## Почему BEGIN не исправляет чтение–проверку–запись

По умолчанию Postgres использует **READ COMMITTED** — уровень изоляции, определяющий видимость между транзакциями. Обычный `SELECT` видит данные других транзакций, подтверждённые до начала этого запроса. Он также видит предыдущие записи собственной транзакции.

B прочитал остаток до подтверждения A. Следующий `UPDATE` — новая команда, но `SET stock = 0` всё ещё записывает значение из старой переменной Go у B. Уменьшение не пересчитывается от значения в базе. В READ COMMITTED конфликтующее обновление может подождать и обработать более новую версию строки. В следующем разделе используем это правило.

Это потерянное обновление в базе, связанное с потерянным обновлением в памяти из GB-4.07. Оно не доказывает гонку данных в памяти Go: race detector Go не проверяет это бизнес-правило SQL.

Ниже полный демонстрационный `naive.go`. Он входит в пакет `bozor` вместе со `Store` и значениями ошибок из `store.go`; это не отдельная программа `main`.

```go filename="naive.go" showLineNumbers
package bozor

import (
	"context"
	"errors"

	"github.com/jackc/pgx/v5"
)

// buyNaive — videoning birinchi, XATO versiyasi: transaction bor, lekin oʻqish va yozish orasida qulf yoʻq.
// Ikki xaridor bir xil eski qoldiqni oʻqib, ikkalasi ham yozadi (lost update). Faqat koʻrsatish uchun (naive_test.go): ishlatmang.
func (s *Store) buyNaive(ctx context.Context, id int64, qty int) error {
	tx, err := s.pool.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx)

	var stock int
	err = tx.QueryRow(ctx,
		"SELECT stock FROM products WHERE id = $1", id).Scan(&stock)
	if errors.Is(err, pgx.ErrNoRows) {
		return ErrNotFound
	}
	if err != nil {
		return err
	}
	if stock < qty {
		return ErrNotEnoughStock
	}
	_, err = tx.Exec(ctx,
		"UPDATE products SET stock = $1 WHERE id = $2", stock-qty, id)
	if err != nil {
		return err
	}
	return tx.Commit(ctx)
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1, 3–8 | `package`, `import` | входит в пакет `bozor`; импортирует context, проверку ошибок и pgx |
| 10–12 | комментарий и `buyNaive` | демонстрационный метод; `s *Store` — получатель, `id` — товар, `qty` — число единиц |
| 13–17 | `Begin`, ветка ошибки, отложенный rollback | занимает одно соединение для `tx`; возвращает ошибку начала; назначает rollback при любом выходе |
| 19–21 | `var stock int`; `QueryRow(...).Scan(&stock)` | читает один остаток по адресу `&stock`; `$1` — это `id` |
| 22–27 | `errors.Is`; `if err != nil` | преобразует отсутствие строки в `ErrNotFound`; возвращает остальные ошибки чтения |
| 28–30 | `stock < qty` | возвращает `ErrNotEnoughStock`, если запомненного остатка недостаточно |
| 31–32 | `_, err = tx.Exec(...)` | отбрасывает описание результата через `_`; записывает `stock-qty` как `$1`, `id` как `$2` |
| 33–36 | ветка ошибки; `tx.Commit(ctx)` | возвращает ошибку записи или подтверждает транзакцию; ошибка commit доходит до вызывающего кода |

Пустые строки и комментарии `//` не выполняются. `:=` создаёт переменные; `=` присваивает существующим. Точка выбирает метод; круглые скобки вызывают его, фигурные ограничивают блок, `return` завершает метод. Это синтаксис из предыдущих уроков.

`buyNaive` намеренно показывает только положительное количество; проверки `qty <= 0` в нём нет. Оба итоговых метода отклоняют неверное количество. Транзакция подтверждает или откатывает записи этого покупателя вместе; она не резервирует для него ранее прочитанный остаток.

Тест запускает 20 покупателей при остатке 5. Центральный цикл, сокращённый из вспомогательной функции курса:

```go
errs := make([]error, 20)
var wg sync.WaitGroup
for i := range errs {
	wg.Go(func() {
		errs[i] = store.Buy(ctx, 4, 1)
	})
}
wg.Wait()
```

`make([]error, 20)` выделяет 20 ячеек результатов. `i` — индекс ячейки; `wg.Go` запускает функцию в горутине. Каждая пишет только в `errs[i]`. У каждой итерации отдельный `i`. `wg.Wait()` ждёт всех покупателей. Вызывающий код считает `nil` успехом и допускает `ErrNotEnoughStock` для отказов. Полностью `WaitGroup` разбирается в [GB-7.01](/lab/youtube/gb#gb-7-01).

Сколько успехов может сообщить наивный метод? **A)** всегда 5 · **B)** больше 5, вплоть до 20 · **C)** всегда panic.

<details>
<summary>Ответ</summary>

**B.** Несколько покупателей могут прочитать один остаток до первой записи. В видео получилось 20, в этой проверке тоже 20. Порядок выполнения меняет число; последовательность SQL выше объясняет ошибку без опоры на длительности. Транзакция не делает ответ A автоматическим, а корректный SQL не обязан вызывать panic.

</details>

## Исправление 1: проверка и уменьшение одним UPDATE

Правило помещается в одно условие SQL:

```sql
UPDATE products
SET stock = stock - 1
WHERE id = 4 AND stock >= 1;
```

`SET` вычисляет из текущего остатка строки. `AND` требует и совпадения id, и наличия хотя бы одной единицы. `UPDATE` удерживает блокировку строки против конфликтующих записей до завершения транзакции. Несоответствующая строка не обновляется.

Восстановите остаток один. A начинает транзакцию и уменьшает остаток, но оставляет её открытой. B отправляет ту же условную команду и ждёт. Что вернёт B после подтверждения A?

**A)** `UPDATE 1`, остаток `-1` · **B)** `UPDATE 0` · **C)** ошибку CHECK.

<details>
<summary>Ответ</summary>

**B.** После ожидания Postgres повторно проверяет `WHERE` на обновлённой строке. Остаток ноль, поэтому `stock >= 1` ложно. Ничего не уменьшается. A игнорирует условие; C предполагает уменьшение до проверки соответствия строки.

</details>

`shartli` выбирает этот сценарий. Программа проверяет, что B не выдаёт результат две секунды до подтверждения A. `kutyapti = True` означает «ждёт»; эту строку выводит помощник, а не Postgres.

```console

-------

(1 row)

[A] BEGIN;
BEGIN

[A] UPDATE products SET stock = stock - 1 WHERE id = 4 AND stock >= 1;

[B] UPDATE products SET stock = stock - 1 WHERE id = 4 AND stock >= 1;
(2 soniya javob yoʻq: kutyapti = True)
```

| Момент | A | B | Остаток по подтверждённым изменениям |
|---|---|---|---|
| A обновил | держит блокировку; неподтверждённый `0` | | `1` |
| B обновляет | ещё открыт | ждёт A | `1` |
| A подтвердил | освободил блокировку | перепроверил `0 >= 1`; обновил ноль строк | `0` |

Метод Go из `store.go`, показанный фрагментом:

```go
func (s *Store) Buy(ctx context.Context, id int64, qty int) error {
	if qty <= 0 {
		return ErrInvalidQuantity
	}
	tag, err := s.pool.Exec(ctx,
		"UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1", qty, id)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 0 {
		return ErrNotEnoughStock
	}
	return nil
}
```

`qty <= 0` возвращает `ErrInvalidQuantity` до SQL. `Exec` возвращает `tag`, то есть `CommandTag`, и `err`. Сначала верните ошибку SQL, затем проверьте `tag.RowsAffected()`. Ноль означает отсутствие обновлённых строк. Здесь считаем, что товар существует, и возвращаем `ErrNotEnoughStock`; неизвестный id тоже даст ноль.

`$1` встречается дважды, но это один параметр — `qty`. `$2` — `id`. `nil` сообщает об успехе. Одна команда уже выполняется в неявной транзакции, поэтому для изолированного уменьшения остатка явный `Begin` не нужен. Полный заказ с несколькими записями по-прежнему требует транзакции из GB-5.07.

## Исправление 2: SELECT FOR UPDATE внутри tx

Если для решения сначала нужно прочитать строку в Go, заблокируйте её при чтении:

```sql
SELECT stock FROM products WHERE id = 4 FOR UPDATE;
```

`FOR UPDATE` блокирует выбранную строку. Записи или конфликтующие чтения с блокировкой из другой транзакции ждут. **Обычный SELECT остаётся разрешённым** и читает видимые подтверждённые данные. Блокировка не заставляет ждать всех читателей.

| Шаг | A | B |
|---|---|---|
| 1 | `BEGIN`; чтение с блокировкой вернуло `1` | `BEGIN` |
| 2 | держит блокировку строки | `SELECT … FOR UPDATE` ждёт |
| 3 | записал `0`; `COMMIT` | ждёт завершения A |
| 4 | завершён | блокирует обновлённую строку, читает `0`; отклоняет покупку |

Предскажите чтение B после подтверждения A: **A)** старое `1` · **B)** текущее `0` · **C)** всегда ошибка.

<details>
<summary>Ответ</summary>

**B** в этом эксперименте с READ COMMITTED. Чтение ждёт, затем возвращает обновлённую строку. Проверка в Go видит недостаточный остаток. При других уровнях изоляции параллельное изменение может потребовать повторить транзакцию.

</details>

`forupdate` запускает настоящие сеансы. Здесь B подтверждает транзакцию после чтения; в Go возврат `ErrNotEnoughStock` приводит к отложенному rollback.

Полный итоговый `store.go` включает оба подхода. Исходный комментарий на строке 45 говорит, что другой покупатель не может прочитать строку. Понимайте это как «не может выполнить конфликтующее чтение с блокировкой»: обычный SELECT разрешён.

```go filename="store.go" showLineNumbers
package bozor

import (
	"context"
	"errors"

	"github.com/jackc/pgx/v5"
	"github.com/jackc/pgx/v5/pgxpool"
)

// ErrNotFound — jadvalda bunday mahsulot yoʻq (GB-2.08, GB-5.05).
var ErrNotFound = errors.New("mahsulot topilmadi")

// ErrNotEnoughStock — omborda yetarli qoldiq yoʻq (GB-5.07).
var ErrNotEnoughStock = errors.New("qoldiq yetarli emas")

// ErrInvalidQuantity — miqdor noldan katta boʻlishi kerak (GB-5.07: manfiy miqdor qoldiqni oshirib yuborar edi).
var ErrInvalidQuantity = errors.New("miqdor noldan katta boʻlishi kerak")

// Store — Postgres'dagi bozor jadvallariga Go'dan kirish (GB-5.05).
type Store struct {
	pool *pgxpool.Pool
}

// Buy id mahsulotdan qty dona sotadi. Tekshiruv va kamaytirish bitta UPDATE buyrugʻida:
// "WHERE stock >= $1" shart bajarilmasa qator oʻzgarmaydi va RowsAffected() nol boʻladi.
// Bu darsda id mavjud deb faraz qilinadi: nol qator "qoldiq yetmaydi" degani (mavjud boʻlmagan id ham nol qator beradi;
// ikkisini ajratish uchun alohida SELECT kerak, BuyLocked esa ErrNoRows orqali ErrNotFound beradi).
func (s *Store) Buy(ctx context.Context, id int64, qty int) error {
	if qty <= 0 {
		return ErrInvalidQuantity
	}
	tag, err := s.pool.Exec(ctx,
		"UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1", qty, id)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 0 {
		return ErrNotEnoughStock
	}
	return nil
}

// BuyLocked ham sotadi, lekin boshqacha: avval qatorni FOR UPDATE bilan qulflaydi, qoldiqni Go'da tekshiradi,
// keyin yozadi. Qulf transaction tugaguncha turadi, shuning uchun boshqa xaridorning FOR UPDATE'i yoki UPDATE'i shu qatorni kutadi (oddiy SELECT kutmaydi).
func (s *Store) BuyLocked(ctx context.Context, id int64, qty int) error {
	if qty <= 0 {
		return ErrInvalidQuantity
	}
	tx, err := s.pool.Begin(ctx)
	if err != nil {
		return err
	}
	defer tx.Rollback(ctx)

	var stock int
	err = tx.QueryRow(ctx,
		"SELECT stock FROM products WHERE id = $1 FOR UPDATE", id).Scan(&stock)
	if errors.Is(err, pgx.ErrNoRows) {
		return ErrNotFound
	}
	if err != nil {
		return err
	}
	if stock < qty {
		return ErrNotEnoughStock
	}
	_, err = tx.Exec(ctx,
		"UPDATE products SET stock = $1 WHERE id = $2", stock-qty, id)
	if err != nil {
		return err
	}
	return tx.Commit(ctx)
}
```

Общие объявления на строках 1–23 импортируют пакеты, создают три значения ошибок (sentinel-ошибки) через `errors.New` и определяют `Store` с `pool *pgxpool.Pool`. `ErrNotFound` — товар не найден, `ErrNotEnoughStock` — недостаточный остаток, `ErrInvalidQuantity` требует положительное количество. Каждая — отдельное значение ошибки, которое вызывающий код распознаёт через `errors.Is`. Строки 29–42 — уже разобранный условный метод.

Только новые части `BuyLocked`:

| Строка | Код | Что делает |
|---|---|---|
| 46–49 | метод и проверка количества | те же входы и правило неверного количества, что у `Buy` |
| 50–54 | `Begin`; отложенный rollback | сохраняет чтение и запись на одном соединении транзакции |
| 56–58 | `tx.QueryRow(... FOR UPDATE).Scan(&stock)` | получает блокировку и читает остаток |
| 59–64 | ветки отсутствия строки и других ошибок | заменяет `pgx.ErrNoRows` на `ErrNotFound`; сохраняет остальные ошибки |
| 65–67 | проверка остатка | отклоняет покупку, ещё удерживая блокировку строки |
| 68–72 | `tx.Exec`; проверка ошибки | записывает остаток, вычисленный под блокировкой |
| 73 | `tx.Commit(ctx)` | подтверждает запись и завершает транзакцию |

При любом раннем выходе после `Begin` выполняется отложенный rollback. Успешный commit тоже завершает транзакцию; последующий отложенный rollback возвращает `ErrTxClosed`, который этот шаблон игнорирует.

## Частые ошибки

**1. Отправить FOR UPDATE через пул.** Это классическая тихая ошибка. После `tx := … Begin` замените только чтение в `BuyLocked` на:

```go
var stock int
err = s.pool.QueryRow(ctx,
	"SELECT stock FROM products WHERE id = $1 FOR UPDATE", id).Scan(&stock)
```

Это фрагмент из `_video/stages/04-store-pool-mistake.go`. `pool.QueryRow` использует отдельное соединение вместо соединения, занятого `tx`. Его неявная транзакция завершается вместе с командой; блокировка строки снимается до последующего `tx.Exec`. Поэтому наличие слов `FOR UPDATE` не защищает всю операцию.

Предскажите тест: **A)** PASS, ведь FOR UPDATE написан · **B)** FAIL, слишком много успехов · **C)** всегда panic.

<details>
<summary>Ответ</summary>

**B** в нашем запуске. Команда корректна, поэтому синтаксическая ошибка SQL или panic не обязательны. Блокировка чтения не охватывает запись в другой транзакции.

</details>

```go filename="solution/coupon.go" showLineNumbers
	}
	if left == 0 {
		return ErrCouponUsedUp
	}
	_, err = tx.Exec(ctx,
		"UPDATE coupons SET uses_left = $1 WHERE code = $2", left-1, code)
	if err != nil {
		return err
	}
	return tx.Commit(ctx)
}
```

Новые имена: `code` определяет промокод, `left` хранит оставшиеся использования, `ErrCouponUsedUp` означает «промокод исчерпан», `ErrCouponNotFound` — «промокод не найден». Строки 19–26 выполняют защищённое уменьшение и возвращают успех. Строки 28–37 классифицируют результат с нулём строк. Строки 44–67 повторяют шаблон транзакции с проверкой `left == 0` под блокировкой строки. Строка 40 сохраняет исходную ошибку необязательной заглушки для проверяющего кода; реализованный метод больше её не возвращает.

</details>
