## Что вы узнаете

Каждый ваш сервис отвечает быстрее секунды на 99 запросов из 100. И всё же 63 % страниц открываются дольше секунды.
Как так? Второй вопрос: вы поменяли кнопку, и покупок стало на 10 % больше. Это победа или шум? Сегодня ответим на
оба вопроса симуляцией на Go и расчётом вручную.

**Одна идея:** немного математики (проценты и степень) меняет инженерное решение. Средняя задержка прячет хвост, а
маленький A/B-тест выдаёт шум за победу. В этом направлении каждая тема подаётся через одну картинку, один расчёт
вручную и один код. Расчёт и код должны совпасть, а допущение проверяет только реальное измерение.

К концу урока вы:

- посчитаете вручную через `1 − 0.99ᴺ` долю медленных страниц, когда страница параллельно шлёт N запросов, и будете
  знать, когда эта формула не работает;
- будете сравнивать релизы не по среднему, а по p50 и p99;
- оцените по стандартной ошибке, шум ли разница в A/B-тесте, и найдёте нужный размер групп по `n = 16σ²/Δ²`;
- узнаете, какие из шести модулей направления «Математика для инженеров» нужны именно вам и что можно пропустить.

Три главных новых слова сегодня:

| Слово | Простой смысл | Английский термин |
|---|---|---|
| p99 | время, быстрее которого (или равно) завершаются 99 % запросов. Самый медленный 1 % сверх него — **хвост** | percentile, tail |
| независимые события | одно из них не меняет вероятность другого; тогда вероятности перемножаются | independent events |
| стандартная ошибка | размер случайного шума: насколько обычно сдвинется результат, если повторить тот же эксперимент | standard error |

Есть и два вспомогательных слова. **A/A-тест** — тест, в котором обе группы видят ровно одно и то же: любая «победа»
в нём — шум. **z-тест** — правило: делим разницу на стандартную ошибку и говорим «разница есть», если получилось
больше 1.96.

Вопрос из GO-1.06. Функция `mediana` из того урока находила средний элемент времён ответа сервера. Времена: 10, 50 и
90 мс. Теперь запрос на 90 мс стал 9000 мс. Как изменятся медиана и среднее?

**A)** оба вырастут примерно в 100 раз · **B)** медиана останется 50 мс, среднее вырастет с 50 до 3020 мс ·
**C)** медиана вырастет, среднее почти не изменится

<details>
<summary>Ответ</summary>

**B.** Отсортированный список `[10 50 9000]`, его середина по-прежнему 50. А среднее — (10 + 50 + 9000) / 3 = 3020 мс.
Один медленный запрос увеличил среднее в 60 раз, а медиану не сдвинул. Одно число не показывает форму распределения:
сегодня увидим и обратное — среднее выглядит *хорошо*, а хвост плохой. Если вы выбрали «A», вы думали, что медиана,
как и среднее, смотрит на все значения.

</details>

## Страница из 100 запросов: как 1 % превращается в 63 %

Страница (или API gateway) на один запрос пользователя параллельно шлёт 100 запросов внутренним сервисам и ждёт ответа
от всех. Время параллельного ожидания
равно времени самого медленного ответа. Проверим на Go с тремя запросами (этого файла нет в папке курса, мы написали
его для этой страницы: сохраните его как `kutish.go` в пустой папке):

```go filename="kutish.go" showLineNumbers
// kutish: sahifa uchta so'rovni parallel kutadi.
package main

import (
	"fmt"
	"sync"
	"time"
)

func main() {
	boshi := time.Now()
	var wg sync.WaitGroup
	for _, ms := range []int{10, 20, 1000} {
		wg.Go(func() { time.Sleep(time.Duration(ms) * time.Millisecond) }) // bitta so'rov
	}
	wg.Wait() // hammasini kutadi
	fmt.Printf("sahifa: %d ms\n", time.Since(boshi).Milliseconds())
}
```

| Строка | Код | Что делает |
|---|---|---|
| 13–15 | `wg.Go(func() { time.Sleep(…) })` | запускает каждый «запрос» в своей горутине; здесь запрос — просто пауза 10, 20 или 1000 мс |
| 16 | `wg.Wait()` | ждёт, пока все закончатся |
| 17 | `time.Since(boshi)` | время с начала |

```console
$ go run kutish.go
sahifa: 1000 ms
```

Три запроса: 10, 20 и 1000 мс. Страница («sahifa») ждала 1000 мс (при втором запуске так же). Два
быстрых запроса не помогли: страница ждёт **самый медленный**.

```text
           ┌─ запрос 1:   23 мс ─┐
           ├─ запрос 2:   41 мс ─┤
страница ──┼─ запрос 3: 1730 мс ─┼──▶ страница готова: max(...) = 1730 мс
           ├─    …               │
           └─ запрос 100: 17 мс ─┘
```

Теперь наша модель. Каждый запрос в 99 случаях из 100 отвечает за 10–50 мс, а в 1 случае из 100 — за 1–3 секунды.
Страница шлёт 100 таких запросов.

Предскажите: какая доля страниц откроется дольше секунды?

**A)** ~1 % · **B)** ~10 % · **C)** ~63 %

<details>
<summary>Ответ</summary>

**C.** Симуляция на Go посчитала 100 000 страниц:

```console
$ go run ./fanout
so'rovlar: 1 s dan sekini  1.00 %
sahifalar (100 so'rovli): 1 s dan sekini 63.5 %
qo'lda hisob: 1 - 0.99^100 = 63.4 %
```

Медленных запросов («so'rovlar») 1.00 %, а медленных страниц («sahifalar») — 63.5 %. Последняя строка — расчёт
вручную («qo'lda hisob»). Если вы выбрали «A», вы посчитали страницу как один запрос. Но в странице 100 запросов, и
достаточно, чтобы медленным оказался *один*. «B» тоже мало: очень трудно, чтобы ни в одном из 100 розыгрышей не выпала
неудача с вероятностью 1 %.

</details>

### Расчёт вручную: почему вероятности перемножаются

Вероятность, что один запрос быстрый, — 0.99. Если запросы не зависят друг от друга, то есть **независимы**,
вероятность «все быстрые» равна произведению отдельных вероятностей (Stanford CS109, *Independence*):

| Шаг | Расчёт | Результат |
|---|---|---|
| 1 запрос быстрый | 0.99 | 99 % |
| 2 запроса тоже быстрые | 0.99 · 0.99 = 0.99² | 98.0 % |
| все 100 запросов быстрые | 0.99¹⁰⁰ | ≈ 0.366, то есть ~37 % |
| хотя бы один медленный | 1 − 0.99¹⁰⁰ | ≈ 0.634, то есть **63.4 %** |

Программа `fanout` выводит тот же ручной расчёт в последней строке своего вывода («qo'lda hisob»).

Симуляция — 63.5 %, формула — 63.4 %: разница случайная. Этот пример взят из статьи инженеров Google Джеффа Дина и
Луиса Баррозу (Jeff Dean, Luiz Barroso, *The Tail at Scale*, CACM 2013, с. 76): «If a user request must collect
responses from 100 such servers in parallel, then 63% of user requests will take more than one second» (если запрос
пользователя должен собрать ответы от 100 таких серверов параллельно, 63 % запросов займут больше секунды).

**Важное условие: независимость.** В жизни медленность часто связана. Одна пауза GC (сборщик мусора ненадолго
останавливает программу) или один перегруженный сетевой switch замедляет сразу несколько запросов. Дин и Баррозу тоже
называют сборку мусора и общие ресурсы среди причин медленности. Наш код тоже написан с допущением независимости.
Поэтому совпадение кода и формулы проверяет только арифметику: формула показывает направление, а допущение проверяет
реальное измерение. Что будет, если медленность связана, измерим в разделе «Частые ошибки».

## Код: симуляция `fanout`

Программа очень простая: функция `sorov` («запрос») возвращает время одного запроса, внутренний цикл находит самый
медленный из 100 запросов, внешний повторяет это для 100 000 страниц.

```go filename="fanout/main.go" showLineNumbers
// fanout: bitta sahifa N ta so'rovni parallel yuboradi va eng sekin javobni kutadi.
// Har bir so'rov yuztadan bitta holatda 1 soniyadan sekin. Sahifalarning qanchasi sekin?
// So'rovlar bir-biriga bog'liq emas (mustaqil) deb olinadi: hayotda bu har doim ham rost emas.
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
	"os"
	"strconv"
)

const sahifalar = 100_000

// sorov: 99 % hollarda 10..50 ms, 1 % hollarda 1..3 soniya.
func sorov(r *rand.Rand) float64 {
	if r.Float64() < 0.01 {
		return 1000 + 2000*r.Float64()
	}
	return 10 + 40*r.Float64()
}

func main() {
	N := 100
	if len(os.Args) > 1 {
		if os.Args[1] == "jadval" { // 1 - 0.99^N, turli N uchun
			for _, n := range []int{1, 10, 20, 50, 100, 200, 500} {
				fmt.Printf("N = %3d: %5.1f %% sahifa sekin\n", n, 100*(1-math.Pow(0.99, float64(n))))
			}
			return
		}
		n, err := strconv.Atoi(os.Args[1])
		if err != nil || n < 1 {
			fmt.Fprintln(os.Stderr, "foydalanish: go run ./fanout [N >= 1 | jadval]")
			os.Exit(2)
		}
		N = n
	}
	r := rand.New(rand.NewPCG(1, 2))
	sekinSorov, sekinSahifa := 0, 0
	for range sahifalar {
		eng := 0.0
		for range N {
			t := sorov(r)
			if t >= 1000 {
				sekinSorov++
			}
			eng = max(eng, t) // sahifa eng sekin javobni kutadi
		}
		if eng >= 1000 {
			sekinSahifa++
		}
	}
	fmt.Printf("so'rovlar: 1 s dan sekini %5.2f %%\n", 100*float64(sekinSorov)/float64(sahifalar*N))
	fmt.Printf("sahifalar (%d so'rovli): 1 s dan sekini %4.1f %%\n", N, 100*float64(sekinSahifa)/sahifalar)
	fmt.Printf("qo'lda hisob: 1 - 0.99^%d = %.1f %%\n", N, 100*(1-math.Pow(0.99, float64(N))))
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1–3 | комментарии | что делает программа и главное допущение: запросы независимы |
| 6–12 | `import (…)` | `math` — `math.Pow` (степень); `math/rand/v2` — генератор случайных чисел; `os` — аргументы и код выхода; `strconv` — превращение текста в число |
| 14 | `const sahifalar = 100_000` | сколько страниц («sahifalar») считаем. `_` — разделитель только для чтения: `100_000` = 100000 |
| 17 | `func sorov(r *rand.Rand) float64` | принимает генератор и возвращает время одного запроса в миллисекундах. `*rand.Rand` — указатель на генератор: все вызовы используют один генератор, а не его копию (указатели — GO-1.11) |
| 18 | `if r.Float64() < 0.01` | `r.Float64()` — случайное число от 0 до 1, все значения равновероятны. Меньше 0.01 — это 1 случай из 100 |
| 19 | `return 1000 + 2000*r.Float64()` | медленный случай: от 1000 до 3000 мс |
| 21 | `return 10 + 40*r.Float64()` | быстрый случай: от 10 до 50 мс |
| 25 | `N := 100` | по умолчанию страница шлёт 100 запросов |
| 26 | `if len(os.Args) > 1` | есть ли аргумент в командной строке (`os.Args[0]` — сама программа) |
| 27–32 | `if os.Args[1] == "jadval"` | («таблица») печатает `1 − 0.99ᴺ` для семи значений N и выходит через `return`. `%3d` — целое на 3 позиции, `%5.1f` — число с одним знаком после точки, `%%` — сам знак `%` |
| 33 | `n, err := strconv.Atoi(os.Args[1])` | превращает аргумент в целое число. Если не получилось, `err` не пустой |
| 34–37 | `if err != nil \|\| n < 1 { … os.Exit(2) }` | не число или меньше 1: печатает подсказку об использовании в stderr и выходит с кодом 2 |
| 38 | `N = n` | число запросов страницы теперь из аргумента |
| 40 | `r := rand.New(rand.NewPCG(1, 2))` | генератор PCG, seed `(1, 2)`. Постоянный seed — каждый раз один и тот же результат |
| 41 | `sekinSorov, sekinSahifa := 0, 0` | два счётчика: медленные запросы и медленные страницы |
| 42 | `for range sahifalar` | внешний цикл: 100 000 раз, каждый раз одна страница |
| 43 | `eng := 0.0` | («самый») самый медленный ответ этой страницы, пока 0 |
| 44 | `for range N` | внутренний цикл: N запросов страницы |
| 45–48 | `t := sorov(r)`, `if t >= 1000` | время одного запроса; если дольше секунды, `sekinSorov` растёт на один |
| 49 | `eng = max(eng, t)` | `max` — встроенная функция Go (с Go 1.21). При параллельных запросах время страницы — время самого медленного |
| 51–53 | `if eng >= 1000` | если самый медленный ответ страницы дольше секунды, страница медленная |
| 55 | `100*float64(sekinSorov)/float64(sahifalar*N)` | доля медленных запросов в процентах. `float64(…)` превращает целое в дробное: иначе деление дало бы целое |
| 56 | `100*float64(sekinSahifa)/sahifalar` | доля медленных страниц |
| 57 | `math.Pow(0.99, float64(N))` | расчёт вручную: `1 − 0.99ᴺ` |

Программа на самом деле не шлёт запросы параллельно: она только случайно выбирает времена. При параллельных запросах
время страницы равно самому медленному ответу, поэтому `max` достаточно. Горутины не нужны.

## В сервисе Google: от 10 мс до 140 мс

Дин и Баррозу измерили и настоящий сервис Google (таблица Table 1 в статье). Это уже не наша модель, а реальная
система:

| Измерение (на root-сервере) | p99 |
|---|---|
| завершение одного случайного запроса | 10 мс |
| завершение всех запросов | 140 мс |

p99 одного запроса — 10 мс, а страница ждёт все, поэтому 140 мс. Решение вытекает из того же расчёта: хвост нельзя
убрать совсем, но его можно обойти. Если ответ задерживается, тот же запрос отправляют ещё и на другую копию
(replica) и берут тот ответ, что пришёл первым. Статья называет это **hedged requests**.

В их тесте читали 1000 значений со 100 серверов. Подождать 10 мс, а потом отправить hedge — это снизило p99.9 (самую
медленную тысячную долю) **с 1800 мс до 74 мс**. А запросов стало всего на **2 %** больше. Вот математика,
превратившаяся в решение: если знаешь, откуда берётся хвост, его можно срезать дёшево.

## Среднее, медиана и p99

Теперь уточним термины. `p50`, `p95`, `p99` на панели Grafana или другого мониторинга — это они.

| Мера | Определение | Расчёт в нашем коде |
|---|---|---|
| среднее (mean) | сумма всех времён / число запросов | `sum/n` |
| **медиана** (p50) | середина отсортированного списка: половина быстрее неё | `percentil(xs, 0.50)` |
| **p99** | 99 % запросов быстрее него или равны ему | `percentil(xs, 0.99)` |
| **хвост** (tail) | самый медленный 1 %, медленнее p99 | — |

Саму медиану мы писали в GO-1.06 (`mediana`). Там бралось `xs[len/2]`. А сегодняшний `percentil` работает методом
«ближайшего ранга» (*nearest rank*): в отсортированном `xs` берётся `xs[ceil(p·n) − 1]`. При чётном n вариант из GO-1.06
выбирает верхний средний элемент, наш — нижний; на 100 000 запросов разница незаметна (README курса).

Книга Google по SRE предупреждает: «the 99th percentile of one backend can easily become the median response of
your frontend» (p99 одного бэкенда легко становится медианой ответа фронтенда). Мы это только что увидели: медленны
1 % запросов, но большинство страниц из 100 запросов.

Маленький пример: 96 запросов по 8 мс, 4 — по 400 мс. `percentil` — та же функция, что в `latency/main.go` ниже
(этого файла нет в папке курса; сохраните его как `ortacha.go` в пустой папке):

```go filename="ortacha.go" showLineNumbers
// ortacha: 96 ta so'rov 8 ms, 4 tasi 400 ms. O'rtacha, mediana va p99.
package main

import (
	"fmt"
	"math"
)

// percentil: latency/main.go dagi funksiyaning o'zi (xs tartiblangan bo'lishi kerak)
func percentil(xs []float64, p float64) float64 {
	k := int(math.Ceil(p*float64(len(xs)))) - 1
	return xs[max(k, 0)]
}

func main() {
	var xs []float64
	for range 96 {
		xs = append(xs, 8)
	}
	for range 4 {
		xs = append(xs, 400)
	}
	var sum float64
	for _, x := range xs {
		sum += x
	}
	fmt.Println(sum/float64(len(xs)), percentil(xs, 0.50), percentil(xs, 0.99))
}
```

```console
$ go run ortacha.go
23.68 8 400
```

Среднее — 23.68 мс: такого запроса вообще нет. Медиана — 8 мс, p99 — 400 мс. Среднее «размазывает» хвост: не видно, что 4 % пользователей ждали 400 мс.

## Какой релиз быстрее? Среднее прячет хвост

Теперь — как это знание меняет решение. Это **синтетическая модель**: числа выбрали мы, а форма — реальная. Есть
два релиза:

| Релиз | Каждый запрос | Примерное время |
|---|---|---|
| `eski` («старый») | каждый раз идёт в базу | ~35 мс |
| `kesh` («кэш») | 96 % запросов из кэша; 4 % нет в кэше, они идут медленным путём (холодный диск, тяжёлый запрос) | ~8 мс или ~400 мс |

Предскажите: какой релиз лучше?

**A)** `kesh`: меньше и среднее, и медиана · **B)** `eski`: если смотреть на p99 · **C)** разницы нет

<details>
<summary>Ответ</summary>

**Зависит от того, на какую меру смотреть** — и это и есть идея урока.

```console
$ go run ./latency
eski so'rov:  o'rtacha   37 ms | p50   35 ms | p99   70 ms
eski sahifa: 100 so'rov   | p50   73 ms | p99  107 ms
kesh so'rov:  o'rtacha   25 ms | p50    8 ms | p99  492 ms
kesh sahifa: 100 so'rov   | p50  531 ms | p99  918 ms
```

По одному запросу («so'rov») `kesh` выигрывает по среднему («o'rtacha», 25 против 37 мс) и по медиане (8 против
35 мс). Но p99 — 492 мс, а у `eski` 70 мс: **в 7 раз медленнее**. 4 % запросов, которых нет в кэше, идут медленным
путём, а среднее этот хвост прячет. Если вы выбрали «A», вы смотрели только на среднее и медиану. Не «C»: разница
огромная, просто она в хвосте.

</details>

Теперь пусть страница шлёт этому сервису 100 запросов. Вероятность, что хотя бы одного запроса нет в кэше:

| Расчёт | Результат |
|---|---|
| один запрос из кэша | 0.96 |
| все 100 из кэша | 0.96¹⁰⁰ ≈ 0.017 |
| хотя бы один на медленном пути | 1 − 0.96¹⁰⁰ ≈ **98.3 %** |

98 % страниц ждут хотя бы один медленный ответ. Программа измерила и это (строки `sahifa` в выводе, 10 000 страниц):
медиана страницы у релиза с кэшем **531 мс**, у старого — **73 мс**. Для такой страницы старый релиз лучше — и
показал это не средний показатель, а перцентиль.

В этой модели промах выбран дорогим (~400 мс). Согласно README курса, если промах дешёвый (например, ~40 мс), кэш
выигрывает по всем мерам (этот вариант мы не запускали). Вывод не меняется: решение определяет не среднее, а хвост.
Книга по SRE тоже советует следить за задержкой (latency) не по среднему, а по гистограмме с подсчётом по интервалам.

### Код `latency`

```go filename="latency/main.go" showLineNumbers
// latency: ikki reliz, sintetik model. Qaysi biri tezroq?
// Javob qaysi o'lchovga qarashingizga bog'liq: o'rtacha, mediana yoki p99.
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
	"slices"
)

const (
	n         = 100_000 // alohida so'rovlar
	sahifalar = 10_000  // har sahifa 100 so'rov yuborib, eng sekinini kutadi
)

// lognormal: mediana atrofida, o'ngga cho'zilgan "dum" bilan (ms).
func lognormal(r *rand.Rand, mediana, sigma float64) float64 {
	return mediana * math.Exp(sigma*r.NormFloat64())
}

// eski: har so'rov bazaga boradi, ~35 ms.
func eski(r *rand.Rand) float64 { return lognormal(r, 35, 0.3) }

// kesh: 96 % so'rov keshdan ~8 ms. 4 % keshda yo'q: sekin yo'l (sovuq disk, og'ir so'rov) ~400 ms.
func kesh(r *rand.Rand) float64 {
	if r.Float64() < 0.96 {
		return lognormal(r, 8, 0.3)
	}
	return lognormal(r, 400, 0.3)
}

// percentil: saralangan xs da "eng yaqin rang" usuli: p ulushdan kam bo'lmagan eng kichik qiymat.
func percentil(xs []float64, p float64) float64 {
	k := int(math.Ceil(p*float64(len(xs)))) - 1
	return xs[max(k, 0)]
}

func olcha(nom string, f func(*rand.Rand) float64) {
	r := rand.New(rand.NewPCG(1, 2))
	xs := make([]float64, n)
	var sum float64
	for i := range xs {
		xs[i] = f(r)
		sum += xs[i]
	}
	slices.Sort(xs)
	sh := make([]float64, sahifalar)
	for i := range sh {
		for range 100 {
			sh[i] = max(sh[i], f(r))
		}
	}
	slices.Sort(sh)
	fmt.Printf("%-4s so'rov:  o'rtacha %4.0f ms | p50 %4.0f ms | p99 %4.0f ms\n",
		nom, sum/n, percentil(xs, 0.50), percentil(xs, 0.99))
	fmt.Printf("%-4s sahifa: 100 so'rov   | p50 %4.0f ms | p99 %4.0f ms\n",
		nom, percentil(sh, 0.50), percentil(sh, 0.99))
}

func main() {
	olcha("eski", eski)
	olcha("kesh", kesh)
}
```

| Строка | Код | Что делает |
|---|---|---|
| 12–15 | `const (n = 100_000; sahifalar = 10_000)` | 100 000 отдельных запросов и 10 000 страниц по 100 запросов |
| 18–20 | `lognormal(r, mediana, sigma)` | `r.NormFloat64()` — число из стандартного нормального распределения (обычно между −2 и 2). `mediana · e^(sigma·z)`: время с медианой `mediana` и хвостом, вытянутым вправо. `sigma = 0.3` — разброс. Почему задержка не нормальна — в MATH-3.09 |
| 23 | `eski` | каждый запрос около ~35 мс |
| 26–31 | `kesh` | в 96 % случаев ~8 мс, в 4 % ~400 мс |
| 34–37 | `percentil(xs, p)` | ближайший ранг: `k = ceil(p·n) − 1`. `max(k, 0)` — чтобы при `p = 0` индекс не стал отрицательным |
| 39 | `func olcha(nom string, f func(*rand.Rand) float64)` | («измерь») `f` — значение-функция: передаётся `eski` или `kesh` (GO-1.06) |
| 40 | `rand.NewPCG(1, 2)` | один и тот же seed для обоих релизов |
| 41–46 | `xs := make([]float64, n)` и цикл | 100 000 времён и их сумма (`sum`) |
| 47 | `slices.Sort(xs)` | сортировка на месте: перцентиль берётся по отсортированному списку |
| 48–53 | `sh` | («страницы») для каждой страницы самый медленный из 100 запросов: `sh[i] = max(sh[i], f(r))` |
| 55–58 | `fmt.Printf("%-4s …")` | `%-4s` — имя в поле из 4 символов, выравнивание влево; `%4.0f` — число без дробной части |
| 61–64 | `main` | вызывает `olcha` дважды: сначала `eski`, потом `kesh` |

## A/B-тест: +10 % — победа или шум?

Второй пример. Вы поменяли кнопку и провели A/B-тест: каждую кнопку увидели 2000 человек.

| Группа | Увидели | Купили | Конверсия |
|---|---|---|---|
| старая кнопка | 2000 | 100 | 5.0 % |
| новая кнопка | 2000 | 110 | 5.5 % |

С новой кнопкой купили на 10 % больше людей. Внимание: это **относительные** 10 % (110 / 100). Абсолютная разница —
0.5 **процентного пункта** (5.5 % − 5.0 %). Прежде чем выкатывать новую кнопку, проверим: если ничего не изменилось,
как часто возникает такая разница?

Программа `abtest` симулирует тест кнопки 10 000 раз. Сначала обе кнопки абсолютно одинаковы (5 %) — это **A/A-тест**.
Кохави и коллеги определяют A/A-тест так: обеим группам дают «exactly the same experience» (ровно одно и то же). У них
это реальный трафик, у нас — симуляция.

Предскажите: если кнопки одинаковы, в какой доле из 10 000 экспериментов новая кнопка «выиграет не меньше +10 %»?

**A)** почти никогда (&lt; 1 %) · **B)** ~5 % · **C)** ~25 %

<details>
<summary>Ответ</summary>

**C: почти в каждом четвёртом эксперименте.**

```console
$ go run ./abtest
har guruhda 2000 kishi, 10000 tajriba
A/A, tugmalar bir xil:
  yangi tugma >= +10 %: 24.4 %
  yangi tugma <= -10 %: 22.4 %
  z-test "farq bor":     4.8 %
A/B, yangi tugma rostdan +10 %:
  z-test "farq bor":    10.9 %
qo'lda hisob: shovqin ~ sqrt(2*0.05*0.95/2000) = 0.69 foiz punkti
```

Первая строка: «в каждой группе 2000 человек, 10000 экспериментов». Кнопки одинаковы («tugmalar bir xil»), но в 24.4 %
экспериментов новая кнопка («yangi tugma») «выиграла» не меньше 10 %, а в 22.4 % — «проиграла» не меньше 10 %. Значит,
почти в половине экспериментов разница в 10 % возникает **случайно**. Если вы выбрали «A» или «B», вы сочли 2000 человек
большой выборкой: при конверсии 5 % это всего ~100 покупок.

</details>

Остальные строки — правильное правило решения. **z-тест** (NIST e-Handbook 7.3.3): делим разницу двух долей на
стандартную ошибку и, если результат больше 1.96, говорим «разница есть» («farq bor»). 1.96 — граница 95 % доверия.

| Случай | z-тест сказал «разница есть» | Что это значит |
|---|---|---|
| A/A, кнопки одинаковы | 4.8 % | ложный сигнал (false positive): ~5 %, так тест и устроен |
| A/B, новая кнопка действительно +10 % (5.5 %) | 10.9 % | настоящее улучшение находится лишь в ~11 % случаев |

Тест не ошибается — он говорит «не знаю». При 2000 людях кнопка, которая действительно лучше на 10 %, в 9 случаях из
10 выходит «без разницы». Почему? Посчитаем вручную.

## Расчёт вручную: шум и размер групп

**1. Сколько шума?** Шум разницы двух долей, то есть **стандартная ошибка** (NIST 7.3.3, при равных группах):

```text
стандартная ошибка = √( 2 · p · (1 − p) / n )
                   = √( 2 · 0.05 · 0.95 / 2000 )
                   ≈ 0.0069 = 0.69 процентного пункта
```

Последняя строка программы вывела то же: `0.69 foiz punkti` («процентного пункта»).

**2. Сколько сигнала?** «+10 %» — это 10 % от 5 %, то есть 0.5 процентного пункта. Сигнал (0.5) **меньше** шума
(0.69). Поэтому даже одинаковые кнопки часто дают разницу ±10 %.

**3. Насколько маленьким должен быть шум?** Чтобы надёжно увидеть разницу, шум должен быть примерно в 2.8 раза меньше
разницы. 2.8 = 1.96 + 0.84: 1.96 — 95 % доверия (ложный сигнал 5 %), 0.84 — находить настоящую разницу в 80 % случаев
(по-английски *power*, мощность). Кохави и соавторы (2009, §3.2) берут именно эти 95 % и 80 %.

```text
нужный шум = 0.5 / 2.8 ≈ 0.18 процентного пункта
```

**4. Во сколько раз больше людей?** Шум убывает обратно пропорционально корню из числа людей: в 4 раза больше людей —
в 2 раза меньше шум. Чтобы снизить шум с 0.69 до 0.18:

```text
(0.69 / 0.18)² ≈ 3.8² ≈ в 15 раз больше людей  →  2000 · 15 ≈ 30 000 человек
```

**5. Точная формула.** Формула (2) из статьи Кохави, Лонгботэма, Соммерфилда и Хенне (Kohavi, Longbotham,
Sommerfield, Henne, 2009; они опираются на van Belle 2002):

| Символ | Смысл | У нас |
|---|---|---|
| n | число людей в каждой группе | ? |
| σ² | дисперсия конверсии: p · (1 − p) | 0.05 · 0.95 = 0.0475 |
| Δ | наименьшая разница, которую хотим заметить | 0.5 процентного пункта = 0.005 |
| 16 | коэффициент для 95 % доверия и 80 % мощности ≈ 2 · 2.8² = 15.7 | 16 |

```text
n = 16 · σ² / Δ² = 16 · 0.0475 / 0.005² = 30 400 человек в каждую группу
```

Предскажите: при 30 400 людях в какой доле случаев z-тест найдёт кнопку, которая действительно лучше на +10 %?

**A)** ~11 %, как раньше · **B)** ~80 % · **C)** ~100 %

<details>
<summary>Ответ</summary>

**B.**

```console
$ go run ./abtest 30400
har guruhda 30400 kishi, 10000 tajriba
A/A, tugmalar bir xil:
  yangi tugma >= +10 %:  0.4 %
  yangi tugma <= -10 %:  0.2 %
  z-test "farq bor":     5.0 %
A/B, yangi tugma rostdan +10 %:
  z-test "farq bor":    79.2 %
qo'lda hisob: shovqin ~ sqrt(2*0.05*0.95/30400) = 0.18 foiz punkti
```

Если кнопки одинаковы, z-тест снова ошибается в 5.0 % случаев. Если новая кнопка действительно лучше, он находит её в
79.2 % случаев. Ровно это формула и обещала: 95 % доверия и 80 % мощности. Шум («shovqin») тоже упал до 0.18
процентного пункта. Если вы выбрали «C»: чтобы дойти до 100 %, нужно бесконечно много людей, формула целится в 80 %.
«A» — результат при 2000 людях.

</details>

Значит, порядок такой: **сначала считаем нужный размер, потом запускаем тест.** `benchstat` из GO-1.07 отвечает на
тот же вопрос: разница двух бенчмарков настоящая или это шум. Ловушку ежедневного подглядывания в результаты
(*peeking*) разберём в [MATH-3.04](/lab/youtube/math#math-3-04), effect size и power — в [MATH-4.04](/lab/youtube/math#math-4-04).

### Код `abtest`

```go filename="abtest/main.go" showLineNumbers
// abtest: tugma testini 10 000 marta simulyatsiya qiladi. Har guruhda n kishi, eski tugmada 5 % sotib oladi.
//
//	A/A: yangi tugma AYNAN BIR XIL (5 %). Har qanday "yutuq" shovqin.
//	A/B: yangi tugma haqiqatan +10 % (5.5 %). Test buni necha marta topadi?
//
// "Farq bor" qarori: ikki ulushning z-testi, |z| > 1.96 (95 % ishonch), NIST e-Handbook 7.3.3.
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
	"os"
	"strconv"
	"sync"
)

const (
	p          = 0.05 // eski tugma konversiyasi
	tajribalar = 10_000
	ishchilar  = 10 // har biri o'z generatori bilan 1000 tajriba: natija har safar bir xil
)

// sotdi: n kishidan nechtasi q ehtimol bilan sotib oldi.
func sotdi(r *rand.Rand, n int, q float64) int {
	k := 0
	for range n {
		if r.Float64() < q {
			k++
		}
	}
	return k
}

type natija struct{ plus10, minus10, farqBor int }

// sina: yangi tugmaning haqiqiy konversiyasi q bo'lganda 10 000 tajriba.
func sina(n int, q float64) natija {
	var mu sync.Mutex
	var jami natija
	var wg sync.WaitGroup
	for w := range ishchilar {
		wg.Go(func() {
			r := rand.New(rand.NewPCG(1, uint64(w)))
			var t natija
			for range tajribalar / ishchilar {
				a, b := sotdi(r, n, p), sotdi(r, n, q)
				nisbiy := float64(b-a) / float64(max(a, 1))
				if nisbiy >= 0.10 {
					t.plus10++
				}
				if nisbiy <= -0.10 {
					t.minus10++
				}
				pa, pb, pp := float64(a)/float64(n), float64(b)/float64(n), float64(a+b)/float64(2*n)
				if se := math.Sqrt(pp * (1 - pp) * 2 / float64(n)); se > 0 && math.Abs(pb-pa)/se > 1.96 {
					t.farqBor++
				}
			}
			mu.Lock()
			jami.plus10, jami.minus10, jami.farqBor = jami.plus10+t.plus10, jami.minus10+t.minus10, jami.farqBor+t.farqBor
			mu.Unlock()
		})
	}
	wg.Wait()
	return jami
}

func foiz(k int) float64 { return 100 * float64(k) / tajribalar }

func main() {
	n := 2000 // har bir guruhda
	if len(os.Args) > 1 {
		k, err := strconv.Atoi(os.Args[1])
		if err != nil || k < 100 {
			fmt.Fprintln(os.Stderr, "foydalanish: go run ./abtest [n >= 100]")
			os.Exit(2)
		}
		n = k
	}
	aa, ab := sina(n, p), sina(n, p*1.10)
	fmt.Printf("har guruhda %d kishi, %d tajriba\n", n, tajribalar)
	fmt.Println("A/A, tugmalar bir xil:")
	fmt.Printf("  yangi tugma >= +10 %%: %4.1f %%\n", foiz(aa.plus10))
	fmt.Printf("  yangi tugma <= -10 %%: %4.1f %%\n", foiz(aa.minus10))
	fmt.Printf("  z-test \"farq bor\":    %4.1f %%\n", foiz(aa.farqBor))
	fmt.Println("A/B, yangi tugma rostdan +10 %:")
	fmt.Printf("  z-test \"farq bor\":    %4.1f %%\n", foiz(ab.farqBor))
	fmt.Printf("qo'lda hisob: shovqin ~ sqrt(2*0.05*0.95/%d) = %.2f foiz punkti\n", n, 100*math.Sqrt(2*p*(1-p)/float64(n)))
}
```

| Строка | Код | Что делает |
|---|---|---|
| 18–22 | `const (p = 0.05; tajribalar = 10_000; ishchilar = 10)` | конверсия старой кнопки 5 %, 10 000 экспериментов («tajriba» — эксперимент), 10 рабочих («ishchi» — worker) |
| 25–33 | `sotdi(r, n, q)` | («купили») каждый из n человек покупает с вероятностью q; возвращает, сколько купили |
| 35 | `type natija struct{ plus10, minus10, farqBor int }` | («результат») три счётчика: «≥ +10 %», «≤ −10 %», «разница есть» (`farqBor`) |
| 38 | `func sina(n int, q float64) natija` | («испытай») 10 000 экспериментов, когда настоящая конверсия новой кнопки равна q |

## Метод: картинка, расчёт вручную, код, измерение

Метод обучения будет таким, как вы видели сегодня. В каждой теме одна картинка, один расчёт вручную и один код:

```text
картинка                  →  расчёт вручную    →  код                  →  измерение
страница из 100 запросов     1 − 0.99¹⁰⁰          симуляция на Go         проверяет допущение
(ждёт самый медленный)       ≈ 63.4 %             63.5 %                  (независимы ли?)
```

Если расчёт и код не совпали, ошибка либо в формуле, либо в коде. Даже если совпали, допущение (например,

строятся по данным, которые выводит Go.

## Частые ошибки

**1. Оценивать релиз по средней задержке (тихая ошибка).** Никакой ошибки не выводится: панель показывает «среднее
37 → 25 мс», и релиз выглядит хорошим. На самом деле p99 вырос с 70 до 492 мс (раздел «Какой релиз быстрее?»).
**Исправление:** сравнивайте p50, p99 (и на уровне страницы), следите за задержкой по гистограмме.

**2. Думать, что `1 − 0.99ᴺ` работает везде.** Формула верна, если запросы независимы. А если медленность связана?
Например, на 1 % страниц случается пауза GC, и *все* запросы этой страницы замедляются вместе. Этой программы нет в
папке курса, мы написали её для этой страницы (`bogliq` — «связанный», correlated; в её папке свой `go.mod`:
`module bogliq`, `go 1.26`):

```go
// bogliq: fanout kabi, lekin sekinlik bog'liq: 1 % sahifada (masalan, GC pauzasi) hamma so'rov birga sekin.
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
)

const sahifalar = 100_000

func main() {
	r := rand.New(rand.NewPCG(1, 2))
	sekinSorov, sekinSahifa := 0, 0
	for range sahifalar {
		pauza := r.Float64() < 0.01 // shu sahifa paytida pauza bo'ldimi
		eng := 0.0
		for range 100 {
			t := 10 + 40*r.Float64()
			if pauza {
				t += 1000
				sekinSorov++
			}
			eng = max(eng, t)
		}
		if eng >= 1000 {
			sekinSahifa++
		}
	}
	fmt.Printf("so'rovlar: 1 s dan sekini %5.2f %%\n", 100*float64(sekinSorov)/float64(sahifalar*100))
	fmt.Printf("sahifalar (100 so'rovli): 1 s dan sekini %4.1f %%\n", 100*float64(sekinSahifa)/sahifalar)
	fmt.Printf("formula (mustaqil deb): 1 - 0.99^100 = %.1f %%\n", 100*(1-math.Pow(0.99, 100)))
}
```

```console
$ go run ./bogliq
so'rovlar: 1 s dan sekini  0.99 %
sahifalar (100 so'rovli): 1 s dan sekini  1.0 %
formula (mustaqil deb): 1 - 0.99^100 = 63.4 %
```

Медленных запросов снова ~1 %, но медленных страниц не 63 %, а 1.0 %: все медленные запросы собрались в одних и тех
же страницах. Отличается одна строка: `pauza` выбирается один раз на страницу, а не на каждый запрос. Реальная
система находится между этими двумя крайностями. **Исправление:** используйте формулу для направления, а число
берите из реального измерения (p99 на уровне страницы).

**3. Говорить «p99 каждого сервиса — 1 секунда».** В статье Дина и Баррозу написано именно так («99th-percentile
latency of one second»). Но по нашему определению это значит «1 % запросов дольше 1 с». В этой модели p99 одного
запроса ~50 мс (README курса): запрос на 99-й границе — ещё самый медленный из быстрой группы. **Исправление:**
говорите точно: «1 % запросов дольше 1 с».

**4. Объявлять «+10 %» победой в тесте на 2000 человек (тихая ошибка).** В A/A-симуляции одинаковые кнопки дали
«+10 %» в 24.4 % случаев (раздел «A/B-тест»). **Исправление:** до теста посчитайте размер по `n = 16σ²/Δ²`,
решение принимайте по z-тесту и не останавливайте тест, «когда понравилось», заглядывая в результаты каждый день
([MATH-3.04](/lab/youtube/math#math-3-04)).

**5. Передать в аргумент не число.**

```console
$ go run ./abtest 2000kishi
foydalanish: go run ./abtest [n >= 100]
exit status 2
```

`strconv.Atoi("2000kishi")` вернул ошибку, программа напечатала подсказку («foydalanish» — usage) и вышла с кодом 2.
Строку `exit status 2` добавляет `go run`. `go run ./fanout 0` останавливается так же: для страницы из 0 запросов
долю посчитать нельзя. **Исправление:** передавайте только число: `go run ./abtest 30400` (100 и больше),
`go run ./fanout 20` (1 и больше) или `go run ./fanout jadval`.

<details>
<summary>Ответ</summary>

**4.** 30 400 человек находят разницу +10 % в 80 % случаев. Теперь вы хотите так же замечать разницу +5 %
(5 % → 5.25 %). Сколько примерно людей нужно в каждую группу?

**A)** ~61 000 (в 2 раза) · **B)** ~122 000 (в 4 раза) · **C)** ~30 400, столько же

<details>
<summary>Ответ</summary>

**B.** `n = 16σ²/Δ²`: если Δ в два раза меньше, Δ² в четыре раза меньше, а n в четыре раза больше:

«A», вы думали, что шум убывает обратно пропорционально числу людей: на самом деле — **корню** из него.

</details>

**5.** Из GO-1.07: один бенчмарк в новой версии оказался на 5 % быстрее. Почему этому не верят, а берут `-count 10` и

<details>
<summary>Ответ</summary>

Потому что и в одном измерении есть шум (нагрузка компьютера, кэш, частота). Как в сегодняшнем A/A-тесте, даже если

z-тест.

</details>

```go filename="homework/main.go" showLineNumbers
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
	"slices"
)

func main() {
	// Oson: 20 so'rovli sahifa, har so'rov 100 tadan 1 holatda 1 s dan sekin.
	fmt.Printf("oson:  1 - 0.99^20 = %.1f %% (tekshiring: go run ./fanout 20)\n", 100*(1-math.Pow(0.99, 20)))

	// O'rta: har so'rov 1000 tadan 1 holatda 1 s dan sekin bo'lsa, 100 so'rovli sahifa.
	fmt.Printf("o'rta: 1 - 0.999^100 = %.1f %% (100 tadan 1 bo'lganda 63.4 %% edi)\n", 100*(1-math.Pow(0.999, 100)))

	// Qiyin: Kohavi formulasi n = 16*sigma^2/delta^2, 5 % konversiya, +5 % nisbiy (5 % -> 5.25 %).
	sigma2, delta := 0.05*0.95, 0.05*0.05
	fmt.Printf("qiyin: n = 16*0.0475/0.0025^2 = %.0f kishi har guruhda\n", 16*sigma2/(delta*delta))

	// Guru: kesh relizida p99 < 100 ms bo'lishi uchun kesh qancha so'rovni ushlashi kerak?

		fmt.Printf("guru:  kesh %.1f %% -> p99 %4.0f ms\n", 100*hit, p99(hit))
	}
}

func p99(hit float64) float64 {
	r := rand.New(rand.NewPCG(1, 2))
	xs := make([]float64, 100_000)
	for i := range xs {
		m := 400.0
		if r.Float64() < hit {
			m = 8
		}
		xs[i] = m * math.Exp(0.3*r.NormFloat64())
	}
	slices.Sort(xs)
	return xs[int(math.Ceil(0.99*float64(len(xs))))-1]
}
```

```console
sahifalar (20 so'rovli): 1 s dan sekini 18.0 %
qo'lda hisob: 1 - 0.99^20 = 18.2 %
```

18.0 % и 18.2 %: разница случайная.

🟡 63.4 % → 9.5 %. Медленный случай у каждого запроса стал в 10 раз реже, а медленных страниц — в 6.7 раза меньше.
Для страницы из 100 запросов важен не p99 каждого запроса, а его p99.9.

🟠 121 600 человек в каждую группу: в четыре раза больше 30 400, потому что Δ в два раза меньше. В статье Кохави на
том же примере сказано «less than 122,000 users».

🔴 Доля промахов должна быть меньше 1 %, то есть кэш > 99 %. При 99 % ещё на границе (185 мс), при 99.5 % — 17 мс.
Причина: p99 — граница самого медленного 1 %. Если промахов больше 1 %, p99 обязательно попадает внутрь промахов.
