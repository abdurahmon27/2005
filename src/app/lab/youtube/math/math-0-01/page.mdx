## Nimani oʻrganasiz

Har bir servisingiz 100 ta soʻrovdan 99 tasiga bir soniyadan tez javob beradi. Shunga qaramay, sahifalarning 63 %
bir soniyadan sekin ochiladi. Qanday qilib? Ikkinchi savol: tugmani oʻzgartirdingiz, xaridlar 10 % oshdi. Bu
yutuqmi yoki shovqin? Ikkala savolga ham bugun Go simulyatsiyasi va qoʻlda hisob bilan javob beramiz.

**Bitta gʻoya:** ozgina matematika (foiz va daraja) muhandislik qarorini oʻzgartiradi. Oʻrtacha latency dumni
yashiradi, kichik A/B test esa shovqinni yutuq deb koʻrsatadi. Bu yoʻnalishda har mavzu bitta rasm, bitta qoʻlda
hisob va bitta kod bilan beriladi. Hisob va kod mos kelishi kerak, taxminni esa haqiqiy oʻlchov tekshiradi.

Dars oxirida siz:

- sahifa N ta soʻrovni parallel yuborsa, sekin sahifalar ulushini `1 − 0.99ᴺ` bilan qoʻlda hisoblaysiz va bu formula
  qachon ishlamasligini bilasiz;
- relizlarni oʻrtacha bilan emas, p50 va p99 bilan solishtirasiz;
- A/B testdagi farq shovqinmi yoki yoʻqmi, standart xato bilan baholaysiz va kerakli guruh hajmini
  `n = 16σ²/Δ²` bilan topasiz;
- Muhandislar uchun matematika yoʻnalishining oltita modulidan sizga qaysilari kerakligini va nimani tashlab ketish
  mumkinligini bilasiz.

Bugungi uchta asosiy yangi soʻz:

| Soʻz | Oddiy maʼnosi | Inglizcha |
|---|---|---|
| p99 | soʻrovlarning 99 % undan tez yoki unga teng boʻlgan vaqt. Undan sekin 1 % — **dum** | percentile, tail |
| mustaqil hodisalar | biri sodir boʻlgani ikkinchisining ehtimolligini oʻzgartirmaydi; shunda ehtimolliklar koʻpaytiriladi | independent events |
| standart xato | tasodifiy shovqinning oʻlchami: bir xil tajribani qayta qilsangiz, natija odatda qanchaga siljiydi | standard error |

Ikkita yordamchi soʻz ham bor. **A/A test** — ikkala guruh aynan bir xil narsani koʻradigan test: undagi har qanday
«yutuq» shovqin. **z-test** — farqni standart xatoga boʻlib, natija 1.96 dan katta boʻlsa «farq bor» deydigan qoida.

## 100 soʻrovli sahifa: 1 % qanday qilib 63 % boʻladi

Sahifa (yoki API gateway) bitta foydalanuvchi soʻrovi uchun 100 ta ichki servisga parallel soʻrov yuboradi va
hammasining javobini kutadi. Frontend'da bu `await Promise.all([...])`, Python'da `asyncio.gather(...)`. Parallel
kutishning vaqti eng sekin javobning vaqtiga teng. JS'da tekshirib koʻramiz (bu fayl kurs papkasida yoʻq, uni
shu sahifa uchun yozdik):

```js
const sorov = (ms) => new Promise((ok) => setTimeout(() => ok(ms), ms));
const boshi = performance.now();
await Promise.all([sorov(10), sorov(20), sorov(1000)]);
console.log(`sahifa: ${Math.round(performance.now() - boshi)} ms`);
```

```console
$ node fanout.mjs
sahifa: 1001 ms
```

Uchta soʻrov: 10, 20 va 1000 ms. Sahifa 1001 ms kutdi (ikkinchi ishga tushirishda 1000 ms, Node 24.10). Tez ikkita
soʻrov yordam bermadi: sahifa **eng sekinini** kutadi.

```text
         ┌─ soʻrov 1:   23 ms ─┐
         ├─ soʻrov 2:   41 ms ─┤
sahifa ──┼─ soʻrov 3: 1730 ms ─┼──▶ sahifa tayyor: max(...) = 1730 ms
         ├─    …               │
         └─ soʻrov 100: 17 ms ─┘
```

Endi bizning model. Har bir soʻrov 100 tadan 99 holatda 10–50 ms da javob beradi, 100 tadan 1 holatda esa 1–3
soniyada. Sahifa 100 ta shunday soʻrov yuboradi.

Taxmin qiling: sahifalarning necha foizi bir soniyadan sekin ochiladi?

**A)** ~1 % · **B)** ~10 % · **C)** ~63 %

<details>
<summary>Javob</summary>

**C.** Go simulyatsiyasi 100 000 sahifani sanadi:

```console
$ go run ./fanout
so'rovlar: 1 s dan sekini  1.00 %
sahifalar (100 so'rovli): 1 s dan sekini 63.5 %
qo'lda hisob: 1 - 0.99^100 = 63.4 %
```

Soʻrovlarning 1.00 % sekin, sahifalarning esa 63.5 %. «A» ni tanlagan boʻlsangiz, sahifani bitta soʻrovdek
hisobladingiz. Lekin sahifada 100 ta soʻrov bor va ulardan *bittasi* sekin boʻlishi yetarli. «B» ham kam: 100 ta
qurʼaning hech birida 1 % lik omadsizlik chiqmasligi ancha qiyin.

</details>

### Qoʻlda hisob: nega ehtimolliklar koʻpaytiriladi

Bitta soʻrovning tez boʻlish ehtimolligi 0.99. Soʻrovlar bir-biriga bogʻliq boʻlmasa, yaʼni **mustaqil** boʻlsa,
«hammasi tez» ehtimolligi alohida ehtimolliklarning koʻpaytmasiga teng (Stanford CS109, *Independence*):

| Qadam | Hisob | Natija |
|---|---|---|
| 1 soʻrov tez | 0.99 | 99 % |
| 2 soʻrov ham tez | 0.99 · 0.99 = 0.99² | 98.0 % |
| 100 soʻrov hammasi tez | 0.99¹⁰⁰ | ≈ 0.366, yaʼni ~37 % |
| kamida bittasi sekin | 1 − 0.99¹⁰⁰ | ≈ 0.634, yaʼni **63.4 %** |

Python'da bir qatorda:

```console
$ python3 -c "print(1 - 0.99**100)"
0.6339676587267709
```

Simulyatsiya 63.5 %, formula 63.4 %: farq tasodifdan. Bu misol Google muhandislari Jeff Dean va Luiz Barroso
maqolasidan (*The Tail at Scale*, CACM 2013, 76-bet): «If a user request must collect responses from 100 such servers
in parallel, then 63% of user requests will take more than one second» (foydalanuvchi soʻrovi 100 ta shunday
serverdan parallel javob yigʻishi kerak boʻlsa, soʻrovlarning 63 % bir soniyadan koʻp davom etadi).

**Muhim shart: mustaqillik.** Hayotda sekinliklar koʻpincha bogʻliq. Bitta GC pauzasi (garbage collector dasturni
qisqa vaqtga toʻxtatadi) yoki bitta tiqilgan switch bir nechta soʻrovni birga sekinlatadi. Dean va Barroso ham
garbage collection va umumiy resurslarni sekinlik sabablari qatorida sanaydi. Bizning kod ham mustaqillik bilan
yozilgan. Shuning uchun kod va formula mos kelishi faqat arifmetikani tekshiradi: formula yoʻnalishni koʻrsatadi,
taxminni esa haqiqiy oʻlchov tekshiradi. Sekinlik bogʻliq boʻlsa nima boʻlishini «Koʻp uchraydigan xatolar»
boʻlimida oʻlchaymiz.

## Kod: `fanout` simulyatsiyasi

Dastur juda sodda: `sorov` («soʻrov» — request) funksiyasi bitta soʻrovning vaqtini qaytaradi, ichki sikl 100 ta
soʻrovning eng sekinini topadi, tashqi sikl buni 100 000 sahifa uchun takrorlaydi.

```go filename="fanout/main.go" showLineNumbers
// fanout: bitta sahifa N ta so'rovni parallel yuboradi va eng sekin javobni kutadi.
// Har bir so'rov yuztadan bitta holatda 1 soniyadan sekin. Sahifalarning qanchasi sekin?
// So'rovlar bir-biriga bog'liq emas (mustaqil) deb olinadi: hayotda bu har doim ham rost emas.
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
	"os"
	"strconv"
)

const sahifalar = 100_000

// sorov: 99 % hollarda 10..50 ms, 1 % hollarda 1..3 soniya.
func sorov(r *rand.Rand) float64 {
	if r.Float64() < 0.01 {
		return 1000 + 2000*r.Float64()
	}
	return 10 + 40*r.Float64()
}

func main() {
	N := 100
	if len(os.Args) > 1 {
		if os.Args[1] == "jadval" { // 1 - 0.99^N, turli N uchun
			for _, n := range []int{1, 10, 20, 50, 100, 200, 500} {
				fmt.Printf("N = %3d: %5.1f %% sahifa sekin\n", n, 100*(1-math.Pow(0.99, float64(n))))
			}
			return
		}
		n, err := strconv.Atoi(os.Args[1])
		if err != nil || n < 1 {
			fmt.Fprintln(os.Stderr, "foydalanish: go run ./fanout [N >= 1 | jadval]")
			os.Exit(2)
		}
		N = n
	}
	r := rand.New(rand.NewPCG(1, 2))
	sekinSorov, sekinSahifa := 0, 0
	for range sahifalar {
		eng := 0.0
		for range N {
			t := sorov(r)
			if t >= 1000 {
				sekinSorov++
			}
			eng = max(eng, t) // sahifa eng sekin javobni kutadi
		}
		if eng >= 1000 {
			sekinSahifa++
		}
	}
	fmt.Printf("so'rovlar: 1 s dan sekini %5.2f %%\n", 100*float64(sekinSorov)/float64(sahifalar*N))
	fmt.Printf("sahifalar (%d so'rovli): 1 s dan sekini %4.1f %%\n", N, 100*float64(sekinSahifa)/sahifalar)
	fmt.Printf("qo'lda hisob: 1 - 0.99^%d = %.1f %%\n", N, 100*(1-math.Pow(0.99, float64(N))))
}
```

## Google servisida: 10 ms dan 140 ms gacha

Dean va Barroso haqiqiy Google servisini ham oʻlchagan (maqoladagi Table 1). Bu ham bizning model emas, haqiqiy
tizim:

| Oʻlchov (root serverda) | p99 |
|---|---|
| bitta tasodifiy soʻrov tugashi | 10 ms |
| hamma soʻrovlar tugashi | 140 ms |

Bitta soʻrovning p99'i 10 ms, sahifa esa hammasini kutgani uchun 140 ms. Yechim ham shu hisobdan chiqadi: dumni
butunlay yoʻqotib boʻlmaydi, lekin uni chetlab oʻtish mumkin. Javob kechiksa, xuddi shu soʻrovni boshqa nusxaga
(replica) ham yuborib, qaysi biri birinchi javob bersa, shuni olish. Maqola buni **hedged requests** deb ataydi.

Ularning testida 100 ta serverdan 1000 ta qiymat oʻqilgan. 10 ms kutib, keyin hedge yuborish p99.9 ni (eng sekin
mingdan bir qism) **1800 ms dan 74 ms ga** tushirgan. Soʻrovlar esa atigi **2 %** koʻpaygan. Bu — matematikaning
qarorga aylangani: dum qayerdan kelishini bilsangiz, uni arzon yoʻl bilan kesasiz.

## Oʻrtacha, mediana va p99

Endi atamalarni aniqlab olamiz. Grafana yoki boshqa monitoring panelida koʻradigan `p50`, `p95`, `p99` aynan shular.

| Oʻlchov | Taʼrif | Bizning koddagi hisob |
|---|---|---|
| oʻrtacha (mean) | hamma vaqtlar yigʻindisi / soʻrovlar soni | `sum/n` |
| **mediana** (p50) | saralangan roʻyxatning oʻrtasi: yarmi undan tez | `percentil(xs, 0.50)` |
| **p99** | soʻrovlarning 99 % undan tez yoki unga teng | `percentil(xs, 0.99)` |
| **dum** (tail) | p99 dan sekin boʻlgan eng sekin 1 % | — |

Mediananing oʻzi GO-1.06 da yozilgan edi (`mediana`). U yerda `xs[len/2]` olinardi. Bugungi `percentil` esa
«eng yaqin rang» (*nearest rank*) usulida: saralangan `xs` da `xs[ceil(p·n) − 1]`. Juft n da GO-1.06 yuqori oʻrtani,
bizniki pastki oʻrtani tanlaydi; 100 000 soʻrovda farq sezilmaydi (kurs README'si).

Google'ning SRE kitobi ogohlantiradi: «the 99th percentile of one backend can easily become the median response of
your frontend» (bitta backend'ning p99'i frontend'ning medianasiga oson aylanishi mumkin). Biz buni hozir
koʻrdik: soʻrovlarning 1 % i sekin, 100 soʻrovli sahifalarning esa koʻpchiligi sekin.

Python'ning `statistics` moduli bilan kichik misol: 96 ta soʻrov 8 ms, 4 tasi 400 ms.

```console
$ python3 -c 'import statistics as s; xs = [8]*96 + [400]*4; print(s.mean(xs), s.median(xs), s.quantiles(xs, n=100)[98])'
23.68 8.0 400.0
```

Oʻrtacha 23.68 ms — bunday soʻrov umuman yoʻq. Mediana 8 ms, p99 400 ms. `quantiles(n=100)` 99 ta chegarani
qaytaradi, `[98]` — 99-si, yaʼni p99. Oʻrtacha dumni «yoyib» yuboradi: 4 % foydalanuvchining 400 ms kutgani
koʻrinmaydi.

## Qaysi reliz tezroq? Oʻrtacha dumni yashiradi

Endi bu bilim qarorni qanday oʻzgartiradi. Bu — **sintetik model**: sonlarni biz tanladik, shakli esa real. Ikki
reliz bor:

| Reliz | Har bir soʻrov | Taxminiy vaqt |
|---|---|---|
| `eski` («eski» — old) | har safar bazaga boradi | ~35 ms |
| `kesh` («kesh» — cache) | 96 % soʻrov keshdan; 4 % keshda yoʻq va sekin yoʻlga ketadi (sovuq disk, ogʻir soʻrov) | ~8 ms yoki ~400 ms |

Taxmin qiling: qaysi reliz yaxshiroq?

**A)** `kesh`: oʻrtachasi ham, medianasi ham kichik · **B)** `eski`: p99 bilan qaraganda · **C)** farqi yoʻq

<details>
<summary>Javob</summary>

**Qaysi oʻlchovga qarashingizga bogʻliq** — va aynan shu darsning gʻoyasi.

```console
$ go run ./latency

kesh so'rov:  o'rtacha   25 ms | p50    8 ms | p99  492 ms
kesh sahifa: 100 so'rov   | p50  531 ms | p99  918 ms
```

Bitta soʻrov boʻyicha `kesh` oʻrtacha (25 vs 37 ms) va mediana (8 vs 35 ms) boʻyicha yutadi. Lekin p99 492 ms,
`eski` da esa 70 ms: **7 barobar sekin**. Keshda yoʻq 4 % soʻrov sekin yoʻlga ketadi, oʻrtacha esa bu dumni
yashiradi. «A» ni tanlagan boʻlsangiz, faqat oʻrtacha va medianaga qaradingiz. «C» emas: farq juda katta, faqat u
dumda.

</details>

Endi sahifa bu servisga 100 ta soʻrov yuborsin. Hech boʻlmasa bitta soʻrov keshda yoʻq boʻlish ehtimolligi:

| Hisob | Natija |
|---|---|
| bitta soʻrov keshdan | 0.96 |
| 100 tasi ham keshdan | 0.96¹⁰⁰ ≈ 0.017 |
| kamida bittasi sekin yoʻlda | 1 − 0.96¹⁰⁰ ≈ **98.3 %** |

Sahifalarning 98 % kamida bitta sekin javobni kutadi. Dastur buni ham oʻlchadi (natijaning `sahifa` qatorlari,
10 000 sahifa): keshli relizda sahifa medianasi **531 ms**, eskisida **73 ms**. Bunday sahifa uchun eski reliz
yaxshiroq — va buni oʻrtacha emas, percentile koʻrsatdi.

Bu modelda miss qimmat (~400 ms) tanlangan. Kurs README'siga koʻra, miss arzon boʻlsa (masalan ~40 ms), kesh hamma
oʻlchovda yutadi (bu variantni biz ishga tushirmadik). Xulosa oʻzgarmaydi: qarorni oʻrtacha emas, dum hal qiladi.
SRE kitobi ham latency'ni oʻrtacha bilan emas, oraliqlar boʻyicha sanalgan gistogramma bilan kuzatishni maslahat
beradi.

### `latency` kodi

```go filename="latency/main.go" showLineNumbers
// latency: ikki reliz, sintetik model. Qaysi biri tezroq?
// Javob qaysi o'lchovga qarashingizga bog'liq: o'rtacha, mediana yoki p99.
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
	"slices"
)

const (
	n         = 100_000 // alohida so'rovlar
	sahifalar = 10_000  // har sahifa 100 so'rov yuborib, eng sekinini kutadi
)

// lognormal: mediana atrofida, o'ngga cho'zilgan "dum" bilan (ms).
func lognormal(r *rand.Rand, mediana, sigma float64) float64 {
	return mediana * math.Exp(sigma*r.NormFloat64())
}

// eski: har so'rov bazaga boradi, ~35 ms.
func eski(r *rand.Rand) float64 { return lognormal(r, 35, 0.3) }

// kesh: 96 % so'rov keshdan ~8 ms. 4 % keshda yo'q: sekin yo'l (sovuq disk, og'ir so'rov) ~400 ms.
func kesh(r *rand.Rand) float64 {
	if r.Float64() < 0.96 {
		return lognormal(r, 8, 0.3)
	}
	return lognormal(r, 400, 0.3)
}

// percentil: saralangan xs da "eng yaqin rang" usuli: p ulushdan kam bo'lmagan eng kichik qiymat.
func percentil(xs []float64, p float64) float64 {
	k := int(math.Ceil(p*float64(len(xs)))) - 1
	return xs[max(k, 0)]
}

func olcha(nom string, f func(*rand.Rand) float64) {
	r := rand.New(rand.NewPCG(1, 2))
	xs := make([]float64, n)
	var sum float64
	for i := range xs {
		xs[i] = f(r)
		sum += xs[i]
	}
	slices.Sort(xs)
	sh := make([]float64, sahifalar)
	for i := range sh {
		for range 100 {
			sh[i] = max(sh[i], f(r))
		}
	}
	slices.Sort(sh)
	fmt.Printf("%-4s so'rov:  o'rtacha %4.0f ms | p50 %4.0f ms | p99 %4.0f ms\n",
		nom, sum/n, percentil(xs, 0.50), percentil(xs, 0.99))
	fmt.Printf("%-4s sahifa: 100 so'rov   | p50 %4.0f ms | p99 %4.0f ms\n",
		nom, percentil(sh, 0.50), percentil(sh, 0.99))
}

func main() {
	olcha("eski", eski)
	olcha("kesh", kesh)
}
```

## A/B test: +10 % yutuqmi yoki shovqinmi?

Ikkinchi misol. Tugmani oʻzgartirdingiz va A/B test qildingiz: har bir tugmani 2000 kishi koʻrdi.

| Guruh | Koʻrdi | Sotib oldi | Konversiya |
|---|---|---|---|
| eski tugma | 2000 | 100 | 5.0 % |
| yangi tugma | 2000 | 110 | 5.5 % |

Yangi tugma bilan 10 % koʻp odam sotib oldi. Diqqat: bu **nisbiy** 10 % (110 / 100). Mutlaq farq esa 0.5 **foiz
punkti** (5.5 % − 5.0 %). Yangi tugmani chiqarishdan oldin tekshiramiz: hech narsa oʻzgarmasa, bunday farq qanchalik
tez-tez chiqadi?

`abtest` dasturi tugma testini 10 000 marta simulyatsiya qiladi. Avval ikkala tugma aynan bir xil (5 %) — bu **A/A
test**. Kohavi va hamkasblari A/A testni shunday taʼriflaydi: ikkala guruhga «exactly the same experience» (aynan bir
xil tajriba) beriladi. Ularda bu haqiqiy trafik bilan, bizda simulyatsiya.

Taxmin qiling: tugmalar bir xil boʻlsa, 10 000 tajribaning qanchasida yangi tugma «kamida +10 %» yutadi?

**A)** deyarli hech qachon (&lt; 1 %) · **B)** ~5 % · **C)** ~25 %

Demak, qariyb yarim tajribada 10 % lik farq **tasodifdan** chiqadi. «A» yoki «B» ni tanlagan boʻlsangiz, 2000 kishini

</details>

Qolgan qatorlar — toʻgʻri qaror qoidasi. **z-test** (NIST e-Handbook 7.3.3): ikki ulush farqini standart xatoga
boʻlamiz, natija 1.96 dan katta boʻlsa «farq bor» deymiz. 1.96 — 95 % ishonch chegarasi.

| Holat | z-test «farq bor» dedi | Maʼnosi |
|---|---|---|
| A/A, tugmalar bir xil | 4.8 % | yolgʻon signal (false positive): ~5 %, testning oʻzi shunday tuzilgan |
| A/B, yangi tugma rostdan +10 % (5.5 %) | 10.9 % | haqiqiy yaxshilanishni faqat ~11 % holatda topadi |

Test adashmaydi — u «bilmayman» deydi. 2000 kishida rostdan 10 % yaxshi tugma 10 tadan 9 holatda «farq yoʻq» boʻlib
chiqadi. Nega? Buni qoʻlda hisoblaymiz.

## Qoʻlda hisob: shovqin va guruh hajmi

**1. Shovqin qancha?** Ikki ulush farqining shovqini, yaʼni **standart xatosi** (NIST 7.3.3, guruhlar teng boʻlsa):

```text
standart xato = √( 2 · p · (1 − p) / n )
              = √( 2 · 0.05 · 0.95 / 2000 )
              ≈ 0.0069 = 0.69 foiz punkti
```

Dasturning oxirgi qatori ham shuni chiqardi: `0.69 foiz punkti`.

**2. Signal qancha?** «+10 %» — 5 % ning 10 % i, yaʼni 0.5 foiz punkti. Signal (0.5) shovqindan (0.69) **kichik**.
Shuning uchun bir xil tugmalar ham tez-tez ±10 % farq beradi.

**3. Shovqin qancha kichik boʻlishi kerak?** Farqni ishonchli koʻrish uchun shovqin farqdan qariyb 2.8 barobar kichik
boʻlishi kerak. 2.8 = 1.96 + 0.84: 1.96 — 95 % ishonch (yolgʻon signal 5 %), 0.84 — haqiqiy farqni 80 % holatda
topish (inglizcha *power*). Kohavi va boshq. (2009, §3.2) aynan shu 95 % va 80 % ni oladi.

```text
kerakli shovqin = 0.5 / 2.8 ≈ 0.18 foiz punkti
```

**4. Necha barobar koʻp odam?** Shovqin odamlar sonining ildiziga teskari kamayadi: odam 4 barobar koʻp boʻlsa,
shovqin 2 barobar kichik. Shovqinni 0.69 dan 0.18 ga tushirish uchun:

```text
(0.69 / 0.18)² ≈ 3.8² ≈ 15 barobar koʻp odam  →  2000 · 15 ≈ 30 000 kishi
```

**5. Aniq formula.** Kohavi, Longbotham, Sommerfield va Henne (2009) maqolasidagi (2)-formula (ular van Belle 2002 ga
tayanadi):

| Belgi | Maʼnosi | Bizda |
|---|---|---|
| n | har bir guruhdagi odamlar soni | ? |
| σ² | konversiyaning dispersiyasi: p · (1 − p) | 0.05 · 0.95 = 0.0475 |
| Δ | sezmoqchi boʻlgan eng kichik farq | 0.5 foiz punkti = 0.005 |
| 16 | 95 % ishonch va 80 % topish uchun koeffitsiyent ≈ 2 · 2.8² = 15.7 | 16 |

```text
n = 16 · σ² / Δ² = 16 · 0.0475 / 0.005² = 30 400 kishi har guruhga
```

### `abtest` kodi

```go filename="abtest/main.go" showLineNumbers
// abtest: tugma testini 10 000 marta simulyatsiya qiladi. Har guruhda n kishi, eski tugmada 5 % sotib oladi.
//
//	A/A: yangi tugma AYNAN BIR XIL (5 %). Har qanday "yutuq" shovqin.
//	A/B: yangi tugma haqiqatan +10 % (5.5 %). Test buni necha marta topadi?
//
// "Farq bor" qarori: ikki ulushning z-testi, |z| > 1.96 (95 % ishonch), NIST e-Handbook 7.3.3.
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
	"os"
	"strconv"
	"sync"
)

const (
	p          = 0.05 // eski tugma konversiyasi
	tajribalar = 10_000
	ishchilar  = 10 // har biri o'z generatori bilan 1000 tajriba: natija har safar bir xil
)

// sotdi: n kishidan nechtasi q ehtimol bilan sotib oldi.
func sotdi(r *rand.Rand, n int, q float64) int {
	k := 0
	for range n {
		if r.Float64() < q {
			k++
		}
	}
	return k
}

type natija struct{ plus10, minus10, farqBor int }

// sina: yangi tugmaning haqiqiy konversiyasi q bo'lganda 10 000 tajriba.
func sina(n int, q float64) natija {
	var mu sync.Mutex
	var jami natija
	var wg sync.WaitGroup
	for w := range ishchilar {
		wg.Go(func() {
			r := rand.New(rand.NewPCG(1, uint64(w)))
			var t natija
			for range tajribalar / ishchilar {
				a, b := sotdi(r, n, p), sotdi(r, n, q)
				nisbiy := float64(b-a) / float64(max(a, 1))
				if nisbiy >= 0.10 {
					t.plus10++
				}
				if nisbiy <= -0.10 {
					t.minus10++
				}
				pa, pb, pp := float64(a)/float64(n), float64(b)/float64(n), float64(a+b)/float64(2*n)
				if se := math.Sqrt(pp * (1 - pp) * 2 / float64(n)); se > 0 && math.Abs(pb-pa)/se > 1.96 {
					t.farqBor++
				}
			}
			mu.Lock()
			jami.plus10, jami.minus10, jami.farqBor = jami.plus10+t.plus10, jami.minus10+t.minus10, jami.farqBor+t.farqBor
			mu.Unlock()
		})
	}
	wg.Wait()
	return jami
}

func foiz(k int) float64 { return 100 * float64(k) / tajribalar }

func main() {
	n := 2000 // har bir guruhda
	if len(os.Args) > 1 {
		k, err := strconv.Atoi(os.Args[1])
		if err != nil || k < 100 {
			fmt.Fprintln(os.Stderr, "foydalanish: go run ./abtest [n >= 100]")
			os.Exit(2)
		}
		n = k
	}
	aa, ab := sina(n, p), sina(n, p*1.10)
	fmt.Printf("har guruhda %d kishi, %d tajriba\n", n, tajribalar)
	fmt.Println("A/A, tugmalar bir xil:")
	fmt.Printf("  yangi tugma >= +10 %%: %4.1f %%\n", foiz(aa.plus10))
	fmt.Printf("  yangi tugma <= -10 %%: %4.1f %%\n", foiz(aa.minus10))
	fmt.Printf("  z-test \"farq bor\":    %4.1f %%\n", foiz(aa.farqBor))
	fmt.Println("A/B, yangi tugma rostdan +10 %:")
	fmt.Printf("  z-test \"farq bor\":    %4.1f %%\n", foiz(ab.farqBor))
	fmt.Printf("qo'lda hisob: shovqin ~ sqrt(2*0.05*0.95/%d) = %.2f foiz punkti\n", n, 100*math.Sqrt(2*p*(1-p)/float64(n)))
}
```

| Big-O, graflar | DSA yoʻnalishida |
| sonlar nazariyasi | bu yoʻnalishda yoʻq |
| rasmiy isbot yozish | MIT 6.042 da «definitions, proofs, sets, functions, relations» kabi asoslar kursning qariyb uchdan bir qismi |
| integral va determinantni qoʻlda hisoblash | maʼnosini tushunamiz, hisobni kompyuter qiladi |
| statistik testlar jadvalini yodlash | Allen Downey: aslida bitta test bor — «all hypothesis tests are based on the same framework». Nol gipotezani simulyatsiya qilib, natijani solishtirasiz. Bugungi A/A aynan shunday |

## Usul: rasm, qoʻlda hisob, kod, oʻlchov

Oʻrganish usuli bugun koʻrganingizdek boʻladi. Har mavzuda bitta rasm, bitta qoʻlda hisob va bitta kod:

```text
rasm                    →  qoʻlda hisob       →  kod                   →  oʻlchov
100 soʻrovli sahifa        1 − 0.99¹⁰⁰           Go simulyatsiyasi        taxminni tekshiradi
(eng sekinini kutadi)      ≈ 63.4 %              63.5 %                   (mustaqilmi?)
```

Hisob va kod mos kelmasa, yo formulada, yo kodda xato bor. Mos kelsa ham, taxminni (masalan, mustaqillikni) faqat
haqiqiy oʻlchov tekshiradi. Grafiklarni Python va NumPy'da chizamiz, simulyatsiya va algoritmlarni Go'da yozamiz.

## Savol: 10 soʻrovli sahifa

Sahifa 10 ta soʻrov yuboradi, har birida 100 tadan bittasi bir soniyadan sekin. Sahifalarning necha foizi bir
soniyadan sekin ochiladi? Qoʻlda hisoblang.

**A)** ~1 % · **B)** ~10 % · **C)** ~63 %

<details>

**B: qariyb 9.6 %.** 1 − 0.99¹⁰ ≈ 1 − 0.904 = 0.096.

</details>

Bugun koʻrdik: oʻrtacha latency dumni yashiradi, 100 ta soʻrovda 1 % lik sekinlik 63 % ga aylanadi. 2000 kishilik

## Koʻp uchraydigan xatolar

**1. Relizni oʻrtacha latency bilan baholash (jim xato).** Hech qanday xato chiqmaydi: panel «oʻrtacha 37 → 25 ms»
deydi va reliz yaxshi koʻrinadi. Aslida p99 70 dan 492 ms ga oshgan («Qaysi reliz tezroq?» boʻlimi). **Tuzatish:**
p50, p99 (va sahifa darajasida) ni solishtiring, latency'ni gistogramma bilan kuzating.

**2. `1 − 0.99ᴺ` ni hamma joyda ishlaydi deb oʻylash.** Formula soʻrovlar mustaqil boʻlsa toʻgʻri. Sekinlik bogʻliq
boʻlsa-chi? Masalan, 1 % sahifada GC pauzasi boʻladi va oʻsha sahifaning *hamma* soʻrovi birga sekinlashadi. Bu
dastur kurs papkasida yoʻq, uni shu sahifa uchun yozdik (`bogliq` — «bogʻliq», correlated; papkada oʻz `go.mod` i
bor: `module bogliq`, `go 1.26`):

```go
// bogliq: fanout kabi, lekin sekinlik bog'liq: 1 % sahifada (masalan, GC pauzasi) hamma so'rov birga sekin.
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
)

const sahifalar = 100_000

func main() {
	r := rand.New(rand.NewPCG(1, 2))
	sekinSorov, sekinSahifa := 0, 0
	for range sahifalar {
		pauza := r.Float64() < 0.01 // shu sahifa paytida pauza bo'ldimi
		eng := 0.0
		for range 100 {
			t := 10 + 40*r.Float64()
			if pauza {
				t += 1000
				sekinSorov++
			}
			eng = max(eng, t)
		}
		if eng >= 1000 {
			sekinSahifa++
		}
	}
	fmt.Printf("so'rovlar: 1 s dan sekini %5.2f %%\n", 100*float64(sekinSorov)/float64(sahifalar*100))
	fmt.Printf("sahifalar (100 so'rovli): 1 s dan sekini %4.1f %%\n", 100*float64(sekinSahifa)/sahifalar)
	fmt.Printf("formula (mustaqil deb): 1 - 0.99^100 = %.1f %%\n", 100*(1-math.Pow(0.99, 100)))
}
```

```console
$ go run ./bogliq
so'rovlar: 1 s dan sekini  0.99 %
sahifalar (100 so'rovli): 1 s dan sekini  1.0 %
formula (mustaqil deb): 1 - 0.99^100 = 63.4 %
```

Sekin soʻrovlar yana ~1 %, lekin sekin sahifalar 63 % emas, 1.0 %: hamma sekin soʻrov bir xil sahifalarga toʻplandi.
Bitta qator farq qiladi: `pauza` sahifa uchun bir marta tanlanadi, har soʻrov uchun emas. Haqiqiy tizim bu ikki
chegara orasida boʻladi. **Tuzatish:** formulani yoʻnalish uchun ishlating, raqamni esa haqiqiy oʻlchovdan oling
(sahifa darajasidagi p99).

**3. «Har bir servisning p99'i 1 soniya» deyish.** Dean va Barroso maqolasida xuddi shunday yozilgan («99th-percentile
latency of one second»). Lekin bizning taʼrif boʻyicha bu «1 % soʻrov 1 s dan sekin» degani. Bu modelda bitta
soʻrovning p99'i ~50 ms (kurs README'si): 99-chegaradagi soʻrov hali tez guruhning eng sekini. **Tuzatish:** aniq
ayting: «soʻrovlarning 1 % i 1 s dan sekin».

**4. 2000 kishilik testda «+10 %» ni yutuq deb chiqarish (jim xato).** A/A simulyatsiyada bir xil tugmalar 24.4 %
holatda «+10 %» berdi («A/B test» boʻlimi). **Tuzatish:** testdan oldin `n = 16σ²/Δ²` bilan hajmni hisoblang, qarorni
z-test bilan qabul qiling va natijaga har kuni qarab, «yoqqanda» toʻxtatmang ([MATH-4.07](/lab/youtube/math#math-4-07)).

**5. Argumentga son boʻlmagan narsa berish.**

```console
$ go run ./abtest 2000kishi
foydalanish: go run ./abtest [n >= 100]
exit status 2
```

`strconv.Atoi("2000kishi")` xato qaytardi, dastur foydalanish xabarini («foydalanish» — usage) chiqarib, 2 kodi bilan
chiqdi. `exit status 2` qatorini `go run` qoʻshadi. `go run ./fanout 0` ham xuddi shunday toʻxtaydi: 0 ta soʻrovli
sahifada ulushni hisoblab boʻlmaydi. **Tuzatish:** faqat raqam bering: `go run ./abtest 30400` (100 va undan katta),
`go run ./fanout 20` (1 va undan katta) yoki `go run ./fanout jadval`.

## Oʻzingizni tekshiring

Avval oʻzingiz javob bering, keyin oching.

**1.** Sahifa 50 ta soʻrov yuboradi, har biri 100 tadan 1 holatda 1 s dan sekin. Sahifalarning necha foizi sekin?

**A)** ~5 % · **B)** ~40 % · **C)** ~50 %

<details>
<summary>Javob</summary>

**B.** 1 − 0.99⁵⁰ ≈ 1 − 0.605 = 39.5 % (`go run ./fanout jadval` dagi `N =  50` qatori). «C» ni tanlagan boʻlsangiz,
«N ta soʻrov → N %» qoidasini 50 gacha choʻzdingiz: u faqat kichik N uchun taxminan toʻgʻri.

</details>

**2.** Yangi reliz oʻrtacha latency'ni 37 dan 25 ms ga tushirdi. Uni chiqarish uchun bu yetarlimi?

<details>
<summary>Javob</summary>

Yoʻq. Oʻrtacha dumni yashiradi. `latency` modelida keshli relizning oʻrtachasi yaxshi, lekin p99 7 barobar yomon
(492 vs 70 ms). Sahifa 100 ta soʻrov yuborsa, 98 % sahifa kamida bitta sekin javobni kutadi va sahifa medianasi
531 ms ga chiqadi (eskisida 73 ms). p50 va p99 ni, imkon boʻlsa sahifa darajasida, solishtirish kerak.

</details>

**3.** A/A test nima va 2000 kishilik A/A simulyatsiyada nega qariyb yarim tajribada ±10 % farq chiqdi?

<details>
<summary>Javob</summary>

A/A test — ikkala guruh aynan bir xil narsani koʻradi, shuning uchun har qanday farq shovqin. 2000 kishida farqning
standart xatosi ~0.69 foiz punkti, «+10 %» esa 0.5 foiz punkti: signal shovqindan kichik. Shuning uchun 24.4 % tajribada
«≥ +10 %», 22.4 % da «≤ −10 %» chiqdi.

</details>

**4.** 30 400 kishi +10 % farqni 80 % holatda topadi. Endi +5 % farqni (5 % → 5.25 %) xuddi shunday sezmoqchisiz.
Har guruhga taxminan nechta odam kerak?

**A)** ~61 000 (2 barobar) · **B)** ~122 000 (4 barobar) · **C)** ~30 400, oʻsha-oʻsha

<details>
<summary>Javob</summary>

**B.** `n = 16σ²/Δ²`: Δ ikki barobar kichik boʻlsa, Δ² toʻrt barobar kichik, n toʻrt barobar katta:
16 · 0.0475 / 0.0025² = 121 600. Kohavi maqolasining oʻzi xuddi shu misolda «less than 122,000 users» deydi. «A» ni
tanlagan boʻlsangiz, shovqin odamlar soniga teskari kamayadi deb oʻyladingiz: aslida uning **ildiziga** teskari.

</details>

**5.** GO-1.07 dan: bitta benchmark yangi versiyada 5 % tez chiqdi. Nega bunga ishonmasdan, `-count 10` va
`benchstat` kerak?

<details>
<summary>Javob</summary>

Chunki bitta oʻlchovda ham shovqin bor (kompyuter yuklamasi, kesh, chastota). Bugungi A/A test kabi, farq «yoʻq»
boʻlsa ham bitta natija ±5 % koʻrsatishi mumkin. `benchstat` koʻp oʻlchovdan mediana va ishonch oraligʻini beradi
va farq statistik jihatdan haqiqiymi, aytadi (`~` — «farq yoʻq»). Bu bugungi z-test bilan bir xil savol.

</details>

  toping, keyin `go run ./fanout 20` bilan tekshiring.
- 🟡 **Oʻrta:** har soʻrov 1000 tadan 1 holatda 1 s dan sekin. 100 soʻrovli sahifa qanday boʻladi?
- 🟠 **Qiyin:** 5 % konversiyada +5 % nisbiy oʻsishni (5 % → 5.25 %) koʻrish uchun maqoladagi formula bilan har

- 🔴 **Guru:** `kesh` relizida p99 &lt; 100 ms boʻlishi uchun kesh soʻrovlarning necha foizini ushlashi kerak?

<details>
<summary>Javob</summary>

Javob dasturi:

```go filename="homework/main.go" showLineNumbers
// Uy vazifasi javoblari: go run ./homework
package main

import (
	"fmt"
	"math"
	"math/rand/v2"
	"slices"
)

func main() {
	// Oson: 20 so'rovli sahifa, har so'rov 100 tadan 1 holatda 1 s dan sekin.
	fmt.Printf("oson:  1 - 0.99^20 = %.1f %% (tekshiring: go run ./fanout 20)\n", 100*(1-math.Pow(0.99, 20)))

	// O'rta: har so'rov 1000 tadan 1 holatda 1 s dan sekin bo'lsa, 100 so'rovli sahifa.
	fmt.Printf("o'rta: 1 - 0.999^100 = %.1f %% (100 tadan 1 bo'lganda 63.4 %% edi)\n", 100*(1-math.Pow(0.999, 100)))

	// Qiyin: Kohavi formulasi n = 16*sigma^2/delta^2, 5 % konversiya, +5 % nisbiy (5 % -> 5.25 %).
	sigma2, delta := 0.05*0.95, 0.05*0.05
	fmt.Printf("qiyin: n = 16*0.0475/0.0025^2 = %.0f kishi har guruhda\n", 16*sigma2/(delta*delta))

	// Guru: kesh relizida p99 < 100 ms bo'lishi uchun kesh qancha so'rovni ushlashi kerak?
	for _, hit := range []float64{0.96, 0.98, 0.99, 0.995} {
		fmt.Printf("guru:  kesh %.1f %% -> p99 %4.0f ms\n", 100*hit, p99(hit))
	}
}

func p99(hit float64) float64 {
	r := rand.New(rand.NewPCG(1, 2))
	xs := make([]float64, 100_000)
	for i := range xs {
		m := 400.0
		if r.Float64() < hit {
			m = 8
		}
		xs[i] = m * math.Exp(0.3*r.NormFloat64())
	}
	slices.Sort(xs)
	return xs[int(math.Ceil(0.99*float64(len(xs))))-1]
}
```

| Qator | Nima qiladi |
|---|---|
| 13 | Oson: `1 − 0.99²⁰` |
| 16 | Oʻrta: `1 − 0.999¹⁰⁰` |
| 19–20 | Qiyin: σ² = 0.05 · 0.95, Δ = 5 % ning 5 % i = 0.0025; `16σ²/Δ²` |
| 23–25 | Guru: toʻrtta kesh ulushi (`hit` — keshdan topilgan ulush) uchun p99 |
| 28–40 | `p99(hit)`: `latency` dagi `kesh` modeli, lekin kesh ulushi parametr; 100 000 soʻrov, eng yaqin rang usulidagi p99 |

🟡 63.4 % → 9.5 %. Har soʻrovning sekin holati 10 barobar kamaydi, sekin sahifalar esa 6.7 barobar. 100 soʻrovli
