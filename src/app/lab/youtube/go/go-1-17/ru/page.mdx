## Что вы узнаете

В официальном FAQ Go до сих пор стоит фраза: *"We do not anticipate that Go will ever add generic methods"* — «мы не
ожидаем, что в Go когда-либо появятся generic-методы». Но Go 1.27 их добавил. Один и тот же файл в Go 1.26 — синтаксическая
ошибка, а в Go 1.27 работает. Условие только одно, и тот же FAQ до сих пор называет это условие «неприемлемым».
Что это за условие и почему команда Go выбрала именно его?

**Одна идея:** параметр типа нужен, чтобы один раз написать одинаковый код для разных типов, а интерфейс — для
поведения. В Go 1.27 методы тоже стали generic, но generic-метод не реализует ни одного интерфейса.

К концу урока вы:

- будете писать параметры типа и ограничения, поймёте, зачем нужен `~` и как устроен `cmp.Ordered`;
- напишете generic-метод Go 1.27 и заранее скажете, когда он не скомпилируется (`go.mod`, интерфейс);
- узнаете лишний generic-код по трём признакам и превратите его в интерфейс или обычную функцию;
- проверите утверждение «дженерики быстрее интерфейсов» бенчмарком, `-gcflags=-m` и `go tool nm`.

Три главных новых слова урока:

| Слово | Простой смысл | По-английски |
|---|---|---|
| параметр типа | имя типа в квадратных скобках в объявлении функции или типа (`T`); какой это тип, решает вызов | type parameter |
| ограничение | интерфейс, который ограничивает, какими типами может быть параметр типа (`cmp.Ordered`) | constraint |
| generic-метод | метод, который объявляет собственный параметр типа: `func (r Royxat[T]) Aylantir[U any](…)` (Go 1.27+) | generic method |

По пути встретятся два вспомогательных слова: **вывод типов** (*type inference*, компилятор сам находит тип по
аргументам) и **инстанцирование** (*instantiation*, вместо `T` подставляется конкретный тип). Оба увидим в первой
программе.

## Загадка: FAQ говорит «никогда», Go 1.27 запускает

Программа из папки `hook/`. Пока не обязательно понимать каждую строку: `[T any]` и `[U any]` разберём в следующих
разделах.

```go filename="hook/main.go" showLineNumbers
// hook: Go 1.27 dagi generic metod. Xuddi shu fayl ../eski da (go 1.26) kompilyatsiya boʻlmaydi.
// go run ./hook
package main

import "fmt"

type Royxat[T any] []T

// Aylantir har bir elementga f ni qoʻllaydi.
// U — metodning oʻz type parametri: Go 1.27 dan beri mumkin.
func (r Royxat[T]) Aylantir[U any](f func(T) U) Royxat[U] {
	natija := make(Royxat[U], len(r))
	for i, x := range r {
		natija[i] = f(x)
	}
	return natija
}

func main() {
	summalar := Royxat[int64]{150000, 99000, 42000}
	matn := summalar.Aylantir(func(s int64) string {
		return fmt.Sprintf("%d soʻm", s)
	})
	fmt.Println(matn)
}
```

| Строка | Код | Что делает |
|---|---|---|
| 7 | `type Royxat[T any] []T` | `Royxat` («список») — тип слайса с элементами типа `T`; `T` — параметр типа, `any` — любой тип |
| 11 | `func (r Royxat[T]) Aylantir[U any](f func(T) U) Royxat[U]` | после имени метода свои квадратные скобки: `U` — **собственный** параметр типа метода. `f` превращает каждый `T` в `U`, результат — `Royxat[U]` |
| 12 | `natija := make(Royxat[U], len(r))` | `natija` («результат»): новый слайс той же длины, что `r`, с элементами `U` |
| 13–15 | `for i, x := range r { natija[i] = f(x) }` | применяет `f` к каждому элементу |
| 20 | `Royxat[int64]{150000, 99000, 42000}` | вместо `T` — `int64`: `summalar` («суммы»), суммы заказов в сумах |
| 21–23 | `summalar.Aylantir(func(s int64) string {…})` | `U` = `string`: каждая сумма становится текстом |
| 24 | `fmt.Println(matn)` | печатает слайс в виде `[a b c]` |

В TypeScript это обычное дело: метод `map<U>(f: (x: T) => U): U[]` у `Array<T>` — именно такой generic-метод.
А в Go до 1.27 такой метод написать было нельзя.

В папке `eski/` («старый») лежит ровно этот файл (`diff` ничего не печатает, значит файлы одинаковы):

```console
$ diff hook/main.go eski/main.go
```

Разница только в `eski/go.mod`: там `go 1.26`. Сначала соберём его старым Go 1.26.8, установленным на компьютере.
`GOTOOLCHAIN=local` — не скачивать другой Go, использовать установленный; `-o /dev/null` — никуда не записывать
бинарник.

Подумайте: что Go 1.26.8 сделает с этим файлом?

**A)** соберёт, программа запустится · **B)** соберёт, но с предупреждением · **C)** ошибка компиляции

<details>
<summary>Ответ</summary>

**C.** В грамматике Go 1.26 после имени метода не может быть квадратных скобок. Парсер останавливается на `[U any]`
в строке 11. Если вы выбрали «B»: в Go нет «сборки с предупреждением», код либо компилируется, либо нет.

</details>

```console
$ cd eski && GOTOOLCHAIN=local go version && GOTOOLCHAIN=local go build -o /dev/null .
go version go1.26.8 linux/amd64
# eski
./main.go:11:28: syntax error: method must have no type parameters
```

*syntax error: method must have no type parameters* — «синтаксическая ошибка: у метода не должно быть параметров
типа». `11:28` — строка 11, столбец 28, то есть начало `[U any]`. Теперь тот же код в Go 1.27.4 (в `go.mod` у
`hook/` стоит `go 1.27`):

```console
$ go version && go run ./hook
go version go1.27.4 linux/amd64
[150000 soʻm 99000 soʻm 42000 soʻm]
```

Release notes Go 1.27: *"Go 1.27 now supports generic methods: a method declaration may declare its own type
parameters"* — «объявление метода может объявлять собственные параметры типа». Этот метод объявляет свой параметр
типа `U`. Условие только одно. Его увидим в разделе «Ограничение».

План урока: сначала параметр типа и ограничение, потом generic-методы и их ограничение, в конце самый важный
вопрос: когда generic-код лишний?

## Параметр типа: одинаковый код, разные типы

В программе из `katta/` («больший») две функции. Одна возвращает большее из двух целых чисел, другая — большую из
двух строк. Код одинаковый, отличается только тип.

```go filename="katta/main.go" showLineNumbers
// katta: bir xil kod ikki marta, faqat tur boshqa → bitta generic funksiya.
// go run ./katta
package main

import (
	"cmp"
	"fmt"
)

func KattaInt(a, b int) int {
	if a > b {
		return a
	}
	return b
}

func KattaString(a, b string) string {
	if a > b {
		return a
	}
	return b
}

// T — type parameter, cmp.Ordered — uning constraint'i.
func Katta[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}

func main() {
	fmt.Println(Katta(3, 7), Katta(1.5, 0.5), Katta("olma", "nok"))
	fmt.Println(Katta[int64](150000, 99000))
	fmt.Println(KattaInt(3, 7), KattaString("olma", "nok"))
}
```

| Строка | Код | Что делает |
|---|---|---|
| 6 | `"cmp"` | пакет `cmp` стандартной библиотеки (Go 1.21+): там лежит `cmp.Ordered` |
| 10–15 | `func KattaInt(a, b int) int` | для `int`: `a`, если `a > b`, иначе `b` |
| 17–22 | `func KattaString(a, b string) string` | ровно тот же код, только для `string` (строки сравниваются в алфавитном порядке) |
| 25 | `func Katta[T cmp.Ordered](a, b T) T` | `T` в квадратных скобках — **параметр типа**; `cmp.Ordered` — **ограничение**: `T` может быть только типом, который сравнивается через `<` и `>` |
| 26–29 | `if a > b { return a }; return b` | тело такое же, как у двух предыдущих |
| 33 | `Katta(3, 7), Katta(1.5, 0.5), Katta("olma", "nok")` | три вызова, три типа, тип мы не писали (`olma` — «яблоко», `nok` — «груша») |
| 34 | `Katta[int64](150000, 99000)` | тип указали сами в квадратных скобках |
| 35 | `KattaInt(3, 7), KattaString("olma", "nok")` | две старые функции, для сравнения |

Та же функция в других языках (обе запущены: TypeScript 5.9.3, Python 3.13):

```text
TypeScript:  function katta<T extends number | string>(a: T, b: T): T { return a > b ? a : b; }
Python 3.12+: def katta[T: (int, str)](a: T, b: T) -> T: return a if a > b else b
Go:          func Katta[T cmp.Ordered](a, b T) T { if a > b { return a }; return b }
```

`<T extends …>` в TS — это `[T ограничение]` в Go. Разница во время выполнения: TS и Python используют типы только
для проверки. Когда программа работает, остаётся одна функция JS или Python, и через неё проходит любое значение.
Компилятор Go сам проверяет тип и генерирует машинный код: `Katta(3, "nok")` вообще не скомпилируется. В PHP
дженериков в самом языке нет: аннотации `@template` проверяют PHPStan и Psalm.

Когда писать параметр типа? Ian Lance Taylor, *When To Use Generics* (блог Go, 2022): *"avoid type parameters until
you notice that you are about to write the exact same code multiple times"* — «не используйте параметры типа, пока
не заметите, что собираетесь написать точно такой же код несколько раз». У нас именно этот случай: `KattaInt` и
`KattaString`.

Подумайте: какая первая строка у `go run ./katta`?

**A)** `7 1.5 olma` · **B)** `7 1.5 nok` · **C)** ошибка компиляции: для `Katta` не указан тип

<details>
<summary>Ответ</summary>

**A.** `"olma"` больше `"nok"`, потому что строки сравниваются побайтово, а `o` (111) идёт после `n` (110). Если вы
выбрали «B», вы думали, что сравнивается длина строки. Если «C»: тип писать не обязательно, компилятор находит его
по аргументам.

</details>

```console
$ go run ./katta
7 1.5 olma
150000
7 olma
```

`Katta` сработала с целым числом, дробным числом и строкой, а тип мы так и не написали. Компилятор сам нашёл `T` по
аргументам: `int` из `3` и `7`, `float64` из `1.5`. Это называется **вывод типов** (*type inference*). Во второй
строке мы указали тип сами: `Katta[int64]`. В обоих случаях компилятор подставляет вместо `T` конкретный тип: это
называется **инстанцирование** (*instantiation*). Спецификация Go: *"A generic function, method, or type is
instantiated by substituting type arguments for the type parameters"*.

| Вызов | Откуда `T` | `T` | Результат |
|---|---|---|---|
| `Katta(3, 7)` | вывод типов | `int` | `7` |
| `Katta(1.5, 0.5)` | вывод типов | `float64` | `1.5` |
| `Katta("olma", "nok")` | вывод типов | `string` | `olma` |
| `Katta[int64](150000, 99000)` | указали сами | `int64` | `150000` |

Одно замечание: с Go 1.21 в самом языке есть функция `max`. Её сигнатура ровно такая:

```console
$ go doc builtin.max | sed -n 3p
func max[T cmp.Ordered](x T, y ...T) T
```

`Katta` — только пример. Прежде чем писать дженерик, поищите готовый: `max`, `min`, пакеты `slices`, `maps`.

## Ограничение — это интерфейс

Ограничение на самом деле обычный интерфейс. Только кроме методов в нём может быть ещё и список типов. Такой список
задаёт **набор типов** интерфейса (*type set*), то есть множество типов, которые он разрешает.

```go filename="cheklov/main.go" showLineNumbers
// cheklov: oʻz constraint'imiz. ~int64 — "asosiy turi int64 boʻlgan har qanday tur".
// go run ./cheklov
package main

import "fmt"

type Son interface {
	~int64 | ~float64
}

type Ball int64 // asosiy (underlying) turi int64

func Jami[T Son](xs []T) T {
	var s T
	for _, x := range xs {
		s += x
	}
	return s
}

func main() {
	fmt.Println(Jami([]Ball{90, 85, 70}))
	fmt.Println(Jami([]float64{1.5, 2.25}))
}
```

| Строка | Код | Что делает |
|---|---|---|
| 7–9 | `type Son interface { ~int64 \| ~float64 }` | `Son` («число») — ограничение: два типа, `\|` — «или». Методов нет, только типы |
| 8 | `~` (тильда) | «все типы, у которых **базовый тип** такой» (ниже) |
| 11 | `type Ball int64` | `Ball` («балл») — новый именованный тип, его базовый тип (*underlying type*) — `int64` |
| 13 | `func Jami[T Son](xs []T) T` | `Jami` («итого»): `T` — только один из типов в `Son` |
| 14 | `var s T` | нулевое значение `T`: `0` |
| 16 | `s += x` | разрешено, потому что каждый тип в `Son` умеет `+` |
| 22 | `Jami([]Ball{90, 85, 70})` | `T` = `Ball` |
| 23 | `Jami([]float64{1.5, 2.25})` | `T` = `float64` |

Похоже на `T extends number | string` в TS. Но в Go `type Ball int64` — не псевдоним `int64`, а отдельный тип (как
`type Status int` в [GO-1.03](/lab/youtube/go/go-1-03/ru)). Поэтому и нужен `~`. Спецификация Go: *"The type set of a term of the
form ~T is the set of all types whose underlying type is T"* — «набор типов терма `~T` — все типы, базовый тип
которых `T`».

```console
$ go run ./cheklov
245
3.75
```

90 + 85 + 70 = 245, 1.5 + 2.25 = 3.75. Теперь уберём знак `~`. `tildesiz/main.go` («без тильды») везде такой же,
отличаются только строки 7–9:

```go
type Son interface {
	int64 | float64
}
```

```console
$ go build -o /dev/null ./tildesiz
# generics/tildesiz
tildesiz/main.go:22:18: Ball does not satisfy Son (possibly missing ~ for int64 in Son)
```

Читаем ошибку: строка 22, `Jami([]Ball{…})`. *Ball does not satisfy Son* — «`Ball` не удовлетворяет `Son`». В скобках
компилятор даже подсказывает: *possibly missing ~ for int64 in Son* — «возможно, в `Son` перед `int64` пропущен
`~`». Без `~` набор типов `Son` — всего два типа: `int64` и `float64`. `Ball` среди них нет.

| `Son` | `int64` | `Ball` (базовый тип `int64`) | `float64` |
|---|---|---|---|
| `~int64 \| ~float64` | да | да | да |
| `int64 \| float64` | да | **нет** | да |

`cmp.Ordered` в стандартной библиотеке написан так же:

```console
$ sed -n 18,23p $(go env GOROOT)/src/cmp/cmp.go
type Ordered interface {
	~int | ~int8 | ~int16 | ~int32 | ~int64 |
		~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 | ~uintptr |
		~float32 | ~float64 |
		~string
}
```

Перед каждым типом стоит `~`, поэтому `cmp.Ordered` работает и с вашими собственными типами: `Katta(Ball(90),
Ball(85))` компилируется.

## Generic-методы (Go 1.27)

Тип `Royxat` — generic, его элементы типа `T`. С Go 1.18 у generic-типов есть методы, но они могут использовать
только `T` из receiver. А если нужен новый тип? `royxat/` — способ Go 1.18–1.26:

```go filename="royxat/main.go" showLineNumbers
// royxat: Go 1.18–1.26 usuli. Metod faqat receiver'dagi T ni ishlata oladi,
// yangi tur (U) kerak boʻlsa — paket darajasidagi funksiya.
// go run ./royxat
package main

import "fmt"

type Royxat[T any] []T

// Filtr: faqat T kerak — metod boʻla oladi (Go 1.18 dan beri).
func (r Royxat[T]) Filtr(ok func(T) bool) Royxat[T] {
	var natija Royxat[T]
	for _, x := range r {
		if ok(x) {
			natija = append(natija, x)
		}
	}
	return natija
}

// Aylantir: yangi U kerak — 1.27 gacha faqat funksiya.
func Aylantir[T, U any](r Royxat[T], f func(T) U) Royxat[U] {
	natija := make(Royxat[U], len(r))
	for i, x := range r {
		natija[i] = f(x)
	}
	return natija
}

func main() {
	r := Royxat[int64]{150000, 99000, 42000}
	fmt.Println(Aylantir(r.Filtr(katta), somda))
}

func katta(s int64) bool   { return s > 50000 }
func somda(s int64) string { return fmt.Sprintf("%d soʻm", s) }
```

| Строка | Код | Что делает |
|---|---|---|
| 8 | `type Royxat[T any] []T` | generic-тип: элементы `T` |
| 11 | `func (r Royxat[T]) Filtr(ok func(T) bool) Royxat[T]` | `Filtr` («фильтр») не нужен новый тип, только `T` из receiver: поэтому это метод |
| 12–18 | `var natija …; if ok(x) { natija = append(natija, x) }` | собирает элементы, для которых `ok` вернул true |
| 22 | `func Aylantir[T, U any](r Royxat[T], f func(T) U) Royxat[U]` | `Aylantir` («преобразовать») возвращает новый тип `U`: до 1.27 это могла быть только функция уровня пакета |
| 31 | `r := Royxat[int64]{…}` | три суммы |
| 32 | `Aylantir(r.Filtr(katta), somda)` | сначала `r.Filtr(katta)`, потом его результат идёт в `Aylantir` |
| 35 | `func katta(s int64) bool` | суммы больше 50 000 сумов |
| 36 | `func somda(s int64) string` | `somda` («в сумах») превращает сумму в текст `"… soʻm"` |

До 1.27 FAQ Go советовал именно это: *"use top-level functions with type parameters"* — «используйте функции уровня
пакета с параметрами типа». Вызов в строке 32 читается изнутри наружу: сначала внутренний `r.Filtr(katta)`, потом
внешний `Aylantir`. `map(somda, filter(katta, r))` в Python читается так же.

Подумайте: что напечатает `go run ./royxat`?

**A)** `[150000 soʻm 99000 soʻm 42000 soʻm]` · **B)** `[150000 soʻm 99000 soʻm]` · **C)** `[42000 soʻm]`

<details>
<summary>Ответ</summary>

**B.** `katta` оставляет суммы больше 50 000: 150 000 и 99 000. 42 000 фильтр не проходит. Если вы выбрали «A», вы
не учли `Filtr`. Если «C», вы прочитали `katta` наоборот.

</details>

```console
$ go run ./royxat
[150000 soʻm 99000 soʻm]
```

В Go 1.27 `Aylantir` может быть методом. `zanjir/` («цепочка») во всём остальном такой же, как `royxat/`:

```go filename="zanjir/main.go" showLineNumbers
// zanjir: Go 1.27 usuli. Aylantir endi metod — chaqiruvlar chapdan oʻngga oʻqiladi.
// go run ./zanjir
package main

import "fmt"

type Royxat[T any] []T

func (r Royxat[T]) Filtr(ok func(T) bool) Royxat[T] {
	var natija Royxat[T]
	for _, x := range r {
		if ok(x) {
			natija = append(natija, x)
		}
	}
	return natija
}

// U — metodning oʻz type parametri (Go 1.27).
func (r Royxat[T]) Aylantir[U any](f func(T) U) Royxat[U] {
	natija := make(Royxat[U], len(r))
	for i, x := range r {
		natija[i] = f(x)
	}
	return natija
}

func main() {
	r := Royxat[int64]{150000, 99000, 42000}
	fmt.Println(r.Filtr(katta).Aylantir(somda))
}

func katta(s int64) bool   { return s > 50000 }
func somda(s int64) string { return fmt.Sprintf("%d soʻm", s) }
```

Новые строки:

| Строка | Код | Что делает |
|---|---|---|
| 20 | `func (r Royxat[T]) Aylantir[U any](f func(T) U) Royxat[U]` | `T` приходит из receiver, а `U` в квадратных скобках принадлежит самому методу: это **generic-метод** |
| 30 | `r.Filtr(katta).Aylantir(somda)` | слева направо: сначала фильтр, потом преобразование. `U` = `string`, нашёл вывод типов |

```console
$ go run ./zanjir
[150000 soʻm 99000 soʻm]
```

Результат тот же. Теперь это очень похоже на `r.filter(katta).map(somda)` в JS. Автор предложения Robert Griesemer
(golang/go#77273) приводит две причины. Первая — чтение: *"x.a().b().c() may naturally be read left to right,
whereas c(b(a(x))) is evaluated inside out"*. Вторая: *"A method is a function associated with a type"* — функция
привязана к своему типу и живёт в пространстве имён этого типа.

| | Go 1.18–1.26 | Go 1.27 |
|---|---|---|
| метод с `T` из receiver (`Filtr`) | да | да |
| метод с собственным параметром типа (`Aylantir[U]`) | **нет**: syntax error | да: generic-метод |
| вызов | `Aylantir(r.Filtr(katta), somda)` | `r.Filtr(katta).Aylantir(somda)` |

## В стандартной библиотеке: rand.N

В стандартной библиотеке тоже появился такой метод: `(*Rand).N` в пакете `math/rand/v2`.

$ sed -n 210,213p $(go env GOROOT)/src/math/rand/v2/rand.go

// The type parameter Int can be any integer type.

Его параметр типа `Int` принимает любой целочисленный тип: ограничение `intType` — это `~int | ~int8 | … |
~uintptr` (строки 340–343 того же файла). В исходниках go1.27.4, не считая тестов, это единственный generic-метод
(проверено командой `grep` из README курса).

```go filename="randn/main.go" showLineNumbers
// randn: standart kutubxonadagi birinchi generic metod — (*rand.Rand).N (Go 1.27).
// go run ./randn
package main

import (
	"fmt"
	"math/rand/v2"
	"time"
)

func main() {
	r := rand.New(rand.NewPCG(1, 2))  // doimiy seed: natija har safar bir xil
	fmt.Println(r.N(10))              // int
	fmt.Println(r.N(int64(150000)))   // int64
	fmt.Println(r.N(3 * time.Second)) // time.Duration
	fmt.Printf("%T\n", r.N[uint8])    // aniq tur bilan instantiate
}
```

| 13 | `r.N(10)` | `Int` = `int`: одно число из 0…9 |
| 14 | `r.N(int64(150000))` | `Int` = `int64` |
| 15 | `r.N(3 * time.Second)` | `Int` = `time.Duration` (базовый тип `int64`, поэтому входит в `~int64`): 0…3 секунды |
| 16 | `fmt.Printf("%T\n", r.N[uint8])` | не вызываем, только инстанцируем: `%T` печатает тип значения |

## Ограничение: generic-метод не реализует интерфейс

Теперь к условию из начала. Оно состоит из двух частей. Release notes Go 1.27: *"methods of interfaces may not
declare type parameters nor can interface methods be implemented by generic methods"*.

**Первая часть:** метод интерфейса не может объявить собственный параметр типа.

```go filename="imetod/main.go" showLineNumbers
// imetod: ATAYLAB kompilyatsiya boʻlmaydi. Interface metodi type parameter e'lon qila olmaydi.
// go build -o /dev/null ./imetod   (plain "go build ./imetod" collides with the folder name)
package main

type Aylantiruvchi interface {
	Aylantir[U any](f func(int64) U) []U
}

func main() {}
```

```console
$ go build -o /dev/null ./imetod
# generics/imetod
imetod/main.go:6:10: interface method must have no type parameters
imetod/main.go:6:32: undefined: U
```

*interface method must have no type parameters* — «у метода интерфейса не должно быть параметров типа». Вторая
ошибка — следствие первой: `[U any]` отвергнут, поэтому `U` не объявлен (*undefined*). А вот **собственные**
параметры типа интерфейса использовать можно (спецификация: *"they may use type parameters from the interface
declaration"*):

```go
type Oluvchi[T any] interface{ Ol() T } // ruxsat: T interface'niki
```

(Комментарий: «разрешено: `T` принадлежит интерфейсу».)

**Вторая часть:** generic-метод не реализует ни одного интерфейса. `ibajar/`:

```go filename="ibajar/main.go" showLineNumbers
// ibajar: ATAYLAB kompilyatsiya boʻlmaydi. Generic metod interface metodini bajarmaydi.
// go build -o /dev/null ./ibajar   (plain "go build ./ibajar" collides with the folder name)
package main

import "fmt"

type Bosh struct{}

func (Bosh) Nop[T any](x T) T { return x }

type MatnNop interface {
	Nop(string) string
}

func main() {
	var b Bosh
	fmt.Println(b.Nop("salom"), b.Nop(42)) // toʻgʻridan-toʻgʻri: ishlaydi
	var _ MatnNop = b                      // interface orqali: yoʻq
}
```

| Строка | Код | Что делает |
|---|---|---|
| 7 | `type Bosh struct{}` | `Bosh` («пустой») — структура без полей |
| 9 | `func (Bosh) Nop[T any](x T) T` | generic-метод: принимает любой `T` и возвращает его же |
| 11–13 | `type MatnNop interface { Nop(string) string }` | интерфейс с обычным методом: принимает строку, возвращает строку |
| 17 | `b.Nop("salom"), b.Nop(42)` | прямой вызов: `T` = `string`, потом `int` (комментарий: «напрямую: работает») |
| 18 | `var _ MatnNop = b` | попытка положить `Bosh` в `MatnNop`; `_` — значение не нужно, только проверка (комментарий: «через интерфейс: нет») |

В TypeScript тот же код работает: `class Bosh { nop<T>(x: T): T }` спокойно присваивается `interface MatnNop \{
nop(x: string): string \}` (проверено в tsc 5.9.3). А в Go?

**A)** компилируется, печатает `salom 42` · **B)** ошибка компиляции в строке 18 · **C)** компилируется, panic в
строке 18

<details>
<summary>Ответ</summary>

**B.** В Go 1.27 generic-метод не реализует метод интерфейса, даже если с `T` = `string` он бы подошёл. Компилятор
выясняет это заранее, поэтому это ошибка компиляции, а не panic. Если вы выбрали «A», вы думали, что Go ведёт себя
как TypeScript. Строка 17 при этом в порядке: прямой вызов работает.

</details>

```console
$ go build -o /dev/null ./ibajar
# generics/ibajar
ibajar/main.go:18:18: cannot use b (variable of struct type Bosh) as MatnNop value in variable declaration: Bosh does not implement MatnNop (wrong type for method Nop)
		have Nop[T any](T) T
		want Nop(string) string
```

Читаем ошибку: *cannot use b … as MatnNop value* — «нельзя использовать `b` как значение `MatnNop`». Причина:
*Bosh does not implement MatnNop (wrong type for method Nop)* — «`Bosh` не реализует `MatnNop` (неверный тип метода
`Nop`)». Дальше разница: *have* (есть у нас) `Nop[T any](T) T` — generic-метод, *want* (требуется)
`Nop(string) string` — обычный метод.

Любопытно, что FAQ Go до сих пор называет этот путь *"unacceptable"* — «неприемлемым».

## Почему выбрали именно так?

В [GO-1.13](/lab/youtube/go/go-1-13/ru) мы видели: внутри интерфейса лежит пара (тип, значение), а `x.(T)` проверяет тип во время
работы программы. Значит, реализация интерфейса проверяется и во время работы программы. А у generic-метода
бесконечно много вариантов: `Nop[string]`, `Nop[int]`, `Nop[Ball]`, … Компилятор записывает в бинарник только
варианты, использованные в коде. Если во время работы программы у `Bosh` внутри `any` попросят
`Nop(float32) float32`, такого варианта в бинарнике может не оказаться.

FAQ Go (*Why does Go not support methods with type parameters?*) перечисляет четыре пути:

| # | Путь | Примечание |
|---|---|---|
| 1 | после линковки перекомпилировать нужные варианты | сборка замедляется |
| 2 | JIT | компиляция в runtime |
| 3 | медленный запасной код | скорость нельзя предсказать заранее |
| 4 | generic-метод вообще не реализует интерфейсы | FAQ: *"unacceptable from a design point of view"* → выбор Go 1.27 |

Четвёртый там назван неприемлемым, но Go 1.27 выбрал именно его. Griesemer объяснил причину в предложении
(golang/go#77273, *"A change of view"*): методы нужны не только для интерфейсов, но и чтобы упорядочивать код. Его
слова: *"concrete methods are a language feature that is useful in itself, irrespective of interfaces"*. В
TypeScript такой проблемы нет: типы стираются до запуска программы, и одна функция JS обслуживает все типы.

Запустим пример из FAQ на Go 1.27. Положим значение `Bosh` в пустой интерфейс и спросим у него метод `Nop`:

```go filename="faq/main.go" showLineNumbers
// faq: Go FAQ'dagi misol (generic_methods), Go 1.27 da ishga tushirilgan.
// Bosh qiymati any ichida: dastur ishlayotganda uning generic metodi koʻrinmaydi.
// go run ./faq
package main

import (
	"fmt"
	"reflect"
)

type Bosh struct{}

func (Bosh) Nop[T any](x T) T { return x }
func (Bosh) Oddiy()           {}

func main() {
	var x any = Bosh{}
	_, ok := x.(interface{ Nop(string) string })
	fmt.Println("Nop(string) string bormi?", ok)
	_, ok = x.(interface{ Nop(int) int })
	fmt.Println("Nop(int) int bormi?", ok)
	_, ok = x.(interface{ Oddiy() })
	fmt.Println("Oddiy() bormi?", ok)
	fmt.Println("reflect koʻrgan metodlar:", reflect.TypeOf(x).NumMethod())
}
```

| Строка | Код | Что делает |
|---|---|---|
| 13 | `func (Bosh) Nop[T any](x T) T` | generic-метод |
| 14 | `func (Bosh) Oddiy()` | `Oddiy` («обычный») — обычный метод, для сравнения |
| 17 | `var x any = Bosh{}` | `Bosh` внутри пустого интерфейса |
| 18, 20, 22 | `_, ok := x.(interface{ … })` | type assertion: «реализует ли тип внутри `x` этот интерфейс?» Если нет, `ok` = `false`, без panic ([GO-1.13](/lab/youtube/go/go-1-13/ru)). Печатаемое `… bormi?` значит «есть ли …?» |
| 24 | `reflect.TypeOf(x).NumMethod()` | `reflect` — стандартный пакет, который изучает типы во время работы программы; `NumMethod` считает методы типа (текст: «методы, которые увидел reflect») |

Подумайте: что напечатают четыре строки?

**A)** `true true true 2` · **B)** `false false true 1` · **C)** `true false true 2`

<details>
<summary>Ответ</summary>

**B.** Обе проверки `Nop` — `false`: generic-метод не реализует интерфейс, и в runtime тоже. `Oddiy` находится.
`reflect` видит только один метод. Если вы выбрали «C», вы думали, что `Nop[string]` существует, хотя программа его
не вызывала. Но даже если бы он был, результат всё равно был бы `false`: таково правило.

</details>

```console
$ go run ./faq
Nop(string) string bormi? false
Nop(int) int bormi? false
Oddiy() bormi? true
reflect koʻrgan metodlar: 1
```

`reflect` тоже видит только один метод, потому что не умеет подставить в generic-метод конкретный тип. В предложении:
*"Generic methods also won't be accessible via reflection"*. Значит, и библиотеки, которые опираются на `reflect`,
ваших generic-методов не увидят.

## Вопрос на паузе: Katta(3, 2.5)

Теперь вопрос вам. Вызываем функцию `Katta` с `3` и `2.5`:

```go filename="savol/main.go" showLineNumbers
// savol: Katta(3, 2.5) — kompilyatsiya boʻladimi? T nima boʻladi?
// go run ./savol
package main

import (
	"cmp"
	"fmt"
)

func Katta[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}

func main() {
	k := Katta(3, 2.5)
	fmt.Printf("%v %T\n", k, k)
}
```

В строке 18 — `Katta(3, 2.5)`, в строке 19 `%v` — значение, `%T` — его тип. Скомпилируется ли этот код? Если да, что
он напечатает и каким типом будет `T`? Подсказка: оба аргумента — нетипизированные константы.

**A)** ошибка компиляции: смешаны `int` и `float64` · **B)** `3 int` · **C)** `3 float64`

<details>
<summary>Ответ</summary>

**C.** Оба аргумента — нетипизированные константы. По спецификации вывод типов выбирает тип таких констант так же,
как в константном выражении. Если смешиваются целая и дробная константа, берётся дробный вид, а его тип по умолчанию
— `float64` ([GO-1.03](/lab/youtube/go/go-1-03/ru)). Хотя `3` — это float64, `%v` печатает его просто как `3`. Если вы выбрали
«A», вы думали, что `3` сразу `int`: так было бы у переменной (`x := 3`), но не у константы. Если «B», вы думали, что
тип определяет первый аргумент.

</details>

```console
$ go run ./savol
3 float64
```

## Когда дженерики не нужны: три признака

Теперь самый важный вопрос: когда дженерики не нужны? В `hid/` («запах») три generic-функции. Все компилируются и
работают, но параметр типа здесь ничего не даёт.

```go filename="hid/main.go" showLineNumbers
// hid: uchta ortiqcha generic. Hammasi kompilyatsiya boʻladi va ishlaydi,
// lekin type parameter hech narsa bermaydi. Tozalangani: ../toza
// go run ./hid
package main

import (
	"fmt"
	"strconv"
)

type Buyurtma struct{ Summa int64 }

func (b Buyurtma) String() string { return fmt.Sprintf("buyurtma: %d soʻm", b.Summa) }

// 1-hid: T bilan faqat metod chaqiriladi.
func Chiqar[T fmt.Stringer](x T) { fmt.Println(x.String()) }

// 2-hid: T hech narsa bermaydi, Println baribir any oladi.
func Yoz[T any](x T) { fmt.Println("log:", x) }

// 3-hid: har bir tur uchun boshqa kod (type switch).
func Matn[T int64 | string](x T) string {
	switch v := any(x).(type) {
	case int64:
		return strconv.FormatInt(v, 10)
	case string:
		return v
	}
	return ""
}

func main() {
	Chiqar(Buyurtma{150000})
	Yoz(42)
	fmt.Println(Matn(int64(99000)), Matn("nok"))
}
```

| Строка | Код | Что делает и почему это лишнее |
|---|---|---|
| 11–13 | `Buyurtma`, `String()` | `Buyurtma` («заказ») — тип, реализующий `fmt.Stringer` ([GO-1.13](/lab/youtube/go/go-1-13/ru)) |
| 16 | `func Chiqar[T fmt.Stringer](x T)` | `Chiqar` («вывести») с `T` только вызывает метод `String()`. Taylor: *"If all you need to do with a value of some type is call a method on that value, use an interface type"* |
| 19 | `func Yoz[T any](x T)` | `Yoz` («записать»): `fmt.Println` и так принимает любое значение (`any`), `T` ничего не добавляет |
| 22–30 | `func Matn[T int64 \| string](x T) string` | `Matn` («текст»): внутри type switch; `any(x)` превращает `T` в пустой интерфейс, дальше для каждого типа свой код. Taylor: *"if the implementation is different for each type, then use an interface type … don't use a type parameter"* |
| 25 | `strconv.FormatInt(v, 10)` | превращает `int64` в текст в десятичной системе |

`toza/` («чистый») — те же три функции без параметров типа:

```go filename="toza/main.go" showLineNumbers
// toza: ../hid dagi uchta funksiya type parameter'siz. Natija bir xil.
// go run ./toza
package main

import (
	"fmt"
	"strconv"
)

type Buyurtma struct{ Summa int64 }

func (b Buyurtma) String() string { return fmt.Sprintf("buyurtma: %d soʻm", b.Summa) }

// 1: faqat metod kerak — interface.
func Chiqar(x fmt.Stringer) { fmt.Println(x.String()) }

// 2: any yetarli.
func Yoz(x any) { fmt.Println("log:", x) }

// 3: har bir tur uchun oʻz kodi — alohida funksiyalar.
func MatnSon(x int64) string   { return strconv.FormatInt(x, 10) }
func MatnSatr(x string) string { return x }

	Yoz(42)

```

| Признак (`hid/`) | Чистый вариант (`toza/`) |
|---|---|
| `Chiqar[T fmt.Stringer](x T)` | `Chiqar(x fmt.Stringer)`: интерфейс |
| `Yoz[T any](x T)` | `Yoz(x any)`: любое значение |
| `Matn[T int64 \| string]` + type switch | `MatnSon(int64)` и `MatnSatr(string)`: две отдельные функции («текст из числа», «текст из строки») |

Сравним вывод двух программ. `diff <(…) <(…)` построчно сравнивает вывод двух команд и ничего не печатает, если они
совпадают; `&&` выполняет следующую команду только при успехе:

```console
$ go run ./hid
buyurtma: 150000 soʻm
log: 42
99000 nok
```

```console
$ diff <(go run ./hid) <(go run ./toza) && echo natija bir xil
natija bir xil
```

(`natija bir xil` — «вывод одинаковый».) Результат тот же, а код проще. Наша практическая проверка такая: если при
удалении параметра типа ничего не теряется, он был лишним. Это основано на советах Taylor, но это не строгое
правило: он пишет *"consider"* («подумайте»).

## Дженерики быстрее интерфейсов? Измеряем

Быстрее ли generic-код интерфейса? Давайте измерим. В `tezlik/` («скорость») одна и та же сумма считается тремя
способами:

```go filename="tezlik/tezlik.go" showLineNumbers
// Package tezlik: bir xil yigʻindi uch usulda — interface, generic, oddiy tur.
// go test -bench . ./tezlik
package tezlik

type Buyurtma struct {
	Summa   int64
	Tolandi bool
}

func (b *Buyurtma) Jami() int64 { return b.Summa }

type Summali interface{ Jami() int64 }

//go:noinline
func JamiInterface(xs []Summali) (s int64) {
	for _, x := range xs {
		s += x.Jami()
	}
	return s
}

//go:noinline
func JamiGeneric[T Summali](xs []T) (s int64) {
	for _, x := range xs {
		s += x.Jami()
	}
	return s
}

//go:noinline
func JamiOddiy(xs []*Buyurtma) (s int64) {
	for _, x := range xs {
		s += x.Jami()
	}
	return s
}
```

| Строка | Код | Что делает |
|---|---|---|
| 10 | `func (b *Buyurtma) Jami() int64` | метод с pointer receiver: возвращает сумму |
| 12 | `type Summali interface{ Jami() int64 }` | `Summali` («имеющий сумму») — типы с методом `Jami` |
| 14, 22, 30 | `//go:noinline` | указание компилятору: не встраивать саму эту функцию в место вызова. Чтобы бенчмарк измерял функцию |
| 15 | `JamiInterface(xs []Summali)` | слайс интерфейсов |
| 23 | `JamiGeneric[T Summali](xs []T)` | generic: `T` = `*Buyurtma` |
| 31 | `JamiOddiy(xs []*Buyurtma)` | `Oddiy` («обычный»): обычный конкретный тип |
| 15, 23, 31 | `(s int64)` | именованный результат: `s` начинается с 0, `return s` его возвращает |

Бенчмарки ([GO-1.07](/lab/youtube/go/go-1-07/ru)) на 1000 заказов:

```go filename="tezlik/tezlik_test.go" showLineNumbers
package tezlik

import "testing"

const n = 1000

func buyurtmalar() []*Buyurtma {
	xs := make([]*Buyurtma, n)

	}

func TestBirXil(t *testing.T) {
	xs := buyurtmalar()
	is := make([]Summali, n)

		is[i] = x
	}

}

func BenchmarkGeneric(b *testing.B) {

```

`TestBirXil` («одинаково») проверяет, что все три функции дают одну и ту же сумму. Три бенчмарка измеряют одни и те
же 1000 заказов; для интерфейсной версии они сначала копируются в `[]Summali` (строки 17–20).

Одно измерение шумное, поэтому `olch.sh` («измерь») запускает каждый бенчмарк 7 раз и берёт медиану:

```bash
#!/usr/bin/env bash
# olch.sh: har bir benchmark'ni 7 marta ishga tushirib, medianasini chiqaradi (shovqinni kamaytirish uchun).
# ./tezlik/olch.sh   (lessons/017-generics papkasidan)
set -euo pipefail
cd "$(dirname "$0")"
go test -run '^$' -bench . -count 7 -cpu 1 . |
	awk '/^Benchmark/ { v[$1] = v[$1] " " $3 }
	END {
		for (k in v) {
			n = split(substr(v[k], 2), a, " ")
			for (i = 1; i <= n; i++) for (j = i + 1; j <= n; j++) if (a[j] < a[i]) { t = a[i]; a[i] = a[j]; a[j] = t }
			printf "%-20s %8.0f ns/op (mediana, %d marta)\n", k, a[int((n + 1) / 2)], n
		}
	}' | sort -k2 -n -r
```

`-run '^$'` пропускает тесты, `-count 7` — 7 раз, `-cpu 1` — одно ядро. `awk` сортирует 7 результатов каждого
бенчмарка и печатает средний (`mediana, 7 marta` — «медиана, 7 раз»).

Подумайте: каким будет результат?

**A)** generic быстрее всех, интерфейс медленнее всех · **B)** интерфейс и generic почти одинаковы, обычный тип в
несколько раз быстрее · **C)** все три почти одинаковы

<details>
<summary>Ответ</summary>

**B.** Причина ниже. Если вы выбрали «A», вы думали, что дженерики генерируют отдельный код для каждого типа:
стандартный компилятор Go так не делает. Если «C», вы не учли встраивание.

</details>

```console
$ ./tezlik/olch.sh
BenchmarkInterface       2038 ns/op (mediana, 7 marta)
BenchmarkGeneric         1961 ns/op (mediana, 7 marta)
BenchmarkOddiy            450 ns/op (mediana, 7 marta)
```

Эти числа зависят от загрузки машины. Этот результат получен на загруженной машине (load average ≈ 11), а в видео —
результат при меньшей загрузке: 1593, 1558 и 287 ns/op. У вас будут другие числа. Но картина та же: интерфейс и
generic очень близки (то один впереди, то другой), а обычный тип в несколько раз быстрее обоих (здесь ≈ 4,4×, при
лёгкой загрузке 5–6×). У всех трёх вариантов `0 allocs/op`: выделения памяти нет.

Причина в компиляторе. Первая: в обычной версии метод `Jami` **встраивается** (inline), то есть вызов исчезает.
`-gcflags=-m` ([GO-1.11](/lab/youtube/go/go-1-11/ru)) печатает решения компилятора:

```console
$ go build -gcflags=-m ./tezlik 2>&1 | grep 'inlining call'
tezlik/tezlik.go:33:14: inlining call to (*Buyurtma).Jami
```

`2>&1` отправляет сообщения компилятора (`stderr`) в `grep`. Строка 33 — `x.Jami()` внутри `JamiOddiy`. В строках 17
и 25 (интерфейс и generic) встраивания нет: там каждый раз настоящий вызов.

Вторая: стандартный компилятор Go не собирает generic-функцию отдельно для каждого типа. Для всех типов-указателей он
собирает одно общее тело. Такая группа называется **shape** («форма»), все типы-указатели относятся к одной форме
`go.shape.*uint8`. С каким конкретным типом тело работает, оно узнаёт через скрытый аргумент — **словарь**
(*dictionary*). Метод тоже вызывается через этот словарь, как через интерфейс. `go tool nm` показывает имена в
бинарнике:

```console
$ go test -c -o /tmp/tezlik.test ./tezlik && go tool nm /tmp/tezlik.test | grep JamiGeneric
  5656e0 R generics/tezlik..dict.JamiGeneric[*generics/tezlik.Buyurtma]
  544560 T generics/tezlik.JamiGeneric[go.shape.*uint8]
```

`go test -c` не запускает тест, а только собирает бинарник. `T` — код (тело функции): `JamiGeneric[go.shape.*uint8]`,
одно на все типы-указатели. `R` — данные только для чтения: словарь для `*Buyurtma`. В задаче уровня «гуру» из
домашнего задания вы сами посчитаете, сколько тел получится с четырьмя типами.

| | Интерфейс | Generic (`T` = `*Buyurtma`) | Обычный |
|---|---|---|---|
| как вызывается `Jami` | через таблицу интерфейса | через словарь | напрямую, встроен |
| есть ли вызов | да, на каждом элементе | да, на каждом элементе | нет |
| скорость | медленно | медленно | в несколько раз быстрее |

Это детали стандартного (gc) компилятора. FAQ Go: *"Different compilers will make different choices"* — «разные
компиляторы выбирают по-разному». Taylor написал и об этом: *"don't change from interface types to type parameters
just for speed, because it probably won't run any faster"* — «не меняйте интерфейсы на параметры типа только ради
скорости: скорее всего, быстрее не станет».

## Итог: нужны ли дженерики?

| Ситуация | Что использовать |
|---|---|
| только ради скорости | нет, сначала измерьте |
| одинаковый код, разные типы (слайс, map, контейнер: `Katta`, `Royxat[T]`) | параметр типа `[T]` |
| от значения нужен только метод или для каждого типа свой код | интерфейс (или отдельные функции) |
| метод возвращает новый тип (`Aylantir[U]`) | generic-метод (Go 1.27+): удобно, но через интерфейс не вызывается |

## Частые ошибки

**1. Ожидать, что generic-метод реализует интерфейс.** Человек из TypeScript спокойно кладёт `nop<T>` в интерфейс с
`nop(string)`. В Go 1.27 `var _ MatnNop = b` → `Bosh does not implement MatnNop (wrong type for method Nop)`,
*have* `Nop[T any](T) T`, *want* `Nop(string) string` (раздел «Ограничение»). И в runtime тоже:
`x.(interface{ Nop(string) string })` → `false` (раздел «Почему выбрали именно так?»). Исправление: если нужен
интерфейс, напишите обычный метод (`func (Bosh) NopMatn(x string) string`) или сделайте generic сам тип
(`type Bosh[T any] struct{}` и `func (Bosh[T]) Nop(x T) T`): тогда `Bosh[string]` реализует `MatnNop`.

**2. Забыть `~`.** `Son interface{ int64 | float64 }` и `type Ball int64` → `Ball does not satisfy Son (possibly
missing ~ for int64 in Son)` (раздел «Ограничение — это интерфейс»). Исправление: `~int64 | ~float64`. В
ограничении, которое должно работать с вашими типами, всегда ставьте `~`, как в `cmp.Ordered`.

**3. Взять generic-метод как значение без инстанцирования.** Method value из [GO-1.12](/lab/youtube/go/go-1-12/ru)
(`f := b.Jami`) с generic-методом не работает. Этой программы нет в папке курса, она запущена в отдельном модуле
(`go 1.27`):

```go
package main

import "fmt"

type Quti[T any] struct{ v T }

func (q Quti[T]) Juft[U any](u U) (T, U) { return q.v, u }

func main() {
	q := Quti[int]{7}
	f := q.Juft
	fmt.Println(f("yetti"))
}
```

```console
$ go run ./juft
# scratch/juft
juft/main.go:11:7: cannot use generic function q.Juft without instantiation
```

*cannot use generic function q.Juft without instantiation* — «нельзя использовать generic-функцию `q.Juft` без
инстанцирования». Компилятор не знает, какого типа должна быть `f`: `U` ещё неизвестен. (`Quti` — «коробка»,
`Juft` — «пара», `yetti` — «семь».) Исправление: укажите тип, `f := q.Juft[string]`, или напишите тип `f`:
`var f func(string) (int, string) = q.Juft`.

**4. Параметр типа у метода интерфейса.** `Aylantir[U any](…)` внутри интерфейса → `interface method must have no
type parameters` (раздел «Ограничение», первая часть). Исправление: поставьте параметр типа на сам интерфейс
(`type Aylantiruvchi[U any] interface{ Aylantir(f func(int64) U) []U }`) или напишите generic-функцию уровня пакета.

**5. Новый Go, старая строка `go`.** Установлен Go 1.27.4, а в `go.mod` — `go 1.26` → `generic method requires
go1.27 or later (-lang was set to go1.26; check go.mod)` (раздел «Условие go.mod»). Исправление: сделайте строку
`go 1.27` (`go get go@1.27`), но в библиотеке это заставит и её пользователей перейти на Go 1.27.

**6. `go build ./папка` и бинарник с именем папки.** В комментарии в файлах курса написано `go build ./tildesiz`. Если
запустить именно так, вместо ошибки компиляции будет другое сообщение:

```console
$ go build ./tildesiz
go: build output "tildesiz" already exists and is a directory
```

*build output "tildesiz" already exists and is a directory* — «результат сборки `tildesiz` уже существует и это
папка». `go build` собирает бинарник из одного пакета `main` и хочет записать его в текущую папку под именем пакета.
А здесь уже есть папка с таким именем, поэтому `go` даже не доходит до компиляции. Исправление:
`go build -o /dev/null ./tildesiz` (бинарник не нужен) или `go vet ./tildesiz`.

**7. Лишние дженерики и вера в то, что «дженерики быстрее».** Ошибки нет, код работает, но он без нужды сложный
(раздел «Когда дженерики не нужны»). Скорость тоже почти не меняется (раздел «Дженерики быстрее интерфейсов?»).
Исправление: попробуйте убрать параметр типа; если ничего не потерялось, он был лишним.

## Проверьте себя

**1.** В `func Katta[T cmp.Ordered](a, b T) T` что параметр типа, а что ограничение? Как называется `int64` в
`Katta[int64](1, 2)`?

<details>
<summary>Ответ</summary>

`T` — параметр типа, `cmp.Ordered` — ограничение. `int64` — аргумент типа (type argument): компилятор подставляет
его вместо `T`, это инстанцирование. В `Katta(1, 2)` тип находит вывод типов (`int`).

</details>

**2.** Что напечатает эта программа? (`Katta` — функция из урока; в папке курса нет, запущено отдельно.)

```go
fmt.Println(Katta("10", "9"), Katta(10, 9))
```

<details>
<summary>Ответ</summary>

```console
$ go run ./satr
9 10
```

Строки сравниваются побайтово, а не как числа: первый байт `"9"`, `'9'`, больше первого байта `"10"`, `'1'`. В
`Katta(10, 9)` `T` = `int`, результат `10`.

</details>

**3.** Какая из функций должна быть generic, а какая нет?
(a) `func Oxirgi[T any](s []T) T { return s[len(s)-1] }`
(b) `func Yop[T io.Closer](c T) error { return c.Close() }`

<details>
<summary>Ответ</summary>

(a) `Oxirgi` («последний») пусть будет generic: одинаковый код для любого типа элементов, и результат именно `T` (с
интерфейсом результат стал бы `any`). (b) `Yop` («закрыть») — лишнее: с `T` только вызывается метод, достаточно
`func Yop(c io.Closer) error` (первый признак).

</details>

**4.** В Go 1.27 у `type Bosh struct{}` есть метод `func (Bosh) Nop[T any](x T) T`. Почему `Bosh` не реализует
`interface{ Nop(string) string }`, и почему команда Go так это и оставила?

<details>
<summary>Ответ</summary>

Правило Go 1.27: generic-метод не реализует метод интерфейса. Реализация интерфейса проверяется и во время работы
программы, а у generic-метода бесконечно много вариантов, и в бинарнике есть только использованные. Остальные три
пути из четырёх в FAQ (перекомпиляция после линковки, JIT, медленный запасной код) ухудшают сборку или скорость.
Go 1.27 выбрал четвёртый, потому что методы полезны и без интерфейсов (Griesemer, #77273).

</details>

**5.** Из [GO-1.13](/lab/youtube/go/go-1-13/ru): после `var x any = Bosh{}` что будет, если `v, ok := x.(MatnNop)` не совпадёт?
А если `v := x.(MatnNop)`, без `ok`?

<details>
<summary>Ответ</summary>

С `ok`: `ok` = `false`, `v` — нулевое значение `MatnNop` (`nil`), без panic. Без `ok`: если не совпало, программа
останавливается с panic. Поэтому сегодняшняя программа `faq/` использует форму с `ok`.

</details>

🟢 **Легко:** напишите `Indeks[T comparable](s []T, x T) int`: индекс, где `x` встречается впервые, или `-1`, если
не найден. Сравните с `slices.Index`.

<details>
<summary>Ответ</summary>

```go filename="homework/oson/main.go" showLineNumbers
// oson: Indeks — x birinchi uchragan oʻrin yoki -1. Bitta generic funksiya.
// go run ./homework/oson
package main

import (
	"fmt"
	"slices"
)

func Indeks[T comparable](s []T, x T) int {
	for i, v := range s {
		if v == x {
			return i
		}
	}
	return -1
}

func main() {
	fmt.Println(Indeks([]int64{150000, 99000}, 99000))
	fmt.Println(Indeks([]string{"olma", "nok"}, "uzum"))
	// Standart kutubxonada tayyori bor (Go 1.21+):
	fmt.Println(slices.Index([]int64{150000, 99000}, 99000))
}
```

```console
$ go run ./homework/oson
1
-1
1
```

`comparable` — встроенное в язык ограничение для типов, которые сравниваются через `==` и `!=`. В строке 12 есть
`v == x`, поэтому `any` недостаточно. `slices.Index` (Go 1.21+) делает ровно это: в реальном коде используйте готовое.

</details>

🟡 **Средне:** `type Quti[T any] struct{ v T }`. Какие строки компилируются в Go 1.27?

1. `func (q Quti[T]) Ol() T { return q.v }`
2. `func (q Quti[T]) Juft[U any](u U) (T, U) { return q.v, u }`
3. `type I interface{ M[T any](T) }`
4. `f := q.Juft`
5. `var o Oluvchi[int] = q` (где `type Oluvchi[T any] interface{ Ol() T }`)
6. `f := q.Juft[string]`

<details>
<summary>Ответ</summary>

Компилируются **1, 2, 5 и 6**. 3 — `interface method must have no type parameters` (раздел «Ограничение»). 4 —
`cannot use generic function q.Juft without instantiation` («Частые ошибки», 3). 5 — generic-*интерфейс* — это
другое: его метод `Ol()` («получить») обычный и использует только `T` интерфейса, поэтому `Quti[int]` его реализует.
Те, что компилируются:

```go filename="homework/orta/main.go" showLineNumbers
// orta: README dagi 6 qatordan kompilyatsiya boʻladiganlari (1, 2, 5, 6).
// 3 va 4 — ATAYLAB yoʻq: ular kompilyatsiya boʻlmaydi.
// go run ./homework/orta
package main

import "fmt"

type Quti[T any] struct{ v T }

// 1: generic turdagi metod, receiver'dagi T bilan (Go 1.18+)
func (q Quti[T]) Ol() T { return q.v }

// 2: generic turdagi metod, oʻz type parametri bilan (Go 1.27+)
func (q Quti[T]) Juft[U any](u U) (T, U) { return q.v, u }

type Oluvchi[T any] interface{ Ol() T }

func main() {
	q := Quti[int]{7}
	// 5: generic interface'ni oddiy metod bajaradi
	var o Oluvchi[int] = q
	fmt.Println(o.Ol())
	// 6: generic metoddan aniq tur bilan method value
	f := q.Juft[string]
	fmt.Println(f("yetti"))
}
```

```console
$ go run ./homework/orta
7
7 yetti
```

</details>

🟠 **Сложно:** добавьте к `Royxat[T]` generic-метод `Guruhla[K comparable](kalit func(T) K) map[K]Royxat[T]` и
протестируйте его: один раз с ключом `bool`, один раз с ключом `string`.

<details>
<summary>Ответ</summary>

```go filename="homework/qiyin/qiyin.go" showLineNumbers
// Package qiyin: Guruhla — Go 1.27 generic metodi. K — metodning oʻz type parametri.
package qiyin

type Royxat[T any] []T

// Guruhla elementlarni kalit(x) boʻyicha guruhlaydi; har guruhda tartib saqlanadi.
func (r Royxat[T]) Guruhla[K comparable](kalit func(T) K) map[K]Royxat[T] {
	natija := make(map[K]Royxat[T])
	for _, x := range r {
		k := kalit(x)
		natija[k] = append(natija[k], x)
	}
	return natija
}
```

`Guruhla` («сгруппировать»), `kalit` («ключ»). `K` — собственный параметр типа метода, `comparable`, потому что это
ключ map. `natija[k]` для отсутствующего ключа возвращает `nil`-слайс, и `append` работает и с ним
([GO-1.08](/lab/youtube/go/go-1-08/ru), [GO-1.09](/lab/youtube/go/go-1-09/ru)). Тест (`homework/qiyin/qiyin_test.go`) группирует один раз
по `Tolandi` («оплачен», `bool`), другой раз по `"katta"`/`"kichik"` («большой»/«маленький», `string`):

```console
$ go test -count=1 ./homework/qiyin
ok  	generics/homework/qiyin	0.002s
```

`-count=1` запускает тест заново, а не берёт результат из кэша. Время у вас будет другим.

</details>

🔴 **Гуру:** вызовите `JamiGeneric[T Summali]` с `*Buyurtma`, `*Mijoz`, `Narx` (на основе `int64`) и `Chegirma`
(на основе `int64`). Сколько тел и сколько словарей соберёт компилятор? Проверьте через `go tool nm`.

<details>
<summary>Ответ</summary>

**2 тела, 4 словаря** (стандартный компилятор gc, go1.27.4):

```console
$ go test -c -o /tmp/guru.test ./homework/guru && go tool nm /tmp/guru.test | grep JamiGeneric
  565480 R generics/homework/guru..dict.JamiGeneric[*generics/homework/guru.Buyurtma]
  5654a0 R generics/homework/guru..dict.JamiGeneric[*generics/homework/guru.Mijoz]
  5654e0 R generics/homework/guru..dict.JamiGeneric[generics/homework/guru.Chegirma]
  5654c0 R generics/homework/guru..dict.JamiGeneric[generics/homework/guru.Narx]
  543d00 T generics/homework/guru.JamiGeneric[go.shape.*uint8]
  543c40 T generics/homework/guru.JamiGeneric[go.shape.int64]
```

Оба типа-указателя делят одно тело `go.shape.*uint8`, а `Narx` («цена») и `Chegirma` («скидка») — одно тело
`go.shape.int64`. Разница между типами (какой `Jami`) — в словаре. Адреса (первый столбец) у вас будут другими.
