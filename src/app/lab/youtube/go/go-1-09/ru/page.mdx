## Что вы узнаете

Пять слов (non, sut, tuxum, choy, olma — «хлеб, молоко, яйца, чай, яблоко») можно расставить 120 способами:
5 × 4 × 3 × 2 × 1 = 120. Мы попросили Go перебрать эти пять слов 100 000 раз и каждый раз записывали, в каком
порядке они пришли. Go выдал всего **5** разных порядков. А один из них выпал почти в **половине** случаев. Значит,
порядок случайный, но не перемешан, как колода карт. Почему? Сегодня найдём ответ в исходном коде самого Go. А в
конце урока увидим ошибку, от которой не спасает даже страховочная сетка (`recover`).

**Одна идея:** map связывает ключ со значением: отсутствующий ключ не даёт ошибки, а возвращает нулевое значение,
а на порядок обхода полагаться нельзя. Если две горутины одновременно пишут в map, это не panic, а fatal error,
который `recover` поймать не может.

К концу урока вы:

- создадите map, добавите в неё значение, измените его, удалите и посчитаете ключи с помощью `len`;
- с помощью comma ok отличите «цена 0» от «такого товара нет»;
- объясните, почему порядок `range` случайный, но распределён неравномерно, и при необходимости отсортируете
  ключи;
- будете знать разницу между записью в nil map (panic, `recover` ловит) и одновременной записью в map (fatal
  error, не ловит), и защитите map с помощью `sync.Mutex`.

Три главных новых слова сегодня:

| Слово | Простой смысл | По-английски |
|---|---|---|
| map | ценник-табло: к каждому **ключу** (названию товара) привязано одно **значение** (цена) | map (key → value) |
| comma ok | вторая переменная: ответ на вопрос «есть ли такой ключ?», `true` или `false` | comma ok idiom |
| fatal error | ошибка, при которой runtime немедленно останавливает программу: `defer` не выполняется, `recover` не ловит | fatal error |

По ходу встретятся ещё два вспомогательных слова: **panic** (аварийное падение программы; `recover` может его
поймать) и **горутина** (goroutine: отдельная работа, которая выполняется одновременно с другими). Оба объясним
там, где они понадобятся, а подробно — в [GO-1.15](/lab/youtube/go/go-1-15/ru) и [GO-1.21](/lab/youtube/go#go-1-21).

## Загадка из начала: 5 порядков из 120

Вот опыт, о котором говорилось в начале. Программа `tartib` («порядок») 100 000 раз перебирает пять названий
товаров. Каждый раз она записывает, в каком порядке пришли названия, а в конце показывает, сколько процентов
пришлось на каждый порядок. Код программы откроем в середине урока, когда изучим нужные инструменты.

```console
$ go run ./tartib

choy olma non sut tuxum   12.3%
non sut tuxum choy olma   50.2%
olma non sut tuxum choy   12.3%
sut tuxum choy olma non   12.6%
tuxum choy olma non sut   12.5%
```

(`100000 ta sikl, 5 xil tartib` — «100000 циклов, 5 разных порядков».) Дробная часть процентов при каждом запуске
немного меняется, а сами пять порядков всегда одни и те же. Из 120 возможных порядков выпало только 5. Порядок
`non sut tuxum choy olma` — почти 50 %, остальные четыре — около 12,5 %.

Урок состоит из трёх частей:

1. основы работы с map;
2. почему порядок случайный (и почему неравномерный);
3. что происходит, когда две горутины пишут в одну map, и почему `recover` бессилен.

## Map: ключ → значение

Мы хотим хранить цены в магазине: хлеб 5000 сумов, молоко 12000 сумов. В слайсе значения лежат в ячейках с
номерами 0, 1, 2. А нам нужно искать не по номеру, а по **названию**: «сколько стоит хлеб?».

Представьте ценник-табло в магазине. В левом столбце название товара, в правом — его цена. Находите название и
читаете цену рядом. Одно название на табло дважды не пишут.

| Ключ (название) | Значение (цена) |
|---|---|
| `"non"` | 5000 |
| `"sut"` | 12000 |

Такое табло в Go называется **map**. Название в левом столбце — **ключ** (по-английски **key**), цена в правом —
**значение** (**value**). Map связывает с каждым ключом одно значение. Тип записывается как `map[string]int`:
«map, у которой ключи типа `string`, а значения типа `int`».

Это `asos/main.go` («основы») из папки курса:

```go filename="asos/main.go" showLineNumbers
package main

import "fmt"

func main() {
	narx := map[string]int{"non": 5000, "sut": 12000}
	narx["choy"] = 25000

	fmt.Println(narx["olma"]) // bunday kalit yoʻq

	n, bor := narx["olma"]
	fmt.Println(n, bor)

	delete(narx, "sut")
	fmt.Println(len(narx))
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1–5 | `package main` … `func main() {` | знакомый шаблон: программа начинается с `main` |
| 6 | `narx := map[string]int{"non": 5000, "sut": 12000}` | новая map с именем `narx` («цена»). В фигурных скобках начальные пары `ключ: значение` через запятую |
| 7 | `narx["choy"] = 25000` | ключ в квадратных скобках: «пусть цена `choy` (чай) будет 25000». Если ключа нет, он добавляется; если есть, старое значение заменяется |
| 9 | `fmt.Println(narx["olma"])` | спрашивает цену `olma` (яблоко), которого в map нет. Комментарий: «такого ключа нет» |
| 11 | `n, bor := narx["olma"]` | тот же запрос, но с **двумя** переменными: `n` — цена, `bor` («есть») — есть ли ключ (`true`/`false`) |
| 12 | `fmt.Println(n, bor)` | выводит обе |
| 14 | `delete(narx, "sut")` | `delete` — встроенная функция Go: удаляет ключ `sut` (вместе со значением) |
| 15 | `fmt.Println(len(narx))` | `len` говорит, сколько ключей в map |

Подумайте до запуска: что выведет строка 9? **A)** программа упадёт с ошибкой · **B)** `0` · **C)** пустую строку

<details>
<summary>Ответ</summary>

**B: `0`.** Отсутствующий ключ — не ошибка. Map возвращает **нулевое значение** (zero value) типа значения: тип
значения `int`, поэтому 0. Если вы выбрали «A», вы ждали поведения других языков: в некоторых из них
отсутствующий ключ даёт ошибку, а в Go — нет. «C» было бы верно, если бы тип значения был `string`: его нулевое
значение — пустая строка `""`.

</details>

```console
$ go run ./asos
0
0 false
2
```

Как менялось табло после каждой строки:

| Строка | Внутри `narx` | На экран |
|---|---|---|
| 6 | non: 5000, sut: 12000 | |
| 7 | non: 5000, sut: 12000, choy: 25000 | |
| 9 | (не изменилась) | `0` |
| 11–12 | (не изменилась; `n` = 0, `bor` = `false`) | `0 false` |
| 14 | non: 5000, choy: 25000 | |
| 15 | (не изменилась) | `2` |

Обратите внимание: строка 9 **ничего не добавила** в map. Чтение отсутствующего ключа map не меняет.

## Comma ok: «0 сумов» или «вообще нет»?

Теперь проблема. `narx["olma"]` вернул 0. Что это значит: яблоки бесплатные (цена 0 сумов) или яблок в магазине
вообще нет? По одному первому значению этого не понять.

Поэтому в строке 11 стоит вторая переменная `bor`. Она отвечает на вопрос: «есть ли такой ключ в map?».
`0 false` — цена 0, но `false`, то есть **такого ключа нет**. Для бесплатного товара вывелось бы `0 true`.

Такая запись в Go называется **comma ok**: запятая (по-английски *comma*) и вторая переменная, которую обычно
называют `ok` (`n, ok := narx["olma"]`). Мы назвали её `bor`. В Go этот приём встречается очень часто. Обычно его
пишут вместе с `if`:

```go
	if n, bor := narx["olma"]; bor {
		fmt.Println("olma:", n)
	} else {
		fmt.Println("olma yoʻq")
	}
```

В строке `if` сначала создаются `n` и `bor`, а после точки с запятой (`;`) проверяется `bor`. Эти две переменные
живут только внутри этого `if`. (`"olma yoʻq"` — «яблок нет».)

После `delete` вызов `len(narx)` дал 2: остались `non` и `choy`.

## nil map: читать можно, писать — panic

Что будет, если объявить map не через `:=`, а через `var`, без значения?

```go
	var narx map[string]int
```

У каждого типа есть нулевое значение. Нулевое значение типа map — **`nil`**, то есть «map ещё нет». Представьте
ценник-табло, которое ещё не повесили. Посмотрите на него — ничего не увидите. Но и цену на нём не напишешь: самого
табло нет.

Пустую map, готовую к работе, можно создать двумя способами:

```go
	narx := map[string]int{}       // boʻsh map literal
	narx2 := make(map[string]int)  // make bilan
```

(Комментарии: «пустой литерал map» и «через make».) `make` — встроенная функция Go: она создаёт новую, пустую, но
готовую к работе map. Map, «не созданная через make», то есть объявленная через `var`, равна `nil`.

Это `nilmap/main.go`. В нём ошибка **специально**:

```go filename="nilmap/main.go" showLineNumbers
package main

import "fmt"

func main() {
	var narx map[string]int // nil map: make qilinmagan
	fmt.Println(narx["non"], len(narx))
	yoz(narx)
	fmt.Println("dastur davom etdi")
}

func yoz(m map[string]int) {
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("qutqarildi:", r)
		}
	}()
	m["non"] = 5000 // ataylab xato: nil map'ga yozib boʻlmaydi
}
```

| Строка | Код | Что делает |
|---|---|---|
| 6 | `var narx map[string]int` | map без значения: `narx` равна `nil` (комментарий: «nil map: не создана через make») |
| 7 | `fmt.Println(narx["non"], len(narx))` | читает из nil map и считает ключи |
| 8 | `yoz(narx)` | вызывает функцию `yoz` («записать») и передаёт ей map |
| 9 | `fmt.Println("dastur davom etdi")` | «программа продолжилась»: дойдёт ли программа сюда после `yoz`? |
| 12 | `func yoz(m map[string]int) {` | наша функция, которая принимает map |
| 13–17 | `defer func() { … }()` | **защита**: `defer` назначает работу, которая выполнится, когда функция завершается. Здесь это анонимная функция; `()` в конце её вызывает, а `defer` откладывает этот вызов до конца функции |
| 14 | `if r := recover(); r != nil {` | `recover` останавливает падение и возвращает его причину. Если падения не было, возвращает `nil`. `!=` — «не равно ли» |
| 15 | `fmt.Println("qutqarildi:", r)` | выводит «спасено:» и причину падения |
| 18 | `m["non"] = 5000` | запись в nil map: здесь ошибка (комментарий: «специальная ошибка: в nil map писать нельзя») |

Здесь новое вспомогательное слово. Если программа попала в состояние, из которого не может продолжать, Go делает
**panic**: функция останавливается, и программа начинает падать. `recover` — страховочная сетка: если вызвать его
внутри функции, отложенной через `defer`, он останавливает падение, и программа продолжает работу. `defer`, `panic`
и `recover` подробно изучим в [GO-1.15](/lab/youtube/go/go-1-15/ru). Сегодня нам достаточно этих двух фраз.

Угадайте: что выведет программа? **A)** `0 0`, затем `qutqarildi: …` и `dastur davom etdi` · **B)** `0 0`, затем
программа упадёт · **C)** упадёт уже на первой строке, потому что из nil map читать нельзя

<details>
<summary>Ответ</summary>

**A.** Читать из nil map можно: она, как пустая map, возвращает нулевое значение (0), а `len` равен 0. Поэтому
не «C». А запись даёт panic. Но внутри `yoz` есть защита `defer` + `recover`: она останавливает падение, `yoz`
завершается, и `main` переходит к строке 9. «B» было бы верно без защиты (это увидим в «Частых ошибках»).

</details>

```console
$ go run ./nilmap
0 0
qutqarildi: assignment to entry in nil map
dastur davom etdi
```

Причина panic: *assignment to entry in nil map* — «присваивание записи в nil map». Официальные правила Go говорят
то же самое: nil map — это то же, что пустая map, только добавлять в неё элементы нельзя.

| Шаг | Что произошло | На экран |
|---|---|---|
| строка 7 | чтение из nil map: 0, `len` 0 | `0 0` |
| строка 18 | запись в nil map → panic | |
| строки 13–17 | сработал `defer`, `recover` поймал panic | `qutqarildi: assignment to entry in nil map` |
| строка 9 | `main` продолжил работу | `dastur davom etdi` |

Ещё одно: в строке 8 мы передали map в `yoz`. Map ведёт себя как слайс: её копия смотрит на **ту же** таблицу.
Поэтому то, что функция запишет в `m`, будет видно и в map снаружи (здесь map была `nil`, поэтому записать не
удалось). Это станет важно в конце урока, когда две горутины будут писать в одну map.

Запомните эту программу. В конце урока увидим случай, когда именно эта защита не работает.

## Порядок: что говорят официальные правила Go

Переходим к порядку. В официальных правилах Go (спецификации Go) это написано прямо:

> *"The iteration order over maps is not specified and is not guaranteed to be the same from one iteration to the
> next."* — «Порядок обхода map не определён и не гарантированно одинаков от одного обхода к следующему».

История этого правила:

| Версия | Что произошло |
|---|---|
| Go 1 | порядок намеренно объявлен «непредсказуемым»: чтобы программисты не полагались на порядок map |
| Go 1.1 | новое внутреннее устройство map забыло сделать порядок случайным для маленьких map (до 8 ключей) |
| Go 1.3 | ошибку исправили: в маленьких map порядок снова случайный |
| Go 1.24 | map стали хранить в памяти по-новому (**Swiss table**), но правила порядка не изменились |

В документе Go 1 цель записана ясно: *"Code should not assume that the elements are visited in any particular
order"* — «Код не должен рассчитывать на то, что элементы обходятся в каком-то определённом порядке».

## Как это устроено: группа из 8 мест и случайное начало

Так почему не 120, а именно 5 порядков? Ответ в исходном коде Go (go1.26.8,
`internal/runtime/maps/table.go`). Сначала простыми словами.

**1. Группа.** В map, где не больше восьми ключей, все ключи лежат в одной **группе**. Группа — это ряд из 8 мест,
как круглый стол на 8 человек. Если удалений не было, ключи садятся на первое свободное место в порядке
добавления. Наши 5 ключей занимают места 0–4, места 5, 6, 7 пустые:

| Место | 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| Ключ | non | sut | tuxum | choy | olma | — | — | — |

**2. Случайное начало.** В начале каждого `range` runtime берёт случайное число и по нему выбирает место начала:
от 0 до 7, каждое с равной вероятностью.

**3. По кругу.** Цикл начинает с этого места и идёт вокруг стола по кругу: после места 7 снова место 0. Пустые
места пропускаются.

Теперь выпишем все восемь вариантов начала:

| Место начала | Получается порядок |
|---|---|
| 0 | non sut tuxum choy olma |
| 1 | sut tuxum choy olma non |
| 2 | tuxum choy olma non sut |
| 3 | choy olma non sut tuxum |
| 4 | olma non sut tuxum choy |
| 5 (пусто) | → 6, 7 пусто → 0: non sut tuxum choy olma |
| 6 (пусто) | → 7 пусто → 0: non sut tuxum choy olma |
| 7 (пусто) | → 0: non sut tuxum choy olma |

Четыре начала из восьми (0, 5, 6, 7) дают один и тот же порядок: `non sut tuxum choy olma`. 4/8 = 50 %. Каждый
из остальных четырёх порядков — 1/8 = 12,5 %. Именно это и показал замер в начале. Ключи всегда идут в одной и той
же круговой последовательности, меняется только точка начала. Поэтому порядков не 120, а 5.

Вот это место в исходном коде (`// ...` — строки, которые мы пропустили). Это внутренний код Go:
`func (it *Iter) Init(…)` — функция, принадлежащая типу `Iter` (метод, [GO-1.12](/lab/youtube/go/go-1-12/ru)), а `*` — указатель
([GO-1.11](/lab/youtube/go/go-1-11/ru)). Понимать всё не обязательно, нам достаточно строк из таблицы.

```go
func (it *Iter) Init(typ *abi.MapType, m *Map) {
	// ...
	it.entryOffset = rand()
	// ...
}

func (it *Iter) Next() {
	// ...
	if it.dirIdx < 0 {
		// Map was small at Init.
		for ; it.entryIdx < abi.MapGroupSlots; it.entryIdx++ {
			k := uintptr(it.entryIdx+it.entryOffset) % abi.MapGroupSlots
			if (it.group.ctrls().get(k) & ctrlEmpty) == ctrlEmpty {
				// Empty or deleted.
				continue
			}
```

| Строка | Что делает |
|---|---|
| 1–5 | `Init` выполняется один раз, когда начинается `range`. `it.entryOffset = rand()`: случайное число, из него берётся место начала |
| 7 | `Next` на каждом шаге находит следующий ключ |
| 9–10 | `if it.dirIdx < 0` — комментарий: *Map was small at Init*, «во время `Init` map была маленькой» (одна группа) |
| 11 | цикл идёт по `abi.MapGroupSlots` = 8 местам группы |
| 12 | `k := … % abi.MapGroupSlots`: к номеру шага прибавляется случайное число и берётся остаток от деления на 8 (`%`, из [GO-1.05](/lab/youtube/go/go-1-05/ru)). Остаток всегда 0–7: после 7 снова 0. Это и есть круг. (`uintptr(…)` — преобразование типа числа, здесь неважно) |
| 13–16 | если место пустое или удалённое (*Empty or deleted*), `continue` пропускает его и переходит к следующему. (`&` здесь — операция над битами: выделяет из метки места бит «пусто») |

Итог: порядок **случайный**, но **не перемешанный**. Из 120 возможных порядков выпадает 5, и они не
равновероятны. Значит, не используйте `range` для выбора случайного элемента: результат распределён неравномерно.
И на этот замер тоже не полагайтесь: это внутреннее устройство Go, в следующей версии оно может измениться.
Правило одно: порядок не гарантирован.

## Пауза: если вывести map два раза

Теперь вместо `range` выведем всю map на экран через `fmt.Println` два раза. Это `chop/main.go` («вывод»):

```go filename="chop/main.go" showLineNumbers
package main

import "fmt"

func main() {
	narx := map[string]int{"non": 5000, "sut": 12000, "tuxum": 18000, "choy": 25000, "olma": 15000}
	fmt.Println(narx)
	fmt.Println(narx)
}
```

- **Строка 6:** те же пять товаров с ценами.
- **Строки 7–8:** выводят всю map два раза.

Будут ли две строки в разном порядке? **A)** да, как и `range`, каждый раз может быть по-разному · **B)** нет,
обе одинаковые, ключи отсортированы · **C)** нет, обе одинаковые, а ключи в порядке добавления

<details>
<summary>Ответ</summary>

**B.** Начиная с Go 1.12 `fmt` перед выводом map сортирует её ключи. Команда Go сделала это, чтобы упростить тесты
(*"to ease testing"*). Если вы выбрали «A», вы рассуждали логично: сама map не упорядочена. Но `fmt` упорядочивает
её перед выводом. Не «C»: в порядке добавления первым был бы `non`, а в выводе первым идёт `choy`.

</details>

```console
$ go run ./chop
map[choy:25000 non:5000 olma:15000 sut:12000 tuxum:18000]
map[choy:25000 non:5000 olma:15000 sut:12000 tuxum:18000]
```

`fmt` выводит map в виде `map[ключ:значение ключ:значение …]`. Ловушка в том, что на экране map выглядит
упорядоченной, а `range` всё равно случайный. Не доверяйте порядку, который видите при проверке программы (во
время отладки).

## Если нужен порядок — отсортируйте ключи

Если нужен порядок, создайте его сами: сначала соберите и отсортируйте ключи, потом читайте из map в этом порядке.
Это `saralash/main.go` («сортировка»):

```go filename="saralash/main.go" showLineNumbers
package main

import (
	"fmt"
	"maps"
	"slices"
)

func main() {
	narx := map[string]int{"non": 5000, "sut": 12000, "tuxum": 18000, "choy": 25000, "olma": 15000}
	for _, nom := range slices.Sorted(maps.Keys(narx)) {
		fmt.Println(nom, narx[nom])
	}
}
```

| Строка | Код | Что делает |
|---|---|---|
| 3–7 | `import ( … )` | три пакета: `fmt`, `maps` (инструменты для map), `slices` (инструменты для слайсов) |
| 11 | `maps.Keys(narx)` | возвращает **итератор**, который выдаёт ключи map по одному. Итератор — не слайс: он не хранит ключи в себе, а выдаёт их по одному по запросу (подробно: [GO-1.18](/lab/youtube/go#go-1-18)) |
| 11 | `slices.Sorted(…)` | собирает все ключи из итератора в **отсортированный слайс** |
| 11 | `for _, nom := range …` | идёт по отсортированному слайсу: `nom` («имя») — очередной ключ |
| 12 | `fmt.Println(nom, narx[nom])` | выводит ключ и его цену из map |

И `maps.Keys`, и `slices.Sorted` появились в Go 1.23.

```console
$ go run ./saralash
choy 25000
non 5000
olma 15000
sut 12000
tuxum 18000
```

Теперь результат каждый раз одинаковый и отсортированный. Внимание: сортировка идёт **по кодам букв** (по байтам),
а не как в узбекском алфавите. В узбекском алфавите `Ch` стоит в конце, после `Z`, `Oʻ`, `Gʻ`, `Sh`. А для
сортировки `choy` — просто слово на букву `c`, поэтому оно стоит первым.

### Исходная программа

Теперь можно полностью прочитать программу `tartib` из начала урока. Она выводила результаты именно этим способом:

```go filename="tartib/main.go" showLineNumbers
package main

import (
	"fmt"
	"maps"
	"slices"
	"strings"
)

func main() {
	narx := map[string]int{"non": 5000, "sut": 12000, "tuxum": 18000, "choy": 25000, "olma": 15000}

	const n = 100_000
	sanoq := map[string]int{} // har bir tartib necha marta chiqdi
	for range n {
		var kalitlar []string
		for nom := range narx {
			kalitlar = append(kalitlar, nom)
		}
		sanoq[strings.Join(kalitlar, " ")]++
	}
	fmt.Printf("%d ta sikl, %d xil tartib:\n", n, len(sanoq))
	for _, t := range slices.Sorted(maps.Keys(sanoq)) {
		fmt.Printf("%-24s %5.1f%%\n", t, 100*float64(sanoq[t])/n)
	}
}
```

| Строка | Код | Что делает |
|---|---|---|
| 3–8 | `import ( … )` | ещё пакет `strings`: инструменты для работы со строками |
| 13 | `const n = 100_000` | константа 100 000. Подчёркивание только для удобства чтения, число не меняется |
| 14 | `sanoq := map[string]int{}` | вторая map (`sanoq` — «подсчёт»): ключ — строка с порядком, значение — сколько раз он выпал (комментарий: «сколько раз выпал каждый порядок») |
| 15 | `for range n {` | повторяет 100 000 раз (переменная цикла не нужна) |
| 16 | `var kalitlar []string` | на каждом круге новый пустой слайс `kalitlar` («ключи») |
| 17–19 | `for nom := range narx { … append … }` | идёт по map `narx` и добавляет ключи в слайс в том порядке, в каком они пришли |
| 20 | `sanoq[strings.Join(kalitlar, " ")]++` | `strings.Join` склеивает ключи через пробел в одну строку: `"non sut tuxum choy olma"`. `++` увеличивает счётчик этого порядка на 1. Для нового порядка map вернёт 0, поэтому отдельная проверка не нужна |
| 22 | `fmt.Printf("%d ta sikl, %d xil tartib:\n", …)` | `Printf` выводит по шаблону: вместо каждого `%d` подставляется очередное целое число; `\n` — новая строка. `len(sanoq)` — сколько разных порядков выпало |
| 23 | `for _, t := range slices.Sorted(maps.Keys(sanoq)) {` | сортирует порядки и берёт по одному |
| 24 | `fmt.Printf("%-24s %5.1f%%\n", …)` | `%-24s` — строка, выровненная влево в поле из 24 символов; `%5.1f` — дробное число с одним знаком после точки; `%%` — сам знак `%`. `100*float64(sanoq[t])/n` — процент; `float64(…)` преобразует счётчик в дробное число, иначе деление целых чисел отбросило бы дробную часть |

## Одновременная запись: fatal error

Теперь самая опасная ловушка. Для неё нужно одно новое вспомогательное слово.

До сих пор наши программы выполняли одну работу шаг за шагом. Но программа может выполнять и несколько работ
одновременно. Например, в магазине одновременно работают два кассира. В Go каждая отдельная работа, которая
выполняется одновременно с другими, называется **горутиной** (goroutine). Сам `main` — тоже горутина. Горутины
подробно изучим в [GO-1.21](/lab/youtube/go#go-1-21).

Это `poyga/main.go` («poyga» — «гонка»). В нём ошибка **специально**:

```go filename="poyga/main.go" showLineNumbers
package main

import (
	"fmt"
	"sync"
)

func main() {
	m := map[int]int{}
	var wg sync.WaitGroup
	for g := range 2 {
		wg.Go(func() { yoz(m, g) }) // ataylab xato: ikki goroutine bitta map'ga yozadi
	}
	wg.Wait()
	fmt.Println("dastur davom etdi:", len(m))
}

func yoz(m map[int]int, g int) {
	defer func() {
		if r := recover(); r != nil {
			fmt.Println("qutqarildi:", r)
		}
	}()
	for i := range 1_000_000 {
		m[i] = g
	}
}
```

| Строка | Код | Что делает |
|---|---|---|
| 5 | `"sync"` | пакет инструментов для горутин, работающих одновременно |
| 9 | `m := map[int]int{}` | пустая map: и ключ, и значение — `int` |
| 10 | `var wg sync.WaitGroup` | **WaitGroup** запускает горутины и ждёт, пока все они закончат (подробно в [GO-1.22](/lab/youtube/go#go-1-22)) |
| 11 | `for g := range 2 {` | два раза: `g` = 0, затем 1 |
| 12 | `wg.Go(func() { yoz(m, g) })` | запускает анонимную функцию в **новой горутине**. Она вызывает `yoz(m, g)`. `main`, не дожидаясь, идёт к следующему шагу. `wg.Go` появился в Go 1.25. Комментарий: «специальная ошибка: две горутины пишут в одну map» |
| 14 | `wg.Wait()` | ждёт здесь, пока обе горутины не закончат |
| 15 | `fmt.Println("dastur davom etdi:", len(m))` | если программа дойдёт сюда, выведет число ключей |
| 18 | `func yoz(m map[int]int, g int) {` | функция, которая пишет в map; `g` — номер горутины |
| 19–23 | `defer func() { … recover … }()` | та же защита, что в `nilmap` |
| 24–26 | `for i := range 1_000_000 { m[i] = g }` | пишет в map миллион раз: ключ `i`, значение `g` |

Обе горутины получили копию `m`, но map ведёт себя как слайс: обе копии смотрят на **одну** таблицу. Значит, две
горутины одновременно пишут в одну map. Внутри каждой стоит `recover`.

```text
main ─┬─ wg.Go ──► горутина 0:  m[0]=0  m[1]=0  m[2]=0  …
      │                              ╲
      │                               ►  одна map  m  ◄──  два писателя одновременно
      │                              ╱
      ├─ wg.Go ──► горутина 1:  m[0]=1  m[1]=1  m[2]=1  …
      └─ wg.Wait()  …ждёт, пока обе закончат
```

Угадайте: что произойдёт? **A)** выведется `qutqarildi: …`, программа продолжит работу · **B)** программа упадёт,
надписи `qutqarildi` не будет · **C)** ошибки нет: `dastur davom etdi: 1000000`

<details>
<summary>Ответ</summary>

**B.** Программа падает, и `recover` ничего не ловит. Это не обычный panic, а **fatal error**. Разберём его ниже.
Если вы выбрали «A», вы думали, что будет panic, как в `nilmap`. Если выбрали «C», вы думали, что одновременная
запись в map безопасна. Так думают и многие программисты (пример Uber в конце урока).

</details>

В видео и здесь программу запускают через вспомогательный скрипт. Причина: Go обнаруживает эту ошибку по принципу
«best effort» (объясним ниже). В очень редких случаях программа падает с другим сообщением или завершается без
падения. `poyga/demo.sh` один раз компилирует программу и перезапускает её, пока не получит сообщение
`fatal error: concurrent map writes` и код выхода 2 (не больше 20 попыток). Затем выводит строку сообщения и код
выхода, полученные из настоящего запуска. `bash` — программа, которая выполняет скрипт.

```console
$ bash ./poyga/demo.sh
fatal error: concurrent map writes
exit status 2
```

*fatal error: concurrent map writes* — «фатальная ошибка: одновременная запись в map». *exit status 2* —
программа остановилась с кодом выхода 2 (0 — успех, другое число — ошибка). Надписи `qutqarildi` нет, нет и
`dastur davom etdi`.

Обычный `go run ./poyga` выводит ту же первую строку. А под ней идёт список горутин (stack trace). В нашем запуске
в нём были `main.yoz` и `poyga/main.go:25`: строка 25, `m[i] = g`. В видео этот длинный список сокращён.

## Почему recover бессилен: panic и fatal

Строка `m[i] = g` на самом деле вызывает одну функцию из runtime. Вот её сокращённый вид (go1.26.8):

```go
// internal/runtime/maps/runtime_fast64.go
func runtime_mapassign_fast64(...) unsafe.Pointer {
	if m == nil {
		panic(errNilAssign)
	}
	// ...
	if m.writing != 0 {
		fatal("concurrent map writes")
	}
	// ...
	m.writing ^= 1 // toggle, see comment on writing
	// ...
}

// runtime/panic.go
// fatal is equivalent to throw, but is used when user code is expected to be
// at fault for the failure, such as racing map writes.
```

| Строка | Что делает |
|---|---|
| 2 | функция runtime, которая пишет в map с ключом `int`: наш `m[i] = g` вызывает именно её. `(...)` — параметры, которые мы сократили; `unsafe.Pointer` — тип возвращаемого значения, здесь неважно |
| 3–5 | если map равна `nil` — обычный `panic`. Это была ошибка в `nilmap`, и `recover` её поймал |
| 7–9 | `m.writing` — флажок: «пишет ли сейчас кто-то в эту map?». Если пишет — не `panic`, а `fatal` |
| 11 | в начале записи переключает флажок (`^= 1`: был 0 — станет 1, был 1 — станет 0) |
| 15–16 | комментарий к `fatal`: *«`fatal` — то же, что `throw`, но используется, когда в ошибке, как ожидается, виноват код пользователя, например при гонке записей в map»* |

Runtime считает это ошибкой программиста. `fatal` выводит сообщение и останавливает программу с кодом 2, не
запуская `defer`. Раз `defer` не выполняется, не выполняется и `recover` внутри него. Логически (это наше
объяснение, а не слова источника): продолжать работу с map, которая, возможно, повреждена, опасно.

| | `nilmap` | `poyga` |
|---|---|---|
| Ошибка | запись в nil map | две горутины пишут одновременно |
| Что делает runtime | `panic(errNilAssign)` | `fatal("concurrent map writes")` |
| Выполняется ли `defer` | да | нет |
| `recover` | ловит: `qutqarildi: …` | не может поймать |
| Программа | продолжает работу | `exit status 2` |

## Два важных момента: «best effort» и только чтение

**1. Эта проверка — не гарантия.** Начиная с Go 1.6 runtime обнаруживает неправильное использование map. В его
документации это названо *"best-effort detection"*: «обнаружение по мере возможности». То есть иногда ошибка может
проскочить незамеченной.

Гораздо лучший инструмент — **race detector** (детектор гонок: инструмент Go, который находит гонки данных).
Запускайте тесты с флагом `-race`: `go test -race`. Но и он проверяет только тот код, который реально выполнился:
ошибку на пути, который ни разу не выполнялся, он не найдёт. В Linux детектору гонок нужен компилятор C (gcc). На
компьютере курса gcc не было, поэтому его вывод здесь не показываем. Его увидим в [GO-1.22](/lab/youtube/go#go-1-22).

**2. Только чтение безопасно.** Если несколько горутин только **читают** map, это безопасно. Go FAQ: *"Map access is
unsafe only when updates are occurring"* — «доступ к map опасен, только когда происходят изменения». Проблема
начинается, когда кто-то пишет.

| Кто что делает | Безопасно ли |
|---|---|
| несколько горутин только читают | да |
| одна горутина пишет, другая читает или пишет | нет: нужна защита |

## Исправление: sync.Mutex

Исправление: оборачиваем каждую запись в map **мьютексом** (mutex). Представьте примерочную на одного человека.
Вошедший запирает дверь изнутри, остальные ждут в очереди. Выходя, он открывает замок, и входит следующий.
`sync.Mutex` и есть такой замок: `Lock` впускает внутрь только одну горутину за раз. Когда работа закончена,
`Unlock` открывает путь другой.

Это `mutex/main.go`:

```go filename="mutex/main.go" showLineNumbers
package main

import (
	"fmt"
	"sync"
)

func main() {
	m := map[int]int{}
	var mu sync.Mutex
	var wg sync.WaitGroup
	for g := range 2 {
		wg.Go(func() {
			for i := range 1_000_000 {
				mu.Lock()
				m[i] = g
				mu.Unlock()
			}
		})
	}
	wg.Wait()
	fmt.Println("tugadi:", len(m))
}
```

Отличия от `poyga`:

| Строка | Код | Что делает |
|---|---|---|
| 10 | `var mu sync.Mutex` | замок. Его нулевое значение готово к работе: открытый замок |
| 13–19 | `wg.Go(func() { … })` | нет ни функции `yoz`, ни `recover`: цикл прямо внутри анонимной функции |
| 15 | `mu.Lock()` | запирает. Если замок занят, вторая горутина ждёт здесь |
| 16 | `m[i] = g` | запись в map: теперь за раз пишет только одна горутина |
| 17 | `mu.Unlock()` | открывает замок, может войти следующая горутина |
| 22 | `fmt.Println("tugadi:", len(m))` | «готово:» и число ключей в map |

Угадайте: какое число выведется после `tugadi:`? **A)** `2000000` · **B)** `1000000` · **C)** каждый раз разное,
меньше 1000000

<details>
<summary>Ответ</summary>

**B: `1000000`.** Обе горутины пишут в **одни и те же** ключи: от 0 до 999 999. Повторная запись в тот же ключ не
добавляет новый ключ, а только заменяет его значение. Значит, в map миллион ключей. Если вы выбрали «A», вы думали,
что каждая запись добавляет новый ключ. «C» — беспорядок, которого можно ждать без мьютекса, но с мьютексом все
записи выполняются по очереди.

</details>

```console
$ go run ./mutex
tugadi: 1000000
```

Теперь программа не падает, и в map миллион ключей. `sync.Mutex` и `WaitGroup` разберём глубже в
[GO-1.22](/lab/youtube/go#go-1-22).

## Реальный мир: Uber, 2022

Это не теоретическая проблема. В 2022 году инженеры Uber изучили **гонки данных** (data race) в своём коде на Go.
Гонка данных — ошибка, когда две горутины одновременно обращаются к одной и той же памяти и хотя бы одна из них
пишет.

| Число | Что |
|---|---|
| около 2000 | найденных гонок данных |
| около 1100 | исправлено и проанализировано (210 программистов, шесть месяцев) |

Одновременный доступ к map был одной из частых причин. Программисты считали, что обращаться к разным ключам
безопасно. Ведь квадратные скобки в `table[key]` выглядят так, будто обращаешься к отдельному элементу. На самом же
деле все ключи лежат в одной map, внутри одной общей структуры.

## Глубже (необязательно): почему проверка — «best effort»

Посмотрите ещё раз на флажок в runtime: `m.writing ^= 1`. Это обычное, **не атомарное** переключение. Атомарную
операцию другая горутина не может увидеть на полпути; эта операция не такая. Если два писателя переключат флажок
одновременно, проверка может этого не заметить.

При подготовке урока критик (отдельный проверяющий) много раз запускал `poyga` и замерил:

| Условия | Результат |
|---|---|
| 300 обычных запусков | 297 раз `fatal error: concurrent map writes`, 2 раза `small map with no empty slot (concurrent map writes?)`, 1 раз `unexpected fault address` (обращение по неверному адресу в памяти) |
| 100 запусков с `GOMAXPROCS=1` | 98 упали, 2 завершились без падения |

`GOMAXPROCS=1` — настройка, при которой код Go выполняется одновременно только на одном ядре процессора. Даже так
программа падала почти каждый раз. Значит, проблема не в том, что две работы выполняются ровно в один и тот же миг:
достаточно, чтобы вторая запись началась, пока первая не закончилась. Поэтому мы говорим не «параллельно», а
«одновременно». А один `unexpected fault address` показывает, что повреждённая map действительно опасна.

Ещё один расчёт: вероятность того, что два запуска `tartib` дадут один и тот же порядок, — около 31 %
(0,5² + 4 · 0,125²). Поэтому «запустил два раза, порядок совпал» ничего не доказывает.

## Частые ошибки

**1. Полагаться на порядок map.** Главная ловушка урока. Программа не выдаёт ошибку, но порядок `range` может
каждый раз быть другим (выше, раздел «Как это устроено»). `fmt.Println(map)` выводит её отсортированной и этим
скрывает проблему (раздел «Пауза»). Использовать `range` для выбора случайного элемента — тоже ошибка: в нашей map
один порядок выпадал в 50 % случаев. **Исправление:** если нужен порядок, сортируйте через
`slices.Sorted(maps.Keys(m))`; если нужен случайный элемент, выбирайте его случайным числом.

**2. Считать ноль «отсутствием».** `if narx["suv"] == 0 { … "yoʻq" … }` посчитает «отсутствующим» (`yoʻq`) и
бесплатный товар (`suv` — «вода»). И отсутствующий ключ, и ключ со значением 0 возвращают 0 (раздел «Comma ok»).
**Исправление:** `n, bor := narx["suv"]` и проверяйте `bor`.

**3. Запись в nil map без защиты.** Этого примера нет в папке курса, он запущен отдельно:

```go
package main

import "fmt"

func main() {
	var narx map[string]int
	narx["non"] = 5000
	fmt.Println(narx)
}
```

```console
$ go run -trimpath nilyoz/main.go
panic: assignment to entry in nil map

goroutine 1 [running]:
main.main()
	./main.go:7 +0x28
exit status 2
```

`-trimpath` только укорачивает путь к файлу в сообщении; без него выведется полный путь к папке на вашем
компьютере. Читаем сообщение: *panic: assignment to entry in nil map* — «panic: присваивание записи в nil map».
*goroutine 1 [running]* — ошибка случилась в горутине 1, то есть в `main`. `main.main()` и `main.go:7` — функция
`main`, строка 7: `narx["non"] = 5000`. `recover` нет, поэтому программа упала с кодом 2. **Исправление:** создайте
map: `narx := map[string]int{}` или `narx := make(map[string]int)`.

**4. Думать, что `recover` поймает и одновременную запись.** Мы видели в `poyga`: `recover` стоит, а программа всё
равно падает, потому что это не panic, а fatal error (раздел «Почему recover бессилен»). **Исправление:** защитите
запись в map через `sync.Mutex` (раздел «Исправление: sync.Mutex»), а тесты запускайте с `go test -race`.

**5. Думать, что `maps.Keys` возвращает слайс.** (Нет в папке курса, запущено отдельно.)

```go
package main

import (
	"fmt"
	"maps"
)

func main() {
	narx := map[string]int{"non": 5000, "sut": 12000}
	kalitlar := maps.Keys(narx)
	fmt.Println(len(kalitlar))
}
```

```console
$ go run kalitlar/main.go
# command-line-arguments
kalitlar/main.go:11:18: invalid argument: kalitlar (variable of func type iter.Seq[string]) for built-in len
```

Строка 11, символ 18: *invalid argument: kalitlar (variable of func type iter.Seq[string]) for built-in len* —
«неверный аргумент для встроенной `len`: `kalitlar` — переменная-функция типа `iter.Seq[string]`». То есть
`maps.Keys` вернула не слайс, а итератор, а `len` не умеет считать итератор. **Исправление:** сначала соберите
ключи в слайс: `kalitlar := slices.Sorted(maps.Keys(narx))` (отсортированный) или
`slices.Collect(maps.Keys(narx))` (без сортировки). После этого `len(kalitlar)` работает.

## Проверьте себя

Сначала ответьте сами, потом откройте.

**1.** Что будет, если прочитать из map отсутствующий ключ? Как отличить «цена 0» от «такого ключа нет»?

<details>
<summary>Ответ</summary>

Ошибки не будет: map вернёт нулевое значение типа значения (для `int` — 0). Чтобы различить, используйте comma ok:
`n, bor := narx["olma"]`. Если `bor` равно `false`, ключа нет; если `true`, ключ есть и цена равна `n`.

</details>

**2.** Нужно каждый раз выводить ключи map в одном и том же порядке. Что вы сделаете?

<details>
<summary>Ответ</summary>

Не будете полагаться на порядок `range`. Отсортируете ключи и пойдёте в этом порядке:
`for _, k := range slices.Sorted(maps.Keys(m)) { … m[k] … }`.

</details>

**3.** Если две горутины одновременно пишут в одну map, спасёт ли программу `recover` внутри каждой из них?

<details>
<summary>Ответ</summary>

Нет. Runtime вызывает не `panic`, а `fatal`: `fatal error: concurrent map writes`. Он останавливает программу с
кодом 2, не запуская `defer`, поэтому до `recover` дело не доходит. Исправление: `sync.Mutex`.

</details>

**4.** Что выведет эта программа? **A)** `2 0 false 2` · **B)** `2 0 false 1` · **C)** `1 0 true 1`

```go
package main

import "fmt"

func main() {
	sanoq := map[string]int{}
	sanoq["a"]++
	sanoq["a"]++
	n, bor := sanoq["b"]
	fmt.Println(sanoq["a"], n, bor, len(sanoq))
}
```

<details>
<summary>Ответ</summary>

**B: `2 0 false 1`.** `sanoq["a"]++` в первый раз увеличивает с 0 до 1, во второй — до 2. Ключа `"b"` нет:
`n` = 0, `bor` = `false`. Чтение отсутствующего ключа ничего не добавляет в map, поэтому `len` равен 1. Если вы
выбрали «A», вы думали, что чтение тоже добавляет ключ. (Этой программы нет в папке курса, она запущена отдельно.)

```console
$ go run savol/main.go
2 0 false 1
```

</details>

**5.** Если несколько горутин только читают map (никто не пишет), нужна ли защита?

<details>
<summary>Ответ</summary>

Не нужна: только чтение безопасно. Проблема начинается, когда кто-то пишет.

</details>

**6.** Из [GO-1.06](/lab/youtube/go/go-1-06/ru): замыкание захватывает копию внешней переменной или саму переменную?

<details>
<summary>Ответ</summary>

Саму переменную. Если после создания замыкания переменная изменится, замыкание увидит новое значение. Анонимные
функции в сегодняшних `poyga` и `mutex` так же захватывают внешние `m`, `g` и `mu`.

</details>
