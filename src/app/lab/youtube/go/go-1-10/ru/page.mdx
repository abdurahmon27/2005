## Что вы узнаете

Есть две записи заказа. В обеих одни и те же три значения: оплачен ли заказ (да/нет), сумма и доставлен ли он
(да/нет). Разница только в порядке. Первая занимает в памяти **24 байта**, вторая **16 байт**. Сами данные при
этом занимают 10 байт. Откуда взялись лишние байты? Несколько таких байтов однажды уронили один из сервисов GitLab.
Сегодня заглянем внутрь записи и посчитаем каждый байт.

**Одна идея:** поля структуры лежат в памяти друг за другом, но каждое поле должно начинаться с адреса,
подходящего для его типа. Поэтому между полями могут оставаться пустые байты (padding): порядок полей меняет
размер структуры. Если поставить поля с большим выравниванием в начало, структура чаще всего становится меньше, но
делайте это по результатам измерений.

К концу урока вы:

- объявите свой тип-структуру и создадите его значение составным литералом, сможете читать встраивание (embedding);
- нарисуете на бумаге каждый байт структуры с помощью `unsafe.Sizeof`, `unsafe.Alignof` и `unsafe.Offsetof` и
  проверите результат;
- сможете уменьшить структуру, переставив поля, и будете знать, когда это даёт выигрыш, а когда нет;
- объясните, почему на 32-битной системе счётчик `int64` вызывает panic и как `atomic.Int64` это исправляет.

Три главных новых слова урока:

| Слово | Простой смысл | По-английски |
|---|---|---|
| структура (поле) | тип с заранее объявленными полями: близко к типу объекта в TS или к `dataclass` в Python | struct (field) |
| padding (пустые байты) | байты между полями или в конце, которые ничего не хранят | padding |
| выравнивание | какому числу должен быть кратен адрес значения: 8-байтовое число — по адресу, кратному 8 | alignment |

По ходу встретятся два вспомогательных слова: **составной литерал** (composite literal: значение структуры,
записанное прямо в коде в фигурных скобках) и **встраивание** (embedding: одна структура внутри другой без имени
поля). Оба объясним там, где они понадобятся.

## Структура: несколько полей, один тип

Магазину нужно помнить клиента: имя, деньги на счёте и адрес доставки. Три отдельные переменные неудобны: они
всегда должны ходить вместе. В JS/TS для этого вы бы написали объект (`{ name, balance }`) и его тип, в Python —
`class` или `dataclass`.

В Go нет `class`. Вместо него — **структура** (struct): тип с заранее объявленными полями. Каждое именованное
значение называется **поле** (по-английски **field**). Отличие от объекта JS: во время работы программы в
структуру нельзя добавить новое поле, поля и их типы известны при компиляции. Структуру мы уже видели в
[GO-1.07](/lab/youtube/go/go-1-07/ru), в табличном тесте, в виде `[]struct{ … }`. Сегодня дадим ей собственное имя.

Вот `literal/main.go` из папки курса:

```go filename="literal/main.go" showLineNumbers
// literal: struct e'lon qilish, composite literal, zero value va embedding.
package main

import "fmt"

type Manzil struct {
	Shahar string
	Kocha  string
}

type Mijoz struct {
	Ism    string
	Balans int64 // tiyinda
	Manzil       // embedding: tur nomi (Manzil) maydon nomi ham boʻladi
}

func main() {
	// kalitli literal: maydon nomi bilan, tartib muhim emas; Manzil yozilmadi -> zero value
	a := Mijoz{Ism: "Aziza", Balans: 50_000}
	fmt.Printf("%+v\n", a)

	// var: hamma maydon zero value oladi
	var b Mijoz
	fmt.Printf("%+v\n", b)

	// embedding: Manzil'ning maydonlari Mijoz'ga "koʻtariladi"
	a.Shahar = "Samarqand"
	fmt.Println(a.Shahar, a.Manzil.Shahar)
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1 | `// literal: …` | комментарий: о чём программа |
| 6 | `type Manzil struct {` | `type` объявляет новый тип. Его имя `Manzil` («адрес»: почтовый адрес), это структура |
| 7–8 | `Shahar string`, `Kocha  string` | два поля: сначала имя поля, потом тип. `Shahar` («город») и `Kocha` («улица») — строки |
| 11 | `type Mijoz struct {` | ещё один новый тип: `Mijoz` («клиент») |
| 12 | `Ism    string` | поле `Ism` («имя»), строка |
| 13 | `Balans int64 // tiyinda` | `Balans` («баланс»): `int64` — целое число на 8 байт. Деньги хранятся в тийинах (1 сум = 100 тийинов) |
| 14 | `Manzil` | имени поля нет, только имя типа: это **встраивание** (embedding). Разберём ниже отдельно |
| 19 | `a := Mijoz{Ism: "Aziza", Balans: 50_000}` | создаём значение `Mijoz`. `50_000` — это 50 000, подчёркивание только для читаемости |
| 20 | `fmt.Printf("%+v\n", a)` | `%v` выводит значение в обычном для Go виде, `+` добавляет имена полей. `\n` — новая строка |
| 23 | `var b Mijoz` | переменная `b` типа `Mijoz` без явного значения |
| 24 | `fmt.Printf("%+v\n", b)` | выводит `b` с именами полей |
| 27 | `a.Shahar = "Samarqand"` | записываем новое значение в поле `Shahar` переменной `a`. Точка `.` обращается к полю |
| 28 | `fmt.Println(a.Shahar, a.Manzil.Shahar)` | два способа обратиться к одному и тому же полю: разберём в разделе о встраивании |

Внимание: в этом уроке слово «адрес» встречается в двух смыслах. Тип `Manzil` — почтовый адрес клиента (город,
улица). А «адрес в памяти» ниже — место, где значение лежит в памяти (`&x` из [GO-1.05](/lab/youtube/go/go-1-05/ru)).

Запись `Mijoz{ … }` в строке 19 называется **составной литерал** (composite literal): значение структуры,
записанное прямо в коде в фигурных скобках. Выглядит как объектный литерал в JS, но перед скобками стоит имя типа.
Внутри стоят пары `поле: значение`. Такой литерал, где поля названы по имени (имена полей служат ключами),
называется литералом с ключами, и порядок полей в нём не важен: `Mijoz{Balans: 50_000, Ism: "Aziza"}` — то же самое
значение. Здесь `Manzil` вообще не указан. По официальным правилам Go незаписанное поле получает нулевое значение.

Прежде чем запускать, подумайте: что выведет вторая строка (`var b Mijoz`)?
**A)** `{Ism: Balans:0 Manzil:{Shahar: Kocha:}}` · **B)** `<nil>` · **C)** ошибка компиляции: `b` не присвоено
значение

<details>
<summary>Ответ</summary>

**A.** В структуре, объявленной через `var`, **все** поля получают нулевое значение: строки пустые (после `Ism:`
ничего нет), число `0`. Поля вложенной структуры `Manzil` — тоже пустые строки. Аналога `undefined` из JS здесь
нет. Если вы выбрали «B»: значение структуры не бывает `null`, оно всегда стоит со своими полями. Не «C»: как мы
видели в [GO-1.02](/lab/youtube/go/go-1-02/ru), Go заполняет переменную без значения нулевым значением и не выдаёт ошибку.

</details>

```console
$ go run ./literal
{Ism:Aziza Balans:50000 Manzil:{Shahar: Kocha:}}
{Ism: Balans:0 Manzil:{Shahar: Kocha:}}
Samarqand Samarqand
```

В первой строке есть имя и баланс Азизы, адрес пустой. Во второй все поля имеют нулевое значение. В памяти оба
значения выглядят так:

| Поле | `a` (через литерал) | `b` (через `var`) |
|---|---|---|
| `Ism` | `"Aziza"` | `""` |
| `Balans` | `50000` | `0` |
| `Manzil.Shahar` | `""` | `""` |
| `Manzil.Kocha` | `""` | `""` |

## Встраивание: поля вложенной структуры поднимаются наружу

В строке 14 структуры `Mijoz` имя поля не написано, стоит только тип `Manzil`. Такое поле называется **встроенным
полем** (embedded field), а сам приём — **встраиванием** (embedding). Имя у поля всё же есть: им становится само
имя типа. Поэтому `a.Manzil.Shahar` в строке 28 работает.

Третью строку можно предсказать заранее. В строке 27 мы записали в `a.Shahar`, хотя поля `Shahar` в `Mijoz` нет.
Что выведет строка 28? **A)** `Samarqand` и пустое место · **B)** `Samarqand Samarqand` · **C)** ошибка компиляции:
в `Mijoz` нет `Shahar`

<details>
<summary>Ответ</summary>

**B: `Samarqand Samarqand`** (вывод выше, третья строка). Поля вложенной структуры «поднимаются» во внешнюю (в
официальных правилах Go — *promoted*): `a.Shahar` — краткая запись `a.Manzil.Shahar`. Это одна и та же ячейка,
поэтому `Samarqand` дважды. Если вы выбрали «A», вы решили, что это два разных поля. Не «C»: поднятое поле
используется как собственное поле внешней структуры.

</details>

```text
a (Mijoz)
├─ Ism      "Aziza"
├─ Balans   50000
└─ Manzil   (тип Manzil)
   ├─ Shahar   "Samarqand"   ← и a.Shahar, и a.Manzil.Shahar — эта ячейка
   └─ Kocha    ""
```

Это не наследование: не то же самое, что `class Mijoz extends Manzil` в JS/TS или `class Mijoz(Manzil)` в Python.
`Mijoz` не становится типом `Manzil`, в него поднимаются только поля `Manzil`. Официальное руководство Go
(Effective Go) пишет то же: встраивание существенно отличается от наследования (subclassing) в других языках. В
«Частых ошибках» увидим это на сообщении об ошибке. Функции, привязанные к типу (методы), поднимаются точно так
же. Это разберём в [GO-1.12](/lab/youtube/go/go-1-12/ru).

## Загадка из начала: одинаковые поля, 24 и 16 байт

Теперь посмотрим, как структура лежит в памяти. Вот `olcham/main.go`:

```go filename="olcham/main.go" showLineNumbers
// olcham: maydonlari bir xil ikki struct, lekin oʻlchami har xil.
package main

import (
	"fmt"
	"unsafe"
)

// Buyurtma: maydonlar "mantiqiy" tartibda yozilgan.
type Buyurtma struct {
	Tolandi    bool  // toʻlandimi?
	Summa      int64 // tiyinda
	Yetkazildi bool  // yetkazildimi?
}

// Ixcham: xuddi shu uchta maydon, faqat tartibi boshqa.
type Ixcham struct {
	Summa      int64
	Tolandi    bool
	Yetkazildi bool
}

func main() {
	fmt.Println("Buyurtma:", unsafe.Sizeof(Buyurtma{}), "bayt")
	fmt.Println("Ixcham:  ", unsafe.Sizeof(Ixcham{}), "bayt")
}
```

| Строка | Код | Что делает |
|---|---|---|
| 4–7 | `import ( "fmt" "unsafe" )` | два пакета. `unsafe` — низкоуровневый пакет, который идёт вместе с Go; мы используем его только для измерений (так же, как в [GO-1.08](/lab/youtube/go/go-1-08/ru)) |
| 10–14 | `type Buyurtma struct { … }` | `Buyurtma` («заказ»): `Tolandi` («оплачен», `bool`), `Summa` («сумма», `int64`, в тийинах), `Yetkazildi` («доставлен», `bool`) |
| 17–21 | `type Ixcham struct { … }` | `Ixcham` («компактный»): те же три поля, только `Summa` стоит первым |
| 24 | `unsafe.Sizeof(Buyurtma{})` | `Buyurtma{}` — литерал, у которого все поля имеют нулевое значение. `unsafe.Sizeof` возвращает его размер в байтах |
| 25 | `unsafe.Sizeof(Ixcham{})` | то же для `Ixcham`. Пробелы в `"Ixcham:  "` выравнивают две строки вывода |

Прежде чем запускать, посчитайте. `bool` — 1 байт, `int64` — 8 байт. Сколько байт занимают три поля вместе?

<details>
<summary>Ответ</summary>

1 + 8 + 1 = **10 байт**. Столько занимают сами поля. Теперь посмотрим, что скажет Go.

</details>

```console
$ go run ./olcham
Buyurtma: 24 bayt
Ixcham:   16 bayt
```

Не 10! `Buyurtma` — 24 байта, `Ixcham` — 16 байт. Поля одинаковые, отличается только порядок. Значит, лишние 14 и
6 байт берутся не из самих полей, а из их **расположения**. Чтобы увидеть, какой байт где лежит, нужны
измерительные инструменты.

## Измеряем структуру изнутри: Sizeof, Alignof, Offsetof

Возьмём три функции из пакета `unsafe`:

```go
var x Buyurtma

unsafe.Sizeof(x)         // 24: jami, padding bilan
unsafe.Alignof(x)        // 8: manzil 8 ga karrali
unsafe.Offsetof(x.Summa) // 8: boshidan 8 bayt narida
```

- **`unsafe.Sizeof`** говорит, сколько байт занимает тип, вместе с пустыми байтами. В документации: *"For a struct,
  the size includes any padding introduced by field alignment"* — «для структуры размер включает padding,
  добавленный из-за выравнивания полей».
- **`unsafe.Alignof`** говорит, какому числу должен быть кратен адрес значения в памяти. «Кратен 8» — делится на 8
  без остатка: 0, 8, 16, 24…
- **`unsafe.Offsetof`** говорит, на сколько байт поле отстоит от начала структуры. Это число по-английски
  называется **offset** (смещение). Смещение первого поля всегда 0.

Из этих чисел можно нарисовать карту каждого байта. Это делает `xarita/main.go`:

```go filename="xarita/main.go" showLineNumbers
// xarita: har bir maydon struct ichida qayerda turadi (Offsetof) va
// orada nechta boʻsh bayt (padding) bor.
package main

import (
	"fmt"
	"strings"
	"unsafe"
)

type Buyurtma struct {
	Tolandi    bool
	Summa      int64
	Yetkazildi bool
}

type Ixcham struct {
	Summa      int64
	Tolandi    bool
	Yetkazildi bool
}

type maydon struct {
	harf           string
	offset, olcham uintptr
}

// chiz: har bir bayt uchun bitta belgi; maydon harfi yoki "·" (padding).
func chiz(nom string, jami, align uintptr, mm ...maydon) {
	b := []string{}
	for range jami {
		b = append(b, "·")
	}
	for _, m := range mm {
		for i := m.offset; i < m.offset+m.olcham; i++ {
			b[i] = m.harf
		}
	}
	fmt.Printf("%-9s %2d bayt, align %d  [%s]\n", nom, jami, align, strings.Join(b, ""))
}

func main() {
	var x Buyurtma
	chiz("Buyurtma", unsafe.Sizeof(x), unsafe.Alignof(x),
		maydon{"T", unsafe.Offsetof(x.Tolandi), unsafe.Sizeof(x.Tolandi)},
		maydon{"S", unsafe.Offsetof(x.Summa), unsafe.Sizeof(x.Summa)},
		maydon{"Y", unsafe.Offsetof(x.Yetkazildi), unsafe.Sizeof(x.Yetkazildi)})

	var y Ixcham
	chiz("Ixcham", unsafe.Sizeof(y), unsafe.Alignof(y),
		maydon{"S", unsafe.Offsetof(y.Summa), unsafe.Sizeof(y.Summa)},
		maydon{"T", unsafe.Offsetof(y.Tolandi), unsafe.Sizeof(y.Tolandi)},
		maydon{"Y", unsafe.Offsetof(y.Yetkazildi), unsafe.Sizeof(y.Yetkazildi)})
}
```

На карте каждая буква — первая буква имени поля и один байт: `T` = `Tolandi`, `S` = `Summa`, `Y` = `Yetkazildi`.
`·` — пустой байт.

Предскажите: с какого байта на карте `Buyurtma` начинаются `S`? **A)** с 1 (сразу после `T`) · **B)** с 8 ·
**C)** с 16

<details>
<summary>Ответ</summary>

**B: с 8.** Выравнивание `int64` равно 8: он должен начинаться с адреса, кратного 8. `T` занял байт 0, а числа от
1 до 7 не кратны 8. Ближайшее кратное место — 8. Если вы выбрали «A», вы думали, что поля всегда лежат вплотную.
Не «C»: 8 само кратно 8.

</details>

```console
$ go run ./xarita

Ixcham    16 bayt, align 8  [SSSSSSSSTY······]
```

Три одинаковых поля, а размер разный. Точки — пустые байты. Они ничего не хранят, а только сдвигают следующее поле
на правильное место. Такие байты называются **пустыми байтами**, по-английски **padding**.

`Buyurtma` побайтово:

| Байты | Что лежит | Почему |
|---|---|---|
| 0 | `T` (`Tolandi`, `bool`) | первое поле, смещение 0 |
| 1–7 | padding, 7 байт | `Summa` должна начинаться с адреса, кратного 8 |
| 8–15 | `S` (`Summa`, `int64`) | смещение 8 |
| 16 | `Y` (`Yetkazildi`, `bool`) | смещение 16 |
| 17–23 | padding, 7 байт | общий размер должен быть кратен 8 (причина — в следующем разделе) |

`Ixcham` побайтово:

| Байты | Что лежит | Почему |
|---|---|---|
| 0–7 | `S` (`Summa`, `int64`) | первое поле, смещение 0, кратно 8 |
| 8 | `T` (`Tolandi`) | выравнивание `bool` равно 1: подходит любой адрес |
| 9 | `Y` (`Yetkazildi`) | смещение 9 |
| 10–15 | padding, 6 байт | 10 округляем до кратного 8: 16 |

В компактном варианте `int64` стоит в начале, оба `bool` идут за ним. Пустое место остаётся только в конце,
6 байт.

## Зачем нужно пустое место: правило выравнивания

Процессор читает память не по одному байту, а **кусками**: словами по 4 или 8 байт (а в кэш — ещё более крупными
кусками). Если 8-байтовое число лежит по адресу, кратному 8, оно целиком помещается в один кусок, и хватает одного
чтения. Если оно начинается с байта 5, оно делится на два куска: процессору придётся прочитать оба и собрать
число, а некоторые процессоры вообще не смогут его прочитать.

В курсе Университета Карнеги — Меллона (CMU) правило записано так:

- примитивное значение размером K байт должно лежать по адресу, кратному K: 8-байтовое — по адресу, кратному 8;
- 4-байтовое — по адресу, кратному 4.

Тогда одно значение не пересекает границу двух кусков. Такое размещение называется **выравниванием**,
по-английски **alignment**. На слайде: *"Required on some machines; advised on IA32"* — «на некоторых машинах
обязательно; на IA32 (32-битных процессорах Intel) рекомендуется». Процессоры Intel умеют читать и невыровненные
значения. Но сама Intel рекомендует выравнивание ради производительности (учебник CS:APP, §3.9.3).

Официальные правила Go (spec) дают гарантию для структур: выравнивание структуры равно **наибольшему из
выравниваний её полей**. Для `Buyurtma` это `max(1, 8, 1) = 8`. А компилятор округляет размер структуры до числа,
кратного этому значению. Поэтому в конце `Buyurtma` есть ещё 7 байт.

Зачем нужны байты в конце? Вспомните массив структур ([GO-1.08](/lab/youtube/go/go-1-08/ru)): элементы лежат друг за другом.
Если бы `Buyurtma` занимала не 24, а 17 байт:

| Элемент | Начало (24 байта) | `Summa` (24 байта) | Начало (если 17) | `Summa` (если 17) |
|---|---|---|---|---|
| `[0]` | 0 | 8 ✓ | 0 | 8 ✓ |
| `[1]` | 24 | 32 ✓ | 17 | 25 ✗ |
| `[2]` | 48 | 56 ✓ | 34 | 42 ✗ |

В 17-байтовом варианте `int64` следующего элемента попал бы на адрес, не кратный 8. Padding в конце держит каждый
элемент массива на правильном месте.

Одна ловушка: не «выравнивание самого большого поля», а «наибольшее из выравниваний полей». Даже поле в 16 байт
может иметь выравнивание 1. Проверим это в «Частых ошибках».

## Пауза: bool, int32, bool

Теперь посчитайте пример сами. `int32` — целое число на 4 байта, его выравнивание 4.

```go
type Savol struct {
	A bool
	B int32
	C bool
}
```

Сколько байт займёт эта структура? Как её уменьшить? Нарисуйте байты на бумаге.

<details>
<summary>Ответ</summary>

**12 байт.** `A` в байте 0. `B` (`int32`) начинается с адреса, кратного 4, поэтому после `A` остаются 3 пустых
байта: `B` в байтах 4–7. `C` в байте 8. Итого 9, но выравнивание структуры 4, и размер должен быть кратен 4: в
конец добавляются ещё 3 байта, **12**.

Если поставить `int32` в начало: 4 + 1 + 1 = 6, ближайшее кратное 4 — **8**. Структура сокращается до 8 байт.

Если у вас получилось 6, вы забыли про padding. Если 9 — забыли про округление в конце.

</details>

Ответ проверяет `savol/main.go`. Он почти совпадает с `xarita/main.go`:

```go filename="savol/main.go" showLineNumbers
// savol: pauzadagi savolning javobi. bool, int32, bool: necha bayt?
package main

import (
	"fmt"
	"strings"
	"unsafe"
)

type Savol struct {
	A bool
	B int32
	C bool
}

type Javob struct {
	B int32
	A bool
	C bool
}

type maydon struct {
	harf           string
	offset, olcham uintptr
}

func chiz(nom string, jami, align uintptr, mm ...maydon) {
	b := []string{}
	for range jami {
		b = append(b, "·")
	}
	for _, m := range mm {
		for i := m.offset; i < m.offset+m.olcham; i++ {
			b[i] = m.harf
		}
	}
	fmt.Printf("%-6s %2d bayt, align %d  [%s]\n", nom, jami, align, strings.Join(b, ""))
}

func main() {
	var x Savol
	chiz("Savol", unsafe.Sizeof(x), unsafe.Alignof(x),
		maydon{"A", unsafe.Offsetof(x.A), unsafe.Sizeof(x.A)},
		maydon{"B", unsafe.Offsetof(x.B), unsafe.Sizeof(x.B)},
		maydon{"C", unsafe.Offsetof(x.C), unsafe.Sizeof(x.C)})
	var y Javob
	chiz("Javob", unsafe.Sizeof(y), unsafe.Alignof(y),
		maydon{"B", unsafe.Offsetof(y.B), unsafe.Sizeof(y.B)},
		maydon{"A", unsafe.Offsetof(y.A), unsafe.Sizeof(y.A)},
		maydon{"C", unsafe.Offsetof(y.C), unsafe.Sizeof(y.C)})
}
```

Отличаются только типы: `Savol` («вопрос»: `A`, `B`, `C`) и переставленный `Javob` («ответ»: `B`, `A`, `C`). В
строке 37 имена короче, поэтому `%-6s`. Функция `chiz` — та же, что в `xarita/`.

## Когда это важно: миллион заказов

8 байт кажутся мелочью. Создадим миллион заказов. Вот `million/main.go`:

```go filename="million/main.go" showLineNumbers
// million: bir million buyurtma xotirada qancha joy oladi?
package main

import (
	"fmt"
	"runtime"
)

type Buyurtma struct {
	Tolandi    bool
	Summa      int64
	Yetkazildi bool
}

type Ixcham struct {
	Summa      int64
	Tolandi    bool
	Yetkazildi bool
}

const n = 1_000_000

// ajratildi: f ishlaganda heap'da necha bayt ajratildi.
func ajratildi(f func()) uint64 {
	var a, b runtime.MemStats
	runtime.ReadMemStats(&a)
	f()
	runtime.ReadMemStats(&b)
	return b.TotalAlloc - a.TotalAlloc
}

var (
	s1 []Buyurtma
	s2 []Ixcham
)

func main() {
	mb := func(b uint64) float64 { return float64(b) / 1e6 }
	fmt.Printf("[]Buyurtma: %.1f MB\n", mb(ajratildi(func() { s1 = make([]Buyurtma, n) })))
	fmt.Printf("[]Ixcham:   %.1f MB\n", mb(ajratildi(func() { s2 = make([]Ixcham, n) })))
}
```

| Строка | Код | Что делает |
|---|---|---|
| 21 | `const n = 1_000_000` | константа: миллион |
| 24 | `func ajratildi(f func()) uint64 {` | функция `ajratildi` («выделено») принимает другую функцию (`f`) и возвращает, сколько памяти было выделено, пока `f` работала. `uint64` — беззнаковое целое на 8 байт |
| 25 | `var a, b runtime.MemStats` | `runtime.MemStats` — отчёт runtime о памяти (это структура!). Два отчёта: до и после |
| 26, 28 | `runtime.ReadMemStats(&a)` | записывает отчёт в `a`. `&a` — адрес `a`: чтобы функция записала результат именно в эту ячейку |
| 27 | `f()` | выполняет измеряемую работу |
| 29 | `return b.TotalAlloc - a.TotalAlloc` | `TotalAlloc` — байты, выделенные в куче с начала программы. Разность — то, что выделила `f` |
| 32–35 | `var ( s1 []Buyurtma; s2 []Ixcham )` | два слайса вне функции: они живут до конца программы |
| 38 | `mb := func(b uint64) float64 { return float64(b) / 1e6 }` | анонимная функция: переводит байты в мегабайты. `1e6` — 1 000 000 (10⁶) |
| 39–40 | `make([]Buyurtma, n)` … | создаёт слайс на миллион элементов и выводит выделенную память с `%.1f` (один знак после запятой) |

**Куча** (heap) — общая память, которая живёт всё время работы программы ([GO-1.08](/lab/youtube/go/go-1-08/ru)); такой
большой слайс попадает туда.

Предскажите: **A)** оба по 10 MB · **B)** 24 MB и 16 MB · **C)** оба по 24 MB

<details>
<summary>Ответ</summary>

**B.** Элементы слайса лежат в массиве друг за другом, и каждый занимает место вместе со своим padding:
24 × 1 000 000 = 24 000 000 байт, 16 × 1 000 000 = 16 000 000 байт. «A» — подсчёт без padding. Если вы выбрали «C»,
вы забыли, что `Ixcham` занимает 16 байт.

</details>

```console
$ go run ./million
[]Buyurtma: 24.0 MB
[]Ixcham:   16.0 MB
```

Первый слайс занял 24 мегабайта, компактный — 16 мегабайт. Данные одинаковые, а 8 мегабайт — это только padding.

Память сэкономили. А скорость? Посчитаем сумму оплаченных заказов. Вот `tezlik/main.go`:

```go filename="tezlik/main.go" showLineNumbers
// tezlik: n ta buyurtmaning toʻlangan summasi (standart: bir million). Ish bir xil,
// faqat xotiradan oʻqiladigan baytlar soni har xil.
// Ikkala variant navbatma-navbat 100 marta oʻlchanadi va eng yaxshi
// natija olinadi: kompyuterda boshqa ish ketayotgan boʻlsa ham shovqin kam.
package main

import (
	"fmt"
	"os"
	"strconv"
	"time"
)

type Buyurtma struct {
	Tolandi    bool
	Summa      int64
	Yetkazildi bool
}

type Ixcham struct {
	Summa      int64
	Tolandi    bool
	Yetkazildi bool
}

var natija int64 // kompilyator hisobni oʻchirib tashlamasin

func jami1(s []Buyurtma) (j int64) {
	for i := range s {
		if s[i].Tolandi {
			j += s[i].Summa
		}
	}
	return j
}

func jami2(s []Ixcham) (j int64) {
	for i := range s {
		if s[i].Tolandi {
			j += s[i].Summa
		}
	}
	return j
}

// vaqt: f ni bir marta ishlatib, ketgan vaqtni qaytaradi.
func vaqt(f func()) time.Duration {
	t := time.Now()
	f()
	return time.Since(t)
}

func main() {
	n := 1_000_000 // go run ./tezlik 100000 — boshqa oʻlcham
	if len(os.Args) > 1 {
		n, _ = strconv.Atoi(os.Args[1])
	}
	s1 := make([]Buyurtma, n)
	s2 := make([]Ixcham, n)
	for i := range n {
		s1[i] = Buyurtma{Tolandi: i%2 == 0, Summa: int64(i)}
		s2[i] = Ixcham{Tolandi: i%2 == 0, Summa: int64(i)}
	}
	eng1, eng2 := time.Hour, time.Hour
	for range 100 {
		eng1 = min(eng1, vaqt(func() { natija += jami1(s1) }))
		eng2 = min(eng2, vaqt(func() { natija += jami2(s2) }))
	}
	fmt.Printf("n = %d\n", n)
	fmt.Printf("Buyurtma: %.1f µs\n", eng1.Seconds()*1e6)
	fmt.Printf("Ixcham:   %.1f µs\n", eng2.Seconds()*1e6)
	fmt.Printf("Ixcham / Buyurtma: %.2f\n", eng2.Seconds()/eng1.Seconds())
}
```

| Строка | Код | Что делает |
|---|---|---|
| 26 | `var natija int64` | сюда прибавляем результат: иначе компилятор может удалить неиспользуемое вычисление ([GO-1.07](/lab/youtube/go/go-1-07/ru)) |
| 28–35 | `func jami1(s []Buyurtma) (j int64) {` | `jami1` («итого»): складывает `Summa` оплаченных (`Tolandi` = `true`) заказов. `(j int64)` — именованный результат, вначале 0; `return j` его возвращает |
| 37–44 | `func jami2(s []Ixcham) …` | ровно та же работа для слайса `Ixcham` |
| 47–51 | `func vaqt(f func()) time.Duration {` | `vaqt` («время»): `time.Now()` берёт текущее время, выполняет `f()`, `time.Since(t)` возвращает прошедшее с тех пор время |
| 54–57 | `n := 1_000_000` … `strconv.Atoi(os.Args[1])` | размер по умолчанию — миллион. Если после команды написать число (`go run ./tezlik 100000`), `os.Args[1]` — эта строка, `strconv.Atoi` превращает её в число |
| 58–63 | `make(…)`, `for i := range n { … }` | заполняет оба слайса одинаковыми данными: каждый второй заказ оплачен (`i%2 == 0`), сумма `i` |
| 64 | `eng1, eng2 := time.Hour, time.Hour` | «лучшее время», вначале намеренно очень большое: час |
| 65–68 | `for range 100 { … min(…) … }` | измеряет оба варианта поочерёдно 100 раз. `min` возвращает меньшее из двух значений: остаётся самый быстрый результат |
| 69–72 | `fmt.Printf(…)` | `µs` — микросекунда (миллионная доля секунды). Последняя строка — отношение, с `%.2f` (два знака после запятой) |

Поочерёдные замеры и выбор лучшего уменьшают шум, даже если на компьютере идёт другая работа. Работа в обоих
вариантах одинаковая.

Предскажите: каким будет отношение в последней строке? **A)** около 1: работа ведь одна и та же · **B)** заметно
меньше 1: компактный быстрее · **C)** около 0,33: втрое быстрее

<details>
<summary>Ответ</summary>

**B.** На нашем компьютере отношение каждый раз было в диапазоне 0,72–0,85: компактный вариант занял примерно на
пятую часть меньше времени. Если вы выбрали «A», вы думали, что время уходит только на вычисления: здесь основная
работа — чтение из памяти. Не «C»: читается на треть меньше байтов, но время не строго пропорционально байтам.

</details>

```console
$ go run ./tezlik
n = 1000000
Buyurtma: 1144.0 µs
Ixcham:   917.4 µs
Ixcham / Buyurtma: 0.80
```

Время каждый раз немного меняется, у вас получится иначе. В видео было 1426,5 и 1162,7 µs, отношение 0,82.

Откуда разница? Внутри процессора есть **кэш**: намного меньше основной памяти, но очень быстрый. На этом компьютере
его самый большой уровень (L3) — 12 MiB (12 × 1 048 576 байт). Ни 24 MB, ни 16 MB в него не помещаются. Поэтому
процессор вынужден читать данные из основной памяти, и работа упирается в это чтение. В компактном слайсе читается
на треть меньше байтов.

## Когда это не важно: сто тысяч заказов

Теперь тот же расчёт, но со ста тысячами заказов. Эти данные (2,4 и 1,6 MB) помещаются в кэш.

Предскажите: будет ли компактный вариант снова примерно на пятую часть быстрее?

свободном компьютере и 0,89–1,08 под нагрузкой. Для данных, которые помещаются в кэш, количество байтов не решает.

</details>

```console
Ixcham / Buyurtma: 1.14
```

На этот раз компактный вариант оказался медленнее (в видео тоже 1,14: 65,8 и 74,7 µs). Почему именно так, точно
сказать не можем. Вероятная причина из README курса: компилятор генерирует разный код для шага в 24 и в 16 байт, а
для данных в кэше это важнее количества байтов. У этого процессора есть производительные и энергоэффективные ядра, и
результат зависит ещё и от того, на каком ядре шла программа. Значит, экономия байтов не всегда даёт скорость.

## На 32-битной системе: GOARCH=386

Есть ещё одна тонкость: эти числа зависят от архитектуры (типа процессора) и правил компилятора. До сих пор всё
измерялось на 64-битном компьютере (`amd64`). На 32-битной системе процессор за раз работает с 4-байтовым числом.

Если написать перед командой `GOARCH=386`, Go только для этой команды соберёт программу для 32-битных процессоров
Intel (`386`). 64-битный Linux обычно может сразу запустить такую программу (если включён запуск 32-битных
программ).

Предскажите: сколько байт займёт `Buyurtma` при `GOARCH=386`? **A)** опять 24 · **B)** 16 · **C)** 10

<details>
<summary>Ответ</summary>

**B: 16.** На `386` Go считает достаточным для `int64` адрес, кратный 4: его выравнивание 4. Теперь после `T`
остаются 3 пустых байта, `S` в байтах 4–11, `Y` в байте 12, в конце 3 байта: 16. Если вы выбрали «A», вы думали,
что выравнивание везде одинаковое. Не «C»: padding всё равно есть, просто меньше.

</details>

```console
$ GOARCH=386 go run ./xarita
Buyurtma  16 bayt, align 4  [T···SSSSSSSSY···]
Ixcham    12 bayt, align 4  [SSSSSSSSTY··]
```

Первая структура теперь 16 байт, компактная — 12 байт. Тот же код, другая архитектура, другой размер.

| | `amd64` (64 бита) | `386` (32 бита) |
|---|---|---|
| выравнивание `int64` | 8 | 4 |
| `Buyurtma` | 24 байта | 16 байт |
| `Ixcham` | 16 байт | 12 байт |

## Когда выравнивание роняет программу: атомарная операция

Эта разница может и уронить программу. Сначала новое понятие. **Атомарная операция** — операция, которую несколько
горутин могут безопасно выполнять одновременно: никто не может прервать её на середине. Горутины и атомарные
операции разберём в следующих уроках ([GO-1.21](/lab/youtube/go#go-1-21)). Сейчас достаточно одного правила: для атомарного
увеличения 64-битного числа в Go есть пакет `sync/atomic`.

Вот `atom/main.go`:

```go filename="atom/main.go" showLineNumbers
// atom: 32-bitli tizimda int64 maydon 8 ga karrali manzilda turmasligi mumkin.
// GOARCH=386 go run ./atom — ataylab xato (panic).
package main

import (
	"fmt"
	"sync/atomic"
	"unsafe"
)

type Hisoblagich struct {
	Yoniq bool
	Soni  int64 // bir nechta goroutine atomik oshiradi
}

func main() {
	h := &Hisoblagich{}
	fmt.Println("Soni offset:", unsafe.Offsetof(h.Soni))
	atomic.AddInt64(&h.Soni, 1)
	fmt.Println("Soni:", h.Soni)
}
```

| Строка | Код | Что делает |
|---|---|---|
| 11–14 | `type Hisoblagich struct { Yoniq bool; Soni int64 }` | `Hisoblagich` («счётчик»): сначала `Yoniq` («включён», `bool`), потом `Soni` («количество», `int64`) |
| 17 | `h := &Hisoblagich{}` | создаёт структуру и записывает её адрес в `h` (`&`). Через адрес тоже можно писать `h.Soni`; это разберём в [GO-1.11](/lab/youtube/go/go-1-11/ru) |
| 18 | `unsafe.Offsetof(h.Soni)` | на сколько байт `Soni` отстоит от начала структуры |
| 19 | `atomic.AddInt64(&h.Soni, 1)` | идёт по адресу `Soni` и атомарно прибавляет к нему 1 |
| 20 | `fmt.Println("Soni:", h.Soni)` | выводит результат |

На 64-битном компьютере эта программа выводит `Soni offset: 8` и `Soni: 1`. А на 32-битном? `2>&1` в команде
объединяет вывод ошибок с обычным выводом, а `| head -2` показывает только первые две строки (остальное — длинная
техническая информация).

```console
$ GOARCH=386 go run ./atom 2>&1 | head -2
Soni offset: 4
panic: unaligned 64-bit atomic operation
```

В 32-битной программе `Soni` отстоит от начала структуры на 4 байта. *unaligned 64-bit atomic operation* —
«невыровненная 64-битная атомарная операция». Это не ошибка процессора: runtime Go сам проверяет адрес и, если он
не кратен 8, вызывает panic. В разделе «Bugs» документации `sync/atomic` написано: *"On ARM, 386, and 32-bit MIPS,
it is the caller's responsibility to arrange for 64-bit alignment of 64-bit words accessed atomically"* — «на ARM,
386 и 32-битных MIPS выравнивание по 64 битам для 64-битных слов, к которым обращаются атомарно, — обязанность
вызывающего (то есть программиста)».

В Go 1.19 добавили новые типы. Один из них — `atomic.Int64`: он выравнивается по 8 байтам на любой системе. Вот
`atomfix/main.go`:

```go filename="atomfix/main.go" showLineNumbers
// atomfix: atomic.Int64 (Go 1.19+) har qanday tizimda 8 baytga tekislanadi.
package main

import (
	"fmt"
	"sync/atomic"
	"unsafe"
)

type Hisoblagich struct {
	Yoniq bool
	Soni  atomic.Int64
}

func main() {
	h := &Hisoblagich{}
	fmt.Println("Soni offset:", unsafe.Offsetof(h.Soni))
	h.Soni.Add(1)
	fmt.Println("Soni:", h.Soni.Load())
}
```

- **Строка 12:** `Soni atomic.Int64` — не обычный `int64`, а специальный тип пакета `sync/atomic`.
- **Строка 18:** `h.Soni.Add(1)` — атомарно прибавляет 1. `Add` — функция, привязанная к этому типу (метод).
- **Строка 19:** `h.Soni.Load()` — атомарно читает значение.

Предскажите: каким будет `Soni offset` при `GOARCH=386`? **A)** 4 · **B)** 8 · **C)** 1

<details>
<summary>Ответ</summary>

**B: 8.** Go 1.19 release notes: *"Int64 and Uint64 are automatically aligned to 64-bit boundaries in structs and
allocated data, even on 32-bit systems"* — «`Int64` и `Uint64` автоматически выравниваются по 64 битам в
структурах и выделенных данных, даже на 32-битных системах». Компилятор поставил после `Yoniq` 7 байт padding.
«A» — смещение обычного `int64` на 32 битах.

</details>

```console
$ GOARCH=386 go run ./atomfix
Soni offset: 8
Soni: 1
```

## Реальный случай: GitLab, 2022

Так было и в реальном проекте. В декабре 2022 года часть пользователей, обновивших свой GitLab до версии 15.7.0,
столкнулась с проблемой. Они запускали его на компьютерах Raspberry Pi с 32-битной Raspberry Pi OS. Их сервис
Gitaly падал именно с этой panic: `panic: unaligned 64-bit atomic operation`. Первым советом было откатиться на
версию 15.6.3.

| Что произошло | Подробности |
|---|---|
| Причина | в структуру `ObjectHash` добавили новое поле `ProtoFormat`: она выросла с 64 до 72 байт. Счётчик `int64` в структуре, которая её содержит, сдвинулся и попал на адрес, не кратный 8 |
| Первая мысль | поставить счётчик в начало структуры. Но автор исправления сам написал: *"Moving `outstandingRequests` first in the struct isn't enough"* — «поставить его первым в структуре недостаточно» |
| Исправление | счётчики вынесли в отдельную структуру и добавили тест, проверяющий их выравнивание (MR !5223); второе место исправили в MR !5226 |
| `atomic.Int64` | предложение перейти на него (gitaly#4702) по состоянию на 2026-11-25 всё ещё открыто |

Почему не хватило поставить счётчик в начало? Документация `sync/atomic` гарантирует выравнивание только для
**первого** слова выделенной структуры, массива или слайса, а также глобальной или локальной переменной. В массиве
структур гарантирован только первый элемент. Вспомните результат для `386` выше: `Ixcham` (`int64` в начале) — 12
байт.

| Элемент массива | Начало | `Summa` кратна 8? |
|---|---|---|
| `[0]` | 0 | ✓ |
| `[1]` | 12 | ✗ |
| `[2]` | 24 | ✓ |
| `[3]` | 36 | ✗ |

С другой стороны, случай возвращает нас к теме урока: проблема началась с того, что добавили одно поле, и сдвинулось
другое.

## Не считайте байты вручную: fieldalignment

Считать байты каждый раз вручную не нужно. У команды Go есть анализатор `fieldalignment` (средство статического
анализа, которое проверяет код без запуска, как линтер). Сначала установим его:

```console
$ go install golang.org/x/tools/go/analysis/passes/fieldalignment/cmd/fieldalignment@v0.53.0
```

`go install` ничего не вывел: установка прошла успешно. Программа попадает в папку `$(go env GOPATH)/bin/` (как
`staticcheck` в [GO-1.05](/lab/youtube/go/go-1-05/ru)). Мы указали версию `v0.53.0`; в README курса стоит `@latest`, и
2026-11-25 это тоже была `v0.53.0`.

Теперь запустим его на нашей первой программе. `2>&1 | sed "s|$PWD/||"` в конце команды только укорачивает длинный
путь к папке в сообщении.

```console
$ $(go env GOPATH)/bin/fieldalignment ./olcham 2>&1 | sed "s|$PWD/||"
olcham/main.go:10:15: Buyurtma has size 24 but the optimal size is 16 leading to a waste of 8 bytes (33%)
```

`olcham/main.go`, строка 10, символ 15 (слово `struct`): *Buyurtma has size 24 but the optimal size is 16 leading
to a waste of 8 bytes (33%)* — «размер `Buyurtma` — 24, а оптимальный — 16: 8 байт (33 %) впустую». Про `Ixcham`
он ничего не сказал: она уже максимально компактна.

Но в документации есть и предупреждение: *"the diagnostics produced by fieldanalyzer very rarely indicate a
significant problem, so the analyzer is not included in typical suites such as vet or gopls"* — «сообщения этого
анализатора очень редко указывают на серьёзную проблему, поэтому он не включён в обычные наборы вроде `go vet` или
`gopls`».

Флаг `-fix` сам переставляет поля. Мы попробовали его на копии `olcham/main.go` (этого опыта нет в папке курса:
мы скопировали файл в отдельную папку с собственным `go.mod` со строкой `go 1.26`):

```console
$ $(go env GOPATH)/bin/fieldalignment -fix .
```

Он ничего не вывел. `sed -n 10,14p main.go` выводит строки 10–14 файла:

```console
$ sed -n 10,14p main.go
type Buyurtma struct {
	Summa      int64
	Tolandi    bool
	Yetkazildi bool
}
```

Порядок правильный, но комментарии рядом с полями (`// toʻlandimi?`, `// tiyinda`, `// yetkazildimi?`) исчезли.
Если пользуетесь `-fix`, обязательно просмотрите файл после него.

## Когда переставлять поля

Так нужно ли переставлять поля в каждой структуре? В большинстве случаев нет.

| Ситуация | Что делать |
|---|---|
| одна структура, разница 8 байт | не важно: оставьте порядок, который легко читать |
| структура, которая хранится в памяти миллионами копий (большие слайсы, записи кэша) | измерьте и при необходимости переставьте |
| сначала | пишите в порядке, который легко читать |
| потом | измерьте и меняйте порядок, только если нужно |

Дэйв Чейни в статье «Padding is hard» 2015 года пишет то же самое: *"Do Go programmers need to care about this
minutiae ? Probably not."* — «Нужно ли Go-программистам заботиться об этих мелочах? Скорее всего, нет».

Есть ещё одно исключение. Процессор работает с кэшем не побайтово, а 64-байтовыми кусками, которые называются
**кэш-линиями** (cache line) (на этом компьютере — 64). Компактный порядок иногда кладёт переменные двух горутин в
одну кэш-линию. Когда одна горутина пишет в свою переменную, копия этой линии на другом ядре устаревает. Это
называется **false sharing** («ложное разделение»), и оно замедляет обе горутины. Документация `fieldalignment`
тоже предупреждает: *"the most compact order is not always the most efficient"* — «самый компактный порядок не
всегда самый эффективный». Это вы измерите в задании уровня Guru.

## Глубже (необязательно): что обещает spec

Этого раздела нет в видео, он из README курса.

- Официальные правила Go дают лишь минимальные гарантии: размеры числовых типов и выравнивание структуры
  (наибольшее из выравниваний полей). Раскладка полей в порядке исходного кода — текущее поведение компилятора `gc`.
- Spec не обещает порядок полей. Роберт Гриземер из команды Go в
  [golang/go#10014](https://github.com/golang/go/issues/10014): *"Currently, the spec does not specify how
  struct fields are laid out in memory"* — «сейчас spec не определяет, как поля структуры располагаются в памяти».
  Но идею, чтобы компилятор сам переставлял поля существующих структур, отклонили.
- Если нужна такая же раскладка, как в C, с Go 1.23 есть маркер
  [`structs.HostLayout`](https://pkg.go.dev/structs#HostLayout).
- На 32-битном Linux и C выравнивал 8-байтовый `double` (дробное число) по 4 байтам (слайд CMU, IA32). Go при
  `GOARCH=386` размещает `int64` так же.

В папке есть и бенчмарк для `go test`. Вот `million/bench_test.go`:

## Частые ошибки

**1. Думать, что размер структуры = сумма размеров полей.** Главная ловушка урока, мы видели её в разделе «Загадка
из начала»: `bool + int64 + bool` — не 10, а 24 байта. Сообщения об ошибке нет, просто память расходуется зря.
**Исправление:** проверяйте размер через `unsafe.Sizeof` или запускайте `fieldalignment`. Если копий миллионы,
ставьте поля с большим выравниванием в начало.

**2. Думать, что «выравнивание структуры = выравнивание самого большого поля».** Этого примера нет в папке курса,
он запущен отдельно:

```go
package main

import (
	"fmt"
	"unsafe"
)

type Katta struct {
	A [16]byte
	B int32
}

func main() {
	var k Katta
	fmt.Println("Sizeof:", unsafe.Sizeof(k), "Alignof:", unsafe.Alignof(k))
}
```

`[16]byte` — массив из 16 байт, самое большое поле этой структуры.

```console
$ go run engkatta/main.go
Sizeof: 20 Alignof: 4
```

Самое большое поле — 16 байт, но выравнивание 4. Выравнивание `[16]byte` равно 1 (он состоит из байтов), у `int32`
— 4. Правило: **наибольшее** из выравниваний полей, `max(1, 4) = 4`. **Исправление:** смотрите на выравнивание
каждого поля, а не на его размер.

**3. Пропустить поле в литерале без ключей.** В литерале без имён полей все поля должны быть записаны по порядку
(в папке курса нет):

```go
package main

import "fmt"

type Mijoz struct {
	Ism    string
	Balans int64
	Shahar string
}

func main() {
	a := Mijoz{"Aziza", 50_000}
	fmt.Println(a)
}
```

```console
$ go run kalitsiz/main.go
# command-line-arguments
kalitsiz/main.go:12:28: too few values in struct literal of type Mijoz
```

Строка 12, символ 28: *too few values in struct literal of type Mijoz* — «слишком мало значений в литерале
структуры типа `Mijoz`». В структуре три поля, а мы написали два. Литерал без ключей ломается так же, когда в
структуру добавляют новое поле. **Исправление:** пишите литерал с ключами: `Mijoz{Ism: "Aziza", Balans: 50_000}`.
Незаписанное `Shahar` получит нулевое значение.

**4. Указать поле, которого нет в структуре.** (В папке курса нет.)

```go
package main

import "fmt"

type Mijoz struct {
	Ism    string
	Balans int64
}

func main() {
	a := Mijoz{Ism: "Aziza", Yosh: 20}
	fmt.Println(a)
}
```

```console
$ go run nomalum/main.go
# command-line-arguments
nomalum/main.go:11:27: unknown field Yosh in struct literal of type Mijoz
```

*unknown field Yosh in struct literal of type Mijoz* — «неизвестное поле `Yosh` в литерале структуры типа `Mijoz`».
Поле `Yosh` («возраст») в `Mijoz` не объявлено. **Исправление:** добавьте поле в тип структуры или исправьте имя.

**5. Считать встраивание наследованием.** Внутри `Mijoz` есть `Manzil`, но `Mijoz` — не `Manzil` (в папке курса
нет):

```go
package main

import "fmt"

type Manzil struct {
	Shahar string
}

type Mijoz struct {
	Ism string
	Manzil
}

func chop(m Manzil) {
	fmt.Println(m.Shahar)
}

func main() {
	a := Mijoz{Ism: "Aziza", Manzil: Manzil{Shahar: "Buxoro"}}
	chop(a)
}
```

```console
$ go run meros/main.go
# command-line-arguments
meros/main.go:20:7: cannot use a (variable of struct type Mijoz) as Manzil value in argument to chop
```

Строка 20, символ 7: *cannot use a (variable of struct type Mijoz) as Manzil value in argument to chop* — «нельзя
использовать `a` (переменную типа `Mijoz`) как значение `Manzil` в аргументе `chop`». Поля поднимаются, а тип не
меняется. **Исправление:** передайте саму вложенную структуру: `chop(a.Manzil)`.

**6. Атомарно увеличивать обычный `int64` на 32-битной системе.** Мы видели это в разделе «Когда выравнивание
роняет программу»: `atomic.AddInt64` для `int64` после `bool` при `GOARCH=386` вызывает panic. На 64-битном
компьютере ошибки не видно, поэтому она остаётся скрытой. **Исправление:** используйте тип `atomic.Int64` (Go 1.19+).

**7. Не проверить файл после `fieldalignment -fix`.** В нашем опыте он удалил комментарии полей (раздел «Не
считайте байты вручную»). **Исправление:** просматривайте изменения после `-fix` или переставляйте поля вручную.

## Проверьте себя

Сначала ответьте сами, потом откройте.

**1.** Почему `Buyurtma` занимает 24 байта, а `Ixcham` 16, хотя поля одинаковые?

<details>
<summary>Ответ</summary>

`int64` должен начинаться с адреса, кратного 8. В `Buyurtma` он стоит после `bool`: между ними 7 байт padding и в
конце ещё 7 байт (чтобы размер был кратен 8). В `Ixcham` `int64` стоит в начале, оба `bool` идут за ним, пустое
место только в конце: 6 байт.

</details>

**2.** Что выведет эта программа на 64-битном компьютере? **A)** `13` · **B)** `16` · **C)** `24`

```go
package main

import (
	"fmt"
	"unsafe"
)

type T struct {
	A int32
	B bool
	C int64
}

func main() {
	fmt.Println(unsafe.Sizeof(T{}))
}
```

<details>
<summary>Ответ</summary>

**B: `16`.** `A` в байтах 0–3, `B` в байте 4, затем 3 байта padding, `C` (`int64`) в байтах 8–15. 16 само кратно
8, padding в конце не нужен. «A» — сумма без padding. Если вы выбрали «C», вы думали, что каждое поле занимает 8
байт. (Этой программы нет в папке курса, она запущена отдельно.)

```console
$ go run savol1/main.go
16
```

</details>

**3.** Что будет, если в составном литерале с ключами не указать некоторые поля?

<details>
<summary>Ответ</summary>

Они получат нулевое значение: число `0`, строка `""`, `bool` `false`. В литерале с ключами порядок полей тоже не
важен.

</details>

**4.** Всегда ли компактная структура ускоряет программу?

<details>
<summary>Ответ</summary>

Нет. На миллионе заказов (не помещается в кэш) компактный вариант оказался примерно на пятую часть быстрее. На ста
тысячах (помещается в кэш) разница намного меньше, а иногда компактный даже медленнее. Сначала измерьте.

</details>

**5.** Какой тип вы выберете на 32-битной системе для 64-битного счётчика, который увеличивают несколько горутин, и
почему?

<details>
<summary>Ответ</summary>

`atomic.Int64`. Он выравнивается по 8 байтам на любой системе (Go 1.19+). Обычный `int64` на `386` может оказаться
по адресу, кратному только 4, а `atomic.AddInt64` по такому адресу вызывает panic.

</details>

**6.** Из [GO-1.07](/lab/youtube/go/go-1-07/ru): как называется функция бенчмарка и как пишется цикл внутри неё?

<details>
<summary>Ответ</summary>

Имя начинается с `Benchmark`, функция принимает `b *testing.B`: `func BenchmarkIxcham(b *testing.B)`. Измеряемая
работа стоит внутри `for b.Loop() { … }`. Имя файла заканчивается на `_test.go`, запуск: `go test -bench .`.
Сегодняшний `million/bench_test.go` устроен именно так.

</details>

🟢 **Лёгкое:** сколько байт занимает `struct { A bool; B int64; C int32; D bool }`? Сначала посчитайте на бумаге,
потом проверьте через `unsafe.Sizeof`.

<details>
<summary>Ответ</summary>

`homework/oson/main.go`. `A` в байте 0, 7 байт padding, `B` 8–15, `C` 16–19, `D` 20. Итого 21, кратное 8 —
**24**. Компактный порядок `B, C, A, D`: 8 + 4 + 1 + 1 = 14 → **16**.


</details>

🟡 **Среднее:** найдите размер и самый компактный порядок для `struct { Faol bool; Ism string; Admin bool; Yosh int32 }`.

<details>
<summary>Ответ</summary>

`homework/orta/main.go`. Внутри `string` две вещи: адрес байтов строки (8 байт) и её длина (8 байт). Всего 16 байт,
выравнивание 8. `Faol` 0, 7 байт padding, `Ism` 8–23, `Admin` 24, 3 байта padding, `Yosh` 28–31 → **32**.
Компактно: `Ism, Yosh, Faol, Admin` = 16 + 4 + 1 + 1 = 22 → **24**. `fieldalignment` говорит то же самое.

```console
Foydalanuvchi:       32
FoydalanuvchiIxcham: 24
```

</details>

🟠 **Сложное:** пустая структура `struct{}` занимает 0 байт. Почему `struct { A int64; B struct{} }` — 16 байт, а
`struct { B struct{}; A int64 }` — 8?

<details>
<summary>Ответ</summary>

`homework/qiyin/main.go`. Адрес последнего поля нулевого размера (`&x.B`) не должен указывать на байт сразу после
структуры, то есть на другой объект. Иначе сборщик мусора мог бы посчитать тот объект тоже «живым». Поэтому
компилятор добавляет к последнему полю нулевого размера 1 байт, а потом округляет до кратного 8: 9 → **16**
(`cmd/compile/internal/types/size.go`, issue 9401). Если такое поле в начале, лишний байт не нужен: **8**.

```console
$ go run ./homework/qiyin
struct{}: 0
Oxirida:  16
Boshida:  8
```

</details>
