## Nimani oʻrganasiz

Ikki endpoint'li Express API'ni Docker image qildik: `node:24-slim` asosida u 235 MB chiqdi. Xuddi shu API Go'da
8.66 MB, va image ichida Node ham, Go ham, hatto shell ham yoʻq. Qanday qilib? Bugun shu API'ni noldan yozamiz va
serverga bitta fayl qilib chiqaramiz.

**Bitta gʻoya:** Go xizmati serverga bitta fayl boʻlib chiqadi. `go build` bizning kod, standart kutubxona va
runtime'ni bitta binary'ga yigʻadi, shuning uchun serverda Node ham, `node_modules` ham, Go ham kerak emas. Lekin
binary bitta OS va bitta CPU uchun yasaladi, va `FROM scratch` image'da ishlashi uchun cgo oʻchiq boʻlishi kerak.

Dars oxirida siz:

- `go mod init` bilan loyiha ochib, `net/http` bilan JSON qaytaradigan API yoza olasiz va har bir qatorini
  Express'dagi oʻxshashi bilan tushuntira olasiz;
- `go run` va `go build` farqini, `go build` yasagan faylda nima borligini ayta olasiz;
- `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build` bilan serverga yoki `FROM scratch` image'ga bitta fayl chiqara olasiz;
- `exec format error` va `exec /api: no such file or directory` xatolarining sababini topib, tuzata olasiz.

Bugungi uchta asosiy yangi tushuncha:

| Tushuncha | Oddiy maʼnosi | JS/TS'dagi oʻxshashi |
|---|---|---|
| `go.mod` (modul) | loyiha fayli: modul nomi va eng kichik Go versiyasi | `package.json` |
| `go run` / `go build` | kompilyatsiya qilib darhol ishga tushirish / kompilyatsiya qilib faylga yozish | `tsx index.ts` / `tsc` |
| static binary, `GOOS`/`GOARCH` | hech narsaga bogʻlanmagan bitta bajariladigan fayl; u bitta OS va bitta CPU uchun yasaladi | serverdagi `node` + `node_modules` |

Ikkita yordamchi tushuncha ham bor: **cgo** (Go'dan C kodini chaqirish; uni `CGO_ENABLED=0` oʻchiradi) va **modul
keshi** bilan `go.sum` (tashqi modullar kodi va ularning xeshlari; pnpm store va `package-lock.json` oʻrnida).

## `go.mod`: `package.json` oʻrnida

Har bir Go loyihasi bitta buyruq bilan boshlanadi. `npm init` oʻrnida `go mod init`. Yangi boʻsh papkada:

```console
$ go mod init api
go: creating new go.mod: module api
$ cat go.mod
module api

go 1.26.8
```

Nomlarga eʼtibor bering, ular npm'dagidan boshqacha:

| npm | Go | Nima |
|---|---|---|
| package (`package.json`'li loyiha) | **modul** (module, `go.mod`'li loyiha) | versiya bilan tarqatiladigan birlik |
| modul (bitta `.js` fayl) | **paket** (package, bitta papka) | bitta papkadagi `.go` fayllar; `import` paketni ulaydi |

`go.mod`da ikki qator bor:

- `module api` — modul nomi. Loyiha ichidagi paketlar shu nom bilan import qilinadi (`api/...`). Kutubxona boʻlsa,
  odatda repozitoriy yoʻli yoziladi, masalan `github.com/siz/api`.
- `go 1.26.8` — bu modul talab qiladigan eng kichik Go versiyasi. `package.json`dagi `"engines"`ga oʻxshaydi, lekin
  ikki farqi bor. Birinchisi: `engines` faqat maslahat, Go esa bu qatorni majburiy qiladi. Eskiroq Go build qilmaydi
  yoki `GOTOOLCHAIN=auto` bilan kerakli versiyani yuklab oladi. Ikkinchisi: bu qator til va standart kutubxonaning
  qaysi xulqi ishlashini ham tanlaydi. Bu haqda batafsil
  [GO-1.16 · `go.mod`dagi bitta qator dasturingiz xulqini oʻzgartiradi](/lab/youtube/go/go-1-16) darsida.

`go mod init` kompyuterdagi Go versiyasini yozadi. Kurs README'si aytganidek, eskiroq 1.26.x bilan ishlatish uchun
uni `go 1.26.0` qilib qoʻyish mumkin.

Endi bogʻliqliklar. Express loyihasida birinchi ish `npm install`:

```console
$ npm install express

added 65 packages, and audited 66 packages in 5s

31 packages are looking for funding
  run `npm fund` for details

found 0 vulnerabilities
```

Bitta Express uchun `node_modules`ga 65 ta paket tushdi. Go'da HTTP server ham, JSON ham **standart kutubxona**da,
yaʼni Go bilan birga keladi, Node'dagi `node:http` kabi. Shuning uchun `go.mod`da `require` qatori, yaʼni bogʻliqlik
qatori, umuman yoʻq. Yuqoridagi `cat go.mod` shuni koʻrsatadi.

Tashqi modul kerak boʻlsa (masalan, Postgres drayveri), `go get` uni qoʻshadi:

| Nima | npm | Go |
|---|---|---|
| bogʻliqlik roʻyxati va versiyasi | `package.json` (`^5.3.0` — diapazon) | `go.mod`dagi `require` (aniq versiya) |
| har bir faylning xeshi | `package-lock.json`dagi `integrity` | `go.sum` (faqat xeshlar) |
| kodi qayerda turadi | loyiha ichida, `node_modules/` | loyihadan tashqarida, umumiy **modul keshi**da (pnpm store kabi; joyi: `go env GOMODCACHE`) |

## 20 qatorlik API

Mana butun API. Ikki endpoint: `GET /health` va `GET /users/{id}`.

```go filename="main.go" showLineNumbers
package main

import (
	"encoding/json"
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
	})
	http.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(map[string]string{"id": r.PathValue("id")})
	})
	log.Println("listening on :3000")
	log.Fatal(http.ListenAndServe(":3000", nil))
}
```

Xuddi shu API Express 5 bilan (kurs papkasida `node/index.js`):

```js filename="node/index.js" showLineNumbers
// Xuddi shu API Express 5 bilan (taqqoslash uchun): node index.js
const express = require("express");
const app = express();

app.get("/health", (req, res) => {
  res.json({ status: "ok" });
});
app.get("/users/:id", (req, res) => {
  res.json({ id: req.params.id });
});

app.listen(3000, () => console.log("listening on :3000"));
```

Go kodini qatorma-qator oʻqiymiz:

| Qator | Kod | Nima qiladi | Express'da |
|---|---|---|---|
| 1 | `package main` | bu fayl `main` paketiga tegishli: ishga tushadigan dastur, kutubxona emas | `node index.js` beriladigan fayl |
| 3–7 | `import ( … )` | standart kutubxonadan uchta paket: JSON, log va HTTP server | `require("express")`, lekin `npm install`siz |
| 9 | `func main() {` | dasturning kirish nuqtasi: Go dasturni shu funksiyadan boshlaydi | faylning yuqori darajadagi kodi |
| 10 | `http.HandleFunc("GET /health", …)` | yoʻl uchun handler roʻyxatdan oʻtkazadi. Metod pattern ichida yoziladi: `GET`, boʻsh joy, yoʻl (Go 1.22 dan) | `app.get("/health", …)` |
| 10 | `func(w http.ResponseWriter, r *http.Request) { … }` | joyida yozilgan **nomsiz funksiya** (function literal). Avval javob yozuvchi `w`, keyin soʻrov `r` | `(req, res) => { … }`, tartib teskari |
| 10 | `w http.ResponseWriter` | tur nomdan keyin yoziladi | TS'dagi `w: ResponseWriter` |
| 10 | `*http.Request` | `*` — pointer. Uni [GO-X.04](/lab/youtube/go/go-x-04) darsida ochamiz; hozircha «soʻrov» deb oʻqing | — |
| 11 | `w.Header().Set("Content-Type", "application/json")` | javob header'ini oʻzimiz qoʻyamiz | `res.json` buni oʻzi qiladi |
| 12 | `json.NewEncoder(w).Encode(…)` | qiymatni JSON qilib toʻgʻridan-toʻgʻri `w`ga yozadi va oxiriga `\n` qoʻshadi | `res.json(…)` |
| 12 | `map[string]string{"status": "ok"}` | kaliti ham, qiymati ham `string` boʻlgan map, joyida toʻldirilgan | `Record<string, string>`, `{ status: "ok" }` |
| 13 | `})` | funksiya va `HandleFunc` chaqiruvini yopadi | `});` |
| 14 | `"GET /users/{id}"` | jingalak qavsdagi `{id}` — yoʻlning oʻzgaruvchan qismi | `"/users/:id"` |
| 16 | `r.PathValue("id")` | yoʻldagi `{id}` qiymatini beradi | `req.params.id` |
| 18 | `log.Println("listening on :3000")` | sana va vaqt bilan log yozadi | `console.log(…)` |
| 19 | `http.ListenAndServe(":3000", nil)` | 3000-portda serverni ishga tushiradi. Faqat xato boʻlsa qaytadi, masalan port band boʻlsa | `app.listen(3000)` |
| 19 | `nil` | handler bermadik degani, JS'dagi `null` kabi. Shunda server standart router'ni (`http.DefaultServeMux`) oladi: yuqoridagi `HandleFunc`lar aynan unga yozilgan | `app` obyektining oʻzi |
| 19 | `log.Fatal(…)` | `ListenAndServe` qaytargan xatoni yozadi va dasturni `exit status 1` bilan toʻxtatadi | `process.exit(1)` |

Yana ikkita Go qoidasi shu kodda koʻrinadi:

- `HandleFunc`, `PathValue`, `NewEncoder`, `ListenAndServe` katta harf bilan boshlanadi. Go'da katta harf **export**
  degani: bu nom paketdan tashqarida koʻrinadi. Kichik harfli nom faqat paket ichida. ES modullardagi `export` soʻzi
  oʻrnida harfning oʻzi ishlaydi.
- `Encode` xato qiymatini ham qaytaradi, biz uni hozircha eʼtiborsiz qoldirdik. Go'da xatolar qanday tekshirilishi —
  [GO-X.03](/lab/youtube/go/go-x-03) darsida.

Mashina nuqtai nazaridan bitta soʻrovning yoʻli:

| Qadam | Nima boʻladi |
|---|---|
| 1 | `main` ikki pattern'ni `DefaultServeMux`ga yozadi: `GET /health`, `GET /users/{id}` |
| 2 | `ListenAndServe(":3000", nil)` portni ochadi va soʻrov kutadi (dastur shu qatorda «turib qoladi») |
| 3 | `GET /users/42` keladi → router metodni va yoʻlni pattern'lar bilan solishtiradi → ikkinchisi mos, `id` = `"42"` |
| 4 | handler header qoʻyadi va `{"id":"42"}` + `\n` yozadi |

## `go run`: `tsx` kabi

Ishga tushiramiz. `go run .` joriy papkadagi paketni kompilyatsiya qiladi va darhol ishga tushiradi, `tsx index.ts`
kabi. Loyiha papkasida yangi fayl qolmaydi.

```console
$ go run .
2026/11/26 18:09:03 listening on :3000
```

Server ishlab turibdi va terminalni band qiladi. Ikkinchi terminalda soʻraymiz:

```console
$ curl localhost:3000/users/42
{"id":"42"}
```

Endi bashorat. `/health` faqat `GET` uchun yozilgan. Unga `POST` yuborsak, Go nima qaytaradi?

**A)** `404 Not Found` · **B)** `405 Method Not Allowed` · **C)** `200 OK`, chunki handler baribir ishlaydi

<details>
<summary>Javob</summary>

**B: `405 Method Not Allowed`.** Metod pattern'da yozilgani uchun router bu yoʻl borligini, lekin metod mos
emasligini biladi. U `Allow` header'ida ruxsat etilgan metodlarni ham aytadi: `GET, HEAD`. `GET` pattern `HEAD`
soʻrovini ham qabul qiladi (Express ham shunday). A ni tanlagan boʻlsangiz, Express'dagi xulqni kutgansiz: u notoʻgʻri
metodga 404 qaytaradi. C ni tanlagan boʻlsangiz, metodni pattern'ning bir qismi emas deb oʻylagansiz.

</details>

## Ishlatilmagan import: ogohlantirish emas, xato

`xato/` papkasida `/health` handler'i JSON'ni qoʻlda yozadi. `encoding/json` import'i esa qolib ketgan va endi
ishlatilmaydi:

```go filename="xato/main.go" showLineNumbers
package main

import (
	"encoding/json"
	"log"
	"net/http"
)

func main() {
	http.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		w.Write([]byte(`{"status":"ok"}`))
	})
	log.Fatal(http.ListenAndServe(":3000", nil))
}
```

Darsdagi `main.go`dan farqi: faqat `/health` route'i qoldi, 12-qatorda esa `w.Write(…)`. U baytlarni javobga
toʻgʻridan-toʻgʻri yozadi. `` `\{"status":"ok"\}` `` —
teskari tirnoqdagi satr (ichidagi qoʻshtirnoqlar ekranlanmaydi), `[]byte(…)` uni baytlarga aylantiradi.

`go build` nima qiladi?

**A)** build boʻladi, ESLint kabi ogohlantirish chiqadi · **B)** build xato beradi, binary yasalmaydi ·
**C)** `go build` import'ni oʻzi oʻchiradi

<details>
<summary>Javob</summary>

**B.** Go kompilyatorida ogohlantirish (warning) umuman yoʻq, faqat kompilyatsiyani toʻxtatadigan xato bor. A ni
tanlagan boʻlsangiz, TS/ESLint odatini kutgansiz: u yerda ishlatilmagan import odatda faqat ogohlantirish. C ni
tanlagan boʻlsangiz, muharrirni nazarda tutgansiz: buni `go build` emas, muharrirdagi gopls qiladi (pastda).

</details>

`cd xato` — `xato` papkasiga oʻtish:

```console
$ cd xato && go build
# api/xato
./main.go:4:2: "encoding/json" imported and not used
```

Xabarni oʻqiymiz. `# api/xato` — xato `api/xato` paketida. `./main.go:4:2` — fayl, 4-qator, 2-ustun, `tsc`dagi kabi.
*"encoding/json" imported and not used* — «import qilingan, lekin ishlatilmagan». Papkada faqat `main.go` qoldi:
binary yasalmadi.

Go jamoasi buni ataylab shunday qilgan. Go FAQ: kompilyator ogohlantirish bermaydi, faqat kompilyatsiyani
toʻxtatadigan xato beradi, chunki ishlatilmagan import'lar kod bazasi oʻsgan sari build'ni sekinlashtiradi
(«unused imports just slow down compilation»). Kundalik ishda buni deyarli sezmaysiz: muharrirdagi **gopls**,
yaʼni Go'ning tsserver'i, bunday import'ni odatda fayl saqlanganda oʻzi olib tashlaydi.

## `go build`: bitta binary

Endi faylga build qilamiz. `-o api` — chiqadigan fayl nomi, `.` — joriy papkadagi paket:

```console
$ go build -o api .
$ ls -l api
-rwxr-xr-x 1 haywan users 8659683 Nov 26 18:09 api
```

`go build` muvaffaqiyatli boʻlsa hech narsa yozmaydi. Natija — 8 659 683 baytlik `api` fayli, yaʼni 8.66 MB.

`tsc` bilan farq shu: `tsc` JavaScript chiqaradi, uni ishga tushirish uchun baribir `node` kerak. `go build` esa
shu kompyuter uchun mashina kodi chiqaradi. `./api` hech narsasiz ishlaydi. Faylda nima bor:

| `api` ichida | Nima | Node'dagi oʻrni |
|---|---|---|
| `main` paketi | bizning 20 qator | `index.js` |
| `net/http`, `encoding/json` va ular tortgan paketlar | standart kutubxona | `node_modules/` + Node'ning ichki modullari |
| Go **runtime** | garbage collector xotirani tozalaydi, scheduler bir vaqtdagi ishlarni taqsimlaydi | `node` ichidagi V8 va event loop |

Bu **static binary**: tizimdagi boshqa kutubxonalarga bogʻlanmagan bitta fayl. Megabaytlarning qaysi biri nimaga
ketishini [GO-1.01 · Go nega bor? go build ichida nima bor](/lab/youtube/go/go-1-01) darsida oʻlchaymiz.

Lekin mashina kodi bitta operatsion tizim va bitta protsessor uchun yasaladi. Go ularni ikki muhit oʻzgaruvchisidan
oladi: **`GOOS`** (OS: `linux`, `darwin`, `windows`) va **`GOARCH`** (CPU: `amd64`, `arm64`). Berilmasa, siz turgan
kompyuternikini oladi:

```console
$ go env GOOS GOARCH
linux
amd64
$ node -p process.arch
x64
```

Bizda `linux` va `amd64`. Node xuddi shu arxitekturani `x64` deydi.

Serverga nima ketishini solishtiramiz:

| Til | Serverga nima ketadi |
|---|---|
| Node | `node` binary'si (129 491 456 bayt) + `node_modules` (Express: 65 paket) + kod |
| Python | `python3` interpretatori + `venv` + kod |
| PHP | php-fpm + `vendor/` + kod |
| Go | `api` (8 659 683 bayt). Serverda Go oʻrnatilmagan boʻlsa ham ishlaydi |

Node'da ham bitta fayl yasash mumkin, masalan Node SEA (single executable application) bilan. Lekin u sizning
skriptingizni butun `node` binary'sining nusxasiga joylaydi.

Bitta istisno: HTML shablonlar yoki SQL migratsiyalar kabi oddiy fayllar binary'ga oʻzi kirmaydi. Ular uchun
`//go:embed` bor (kurs README'sida nomi bor, keyingi darslarda).

### Bashorat: MacBook'dan VPS'ga

Apple chipli MacBook'da shunday build qildingiz va faylni `scp` bilan oddiy amd64 VPS'ga koʻchirdingiz:

```bash
GOOS=linux go build -o api .
```

VPS'da `./api` nima qiladi?

**A)** ishlaydi · **B)** `exec format error` · **C)** `no such file or directory`

<details>
<summary>Javob</summary>

**B: `exec format error`.** `GOOS` berildi, `GOARCH` esa berilmadi. U MacBook'niki boʻlib qoldi, yaʼni `arm64`.
amd64 protsessor arm64 mashina kodini bajara olmaydi. A ni tanlagan boʻlsangiz, «Linux uchun build qildim, demak
Linux'da ishlaydi» deb oʻylagansiz: OS toʻgʻri, CPU esa yoʻq. C boshqa xato: uni Docker boʻlimida koʻramiz.
Docker'da ham xuddi shunday: Apple chipli Mac'da yigʻilgan image amd64 serverda shu xatoni beradi.

</details>

Bizda amd64 kompyuter, shuning uchun teskarisini koʻrsatamiz: arm64 uchun yasalgan faylni shu yerda ishga
tushiramiz (bash'da):

```console
$ GOOS=linux GOARCH=arm64 go build -o api-arm .
$ ./api-arm
bash: ./api-arm: cannot execute binary file: Exec format error
```

*cannot execute binary file: Exec format error* — «binary faylni bajarib boʻlmaydi: format xato». zsh'da xuddi shu
xato `zsh:1: exec format error: ./api-arm` boʻlib chiqadi. Tuzatish: ikkalasini ham yozing,
`GOOS=linux GOARCH=amd64`. Go boshqa tizim uchun build qilishni (**cross-compile**) shu ikki oʻzgaruvchi bilan qiladi:
qoʻshimcha toolchain kerak emas.

## Docker: `FROM scratch` va 8.66 MB

Docker'da ham xuddi shu gʻoya. `FROM scratch` — boʻm-boʻsh image: unda shell ham, tizim kutubxonalari ham yoʻq. Ichiga
faqat bitta binary tushadi:

```dockerfile filename="Dockerfile" showLineNumbers

COPY api /api
EXPOSE 3000
ENTRYPOINT ["/api"]
```

| Qator | Nima qiladi |
|---|---|
| 1 | boʻsh image'dan boshlaydi |
| 2 | tayyor `api` faylini image'ning ildiziga koʻchiradi |

| 4 | konteyner ishga tushganda `/api`ni bajaradi |

Express image'i uchun biz `node:24-slim` oldik, yaʼni Debian 12 va Node v24.22.3:

## Tuzoq: «no such file or directory», fayl esa joyida

Endi production'da koʻp uchraydigan holat. Binary'ni `golang` image'da yigʻib, `scratch` image'ga qoʻyamiz
(multi-stage build). Kurs papkasidagi `tuzoq/Dockerfile`:

```dockerfile filename="tuzoq/Dockerfile" showLineNumbers
# TUZOQ: golang image'da gcc bor, shuning uchun cgo yoqiladi va net paketi libc'ga bogʻlanadi
FROM golang:1.26.8 AS build
WORKDIR /src
COPY go.mod main.go ./
RUN go build -o /api .

FROM scratch
COPY --from=build /api /api
ENTRYPOINT ["/api"]
```

2–5-qatorlar birinchi bosqich: `golang` image'ida kodni koʻchirib, build qiladi. 7–9-qatorlar: boʻsh image'ga faqat
tayyor `/api`ni oladi. 5-qatorda `CGO_ENABLED` yoʻq.

```console
$ docker build -q -t tuzoq -f tuzoq/Dockerfile .
sha256:cf5f14afa9770685cc7ffceec8c18986d6c8fba70dcd0d495d7be672b1aba41b
$ docker run --rm tuzoq
exec /api: no such file or directory
```

*no such file or directory* — «bunday fayl yoki papka yoʻq». Lekin `/api` image'da bor: `COPY` uni koʻchirdi. Qaysi
fayl yoʻq?

Sabab — **cgo**, yaʼni Go'dan C kodini chaqirish imkoniyati. `golang` image'ida C kompilyatori (gcc) bor, shuning uchun
Go cgo'ni yoqadi. Shunda `net` paketi DNS nomlarini hal qilish uchun tizimning C kutubxonasiga, **libc**ga bogʻlanadi.
Binary endi static emas. Birinchi bosqich image'ida (`--target build`) `ldd` bilan tekshiramiz. `ldd` binary
qaysi kutubxonalarni soʻrashini koʻrsatadi:

```console
$ docker build -q --target build -t tuzoq-build -f tuzoq/Dockerfile .
sha256:61c83141fef877a127f29749e7628accc2d8abbceacac99ad0676395387336b9
$ docker run --rm tuzoq-build ldd /api
	linux-vdso.so.1 (0x000072a3a014f000)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x000072a39ff50000)
	/lib64/ld-linux-x86-64.so.2 (0x000072a3a0151000)
$ docker run --rm tuzoq-build readelf -l /api | grep interpreter
      [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]
```

Binary ikki narsani soʻraydi: `libc.so.6` va `/lib64/ld-linux-x86-64.so.2`. Ikkinchisi — **dinamik yuklovchi**
(dynamic loader). U skriptdagi shebang (`#!/usr/bin/env node`) kabi ishlaydi: kernel avval yuklovchini ishga
tushiradi, yuklovchi esa libc'ni ulab, binary'ni boshlaydi. `readelf -l` buni koʻrsatadi: *Requesting program
interpreter* — «dastur interpretatorini soʻrayapti». `scratch`da yuklovchi yoʻq, shuning uchun kernel «fayl topilmadi»
deydi. Xabar `/api` haqida emas, yuklovchi haqida.

```text
docker run tuzoq
  └─ kernel: /api ni ishga tushir
       └─ /api: «meni /lib64/ld-linux-x86-64.so.2 ishga tushirsin»
            └─ scratch: bu fayl yoʻq → ENOENT → "exec /api: no such file or directory"

docker run tuzoq-ok   (CGO_ENABLED=0)
  └─ kernel: /api ni ishga tushir
       └─ /api: static, hech narsa soʻramaydi → ishlaydi
```

Tuzatish: build qatoriga `CGO_ENABLED=0` qoʻshing. `tuzoq/Dockerfile.ok` faqat 5-qatorda farq qiladi:

```dockerfile filename="tuzoq/Dockerfile.ok" showLineNumbers
# TUZATISH: CGO_ENABLED=0 → net paketi sof Go resolver bilan, binary static
FROM golang:1.26.8 AS build
WORKDIR /src
COPY go.mod main.go ./
RUN CGO_ENABLED=0 go build -o /api .

FROM scratch
COPY --from=build /api /api
ENTRYPOINT ["/api"]
```

Endi `net` paketi DNS'ni sof Go'da hal qiladi, libc kerak emas:

```console
$ docker build -q --target build -t tuzoq-ok-build -f tuzoq/Dockerfile.ok .
sha256:70ab7438464228cb30ed8983c07789f0acbff57226430b46712cdb2cf1831689
$ docker run --rm tuzoq-ok-build ldd /api
	not a dynamic executable
$ docker build -q -t tuzoq-ok -f tuzoq/Dockerfile.ok .
sha256:35ca30f9d92756d4142d1ad567fd593613160ab7547f136f1dc1de3e1f938062
$ docker run -d --rm --name tuzoq-ok -p 3001:3000 tuzoq-ok
e0cb1ed36cb5b451d5e4fa95786a0fc9b586e7307268e6ccd56626fcdc83cb06
$ curl localhost:3001/health
{"status":"ok"}
$ docker stop tuzoq-ok
tuzoq-ok
```

*not a dynamic executable* — «dinamik bajariladigan fayl emas», yaʼni static. Konteyner ishlaydi.

JS'dagi oʻxshashi: glibc'li kompyuterda yigʻilgan Node native addon (C++ modul) Alpine image'da ishlamaydi. Sabab
xuddi shu: addon — dinamik bogʻlangan kutubxona, Alpine'da esa glibc oʻrnida musl.

Qachon cgo oʻzi yoqiladi? `cmd/cgo` hujjati boʻyicha: oddiy (native) build'da, C kompilyatori topilsa, cgo yoqiq.
Boshqa tizim uchun build qilganda (cross-compile) yoki C kompilyatori topilmasa, oʻchiq. Shuning uchun Mac'da
`GOOS=linux` bilan build qilsangiz, cgo oʻzi oʻchadi. Lekin gcc oʻrnatilgan Linux'da, `golang` image'ida va CI'da
yoqiq qolishi mumkin. Demak, yozib qoʻying.

Ishga yaraydigan retsept, bitta qator:

```bash
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o api .
scp api server:/srv/api/    # yoki: COPY api /api  →  FROM scratch
```

| Qadam | Nima |
|---|---|
| 1 | `CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o api .` — uchala oʻzgaruvchi ham |
| 2 | `api`: bitta fayl, ichida kod, `net/http` va runtime |
| 3 | `scp` bilan VPS'ga, yoki `COPY` bilan `FROM scratch` image'ga |
| 4 | CI'da ham aynan shu qator |

Bitta shart: loyihada C kutubxonasiga bogʻliq paket boʻlmasin. Masalan, `github.com/mattn/go-sqlite3` cgo paketi:
u `CGO_ENABLED=1` va gcc talab qiladi. Kurs README'si sof Go'dagi `modernc.org/sqlite`ni muqobil sifatida aytadi.

## Chuqurroq (ixtiyoriy): `go version -m` va HTTPS sertifikatlari

**Binary ichidagi build maʼlumoti.** `go version -m` binary'ga yozilgan build maʼlumotini oʻqiydi:

```console
$ go version -m api | grep -E 'go1|GOOS|GOARCH|CGO|vcs.revision|modified'
api: go1.26.8
	build	CGO_ENABLED=0
	build	GOARCH=amd64
	build	GOOS=linux
	build	vcs.revision=95652b3dc33eb53aa4bd94febbc5a2f5c8899ecc
	build	vcs.modified=true
```

Go versiyasi, `GOOS`, `GOARCH`, cgo holati, git commit (`vcs.revision`) va commit'dan keyin oʻzgargan fayllar
bor-yoʻqligi (`vcs.modified`). Production'da qaysi commit ishlayotganini binary'ning oʻzidan soʻrash mumkin. Sizda
commit hash boshqa boʻladi: u papka qaysi commit'da build qilinganiga bogʻliq. Commit maʼlumoti faqat `go build`da
yoziladi, `go run`da va `.git`siz build'da (masalan, Docker ichida) yoʻq. Buni 🟡 uy vazifasida oʻlchaysiz.

**Scratch'ning ikkinchi tuzogʻi: HTTPS.** Xizmatingiz tashqi API'ga (toʻlov tizimi, Telegram Bot API) HTTPS soʻrov
yuborsa, server sertifikatini tekshirishi kerak. Buning uchun ishonchli sertifikatlar (CA) roʻyxati kerak, u esa
tizimda turadi. `chuqur/https/main.go` bitta HTTPS soʻrov yuboradi:

```go filename="chuqur/https/main.go" showLineNumbers
// Chuqurroq: scratch image'da sertifikatlar yoʻq, tashqi HTTPS soʻrov yiqiladi.
package main

import (
	"fmt"
	"net/http"
	"os"
)

func main() {
	resp, err := http.Get("https://go.dev")
	if err != nil {
		fmt.Println("xato:", err)
		os.Exit(1)
	}
	resp.Body.Close()
	fmt.Println("status:", resp.Status)
}
```

| Qator | Kod | Nima qiladi |
|---|---|---|
| 11 | `resp, err := http.Get(…)` | GET soʻrov; ikki qiymat qaytaradi: javob va xato. `:=` — eʼlon qilib, qiymat berish ([GO-X.02](/lab/youtube/go/go-x-02)) |
| 12–15 | `if err != nil { … os.Exit(1) }` | xato boʻlsa, uni chiqarib, `exit status 1` bilan toʻxtaydi ([GO-X.03](/lab/youtube/go/go-x-03)) |
| 16 | `resp.Body.Close()` | javob tanasini yopadi (ulanishni boʻshatadi) |
| 17 | `fmt.Println("status:", resp.Status)` | `200 OK` kabi statusni chiqaradi |

`Dockerfile` — oddiy `FROM scratch` + binary. `Dockerfile.ok` esa sertifikatlar faylini `golang` image'idan koʻchiradi:

```dockerfile filename="chuqur/https/Dockerfile.ok" showLineNumbers
FROM scratch
COPY --from=golang:1.26.8 /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY https /https
ENTRYPOINT ["/https"]
```

```console
$ cd chuqur/https && CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o https .
$ docker build -q -t chuqur-https .
sha256:f3235ab993be4a1e866e745d3f635192b66e90eb3a71793dabbf59e1ee7b99d7
$ docker run --rm chuqur-https
xato: Get "https://go.dev": tls: failed to verify certificate: x509: certificate signed by unknown authority
$ docker build -q -t chuqur-https-ok -f Dockerfile.ok .
sha256:2e25c61d41e2c66ec63af46518c3d94a9d5dc1d50cae296878f2040d4f6fb6e4
$ docker run --rm chuqur-https-ok
status: 200 OK
```

*certificate signed by unknown authority* — «sertifikat nomaʼlum markaz tomonidan imzolangan»: `scratch`da Go
ishonadigan birorta markaz yoʻq. Sertifikatlar fayli bilan image 8.5 MB'dan 8.73 MB'ga oʻsdi. Ikkinchi yoʻl —
`scratch` oʻrniga `gcr.io/distroless/static`: u ham deyarli boʻsh, lekin unda sertifikatlar va vaqt zonalari bazasi
bor. Vaqt zonalari bilan bogʻliq xuddi shunday tuzoq [GO-1.01](/lab/youtube/go/go-1-01) darsida.

## Koʻp uchraydigan xatolar

**1. «Go binary hamma joyda ishlaydi» deb oʻylash.** Bu mavzudagi eng klassik xato tushuncha. Binary bitta OS va
bitta CPU uchun yasaladi. Apple chipli Mac'da `GOOS=linux go build` qilib, amd64 serverga qoʻysangiz:
`cannot execute binary file: Exec format error`. Toʻliq misol «`go build`: bitta binary» boʻlimida.
**Tuzatish:** `GOOS` bilan birga `GOARCH`ni ham yozing. Qaysi arxitektura uchun yasalganini
`go version -m api | grep GOARCH` aytadi.

**2. `scratch`da `exec /api: no such file or directory`.** Binary gcc bor joyda (`golang` image, CI) cgo yoqiq holda
yigʻilgan, u libc va dinamik yuklovchini soʻraydi. Toʻliq misol «Tuzoq» boʻlimida. **Tuzatish:** `CGO_ENABLED=0`;
tekshirish: `ldd api` → `not a dynamic executable`.

**3. Ishlatilmagan import.** `./main.go:4:2: "encoding/json" imported and not used`, binary yasalmaydi. Misol
«Ishlatilmagan import» boʻlimida. **Tuzatish:** import'ni oʻchiring (gopls buni saqlashda qiladi) yoki uni ishlating.

**4. `go build ./xato` dars papkasidan.** `cd xato && go build` oʻrniga shunday yozsangiz:

```console
$ go build ./xato
go: build output "xato" already exists and is a directory
```

Kutilgan kompilyatsiya xatosi oʻrniga boshqa xabar chiqdi: *build output "xato" already exists and is a directory* —
«build natijasi "xato" allaqachon bor va u papka». `go build` bitta `main` paketini build qilganda binary'ni paket
papkasi nomi bilan joriy papkaga yozmoqchi boʻladi. `xato` nomi esa papkaning oʻzi bilan band. **Tuzatish:**
`cd xato && go build` yoki natijaga boshqa joy bering (`-o /dev/null` — natijani tashlab yuborish):

```console
$ go build -o /dev/null ./xato
# api/xato
xato/main.go:4:2: "encoding/json" imported and not used
```

**5. Port band.** Bitta terminalda server ishlab turganda ikkinchisini ham ishga tushirsangiz:

```console
$ go run .
2026/11/26 18:11:27 listening on :3000
2026/11/26 18:11:27 listen tcp :3000: bind: address already in use
exit status 1
```

Birinchi qatorga ishonmang. `log.Println("listening …")` `ListenAndServe`dan **oldin** turadi, shuning uchun port band
boʻlsa ham chiqadi. Keyingi qator — `ListenAndServe` qaytargan xato, uni `log.Fatal` yozdi va dasturni toʻxtatdi.
*address already in use* — «manzil allaqachon band». `exit status 1` — buni `go run` qoʻshadi. **Tuzatish:**
birinchi serverni toʻxtating (<kbd>Ctrl</kbd>+<kbd>C</kbd>) yoki boshqa port bering (🟢 uy vazifasi).

**6. gcc yoʻq, lekin cgo yoqiq.** Bu dars yozilgan laptop'da (NixOS) `go env CGO_ENABLED` `1` deydi, gcc esa yoʻq.
`CGO_ENABLED=0`siz oddiy build shunday tugaydi:

```console
$ go build -o api .
# runtime/cgo
cgo: C compiler "gcc" not found: exec: "gcc": executable file not found in $PATH
```

`# runtime/cgo` — xato `runtime/cgo` paketida. *C compiler "gcc" not found* — «C kompilyatori gcc topilmadi».
Odatda gcc topilmasa Go cgo'ni oʻzi oʻchiradi (`cmd/cgo`), lekin `CGO_ENABLED=1` aniq yozilgan boʻlsa, gcc'ni talab
qiladi. **Tuzatish:** `CGO_ENABLED=0 go build …` yoki terminalda bir marta `export CGO_ENABLED=0`.

**7. `scratch`dan tashqi HTTPS.** `x509: certificate signed by unknown authority`. Misol «Chuqurroq» boʻlimida.
**Tuzatish:** `ca-certificates.crt`ni image'ga koʻchiring yoki `distroless/static` oling.

## Oʻzingizni tekshiring

Avval oʻzingiz javob bering, keyin oching.

**1.** Express loyihada kutubxonalar `node_modules`da turadi. Go API'da ular qayerda?

<details>
<summary>Javob</summary>

`net/http` va `encoding/json` standart kutubxonada, Go bilan birga keladi. Tashqi modullar (`go get`) loyihada
emas, umumiy modul keshida turadi, `go.mod` ularning aniq versiyasini, `go.sum` xeshlarini saqlaydi. `go build` esa
kerakli hamma kodni runtime bilan birga bitta binary'ga yigʻadi: serverga hech qanday papka ketmaydi.

</details>

**2.** Apple chipli MacBook'dan amd64 server uchun `FROM scratch` image qilmoqchisiz. Build qatori qanday?

<details>
<summary>Javob</summary>

`CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o api .` — uchala oʻzgaruvchi ham. `GOARCH`siz binary arm64
boʻladi (`exec format error`). `CGO_ENABLED=0` Mac'dan cross-compile qilganda oʻzi oʻchadi, lekin CI'da yoki
`golang` image'ida yoqiq qolishi mumkin, shuning uchun yozib qoʻyiladi.

</details>

**3.** Fayl image'da joyida, lekin `docker run` `exec /api: no such file or directory` dedi. Sabab nima?

<details>
<summary>Javob</summary>

cgo yoqiq qolgan: binary libc'ga bogʻlangan va dinamik yuklovchi `/lib64/ld-linux-x86-64.so.2`ni soʻraydi.
`scratch`da u yoʻq, kernel shuni «fayl topilmadi» deydi. `ldd` buni koʻrsatadi. Tuzatish: `CGO_ENABLED=0`.

</details>

**4.** `go run .` ishlab turibdi. Nima chiqadi?

```bash
curl -i -X DELETE localhost:3000/users/42
```

**A)** `404 Not Found` · **B)** `405 Method Not Allowed` va `Allow: GET, HEAD` · **C)** `200 OK` va `{"id":"42"}`

<details>
<summary>Javob</summary>

**B.** `/users/{id}` yoʻli bor, lekin faqat `GET` (va `HEAD`) uchun. `POST /health` bilan bir xil qoida.

```console
$ curl -i -X DELETE localhost:3000/users/42
HTTP/1.1 405 Method Not Allowed
Allow: GET, HEAD
Content-Type: text/plain; charset=utf-8
X-Content-Type-Options: nosniff
Date: Thu, 26 Nov 2026 13:09:07 GMT
Content-Length: 19

Method Not Allowed
```

Yoʻlning oʻzi boʻlmasa (masalan, `GET /users`), Go `404 page not found` qaytaradi.

</details>

**5.** Dars boshidan: `go.mod`dagi `go 1.26.8` qatori `package.json`dagi `"engines"`dan nimasi bilan farq qiladi?

<details>
<summary>Javob</summary>

Ikki narsa bilan. Go uni majburiy qiladi: eskiroq Go build qilmaydi yoki `GOTOOLCHAIN=auto` bilan yangisini yuklaydi
(`engines` esa faqat maslahat). Va u til hamda standart kutubxonaning qaysi xulqi ishlashini ham tanlaydi
([GO-1.16](/lab/youtube/go/go-1-16)).

</details>

## Uy vazifasi

Boshlangʻich fayllar va javoblar GitHub'dagi dars papkasida:
[lessons/0x-01-http-api](https://github.com/abdurahmon27/go-backend-uz/tree/main/lessons/0x-01-http-api)
(`uyga/` papkasi, javoblar
[uyga/javob/](https://github.com/abdurahmon27/go-backend-uz/tree/main/lessons/0x-01-http-api/uyga/javob)). Buyruqlar
dars papkasidan (`lessons/0x-01-http-api`) ishlaydi.

🟢 **Oson** (`uyga/oson/main.go`): portni `PORT` muhit oʻzgaruvchisidan oʻqing (`os.Getenv("PORT")`, Node'dagi
`process.env.PORT`), boʻsh boʻlsa `3000`. `:=` va `if` keyingi darsda, shuning uchun kerakli ikki qator boshlangʻich
faylning izohida tayyor:

```go
port := os.Getenv("PORT")
if port == "" { port = "3000" }
```

Keyin arm64 uchun build qiling va `go version -m` bilan tekshiring:
`GOOS=linux GOARCH=arm64 go build -o api-arm ./uyga/oson && go version -m api-arm | grep GOARCH`.

🟡 **Oʻrta** (`uyga/orta/main.go`): `GET /version` endpoint'ini qoʻshing, u
`{"go":"go1.26.8","revision":"<commit>"}` qaytarsin. `version` funksiyasi tayyor: u binary ichidagi build
maʼlumotini oʻqiydi (`go version -m` koʻrsatgan maʼlumotning oʻzi). Sizning ishingiz — uni route'ga ulash va natijani
`go run .` hamda `go build` bilan solishtirish. Qaysi birida `revision` `unknown`?

Boshlangʻich faylda `/health` route'i, `log.Println` va `ListenAndServe` darsdagidek. Ular orasida esa siz
toʻldiradigan izoh qatori va tayyor funksiya:

```go
func version(w http.ResponseWriter, r *http.Request) {
	out := map[string]string{"go": "", "revision": "unknown"}
	if bi, ok := debug.ReadBuildInfo(); ok {
		out["go"] = bi.GoVersion
		for _, s := range bi.Settings {
			if s.Key == "vcs.revision" {
				out["revision"] = s.Value
			}
		}
	}
	w.Header().Set("Content-Type", "application/json")
	json.NewEncoder(w).Encode(out)
}
```

Import'larga `"runtime/debug"` ham qoʻshilgan. `version` ichini toʻliq tushunish shart emas (`:=`, `range` — [GO-X.02](/lab/youtube/go/go-x-02)). Qisqasi:
`debug.ReadBuildInfo()` binary'dagi build maʼlumotini beradi, sikl uning sozlamalari orasidan `vcs.revision`ni
qidiradi. Eʼtibor bering: `version` — oddiy, nomli funksiya, lekin turi handler bilan bir xil:
`func(w http.ResponseWriter, r *http.Request)`.

🔍 **Qiziqish:** `tuzoq/Dockerfile.ok` asosida multi-stage Dockerfile yozing va oxirgi bosqichga sertifikatlarni ham
qoʻshing (`chuqur/https/Dockerfile.ok`dagi kabi). Image hajmini `docker images` bilan `api-go` bilan solishtiring.

🟢 `uyga/javob/oson/main.go`: port muhitdan, boʻsh boʻlsa 3000. Log va `ListenAndServe` ham `port`ni ishlatadi:

```go filename="uyga/javob/oson/main.go" showLineNumbers
// 🟢 Javob: port muhitdan, boʻsh boʻlsa 3000 (12-factor: sozlama muhitda).
package main

import (
	"encoding/json"
	"log"
	"net/http"
	"os"
)

func main() {
	http.HandleFunc("GET /health", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(map[string]string{"status": "ok"})
	})
	http.HandleFunc("GET /users/{id}", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "application/json")
		json.NewEncoder(w).Encode(map[string]string{"id": r.PathValue("id")})
	})
	port := os.Getenv("PORT")
	if port == "" {
		port = "3000"
	}
	log.Println("listening on :" + port)
	log.Fatal(http.ListenAndServe(":"+port, nil))
}
```
