## What you will learn

We add one to a large identifier, `9223372036854775807`, in three languages. Python gives the exact answer:
`9223372036854775808`. JavaScript rounds the last digits and prints `9223372036854776000`. In Go this number sits in
an `int64` variable, and `id++` gives a **negative number** with no error: `-9223372036854775808`. Where does this
negative number come from, and when does Go refuse to compile it at all?

**One idea:** in Go, the type you choose sets the limit of an integer (`int8` = −128 … 127). When a value in a
variable crosses the limit, it silently wraps around by two's complement (Python has no limit, JS loses precision).
A constant expression is evaluated exactly: if the final value does not fit the type, Go rejects it at compile time.

By the end of the lesson you will be able to:

- name the limits of `int8`, `int16`, `int32`, `int64` and `int` from the type name, and compare them with Python
  `int` and JS `number`;
- show in bits why `127 + 1` in `int8` is exactly `−128`;
- say, without running the code, which line is a compile error and which one silently wraps;
- find and fix the bug in an `int8` like counter, and send a large `int64` ID to the frontend intact with
  `json:"id,string"`.

Today's three core new words:

| Word | Plain meaning | English term |
|---|---|---|
| `int8` … `int64`, `int` | integer types with a fixed size: the number in the name is the number of bits | sized integer types |
| overflow | a value crosses the type's limit and comes back from the other end: in `int8`, 127 + 1 → −128 | overflow |
| constant | an expression whose value is known at compile time (`128`, `math.MaxInt64 + 1`): evaluated exactly, checked when it is put into a type | constant |

Two helper words also appear: **two's complement** (the way a negative number is written in bits) and
**`math.MaxInt64`** (the largest number that fits in an `int64` variable). We explain both where they are needed.

## Each language puts the integer limit in a different place

Why are the answers different? Because each language stores "an integer" in its own way:

| Language | Integer | Limit | `9223372036854775807 + 1` |
|---|---|---|---|
| Python | `int` | none: "Integers have unlimited precision" | `9223372036854775808`, exact |
| JavaScript | `number` = float64 (a floating-point format) | precision is lost after 2⁵³; for exact integers, `BigInt` | `9223372036854776000`, rounded |
| Go | `int8`, `int16`, `int32`, `int64`, `int` | the type you choose | in `int64`, `-9223372036854775808` |

See the JavaScript limit yourself. These commands are not files in the course folder; the code is inside the
command:

```console
$ node -p 'Number.MAX_SAFE_INTEGER'
9007199254740991
$ node -p '2**53 + 1'
9007199254740992
$ node -p '9223372036854775807n + 1n'
9223372036854775808n
```

`Number.MAX_SAFE_INTEGER` = 2⁵³ − 1. After it, float64 cannot store every integer: instead of `2**53 + 1` we got
the neighbour `2**53`. A `BigInt`, written with the `n` suffix, computes exactly, like Python.

In Go, the type sets the limit. The types are in the next section.

## The number in the type name is the number of bits: `int8` … `int64`

In Go, the number in an integer type's name is the number of bits: `int8` is 8 bits, that is 1 byte; `int64` is 64
bits, 8 bytes. `sizes/main.go` prints the sizes and limits:

```go filename="sizes/main.go" showLineNumbers
package main

import (
	"fmt"
	"math"
	"unsafe"
)

func main() {
	fmt.Println("int8 ", unsafe.Sizeof(int8(0)), "bayt:", math.MinInt8, "...", math.MaxInt8)
	fmt.Println("int16", unsafe.Sizeof(int16(0)), "bayt:", math.MinInt16, "...", math.MaxInt16)
	fmt.Println("int32", unsafe.Sizeof(int32(0)), "bayt:", math.MinInt32, "...", math.MaxInt32)
	fmt.Println("int64", unsafe.Sizeof(int64(0)), "bayt:", math.MinInt64, "...", math.MaxInt64)
	fmt.Println("uint8", unsafe.Sizeof(uint8(0)), "bayt:", 0, "...", math.MaxUint8)
	fmt.Println("int  ", unsafe.Sizeof(int(0)), "bayt (bu kompyuterda)")
}
```

| Line | Code | What it does |
|---|---|---|
| 3–7 | `import (…)` | imports the `fmt`, `math` and `unsafe` packages |
| 10–15 | `unsafe.Sizeof(int8(0))` | `int8(0)` is a zero of type `int8`; `unsafe.Sizeof` says how many bytes a value of that type takes in memory. The `unsafe` package holds tools that bypass Go's type safety; here it is used only to measure |
| 10–13 | `math.MinInt8`, `math.MaxInt8`, … | constants in the `math` package: the smallest and largest value of each type |
| 14 | `uint8` | `u` means unsigned: no negative numbers, 0 … 255. We do not use it today; `byte` is exactly this type |
| 15 | `int(0)` | the size of plain `int` |

The output words are Uzbek: `bayt` means "byte", `bu kompyuterda` means "on this computer".

```console
$ go run sizes/main.go
int8  1 bayt: -128 ... 127
int16 2 bayt: -32768 ... 32767
int32 4 bayt: -2147483648 ... 2147483647
int64 8 bayt: -9223372036854775808 ... 9223372036854775807
uint8 1 bayt: 0 ... 255
int   8 bayt (bu kompyuterda)
```

The main rule: the `int8` type holds only **−128 to 127**, 256 numbers in total. Plain `int` on this computer has
the same size as `int64`. By Go's official rules (the Go spec), `int` is 32 or 64 bits. (The video trims the
`uint8` line; this is the full output.)

`:=` always picks `int` for an integer (GO-X.02). So when you need `int8`, you write the type with `var`:
`var x int8 = 127`.

## Why exactly −128: bits and two's complement

In eight bits, 127 is `0111 1111`: a zero and seven ones. Add one: the ones on the right become zeros, and a one
carries to the left: `1000 0000`. The question: which number is this?

Go stores negative numbers in **two's complement**: the leftmost bit has a negative weight, in `int8` it is **−128**.
The other bits are positive, as usual:

```text
bit weight:   −128   64   32   16    8    4    2    1
  127  =         0    1    1    1    1    1    1    1    = 64+32+16+8+4+2+1
  + 1
 −128  =         1    0    0    0    0    0    0    0    = −128
   −1  =         1    1    1    1    1    1    1    1    = −128 + 127

number circle:    … 126 → 127 → −128 → −127 …
```

Go's official rules require integers to be stored exactly like this: "represented using two's complement
arithmetic". Almost all processors store negative numbers this way too. `binary/main.go` prints the bits:

```go filename="binary/main.go" showLineNumbers
package main

import "fmt"

func main() {
	var x int8 = 127
	fmt.Printf("%4d = %08b\n", x, uint8(x))
	x++
	fmt.Printf("%4d = %08b\n", x, uint8(x))
	x = -1
	fmt.Printf("%4d = %08b\n", x, uint8(x))
}
```

- **Line 7:** `Printf` prints by a template: `%4d` is a number in a field 4 characters wide; `%08b` is the binary
  form, padded with zeros to 8 digits; `\n` is a new line. `uint8(x)` reads the same bits as an unsigned number:
  `%b` would print a negative number with a minus sign, and we want the bits themselves. Conversion is covered in
  "Going deeper".
- **Lines 8–9:** add one and print again.
- **Lines 10–11:** `x = -1` and its bits.

```console
$ go run binary/main.go
 127 = 01111111
-128 = 10000000
  -1 = 11111111
```

The same three rows as in the table, now from Go itself.

## Overflow: not an error, but no check either

Crossing the type's limit and wrapping around is called **overflow**. By Go's official rules it is not an error:

> For signed integers, the operations `+`, `-`, `*`, `/`, and `<<` may legally overflow and the resulting value exists and is
> deterministically defined by the signed integer representation, the operation, and its operands. Overflow does not
> cause a run-time panic.

In other words, for signed integers `+`, `-`, `*`, `/` and `<<` may legally overflow. The result is well defined,
and the program does not stop (no panic).

| Line | `x` (`int8`) | What happened |
|---|---|---|
| `var x int8 = 127` | 127 | |
| `x++` | −128 | 127 + 1 → −128 |
| next line | −128 | no error, the program goes on |

But Go does not check overflow for you either. Where a value can reach the limit, you write the check yourself: you
do that with `safeAdd` in the 🟡 homework.

## When Go refuses: a constant

Now we do not add; we write 128 directly. `sigmaydi/main.go`:

```go filename="sigmaydi/main.go" showLineNumbers
package main

import "fmt"

func main() {
	var x int8 = 128
	fmt.Println(x)
}
```

Remember from GO-X.02 when Go catches type errors. What does this program do?
**A)** prints `-128` · **B)** prints `128` · **C)** a compile error

<details>
<summary>Answer</summary>

**C: a compile error.** `128` is a **constant**: its value is known at compile time. When it is put into an `int8`
variable, Go checks whether it fits and refuses. If you chose "`-128`", you carried the wrap from `x++` over to
here. If you chose "`128`", you forgot the `int8` limit.

</details>

```console
$ go run sigmaydi/main.go
# command-line-arguments
sigmaydi/main.go:6:15: cannot use 128 (untyped int constant) as int8 value in variable declaration (overflows)
```

Let us read the message. `# command-line-arguments` is the name of the package that `go run` built from the given
file. Then `sigmaydi/main.go:6:15`: the file, line 6, column 15, which is where `128` stands. Then the reason:
*cannot use 128 (untyped int constant) as int8 value in variable declaration (overflows)* — "128 (an untyped integer
constant) cannot be used as an `int8` value in a variable declaration (it overflows)". The program did not even
start.

What the *untyped constant* in the message is, we open up in the next lesson, [GO-1.03](/lab/youtube/go/go-1-03/en). There we also see why the
wait function `time.Sleep(2)` waits only 2 nanoseconds.

## The rule: a constant expression is evaluated exactly

The precise rule is this. **Constant expressions are evaluated exactly, with no limit.** The Go spec: "Constant
expressions are always evaluated exactly; intermediate values and the constants themselves may require precision
significantly larger than supported by any predeclared type". The error appears only when the result is put into a
type like `int8` or `int64` and does not fit.

That is why the first example, written with a constant, is rejected too. `const64/main.go`:

```go filename="const64/main.go" showLineNumbers
package main

import (
	"fmt"
	"math"
)

// Ataylab kompilyatsiya bo'lmaydi: konstanta int64 ga sig'maydi.
func main() {
	var id int64 = math.MaxInt64 + 1
	fmt.Println(id)
}
```

The comment on line 8: "Does not compile on purpose: the constant does not fit in int64".

```console
$ go run const64/main.go
# command-line-arguments
const64/main.go:10:17: cannot use math.MaxInt64 + 1 (untyped int constant 9223372036854775808) as int64 value in variable declaration (overflows)
```

Line 10, column 17: `math.MaxInt64 + 1`. Look at the message: Go computed the sum exactly, `9223372036854775808`,
and nothing wrapped. Then it saw that this number does not fit in `int64` and refused. In `hook/main.go`, the same
`+ 1` happened in a variable, at run time, and wrapped silently.

TypeScript does not check such a line at all. `tsc 5.9.3` with `strict: true` compiled the file below with no errors
(the file is not in the course folder; we checked it separately). The value is then rounded at run time, as in the
Node example:

```ts
declare const console: { log(...a: unknown[]): void }
const id: number = 9223372036854775807 + 1
console.log(id)
```

Everything in one table:

| Code | What it is | Result |
|---|---|---|
| `var x int8 = 128` | a constant, does not fit in `int8` | compile error 🛑 |
| `var id int64 = math.MaxInt64 + 1` | a constant expression, does not fit in `int64` | compile error 🛑 |
| `x++` (`x` = 127, `int8`) | a variable, at run time | −128, silently 🔄 |
| TS: `const id: number = 2⁶³ − 1 + 1` | `tsc --strict` | no error, rounded |

## Check: `100 + 50 - 60`

Let us test the rule. `var a int8 = 100 + 50 - 60`. In between we get 150, which does not fit in `int8`.

```go
var a int8 = 100 + 50 - 60
fmt.Println(a)
```

What is the result? **A)** `90` · **B)** a compile error · **C)** a negative number

<details>
<summary>Answer</summary>

**A: `90`.** The program compiles. A constant expression is evaluated exactly, and the intermediate 150 is stored
nowhere. Only the final 90 is put into the `int8` variable, and it fits. If you chose "a compile error", you thought
Go checks every step: it checks only the final value. If you chose "a negative number", you thought 150 wraps in
`int8`: there is no variable here, so nothing can wrap.

</details>

```go filename="ifoda/main.go" showLineNumbers
package main

import "fmt"

func main() {
	// Konstanta ifoda aniq hisoblanadi: oraliqdagi 150 hech qayerga saqlanmaydi,
	// int8 ga faqat yakuniy 90 qo'yiladi.
	var a int8 = 100 + 50 - 60
	fmt.Println(a)
}
```

The comment on lines 6–7: "A constant expression is evaluated exactly: the intermediate 150 is stored nowhere, only
the final 90 is put into int8".

```console
$ go run ifoda/main.go
90
```

## A real bug: the `int8` like counter

To save space in the like counter of a post, we pick `int8`. The loop starts it at zero and increases it 200 times.
`layk/main.go`:

```go filename="layk/main.go" showLineNumbers
package main

import "fmt"

func main() {
	var layk int8
	for i := 1; i <= 200; i++ {
		layk++
	}
	fmt.Println(layk)
}
```

| Line | Code | What it does |
|---|---|---|
| 6 | `var layk int8` | `layk` ("like") is an `int8` counter, zero value 0 |
| 7 | `for i := 1; i <= 200; i++ {` | the same as `for (let i = 1; i <= 200; i++)` in JS, only without parentheses: 200 times |
| 8 | `layk++` | one like each time |
| 10 | `fmt.Println(layk)` | the result after the loop |

The post got 200 likes. What does it print?
**A)** stops at `127` · **B)** stops at `-128` · **C)** `-56`

<details>
<summary>Answer</summary>

**C: `-56`.** After the 127th like, `layk` = 127. At the 128th it turned into −128. The remaining 72 likes brought it
to −56: −128 + 72 = −56. If you chose "stops at `127`", you thought Go holds the number at the limit (saturation):
it does not. If you chose "stops at `-128`", you thought adding stops after the wrap: after −128 come −127, −126 and
so on.

</details>

```console
$ go run layk/main.go
-56
```

| `i` | `layk` after the step |
|---|---|
| 1 | 1 |
| 127 | 127 |
| 128 | −128 |
| 129 | −127 |
| 200 | −56 |

No error and no log. That is why such a bug is hard to notice without tests.

**Fix:** `int` instead of `int8`. In `layk-int/main.go` only line 6 changed:

```go filename="layk-int/main.go" showLineNumbers
package main

import "fmt"

func main() {
	var layk int
	for i := 1; i <= 200; i++ {
		layk++
	}
	fmt.Println(layk)
}
```

```console
$ go run layk-int/main.go
200
```

The Go Tour rule says the same: "you should use `int` unless you have a specific reason to use a sized or unsigned
integer type". Picking a small type to save a few bytes is usually not worth it.

## A large ID to the frontend: `json:"id,string"`

There is a second limit for the frontend. If the backend sends an `int64` ID in JSON as a number, JavaScript reads it
into a float64 and rounds it: a different ID comes out. `hook/id.js` shows this:

```js filename="hook/id.js"
// Backend JSON'da 64 bitlik ID yubordi, frontend uni JSON.parse bilan son qilib o'qidi.
const body = '{"id":1234567890123456789}'
console.log(body)
console.log(JSON.parse(body).id)
```

The comment on line 1: "The backend sent a 64-bit ID in JSON, the frontend read it as a number with JSON.parse".

```console
$ node hook/id.js
{"id":1234567890123456789}
1234567890123456800
```

The last digits are not `789` but `800`. That ID may belong to a different post in the database, or to none at all.
That is why the X API (formerly Twitter) returns IDs as strings. Its documentation says: "In JavaScript, integers are
limited to 53 bits. This causes precision loss with large IDs" and "Always use string IDs in your code". Twitter
added the `id_str` field in 2010 for this reason.

In Go this is one tag on a struct field. `jsonid/main.go`:

```go filename="jsonid/main.go" showLineNumbers
package main

import (
	"encoding/json"
	"fmt"
)

// ",string" teg int64 ni JSON'da string qilib yozadi: JS uni yaxlitlamaydi.
type Post struct {
	ID int64 `json:"id,string"`
}

func main() {
	b, _ := json.Marshal(Post{ID: 1234567890123456789})
	fmt.Println(string(b))
}
```

| Line | Code | What it does |
|---|---|---|
| 4 | `"encoding/json"` | the JSON package that ships with Go |
| 8 | comment | "the ",string" tag writes an int64 into JSON as a string: JS will not round it" |
| 9–11 | `type Post struct { … }` | `Post` is a set of fields (a struct), similar to `type Post = { id: … }` in TS. We cover structs in detail in [GO-1.10](/lab/youtube/go/go-1-10/en) |
| 10 | `` ID int64 `json:"id,string"` `` | the `ID` field, of type `int64`. The text in backquotes is a **tag**: `encoding/json` reads it. `id` is the key name in JSON, `,string` means "write this number into JSON as a string" |
| 14 | `b, _ := json.Marshal(…)` | turns the struct into JSON bytes. `json.Marshal` returns the bytes and an `error`; `_` throws the error away (in real code, check it, GO-X.03) |
| 15 | `fmt.Println(string(b))` | prints the bytes as text |

```console
$ go run jsonid/main.go
{"id":"1234567890123456789"}
```

Now the ID is in quotes: `JSON.parse` reads it as a string, and no digit changes. The frontend keeps it as a string
and calls `BigInt(post.id)` when it needs arithmetic.

## In real life: the Boeing 787

This is not only a textbook example. In 2015 the US Federal Aviation Administration (FAA) issued a mandatory
directive for the Boeing 787 (AD 2015-09-07). If the four generator control units (GCUs) were powered up at the same
time and ran for **248 days** without a break, a software counter in them would overflow. The airplane could then
lose all generator power and, in the directive's words, "loss of control of the airplane".

Until the software was fixed, operators were ordered to power the airplane off and on regularly: "at intervals not to
exceed 120 days", that is, at most every **120 days**. Later, AD 2018-20-15 required new GCU software. The FAA did
not name the counter's type or how fast it grows.

| Number | What it is |
|---|---|
| 248 days | after this much continuous power, the counter overflows |
| 120 days | the power-off-and-on interval must not exceed this |

## Going deeper (optional): the conversion `int8(big)`

One more silent place: **conversion**, that is, turning a value of one integer type into another. `convert/main.go`:

```go filename="convert/main.go" showLineNumbers
package main

import "fmt"

func main() {
	big := 300
	small := int8(big)
	fmt.Println(small)

	other := 200
	fmt.Println(int8(other))
}
```

- **Line 6:** `big` is an `int` because of `:=`, with the value 300.
- **Line 7:** `int8(big)` converts `big` to `int8`. 300 does not fit in `int8`.
- **Lines 10–11:** the same with 200.

```console
$ go run convert/main.go
44
-56
```

Go takes the low 8 bits, throws the rest away and gives a result with no error:

| Number | Bits | Low 8 bits | As `int8` |
|---|---|---|---|
| 300 | `1 0010 1100` | `0010 1100` | 32 + 8 + 4 = **44** |
| 200 | `1100 1000` | `1100 1000` | −128 + 64 + 8 = **−56** |

The Go spec (Conversions): the number is "truncated to fit in the result type's size", and "there is no indication of
overflow". `Int8Array` in JavaScript also turns 300 into 44:

```console
$ node -p 'new Int8Array([300])[0]'
44
```

Code that reads an `int64` from a database and converts it to `int32` can have the same bug. (When a floating-point
number is converted to an integer and does not fit, the result depends on the Go implementation.)

## Common mistakes

**1. Thinking "Go reports an error on overflow".** This is the most classic misconception of this topic. Overflow in
a variable gives no error, no panic and no log: the `int8` like counter printed `-56` instead of 200 likes. The full
example is in the section "A real bug: the `int8` like counter". **Fix:** use `int` unless you have a specific reason.
In calculations that can reach the limit (money, counters), write the check yourself, like `safeAdd` in the 🟡
homework.

**2. Putting a constant into a small type.** `var x int8 = 128` and `var id int64 = math.MaxInt64 + 1` do not
compile: see the sections "When Go refuses" and "The rule". The same mistake happens with a typed constant, but the
message is different. This is `constover/main.go` (from the first version of the lesson, in the course folder):

```go filename="constover/main.go" showLineNumbers
package main

import "fmt"

func main() {
	fmt.Println(int8(127) + 1)
}
```

```console
$ go run constover/main.go
# command-line-arguments
constover/main.go:6:14: int8(127) + 1 (constant 128 of type int8) overflows int8
```

Line 6, column 14: `int8(127) + 1`. *(constant 128 of type int8) overflows int8* means "the constant 128 of type
`int8` goes beyond `int8`". `int8(127)` is a typed constant, so Go checks the sum as an `int8` too. Why the check is
stricter in this case is in [GO-1.03](/lab/youtube/go/go-1-03/en). **Fix:** put the value into a type it fits in (`int`), or
keep the constant within the `int8` limits.

**3. Sending a large `int64` ID in JSON as a number.** There is no error message: the frontend gets
`1234567890123456800` instead of `1234567890123456789`. The example is in the section "A large ID to the frontend".
**Fix:** add the tag `json:"…,string"` to the field, and keep the ID on the frontend as a string or a `BigInt`.

**4. Converting a number that does not fit.** `int8(300)` gives `44` with no error. The example is in "Going deeper".
**Fix:** check the limits before converting: `if big < math.MinInt8 || big > math.MaxInt8 { … }`.

## Check yourself

Answer first, then open.

**1.** What is printed after `x = 127; x++` for an `int8` variable?

<details>
<summary>Answer</summary>

`-128`. This is overflow: the value crossed the limit and came back from the other end, silently. In bits:
`0111 1111` + 1 = `1000 0000`, and the leftmost bit weighs −128.

</details>

**2.** Why is `var x int8 = 128` rejected, but `var a int8 = 100 + 50 - 60` is not?

<details>
<summary>Answer</summary>

A constant expression is evaluated exactly, and Go checks only whether the final value fits the type: 128 does not
fit ❌, 90 fits ✅. The intermediate 150 is stored nowhere.

</details>

**3.** How do you send a large `int64` ID to the frontend?

<details>
<summary>Answer</summary>

As a string, with the tag `json:"id,string"`. The reason: in JavaScript a number is a float64, and integers larger
than 2⁵³ are rounded. The frontend keeps the ID as a string or a `BigInt`.

</details>

**4.** What does `sinov/main.go` print? **A)** `150` · **B)** a compile error · **C)** `-106`

```go filename="sinov/main.go" showLineNumbers
package main

import "fmt"

func main() {
	var a int8 = 100
	a = a + 50
	fmt.Println(a)
}
```

<details>
<summary>Answer</summary>

**C: `-106`.** This time `a + 50` contains a variable, so the calculation happens at run time and wraps silently:
150 − 256 = −106. That is the difference from `100 + 50 - 60`: there, everything was a constant.

```console
$ go run sinov/main.go
-106
```

</details>

**5.** From [GO-1.01](/lab/youtube/go/go-1-01/en): why is the binary of a seven-line Go program about 2 MB?

<details>
<summary>Answer</summary>

The Go linker builds a static binary by default: every binary contains the Go runtime (the garbage collector, the
scheduler and more). The program's own code is very small; most of the bytes are the runtime.

</details>

🟡 Overflow happens only when two numbers of the same sign are added: positive + positive gave a negative, or
negative + negative gave a positive (or 0). In Go, `a + b` does not panic, so it is safe to add first and check the
sign afterwards:

```go filename="uyga/javob/orta/main.go" showLineNumbers
package main

import (
	"errors"
	"fmt"
	"math"
)

var ErrOverflow = errors.New("int64 overflow")

// safeAdd a+b ni qaytaradi; int64 ga sig'masa ErrOverflow.
// Go'da a+b panic bermaydi, jim aylanadi. Shuning uchun natijani hisoblab,
// keyin ishorasini tekshiramiz: musbat+musbat manfiy chiqsa yoki
// manfiy+manfiy musbat (yoki 0) chiqsa, overflow bo'lgan.
func safeAdd(a, b int64) (int64, error) {
	sum := a + b
	if (a > 0 && b > 0 && sum < 0) || (a < 0 && b < 0 && sum >= 0) {
		return 0, ErrOverflow
	}
	return sum, nil
}

func main() {
	fmt.Println(safeAdd(2, 3))                         // 5 <nil>
	fmt.Println(safeAdd(math.MaxInt64, 1))             // 0 int64 overflow
	fmt.Println(safeAdd(math.MinInt64, -1))            // 0 int64 overflow
	fmt.Println(safeAdd(math.MaxInt64, math.MinInt64)) // -1 <nil>
}
```

```console
$ go run ./uyga/javob/orta
5 <nil>
0 int64 overflow
0 int64 overflow
-1 <nil>
```

On line 17, `&&` means "and" and `||` means "or", as in JS. `MaxInt64 + MinInt64` adds two numbers of different
signs, so there is no overflow: `-1`.

The harder tasks (details in `homework/README.md`):

- 🟢 In `int16`, `32767 + 1` → `-32768`: `0111 1111 1111 1111` + 1 = `1000 0000 0000 0000`, the same rule as in
  `int8`, only on 16 bits.
- 🟡 The largest `int32` value is 2 147 483 647 seconds, which is **19 January 2038, 03:14:07 UTC**. One second later
  the number becomes negative and turns into 13 December 1901 (the "year 2038 problem"). The range of MySQL's
  `TIMESTAMP` type ends at exactly the same point.
- 🟠 The idea is the same as in 🟡: if numbers of the same sign are added and the sign of the result changes, it is
  overflow.
- 🔴 `abs8(math.MinInt8)` → `-128`: +128 does not fit in `int8`, so `-(-128)` turns into −128 again. The fix: return
  the result in a larger type (`int16`), or check `math.MinInt8` separately.

</details>
