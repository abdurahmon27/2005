## Что вы узнаете

Зададим компьютеру простой вопрос: «2024 год високосный?» Инструмент измерения сообщает, что на ответ ушло
несколько десятых наносекунды. Наносекунда — миллиардная доля секунды. На максимальной частоте нашего
процессора один «шаг» (такт) длится примерно 0,23 наносекунды. То есть ответ получен почти за один такт. Неужели
так быстро? Это ещё не доказательство, но подозрительно. В конце урока мы измерим и покажем: это число вовсе не
про високосный год.

**Одна идея:** правильность кода проверяет **тест**, скорость измеряет **бенчмарк**. Не доверяйте ни тому, ни
другому вслепую: не гадайте, измеряйте.

К концу урока вы:

- напишете тест и табличный тест с `go test` и запустите нужный подтест с помощью `-v` и `-run`;
- прочитаете сообщение упавшего теста, найдёте ошибку и после исправления заново проверите весь пакет;
- напишете бенчмарк с `b.Loop` и сможете прочитать столбцы `-benchmem` (`ns/op`, `B/op`, `allocs/op`);
- сможете разоблачить лгущий бенчмарк, сравнив его с пустым циклом.

Три главных новых слова урока:

| Слово | Простой смысл | По-английски |
|---|---|---|
| тест | маленькая программа: задаёт функции вопрос и сравнивает её ответ с ожидаемым | test |
| табличный тест | список, где в каждой строке один случай (имя, вход, ожидаемый ответ), и один цикл, который его обходит | table-driven test |
| бенчмарк | функция, которая много раз запускает код и измеряет, сколько времени и памяти уходит на один вызов | benchmark |

По пути встретятся ещё два вспомогательных слова: **подтест** (отдельный именованный тест для одной строки таблицы)
и **выделение памяти** (программа берёт из памяти новое место под новое значение). Объясним их там, где они
понадобятся.

<details>
<summary>Ответ</summary>

**Нет.** Программа скомпилировалась без ошибок и работала, только неправильно. `:=` внутри `if` создал новую

сами.

</details>

## План: сначала правильность, потом скорость

Сегодня ответим на два вопроса:

| Этап | Вопрос | Инструмент |
|---|---|---|
| 1 | Функция работает **правильно**? | `go test` (тест) |
| 2 | Насколько функция **быстрая**? | `go test -bench` (бенчмарк) |

Девиз в обоих случаях один: **не гадайте, измеряйте.**

## Первый тест

Для примера возьмём **високосный год**: год, в котором в феврале 29 дней. Первая попытка — одна строка: если год
делится на 4, он високосный. Это `sodda/kabisa.go` (*sodda* — «простой», *kabisa* — «високосный»):

```go filename="sodda/kabisa.go" showLineNumbers
package kabisa

// kabisa: yil kabisa yilimi? Birinchi, sodda urinish.
func kabisa(yil int) bool {
	return yil%4 == 0
}
```

| Строка | Код | Что делает |
|---|---|---|
| 1 | `package kabisa` | файл принадлежит пакету `kabisa`. На этот раз не `main`: это не самостоятельная программа, а набор функций, которые вызывает другой код |
| 3 | `// kabisa: …` | комментарий, Go его не читает |
| 4 | `func kabisa(yil int) bool {` | функция `kabisa`: принимает `yil` («год») типа `int`, возвращает `bool` (`true` или `false`) |
| 5 | `return yil%4 == 0` | `yil % 4` — остаток от деления на 4. Если остаток 0 — `true`, иначе `false` |

Правильна ли эта функция? Чтобы не проверять её каждый раз вручную, напишем маленькую программу. Вспомните, как
проверяют калькулятор: нажимаете `2 + 2` и ждёте `4`. Ожидаемый ответ известен заранее, вы сравниваете его с
ответом калькулятора. Маленькая программа, которая задаёт функции вопрос и сравнивает её ответ с ожидаемым,
называется **проверкой**, по-английски **test** — **тест**. Это `sodda/kabisa_test.go`:

```go filename="sodda/kabisa_test.go" showLineNumbers
package kabisa

import "testing"

func TestKabisa(t *testing.T) {
	if !kabisa(2024) {
		t.Errorf("kabisa(2024) = false, kutilgan true")
	}
}
```

| Строка | Код | Что делает |
|---|---|---|
| — | имя файла `kabisa_test.go` | имя **заканчивается на `_test.go`**. `go build` не включает такие файлы в программу, а `go test` находит и запускает их |
| 1 | `package kabisa` | тест лежит в том же пакете, поэтому видит функцию `kabisa` |
| 3 | `import "testing"` | пакет `testing`, который поставляется с Go: инструменты для тестов |
| 5 | `func TestKabisa(t *testing.T) {` | тестовая функция: имя начинается со слова **`Test`**, принимает `t` типа `testing.T`. `t` — «пульт» теста: через него мы сообщаем об ошибке. Знак `*` разберём в [GO-1.11](/lab/youtube/go#go-1-11) |
| 6 | `if !kabisa(2024) {` | `!` — «не»: если `kabisa(2024)` вернула `false`, заходим внутрь |
| 7 | `t.Errorf(…)` | пишет сообщение об ошибке и помечает тест как **упавший**, но **не останавливает** его: следующие строки тоже выполнятся. Сообщение по-узбекски: «…, ожидалось true» |

`t.Errorf` тест не останавливает. Если нужно остановить, есть `t.Fatalf`: он пишет сообщение и сразу завершает этот
тест.

Теперь запустим. `go test ./sodda` — «запусти тесты в папке `sodda`». Два дополнения:

- `-v` («verbose», подробно) — выводит имя и результат каждого теста;
- `-run TestKabisa` — выбирает только тесты, имя которых подходит под этот шаблон. Шаблон — regexp (образец для
  поиска в тексте); слова `TestKabisa` нет в имени `TestJadval`, поэтому тот не выбирается.

Предскажите: **A)** `PASS` (прошёл) · **B)** `FAIL` (упал) · **C)** ошибка компиляции

<details>
<summary>Ответ</summary>

**A: `PASS`.** Если разделить 2024 на 4, остаток 0: `kabisa(2024)` возвращает `true`. А `!true` — это `false`,
поэтому в `if` мы не заходим и `t.Errorf` не вызывается. Тест, в котором не записано ни одной ошибки, — прошедший
тест.

</details>

```console
$ go test -v -run TestKabisa ./sodda
=== RUN   TestKabisa
--- PASS: TestKabisa (0.00s)
PASS
ok  	github.com/abdurahmon27/go-backend-uz/lessons/007-test-bench/sodda	0.002s
```

| Строка | Смысл |
|---|---|
| `=== RUN   TestKabisa` | тест начался |
| `--- PASS: TestKabisa (0.00s)` | тест прошёл; в скобках затраченное время |
| `PASS` | все выбранные тесты пакета прошли |
| `ok  	…/sodda	0.002s` | полное имя пакета (имя модуля курса + папка) и общее время |

В последней строке вместо времени может появиться и `(cached)`. Если код не менялся, Go не запускает тест заново и
берёт прошлый результат из кэша (места, где он сохранён). Чтобы принудительно запустить тест заново, добавляют
`-count=1`.

Тест прошёл. Значит, функция правильная?

## Табличный тест: много случаев, один цикл

Одного примера мало. 2024 вышел правильно, а другие годы? Писать отдельную тестовую функцию для каждого года долго
и скучно. Вспомните школьный журнал: в каждой строке один ученик, в столбцах — его данные. Тесты пишем так же: в
каждой строке один случай — его имя, вход и ожидаемый ответ. А ниже один цикл проверяет все строки. Это обычный
путь в Go, **табличный тест** (по-английски **table-driven test**).

Ожидаемые ответы в таблице взяты из григорианского календаря. Его правило: если год делится на 4, он високосный;
но год, который делится на 100, високосный, только если делится и на 400. Это `sodda/jadval_test.go`
(*jadval* — «таблица»):

```go filename="sodda/jadval_test.go" showLineNumbers
package kabisa

import "testing"

func TestJadval(t *testing.T) {
	jadval := []struct {
		nom  string
		yil  int
		want bool
	}{
		{"oddiy", 2026, false},
		{"4 ga", 2024, true},
		{"100 ga", 1900, false},
		{"400 ga", 2000, true},
	}
	for _, tc := range jadval {
		t.Run(tc.nom, func(t *testing.T) {
			if got := kabisa(tc.yil); got != tc.want {
				t.Errorf("kabisa(%d) = %v, kutilgan %v", tc.yil, got, tc.want)
			}
		})
	}
}
```

| Строка | Код | Что делает |
|---|---|---|
| 6–10 | `jadval := []struct { nom string; yil int; want bool }` | описывает, как выглядит одна строка таблицы: `nom` («имя», текст), `yil` («год», число), `want` (`bool`, «ожидаемый ответ»). Тип, который собирает несколько именованных частей (полей) в одно значение, называется **struct**, разберём его в [GO-1.10](/lab/youtube/go#go-1-10). `[]` — список таких значений, то есть слайс ([GO-1.08](/lab/youtube/go/go-1-08/ru)) |
| 11–14 | `{"oddiy", 2026, false},` … | четыре строки таблицы: имя, год, ожидаемый ответ (*oddiy* — «обычный», *4 ga* — «на 4») |
| 16 | `for _, tc := range jadval {` | по очереди берёт каждую строку в `tc` (`tc` — «test case», то есть «случай») |
| 17 | `t.Run(tc.nom, func(t *testing.T) {` | `t.Run` запускает строку как отдельный тест с именем `tc.nom`. Второй аргумент — анонимная функция ([GO-1.06](/lab/youtube/go/go-1-06/ru)): код, проверяющий эту строку |
| 18 | `if got := kabisa(tc.yil); got != tc.want {` | записывает ответ функции в `got` («полученное») и сравнивает с ожидаемым |
| 19 | `t.Errorf("kabisa(%d) = %v, kutilgan %v", …)` | сообщение по шаблону: вместо `%d` — год, вместо `%v` — значения `got` и `want` в обычном виде (`true`/`false`) |

Отдельный тест, который открывает `t.Run`, называется **подтестом** (**subtest**). У каждого подтеста своё имя и
свой результат. Поэтому в сообщении видно, какой именно случай упал. Если нужен новый случай, вы добавляете в
таблицу одну строку, и всё: цикл и проверка не меняются.

Как идёт цикл:

| Круг | `tc.nom` | `tc.yil` | `tc.want` | `kabisa(tc.yil)` = `got` | Подтест |
|---|---|---|---|---|---|
| 1 | `oddiy` | 2026 | `false` | ? | `TestJadval/oddiy` |
| 2 | `4 ga` | 2024 | `true` | ? | `TestJadval/4_ga` |
| 3 | `100 ga` | 1900 | `false` | ? | `TestJadval/100_ga` |
| 4 | `400 ga` | 2000 | `true` | ? | `TestJadval/400_ga` |

Полное имя подтеста — имя теста, `/` и имя строки. Пробел в имени превращается в нижнее подчёркивание `_`.

`sodda/kabisa.go` по-прежнему проверяет только `yil%4 == 0`. Какой подтест упадёт? **A)** никакой ·
**B)** `100 ga` · **C)** `oddiy` и `100 ga`

<details>
<summary>Ответ</summary>

**B: `100 ga`.** Заполним `?` в таблице: 2026 → остаток 2 → `false` (ожидалось `false`, верно); 2024 → `true`
(верно); 1900 → при делении 1900 на 4 остаток 0 → `true`, а ожидалось `false`: **падает**; 2000 → `true` (верно).
Если вы выбрали «C»: 2026 не делится на 4, и простая функция тоже правильно отвечает `false`.

</details>

```console
$ go test ./sodda
--- FAIL: TestJadval (0.00s)
    --- FAIL: TestJadval/100_ga (0.00s)
        jadval_test.go:19: kabisa(1900) = true, kutilgan false
FAIL
FAIL	github.com/abdurahmon27/go-backend-uz/lessons/007-test-bench/sodda	0.002s
FAIL
```

На этот раз без `-v`: `go test` молчит о прошедших тестах и показывает только упавшие. Читаем сообщение снизу
вверх:

- `jadval_test.go:19:` — сообщение записано в файле `jadval_test.go`, строка 19, в `t.Errorf`;
- `kabisa(1900) = true, kutilgan false` — какой вход, что получилось, что ожидалось (*kutilgan* — «ожидалось»);
- `--- FAIL: TestJadval/100_ga` — какой подтест; пробел в `100 ga` превратился в `_`;
- `--- FAIL: TestJadval` — если упал хоть один подтест, весь `TestJadval` тоже считается упавшим;
- последние строки `FAIL` — пакет и вся команда завершились неудачей.

`TestKabisa` тоже запустился и прошёл, но без `-v` его не видно.

## 1900: григорианское правило и Excel

Правило ещё раз:

| Год | На 4? | На 100? | На 400? | Високосный? |
|---|---|---|---|---|
| 2024 | да | нет | — | ✅ да |
| 2026 | нет | — | — | ❌ нет |
| 1900 | да | да | нет | ❌ нет |
| 2000 | да | да | да | ✅ да |

То есть год, делящийся на 4, високосный, но если он делится на 100, он обязан делиться и на 400. Поэтому 2000 был
високосным, а 1900 — нет.

Эта ошибка есть и в известных программах. Согласно документации Microsoft, табличный процессор Lotus 1-2-3 считал
1900 год високосным: так программе было проще обрабатывать високосные годы. А Excel ради совместимости с ним
сохраняет эту ошибку до сих пор: в Excel 29 февраля 1900 года всё ещё «существует». Исправление сломало бы старые
расчёты: например, функция `WEEKDAY`, которая находит день недели, начала бы возвращать другой ответ для некоторых
дат.

## Исправление и запуск одного подтеста

Запишем правило в код. Это другая папка, исправленная версия: `kabisa/`. Тесты в ней такие же, как в `sodda/`,
отличается только функция. `grep` — инструмент, который находит и выводит строки файла, где есть заданное слово:

```console
$ grep return kabisa/kabisa.go
	return yil%4 == 0 && (yil%100 != 0 || yil%400 == 0)
```

Файл целиком:

```go filename="kabisa/kabisa.go" showLineNumbers
package kabisa

// kabisa: yil kabisa yilimi? Grigorian qoidasi:
// 4 ga boʻlinadi, lekin 100 ga boʻlinsa, 400 ga ham boʻlinishi shart.
func kabisa(yil int) bool {
	return yil%4 == 0 && (yil%100 != 0 || yil%400 == 0)
}
```

Строка 6 состоит из трёх частей: `&&` — «и», `||` — «или», `!=` — «не равно ли?». Часть в скобках вычисляется
первой: «не делится на 100 **или** делится на 400».

| Год | `yil%4 == 0` | `yil%100 != 0` | `yil%400 == 0` | Результат |
|---|---|---|---|---|
| 2026 | `false` | — | — | `false` |
| 2024 | `true` | `true` | — | `true` |
| 1900 | `true` | `false` | `false` | `false` |
| 2000 | `true` | `false` | `true` | `true` |

(`—` — Go эту часть даже не вычисляет: если левая сторона `&&` равна `false` или левая сторона `||` равна `true`,
ответ уже известен.)

Сначала запустим только упавший подтест. Косая черта `/` в `-run Jadval/100` отделяет имя теста от имени подтеста:
«среди тестов с `Jadval` в имени — подтест с `100` в имени».

```console
$ go test -v -run Jadval/100 ./kabisa
=== RUN   TestJadval
=== RUN   TestJadval/100_ga
--- PASS: TestJadval (0.00s)
    --- PASS: TestJadval/100_ga (0.00s)
PASS
```

## Защищаем tozala тестом

Теперь обещание из [GO-1.04](/lab/youtube/go/go-1-04/ru). Там мы написали функцию `tozala` («очистить»), которая приводит виды
апострофов к одному, и сказали: «защитите её тестом». Это `tozala/tozala.go`, функция из 4-го урока без изменений
(только без `main`):

```go filename="tozala/tozala.go" showLineNumbers
package tozala

import (
	"strings"
	"unicode"
)

// 004-darsdagi funksiya, oʻzgarishsiz.
// tozala apostrof turlarini bir xil qiladi:
// o/g dan keyin -> ʻ (U+02BB), boshqa harfdan keyin -> ʼ (U+02BC, tutuq belgisi).
// Faqat harfdan keyin turganlarini oʻzgartiradi: soʻz boshidagi ‘ qoʻshtirnoqqa tegmaydi.
func tozala(s string) string {
	r := []rune(s)
	for i := 1; i < len(r); i++ {
		if !strings.ContainsRune("'`´‘’ʻʼ", r[i]) || !unicode.IsLetter(r[i-1]) {
			continue
		}
		ogdan := strings.ContainsRune("oOgG", r[i-1])
		keyingiHarf := i+1 < len(r) && unicode.IsLetter(r[i+1])
		soz2 := i >= 2 && unicode.IsLetter(r[i-2]) // o/g soʻz boshida emas
		switch {
		case ogdan && (keyingiHarf || soz2): // oʻzbek, togʻ
			r[i] = 'ʻ'
		case keyingiHarf: // maʼno
			r[i] = 'ʼ'
		}
	}
	return string(r)
}
```

Краткое напоминание (каждая строка разобрана в [GO-1.04](/lab/youtube/go/go-1-04/ru)):

- строка 13: превращает текст в список рун, потому что `string` нельзя изменить на месте;
- строки 14–27: апостроф после буквы заменяет на `ʻ` после o/g и на `ʼ` между двумя буквами;
- строка 28: снова превращает список в текст и возвращает его.

Её табличный тест, `tozala/tozala_test.go`:

```go filename="tozala/tozala_test.go" showLineNumbers
package tozala

import "testing"

func TestTozala(t *testing.T) {
	jadval := []struct {
		nom, kirish, want string
	}{
		{"klaviatura", "O'zbekiston", "Oʻzbekiston"},
		{"jingalak", "tog’", "togʻ"},
		{"tutuq", "ma'no", "maʼno"},
		{"qoshtirnoq", "U ‘Salom’ dedi", "U ‘Salom’ dedi"},
	}
	for _, tc := range jadval {
		t.Run(tc.nom, func(t *testing.T) {
			if got := tozala(tc.kirish); got != tc.want {
				t.Errorf("tozala(%+q) = %+q, kutilgan %+q", tc.kirish, got, tc.want)
			}
		})
	}
}
```

Новые строки:

| Строка | Код | Что делает |
|---|---|---|
| 7 | `nom, kirish, want string` | все три поля типа `string` (*kirish* — «вход»): поля одного типа можно записать в одну строку |
| 9 | `{"klaviatura", "O'zbekiston", "Oʻzbekiston"}` | обычный апостроф с клавиатуры `'` |
| 10 | `{"jingalak", "tog’", "togʻ"}` | фигурный апостроф `’` (U+2019) в конце слова (*jingalak* — «фигурный», *togʻ* — «гора») |
| 11 | `{"tutuq", "ma'no", "maʼno"}` | место, где должен стоять знак тутук (знак разделения) |
| 12 | `{"qoshtirnoq", "U ‘Salom’ dedi", …}` | фраза в кавычках («Он сказал ‘Привет’»): она **не должна меняться** |
| 17 | `t.Errorf("tozala(%+q) = %+q, kutilgan %+q", …)` | `%+q` — выводит текст в кавычках, а символы вне ASCII — их номером Unicode (`’`) |

Зачем `%+q`? На экране `’` и `ʻ` выглядят почти одинаково, глаз их не различает. А `%+q` записывает их номерами:
`’` и `ʻ` — разница видна сразу. (ASCII — латинские буквы, цифры и простые символы с клавиатуры; `’` и
`ʻ` в него не входят.)

## Быстрый путь и вопрос на паузе

Теперь ускорим `tozala`. В некоторых текстах апострофа нет вовсе, например в числах, кодах или тексте на кириллице.
Зачем тогда превращать весь текст в руны? Новая `tozala` сначала проверяет: если апострофа нет, она возвращает
сам текст. Если есть, вызывает старую функцию из 4-го урока. Это `tez/tozala.go` (*tez* — «быстрый»):

```go filename="tez/tozala.go" showLineNumbers
package tozala

import "strings"

func tozala(s string) string {
	if !strings.Contains(s, "'") { // tez yoʻl: apostrof yoʻq
		return s
	}
	return tozalaEski(s)
}
```

| Строка | Код | Что делает |
|---|---|---|
| 6 | `if !strings.Contains(s, "'") {` | `strings.Contains` — есть ли в `s` символ `"'"`? `!` — «если нет» |
| 7 | `return s` | **быстрый путь:** возвращает сам текст, ничего не превращая |
| 9 | `return tozalaEski(s)` | иначе работает старая функция (*eski* — «старый») |

`tozalaEski` — это та самая `tozala` из 4-го урока, только с другим именем (в файле `tez/eski.go`). А тесты — те
же четыре строки из `tozala/tozala_test.go`.

**Вопрос:** пройдут ли все четыре теста из таблицы? Ещё раз посмотрите на строки таблицы.
**A)** да, все четыре · **B)** нет, упадёт `jingalak` · **C)** нет, упадёт `qoshtirnoq`

<details>
<summary>Ответ</summary>

**B: упадёт `jingalak`.** Быстрый путь ищет только клавиатурный апостроф `'`. А в `tog’` стоит фигурный `’`, а не
`'`. Поэтому функция «думает», что апострофа нет, и возвращает текст без изменений. Если вы выбрали «C»:
`U ‘Salom’ dedi` тоже возвращается быстрым путём, но эта фраза и не должна меняться, поэтому тест проходит.

| Случай | Есть `'`? | Какой путь | Результат | Тест |
|---|---|---|---|---|
| `klaviatura` | да | старый | `Oʻzbekiston` | ✅ |
| `jingalak` | **нет** (есть `’`) | **быстрый** | `tog’` (без изменений) | ❌ |
| `tutuq` | да | старый | `maʼno` | ✅ |
| `qoshtirnoq` | нет | быстрый | `U ‘Salom’ dedi` | ✅ |

</details>

Проверим обе папки одной командой: старую `tozala/` и новую `tez/`.

```console
$ go test ./tozala ./tez

--- FAIL: TestTozala (0.00s)
    --- FAIL: TestTozala/jingalak (0.00s)
        tozala_test.go:17: tozala("tog’") = "tog’", kutilgan "togʻ"
FAIL
```

Старая функция прошла, а быстрая версия упала на случае `jingalak`. Читаем сообщение: вход `"tog’"`, результат
тоже `"tog’"`, а ожидалось `"togʻ"`. `’` — фигурный апостроф, `ʻ` — знак для oʻ/gʻ. Если бы
сообщение было записано обычным `%q`, на экране стояли бы `"tog’"` и `"togʻ"`: различить их очень трудно (увидим
в «Частых ошибках»).

Такую ошибку не видно глазом, потому что на экране символы почти одинаковы. Без теста она тихо дошла бы до
пользователя.

## Исправление: strings.ContainsAny

Исправление: ищем не один символ, а все виды апострофа. `strings.ContainsAny(s, символы)` — «есть ли в `s`
хоть один из `символов`?». Это `tezfix/tozala.go`:

```console
$ grep ContainsAny tezfix/tozala.go
```

```go filename="tezfix/tozala.go" showLineNumbers

}
```

`` "'`´‘’ʻʼ" `` — ровно те семь символов, которые ищет старая функция. Теперь быстрый путь срабатывает, только когда

## Бенчмарк: измеряем скорость

Стало быстрее? Не гадаем, измеряем. Один вызов слишком короткий, его не измерить часами. Представьте забег: один шаг
секундомером не измерить, но можно измерить миллион шагов и разделить время на число шагов. Функция, которая так же
много раз запускает код и вычисляет, сколько времени ушло на один вызов, называется **измерением скорости**,
по-английски **benchmark** — **бенчмарк**.

Бенчмарк тоже пишется в тестовом файле. Это `tezfix/bench_test.go`:

```go filename="tezfix/bench_test.go" showLineNumbers
package tozala

import "testing"

var matnlar = []struct{ nom, s string }{
	{"toza", "Bugun havo yaxshi, darsdan keyin bozorga boramiz"},
	{"apostrof", "Oʻzbekiston togʻlari, maʼno va qoʻshiq"},
}

func BenchmarkEski(b *testing.B) {
	for _, m := range matnlar {
		b.Run(m.nom, func(b *testing.B) {
			for b.Loop() {
				tozalaEski(m.s)
			}
		})
	}
}

func BenchmarkTez(b *testing.B) {
	for _, m := range matnlar {
		b.Run(m.nom, func(b *testing.B) {
			for b.Loop() {
				tozala(m.s)
			}
		})
	}
}
```

| Строка | Код | Что делает |
|---|---|---|
| 5–8 | `var matnlar = []struct{ nom, s string }{…}` | два текста (*matnlar* — «тексты»): `toza` («чистый») — без апострофов, `apostrof` — с апострофами. Объявлены через `var` вне функции, поэтому их видят оба бенчмарка |
| 10 | `func BenchmarkEski(b *testing.B) {` | функция-бенчмарк: имя начинается с **`Benchmark`**, принимает `b` типа `testing.B` |
| 11 | `for _, m := range matnlar {` | для каждого текста |
| 12 | `b.Run(m.nom, func(b *testing.B) {` | как `t.Run`: открывает для каждого текста отдельный именованный бенчмарк (`BenchmarkEski/toza`, `BenchmarkEski/apostrof`) |
| 13 | `for b.Loop() {` | **измеряемый цикл.** `b.Loop()` спрашивает у Go «ещё круг?»: Go возвращает `true`, пока не наберёт достаточно кругов, потом `false` |
| 14 | `tozalaEski(m.s)` | измеряемый код: старая функция |
| 20–28 | `func BenchmarkTez…` | то же самое, но с новой `tozala` |

Сколько раз Go прокрутит цикл? Сколько нужно: обычно пока измерение в сумме не займёт одну секунду, но не больше
миллиарда (1 000 000 000) раз.

## Читаем результат: ns/op, B/op и allocs/op

Запускаем. Команда длинная, разберём её по частям:

| Часть | Смысл |
|---|---|
| `go test -bench .` | запусти и бенчмарки; `.` — «любое имя», то есть все |
| `-benchmem` | кроме времени, измерь и память |
| `./tezfix` | в папке `tezfix` |
| `\| grep ns/op` | `\|` (конвейер) передаёт вывод левой команды правой; `grep` оставляет только строки с `ns/op`, то есть строки с результатами |
| `\| column -t` | выравнивает строки по столбцам, чтобы было легче читать |

Нужно одно новое понятие. Старая `tozala` при каждом вызове создаёт новый список (`[]rune(s)`) и новый текст
(`string(r)`). Под них программа берёт новое место в памяти — как будто каждый раз вырывает новый лист из тетради.
Это называется **выделением памяти** (по-английски **allocation**). Оно занимает время, а потом Go ещё должен
убрать место, которое больше не используется.

Предскажите: сколько раз за вызов быстрая версия выделяет память на тексте `toza` без апострофов? **A)** 0 ·
**B)** 1 · **C)** 2

<details>
<summary>Ответ</summary>

**A: 0.** Апострофа нет, поэтому быстрый путь возвращает сам `s`: не создаются ни новый список, ни новый текст.
Если вы выбрали «C», вы имели в виду старую функцию: она каждый раз создаёт `[]rune(s)` и `string(r)`.

</details>

```console
$ go test -bench . -benchmem ./tezfix | grep ns/op | column -t
BenchmarkEski/toza-12      1908316  602.0  ns/op  256  B/op  2  allocs/op
BenchmarkEski/apostrof-12  1954908  619.8  ns/op  208  B/op  2  allocs/op
BenchmarkTez/toza-12       4480161  232.1  ns/op  0    B/op  0  allocs/op
BenchmarkTez/apostrof-12   1784139  694.1  ns/op  208  B/op  2  allocs/op
```

Столбцы (на примере первой строки):

| Столбец | Значение | Смысл |
|---|---|---|
| имя | `BenchmarkEski/toza-12` | имя бенчмарка и текста; `-12` — сколько ядер процессора Go может использовать одновременно (на этом компьютере 12) |
| круги | `1908316` | сколько раз прокрутился цикл `b.Loop` |
| `ns/op` | `602.0` | время на один вызов в наносекундах («op» — operation, один вызов) |
| `B/op` | `256` | сколько байт выделено за один вызов |
| `allocs/op` | `2` | сколько раз за один вызов выделялась память |

Что мы увидели:

- **На тексте такой длины старая версия при каждом вызове выделяет память дважды:** под список рун и под новый
  текст. (На очень коротком тексте, до 32 рун, отдельное место под список не выделяется, и тогда раз один.)
- **На тексте без апострофов быстрая версия не выделяет память ни разу** и в нашем запуске примерно в 2,6 раза
  быстрее (602,0 и 232,1 нс). В измерениях при подготовке урока разница была 2,4–2,9 раза: примерно в два-три раза.
- **На тексте с апострофами выигрыша нет:** обе выделяют память дважды, по 208 байт. Быстрая версия сначала ищет
  через `ContainsAny`, а потом всё равно вызывает старую функцию. В нашем запуске она вышла даже чуть медленнее;
  в измерении при подготовке урока обе были одинаковы (437 и 438 нс). Такая маленькая разница — шум.

В узбекском тексте апостроф есть почти в каждом предложении: в тексте видео этого урока — в двух предложениях из
трёх (в 75 из 108). Значит, это ускорение работает не везде. Наносекунды каждый раз немного меняются, а число
выделений памяти (`allocs/op`) и `B/op` — нет.

## Бенчмарк солгал: сравниваем с пустым циклом

Теперь вернёмся к загадке из начала. Это `kabisa/bn_test.go`. В нём два бенчмарка **в старом стиле**: так писали
бенчмарки до `b.Loop`. Оба — обычный цикл `for`, который считает до `b.N`. `b.N` — число кругов, которое выбрал Go.

```go filename="kabisa/bn_test.go" showLineNumbers
package kabisa

import "testing"

func BenchmarkBoshBN(b *testing.B) {
	for i := 0; i < b.N; i++ {
	}
}

func BenchmarkKabisaBN(b *testing.B) {
	for i := 0; i < b.N; i++ {
		kabisa(i)
	}
}
```

| Строка | Код | Что делает |
|---|---|---|
| 5–8 | `BenchmarkBoshBN` | **пустой** цикл (*bosh* — «пустой»): считает `i` от 0 до `b.N` и ничего не делает |
| 10–14 | `BenchmarkKabisaBN` | тот же цикл, но на каждом круге вызывается `kabisa(i)`. А её результат **нигде не используется** |

Число, которое мы видели в начале, было от `KabisaBN`. Вот оно:

```console
$ go test -bench KabisaBN ./kabisa | grep ns/op
BenchmarkKabisaBN-12    	1000000000	         0.2267 ns/op
```

Цикл прокрутился ровно миллиард раз (верхний предел Go), а на один вызов ушло 0,23 нс. На этом компьютере один
такт — примерно 0,23 нс: максимальная частота 4,4 ГГц. Это ещё не доказательство: процессор может крутить простой
цикл даже быстрее одного такта. Для доказательства запустим оба бенчмарка рядом (`-bench BN` — все бенчмарки, в
имени которых есть `BN`).

Предскажите: **A)** `KabisaBN` в несколько раз медленнее пустого цикла · **B)** оба почти одинаковы ·
**C)** пустой цикл медленнее

<details>
<summary>Ответ</summary>

**B: почти одинаковы.** Если бы проверка на високосность (три деления, сравнения) выполнялась, `KabisaBN` был бы
заметно медленнее. Одинаковое время значит, что оба цикла делают одну и ту же работу, то есть високосность вообще
не вычисляется. «A» — ответ, которого мы ждали, но нас обманули.

</details>

```console
$ go test -bench BN ./kabisa | grep ns/op
BenchmarkBoshBN-12      	1000000000	         0.1831 ns/op
BenchmarkKabisaBN-12    	1000000000	         0.2118 ns/op
```

Бенчмарк может лгать. Вот доказательство: цикл, в котором вызывается `kabisa`, показал почти то же время, что и
пустой цикл (0,18 и 0,21 нс; в измерениях при подготовке урока разница 7–20 %). То есть он измерил не
високосность, а ничегонеделание.

Посмотрим на машинный код, который выдал компилятор. Команда состоит из двух частей (`&&` — «если первая прошла
успешно, выполни вторую»):

- `go test -c -o k.test ./kabisa` — не запускает тесты, а только компилирует их в программу-файл `k.test`;
- `go tool objdump -s 'KabisaBN$' k.test` — выводит из этого файла машинный код (команды процессора) функции, имя
  которой заканчивается на `KabisaBN`;
- `awk 'NR>1 {print $4, $5, $6}'` — пропускает строку заголовка и оставляет из каждой строки только 4-е, 5-е и 6-е
  слово, то есть саму команду.

```console
$ go test -c -o k.test ./kabisa && go tool objdump -s 'KabisaBN$' k.test | awk 'NR>1 {print $4, $5, $6}'
XORL CX, CX
JMP 0x52e8c7 
INCQ CX 
CMPQ 0x210(AX), CX
JG 0x52e8c4 
RET  
```

| Команда | Смысл | Часть в Go |
|---|---|---|
| `XORL CX, CX` | обнулить регистр `CX` (ячейку внутри процессора) | `i := 0` |
| `JMP …` | перейти к проверке | — |
| `INCQ CX` | увеличить `CX` на 1 | `i++` |
| `CMPQ 0x210(AX), CX` | сравнить `CX` с `b.N` | `i < b.N` |
| `JG …` | если `b.N` больше, вернуться к `INCQ` | цикл продолжается |
| `RET` | выйти из функции | — |

В цикле только счётчик: увеличить, сравнить, вернуться. От проверки на високосность (`%4`, `%100`, `%400`) не
осталось ничего. Машинный код `BenchmarkBoshBN` — ровно те же шесть команд (отличаются только адреса).

Причина в двух шагах. Первый: компилятор делает **встраивание** маленькой функции (по-английски **inline**), то
есть вместо вызова копирует её тело (код внутри) на место вызова. Второй: увидев, что результат нигде не
используется, он полностью удаляет вычисление. Представьте повара: плов, который никто не будет есть, он даже не
готовит. Компилятор делает так, чтобы ускорить программу, но наше измерение осталось пустым.

## b.Loop: держим результат живым

`b.Loop`, добавленный в Go 1.24, это исправляет: он держит «живыми» аргументы и результаты вызовов внутри цикла, то
есть компилятор не может удалить их как ненужные. Это `kabisa/loop_test.go`: те же два бенчмарка, но с `b.Loop`:

```go filename="kabisa/loop_test.go" showLineNumbers
package kabisa

import "testing"

func BenchmarkBoshLoop(b *testing.B) {
	yil := 0
	for b.Loop() {
		yil++
	}
}

func BenchmarkKabisaLoop(b *testing.B) {
	yil := 0
	for b.Loop() {
		kabisa(yil)
		yil++
	}
}
```

| Строка | Код | Что делает |
|---|---|---|
| 5–10 | `BenchmarkBoshLoop` | «пустой» цикл: только увеличивает `yil`. Чтобы сравнение было честным, здесь тоже есть `yil++` |
| 13 | `yil := 0` | год создаётся один раз перед циклом |
| 15 | `kabisa(yil)` | вызывается на каждом круге; `b.Loop` сохраняет её аргумент и результат |
| 16 | `yil++` | на каждом круге год меняется |

В обоих год меняется на каждом круге. Каким будет результат?

```console
$ go test -bench Loop ./kabisa | grep ns/op
BenchmarkBoshLoop-12      	1000000000	         0.7043 ns/op
BenchmarkKabisaLoop-12    	850859284	         1.331 ns/op
```

- **Сам пустой цикл `b.Loop` тоже занимает немного времени** (здесь 0,70 нс). Это цена измерения: `b.Loop` на каждом
  круге проверяет свой счётчик.
- **Цикл с проверкой на високосность примерно в два раза медленнее** (1,33 нс, в 1,9 раза; в README курса в
  1,7–2,1 раза), потому что теперь выполняется настоящее вычисление. Собственная работа `kabisa` — разница между
  двумя числами.

| Бенчмарк | Что осталось в цикле | ns/op (у нас) |
|---|---|---|
| `BoshBN` | только счётчик | 0,18 |
| `KabisaBN` | только счётчик (`kabisa` удалена) | 0,21 |
| `BoshLoop` | счётчик `b.Loop` + `yil++` | 0,70 |
| `KabisaLoop` | счётчик `b.Loop` + `yil++` + **проверка на високосность** | 1,33 |

Одна тонкость: `b.Loop` сохраняет результат, но не запрещает компилятору вычислить его заранее. Если передать
постоянное число, например `kabisa(2024)`, ответ будет готов уже во время компиляции. Поэтому в наших бенчмарках год
меняется на каждом круге. Этот эксперимент ниже, в разделе «Глубже».

## Не верьте одному измерению

Последнее правило: не верьте одному измерению. Даже один и тот же бенчмарк каждый раз даёт немного другой результат,
особенно если компьютер занят чем-то ещё. Мы это видели сами: `BenchmarkEski/toza` на этой странице показал 602 нс
(компьютер был загружен), а при подготовке урока (2026-11-25) — 437 нс. А число выделений памяти в обоих случаях 2.

Когда сравниваете две версии:

| Правило | Как |
|---|---|
| минимум 10 раз | `-count 10` — запускает каждый бенчмарк 10 раз |
| смотрите на статистику | программа **benchstat** сравнивает два файла и говорит, реальна ли разница или случайна |
| если подозрительно быстро | как сегодня, сравните с пустым циклом |

Порядок работы из README курса (benchstat устанавливается отдельно; для этой страницы он не запускался):

```bash
go install golang.org/x/perf/cmd/benchstat@latest
go test -run '^$' -bench . -benchmem -count 10 ./tezfix > eski.txt   # oʻzgarishdan oldin
# ... kodni oʻzgartiring ...
go test -run '^$' -bench . -benchmem -count 10 ./tezfix > yangi.txt  # keyin
benchstat eski.txt yangi.txt
```

- `-run '^$'` — шаблон, который не подходит ни одному тесту: работают только бенчмарки, не тесты;
- `> eski.txt` — записывает вывод не на экран, а в файл (*eski* — «старый», *yangi* — «новый»; комментарии в
  коде: «до изменения», «измените код», «после»);
- `benchstat` даёт для каждого бенчмарка медиану (среднее по порядку значение) и доверительный интервал; знак `~`
  значит «статистической разницы нет».

«Запускать снова и снова, пока результат не понравится» — тоже ошибка: так вы примете случайную удачу за настоящую
разницу.

Сегодня мы увидели: тест проверяет правильность, бенчмарк измеряет скорость, и ни тому, ни другому нельзя верить
вслепую. На следующем уроке, [GO-1.08 · Слайсы: ловушка append](/lab/youtube/go/go-1-08/ru),
посмотрим, как растёт `append`, и измерим это сами, как сегодня.

## Глубже (необязательно): b.Loop — тоже не волшебство

В видео этому разделу посвящена одна фраза; эксперимент лежит в папке курса `doimiy/` (*doimiy* — «постоянный»). Это
`doimiy/bench_test.go` (а `doimiy/kabisa.go` совпадает с `kabisa/kabisa.go`):

```go filename="doimiy/bench_test.go" showLineNumbers
package kabisa

import "testing"

// Tajriba (README): doimiy argument. Go 1.26 kabisa'ni inline qilib,
// kabisa(2024) = true javobini kompilyatsiya paytida hisoblaydi.
// b.Loop natijani "tirik" saqlaydi, lekin hisobning oʻzi siklda qolmaydi.
func BenchmarkDoimiyLoop(b *testing.B) {
	for b.Loop() {
		kabisa(2024)
	}
}

// Har aylanishda boshqa yil: hisob haqiqatan bajariladi.
func BenchmarkKabisaLoop(b *testing.B) {
	yil := 0
	for b.Loop() {
		kabisa(yil)
		yil++
	}
}
```

Как узнать, есть ли проверка на високосность в машинном коде? Go вычисляет `% 100` не делением, а более быстрым
умножением (команда `IMULQ`). Значит, если есть `IMULQ`, есть и вычисление. `grep -c` выводит число подходящих строк.

```console
$ go test -c -o d.test ./doimiy
```

Эта команда ничего не вывела: она только создала файл `d.test`.

```console
$ go tool objdump -s 'BenchmarkDoimiyLoop$' d.test | grep -c IMULQ
0
```

```console
$ go tool objdump -s 'BenchmarkKabisaLoop$' d.test | grep -c IMULQ
1
```

В `DoimiyLoop` вычисления нет: Go 1.26.8 посчитал `kabisa(2024) = true` во время компиляции, и в цикле осталось только
сохранение готового `true`. А в `KabisaLoop` вычисление есть. `b.Loop` держит результат живым, но не запрещает
вычислить его заранее.

Ещё два факта:

- В Go 1.24 `b.Loop` запрещал встраивание внутри цикла. В Go 1.26 этот запрет сняли, а аргумент и результат
  сохраняются через `runtime.KeepAlive`. Мы проверяли только Go 1.26.8; в 1.24 этот эксперимент может дать другой
  результат.
- Код подготовки перед `b.Loop` (например, подготовка больших данных) выполняется только один раз и не входит во
  время: `b.Loop` сам управляет таймером. В старом стиле `b.N` функция бенчмарка вызывалась несколько раз.

## Частые ошибки

**1. «Тест прошёл — значит, код правильный».** Главная ловушка урока. `TestKabisa` прошёл с 2024, но функция
ошибалась на 1900 (видели в разделе «Табличный тест»). Тест проверяет только те вопросы, которые вы задали.
**Исправление:** добавляйте в таблицу и пограничные случаи: годы, делящиеся на 100 и на 400, пустой текст, все виды
апострофа.

**2. Бенчмарк в старом стиле, результат которого не используется.** `for i := 0; i < b.N; i++ { kabisa(i) }`
измеряет не високосность, а пустой цикл: компилятор удаляет вычисление (выше, в разделе «Бенчмарк солгал»).
Сообщения об ошибке нет, есть только подозрительно маленькое число. **Исправление:** пишите `for b.Loop() { … }`
и сравнивайте с пустым циклом.

**3. Имя тестового файла не заканчивается на `_test.go`.** Этого примера нет в папке курса, он запущен в отдельном
модуле. В папке `nomi/` лежат `sodda/kabisa.go` и файл `kabisatest.go` (без подчёркивания):

```go

		t.Errorf("kabisa(2024) = false, kutilgan true")
	}
}
```


*no test files* — «нет тестовых файлов». `go test` ищет тесты только в файлах, имя которых заканчивается на
`_test.go`. Хуже того: `kabisatest.go` теперь обычный файл, и пакет `testing` попал в саму программу.
**Исправление:** назовите файл `kabisa_test.go`.

**4. Строчная буква после `Test`.** (Нет в папке курса.) Вместо `TestKabisa` написано `Testkabisa`:

не компилятор, а `go vet`: перед тестами `go test` сам запускает часть проверок `go vet`. **Исправление:**

**5. В шаблоне `Errorf` забыт аргумент.** (Нет в папке курса.) В шаблоне есть `%d` (год) и `%v`, но год не передан:

*Errorf format %d has arg got of wrong type bool* — «в `%d` шаблона `Errorf` попал аргумент `got` неправильного

запустился (`build failed`). **Исправление:** `t.Errorf("kabisa(%d) = %v, kutilgan false", 1900, got)`.

**6. Для `-bench` не указан шаблон.** После `-bench` обязательно нужен шаблон, например `.`:

Цикл по байтам у нас примерно в 6 раз быстрее (в измерении из README ≈4,5 раза), обе версии не выделяют память,
тесты проходят. `ContainsAny` на наборе символов вне ASCII проверяет текст руну за руной, поэтому медленнее. Цена:
текст на кириллице (его байты больше `0x80`) теперь тоже уходит на медленный путь. У каждого ускорения свои границы,
поэтому мы измеряем.

</details>

🟠 **Сложно:** исправьте бенчмарк в старом стиле без `b.Loop`: запишите результат в переменную уровня пакета.

<details>
<summary>Ответ</summary>

`homework/qiyin/bench_test.go` (*natija* — «результат»):

```go
var natija bool

func BenchmarkSinkBN(b *testing.B) {
	for i := 0; i < b.N; i++ {
		natija = kabisa(i)
	}
}
```

Результат записывается в переменную вне функции и может быть виден из другого места. Поэтому компилятор не может
удалить вычисление.

```console
$ go test -bench . ./homework/qiyin | grep ns/op
BenchmarkKabisaBN-12      	1000000000	         0.2126 ns/op
BenchmarkSinkBN-12        	1000000000	         0.7216 ns/op
BenchmarkKabisaLoop-12    	904552358	         1.478 ns/op
```

`SinkBN` заметно медленнее пустого цикла (`KabisaBN`): вычисление теперь выполняется. Этот способ советовал Дейв Чейни
(Dave Cheney) в 2013 году; сегодня лучше `b.Loop`.

</details>
