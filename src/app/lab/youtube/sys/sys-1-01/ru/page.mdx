## Что вы узнаете

Компьютер берёт одно число из своей самой быстрой памяти. Потом ждёт ответа от сайта в интернете. Насколько
отличаются эти два действия? Если первое длится одну секунду, второе длится почти двенадцать лет. Этот расчёт мы
сделаем вместе в конце страницы.

**Одна идея:** у каждого действия внутри компьютера своё время ожидания, и эти времена отличаются в миллион раз.
Одно число из самой быстрой памяти процессора — ~1,5 нс, ответ сайта в интернете — ~0,55 с. Сегодня мы сами измерим
эти времена программой на Go и сравним с известной таблицей, которую программисты знают наизусть.

К концу урока вы:

- будете переводить нс, мкс и мс друг в друга и сможете прикинуть, на каком «этаже» находится действие;
- измерите медленное действие много раз через `time.Now` / `time.Since` и прочитаете медиану и диапазон;
- поймёте ошибку «записал в файл — значит, на диске» и узнаете цену `f.Sync()` (fsync);
- объясните по этапам, почему один HTTPS-запрос занимает сотни миллисекунд.

Три главных новых слова сегодня:

| Слово | Простой смысл | Английский термин |
|---|---|---|
| задержка | время от момента, когда программа что-то запросила, до прихода ответа | latency |
| кэш | маленькая и очень быстрая память внутри процессора | cache |
| обмен туда-обратно | время, пока короткое сообщение дойдёт до другого компьютера и вернётся ответ | round trip |

Есть и два вспомогательных слова. **SSD** — диск, который хранит данные и без электричества: движущихся частей нет,
только микросхемы. **fsync** — команда, которая говорит Linux «жди, пока данные дойдут до диска», в Go это `f.Sync()`.

## Единицы времени: мс, мкс, нс

Сегодняшние числа выходят в трёх единицах. Моргание длится от 100 до 400 миллисекунд (BioNumbers BNID 100706).

| Единица | Обозначение | Доля секунды | Пример (из сегодняшних замеров) |
|---|---|---|---|
| миллисекунда | ms (мс) | 1/1 000 | обмен туда-обратно через Wi-Fi ~5 мс |
| микросекунда | µs (мкс) | 1/1 000 000 | чтение 4 KiB с SSD ~120–150 мкс |
| наносекунда | ns (нс) | 1/1 000 000 000 | одно число из кэша ~1,5 нс |

Каждый шаг — в тысячу раз: 1 мс = 1000 мкс, 1 мкс = 1000 нс. В Go эти единицы есть в пакете `time`:
`time.Millisecond`, `time.Microsecond`, `time.Nanosecond`. Промежуток времени хранится в типе `time.Duration`. На
самом деле это число наносекунд (`int64`), но при печати он выглядит как `1.29ms`, `146µs`. Программы урока печатают
латинские обозначения (`ms`, `µs`, `ns`).

## Задержка (latency): от запроса до ответа

Когда во фронтенде вы пишете `await fetch(url)`, страница ждёт ответа. В Python `requests.get(url)` — так же. Это
ожидание бывает не только в сети: процессор ждёт, когда просит число из памяти, программа ждёт, когда читает файл с
диска.

В DSA-A.01 мы сравнивали память с карманом и складом. Вещь из кармана берёте сразу. За вещью со склада нужно
сходить. Сегодня добавим ещё один этаж: дальний архив, то есть диск. Ещё дальше — другой компьютер, через сеть.

| Этаж | Сравнение | Сегодняшний порядок |
|---|---|---|
| кэш (внутри процессора) | карман | наносекунды |
| оперативная память (RAM) | склад | ~100 нс |
| диск (SSD) | дальний архив | сотни микросекунд |
| сеть, интернет | отправить соседу вопрос и ждать ответа | миллисекунды, сотни мс |

Это время ожидания мы называем **задержкой**, по-английски **latency**. Задержка говорит, сколько *ждёт* одно
действие. Она не говорит, сколько действий выполняется за секунду (по-английски *throughput*, пропускная
способность). Это разные вещи: на уровне «Гуру» в домашнем задании увидим это на числах.

## Как измеряем: функция `olcha`

В JS время измеряют так:

```js
const boshi = performance.now();
await ish();
console.log(performance.now() - boshi); // миллисекунды, с дробной частью
```

В Python — `boshi = time.perf_counter()` и `time.perf_counter() - boshi`. В Go та же идея делается двумя функциями:
`time.Now()` смотрит на часы, `time.Since(boshi)` говорит, сколько прошло с начала. В видео сердце программы показано
в сокращённом виде:

```go
for i := range n {
	boshi := time.Now()
	ish(i)
	vaqt := time.Since(boshi)
	natija = append(natija, vaqt)
}
```

Строка 1 повторяет работу `n` раз. Строка 2 приклеивает текущее время к ярлыку `boshi` («boshi» — начало) (`:=` —
новая переменная). Строка 3 один раз выполняет измеряемую работу (`ish`, «работа»). Строка 4 берёт время, прошедшее
с начала. Строка 5 добавляет его в список `natija` («natija» — результат).

Настоящая функция в папке курса (из `olcha/main.go`, без изменений) чуть короче: ярлыка `vaqt` («время») нет.
`olcha` — «измерь»:

```go
// olcha: ishni n marta bajarib, har birining vaqtini yozib boradi.
func olcha(nom string, n int, ish func(i int)) natija {
	r := natija{nom: nom}
	for i := range n {
		boshi := time.Now()
		ish(i)
		r.t = append(r.t, time.Since(boshi))
	}
	return r
}
```

| Код | Что делает |
|---|---|
| `func olcha(nom string, n int, ish func(i int)) natija` | три параметра: имя замера (`nom`), сколько раз (`n`) и измеряемая работа. `ish` — значение-функция, как callback `(i) => {…}` в JS (GO-1.06). Результат — структура `natija` |
| `r := natija{nom: nom}` | пустой результат: имя есть, список времён пока пуст |
| `for i := range n` | `i` = 0, 1, …, n−1 (GO-1.05) |
| `boshi := time.Now()` | смотрит на часы. Внутри `time.Now()` в Go есть и монотонные часы: даже если системные часы подведут, `time.Since` останется верным (как `performance.now()` в JS) |
| `ish(i)` | вызывает измеряемую работу: например, чтение 4 KiB с SSD |
| `r.t = append(r.t, time.Since(boshi))` | добавляет прошедшее время (`time.Duration`) в конец списка (GO-1.08) |
| `return r` | возвращает все времена |

Почему много раз? Каждый раз результат немного другой: диск занят, в сети пакет задерживается. Одному замеру
доверять нельзя (правило GO-1.07). Поэтому работа повторяется от 30 до 5000 раз, потом времена сортируются:

```go
// natija: bitta o'lchovning hamma vaqtlari.
type natija struct {
	nom string
	t   []time.Duration
	yoq int // tarmoq: javobsiz qolgan urinishlar
}

// p: tartiblangan vaqtlarning q-qismi, eng yaqin o'rin bo'yicha (0.5 = mediana; juft n da yuqori o'rtadagi).
func (n natija) p(q float64) time.Duration {
	s := slices.Clone(n.t)
	slices.Sort(s)
	return s[int(q*float64(len(s)-1)+0.5)]
}
```

В структуре `natija` хранятся имя замера и все времена (`t`). `yoq` («нет») — сколько попыток в сети не получили
ответа за 3 секунды: к времени они не добавляются, их считают отдельно. Метод `p` берёт копию времён (`slices.Clone`:
чтобы не испортить исходный порядок), сортирует и возвращает элемент на доле `q`. Отсюда три столбца вывода:

| Столбец | Смысл | Как считается |
|---|---|---|
| `marta` («раз») | сколько раз измерили | `len(n.t)` |
| `odatda` («обычно») | **медиана**: середина отсортированного списка, половина результатов быстрее, половина медленнее | `p(0.5)` |
| `oraliq` («диапазон») | что осталось после отбрасывания 10 % самых быстрых и 10 % самых медленных | `p(0.1) … p(0.9)` |

Почему медиана, а не среднее? Одна сетевая попытка на 500 мс удваивает среднее из 99 попыток по 5 мс (с 5 мс до
~10 мс). Медиана же остаётся 5 мс. p50 / p90 / p99, которые вы видите в Grafana и APM-инструментах, — то же самое.

Одно важное ограничение: этот способ подходит только для действий **от микросекунды и медленнее**. Сам `time.Now()` на
этом ноутбуке стоит ~25 нс (измерим в разделе «Глубже»). Действие на 1,5 нс нельзя мерить поштучно часами за 25 нс:
для таких действий нужен цикл бенчмарка из GO-1.07.

## Кэш и оперативная память: карман и склад

**Кэш** — маленькая и очень быстрая память внутри процессора, наш карман. Оперативная память побольше — склад. В
DSA-A.01 мы измерили их методом цепочки. В этом уроке они **заново не измерялись**: числа из файла `natija.txt`
урока DSA-A.01 (медиана 10 замеров):

| Откуда | Размер | Одно чтение | Известная таблица |
|---|---|---|---|
| кэш L1 | 8 KiB | 1,52 нс | 0,5 нс |
| кэш L2 | 256 KiB | 4,23 нс | 7 нс |
| оперативная память | 128 MiB | 105,8 нс | 100 нс |

```text
процессор ──просит──▶ кэш (карман)              ~1,5 нс
                         │ если нет
                         ▼
               оперативная память (склад)       ~106 нс   ≈ в 70 раз дольше
```

1,52 нс — время, когда каждое чтение ждёт предыдущего, то есть настоящая *задержка*. Последовательные, независимые
друг от друга чтения быстрее: в DSA-A.01 из L1 — 0,31 нс на элемент. Но это не ожидание, а скорость потока. Сегодня
нас интересует ожидание, поэтому считаем от 1,52 нс.

## Диск: SSD и копия Linux

Диск — место, где данные сохраняются и без электричества, наш дальний архив. На этом ноутбуке диск — SSD: движущихся
частей нет, только микросхемы. А Linux держит копию прочитанного с диска файла в оперативной памяти. Эта копия
называется **страничный кэш** (page cache). Если то же место запросят снова, Linux не пойдёт на диск, а отдаст копию.

Программа читает 4 KiB двумя способами. Один раз напрямую с SSD: для этого файл открывается с флагом `O_DIRECT`,
который обходит копию Linux (open(2)). Другой раз обычным `os.Open`, из копии. Код (`olcha/main.go`, без изменений):

```go
func disk() {
	tayyorla()
	r := rand.New(rand.NewPCG(3, 4))

	// 1) SSD'dan 4 KiB, tasodifiy joydan. O_DIRECT xotiradagi nusxani (page cache) chetlab o'tadi:
	// har bir o'qish haqiqatan SSD'ga boradi.
	f, buf, err := ochDirect(*faylYoli, kb4)
	tekshir(err)
	chiqar(olcha("SSD'dan 4 KiB", 5000, func(int) {
		_, err := f.ReadAt(buf, int64(r.IntN(hajm/kb4))*kb4)
		tekshir(err)
	}))
	f.Close()

	// 2) Xuddi shu 4 KiB, oddiy open bilan: avval 16 MiB ni bir marta o'qiymiz,
	// Linux uni operativ xotirada nusxa qilib saqlaydi, keyingi o'qishlar nusxadan.
	g, err := os.Open(*faylYoli)
	tekshir(err)
	defer g.Close()
	_, err = g.ReadAt(make([]byte, 16*mib), 0)
	tekshir(err)
	b := make([]byte, kb4)
	chiqar(olcha("nusxadan 4 KiB", 5000, func(int) {
		_, err := g.ReadAt(b, int64(r.IntN(16*mib/kb4))*kb4)
		tekshir(err)
	}))
}
```

| Код | Что делает |
|---|---|
| `kb4`, `mib`, `hajm` | константы: 4 KiB, 1 MiB и размер тестового файла («hajm» — объём) 1 GiB |
| `tayyorla()` | («подготовь») создаёт 1 GiB `sinov.dat` из случайных байтов, если его ещё нет |
| `rand.New(rand.NewPCG(3, 4))` | генератор случайных чисел, каждый раз одна и та же последовательность (`math/rand/v2`) |
| `ochDirect(*faylYoli, kb4)` | `*faylYoli` — значение флага `-fayl` (по умолчанию `sinov.dat`; `*` читает значение через указатель). Функция открывает файл с `O_DIRECT` и даёт буфер 4 KiB. Она в файле `olcha/direct_linux.go`: `O_DIRECT` требует, чтобы адрес буфера был кратен 4096, поэтому буфер берётся через `syscall.Mmap` |
| `f.ReadAt(buf, int64(r.IntN(hajm/kb4))*kb4)` | читает из случайного места размером 4 KiB внутри 1 GiB. Случайное место — чтобы предыдущее чтение не помогало следующему |
| `g.ReadAt(make([]byte, 16*mib), 0)` | один раз читает первые 16 MiB файла: Linux кладёт их копию в оперативную память |
| `g.ReadAt(b, …16*mib/kb4…)` | теперь читает только внутри этих 16 MiB: все чтения — из копии |
| `tekshir(err)` | («проверь») при ошибке печатает сообщение и останавливает программу |

устройство выполнило +5066 чтений (5000 замеров и 16 MiB). Значит, да.

## Частая ошибка: «записал в файл — значит, на диске»

Многие программисты думают так: `write` вернулся, значит, данные на диске. На самом деле Linux сначала кладёт данные
на склад, то есть в копию в оперативной памяти. А на диск пишет позже, когда ему удобно. Если в это время пропадёт
электричество, данные могут потеряться. Документация write(2) говорит об этом прямо: «A successful return from
write() does not make any guarantee that data has been committed to disk» (успешный `write` не гарантирует, что
данные записаны на диск).

```text
программа: f.WriteAt(b, joy)
   │
   ▼
оперативная память (склад)  ◀── WriteAt возвращается здесь. Пропадёт питание — данные могут потеряться
   │  позже (Linux выбирает сам)
   ▼
SSD (архив)                 ◀── f.Sync() ждёт до этого места
```

Чтобы дождаться, пока данные дойдут до диска, есть отдельная команда: **fsync**. В Go это `f.Sync()`: она «фиксирует
текущее содержимое файла в постоянном хранилище» (документация `os.File.Sync`). В других языках она тоже есть: в Node
`fs.fsync(fd)`, в Python `os.fsync(f.fileno())` (документация Python: сначала `f.flush()`, потому что у файла Python
есть свой буфер), в PHP с 8.1 — `fsync($f)`. Сравнение из видео: обычная запись — бросить письмо в почтовый ящик, а
fsync — донести письмо до адресата и вернуться с подписью.

В видео код сокращён до двух строк:

```go
f.WriteAt(b, joy)
f.Sync()
```

`WriteAt` записывает в файл `f` байты `b` по позиции `joy` («место»). `f.Sync()` ждёт, пока диск не ответит
«записал». Полная функция в папке курса:

```go
func fsync() {
	f, err := os.Create("fsync.dat")
	tekshir(err)
	defer os.Remove("fsync.dat")
	defer f.Close()
	b := make([]byte, kb4)
	for i := range 256 { // 1 MiB joy: keyin shu joyga qayta-qayta yozamiz
		_, err := f.WriteAt(b, int64(i)*kb4)
		tekshir(err)
	}
	tekshir(f.Sync())

	chiqar(olcha("4 KiB yozish", 2000, func(i int) {
		_, err := f.WriteAt(b, int64(i%256)*kb4)
		tekshir(err)
	}))
	chiqar(olcha("4 KiB yozish + fsync", 300, func(i int) {
		_, err := f.WriteAt(b, int64(i%256)*kb4)
		tekshir(err)
		tekshir(f.Sync()) // Linux'da fsync(2): ma'lumot diskka yetib borguncha kutadi
	}))
}
```

| Код | Что делает |
|---|---|
| `os.Create("fsync.dat")` | новый файл. `defer os.Remove` и `defer f.Close` закроют и удалят его, когда функция закончится |
| `for i := range 256 { f.WriteAt(b, …) }` | готовит место 256 × 4 KiB = 1 MiB; потом пишем в это же место снова и снова |
| `tekshir(f.Sync())` | доводит подготовку до диска: до начала замера всё уже на диске |
| `"4 KiB yozish", 2000` | обычная запись («yozish» — запись), 2000 раз |
| `"4 KiB yozish + fsync", 300` | запись и каждый раз `f.Sync()`, 300 раз (медленнее, поэтому меньше) |
| `int64(i%256)*kb4` | `%` — остаток от деления: позиция идёт по кругу 0, 1, …, 255, 0, 1, … |

Прикиньте. Обычная запись идёт на склад (наносекунды), а fsync доходит до архива и ждёт ответа (сотни микросекунд).
Во сколько раз запись с fsync медленнее?

**A)** в 10 раз · **B)** в 100 раз · **C)** в 1000 раз

<details>
<summary>Ответ</summary>

**C: даже больше чем в тысячу раз.**

```console

o'lchov                 marta   odatda   oraliq
4 KiB yozish             2000    660ns   579ns … 941ns
4 KiB yozish + fsync      300   1.62ms   1.52ms … 2.12ms
```

Обычная запись — 660 нс, меньше микросекунды. С fsync — 1.62 мс: в 2455 раз. В видео было 732 нс и 1.29 мс: в 1762
раза. За 5 утренних раундов соотношение менялось от 219 до 2104 раз: обычная запись сильно разбросана (0,67–6,2 мкс).
Но каждый раз — в сотни или тысячи раз. Это диск этого ноутбука. Серверные диски с защитой от пропадания питания
выполняют fsync намного быстрее (README курса). Если вы выбрали «A» или «B», вы думали, что обычная запись тоже идёт

Поэтому некоторые базы данных собирают несколько записей и делают для них один fsync. PostgreSQL называет это
*group commit* (настройка `commit_delay`: «позволяет большему числу транзакций зафиксироваться одним сбросом WAL»).
На уровне «Средний» в домашнем задании вы измерите это сами.

## Сеть: обмен туда-обратно (round trip)

Сеть — путь, который связывает компьютеры проводом или радиоволной. Один компьютер отправляет короткое сообщение,
другой возвращает ответ. Время от отправки сообщения до прихода ответа — **обмен туда-обратно**, по-английски
**round trip** (сокращённо RTT). `time=…ms`, который показывает `ping`, — это оно.

Программа измеряет обмен туда-обратно через TCP-соединение. Соединение начинается так: ноутбук отправляет пакет SYN,
другая сторона отвечает SYN-ACK (RFC 9293 §3.5). Это один полный обмен туда-обратно. Утром ноутбук был подключён к
телефону через Wi-Fi, интернет шёл с телефона. Программа подключается к шлюзу сети Wi-Fi (default gateway, утром —
телефон) на порт 53:

```go
func tarmoq() {
	// Wi-Fi orqali routergacha (bizda: telefon hotspot'i). TCP ulanish = SYN ketadi, SYN-ACK qaytadi:
	// bitta borib-kelish.
	addr := *lanAddr
	if addr == "" {
		gw, err := gateway()
		tekshir(err)
		addr = net.JoinHostPort(gw, "53")
	}
	ulan(addr) // isitish: hisobga kirmaydi
	chiqar(olchaTarmoq("Wi-Fi: borib-kelish", 100, func() bool { return ulan(addr) }))
}

// ulan: TCP ulanish o'rnatib, darhol yopadi (vaqtni olchaTarmoq o'lchaydi).
// Port yopiq bo'lsa, qurilma SYN'ga RST bilan javob beradi ("connection refused"):
// bu ham bitta to'liq borib-kelish. 3 soniyada javob kelmasa (paket yo'qoldi), false.
func ulan(addr string) bool {
	c, err := net.DialTimeout("tcp", addr, 3*time.Second)
	if errors.Is(err, syscall.ECONNREFUSED) {
		return true
	}
	var ne net.Error
	if errors.As(err, &ne) && ne.Timeout() {
		return false
	}
	tekshir(err)
	c.Close()
	return true
}
```

| Код | Что делает |
|---|---|
| `gateway()` | находит адрес шлюза в `/proc/net/route` (Linux) |
| `ulan(addr) // isitish` | первая попытка («isitish» — прогрев) не учитывается: чтобы «пробуждение» радио Wi-Fi не испортило замер |
| `olchaTarmoq(…, 100, …)` | как `olcha`, 100 раз, пауза 100 мс между попытками; попытка без ответа не добавляется к времени, а считается отдельно |
| `net.DialTimeout("tcp", addr, 3*time.Second)` | TCP-соединение: уходит SYN, возвращается SYN-ACK. Нет ответа за 3 секунды — пакет потерян |
| `errors.Is(err, syscall.ECONNREFUSED)` | если порт закрыт, устройство отвечает RST («connection refused»). Это тоже полный обмен туда-обратно, поэтому `true` |
| `c.Close()` | сразу закрывает соединение: нам нужно только время соединения |

## Интернет: сколько обменов туда-обратно внутри одного запроса

Теперь настоящий интернет. `head -3` показывает только первые три строки вывода (SYS-0.01):

```console
$ go run ./olcha internet | head -3
o'lchov                 marta   odatda   oraliq
internet: borib-kelish     30    144ms   92.5ms … 164ms
sahifa so'rovi             10    529ms   450ms … 643ms
```

Вторая строка: один обмен туда-обратно (TCP-соединение) до сервера Google, который отвечает за go.dev, — 144 мс. В
видео было 128 мс. До шлюза было ~5 мс: остальное — путь после него, через сеть провайдера (утром — мобильного
оператора) и интернет до сервера. Где находится сервер, мы не измеряли: в заголовке ответа есть только
`server: Google Frontend`.

Третья строка: запрашиваем маленький файл `https://go.dev/robots.txt`, каждый раз с новым соединением. 529 мс (в
видео 555 мс). Это в 3,7 раза дольше одного обмена туда-обратно. Почему? Один запрос на самом деле состоит из четырёх
этапов:

| Этап | Что происходит | Обмен туда-обратно |
|---|---|---|
| поиск адреса (DNS) | имя `go.dev` превращается в числовой IP-адрес | один, но к близкому серверу (утром ответ шёл с телефона) |
| соединение (TCP) | SYN → SYN-ACK | один, до сервера |
| шифрование (TLS) | стороны договариваются шифровать данные так, чтобы посторонние не могли их прочитать | в TLS 1.3 один (RFC 8446 §2) + вычисления |
| ожидание ответа | запрос уходит, приходит первый байт ответа | один + работа сервера |

В браузере вы видели это в DevTools → Network → один запрос → вкладка **Timing**: «DNS Lookup», «Initial
connection», «SSL», «Waiting for server response». В Go те же этапы даёт пакет `net/http/httptrace`. Код (часть
функции `internet` в `olcha/main.go`):

```go
		iz := &httptrace.ClientTrace{
			// DNS: go.dev nomidan IP manzilni topish
			DNSStart: func(httptrace.DNSStartInfo) { dns0 = time.Now() },
			DNSDone:  func(httptrace.DNSDoneInfo) { dD = time.Since(dns0) },
			// TCP: ulanish (bitta borib-kelish)
			ConnectStart: func(string, string) { tcp0 = time.Now() },
			ConnectDone:  func(string, string, error) { tD = time.Since(tcp0) },
			// TLS: shifrlangan kanal haqida kelishish
			TLSHandshakeStart: func() { tls0 = time.Now() },
			TLSHandshakeDone:  func(tls.ConnectionState, error) { sD = time.Since(tls0) },
			// so'rov yuborilgandan javobning birinchi baytigacha
			WroteRequest:         func(httptrace.WroteRequestInfo) { yubordi = time.Now() },
			GotFirstResponseByte: func() { jD = time.Since(yubordi) },
		}
```

`httptrace.ClientTrace` — набор функций (хуков), которые `http.Client` вызывает в начале и в конце каждого этапа.
Каждая пара измеряет один этап через `time.Now()` и `time.Since()`: `dD` — DNS, `tD` — TCP, `sD` — TLS, `jD` — от
отправки запроса до первого байта (`iz` — «след», trace; `yubordi` — «отправил»). Другие части функции:
`DisableKeepAlives: true` делает каждый запрос с новым соединением, `"tcp4"` использует только IPv4, а первый запрос
отбрасывается как прогрев (загружаются сертификаты).

Полный вывод:

```console
$ go run ./olcha internet
o'lchov                 marta   odatda   oraliq
internet: borib-kelish     30    150ms   90.4ms … 164ms
sahifa so'rovi             10    547ms   447ms … 683ms
  manzil topish            10   14.2ms   7.98ms … 22.8ms
  ulanish                  10    153ms   89.2ms … 157ms
  shifrlash                10    152ms   114ms … 216ms
  javob kutish             10    285ms   223ms … 308ms
```

Сравните числа между собой. Обмен туда-обратно — 150 мс. Соединение (`ulanish`, 153 мс) — один обмен. Шифрование
(`shifrlash`, 152 мс) — ещё один. Ожидание ответа (`javob kutish`, 285 мс) — один обмен и работа сервера. Поиск
адреса (`manzil topish`) — всего 14 мс: ответ пришёл с близкого сервера. Каждая строка — отдельная медиана,
поэтому в сумме они не дают ровно 547. В видео этапы были 13 / 121 / 154 / 261 мс: картина та же.

Вывод: запрос в интернет медленный, потому что внутри него несколько обменов туда-обратно. Повторное использование

## Если растянуть до человеческого времени

Обещанный расчёт. Растянем каждое время в одно и то же число раз: пусть одно число из кэша (1,52 нс) станет одной
секундой. Делим каждое время на 1,52 нс:

| Действие | Видео | Растянуто | Наш повторный замер | Растянуто |
|---|---|---|---|---|
| одно число из кэша | 1,52 нс | 1 секунда | (не перемерялось) | 1 секунда |
| одно число из оперативной памяти | 106 нс | ~70 секунд (1 минута) | (не перемерялось) | ~70 секунд |
| 4 KiB с SSD | 146 мкс | ~27 часов (1 день) | 119 мкс | ~22 часа |
| обмен туда-обратно по Wi-Fi | 4,89 мс | ~37 дней (1 месяц) | 5,69 мс | ~43 дня |
| обмен туда-обратно в интернете | 128 мс | ~2,7 года | 144 мс | ~3,0 года |
| ответ сайта (новое соединение) | 555 мс | ~11,6 года | 529 мс | ~11,0 года |

Если число из кэша — одна секунда, ответ сайта — одиннадцать-двенадцать лет. В два разных времени дня, в двух разных
сетях Wi-Fi — числа другие, но лестница та же. Это и есть сегодняшняя одна идея.

Практический совет: если программа медленная, сначала посчитайте, сколько раз она ходила на диск и в сеть. Один
`fsync` или одно новое HTTPS-соединение дороже миллионов операций процессора.

## Глубже (необязательно): наносекундные действия, keep-alive и разброс диска

**Как измерять наносекундные действия.** Сколько стоит сам `time.Now()`? Поштучно его не измерить, поэтому нужен цикл
бенчмарка из GO-1.07 (`b.Loop()`). Пакет `xotira/` («память») в папке курса измеряет три вещи:

```go filename="xotira/xotira_test.go" showLineNumbers
// Nanosekund darajasidagi amallar: ularni bittalab soat bilan o'lchab bo'lmaydi,
// shuning uchun GO-1.07 dagi kabi benchmark sikli ishlatiladi (b.Loop).
//
//	taskset -c 2 go test -run '^$' -bench . -count 10 ./xotira
//
// Kesh va operativ xotiradan bitta o'qish (L1, L2, RAM) bu yerda qayta o'lchanmaydi:
// ular DSA-A.01 darsida o'lchangan (../dsa-a01-cache, Zanjir benchmark'i).
package xotira

import (
	"sync"
	"testing"
	"time"
)

// time.Now() ning o'zi qancha turadi? Shu sababli 1 ns lik amalni bittalab o'lchamaymiz.
func BenchmarkVaqt(b *testing.B) {
	var t time.Time
	for b.Loop() {
		t = time.Now()
	}
	_ = t
}

// Hech kim raqobat qilmayotgan mutex: Lock + Unlock juftligi.
func BenchmarkMutex(b *testing.B) {
	var mu sync.Mutex
	for b.Loop() {
		mu.Lock()
		mu.Unlock()
	}
}

const (
	mb    = 1 << 20    // 1 MiB
	katta = 512 << 20  // 512 MiB: L3 (12 MiB) dan ancha katta
	el    = mb / 8     // 1 MiB dagi int64 soni
	nKat  = katta / mb // nechta 1 MiB lik bo'lak
)

var yigindi int64

// 1 MiB ni ketma-ket o'qish (qo'shish), har safar keyingi bo'lakdan:
// 512 MiB aylanib chiqquncha bitta bo'lak keshda qolmaydi, demak o'qish operativ xotiradan.
func BenchmarkMegabayt(b *testing.B) {
	s := make([]int64, katta/8)
	for i := range s {
		s[i] = int64(i)
	}
	var y int64
	k := 0
	for b.Loop() {
		bolak := s[k*el : (k+1)*el]
		for _, v := range bolak {
			y += v
		}
		k = (k + 1) % nKat
	}
	yigindi = y
}
```

| Строка | Код | Что делает |
|---|---|---|
| 17–23 | `BenchmarkVaqt` | («время») в цикле только `time.Now()`: цена одного взгляда на часы |
| 26–32 | `BenchmarkMutex` | пара `Lock` + `Unlock` у `sync.Mutex`, за который никто не конкурирует (мьютекс — в GO-1.22) |
| 34–39 | `const (…)` | 1 MiB, 512 MiB и производные числа. `<<` — сдвиг влево: `1 << 20` = 2²⁰ = 1 048 576 |
| 45–59 | `BenchmarkMegabayt` | каждый раз последовательно складывает следующий кусок 1 MiB из слайса 512 MiB. 512 MiB не помещаются в кэш (L3 12 MiB), значит, чтение идёт из оперативной памяти |
| 58 | `yigindi = y` | записывает результат в переменную пакета: чтобы компилятор не выбросил цикл как ненужный |

выросли в два-три раза (`time.Now` 38–76 нс, мьютекс 18–35 нс): поэтому `jadval` показывает для мьютекса 20.7 нс.
При измерении задержки нагрузка — тоже часть задержки.

погрешность часов 0,02 %.

**Keep-alive.** Наш замер `internet` каждый раз открывает новое соединение (`DisableKeepAlives: true`). Настоящий
`http.Client` оставляет соединение открытым и использует его снова: в следующем запросе нет DNS, TCP и TLS, только
«ожидание ответа». Измерено в предыдущей версии программы (журнал исследования, мы не перезапускали): с открытым
соединением ~0,28–0,34 с, с новым — ~0,7–0,8 с. Поэтому в Go не создавайте `http.Client` заново на каждый запрос:
используйте один клиент повторно.

**Разброс диска.** Выше мы видели: на только что созданном файле SSD — 73 мкс, через минуту — 119 мкс. В утренних
замерах было так же (68–81 мкс → 116–145 мкс). Причина не изучена (может быть кэш внутри SSD, но это не проверено).
В таком случае показывайте не одно число, а диапазон и несколько замеров.

## Частые ошибки

**1. «Записал в файл — значит, на диске» (тихая ошибка).** Никакой ошибки не выводится. Если пропадёт питание или
упадёт сервер, последние записи могут потеряться (раздел «Частая ошибка»). **Исправление:** после важных данных
делайте `f.Sync()` и проверяйте его ошибку. Цена ~1–2 мс, поэтому собирайте много записей и делайте один fsync
(домашнее задание, «Средний»).

**2. `go run main.go` запускает один файл.** Если указать файл из папки по имени:

```console
$ go run olcha/main.go disk
# command-line-arguments
olcha/main.go:188:17: undefined: ochDirect
```

*undefined: ochDirect* — «`ochDirect` не определена». `olcha/main.go:188:17` — файл, строка, столбец. Функция
`ochDirect` лежит в другом файле той же папки, в `direct_linux.go`. Если дать имя файла, Go собирает только этот файл.
**Исправление:** передавайте пакет папкой: `go run ./olcha disk`.

**3. Забыли выбрать замер.** Если не передать аргумент:

```console
$ go run ./olcha
ishlatish: go run ./olcha disk|fsync|tarmoq|internet|hammasi
exit status 2
```

«ishlatish» — usage, «использование»: программа говорит, каких слов ждёт, и выходит с кодом 2 (`os.Exit(2)`). Строку
`exit status 2` добавляет `go run`. **Исправление:** `go run ./olcha disk` (или `fsync`, `tarmoq`, `internet`,
`hammasi`).

**4. Мерить наносекундное действие поштучно через `time.Now()` (тихая ошибка).** Результат выйдет, но это цена часов
(~25 нс), а не действия. **Исправление:** цикл бенчмарка (`b.Loop()`, GO-1.07), раздел «Глубже».

**5. Доверять одному замеру или среднему (тихая ошибка).** Сеть за несколько минут меняется в 10 раз (4–5 мс и больше
100 мс). Одна медленная попытка портит среднее. **Исправление:** мерьте много раз, показывайте медиану и p10 … p90,
повторяйте в нескольких раундах (`olchov.sh` делает 5 раундов).

**6. Доверять строке «SSD» в macOS или Windows (тихая ошибка).** `O_DIRECT` есть только в Linux. В другой системе
`olcha/direct_other.go` открывает файл обычно, и строка «SSD'dan» может на самом деле мерить копию: выйдут не
микросекунды, а наносекунды. **Исправление:** делайте замер диска в Linux.

**7. Сравнивать Wi-Fi с дата-центром.** «Мы в 10 раз медленнее известной таблицы» — неверный вывод: 500 мкс в таблице —
для сети внутри одного здания. **Исправление:** прежде чем сравнивать, проверьте, *что* измеряли оба числа.

## Проверьте себя

Сначала ответьте сами, потом откройте.

**1.** Какое место из сегодняшних замеров самое быстрое и сколько оно стоит?

<details>
<summary>Ответ</summary>

Кэш процессора: одно число ~1,5 нс (DSA-A.01, L1, метод цепочки). Оперативная память ~в 70 раз дольше (~106 нс).

</details>

**2.** «Записал в файл — значит, на диске». Верно?

<details>
<summary>Ответ</summary>

Нет. `write` (в Go `f.Write` / `f.WriteAt`) кладёт данные в копию в оперативной памяти и возвращается. Что данные
дошли до диска, сообщает специальная команда вроде fsync (в Go `f.Sync()`). У нас она была в 1762–2455 раз медленнее
обычной записи.

</details>

**3.** Почему один HTTPS-запрос в интернете в 3–4 раза дольше одного обмена туда-обратно?

<details>
<summary>Ответ</summary>

Потому что внутри него несколько обменов туда-обратно: TCP-соединение (один), согласование TLS (в TLS 1.3 один),
запрос и ответ (один + работа сервера), а перед ними ещё поиск адреса (DNS). Повторное использование открытого
соединения (keep-alive) убирает первые три.

</details>

**4.** Программа пишет 1000 записей и после каждой делает `f.Sync()`. Сколько примерно это займёт на этом ноутбуке?

**A)** ~1 мс · **B)** ~1–2 секунды · **C)** ~1 минуту

<details>
<summary>Ответ</summary>

**B.** Одна запись + fsync у нас — 1.29–1.62 мс: 1000 × ~1,5 мс ≈ 1,5 секунды. Без fsync — 1000 × ~0,7 мкс ≈ 0,7 мс
(«A» — программа, которая забыла fsync). Если делать один fsync на 10 записей, по замеру из домашнего задания —
~0,2 секунды.

</details>

**5.** Из GO-1.07: почему пару Lock + Unlock у `sync.Mutex` (~11 нс) не меряют поштучно через `time.Now()` /
`time.Since()`?

<details>
<summary>Ответ</summary>

Потому что сам `time.Now()` стоит ~25 нс: часы дороже измеряемого действия. Цикл бенчмарка выполняет действие
миллионы раз и делит общее время на их число (`ns/op`), так цена часов исчезает. Мы измерили это в пакете `xotira/`
через `b.Loop()`: 11.4 нс.

</details>

```go
// guruh: ma'lumotlar bazalaridagi "group commit" g'oyasi: bir nechta yozuv, bitta fsync.
func guruh() {
	f, err := os.Create("guruh.dat")
	tekshir(err)
	defer os.Remove("guruh.dat")
	defer f.Close()
	b := make([]byte, 4096)
	const n = 300
	for _, k := range []int{1, 10} { // k ta yozuvdan keyin bitta fsync
		t0 := time.Now()
		for i := range n {
			_, err := f.WriteAt(b, int64(i%256)*4096)
			tekshir(err)
			if (i+1)%k == 0 {
				tekshir(f.Sync())
			}
		}
		d := time.Since(t0)
		fmt.Printf("%2d ta yozuvga 1 fsync: bitta yozuvga %v\n", k, (d / n).Round(time.Microsecond))
	}
}
```

`k` — после скольких записей один fsync: сначала 1, потом 10. `(i+1)%k == 0` — на каждой `k`-й записи. Общее время
300 записей делится на 300. Результат: fsync на каждую запись — 1.77 мс/запись, один на 10 записей — 226 мкс/запись,
~в 8 раз быстрее (README: в трёх замерах в 5–19 раз). Это идея *group commit* в базах данных: цена в основном в
fsync, а не в числе записей. Плата: перед одним fsync под угрозой 10 записей — если пропадёт питание, они потеряются
вместе.

🟠 TCP localhost: 6.6 мкс, Unix domain socket: 2.8 мкс — в 2,3 раза быстрее (README: в трёх замерах в 1,4–2,7 раза).
Сетевая карта не используется, но слой TCP (пакеты, подтверждения) всё равно работает; Unix-сокет его обходит. В любом
случае это в тысячу раз быстрее ~5 мс по Wi-Fi.

🔴 1 горутина: одно чтение 116 мкс, 3472 в секунду. 32 горутины: одно чтение 223 мкс (в 2 раза медленнее), но
84 072 в секунду (в 24 раза больше). NVMe SSD выполняет много запросов параллельно. Задержка (latency) и число
действий в секунду (throughput) — разные вещи: одно может ухудшаться, когда другое улучшается.
