## What you will learn

Your team has a year of standup notes: 12 text files, 360 lines. A finished job is written plainly, an open job starts
with `TODO`. The question: how many jobs has Aziz not closed yet? You could write a small script in Python or Node.
Today we get the answer without a script, by connecting three small commands in the terminal.

**One idea:** if we connect small commands, each doing one job, step by step with a vertical bar (a pipe), they answer
a big question without a script: `grep` filters, `wc -l` counts, just like `filter().filter().length` in JavaScript.

By the end of the lesson you will:

- find the lines you need in every file of a folder with `grep -r`, and read the `file path:line` form of its output;
- count lines with `|` and `wc -l`, and add a new filter stage in the middle;
- remove the last stage of a pipeline to check the intermediate result;
- explain why giving a folder or `-r` to the `grep` after a pipe silently gives a wrong number.

The three core new words of this lesson:

| Word | Plain meaning | English term |
|---|---|---|
| `grep` | filters lines: passes a line that contains the pattern as a whole, drops the rest | grep |
| `wc -l` | counts the lines it receives and prints one number | wc (word count), `-l` = lines |
| vertical bar `\|` | gives the output of the command on the left to the input of the command on the right | pipe |

There are also two helper words: **standard input** (stdin) — where a command reads data from when no file is given;
**stderr** — a separate output for error messages (only in the "Going deeper" section). A **pattern** is the text
`grep` searches for; today it is a plain word: `TODO`, `Aziz`.

Before we start, one question in a language you already know. An array has four lines:

```js
const qatorlar = [
  "Aziz: saytga logo qoʻydi",
  "TODO Aziz: menyuni tuzatish",
  "Malika: narxlarni yangiladi",
  "TODO Malika: rasmlarni kichraytirish",

qatorlar.filter((q) => q.includes("TODO")).filter((q) => q.includes("Aziz")).length;
```

(`qatorlar` means "lines"; the notes are in Uzbek: "put the logo on the site", "fix the menu", "updated the prices",

**A)** `1` · **B)** `2` · **C)** `4`

<details>
<summary>Answer</summary>

**A: `1`.** The first `filter` keeps the two lines with `TODO`, the second keeps those with `Aziz`, and `length`

a `TODO`. Today we build exactly this chain in the terminal.

</details>

## From a JavaScript chain to the terminal

In JavaScript you would write this question like this: filter the array of lines for `TODO`, then for `Aziz`, and
finally take `length`. In the terminal, each step has one command:

| JavaScript | Terminal | What it does |
|---|---|---|
| `.filter(q => q.includes("TODO"))` | `grep TODO` | keeps the lines with the pattern |
| `.filter(q => q.includes("Aziz"))` | `grep Aziz` | filters again |
| `.length` | `wc -l` | counts the lines |
| `.` (the chain) | `\|` (vertical bar) | gives the output of one step to the next |

For comparison, here is the same question for the `eslatmalar/` folder in Node. This file is not in the course
folder: save it in the lesson folder as `zanjir.js` ("chain") and run it with Node 24.

```js
// zanjir.js: xuddi shu savol JavaScript'da (Node 24)
const fs = require("fs");

const qatorlar = fs.readdirSync("eslatmalar")
  .flatMap((f) => fs.readFileSync(`eslatmalar/${f}`, "utf8").trimEnd().split("\n"));

const javob = qatorlar
  .filter((q) => q.includes("TODO"))
  .filter((q) => q.includes("Aziz"))
  .length;

console.log(javob);
```

| Line | Code | What it does |
|---|---|---|
| 4–5 | `readdirSync` + `flatMap(…split("\n"))` | reads every file in the folder and collects one array of lines |
| 7–10 | `.filter(…).filter(…).length` | the lines with `TODO`, then those with `Aziz`, then their count (`javob` = "answer") |
| 12 | `console.log(javob)` | prints the number |

```console
$ node zanjir.js
3
```

That is a 12-line program. In the terminal one line gives the same answer:
`grep -r TODO eslatmalar | grep Aziz | wc -l`. Now we build it step by step.

## A production line: the pipe

Think of a pipe as a production line. Each stage does one job and puts its result on the next belt. The first stage
reads from the warehouse, that is, from the folder. The following stages read only from the belt in front of them.

In the terminal, a **stage** is a command, and a **belt** is the vertical bar `|`. In English it is called a **pipe**.
The whole chain is called a **pipeline**.

```text
 warehouse (folder)       belt (|)             belt (|)
 ┌────────────┐      ┌──────────────┐     ┌────────────┐     ┌───────────┐
 │ eslatmalar/│ ───► │ grep -r TODO │ ──► │ grep Aziz  │ ──► │  wc -l    │ ──► screen
 └────────────┘      │   filters    │     │  filters   │     │  counts   │
                     └──────────────┘     └────────────┘     └───────────┘
                      stage 1:             stage 2:            stage 3:
                      reads the folder     reads the belt      reads the belt
```

There is a difference from an array chain, and it matters:

| | JavaScript `filter().length` | Terminal pipeline |
|---|---|---|
| What a stage is | a method call inside one program | a separate program (a separate process) |
| When it runs | in turn: first the whole new array is built, then the next method | all stages run at the same time |
| What is passed | an array (objects, with types) | a stream of text: bytes, split into lines |

The shell starts each command of a pipeline in a separate process, and they run at the same time. The data flows as a
**stream** through a small buffer in the kernel (POSIX §2.9.2, bash(1), pipe(7)). The third row, "only text", will
matter twice in this lesson.

## Stage 1: `grep`

The first stage is `grep`. It filters lines: it passes a line that contains the pattern as a whole and drops the rest.

```console
$ grep -r TODO eslatmalar
eslatmalar/seshanba.txt:TODO Bobur: zaxira nusxa olish
eslatmalar/seshanba.txt:TODO Aziz: mijozga javob yozish
eslatmalar/chorshanba.txt:TODO Malika: biz haqimizda matni
eslatmalar/chorshanba.txt:TODO Aziz: telefon raqamini tekshirish
eslatmalar/dushanba.txt:TODO Aziz: menyuni tuzatish
eslatmalar/dushanba.txt:TODO Malika: rasmlarni kichraytirish
```

Don't look at the output yet. First we take the command apart:

| Part | What it is |
|---|---|
| `grep` | the name of the command (the program) |
| `-r` | a **flag**: read the folder recursively, every file inside it (like `-g` in npm) |
| `TODO` | the pattern: the text to search for |
| `eslatmalar` | where to read from: a folder |

`grep` is case-sensitive: if you write the pattern as `todo`, nothing is found (we see this in "Common mistakes").

Now a question. Here `grep` reads three files. What does each line of the output look like?

**A)** only the line itself · **B)** the file path, a colon, then the line · **C)** only the file names

<details>
<summary>Answer</summary>

**B.** Look at the output above: six lines came out, two from Monday. Each line starts with the file path
(`eslatmalar/dushanba.txt`), and after the colon comes the line itself. When several files are read, `grep` shows
which file a line comes from in this way (GNU grep manual, `-H`: "This is the default when there is more than one
file to search").

If you chose "A", you were thinking of `grep` on one file: `grep TODO eslatmalar/dushanba.txt` does print only the
lines. "C" is a different flag, `grep -l`, which prints only the file names.

</details>

The output went to the screen because there is no next stage. The order of the files may be different on your
machine: `grep -r` reads files in the order the file system gives them (here Tuesday, Wednesday, Monday).

## Stage 2: `wc -l`

The second stage is `wc -l`. `wc` means *word count*, and with the `-l` flag it gives only the number of lines. We
connect it with a vertical bar:

```text
grep -r TODO eslatmalar  |  wc -l
└────── stage 1 ──────┘  │  └─ stage 2: no file given → reads the belt
                        belt
```

We do not give `wc` a file. When no file is given, it reads what comes through the vertical bar. This input of a
command is called **standard input** (**stdin** for short). wc(1): "With no FILE … read standard input".

What appears on the screen now?

**A)** the same 6 lines · **B)** one number: `6` · **C)** one number: `13`

<details>
<summary>Answer</summary>

**B: `6`.** The lines from `grep` went onto the belt, not to the screen. `wc -l` counted them and printed only the
number.

If you chose "A", you skipped over the `|`: the lines now go to `wc`, not to the screen. "C", `13`, is the number of
all lines in the folder. But `wc` did not read the folder; it counts only what comes on the belt.

</details>

```console
$ grep -r TODO eslatmalar | wc -l
6
```

Where could `13` come from? From `wc` reading every file. `cat` prints files one after another, and `*.txt` means
every `.txt` file in the folder:

```console
$ cat eslatmalar/*.txt | wc -l
13
```

## A new stage in the middle: `grep Aziz`

Now the main question: Aziz's jobs. Like the second `filter` in JavaScript, we put one more `grep` in the middle,
with the pattern `Aziz`. We give it neither `-r` nor a folder: it takes its lines from the belt. Three stages, two
vertical bars.

Which number appears on the screen? Remember the six lines from before.

**A)** `6` · **B)** `3` · **C)** `5`

<details>
<summary>Answer</summary>

**B: `3`.** There were six `TODO` lines on the belt, and three of them contain `Aziz`.

If you chose "A", you thought the second `grep` drops nothing. "C", `5`, is **all** of Aziz's records, including the
finished ones. That number comes from a different command; we see it in "Common mistakes".

</details>

First we remove `wc -l` to see what is on the belt:

```console
$ grep -r TODO eslatmalar | grep Aziz
eslatmalar/seshanba.txt:TODO Aziz: mijozga javob yozish
eslatmalar/chorshanba.txt:TODO Aziz: telefon raqamini tekshirish
eslatmalar/dushanba.txt:TODO Aziz: menyuni tuzatish
```

Three lines, all of them Aziz's `TODO` lines. This is a handy way to check a pipeline: remove the last stage and
look at the intermediate result. It is like putting a `console.log` in the middle of a JavaScript chain. Now we put
`wc -l` back:

```console
$ grep -r TODO eslatmalar | grep Aziz | wc -l
3
```

What is on each belt:

| Place | What is there | Lines |
|---|---|---|
| warehouse: `eslatmalar/` | all lines of the three files | 13 |
| belt 1: after `grep -r TODO eslatmalar` | the `TODO` lines (with the file path) | 6 |
| belt 2: after `grep Aziz` | Aziz's `TODO` lines | 3 |
| screen: after `wc -l` | one number | `3` |

The Node script `zanjir.js` also said `3`.

## Order matters: `wc -l` in the middle

What if we swap the order of the stages: `wc -l` in the middle, `grep Aziz` at the end?

```text
grep -r TODO eslatmalar | wc -l | grep Aziz
```

What appears on the screen?

**A)** `3` · **B)** `6` · **C)** nothing

<details>
<summary>Answer</summary>

**C: nothing.** `wc -l` puts only one line on the belt: `6`. The last `grep` does not find the pattern `Aziz` in that
line and prints nothing.

If you chose "A", you thought the order of the stages does not matter. If you chose "B", you forgot the last `grep`:
`6` is on the belt, but it does not pass the `grep Aziz` filter.

</details>

```console
$ grep -r TODO eslatmalar | wc -l | grep Aziz
```

The command printed nothing: no number, no error. Let's remove the last `grep`:

```console
$ grep -r TODO eslatmalar | wc -l
6
```

`wc` put one line on the belt: `6`. `grep Aziz` finds nothing in it. (When `grep` finds nothing, its exit code is
1, but it writes nothing to the screen.)

In JavaScript, calling `filter` after `length` gives you a TypeError (in Node 24:
`TypeError: [1,2].length.filter is not a function`). The terminal stays silent, because the belt carries only text,
there are no types: `6` is just a line of text. Order matters: filter first, count after.

## The folder for a whole year

Now the question from the start: the folder for a whole year. What do we need to change in the pipeline? Think about
it before you go on.

Only the folder name: `yil` instead of `eslatmalar`.

```console
$ grep -r TODO yil | grep Aziz | wc -l
22
```

Aziz has 22 open jobs. We went through 12 files with a one-line command. To be sure, the size of the folder (`ls`
lists the files of a folder, each on its own line, because the output goes into a pipe):

```console
$ ls yil | wc -l
12
```

```console
$ cat yil/* | wc -l
360
```

```console
$ grep -r TODO yil | wc -l
93
```

12 files, 360 lines, 93 `TODO`s. The `yil/` folder is generated by `yasash.py` in the course folder (the result is
always the same). In it, every `TODO` is a separate job, and it is never written as "done". So `22` really is the
number of open jobs.

## Going deeper (optional): errors don't go onto the belt

One more subtle point. Every program has two outputs: the main output (*standard output*, **stdout**) and a separate
stream for error messages, **stderr**. It is the same as the difference between `console.log` and `console.error` in
Node: `console.error` also writes to stderr. A plain vertical bar carries only the main output.

If we add a folder that does not exist (`arxiv`, "archive"), what will `wc -l` say? Think first.

```console
$ grep -r TODO eslatmalar arxiv | wc -l
grep: arxiv: No such file or directory
6
```

The error stayed on the screen. `wc` still says `6`: the error line did not go onto the belt and was not counted. So a
pipeline can show an error and still give the right number. Ways to put errors onto the belt too (`2>&1 |`, or `|&`
in bash) are in the "Chuqurroq" part of the course README and in later lessons.

## Common mistakes

### 1. Giving a folder to the `grep` after a pipe

This is the most common mistake. What if, out of habit, we also write `-r` and the folder name for the second `grep`?

```text
grep -r TODO eslatmalar | grep -r Aziz eslatmalar | wc -l
```

**A)** still `3` · **B)** more than `3` · **C)** `0`

<details>
<summary>Answer</summary>

**B: `5`.** A `grep` that is given a file or a folder does not look at the belt; it goes back to the warehouse. It
reads the folder from the start and prints all of Aziz's records, the finished ones too. `wc` then counts them.

</details>

```console
$ grep -r TODO eslatmalar | grep -r Aziz eslatmalar | wc -l
5
```

There is no error message; the number is simply wrong. You can see what the second `grep` really printed without the
last stage. It reads the folder, not the belt, so its output is the same as this:

```console
$ grep -r Aziz eslatmalar
eslatmalar/seshanba.txt:Aziz: tugma rangini oʻzgartirdi
eslatmalar/seshanba.txt:TODO Aziz: mijozga javob yozish
eslatmalar/chorshanba.txt:TODO Aziz: telefon raqamini tekshirish
eslatmalar/dushanba.txt:Aziz: saytga logo qoʻydi
eslatmalar/dushanba.txt:TODO Aziz: menyuni tuzatish
```

Three `TODO`s and two finished jobs: 5. The work of the first `grep` was wasted. The rule is written in `grep --help`:
"With no FILE, read '.' if recursive, '-' otherwise" (`-` is standard input).

**The rule:** give the stage after a vertical bar neither `-r` nor a folder. The correct version:

```console
$ grep -r TODO eslatmalar | grep Aziz | wc -l
3
```

### 2. Only `-r`, no folder

Removing the folder but keeping `-r` does not work either: `grep -r` without a file reads the **current folder**
(`.`), not the belt.

```console
$ grep -r TODO eslatmalar | grep -r Aziz | wc -l
112
```

`112` is the number of `Aziz` lines in every file of the lesson folder (`yil/` too, and the README). This number
depends on what is in the folder; yours may differ. What matters: it is not `3`, and there is no error.

### 3. Only the folder, no `-r`

The opposite case: a folder but no `-r`. This time `grep` gives an error:

```console
$ grep -r TODO eslatmalar | grep Aziz eslatmalar | wc -l
grep: eslatmalar: Is a directory
0
```

How to read it: `grep:` means `grep` wrote the error; `eslatmalar: Is a directory` means "`eslatmalar` is a folder":
without `-r`, `grep` does not read folders. Nothing went onto the belt, so `wc` said `0`. The fix is the same: remove
the folder too.

### 4. A pattern in lowercase

```console
$ grep -r todo eslatmalar | wc -l
0
```

No error, just `0`. `grep` is case-sensitive: the files contain `TODO`, not `todo`. Write the pattern as it is in the
file. (To ignore case there is `grep -i`.)

### 5. The terminal is in another folder

If you run the command outside the lesson folder (for example, in your home folder):

```console
$ grep -r TODO eslatmalar | wc -l
grep: eslatmalar: No such file or directory
0
```

"`eslatmalar`: no such file or folder". This command was run outside the lesson folder. The fix:
`cd go-backend-uz/lessons/sys-01-terminal` (or check where you are with `pwd`).

### 6. `wc -l` in the middle

`… | wc -l | grep Aziz` prints nothing and gives no error: only `6` is left on the belt. We saw this in the "Order
matters" section. The fix: filter first, count after: `… | grep Aziz | wc -l`.

### 7. The terminal "hangs"

If you write `grep Aziz` on its own (with no vertical bar before it and no folder), `grep` waits for standard input,
that is, the keyboard. The terminal seems not to respond. Press **Ctrl+C**: it stops the running command.

## Check yourself

1. What does the vertical bar `|` do?

<details>
<summary>Answer</summary>

It gives the output (stdout) of the command on the left to the input (stdin) of the command on the right. The output
goes to the next stage, not to the screen.

</details>

2. Why don't we give a folder (or `-r`) to the `grep` after a vertical bar?

<details>
<summary>Answer</summary>

If it gets a folder or `-r`, `grep` does not look at the belt: it reads the folder (or the current folder) again. The
filter of the previous stage is lost, and the number is silently wrong (`5` or `112`, not `3`).

</details>

3. Why does the terminal give no error when `wc -l` is in the middle, while JavaScript gives a TypeError?

<details>
<summary>Answer</summary>

The belt carries only text, there are no types. `wc -l` puts the plain text line `6` on the belt, and the next `grep`
filters it like any other line and finds nothing. In JavaScript, `length` returns a number, and a number has no
`filter` method.

</details>

`1`. Of the six `TODO` lines, only one is Bobur's (`seshanba.txt`).

```console
eslatmalar/seshanba.txt:TODO Bobur: zaxira nusxa olish
```

```console
$ grep -r TODO eslatmalar | grep Bobur | wc -l

```

</details>

<details>
<summary>Answer</summary>

`grep` is reading several files (`-r` reads all three files in the folder). In that case it writes which file each

</details>
