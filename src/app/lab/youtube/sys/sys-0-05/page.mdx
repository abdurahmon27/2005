## Nimani oʻrganasiz

Bitta Go server va ikkita Docker image. Birining hajmi 969 MB, ikkinchisiniki 8.36 MB. Ikkalasini ishga tushirib,
soʻrov yuboramiz: javob aynan bir xil. Farq Dockerfile'dagi bir necha qatorda. Dastur nega sizda ishlaydi-yu,
serverda yiqiladi? Va nega `docker stop` baʼzan 10 soniya osilib, keyin 137 qaytaradi?

**Bitta gʻoya:** image — dastur va u ishlashi uchun kerak boʻlgan hamma narsa yigʻilgan oʻzgarmas paket. Container —
shu paketdan ishga tushgan oddiy Linux jarayoni. Shuning uchun image'ga faqat ishga tushish uchun kerak narsani
qoʻyamiz, port va maʼlumotni esa container ishga tushganda ulaymiz.

Dars oxirida siz:

- Go servisi uchun multi-stage Dockerfile yozasiz va image'ni 969 MB dan 8.36 MB ga tushirasiz;
- `CGO_ENABLED=0` nega kerakligini va `exec /server: no such file or directory` xatosini oʻqishni bilasiz;
- container'ni `-p` (port) va `-v` (volume) bilan ishga tushirasiz va container oddiy jarayon ekanini `ps` bilan
  koʻrsatasiz;
- `docker stop` 10 soniya kutib 137 qaytarsa, sababini topasiz va bitta soʻz (`exec`) bilan tuzatasiz.

Bugungi uchta asosiy yangi soʻz:

| Soʻz | Oddiy maʼnosi | Inglizcha |
|---|---|---|
| image | dastur, uning fayllari va qaysi buyruq ishga tushishi yigʻilgan oʻzgarmas paket | image |
| container | image'dan ishga tushgan jarayon, ustida oʻzining yoziladigan qatlami bor | container |
| volume | Docker boshqaradigan papka: container oʻchsa ham maʼlumot qoladi | volume |

Ikkita yordamchi soʻz ham bor. **Multi-stage build** — bir nechta bosqichli Dockerfile: birinchi bosqichda yigʻamiz,
oxirgisiga faqat tayyor binary'ni olamiz. **Namespace** — yadroning jarayonga «oʻz» PID raqamlarini, tarmogʻini va
fayllarini koʻrsatish usuli.

## Ikki image, bitta javob

`docker image ls` yigʻilgan image'larni koʻrsatadi. `--format` bilan faqat nom, teg va hajmni qoldiramiz
(`{{.Size}}` — Go'ning `text/template` shabloni: Docker `--format` da Go shablonlarini ishlatadi):

```console
$ docker image ls mehmon --format 'table {{.Repository}}:{{.Tag}}\t{{.Size}}'
REPOSITORY:TAG   SIZE
mehmon:kichik    8.36MB
mehmon:bir       969MB
```

`mehmon:bir` («bir» — bitta bosqich) 969 MB, `mehmon:kichik` («kichik») 8.36 MB. 116 baravar farq. Endi ikkalasini
navbat bilan ishga tushirib, soʻrov yuboramiz:

```console
$ for t in bir kichik; do docker run -d --rm --name sinov -p 8078:8077 mehmon:$t >/dev/null; sleep 0.3; echo -n "$t: "; curl -s localhost:8078; docker rm -f sinov >/dev/null; done
bir: Salom! Siz 1-mehmonsiz
kichik: Salom! Siz 1-mehmonsiz
```

| Qism | Nima qiladi |
|---|---|
| `for t in bir kichik; do …; done` | bash sikli: `t` avval `bir`, keyin `kichik` |
| `docker run -d --rm --name sinov` | image'dan container ishga tushiradi: fonda (`-d`), toʻxtaganda oʻchiriladi (`--rm`), nomi `sinov` («sinov») |
| `-p 8078:8077` | xostdagi 8078-portni container ichidagi 8077-portga ulaydi («Port» boʻlimida batafsil) |
| `>/dev/null` | `docker run -d` chiqaradigan uzun container ID'sini yashiradi |
| `sleep 0.3` | serverga ishga tushish uchun 0.3 soniya beradi |
| `echo -n "$t: "` | image nomini qator oxirisiz chiqaradi |
| `curl -s localhost:8078` | serverga soʻrov yuboradi |
| `docker rm -f sinov` | container'ni majburan toʻxtatib oʻchiradi |

Javob bir xil: ikkalasida ham bitta va oʻsha server. Bu darsda 969 MB qayerdan kelganini, uni qanday olib
tashlashni va 8 MB'lik image'ni qanday toʻgʻri ishga tushirishni koʻramiz.

## «Menda ishlaydi»: dasturga koddan tashqari nima kerak

Nega dastur sizda ishlaydi-yu, serverda yiqiladi? GO-1.01 da Go binary'si static ekanini koʻrgan edik: uni boshqa
Linux serverga koʻchirish oson. Lekin dasturni **yigʻish** uchun aniq Go versiyasi va baʼzan C kutubxonalari kerak.
**Ishga tushirish** uchun esa port, muhit oʻzgaruvchilari va maʼlumot papkasi kerak.

| Nima kerak | Bizning serverda | Qayerda farq qilishi mumkin |
|---|---|---|
| Go versiyasi | Go 1.26.8 | CI'da Go 1.22 turgan boʻlsa, boshqa natija |
| C kutubxonalari | libc (cgo yoqilgan boʻlsa) | boʻsh serverda yoki boʻsh image'da libc yoʻq |
| muhit oʻzgaruvchilari | `PORT`, `DATA` | serverda boshqa qiymat yoki umuman yoʻq |
| maʼlumot papkasi | `/data` | papka yoʻq yoki yozib boʻlmaydi |

Sizda bularning hammasi bor. Hamkasbingizda yoki serverda esa boshqacha boʻlishi mumkin. Node'da `.nvmrc` va
`package-lock.json`, Python'da `requirements.txt` va venv kutubxona versiyalarini mahkamlaydi. Lekin ular tizim
kutubxonalarini, muhitni va papkalarni mahkamlamaydi. Docker dasturni shu muhit bilan birga bitta paketga yigʻadi.
Bu paketning nomi — **image**.

## Bugungi server: `mehmon`

Image ichiga nima qoʻyishimizni koʻramiz. `server/` papkasida kichik HTTP server bor. U har bir mehmonni faylga
yozadi va nechanchi ekanini aytadi. Uchta fayl, bitta `main` paketi.

```go filename="server/main.go" showLineNumbers
package main

import (
	"fmt"
	"net"
	"net/http"
	"os"
)

func main() {
	port := os.Getenv("PORT") // sozlama muhitdan (SYS-0.02)
	if port == "" {
		port = "8077"
	}
	dir := os.Getenv("DATA") // mehmonlar daftari shu papkada
	if dir == "" {
		dir = "data"
	}
	if err := os.MkdirAll(dir, 0o755); err != nil {
		fmt.Println("server:", err)
		os.Exit(1)
	}
	ln, err := net.Listen("tcp", ":"+port)
	if err != nil {
		fmt.Println("server:", err)
		os.Exit(1)
	}
	srv := &http.Server{Handler: daftar(dir)}
	go srv.Serve(ln)
	fmt.Println("server: :" + port + " da tinglayapman")
	kut(srv)
}
```

| Qator | Kod | Nima qiladi |
|---|---|---|
| 5 | `"net"` | tarmoq paketi. Bugun u muhim: cgo yoqilganda `net` C kutubxonasiga bogʻlanadi («Savol» boʻlimi) |
| 11–14 | `os.Getenv("PORT")` | portni muhit oʻzgaruvchisidan oʻqiydi, boʻsh boʻlsa — 8077 (Node'dagi `process.env.PORT \|\| 8077` kabi) |
| 15–18 | `os.Getenv("DATA")` | maʼlumot papkasi, boʻsh boʻlsa — joriy papkadagi `data` |
| 19–22 | `os.MkdirAll(dir, 0o755)` | papkani yaratadi (`mkdir -p` kabi). `0o755` — ruxsatlar, sakkizlik sanoqda |
| 23–27 | `net.Listen("tcp", ":"+port)` | portni ochadi. Port band boʻlsa, xato bilan chiqadi |
| 28 | `&http.Server{Handler: daftar(dir)}` | har bir soʻrovni `daftar` funksiyasi qaytargan handler'ga beradi |
| 29 | `go srv.Serve(ln)` | soʻrovlarni alohida goroutine'da qabul qiladi (goroutine — GO-1.21 da) |
| 30 | `fmt.Println(…)` | `server: :8077 da tinglayapman` deb yozadi |
| 31 | `kut(srv)` | signal kelguncha kutadi va serverni toza toʻxtatadi |

```go filename="server/daftar.go" showLineNumbers
package main

import (
	"bytes"
	"fmt"
	"net/http"
	"os"
	"path/filepath"
	"sync"
)

// daftar har bir mehmonni faylga yozadi va nechanchi ekanini aytadi.
func daftar(dir string) http.Handler {
	var mu sync.Mutex
	fayl := filepath.Join(dir, "mehmonlar.txt")
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		mu.Lock()
		defer mu.Unlock()
		f, err := os.OpenFile(fayl, os.O_APPEND|os.O_CREATE|os.O_RDWR, 0o644)
		if err != nil {
			http.Error(w, err.Error(), http.StatusInternalServerError)
			return
		}
		defer f.Close()
		fmt.Fprintln(f, "mehmon")
		b, _ := os.ReadFile(fayl)
		fmt.Fprintf(w, "Salom! Siz %d-mehmonsiz\n", bytes.Count(b, []byte("\n")))
	})
}
```

`daftar` («daftar») Express'dagi `(req, res) => {…}` ga oʻxshash funksiya qaytaradi. 14-qatordagi `sync.Mutex` bir
vaqtda kelgan ikki soʻrov faylga navbat bilan yozishini taʼminlaydi (mutex — GO-1.22 da batafsil). 15-qator fayl
yoʻlini yasaydi: `$DATA/mehmonlar.txt`. 19-qator faylni oxiriga yozish uchun ochadi, yoʻq boʻlsa yaratadi
(`O_APPEND|O_CREATE|O_RDWR`). 25-qator bitta `mehmon` qatorini qoʻshadi, 26–27-qatorlar faylni oʻqib, qatorlarni
sanaydi va javob yozadi. Demak, hisob faylda turadi: fayl yoʻqolsa, hisob yana 1 dan boshlanadi. Bu «Volume»
boʻlimida muhim boʻladi.

```go filename="server/kut.go" showLineNumbers
package main

import (
	"context"
	"fmt"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

// kut signal kelguncha kutadi, keyin serverni toza toʻxtatadi (SYS-0.02).
func kut(srv *http.Server) {
	ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGTERM, os.Interrupt)
	defer stop()
	<-ctx.Done()
	fmt.Println("server: signal keldi, toʻxtayapman")

	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()
	if err := srv.Shutdown(ctx); err != nil {
		fmt.Println("server: ulgurmadi:", err)
	}
	fmt.Println("server: xayr")
}
```

`kut` («kut») — SYS-0.02 dagi fayl. 15-qator SIGTERM yoki Ctrl+C kelganini kutish uchun **signalni ushlaydi**. 17-qator
signal kelguncha toʻxtab turadi. Keyin `Shutdown` yangi ulanishlarni qabul qilmaydi va boshlangan soʻrovlarni
5 soniyagacha kutadi. `context` haqida batafsil — GO-1.23 da. «PID 1 tuzogʻi» boʻlimida aynan shu ikki qator
(«signal keldi», «xayr») signal serverga yetib kelgan-kelmaganini koʻrsatadi.

## Dockerfile → image → container

**Dockerfile** — image uchun retsept: matnli fayl, har qatori bitta koʻrsatma. `docker build` undan image yigʻadi.
Image ichida container uchun kerakli hamma fayllar va qaysi buyruq ishga tushishi yozilgan. Image oʻzgarmaydi va
**qatlamlardan** (layers) iborat: Dockerfile'ning fayl qoʻshadigan har bir qatori bitta qatlam beradi.

`docker run` image'dan **container** ishga tushiradi. Container image qatlamlarini oʻzgartirmasdan oladi va ustiga
oʻzining yupqa yoziladigan qatlamini qoʻshadi. Bitta image'dan istalgancha container ishga tushirish mumkin.

```text
Dockerfile ──docker build──▶ image ──docker run──▶ container
 (retsept)                   (oʻzgarmas,           (jarayon + oʻzining
                              qatlamlar)            yoziladigan qatlami)
```

SYS-0.02 dagi dastur va jarayonni eslang:

| SYS-0.02 | Bugun | Nima umumiy |
|---|---|---|
| dastur (diskdagi fayl) | image | oʻzgarmas, ishga tushmagan |
| jarayon (ishlayotgan dastur) | container | bitta dasturdan bir nechta jarayon, bitta image'dan bir nechta container |
| `ps` | `docker ps` | ishlayotganlarni koʻrsatadi |

Container virtual mashina emas. U xost yadrosidan foydalanadigan oddiy jarayon. Buni «Container — oddiy jarayon»
boʻlimida `ps` bilan isbotlaymiz.

## Birinchi Dockerfile: bitta bosqich, 969 MB

Birinchi Dockerfile juda oddiy:

```dockerfile filename="Dockerfile.bir" showLineNumbers
# Bitta bosqich: Go kompilyatori ham image ichida qoladi
FROM golang:1.26.8
WORKDIR /src
COPY . .
RUN go build -o /server ./server
CMD ["/server"]
```

| Qator | Kod | Nima qiladi |
|---|---|---|
| 1 | `# …` | izoh: «Go kompilyatori ham image ichida qoladi» |
| 2 | `FROM golang:1.26.8` | asos image'ni tanlaydi: rasmiy `golang` image, Go 1.26.8 |
| 3 | `WORKDIR /src` | image ichidagi ish papkasi (keyingi buyruqlar shu yerda) |
| 4 | `COPY . .` | loyiha papkasini image ichidagi `/src` ga koʻchiradi |
| 5 | `RUN go build -o /server ./server` | **build paytida** bajariladi: serverni `/server` binary'siga yigʻadi |
| 6 | `CMD ["/server"]` | container ishga tushganda qaysi buyruq ishlashini aytadi |

`RUN` va `CMD` farqi: `RUN` image yigʻilayotganda bir marta ishlaydi (`npm run build` kabi), `CMD` esa har safar
container ishga tushganda ishlaydi (`npm start` kabi).

`COPY . .` hamma narsani koʻchiradi, lekin `.dockerignore` faylidagilarni emas. Bu `.gitignore` ga oʻxshaydi:

```text
# image'ga keraksiz narsalar build context'ga ham yuborilmaydi
data
srv
*.md
homework
```

**Build context** — `docker build` oxiridagi `.` papkasi: Docker uni toʻliq build'ga yuboradi.

`docker build` shu retsept boʻyicha image yigʻadi. `-t` unga nom beradi, `-f` qaysi Dockerfile ekanini aytadi, `-q`
faqat image ID'sini chiqaradi:

```console
$ docker build -q -t mehmon:bir -f Dockerfile.bir .
sha256:a771b1a8923d79007e32b2497bb5090a2bcfd7ce453301f35dd2d0a509754ada
```

Image ichida nima qoldi? `docker run --rm IMAGE buyruq` image'dagi `CMD` oʻrniga boshqa buyruqni ishga tushiradi:

```console
$ docker run --rm mehmon:bir go version
go version go1.26.8 linux/amd64
$ docker run --rm mehmon:bir sh -c 'gcc --version | head -1; head -1 /etc/os-release'
gcc (Debian 14.2.0-19) 14.2.0
PRETTY_NAME="Debian GNU/Linux 13 (trixie)"
```

Go kompilyatori shu yerda, C kompilyatori gcc ham shu yerda, ostida esa butun Debian 13. Ular faqat yigʻish uchun
kerak edi. Serverni ishga tushirish uchun bitta binary yetadi. 969 MB ning taqsimoti «Chuqurroq» boʻlimida.

## Multi-stage build: kompilyator ortda qoladi

Yechimning nomi — **multi-stage build**. Frontend'dan tanish andoza: bitta bosqichda `npm ci && npm run build`
(`node_modules` bilan), keyingisida faqat `dist` papkasi Nginx'ga. Go'da oxirgi bosqichga bitta fayl tushadi:

```dockerfile filename="Dockerfile" showLineNumbers
# 1-bosqich: yigʻish, Go kompilyatori shu yerda qoladi
FROM golang:1.26.8 AS build
WORKDIR /src
COPY go.mod ./
COPY server ./server
RUN CGO_ENABLED=0 go build -o /server ./server

# 2-bosqich: boʻm-boʻsh image, faqat binary
FROM scratch
COPY --from=build /server /server
ENV DATA=/data
EXPOSE 8077
CMD ["/server"]
```

| Qator | Kod | Nima qiladi |
|---|---|---|
| 2 | `FROM golang:1.26.8 AS build` | birinchi bosqich, nomi `build` |
| 4–5 | `COPY go.mod ./` · `COPY server ./server` | faqat kerakli fayllarni koʻchiradi: `go.mod` va `server` papkasi |
| 6 | `RUN CGO_ENABLED=0 go build …` | yigʻadi. `CGO_ENABLED=0` ga eʼtibor bering: unga «Savol» boʻlimida qaytamiz |
| 9 | `FROM scratch` | ikkinchi bosqich boʻm-boʻsh image'dan boshlanadi: ichida hatto shell ham yoʻq |
| 10 | `COPY --from=build /server /server` | birinchi bosqichdan faqat tayyor binary'ni oladi. Qolgan hammasi ortda qoladi |
| 11 | `ENV DATA=/data` | serverga maʼlumot papkasini muhit oʻzgaruvchisi orqali aytadi (`main.go`, 15-qator) |
| 12 | `EXPOSE 8077` | faqat hujjat: «server 8077 da tinglaydi». Portni **ochmaydi** («Port» boʻlimi) |
| 13 | `CMD ["/server"]` | kvadrat qavs — **exec shakli**: shell yoʻq, server toʻgʻridan-toʻgʻri ishga tushadi |

Image'da faqat oxirgi bosqich qoladi. Birinchi bosqich (Go, gcc, Debian) yakuniy image'ga tushmaydi.

`CMD` ning ikki shakli bor. `CMD ["/server"]` (exec shakli) dasturni toʻgʻridan-toʻgʻri ishga tushiradi.
`CMD /server` (shell shakli) esa uni `/bin/sh -c` orqali ishga tushiradi. `scratch` da shell yoʻq, shuning uchun bu
yerda faqat exec shakli ishlaydi. Bu farq «PID 1 tuzogʻi» boʻlimida yana kerak boʻladi.

```console
$ docker build -q -t mehmon:kichik -f Dockerfile .
sha256:24a42ee1e95189abd1fba310c37b120a8e069bd5f0e614ae0561bd759b5652ed
```

Natija — «Ikki image» boʻlimidagi 8.36 MB'lik `mehmon:kichik`.

## Savol: `CGO_ENABLED=0` boʻlmasa-chi?

`Dockerfile` ning 6-qatoridan `CGO_ENABLED=0` ni olib tashlaymiz:

```dockerfile
RUN go build -o /server ./server
```

GO-1.01 da `ldd` binary'ni static deb koʻrsatgan edi. Server `scratch` da ishga tushadimi?

**A)** ha, xuddi oldingidek javob beradi · **B)** yoʻq, `docker build` xato beradi · **C)** build oʻtadi, lekin
container ishga tushmaydi

Oʻylab koʻring, keyin javobni oching.

<details>
<summary>Javob</summary>

**C.** Build oʻtadi, container esa ishga tushmaydi. Xatosi juda chalgʻituvchi. Kurs papkasidagi
`boshqa/Dockerfile.cgo` aynan shu variant:

```dockerfile filename="boshqa/Dockerfile.cgo" showLineNumbers
# Xato variant: CGO_ENABLED=0 yoʻq. golang image'da gcc bor, shuning uchun cgo yoqilgan.
FROM golang:1.26.8 AS build
WORKDIR /src
COPY go.mod ./
COPY server ./server
RUN go build -o /server ./server

FROM scratch
COPY --from=build /server /server
CMD ["/server"]
```

```console
$ docker run --rm mehmon-boshqa:cgo
exec /server: no such file or directory
```

*no such file or directory* — «bunday fayl yoki papka yoʻq». Holbuki `/server` joyida turibdi: `COPY` uni koʻchirdi.
«A» ni tanlagan boʻlsangiz, Go binary'si har doim static deb oʻylagansiz. «B» ni tanlagan boʻlsangiz, Go buni build
paytida sezadi deb oʻylagansiz: yoʻq, build bosqichida libc bor, hammasi joyida.

</details>

Sabab — **cgo**, yaʼni Go'dan C kodini chaqirish imkoniyati. `cmd/cgo` hujjatiga koʻra, C kompilyatori topilsa,
cgo oʻz-oʻzidan yoqiladi. `golang` image'ida gcc bor. Birinchi bosqich image'ida tekshiramiz (`mehmon-boshqa:cgo-build`
— `yigish.sh` uni `--target build` bilan yigʻadi, yaʼni faqat `build` bosqichigacha):

```console
$ docker run --rm mehmon-boshqa:cgo-build sh -c 'which gcc; go env CGO_ENABLED'
/usr/bin/gcc
1
```

cgo yoqilganda `net` paketi nomlarni hal qilish uchun C kutubxonasining `getaddrinfo` kabi funksiyalarini chaqiradi.
Shunda binary tizimning C kutubxonasiga — **libc** ga — bogʻlanadi. `ldd` buni koʻrsatadi:

```console
$ docker run --rm mehmon-boshqa:cgo-build ldd /server
	linux-vdso.so.1 (0x00007f57f7d2f000)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f57f7b30000)
	/lib64/ld-linux-x86-64.so.2 (0x00007f57f7d31000)
```

(Qavs ichidagi manzillar har safar boshqacha: xotira manzillari tasodifiy tanlanadi.) Binary ikki narsani soʻraydi:
`libc.so.6` va `/lib64/ld-linux-x86-64.so.2`. Ikkinchisi — **dinamik yuklovchi** (dynamic loader). Yadro avval
yuklovchini ishga tushiradi, yuklovchi esa libc'ni ulab, binary'ni boshlaydi. Skriptdagi `#!/usr/bin/env node`
qatori ham shunday ishlaydi. `scratch` da yuklovchi yoʻq. `execve(2)` ning hujjati: ELF interpretator (yuklovchi)
topilmasa, yadro `ENOENT` qaytaradi. Docker uni `no such file or directory` deb koʻrsatadi.

```text
docker run mehmon-boshqa:cgo   (cgo yoqilgan)
  └─ yadro: /server ni ishga tushir
       └─ /server: «meni /lib64/ld-linux-x86-64.so.2 ishga tushirsin»
            └─ scratch'da bu fayl yoʻq → ENOENT → "exec /server: no such file or directory"

docker run mehmon:kichik       (CGO_ENABLED=0)
  └─ yadro: /server ni ishga tushir
       └─ /server: static, hech narsa soʻramaydi → ishlaydi
```

Bu oʻsha «menda ishlaydi» holati: libc bor kompyuterda (Debian'li build bosqichida) bu binary ishlaydi, boʻm-boʻsh
image'da esa yoʻq. Tuzatish: `CGO_ENABLED=0`. Shunda `net` sof Go'dagi resolver'ni ishlatadi va binary static boʻladi.

## Toʻrt asos, toʻrt oʻlcham

Bitta binary'ni toʻrt xil asosga qoʻyib, oʻlchaymiz. Ikki yangi variant kurs papkasining `boshqa/` («boshqa»)
papkasida. Ular `Dockerfile` dan faqat `FROM` qatori bilan farq qiladi (va `EXPOSE` qatori yoʻq):

```dockerfile filename="boshqa/Dockerfile.alpine" showLineNumbers
# Oʻlchov uchun: xuddi shu binary, lekin alpine ustida (shell va paket menejeri bor)
FROM golang:1.26.8 AS build
WORKDIR /src
COPY go.mod ./
COPY server ./server
RUN CGO_ENABLED=0 go build -o /server ./server

FROM alpine:3.24
COPY --from=build /server /server
ENV DATA=/data
CMD ["/server"]
```

```dockerfile filename="boshqa/Dockerfile.distroless" showLineNumbers
# Oʻlchov uchun: distroless/static — CA sertifikatlar, tzdata, /etc/passwd bor, shell yoʻq
FROM golang:1.26.8 AS build
WORKDIR /src
COPY go.mod ./
COPY server ./server
RUN CGO_ENABLED=0 go build -o /server ./server

FROM gcr.io/distroless/static-debian13
COPY --from=build /server /server
ENV DATA=/data
CMD ["/server"]
```

Hajmlar `./yigish.sh` natijasidan (yuqorida, «Oldin bilish kerak» boʻlimida):

| Image | Asos | Hajm | Ichida nima bor |
|---|---|---|---|
| `mehmon:bir` | `golang:1.26.8`, bitta bosqich | 969 MB | Debian, Go, gcc, build keshi |
| `mehmon-boshqa:alpine` | `alpine:3.24` | 16.8 MB | shell va paket menejeri (`apk`) |
| `mehmon-boshqa:distroless` | `distroless/static-debian13` | 10.7 MB | shell yoʻq; HTTPS uchun CA sertifikatlar, vaqt zonalari, `/etc/passwd` |
| `mehmon:kichik` | `scratch` | 8.36 MB | deyarli faqat binary'ning oʻzi |

Qaysi birini tanlash kerak? Serverga tashqi HTTPS soʻrov (sertifikatlar) yoki vaqt zonalari kerak boʻlmasa,
`scratch` yetarli. Kerak boʻlsa, distroless qulayroq. Ichkarida shell kerak boʻlsa (debug uchun), alpine. Raqamlar
sizda biroz farq qilishi mumkin: biz eski `overlay2` saqlash drayveridamiz, Docker Engine 29 ning yangi
oʻrnatmalarida esa standart boshqa (containerd image store). `docker image ls` dagi `SIZE` — image diskda
egallaydigan ochilgan hajm, yuklab olinadigan siqilgan hajm emas.

## Port: `-p` va `docker ps`

Endi `mehmon:kichik` ni ishga tushiramiz. `docker run -d` container'ni fonda ishga tushiradi. Server 8077 da
tinglaydi, Dockerfile'da `EXPOSE 8077` ham bor. Keyin `curl -sS` bilan soʻrov yuboramiz (`-S` xatoni koʻrsatadi).

Natija qanday boʻladi?

**A)** `Salom! Siz 1-mehmonsiz` · **B)** `curl` ulana olmaydi · **C)** server 404 qaytaradi

<details>
<summary>Javob</summary>

**B.** `curl` ulana olmaydi:

```console
$ docker run -d --name mehmon mehmon:kichik >/dev/null; sleep 0.3; curl -sS localhost:8077
curl: (7) Failed to connect to localhost:8077 after 0 ms: Could not connect to server
```

*Failed to connect* — «ulana olmadi». Container oʻz tarmogʻida ishlaydi, xostdagi 8077-portda esa hech kim yoʻq.
`EXPOSE` portni ochmaydi: Dockerfile hujjati boʻyicha u «aslida portni publish qilmaydi, hujjat vazifasini bajaradi».
«A» ni tanlagan boʻlsangiz, `EXPOSE` ni port ochadi deb oʻylagansiz. «C» uchun esa soʻrov serverga yetib borishi
kerak edi.

</details>

`-p XOST:CONTAINER` xostdagi portni container ichidagi portga ulaydi (publish qiladi). Oldingi container'ni
oʻchirib, `-p 8077:8077` bilan qayta ishga tushiramiz:

```console
$ docker rm -f mehmon >/dev/null; docker run -d --name mehmon -p 8077:8077 mehmon:kichik >/dev/null; sleep 0.3; curl -s localhost:8077; curl -s localhost:8077
Salom! Siz 1-mehmonsiz
Salom! Siz 2-mehmonsiz
```

Endi `curl` javob oldi, ikkinchi mehmon ham. `docker ps` ishlayotgan container'larni koʻrsatadi. `--filter name=mehmon`
faqat bizning container'ni qoldiradi:

```console
$ docker ps --filter name=mehmon --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
NAMES     IMAGE           PORTS
mehmon    mehmon:kichik   0.0.0.0:8077->8077/tcp, [::]:8077->8077/tcp
```

`docker image ls` paketlarni koʻrsatadi, `docker ps` esa ishlayotganlarini. Server nima yozganini `docker logs`
koʻrsatadi (container'ning stdout'i):

```console
$ docker logs mehmon
server: :8077 da tinglayapman
```

**Serverda ehtiyot boʻling.** `PORTS` ustunidagi `0.0.0.0` va `[::]` — xostning hamma manzillari. Yaʼni
`-p 8077:8077` portni tashqi dunyoga ham ochadi. Docker hujjati buni ochiq aytadi: «Publishing container ports is
insecure by default» (port publish qilish standart holatda xavfsiz emas). Port faqat oʻzingiz uchun boʻlsa, oldiga
localhost manzilini yozing. Buni alohida ishga tushirdik (avvalgi `mehmon` oʻchirilgan holda):

```console
$ docker run -d --name mehmon -p 127.0.0.1:8077:8077 mehmon:kichik >/dev/null; sleep 0.3; curl -s localhost:8077; docker ps --filter name=mehmon --format 'table {{.Names}}\t{{.Ports}}'
Salom! Siz 1-mehmonsiz
NAMES     PORTS
mehmon    127.0.0.1:8077->8077/tcp
```

Endi port faqat `127.0.0.1` da: tashqaridan ulanib boʻlmaydi.

## Container — oddiy jarayon

Endi vaʼda qilingan isbot. `docker inspect` container'ning xostdagi PID'ini beradi:

```console
$ docker inspect -f '{{.State.Pid}}' mehmon
28200
```

`ps` uni oddiy jarayon sifatida koʻrsatadi, xuddi SYS-0.02 dagidek. `-o pid,ppid,comm` — faqat PID, ota jarayon PID'i
va buyruq nomi. Ota jarayonning PID'ini `ps -o ppid= -p 28200` bilan topdik:

```console
$ ps -o pid,ppid,comm -p 28200,28176
    PID    PPID COMMAND
  28200   28176 server
  28176       1 containerd-shim
```

PID'lar sizda boshqacha boʻladi (videoda 199934 va 199908 edi): oʻzingiznikini qoʻying. Bizning `server` — xostdagi
oddiy jarayon. Uning otasi `containerd-shim` — Docker'ning container'larni kuzatib turadigan yordamchi jarayoni.

`/proc/PID/status` faylining `NSpid` qatori jarayonning har bir PID namespace'dagi raqamini beradi:

```console
$ grep NSpid /proc/28200/status
NSpid:	28200	1
```

Ikkita raqam: xostdagi PID (28200) va container ichidagi PID — 1. Buni **namespace** taʼminlaydi. Yadro jarayonga oʻz
PID raqamlarini, oʻz tarmogʻini va oʻz fayllarini koʻrsatadi. Jarayon oʻzini ajratilgan kompyuterda deb biladi.

```text
xost (Linux yadrosi bitta)
├─ PID 1        systemd
├─ PID 28176    containerd-shim
│   └─ PID 28200  server   ← xostdan qaraganda
│
└─ container ichidan qaraganda (oʻz PID namespace'i):
     PID 1      server     ← xuddi shu jarayon
     tarmoq:    oʻz tarmogʻi (xostning localhost:8077 i emas)
     fayllar:   faqat image'dagi /server + yoziladigan qatlam
```

Shuning uchun `curl` ham avval ulana olmagan edi: container'ning oʻz tarmogʻi bor, `-p` esa ikki tarmoqni ulaydi.
Virtual mashina oʻz yadrosini ishga tushiradi, container esa xostning yadrosini boshqa jarayonlar bilan baham koʻradi.

Windows va macOS'da Docker Desktop container'larni Linux virtual mashinasi ichida ishga tushiradi. Shuning uchun bu
isbotni Linux kompyuterda koʻrasiz.

## Volume: maʼlumot container'dan uzoq yashaydi

Server har bir mehmonni `/data/mehmonlar.txt` ga yozadi (`ENV DATA=/data`). Hozirgi container'ni oʻchirib,
yangisini ishga tushiramiz. Hisob nechadan boshlanadi?

**A)** davom etadi (avvalgi container'dagi hisobdan keyin) · **B)** yana 1 dan · **C)** server xato beradi

<details>
<summary>Javob</summary>

**B: yana 1 dan.**

```console
$ docker rm -f mehmon >/dev/null; docker run -d --name mehmon -p 8077:8077 mehmon:kichik >/dev/null; sleep 0.3; curl -s localhost:8077
Salom! Siz 1-mehmonsiz
```

Fayl container'ning yoziladigan qatlamida edi va u bilan birga oʻchdi. Docker hujjati: container qatlamiga yozilgan
maʼlumot container yoʻq qilinganda saqlanmaydi. «A» ni tanlagan boʻlsangiz, fayl image'da saqlanadi deb oʻylagansiz:
image oʻzgarmaydi. «C» boʻlmaydi: `main.go` papkani `MkdirAll` bilan oʻzi yaratadi.

</details>

`-v daftar:/data` `daftar` nomli **volume** ni container'ning `/data` papkasiga ulaydi. Volume'ni Docker boshqaradi:
u birinchi marta ishlatilganda oʻzi yaratiladi.

```console
$ docker rm -f mehmon >/dev/null; docker run -d --name mehmon -p 8077:8077 -v daftar:/data mehmon:kichik >/dev/null; sleep 0.3; curl -s localhost:8077; curl -s localhost:8077
Salom! Siz 1-mehmonsiz
Salom! Siz 2-mehmonsiz
```

Server ikki mehmonni volume'ga yozdi. Endi container'ni yana oʻchirib, yangisini xuddi shu volume bilan ishga
tushiramiz:

```console
$ docker rm -f mehmon >/dev/null; docker run -d --name mehmon -p 8077:8077 -v daftar:/data mehmon:kichik >/dev/null; sleep 0.3; curl -s localhost:8077
Salom! Siz 3-mehmonsiz
```

Hisob 3 dan davom etdi. Volume container'dan alohida yashaydi.

| Qadam | Container | `mehmonlar.txt` qayerda | Javob |
|---|---|---|---|
| 1 | yangi, volume'siz | container'ning yoziladigan qatlamida | 1 |
| 2 | yangi, `-v daftar:/data` | `daftar` volume'ida | 1, 2 |
| 3 | yana yangi, `-v daftar:/data` | oʻsha `daftar` volume'ida | 3 |

Postgres'ni Docker'da ishga tushirganlar uchun bu tanish: maʼlumot papkasiga volume ulanmasa, container bilan birga
baza ham yoʻqoladi. Keyingi darsda (SYS-0.06) aynan shuni `docker compose` bilan qilamiz.

Ishimiz tugadi, tozalaymiz:

```console
$ docker rm -f mehmon; docker volume rm daftar
mehmon
daftar
```

## PID 1 tuzogʻi: `docker stop` nega 10 soniya kutadi

SYS-0.02 da vaʼda qilingan tuzoq. `docker stop` container'ning asosiy jarayoniga (container ichidagi PID 1) SIGTERM
yuboradi. 10 soniyadan keyin esa SIGKILL. Koʻp loyihalarda server toʻgʻridan-toʻgʻri emas, start skripti orqali ishga
tushadi: avval tayyorgarlik (migratsiya, sozlama), keyin server. Kurs papkasidagi `tuzoq/` («tuzoq») aynan shunday:

```sh filename="tuzoq/start.sh" showLineNumbers
#!/bin/sh
echo "start.sh: tayyorlanyapman"
/server
```

```dockerfile filename="tuzoq/Dockerfile" showLineNumbers
# PID 1 tuzogʻi: server shell skript ichidan ishga tushadi
FROM golang:1.26.8 AS build
WORKDIR /src
COPY go.mod ./
COPY server ./server
RUN CGO_ENABLED=0 go build -o /server ./server

FROM alpine:3.24
COPY --from=build /server /server
COPY tuzoq/start.sh tuzoq/start-exec.sh /
CMD ["/start.sh"]
```

`start.sh` ning 1-qatori skriptni `/bin/sh` ga beradi, 2-qatori tayyorgarlikni bildiradi, 3-qatori serverni ishga
tushiradi. Dockerfile'da shell kerak, shuning uchun asos — alpine (8-qator). 10-qator ikkala skriptni image'ning
ildiziga koʻchiradi, 11-qator `start.sh` ni ishga tushiradi.

Bunday image'da container'ning birinchi jarayoni server emas, shell boʻladi. Kurs papkasidagi `toxtat.sh`
(«toʻxtat») `docker stop` qancha kutganini oʻlchaydi:

```bash filename="toxtat.sh" showLineNumbers
#!/usr/bin/env bash
# ./toxtat.sh IMAGE [buyruq]
# Container'ni ishga tushiradi, docker stop qancha kutganini oʻlchaydi va chiqish kodini aytadi.
exec 2>&1
docker rm -f toxtat >/dev/null 2>&1
docker run -d --name toxtat "$@" >/dev/null || exit 1
sleep 0.5
bosh=$(date +%s%N)
docker stop toxtat >/dev/null              # SIGTERM, 10 soniyadan keyin SIGKILL
tugash=$(date +%s%N)
docker logs toxtat
ms=$(( (tugash - bosh) / 1000000 ))
kod=$(docker inspect -f '{{.State.ExitCode}}' toxtat)
printf 'docker stop: %d.%d s, chiqish kodi: %s\n' $((ms / 1000)) $((ms % 1000 / 100)) "$kod"
docker rm toxtat >/dev/null
```

Muhim qatorlar: 6-qator `"$@"` — skriptga berilgan hamma argumentlarni `docker run` ga uzatadi (image va, berilsa,
`CMD` oʻrniga buyruq). 8 va 10-qatorlar `docker stop` dan oldin va keyin vaqtni nanosoniyada oladi. 11-qator
container nima yozganini chiqaradi. 13-qator container'ning chiqish kodini oladi.

`./toxtat.sh mehmon-tuzoq` nima chiqaradi?

**A)** `docker stop: 0.1 s, chiqish kodi: 0` · **B)** `docker stop: 10.1 s, chiqish kodi: 137` ·
**C)** `docker stop: 0.1 s, chiqish kodi: 143`

<details>
<summary>Javob</summary>

**B.**

```console
$ ./toxtat.sh mehmon-tuzoq
start.sh: tayyorlanyapman
server: :8077 da tinglayapman
docker stop: 10.1 s, chiqish kodi: 137
```

`docker stop` 10 soniya osilib, 137 qaytardi. «signal keldi» qatori yoʻq: server signalni umuman olmadi. «A» ni
tanlagan boʻlsangiz, SIGTERM serverga yetadi deb oʻylagansiz. «C» ni tanlagan boʻlsangiz, shell SIGTERM'dan oʻladi deb
oʻylagansiz (SYS-0.02 dagi oddiy jarayon kabi, 128 + 15). PID 1 bundan istisno, quyida.

</details>

Umumiy qoida: `docker stop` 10 soniya osilib qolib, 137 qaytarsa, server signalni yo umuman olmagan, yo 10 soniyada
ulgurmagan. Bizda server start skripti orqali ishga tushgan, container'da PID 1 esa shell.

SYS-0.02 da «signalni ushlamagan dastur toʻxtaydi» degan edik. PID 1 bundan istisno. `pid_namespaces(7)` boʻyicha,
yadro namespace'ning PID 1 jarayoniga faqat u ushlaydigan (handler oʻrnatgan) signallarni yetkazadi. SIGKILL bundan
mustasno. Shell SIGTERM'ni ushlamaydi va serverga uzatmaydi. 10 soniyadan keyin SIGKILL keladi: 128 + 9 = 137.

Yechim — bitta soʻz, `exec`. U shell'ni yangi jarayon yaratmasdan serverning oʻzi bilan almashtiradi:

```sh filename="tuzoq/start-exec.sh" showLineNumbers
#!/bin/sh
echo "start.sh: tayyorlanyapman"
exec /server
```

Xuddi shu image, faqat `CMD` oʻrniga `/start-exec.sh` beramiz (`toxtat.sh` uni `docker run` ga uzatadi):

```console
$ ./toxtat.sh mehmon-tuzoq /start-exec.sh
start.sh: tayyorlanyapman
server: :8077 da tinglayapman
server: signal keldi, toʻxtayapman
server: xayr
docker stop: 0.1 s, chiqish kodi: 0
```

Endi server PID 1. `kut` funksiyasi signalni ushlaydi va server 0.1 soniyada toza toʻxtaydi, chiqish kodi 0.

Buni container ichidan koʻramiz. `docker exec` ishlayotgan container ichida buyruq bajaradi. Alpine'da `ps` bor:

```console
$ docker run -d --name tuzoqps mehmon-tuzoq >/dev/null; sleep 0.5; docker exec tuzoqps ps -o pid,ppid,comm; docker rm -f tuzoqps >/dev/null
PID   PPID  COMMAND
    1     0 start.sh
    7     1 server
   14     0 ps
$ docker run -d --name tuzoqps mehmon-tuzoq /start-exec.sh >/dev/null; sleep 0.5; docker exec tuzoqps ps -o pid,ppid,comm; docker rm -f tuzoqps >/dev/null
PID   PPID  COMMAND
    1     0 server
   13     0 ps
```

`exec`'siz PID 1 — `start.sh` ni bajarayotgan shell, server esa uning bolasi (PID 7). `exec` bilan server PID 1.
(`ps` ning oʻzi ham roʻyxatda: u `docker exec` bilan ishga tushgan.) Bu ikki buyruq videoda yoʻq, lekin kurs
papkasidagi image bilan ishga tushirildi.

```text
start.sh (exec'siz)                  start-exec.sh (exec bilan)
PID 1  start.sh (sh)                 PID 1  server   (sh oʻrnini egalladi)
└─ PID 7  server
docker stop → SIGTERM → PID 1        docker stop → SIGTERM → PID 1
sh: handler yoʻq → yadro tashlaydi   server: kut ushlaydi → Shutdown
server hech narsa bilmaydi           "signal keldi", "xayr"
10 s → SIGKILL → 137                 0.1 s → 0
```

Bizning asosiy `scratch` image'da bu muammo yoʻq: shell umuman yoʻq, `CMD ["/server"]` exec shaklida, server oʻzi
PID 1. Tekshiramiz:

```console
$ ./toxtat.sh mehmon:kichik
server: :8077 da tinglayapman
server: signal keldi, toʻxtayapman
server: xayr
docker stop: 0.1 s, chiqish kodi: 0
```

Bu buyruq videoda yoʻq, lekin kurs papkasidagi `toxtat.sh` bilan ishga tushirildi.

## Chuqurroq (ixtiyoriy): 969 MB ichida nima, keshlash va shell shakli

**969 MB qayerdan.** `golang:1.26.8` ning oʻzi 874 MB: Debian 13, Go (270 MB), gcc va git. `docker history`
image qatlamlarini koʻrsatadi (`head -4` — birinchi toʻrt qator):

```console
$ docker history mehmon:bir --format 'table {{.Size}}\t{{.CreatedBy}}' | head -4
SIZE      CREATED BY
0B        CMD ["/server"]
94.9MB    RUN /bin/sh -c go build -o /server ./server …
5.09kB    COPY . . # buildkit
```

`RUN go build` qatlami 94.9 MB qoʻshdi: binary va Go'ning build keshi (`/root/.cache/go-build`, kurs README'siga
koʻra 88 MB). Bularning hech biri serverni ishga tushirish uchun kerak emas.

**Qatlam keshi va `go.mod`.** Docker har bir qatlamni keshlaydi: qatorning kirishi oʻzgarmasa, qatlam keshdan olinadi.
Shuning uchun real loyihada `COPY go.mod go.sum ./` va `RUN go mod download` ni kodni koʻchirishdan **oldin** yozing.
Kod oʻzgarganda bogʻliqliklar qatlami keshdan olinadi. Node'dagi `COPY package*.json ./` → `RUN npm ci` → `COPY . .`
andozasi xuddi shu sababli. Bizning loyihada tashqi bogʻliqlik yoʻq (`go.sum` ham yoʻq), shuning uchun bu qadam
tushirib qoldirilgan.

**Shell shakli har doim ham tuzoq emas.** Kurs README'sida oʻlchangan (biz qayta ishga tushirmadik): alpine'da
`CMD /server` (shell shakli) yozilsa, alpine'ning `sh` i yagona buyruqni `exec` qilib yuboradi. Server baribir PID 1
boʻladi, `docker stop` 0.1 soniya, kod 0. Tuzoq skriptda bir nechta buyruq boʻlganda chiqadi, bizning `start.sh` kabi.

**Signal va Go server.** Bizning server `signal.NotifyContext` orqali SIGTERM uchun handler oʻrnatadi. Shuning uchun u
PID 1 boʻlsa ham signalni oladi. PID 1 qoidasi aynan shu «handler bormi» savoliga bogʻliq.

## Koʻp uchraydigan xatolar

**1. «`EXPOSE` portni ochadi».** Eng keng tarqalgan notoʻgʻri tasavvur. `EXPOSE 8077` bor, `-p` yoʻq — natija
`curl: (7) Failed to connect` («Port» boʻlimi). `EXPOSE` — faqat hujjat. **Tuzatish:** `-p 8077:8077` (yoki faqat
oʻzingiz uchun `-p 127.0.0.1:8077:8077`).

**2. cgo yoqilgan binary `scratch` da.** `exec /server: no such file or directory`, fayl esa joyida («Savol» boʻlimi).
Xabar `/server` haqida emas, yetishmayotgan dinamik yuklovchi haqida. **Tuzatish:** `RUN CGO_ENABLED=0 go build …`.

**3. Container nomi band.** Bir xil `--name` bilan ikkinchi marta `docker run`:

```console
$ docker run -d --name mehmon -p 8077:8077 mehmon:kichik
48f170e52766df023a9c1f892a3df1c8b87edde701cd35859d407f034419c92d
$ docker run -d --name mehmon -p 8077:8077 mehmon:kichik
docker: Error response from daemon: Conflict. The container name "/mehmon" is already in use by container "48f170e52766df023a9c1f892a3df1c8b87edde701cd35859d407f034419c92d". You have to remove (or rename) that container to be able to reuse that name.

Run 'docker run --help' for more information
```

Birinchi buyruq container ID'sini chiqardi. Ikkinchisi: *Conflict … is already in use* — «nom allaqachon band».
Toʻxtatilgan container ham nomni ushlab turadi. **Tuzatish:** avval `docker rm -f mehmon` (darsdagi buyruqlar shuning
uchun `docker rm -f mehmon >/dev/null;` bilan boshlanadi) yoki `--rm`.

**4. Xostdagi port band.** Birinchi `mehmon` hali ishlayapti, ikkinchi container ham 8077 ni soʻraydi:

```console
$ docker run -d --name mehmon2 -p 8077:8077 mehmon:kichik
30896b1ecefe6c80c6ca596ae6a074b0bba68d60c7fe8d1d104f277459d6cd49
docker: Error response from daemon: failed to set up container networking: driver failed programming external connectivity on endpoint mehmon2 (a5820599b823045ceac88629e37f633ff660211fc687d69d8f975203c27a8417): Bind for 0.0.0.0:8077 failed: port is already allocated

Run 'docker run --help' for more information
```

*Bind for 0.0.0.0:8077 failed: port is already allocated* — «8077-portni bogʻlab boʻlmadi: port band». Container
yaratildi (ID chiqdi), lekin ishga tushmadi: `docker ps -a` uni `Created` holatida koʻrsatadi va u `mehmon2` nomini
ushlab turadi. **Tuzatish:** boshqa xost porti (`-p 8078:8077`) yoki avvalgisini toʻxtating. Keyin `docker rm mehmon2`.

**5. `scratch` ichiga shell bilan kirish.** Debug uchun `docker run … sh` yoki `docker exec … sh`:

```console
$ docker run --rm mehmon:kichik sh
docker: Error response from daemon: failed to create task for container: failed to create shim task: OCI runtime create failed: runc create failed: unable to start container process: error during container init: exec: "sh": executable file not found in $PATH

Run 'docker run --help' for more information
```

*executable file not found in $PATH* — «`$PATH` da bajariladigan fayl topilmadi». `scratch` da shell yoʻq: bu xato
emas, bu image'ning maqsadi. **Tuzatish:** loglarni `docker logs` bilan oʻqing. Ichkarida shell kerak boʻlsa, oʻsha
binary'ni alpine asosida yigʻing (`boshqa/Dockerfile.alpine`).

**6. Maʼlumot container ichida (jim xato).** Xato yoʻq, lekin container qayta yaratilganda maʼlumot yoʻqoladi: hisob
yana 1 dan («Volume» boʻlimi). **Tuzatish:** maʼlumot papkasiga volume ulang: `-v daftar:/data`.

**7. Start skriptida `exec` yoʻq (jim xato).** Har deploy'da `docker stop` 10 soniya kutadi, server SIGKILL bilan
oʻladi, boshlangan soʻrovlar uziladi, kod 137 («PID 1 tuzogʻi» boʻlimi). **Tuzatish:** skriptning oxirgi qatori
`exec /server`.

**8. VPS'da `-p 8077:8077` (jim xavf).** Port hamma manzillarda ochiladi (`0.0.0.0`, `[::]`). Faqat Nginx yoki
oʻzingiz ishlatadigan servis uchun bu ortiqcha. **Tuzatish:** `-p 127.0.0.1:8077:8077`.

## Oʻzingizni tekshiring

Avval oʻzingiz javob bering, keyin oching.

**1.** Image va container farqi nima? Qaysi buyruq qaysi birini roʻyxatlaydi?

<details>
<summary>Javob</summary>

Image — oʻzgarmas paket: fayllar, qatlamlar va qaysi buyruq ishga tushishi. Container — image'dan ishga tushgan
jarayon, ustida oʻzining yoziladigan qatlami bor. Bitta image'dan bir nechta container. `docker image ls` — image'lar,
`docker ps` — ishlayotgan container'lar (`docker ps -a` — toʻxtaganlari ham).

</details>

**2.** Container `-p 9000:8077` bilan ishga tushirildi. Keyin `curl -s localhost:9000` va `curl -sS localhost:8077`.
Nima chiqadi?

**A)** ikkalasi ham `Salom!` · **B)** 9000 — `Salom!`, 8077 — ulanish xatosi · **C)** 9000 — ulanish xatosi, 8077 — `Salom!`

<details>
<summary>Javob</summary>

**B.** `-p XOST:CONTAINER`: xostdagi 9000 container ichidagi 8077 ga ulanadi. Xostdagi 8077 da hech kim yoʻq.

```console
$ docker run -d --name mehmon -p 9000:8077 mehmon:kichik >/dev/null; sleep 0.3; curl -s localhost:9000; curl -sS localhost:8077; docker rm -f mehmon >/dev/null
Salom! Siz 1-mehmonsiz
curl: (7) Failed to connect to localhost:8077 after 0 ms: Could not connect to server
```

«C» ni tanlagan boʻlsangiz, raqamlar tartibini teskari oʻqigansiz: chapda xost, oʻngda container.

</details>

**3.** `docker stop` 10 soniya kutdi va 137 qaytardi. Bu nimani bildiradi va eng koʻp uchraydigan sabab nima?

<details>
<summary>Javob</summary>

137 = 128 + 9: jarayon SIGKILL bilan oʻldirilgan. Demak, server SIGTERM'ni yo umuman olmagan, yo 10 soniyada
ulgurmagan. Koʻp uchraydigan sabab: server start skripti orqali ishga tushgan, PID 1 esa shell. Yadro PID 1 ga faqat u
ushlaydigan signalni yetkazadi, shell esa SIGTERM'ni ushlamaydi va serverga uzatmaydi. Tuzatish: `exec /server`.

</details>

**4.** `exec /server: no such file or directory` — lekin `/server` image'da bor. Qaysi fayl yoʻq?

<details>
<summary>Javob</summary>

Dinamik yuklovchi `/lib64/ld-linux-x86-64.so.2` (va libc). Binary cgo yoqilgan holda yigʻilgan, `scratch` da esa ular
yoʻq. `ldd` buni koʻrsatadi. Tuzatish: `CGO_ENABLED=0`.

</details>

**5.** GO-1.01 dan: static binary'ga `ldd` nima deydi?

<details>
<summary>Javob</summary>

`not a dynamic executable` — «dinamik bajariladigan fayl emas». Binary hech qanday tizim kutubxonasini soʻramaydi,
shuning uchun `scratch` da ham ishlaydi. `CGO_ENABLED=0` bilan yigʻilgan `mehmon:kichik` dagi `/server` aynan shunday.

</details>

- 🟢 **Oson:** `mehmon:kichik` ni `PORT=9000` bilan ishga tushiring (muhit oʻzgaruvchisini `-e` beradi) va `-p` ni
  shunga moslang.
- 🟡 **Oʻrta:** volume oʻrniga oʻz papkangizni ulang (`-v "$PWD/papka:/data"`) va faylni xostda oching. Fayl kimniki

- 🟠 **Qiyin:** exec'siz `mehmon-tuzoq` ni `--init` bilan ishga tushirib toʻxtating. Tez toʻxtaydimi? Server «signal
  keldi» deb yozadimi?
- 🔴 **Guru:** server root emas, `65532` foydalanuvchisi nomidan ishlasin, volume'ga esa baribir yozilsin.

Hamma javoblarni bitta skript ishga tushiradi (avval `./yigish.sh`; 8077, 8078 va 9000 portlari boʻsh boʻlsin):

```bash

```

<details>
<summary>Javob</summary>

Skriptning bizdagi natijasi (`docker top` dagi PID har safar boshqacha):

```console
$ bash homework/javoblar.sh
== Oson: PORT=9000 muhitdan, -p 9000:9000
server: :9000 da tinglayapman
Salom! Siz 1-mehmonsiz
== Oʻrta: volume oʻrniga papka (bind mount), fayl egasi siz
Salom! Siz 1-mehmonsiz
Salom! Siz 2-mehmonsiz
xostdagi fayl: homework/papka/mehmonlar.txt, qatorlar: 2
== Qiyin: exec'siz image + --init
start.sh: tayyorlanyapman
server: :8077 da tinglayapman
docker stop: 0.1 s, chiqish kodi: 143
== Guru: USER 65532 (root emas) + volume
-- oddiy image'ga --user 65532 bersak:
open /data/mehmonlar.txt: permission denied
-- homework/guru/Dockerfile bilan:
Salom! Siz 1-mehmonsiz
Salom! Siz 2-mehmonsiz
USER                PID                 COMMAND
65532               40431               server
```

🟢 `docker run -d -e PORT=9000 -p 9000:9000 mehmon:kichik`. Server portni muhitdan oladi (`main.go`, 11-qator,
SYS-0.02). `-p` ning ikkinchi raqami container ichidagi port bilan bir xil boʻlishi kerak: endi u 9000.

🟡 `-v "$PWD/papka:/data"` — volume emas, **bind mount**: xostdagi oddiy papka toʻgʻridan-toʻgʻri ulanadi. Fayl
xostdagi papkada paydo boʻladi. `--user "$(id -u):$(id -g)"` bermasangiz, server container ichida root, fayl ham xostda
root'niki boʻladi va uni oddiy foydalanuvchi oʻchira olmaydi. Javobda `--user` bor: fayl sizniki.

🟠 `./toxtat.sh --init mehmon-tuzoq` → 0.1 s, lekin kod **143** va «signal keldi» **yoʻq**. `--init` PID 1 qilib
`docker-init` (tini) ni qoʻyadi. U SIGTERM'ni faqat bevosita bolasiga — shell'ga — uzatadi. Shell endi PID 1 emas,
shuning uchun SIGTERM uni oʻldiradi (128 + 15 = 143). Init chiqadi, yadro esa namespace'dagi qolgan jarayonlarni,
jumladan serverni, SIGKILL bilan oʻldiradi (`pid_namespaces(7)`). Tez, lekin toza emas: yechim baribir `exec`.

🔴 Shunchaki `--user 65532:65532` bersangiz, `open /data/mehmonlar.txt: permission denied` — yangi volume'ning
papkasi root'niki. Yechim — `homework/guru/Dockerfile`:

```dockerfile filename="homework/guru/Dockerfile" showLineNumbers
# Guru javobi: server root emas, 65532 foydalanuvchisi nomidan ishlaydi.
# Kontekst: dars papkasi (docker build -f homework/guru/Dockerfile .)
FROM golang:1.26.8 AS build
WORKDIR /src
COPY go.mod ./
COPY server ./server
RUN CGO_ENABLED=0 go build -o /server ./server
# scratch'da mkdir yoʻq: papkani shu bosqichda yaratamiz
RUN mkdir /data

FROM scratch
COPY --from=build /server /server
# /data egasi 65532: yangi (boʻsh) volume ulanganda shu egalikni oladi
COPY --from=build --chown=65532:65532 /data /data
ENV DATA=/data
USER 65532:65532
EXPOSE 8077
CMD ["/server"]
```

9-qator build bosqichida boʻsh `/data` yaratadi (`scratch` da `mkdir` yoʻq). 14-qator uni egasi 65532 qilib
koʻchiradi. 16-qator serverni shu foydalanuvchi nomidan ishga tushiradi. Boʻsh volume birinchi marta ulanganda Docker
image'dagi papka tarkibini egasi bilan birga unga koʻchiradi: hisob 1, 2, `docker top` da `USER 65532`. `scratch` da
`/etc/passwd` yoʻq, shuning uchun foydalanuvchi nomi emas, raqami (UID) yoziladi.

</details>
