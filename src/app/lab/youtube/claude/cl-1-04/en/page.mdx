## What you will learn

In Turkey, nearly a thousand high school students were split into three groups. One group did its maths practice with
a helper that looked like ChatGPT and scored 48 percent better in practice. Then the AI was taken away for the exam.
This group's grades came out 17 percent lower than those of the students who had studied without AI, and the students
themselves did not notice (Bastani et al., PNAS 2025). You also get code from Claude every day. It works. But are you
learning?

**One idea:** if the AI writes the answer and you only copy it, you may not be able to solve the problem on your own
later. So you write first, even with mistakes. Claude becomes a tutor: it shows where the mistake is and asks a
question.

By the end of the lesson you will:

- give Claude six lines of tutor rules and see it point at the wrong line and ask a question instead of writing
  ready-made code;
- compare two ways on one Go bug: "fix it" (the answer machine) and the tutor; measure 12 stored Claude answers with a
  Go program;
- judge your understanding by a check, not by the feeling "I understand": close the chat and write it from memory, or
  explain it;
- fix a classic Go mistake on the way: why `errors.Is(err, &MaydonXato{})` is never `true`.

Today's three core new words:

| Word | Plain meaning | English term |
|---|---|---|
| illusion of knowing | you have the feeling "I understand", but you cannot explain it step by step | illusion of explanatory depth |
| tutor rules | instructions Claude gets before the conversation: don't write ready code, point at the mistake, ask a question | system prompt (in Claude.ai: Project instructions) |
| recall | close the material and write down what you remember | retrieval practice |

Two helper names: the **answer machine** is the way of asking Claude for a ready-made fix; **Learning mode** is
Anthropic's official tutor mode in Claude for Education (below).

## The illusion of knowing: the feeling "I understand" is not understanding

One question: how does the zipper on a jacket work? Most people say "I know". Now try to write it down step by step: how
do the teeth lock together, and why doesn't it come apart?

Rozenblit and Keil (Cognitive Science, 2002, Study 1) asked 16 graduate students at Yale University to rate, from 1 to 7,
how well they understood things like these — a zipper, a speedometer, a piano key, a lock. Then each of them wrote a
step-by-step explanation of how it works and rated again. The authors: *"Nearly all participants showed drops in
estimates of what they knew when confronted with having to provide a real explanation."*

| Step | What happened |
|---|---|
| 1. "I know": a rating from 1 to 7 | based on a feeling, without thinking |
| 2. A step-by-step explanation | the gaps become visible |
| 3. Rating again | lower for almost everyone |
| Conclusion | feeling ≠ understanding: if you can't explain it, you haven't understood it |

The authors called this the **illusion of knowing** (*illusion of explanatory depth*). A developer knows this
situation: you read Claude's explanation, everything seems logical, but after you close the chat you cannot write that
code. The students in the Turkish study were in exactly this position: they did worse in the exam and did not notice.

**A tutor is not a guarantee either.** The Turkish study had a third group too: **GPT Tutor**. Its helper did not give
the answer but a hint; teachers had also written down the solution to each problem and the common mistakes for it.

| Group | In practice | In the exam (without AI) | How they rated themselves |
|---|---|---|---|
| no AI | — | baseline | — |
| GPT Base (like ChatGPT) | +48 % | −17 % | did not notice they got worse |
| GPT Tutor (hints, not answers) | +127 % | almost no harm, no benefit either | thought they did better |

So a tutor removes the harm, but not the illusion. That is why you check yourself even after the tutor. How to do it is
in the last part of this page.

Why do you write first? A meta-analysis by Bertsch and colleagues (Memory & Cognition, 2007) combined 86 studies:
information you produce yourself (*generate*) is remembered better than material you simply read. Psychologists call
this the *generation effect*. The average effect is 0.40 standard deviations, "a benefit of almost half a standard
deviation".

## The experiment: price −5, answer 500

The experiment uses the code of a small online shop (`bozor`, "bazaar") from the course project. A handler checks an
order and returns an HTTP status depending on the error. The requirement: if the price is negative, return `400` (the
client sent bad data), not `500`. Our learner is **fictional**: we wrote their code and messages; Claude's answers are
unchanged. The learner has just learned `errors.Is` in [CL-1.03](/lab/youtube/claude/cl-1-03/en) and wrote it for 400 too:

```go filename="bozor/main.go" showLineNumbers
package main

import (
	"errors"
	"fmt"
)

var ErrTopilmadi = errors.New("buyurtma topilmadi")

// MaydonXato: buyurtmaning bitta maydoni notoʻgʻri
type MaydonXato struct {
	Maydon string
	Sabab  string
}

func (e *MaydonXato) Error() string { return e.Maydon + ": " + e.Sabab }

func tekshir(narx int) error {
	if narx <= 0 {
		return fmt.Errorf("tekshir: %w", &MaydonXato{Maydon: "narx", Sabab: "musbat boʻlishi kerak"})
	}
	return nil
}

// holat: handler shu kodni HTTP javobga yozadi
func holat(err error) int {
	if err == nil {
		return 200
	}
	if errors.Is(err, ErrTopilmadi) {
		return 404
	}
	// mening urinishim: oʻtgan safar errors.Is yordam bergan edi
	if errors.Is(err, &MaydonXato{}) {
		return 400
	}
	return 500
}

func main() {
	for _, narx := range []int{12000, -5} {
		err := tekshir(narx)
		fmt.Printf("POST /buyurtma narx=%d → %d %v\n", narx, holat(err), err)
	}
}
```

| Line | Code | What it does |
|---|---|---|
| 8 | `var ErrTopilmadi = errors.New(…)` | a **sentinel error** ("order not found"): one ready value, compared with `errors.Is` ([GO-1.14](/lab/youtube/go/go-1-14/en)) |
| 11–14 | `type MaydonXato struct` | our own error type ("field error"): which field (`Maydon`, "field") is wrong and why (`Sabab`, "reason") |
| 16 | `func (e *MaydonXato) Error() string` | pointer receiver: only `*MaydonXato` implements `error` |
| 18–23 | `func tekshir(narx int) error` | `tekshir` ("check"): if the price (`narx`) is ≤ 0, creates a **new** `&MaydonXato{…}` and wraps it with `%w` in `tekshir: ` |
| 26–38 | `func holat(err error) int` | `holat` ("status"): turns the error into an HTTP status: `nil` → 200, `ErrTopilmadi` → 404, `MaydonXato` → 400, anything else → 500 |
| 33 | `// mening urinishim…` | the learner's comment: "last time `errors.Is` helped" |
| 34 | `errors.Is(err, &MaydonXato{})` | the learner's intent: "if the error is a `MaydonXato`, return 400". But the line asks something else (below) |
| 41 | `for _, narx := range []int{12000, -5}` | two requests: a valid price and a negative one |
| 43 | `fmt.Printf(…)` | the request, the status and the error text; `%v` prints the error as text, and `<nil>` when there is no error |

What is printed for `narx=-5`?

**A)** `400` · **B)** `500` · **C)** a compile error

<details>
<summary>Answer</summary>

**B.** The code compiles: `&MaydonXato{}` is an `error` of the right type. But `errors.Is` on line 34 never returns
`true`, so `holat` falls through to the last `return 500`. If you chose "A", you read `errors.Is` like the learner did,
as "is there an error of this type?". Why it isn't — in the next section.

</details>

```console
$ go run ./bozor
POST /buyurtma narx=12000 → 200 <nil>
POST /buyurtma narx=-5 → 500 tekshir: narx: musbat boʻlishi kerak
```

In the first line the price is valid: `200`, and `<nil>` means "no error". In the second line the error text is right —
"narx: musbat boʻlishi kerak" ("price: must be positive") — but the status is `500`. `go vet` does not help either:

```console
$ go vet ./bozor
```

It printed nothing: from Go's point of view this code is correct. This is a silent bug: neither the compiler nor `vet`
catches it.

## Where the mistake is: `errors.Is` looks for an exact value

The error that `tekshir` returns is a two-layer **error chain**: outside, the `fmt.Errorf("tekshir: %w", …)` wrapper;
inside, a `*MaydonXato` pointer. The picture from the video: your passport is in a bag, the bag is in a suitcase. Both
`errors.Is` and `errors.As` open the suitcase layer by layer. The difference is what they look for:

```text
err  =  "tekshir: …"  (%w wrapper)
          └── *MaydonXato  address 0xA1  {Maydon: "narx", Sabab: "musbat boʻlishi kerak"}

errors.Is(err, &MaydonXato{})       looks for: a NEW, empty value at address 0xB2
                                    0xA1 == 0xB2 ?  no → false → 500

errors.AsType[*MaydonXato](err)     looks for: any error OF TYPE *MaydonXato
                                    is the type of 0xA1 *MaydonXato ?  yes → true → 400
```

(The addresses are made up, only to show the difference.) `errors.Is` compares each error in the chain with the given
value using `==`. For pointers, `==` means "do both point to **the same** object in memory?". `&MaydonXato{}` creates a
new object every time, and it is never the same as the object `tekshir` created. In passport terms: `errors.Is` asks
"is **my exact** passport inside?", while the learner made a new, empty passport and asked "is this one inside?". The
question we need is different: "is there **any** passport inside?" That is `errors.As` and `errors.AsType`.

So comparing values and checking a type are two different operations:

| Question | Go (along the chain) |
|---|---|
| exactly this value? | `errors.Is(err, ErrTopilmadi)` |
| an error of this type? | `errors.As(err, &me)` or `errors.AsType[*MaydonXato](err)` |

`errors.Is` is for sentinel errors (`ErrTopilmadi`). To search by type you need `errors.As` (since Go 1.13) or
`errors.AsType` (since Go 1.26) ([GO-1.14](/lab/youtube/go/go-1-14/en)). Now we give this bug to Claude in two ways.

## Way 1: the answer machine

The first line of `promptlar/1-javob.txt`, followed by the whole `bozor/main.go` and the `go run` output:

```text
Bu Go kodni tuzatib ber. Narx manfiy bo'lsa 400 qaytishi kerak, lekin 500 qaytyapti. Go 1.26.8.
```

("Fix this Go code. If the price is negative it should return 400, but it returns 500. Go 1.26.8.") We gave it to
Claude Sonnet 5.5 with no system text, three times, each time in a new conversation (`takrorla.sh`, as in CL-1.03). All
three answers contain ready code. An excerpt from the first answer (`javoblar/1-javob/1-1.txt`):

```text
Xato **turini** tekshirish uchun `errors.As` kerak. U zanjirdagi (`%w` orqali o'ralgan) xatolar ichidan shu turdagisini topib, o'zgaruvchiga yozadi.

`holat` funksiyasini shunday o'zgartiring:
```

("To check the **type** of the error you need `errors.As`. It finds the error of that type among the errors in the
chain (wrapped with `%w`) and writes it into a variable. Change the `holat` function like this:") Then the answer gives
a ready function, exactly this:

```go
func holat(err error) int {
	if err == nil {
		return 200
	}
	if errors.Is(err, ErrTopilmadi) {
		return 404
	}
	var me *MaydonXato
	if errors.As(err, &me) {
		return 400
	}
	return 500
}
```

This is a correct fix. The two changed lines:

| Code | What it does |
|---|---|
| `var me *MaydonXato` | an empty "pocket" for the error that is found: a pointer variable that is `nil` |
| `errors.As(err, &me)` | looks for an error of type `*MaydonXato` in the chain; if found, writes it into `me` and returns `true`. To be able to write, it gets the **address** of `me` (`&me`) |

We put the code into `bozor/main.go` (the `olchov` program does this, below): the code from all three answers worked
and printed `narx=-5 → 400`. The answer also has an explanation: `errors.Is` compares with `==`, and a new pointer is
never equal.

**Let's sum up: what happened?** The code works and there is an explanation. But we wrote nothing and recalled nothing.
It is easy to skim an explanation — that is the illusion of knowing itself. In the Turkish study, the most common
message the GPT Base students sent the helper was the same: *"What is the answer?"*

## Way 2: tutor rules

In the second way we give Claude six lines of rules **before** the conversation. These are the **tutor rules**: in the
API and the Claude Code CLI they become the *system prompt*, and in Claude.ai you put them into the Project
instructions ([CL-1.02](/lab/youtube/claude/cl-1-02/en)). `promptlar/ustoz-tizim.txt` (`ustoz` means "tutor"):

```text
Sen Go o'rganayotgan dasturchining ustozisan. Maqsad: u kodni o'zi yozib, xatoning sababini o'zi tushunsin.
- Tayyor kod, tuzatilgan qator yoki to'g'ri funksiya nomini yozma, hatto so'rasa ham. Uning o'rniga yo'nalish ber.
- Avval o'quvchining urinishini o'qi: nima to'g'ri ekanini ayt, keyin xato qaysi qatorda ekanini ko'rsat.
- So'ng bitta savol ber, javobini u o'zi topsin. Savolga o'zing javob berma.
- O'quvchi tuzatishini yuborsa, uni tekshir: xato bo'lsa, qaysi qator va nega ekanini ayt, lekin to'g'ri kodni yozma.
- Javobing 150 so'zdan oshmasin, o'zbek tilida yoz.
```

| Line | What it says | Why |
|---|---|---|
| 1 | you are the tutor of a developer learning Go; the goal is that they write the code and understand the cause of the bug themselves | sets the goal: understanding, not an answer |
| 2 | don't write ready code, a fixed line or the right **function name**, even if asked; give a direction instead | the name `errors.As` alone is half the answer: the learner finds it in the docs |
| 3 | first read the learner's attempt: say what is right, then show which line has the mistake | narrows the search to one line without giving the solution |
| 4 | then ask one question and let them find the answer; don't answer your own question | the learner produces it (generation effect) |
| 5 | if the learner sends a fix, check it: if it's wrong, say which line and why, but don't write the correct code | stays a tutor on the second and third attempts too |
| 6 | no more than 150 words, write in Uzbek | a short answer is harder to skim |

We tested the rules with `claude -p --system-prompt "$(cat promptlar/ustoz-tizim.txt)"`. We did not test them in a
Claude.ai Project: you will check that they work there yourself (homework 🟢).

Anthropic has a similar idea. Claude for Education, first announced for universities, has a **Learning mode**.
According to the official announcement (2025-04-02), instead of a ready solution it asks *"How would you approach this

## The conversation with the tutor: three messages

Now we give the same code with the tutor rules (`promptlar/2-ustoz.txt`). Besides the code and the output, this prompt
has the learner's note: "last time `==` didn't work on a wrapped error and `errors.Is` helped". The conversation has
three messages and was repeated three times. We wrote messages 2 and 3 once and sent them unchanged in all three
conversations.

**Message 1.** Claude pointed at the wrong line exactly, but did not fix it. An excerpt from conversation 1
(`javoblar/2-ustoz/1-1.txt`):

```text
…

Xato `holat` funksiyasidagi `errors.Is(err, &MaydonXato{})` qatorida. `errors.Is` zanjirdagi har bir xatoni berilgan qiymatga `==` bilan solishtiradi. Ko'rsatkichlarda esa `==` ikkala ko'rsatkich xotirada aynan bir ob'ektga qaraganini tekshiradi, maydonlari bir xil bo'lishi yetmaydi.

Savol: `errors` paketida zanjirdan qiymatni emas, **turni** qidiradigan va topilganini senga qaytarib beradigan funksiya bormi? Uning nomini `go doc errors` orqali topib ko'r.
```

("The mistake is on the `errors.Is(err, &MaydonXato{})` line of the `holat` function. `errors.Is` compares each error
in the chain with the given value using `==`. For pointers, `==` checks that both pointers refer to the same object in
memory; having the same fields is not enough. Question: is there a function in the `errors` package that looks for a
**type** in the chain, not a value, and gives you back what it found? Try to find its name with `go doc errors`.")

As the rule says, it did not name the function. None of the three conversations has the name `errors.As` in message 1
(0/3).

**Message 2.** The learner found `errors.As` in the docs and wrote it themselves (`promptlar/3-urinish.txt`). This
attempt is in `urinish/main.go`; the changed lines inside `holat`:

```go
	// ikkinchi urinish: hujjatdan errors.As ni topdim
	var mx *MaydonXato
	if errors.As(err, mx) {
		return 400
	}
```

(The comment: "second attempt: I found errors.As in the docs".) The difference from the answer machine's code is one
character: `mx`, not `&mx`. What happens?

**A)** prints `400` · **B)** prints `500` · **C)** the program stops with a `panic` · **D)** a compile error

<details>
<summary>Answer</summary>

**C**, but only on the second request. The second parameter of `errors.As` has type `any`, so the compiler accepts
`mx` too (not "D"). `mx` is a `nil` pointer: nothing can be written into it. `errors.As` checks this at run time and
panics. On the first request `err == nil`, so `holat` never reaches `errors.As`, and the first line is printed. If you
chose "A", you thought `As` fills `mx` by itself: in Go a function can write into your variable only through its address
([GO-1.11](/lab/youtube/go/go-1-11/en)).

</details>

The full `panic` message with the stack trace is long; the first two lines are enough (`2>&1 | head -2` also takes the
error stream and shows only two lines):

```console
$ go run ./urinish 2>&1 | head -2
POST /buyurtma narx=12000 → 200 <nil>
panic: errors: target must be a non-nil pointer
```

`go vet` finds this mistake in advance:

```console
$ go vet ./urinish
urinish/main.go:35:5: second argument to errors.As must be a non-nil pointer to either a type that implements error, or to any interface type
```

`urinish/main.go`, line 35, column 5: the second argument to `errors.As` must be a non-nil pointer to a type that
implements `error`, or to an interface type.

Claude again did not fix it: it said the mistake is on this line, in fact in its second argument, and asked one question
(`javoblar/2-ustoz/1-2.txt`, excerpt):

```text
…

Xato `errors.As(err, mx)` qatorida, ikkinchi argumentda. `mx` hozir `nil` ko'rsatkich, `As` esa unga hech narsa yoza olmaydi. Panic xabari ham shuni aytyapti: `target must be a non-nil pointer`.

`As` topilgan xatoni sening o'zgaruvchingga **yozishi** kerak. Buning uchun unga o'zgaruvchining qiymatini emas, boshqa narsani berish lozim.

Savol: `mx` o'zgaruvchisining ichidagi qiymat emas, o'zgaruvchining o'zi qaerda turishini `As`ga bildirish uchun Go'da qaysi operatordan foydalanasan?
```

("The mistake is on the `errors.As(err, mx)` line, in the second argument. `mx` is a `nil` pointer now, and `As` cannot
write anything into it. The panic message says the same. `As` has to **write** the error it finds into your variable.
For that you must give it something other than the variable's value. Question: which Go operator do you use to tell
`As` where the variable `mx` itself is, not the value inside it?")

In none of the three conversations did Claude write `&mx`; it only asked how to pass it. With the picture from the
video: `var mx` is a pocket for the passport that is found, `&mx` is handing over that pocket, and `mx` is handing over
an empty hand.

**Message 3.** The learner did not answer that question: they remembered another way from GO-1.14, `errors.AsType`.
This function needs no pocket; it returns the error it finds. The new `holat` in `tuzatildi/main.go`:

```go
// holat: handler shu kod va matnni HTTP javobga yozadi
func holat(err error) (int, string) {
	if err == nil {
		return 200, "ok"
	}
	if errors.Is(err, ErrTopilmadi) {
		return 404, "topilmadi"
	}
	// zanjirdan *MaydonXato turidagi xatoni qidiradi va topilsa oʻzini qaytaradi (Go 1.26)
	if mx, ok := errors.AsType[*MaydonXato](err); ok {
		return 400, "notoʻgʻri maydon: " + mx.Maydon
	}
	return 500, "ichki xato"
}
```

| Code | What it does |
|---|---|
| `(int, string)` | now `holat` returns two values: the status and the response text (the learner also wanted to say which field is wrong) |
| `errors.AsType[*MaydonXato](err)` | the type being searched for is in square brackets (a type argument). If the chain has an error of this type, it returns it and `true` |
| `mx, ok := …; ok` | `mx` is the `*MaydonXato` that was found, visible only inside this `if`; `ok` says whether it was found |
| `"notoʻgʻri maydon: " + mx.Maydon` | writes which field is wrong into the response ("wrong field: …") |

`main` also takes the two values (`kod, matn := holat(err)`). We run the program again:

```console
$ go run ./tuzatildi
POST /buyurtma narx=12000 → 200 ok
POST /buyurtma narx=-5 → 400 notoʻgʻri maydon: narx
```

Now `narx=-5` gives `400` and the name of the wrong field: `narx` ("price").

At the end the learner wrote "did I understand correctly? Ask me one question". Claude confirmed the fix and asked a

1. **This measures rule-following, not learning.** We did not measure learning in people — the studies above and below

2. **The prompts differ in two places:** the tutor prompt has both the rules and the learner's note (`<urinishim>`, "my

## Recall: how to check that you understood

We said you check yourself even after the tutor. One of the best-studied ways is **recall** (*retrieval practice*).
Roediger and Karpicke (Psychological Science, 2006, Experiment 2): one group read a text four times. Another group read
it once and then three times closed the book and wrote down what they remembered.

| Group | After 5 minutes | After 1 week |
|---|---|---|
| reading only (4 times) | 83 % | 40 % |
| one reading + 3 recalls | 71 % | 61 % |

After five minutes the readers remembered more and were more confident. After a week, though, they remembered 40 %,
and the recall group 61 %. The illusion of knowing again: rereading gives the feeling "I know", but does not keep it in
memory for long.

Developers show a similar result. Anthropic researchers Shen and Tamkin (arXiv, 2026) gave 52 developers a task with an
unfamiliar Python library (Trio), at most 35 minutes long. Half of them got an AI assistant (it was GPT-4o). In the test
that followed, the AI group's average score was 50 %, the no-AI group's 67 %; the largest gap was on debugging
questions. Within the AI group, the 7 people who asked only for explanations (*conceptual inquiry*) scored high. The
authors do not claim a cause-and-effect link for these groups, and the test came right after the task.

**The code works. How do you know you really understood it?** Think before you open the answer (hint: the zipper
experiment).

<summary>Answer</summary>

Close the chat and try to write that line from memory. Or explain it to a teammate (or to a toy on your desk): what
`errors.Is` compares and why `errors.As` needs `&me`. If you cannot write it or explain it, it was the illusion of
knowing. Then go back to the tutor and ask again.

</details>

## Going deeper (optional): Claude Code's Learning style

Claude Code also has a **Learning** output style. According to the docs, in it Claude adds `Insight` blocks and leaves
part of the code to you: it writes a `TODO(human)` comment into the file and waits. We tested it on a copy of `bozor/`
(`uslub.sh`, `{"outputStyle": "Learning"}` in `.claude/settings.local.json`, print mode, 3 times). This test is not in
the video: it was narrow.

```console
$ go run ./olchov -code

Code: default    3/3         0/3    3/3      0/3         0/3
Code: Learning   3/3         0/3    3/3      0/3         2/3
```

On our single task the Learning style also wrote the code itself 3/3, `TODO(human)` 0/3, `Insight` 2/3. The reasons:
print mode (`claude -p`) cannot wait, our task was a plain "fix it", and the docs place `TODO(human)` where there is a
real design decision. The docs themselves warn: *"An output style gives Claude instructions to follow. It doesn't
guarantee that something always happens or never happens."* So your own tutor rules and a check like `olchov` are still
needed.

## Common mistakes

### 1. "The code works and I read the explanation, so I understood it"

The main trap of this lesson. The answer machine's code worked 3/3 and came with an explanation, but we wrote nothing.
In the Rozenblit and Keil experiment, too, the feeling "I know" dropped when people had to explain. The fix: close the
chat and write it from memory, or explain it (the "Recall" section). If it doesn't work, go back to the tutor.

### 2. "I have tutor rules, so I am learning"

In the GPT Tutor group the exam harm almost disappeared, but there was no benefit, and the students thought they had
done better. `olchov` also measures rule-following, not learning. The fix: check yourself even after the tutor, and ask
Claude for a check question at the end (homework 🟠).

### 3. `errors.Is(err, &MaydonXato{})`: searching for an error type with `Is`

A silent bug: it compiles, `go vet` is silent, the result is `500` (the "Experiment" section). `errors.Is` compares with
`==`, and a new `&MaydonXato{}` is never equal to the pointer in the chain. The fix: search by type.

```go
	if mx, ok := errors.AsType[*MaydonXato](err); ok {
		return 400, "notoʻgʻri maydon: " + mx.Maydon
	}
```

### 4. `errors.As(err, mx)` without `&`

`panic: errors: target must be a non-nil pointer`, and `go vet` warns about it in advance ("The conversation with the
tutor", message 2). The fix: `errors.As(err, &mx)`, or `errors.AsType`, which needs no pointer at all. Run `go vet` in
CI — it catches this mistake, but not mistake 3.

### 5. Writing the rules once and never checking them

A rule is an instruction, not a guarantee: even Claude Code's Learning style wrote the code itself on our task. The fix:
test your rules several times, store the answers and measure them (`takrorla.sh` + `olchov`), as in CL-1.03.

1. In the study by Bastani and colleagues, which group did worse in the exam than the no-AI group, and which group

<details>
<summary>Answer</summary>

GPT Base (like ChatGPT) did worse: +48 % in practice, −17 % once the AI was taken away, and the students did not

2. In the Roediger and Karpicke experiment, which group remembered more after 5 minutes? And after a week?

**A)** the recall group both times · **B)** the readers after 5 minutes, the recall group after a week · **C)** the
readers both times

<details>
<summary>Answer</summary>

**B.** After 5 minutes: reading only 83 %, recall 71 %. After a week: 40 % and 61 %. If you chose "A", you thought
recall wins right away: right away rereading wins, and that is why it fools you — the readers were also more confident.

</details>

3. What does this code return for `narx=-5`? (`tekshir` and `MaydonXato` as in `bozor/main.go`.)

```go
	var me *MaydonXato
	if errors.As(err, &me) {
		return 400
	}
	return 500
```

**A)** `400` · **B)** `500` · **C)** `panic`

<details>
<summary>Answer</summary>

**A.** This is the answer machine's code: `&me` is the address of the variable `me`; `errors.As` writes the
`*MaydonXato` it finds in the chain there and returns `true`. `olchov` checked this for all three answers:
`ishladi 3/3`. "C" would happen with `errors.As(err, me)`, without `&`.

</details>

4. Why does the second line of the tutor rules forbid even the function's **name**?

<details>
<summary>Answer</summary>

Because the name alone is half the answer: if the tutor says "use `errors.As`", the learner searches for nothing and
produces nothing. Without the name, the learner looks for an answer to the question ("is there a function that searches
for a type?") and finds it in the docs — that is the generation effect. In message 1 none of the three conversations had
the name (0/3).

</details>

5. From CL-1.02: where in Claude.ai do you put the tutor rules so you don't retype them in every conversation?

<details>

In the Project instructions. Every new conversation inside the Project gets these instructions. In the API and the

```go filename="homework/sinov/main.go" showLineNumbers
// sinov: Claude ustoz rejimida bergan uchta tekshiruv savoliga javobni ishga tushirib koʻrsatadi.
// Avval savollarga oʻzingiz javob yozing (README → Uy vazifasi), keyin: go run ./homework/sinov
package main

import (
	"errors"
	"fmt"
)

type MaydonXato struct{ Maydon, Sabab string }

func (e *MaydonXato) Error() string { return e.Maydon + ": " + e.Sabab }

// QiymatXato: xuddi shunday, lekin Error() qiymat qabul qiluvchida va pointersiz qaytariladi
type QiymatXato struct{ Maydon, Sabab string }

func (e QiymatXato) Error() string { return e.Maydon + ": " + e.Sabab }

func main() {
	err := fmt.Errorf("tekshir: %w", &MaydonXato{Maydon: "narx", Sabab: "musbat boʻlishi kerak"})

	// 1-savol: errors.Is qiymatni (bu yerda pointer manzilini) solishtiradi, AsType esa turni qidiradi
	_, ok := errors.AsType[*MaydonXato](err)
	fmt.Println("1. errors.Is(err, &MaydonXato{}):", errors.Is(err, &MaydonXato{}), "· AsType[*MaydonXato]:", ok)

	// 2-savol: yana bir qavat %w bilan oʻrasak zanjir saqlanadi, %v bilan esa uziladi
	w := fmt.Errorf("handler: %w", err)
	v := fmt.Errorf("handler: %v", err)
	_, okW := errors.AsType[*MaydonXato](w)
	_, okV := errors.AsType[*MaydonXato](v)
	fmt.Println("2. %w bilan yana oʻralgan:", okW, "· %v bilan:", okV)

	// 3-savol: xato pointersiz qaytsa, *QiymatXato turi zanjirda yoʻq
	q := fmt.Errorf("tekshir: %w", QiymatXato{Maydon: "narx", Sabab: "musbat boʻlishi kerak"})
	_, okP := errors.AsType[*QiymatXato](q)
	_, okQ := errors.AsType[QiymatXato](q)
	fmt.Println("3. pointersiz xato: AsType[*QiymatXato]:", okP, "· AsType[QiymatXato]:", okQ)
}
```

```console
$ go run ./homework/sinov
1. errors.Is(err, &MaydonXato{}): false · AsType[*MaydonXato]: true
2. %w bilan yana oʻralgan: true · %v bilan: false
3. pointersiz xato: AsType[*QiymatXato]: false · AsType[QiymatXato]: true
```

- (1) `errors.Is` compares each error in the chain with `==`; for pointers that means "exactly this address?", and a
  new `&MaydonXato{}` is a different address. `AsType`, on the other hand, looks for the **type**.
- (2) `%w` keeps the chain — the number of layers does not matter, `holat` returns 400. `%v` turns the error into plain
  text, the chain breaks → 500.
- (3) The chain has a `QiymatXato` (a value), not a `*QiymatXato` (a pointer), so `false`; you need
  `AsType[QiymatXato]` (provided `Error()` is on a value receiver). The type must match exactly. The file has a separate
  `QiymatXato` type ("value error") for this question, because the `Error()` of `MaydonXato` is on a pointer receiver.
