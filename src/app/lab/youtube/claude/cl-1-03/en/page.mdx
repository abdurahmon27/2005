## What you will learn

We sent Claude Sonnet 5.5 one line: "Go'da xato tekshirish ishlamayapti, nega?" ("Error checking doesn't work in Go,
why?"). We asked three times and got three answers of 340–374 words. Each had seven guesses, and the real cause was in
3rd or 4th place. Then we described the same bug to the same model in a different way. We got a 31-word fix that works
when you run it. The model was the same. What changed? Today we find out with seven prompts, 21 stored answers and a
Go program that measures them.

**One idea:** a prompt is a technical spec for the model. The model sees only the text you wrote, so the context (code,
version, expected and actual result) and the output format change the answer the most. And you learn whether any
technique helps by measuring and running, not by guessing.

By the end of the lesson you will:

- turn a one-line question into a full prompt that reads like a bug report: context, code, actual output, format and
  the reason for it;
- show which part of the prompt changed what in the answer, by running each prompt three times and measuring with a Go
  program;
- know when to add a few-shot example and XML tags: an example changes the shape of the answer, not its correctness;
- know why prefill and `temperature` from old tutorials return an error on current models.

The three core new words of this lesson:

| Word | Plain meaning | English term |
|---|---|---|
| prompt | the task you write for the model: question, context, code, requirements, all in one text | prompt |
| few-shot example | a sample answer inside the prompt: "write it like this" | few-shot example |
| XML tag | markers like `<kod>…</kod>` that separate the parts of a prompt | XML tag |

Helper words get one plain sentence where they first appear: **context** (facts about the task), **output format** (what
the answer should look like), **success criteria** (when an answer counts as "good"), **system prompt** and
**prefill**.

First, a question from CL-1.01. Why do we send each prompt three times?

**A)** the model samples every time, so the answer can change · **B)** with `temperature: 0` once would be enough, but
we forgot · **C)** the API gives a short answer to the first request

<details>
<summary>Answer</summary>

**A.** At every step the model computes probabilities for the next token and picks one (sampling). So the same prompt
can give different answers, and a single answer can be a fluke. If you chose "B", you forgot two conclusions of CL-1.01.
First, even `temperature: 0` does not guarantee identical output. Second, current models have no `temperature` at all:
the Sonnet 5.5 docs say "Sampling parameters return an error". "C" is made up: there is no such rule.

</details>

The first prompt is one line:

`grep -E '^\*\*[0-9]'` prints only lines that start with `**` and a digit, that is, the bold Markdown headings. Seven

goroutines, in `defer`, mixing with `panic`/`recover`. Our bug is item 4: comparing a wrapped error with `==`. The 2nd
and 3rd answers also have seven guesses each, with the real cause in 4th and 3rd place. The end of the answer:

```console
$ tail -7 javoblar/1-yomon/1.txt

Aniq sababni topish uchun, iltimos, quyidagilarni yuboring:
- Muammoli kod bo'lagi
- Kutgan natija va aslida nima bo'layotgani
```

Claude asked for the code and the expected and actual result (and the error text, if any); the 2nd and 3rd answers
also asked for the Go version (`go version`). This is not a bad answer: there is no other way to answer a question
without code. The model cannot answer without guessing, because it cannot see the code. The last sentence ("if you
want, I'll look at the Go files in the working folder myself") is curious: in the experiment Claude could not read
files, as the next section shows.

## How the experiment was run

One script produced all the answers (`takrorla.sh`, "repeat"). It uses the **print mode** of Claude Code (`claude -p`):
it sends the prompt, prints the answer and exits, with no chat.

```bash filename="takrorla.sh" showLineNumbers
#!/usr/bin/env bash
# takrorla.sh promptlar/2-kontekst.txt [N]
# Promptni Claude'ga N marta (standart 3) beradi, javoblarni javoblar/<prompt>/ ga yozadi:
#   <i>.txt   javob matni, oʻzgartirilmagan
#   <i>.json  sana, model, tokenlar, vaqt
# Javob har safar boshqacha boʻlishi mumkin: shuning uchun uchta javob saqlaymiz.
set -euo pipefail
prompt=$(realpath "$1"); n=${2:-3}; model=${MODEL:-claude-sonnet-5-5}
dir=$(realpath javoblar)/$(basename "$prompt" .txt); mkdir -p "$dir"
cd "$(mktemp -d)"   # boʻsh papka: CLAUDE.md va loyiha fayllari taʼsir qilmasin
for i in $(seq 1 "$n"); do
  # boʻsh system prompt, asboblarsiz: Claude faqat bizning promptni oladi
  claude -p --model "$model" --effort high --system-prompt "" --tools "" \
    --setting-sources "" --strict-mcp-config --disable-slash-commands \
    --no-session-persistence --output-format json < "$prompt" > raw.json
  jq -r .result raw.json > "$dir/$i.txt"
  jq --arg sana "$(date -u +%FT%TZ)" --arg model "$model" \
    --arg prompt "$(basename "$prompt")" \
    '{sana: $sana, model: $model, prompt: $prompt, effort: "high",
      stop_reason, duration_ms, output_tokens: .usage.output_tokens,
      input_tokens_jami: (.usage.input_tokens + .usage.cache_creation_input_tokens
                     + .usage.cache_read_input_tokens),
      models: (.modelUsage | keys)}' raw.json > "$dir/$i.json"
  echo "$dir/$i.txt: $(wc -w < "$dir/$i.txt") soʻz"
done
```

| Line | Code | What it does |
|---|---|---|
| 7 | `set -euo pipefail` | if any command fails, the script stops |
| 8 | `n=${2:-3}`, `model=${MODEL:-…}` | number of runs (default 3) and the model (default `claude-sonnet-5-5`) |
| 9 | `dir=…/javoblar/<prompt name>` | `promptlar/3-format.txt` → `javoblar/3-format/` |
| 10 | `cd "$(mktemp -d)"` | moves to an empty temp folder: CLAUDE.md and project files do not affect the answer |
| 13 | `--effort high --system-prompt "" --tools ""` | high effort, an empty **system prompt**, no tools: Claude cannot read files or run commands |
| 14–15 | `--setting-sources ""` … `--output-format json` | settings, MCP and slash commands off; no saved session; JSON result |
| 16 | `jq -r .result` | the answer text goes to `<i>.txt` unchanged |
| 17–23 | `jq … > "$dir/$i.json"` | next to it: date, model, effort, token counts and time |
| 24 | `wc -w` | prints the answer's word count |

A **system prompt** is a standing instruction the model gets before your message; the Project instructions from
CL-1.02 are similar. We left it empty, so that only the prompt itself affects the answer.

Two honest caveats (from the README):

1. **The CLI preamble.** Even with `--system-prompt ""`, the CLI still adds a short system text. For the one-line
   prompt `input_tokens_jami` ("input tokens, total") is 581, while the prompt itself is about 12 tokens. So the
   preamble is about 570 tokens, and we cannot see its content. The "I'll look at the files myself" sentence in the
   bad-prompt answer probably comes from it.
2. **The Haiku entry.** The `models` list in the `.json` also has `claude-haiku-5-5`. That is a small housekeeping call
   by the CLI itself; Sonnet 5.5 wrote the answer.

We add four things to the prompt, one at a time: context, output format, an example and XML tags. At each step we
measure with a Go program how the answer changes. The seven prompts are built around one bug, and each adds one thing
to the one before:

| Prompt | What was added | Question |
|---|---|---|
| `1-yomon` ("bad") | one line | why doesn't error checking work? |
| `2-kontekst` | who, which project, Go version, expected result, the whole code, `go run` output | same |
| `3-format` | output format (exactly 3 lines) and why that format | same |
| `4-misol` ("example") | one sample answer for a different bug (nil map) | same |
| `5-xml` | same content as 4, but in XML tags | same |
| `6-test` | code + task, in XML tags | write a table test for `holat` |
| `7-test-misol` | 6 + the `kabisa` test from GO-1.07 as an example | same |

7 prompts × 3 = 21 answers, plus 2 × 3 = 6 more in the homework. All on GitHub, with date and model.

## Context: show the prompt to a colleague who doesn't know the task

Anthropic's prompting guide (*Prompting best practices*) compares Claude to a "brilliant but new employee" who lacks
context on your norms and work processes (workflows). The same page gives the test: show your prompt to a colleague with minimal
context on the task and ask them to follow it.

A colleague who gets our one-line question asks at once: which code? which Go version? what was expected and what
happened? Every GitHub issue template asks the same: *steps to reproduce*, *expected*, *actual*, *version*. And Claude
asked exactly this at the end of its answer. In this sense a prompt is a technical spec: the contractor knows only
what is written.

The second prompt has everything the colleague asked for. The start:

```console
$ head -3 promptlar/2-kontekst.txt
Men Go'ni o'rganyapman va bozor degan onlayn do'kon backend'ini yozyapman. Go 1.26.8.
Mavjud bo'lmagan buyurtma uchun 404 qaytishi kerak, lekin 500 qaytyapti.
Xatoni o'zim tuzatib, sababini tushunmoqchiman.
```

In three lines: "I'm learning Go and writing the backend of an online shop called bozor. Go 1.26.8. A missing order
should return 404, but it returns 500. I want to fix the bug myself and understand the cause." So: who is writing and
which project, the Go version, the expected result (404) and the actual one (500). Remember the third line; it matters
later. This is **context**: facts about the task. The difference from the context window of CL-1.01: the context
window is all the text the model sees, while context is the needed facts you put into it.

Below that is the whole code. This is the file pasted into the prompt:

```go filename="bozor/main.go" showLineNumbers
package main

import (
	"errors"
	"fmt"
)

var ErrTopilmadi = errors.New("buyurtma topilmadi")

var buyurtmalar = map[string]string{"1": "olma, 2 kg"}

func topish(id string) (string, error) {
	b, ok := buyurtmalar[id]
	if !ok {
		return "", fmt.Errorf("topish %s: %w", id, ErrTopilmadi)
	}
	return b, nil
}

// holat: handler shu kodni HTTP javobga yozadi
func holat(err error) int {
	if err == nil {
		return 200
	}
	if err == ErrTopilmadi {
		return 404
	}
	return 500
}

func main() {
	for _, id := range []string{"1", "42"} {
		_, err := topish(id)
		fmt.Printf("GET /buyurtma/%s → %d %v\n", id, holat(err), err)
	}
}
```

| Line | Code | What it does |
|---|---|---|
| 8 | `var ErrTopilmadi = errors.New(…)` | one package-level error value, a **sentinel error** (GO-1.14): `ErrTopilmadi` ("not found") |
| 10 | `var buyurtmalar = map[string]string{…}` | a map instead of a "database": only order `"1"` exists (`buyurtmalar`, "orders") |
| 12–18 | `func topish(id string) (string, error)` | looks up an order (`topish`, "find"); if missing, returns `ErrTopilmadi` wrapped with `%w` |
| 15 | `fmt.Errorf("topish %s: %w", id, ErrTopilmadi)` | a new error: its text is `topish 42: buyurtma topilmadi`, the original `ErrTopilmadi` inside |
| 21–29 | `func holat(err error) int` | turns the error into an HTTP status code (`holat`, "status"): `nil` → 200, not found → 404, anything else → 500 |
| 25 | `if err == ErrTopilmadi {` | **the bug is here**: the wrapped error is not `ErrTopilmadi` itself |
| 31–35 | `main` | simulates two requests: `/buyurtma/1` and `/buyurtma/42` |
| 34 | `fmt.Printf("GET /buyurtma/%s → %d %v\n", …)` | `%s` is a string, `%d` an integer, `%v` the error's text (`<nil>` if `nil`) |

Under the code the prompt gives its real output. Get it yourself:

```console
$ go run ./bozor
GET /buyurtma/1 → 200 <nil>
GET /buyurtma/42 → 500 topish 42: buyurtma topilmadi
```

Order 42 does not exist, 404 was expected, but 500 came back. Anyone who has seen GO-1.14 knows why:

```text
err returned by topish("42"):
  *fmt.wrapError  "topish 42: buyurtma topilmadi"
        │ Unwrap()
        ▼
  ErrTopilmadi    "buyurtma topilmadi"

err == ErrTopilmadi            → false  (two different values)
errors.Is(err, ErrTopilmadi)   → true   (looks inside along the chain)
```

`==` compares only the outer value. `errors.Is` walks the error chain with `Unwrap` and finds `ErrTopilmadi` inside.
The fix is one line:

```console
$ diff bozor/main.go tuzatildi/main.go
25c25
< 	if err == ErrTopilmadi {
---
> 	if errors.Is(err, ErrTopilmadi) {
```

`diff` prints the difference between two files: `25c25` means "line 25 changed", `<` is the old file, `>` the new one
(`tuzatildi`, "fixed").

You don't have to retype the permanent context (who you are, which project, which Go version) every time: that is what
the Project instructions from CL-1.02 are for. In this experiment we wrote it into the prompt on purpose, to keep the
measurement clean.

## The answer with context: cause found, no ready line

The context is in. What do you think the answer will contain?

**A)** the cause, plus a copy-ready `if errors.Is(err, ErrTopilmadi) {` line · **B)** the cause, but no ready line ·
**C)** seven guesses again, because the question didn't change

<details>
<summary>Answer</summary>

**B.** We read all three answers: all three found the cause correctly (an error wrapped with `%w` is not found by `==`;
you need `errors.Is`). The answers shrank to 196, 208 and 234 words. But none of them has the ready
`errors.Is(err, ErrTopilmadi)` line. If you chose "A", you missed one sentence inside the prompt. If you chose "C", you
forgot that it is the context, not the question, that changes the answer.

</details>

One answer even gave a link to the docs and said "replace the condition yourself":

```console
$ grep -h "o'zingiz almashtiring" javoblar/2-kontekst/*.txt
`errors.Is(err, target)` imzosini [pkg.go.dev/errors#Is](https://pkg.go.dev/errors#Is) sahifasida ko'rib chiqing va `holat` ichidagi shartni o'zingiz almashtiring.
```

`grep -h` prints the matching line without the file name. In English: "Look up the signature of `errors.Is(err, target)`
on pkg.go.dev/errors#Is and replace the condition inside `holat` yourself." Why no ready line? The reason is in the
prompt: we wrote "I want to fix the bug myself and understand the cause". Claude did what we asked: it showed the way
and did not write the code. Context changes both the precision of the answer and its tone. We judged "the cause is
right" by reading, not with a program; the "no ready line" part is also confirmed by the measuring program below.

## Output format: three lines and the "why"

In the third prompt we add an **output format**: what the answer must look like. This is the **constraint** in the
lesson title: exactly three lines and nothing else. The end of the prompt:

```console
$ tail -4 promptlar/3-format.txt
Javobni terminalda o'qiyman, shuning uchun o'zbekcha, aynan uch qator yoz, boshqa hech narsa qo'shma:
Sabab: <bitta gap>
Tuzatish: <o'zgaradigan bitta Go qatori>
Tekshirish: <bitta buyruq>
```

In English: "I read the answer in the terminal, so write in Uzbek, exactly three lines, add nothing else: `Sabab:`
(cause) &lt;one sentence>, `Tuzatish:` (fix) &lt;one Go line that changes>, `Tekshirish:` (check) &lt;one command>". The first
line gives the format together with its reason: "I read the answer in the terminal". Anthropic's docs (*Add context to
improve performance*) say that if you explain why a rule matters, Claude understands your goal better: "Claude can
generalize from the explanation". That is the docs' claim: we did not measure the effect of the reason sentence alone.

A format is like an API contract: whoever reads the answer (you, a terminal or a script) knows in advance which field
is where. The result:

```console
$ cat javoblar/3-format/1.txt
Sabab: `topish` xatoni `%w` bilan o'rab qaytaradi, shuning uchun `err == ErrTopilmadi` taqqoslashi false bo'ladi (err endi o'ralgan xato, `ErrTopilmadi` o'zi emas).
Tuzatish: `if errors.Is(err, ErrTopilmadi) {`
Tekshirish: `go run ./bozor`
```

31 words, three lines and a ready fix. We sent it three times, and the three answers came out almost word for word the
same: they differ only in "`ErrTopilmadi` o'zi", "`ErrTopilmadi`ning o'zi" and "ErrTopilmadi'ning o'zi" (spellings of
"`ErrTopilmadi` itself"). The tokens tell the same story: the 1-yomon answers took 1375–1582 output tokens and 12–16
seconds, the 3-format answers 144–146 tokens and 2–6 seconds (from the `.json` files).

## Measuring: success criteria first

"The answer got better" should be a number, not a feeling. Anthropic's *Prompt engineering overview* page assumes two
things before you write a prompt: clear **success criteria** (when an answer counts as good) and a way to test against
them empirically. Our criterion is clear: there is a fix line, and it works. The test is a Go program in the `olchov/`
("measurement") folder. It measures the 15 answers to prompts 1–5.

Before you look at the table, think: from which prompt on does the `404` column fill up (Claude's line is inserted into
the code and run), and how much do the example (4) and XML (5) improve the result?

<details>
<summary>Answer</summary>

`404` is 3/3 from 3-format on, because only the format asks for a fix line. The example and XML changed nothing in this
small, precise task: the format was already 3/3, so there was nothing left to improve. If you expected a big jump from
the example and XML, that is natural: many tutorials present them as a universal fix.

</details>

```console
$ go run ./olchov
prompt        soʻz (3 marta)  format  tayyor      404
1-yomon       340 374 345     0/3     0/3         —
2-kontekst    196 208 234     0/3     0/3         —
3-format      31 31 31        3/3     3/3         3/3
4-misol       28 32 29        3/3     3/3         3/3
5-xml         32 27 28        3/3     3/3         3/3
```

| Column | What it measures |
|---|---|
| `soʻz (3 marta)` | word counts of the three answers ("words, 3 times"); this is length, not quality |
| `format` | the answer is exactly three lines starting with `Sabab:`, `Tuzatish:`, `Tekshirish:` |
| `tayyor` | the answer contains a copy-ready `errors.Is(err, ErrTopilmadi)` ("ready") |
| `404` | the `Tuzatish:` line is inserted into the code, the program runs, and `/buyurtma/42` really returns 404; `—` means there is nothing to test |

The word count fell from 340 to about 30. The format and the ready line appeared only from prompt 3. The most important
column is the last one: the program ran Claude's line and got 404 in all nine answers.

The full program is in `olchov/main.go` (227 lines). Here are its main parts. The `format` column:

```go
// formatda: boʻsh boʻlmagan qatorlar aynan uchta va kerakli soʻzlar bilan boshlanadi
func formatda(javob string) bool {
	var q []string
	for _, l := range strings.Split(javob, "\n") {
		if strings.TrimSpace(l) != "" {
			q = append(q, strings.TrimSpace(l))
		}
	}
	return len(q) == 3 && strings.HasPrefix(q[0], "Sabab:") &&
		strings.HasPrefix(q[1], "Tuzatish:") && strings.HasPrefix(q[2], "Tekshirish:")
}
```

The answer is split into lines and empty lines are dropped. Then three conditions: exactly three lines, each starting
with the right word. `strings.HasPrefix(s, p)` reports whether `s` starts with `p`. The code comments are in Uzbek, as
in the whole course: "formatda: exactly three non-empty lines, starting with the needed words".

Extracting the `Tuzatish:` line:

```go
// tuzatish: «Tuzatish:» qatoridagi Go kodi (` belgilarisiz)
func tuzatish(javob string) (string, bool) {
	for _, l := range strings.Split(javob, "\n") {
		l = strings.TrimSpace(l)
		if s, ok := strings.CutPrefix(l, "Tuzatish:"); ok {
			s = strings.TrimSpace(strings.Trim(strings.TrimSpace(s), "`"))
			return s, s != ""
		}
	}
	return "", false
}
```

`strings.CutPrefix` cuts `Tuzatish:` off the start of the line and returns the rest; `ok` means the prefix was there.
`strings.Trim(…, "`")` removes the Markdown backticks: `` `if errors.Is(err, ErrTopilmadi) {` `` →
`if errors.Is(err, ErrTopilmadi) {`.

The `404` column matters most, because it runs the answer:

```go
// ishlat: tuzatilgan kodni vaqtinchalik papkada ishga tushiradi, /buyurtma/42 holatini qaytaradi
func ishlat(kod, yangi string) string {
	if !strings.Contains(kod, eski) {
		return "eski qator topilmadi"
	}
	dir := vaqtinchalik(map[string]string{"main.go": strings.Replace(kod, eski, yangi, 1)})
	defer os.RemoveAll(dir)
	cmd := exec.Command("go", "run", ".")
	cmd.Dir = dir
	out, err := cmd.CombinedOutput()
	if err != nil {
		return "kompilyatsiya xatosi"
	}
	for _, l := range strings.Split(string(out), "\n") {
		if s, ok := strings.CutPrefix(l, "GET /buyurtma/42 → "); ok {
			return strings.Fields(s)[0]
		}
	}
	return "natija yoʻq"
}
```

```text
answer ──► «Tuzatish:» line ──► replaces line 25 of bozor/main.go
                                 (eski = "if err == ErrTopilmadi {")
       ──► temp folder: main.go + go.mod ──► go run .
       ──► «GET /buyurtma/42 → 404 …» ──► "404"
```

`eski` ("old") is a constant at the top of the file: `"if err == ErrTopilmadi {"`. `strings.Replace(kod, eski, yangi,
1)` replaces it with Claude's line (1 means only the first match). `vaqtinchalik` ("temporary") creates a new folder
and writes `main.go` and `go.mod` into it. `exec.Command("go", "run", ".")` runs the program in that folder, and
`cmd.CombinedOutput()` collects its output. If the code does not compile, the result is `kompilyatsiya xatosi`
("compile error"). If it does, the first word on the order-42 line is taken: `404` or `500`. `defer os.RemoveAll(dir)`
deletes the folder when the function returns.

So the `404` column does not mean "Claude said the right thing"; it means "Claude's line worked". Running a model's
answer instead of just reading it is the rule from CL-1.01 in practice.

## XML tags and long prompts

Prompts 5, 6 and 7 use **XML tags**: each part of the prompt sits inside its own tag. Like a Markdown code block or a
*boundary* in a multipart request, a tag says exactly where a part starts and where it ends. The structure of prompt 5:

```console
$ grep -n '^<' promptlar/5-xml.txt
1:<kontekst>
5:</kontekst>
7:<kod fayl="bozor/main.go">
44:</kod>
46:<natija buyruq="go run ./bozor">
49:</natija>
51:<format>
56:</format>
58:<misol>
64:</misol>
66:<savol>Nega 404 emas?</savol>
```

`grep -n` also prints the line number. Prompt 5 has the same content as prompt 4, only split into tags (`kontekst`,
`kod`, `natija` "output", `format`, `misol` "example", `savol` "question"). Prompt 7 needs tags most, because it has two
different pieces of Go code.

```text
<kod fayl="bozor/main.go">      our code: the test is for this
   …
</kod>
<misol fayl="kabisa_test.go">   only a sample, another package (kabisa)
   …
</misol>
<vazifa>                        what to do
   …
</vazifa>
```

The tags separate our code from the code that is only a sample (`vazifa`, "task"). Anthropic's docs (*Structure prompts
with XML tags*) say: XML tags help Claude parse complex prompts unambiguously; use consistent, descriptive tag names
across your prompts; nest tags when content has a natural hierarchy. There are no special "correct" tag names: we used
Uzbek names (`kod`, `misol`, `vazifa`), and the answers came out right.

But the honest conclusion: we could not see a separate effect of XML in this experiment. In the measurement table
4-misol and 5-xml are the same: 3/3, 3/3, 3/3.

For long prompts the docs have one more specific tip (*Long context prompting*). If the text is over 20,000 tokens, put
long documents at the top of the prompt and the question at the end. In Anthropic's tests, queries at the end improved
response quality by up to 30 percent, especially with complex, multi-document inputs. That number is about where the
question goes, not about XML. Our small prompts are under 1,400 tokens (`input_tokens_jami` 1327 and 1374, including
the CLI preamble), so they are not a case of this: variants 4 and 5 gave the same result.

| Prompt size | Tip | In our experiment |
|---|---|---|
| small, one task | precise context + format is enough | nothing changed after 3-format |
| several different parts (code + sample) | separate them with XML tags | prompt 7: tags say which code is ours |
| 20,000+ tokens, many documents | documents first, question last | not tested (docs: up to 30 percent better) |

## Two techniques from old tutorials: prefill and temperature

Old tutorials on the internet show two more techniques. Neither works on current models.

**Prefill** means writing the start of Claude's answer yourself: the list of messages in the request ends with an
assistant message, and the model continues it. Anthropic's *Prompt Engineering Interactive Tutorial* teaches this in
chapter 5 ("Speaking for Claude"): `{"role": "assistant", "content": prefill}`. It is a good course, but it was written
for the old Claude 3 Haiku model. The migration guides of the four current models say:

| Model | Prefill | `temperature`, `top_p`, `top_k` |
|---|---|---|
| Sonnet 5.5 | «rejects a prefilled last assistant turn with a 400 error» | «Sampling parameters return an error» |
| Opus 5.5 | «Don't end `messages` with a prefilled assistant turn: it is rejected» | «Omit `temperature`, `top_p`, and `top_k`» |
| Haiku 5.5 | «rejects it with a 400 error, even with thinking turned off» | remove them |
| Fable 5.2 | «Prefilling the assistant message returns a 400 error» | «Omit `temperature`, `top_p`, and `top_k`» |

400 is the HTTP "bad request" code: the API does not run the request at all. The second technique is tuning
`temperature`, `top_p` and `top_k` (the sampling parameters of CL-1.01). If you send them, you now get an error too. We
did not call the API for this page, so we don't show the error text: everything above is quoted from the docs.

In both cases the docs point to one path: state what you want clearly in the prompt itself. Our 3-format prompt does
exactly that: it sets how the answer starts with a format requirement, not with prefill.

## Common mistakes

### 1. "The model sees my code"

The classic misconception of this topic. The model sees only the text of the prompt (CL-1.01). For a question without
code it wrote a 340–374-word list with seven guesses and asked for the code at the end (section "A one-line
question"). Fix: put everything a bug report has into the prompt: code, version, expected and actual result.

### 2. A self-contradicting prompt

A silent bug: there is no message, you just get an answer you did not expect. If you write "I'll fix it myself" but ask
for a `Tuzatish:` line in the format, you get ready code (section "A self-contradicting prompt"). Fix: point the wish
and the format in the same direction. If you want to learn, use `Ishora:` and "don't write ready code".

### 3. "Examples and XML always help"

In our small task they changed nothing (4-misol = 5-xml = 3-format). The example changed the shape, not the
correctness. An example also carries over unwanted patterns: in homework task 3 Claude even copied the `ʻ` letter from
the example's comments. Fix: add an example only when the shape matters, use several varied ones, and measure the
result.

### 4. Prefill or `temperature` from an old tutorial

On current models such a request comes back with a 400 error (section "Two techniques from old tutorials"). We did not
call the API, so we don't show the error text. Fix: remove the parameter or the final assistant message and state what
you want in the prompt.

### 5. "It worked once, so the prompt is good"

One answer can be a fluke. Even three nearly identical answers are not proof yet (CL-1.01: consistency is not
correctness). Here only the `404` and `PASS`/`FAIL` columns say "correct", because they run the code. Fix: send each
prompt several times and check the answer by running it.

### 6. Program errors: wrong folder and no `./`

`olchov` reads the stored files from the current folder. If you run it outside the lesson folder (`cd ..` goes one
folder up):

```console
$ cd .. && go run ./cl-03-prompt/olchov
bu papkadan ishga tushiring: open bozor/main.go: no such file or directory
exit status 1
```

The program wrote the first line (line 41): "bu papkadan ishga tushiring" ("run it from this folder"), then Go's error:
"could not open `bozor/main.go`: no such file or directory". `go run` adds `exit status 1`. Fix: `cd cl-03-prompt` and
`go run ./olchov`.

If you leave out `./`:

```console
$ go run olchov
package olchov is not in std (/nix/store/h3rc4y3szd0391wryw9hslrijdvni030-go-1.26.8/share/go/src/olchov)
```

"Package `olchov` is not in the standard library". Without `./`, Go looks for `olchov` as a standard package name like
`fmt`, not as a folder. The path in parentheses is where Go is installed; yours will differ. Fix: `go run ./olchov`.

All three answers have the cause and "where to look"; the ready line is 0/3. One answer read `Tekshirish:` differently:

```console
$ grep -h '^Tekshirish' homework/javoblar/ishora/*.txt
Tekshirish: `go run ./bozor`
Tekshirish: `go doc errors.Is`
Tekshirish: `go run ./bozor`
```

`go doc errors.Is` is also "one command", but it shows the docs, not the fix. The prompt also says "don't write ready
code", so the result cannot be credited to the word `Ishora` alone. Now you write the fix yourself; CL-1.04 is about
this approach.

🟠 The prompt is `homework/qiyin.txt` ("hard"): two examples inside `<misollar>`, `kabisa` (a struct table) and `TestLuhn`
from cl-02 (a map, no `t.Run`). All three answers took the struct-table style:

```console
$ grep -E '^func Test|:= \[\]struct' homework/javoblar/qiyin/*.txt
homework/javoblar/qiyin/1.txt:func TestHolat(t *testing.T) {
homework/javoblar/qiyin/1.txt:	jadval := []struct {
homework/javoblar/qiyin/2.txt:func TestHolat(t *testing.T) {
homework/javoblar/qiyin/2.txt:	jadval := []struct {
homework/javoblar/qiyin/3.txt:func TestHolat(t *testing.T) {
homework/javoblar/qiyin/3.txt:	jadval := []struct {
```

But there is one unexpected difference. The comments of `TestLuhn` write Uzbek letters with `ʻ` (U+02BB), and now Claude
wrote them that way too:

```console
$ grep -c 'ʻ' homework/javoblar/qiyin/*.txt javoblar/7-test-misol/*.txt
homework/javoblar/qiyin/1.txt:5
homework/javoblar/qiyin/2.txt:4
homework/javoblar/qiyin/3.txt:4
javoblar/7-test-misol/1.txt:0
javoblar/7-test-misol/2.txt:0
javoblar/7-test-misol/3.txt:0
```

`grep -c` prints the number of matching lines in each file. The prompt 7 answers used a plain `'`; the two-example
prompt got `ʻ` (`oʻralgan`). This is a small but real case of the unintended pattern the docs warn about. All three
tests passed with `tuzatildi/` and failed with `bozor/`.

🔴 The solution is in `homework/guru/main.go`. It uses regular expressions to count, in each test answer, the
`func Test` lines and the table cases (lines starting with `{"nom", …}` or `nom: "…"`):

```console
$ go run ./homework/guru
6-test        Test funksiya: 2 2 2 · holat: 11 11 11
7-test-misol  Test funksiya: 1 1 1 · holat: 6 6 7
```

These numbers are used in the table of the "Example" section.
