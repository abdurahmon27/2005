## Что вы узнаете

Мы написали Claude Sonnet 5.5 одну строку: «Go'da xato tekshirish ishlamayapti, nega?» («В Go не работает проверка
ошибки, почему?»). Спросили три раза и три раза получили ответ на 340–374 слова. В каждом семь догадок, а настоящая
причина стоит на 3-м или 4-м месте. Потом той же модели мы описали ту же ошибку по-другому и получили исправление
на 31 слово, которое работает, если его запустить. Модель была та же. Что изменилось? Сегодня разберём это на семи
промптах, 21 сохранённом ответе и программе на Go, которая их измеряет.

**Одна идея:** промпт — это техническое задание для модели. Модель видит только текст, который вы написали, поэтому
сильнее всего ответ меняют контекст (код, версия, ожидаемый и фактический результат) и формат ответа. А пользу любого
приёма вы узнаёте не догадкой, а измерением и запуском.

К концу урока вы:

- превратите вопрос в одну строку в полный промпт, похожий на баг-репорт: контекст, код, фактический результат, формат
  и его причина;
- покажете, какая часть промпта что изменила в ответе: запустите каждый промпт три раза и измерите программой на Go;
- будете знать, когда добавлять few-shot пример и XML-теги: пример меняет форму ответа, а не его правильность;
- будете знать, почему prefill и `temperature` из старых руководств на нынешних моделях возвращают ошибку.

Три главных новых слова урока:

| Слово | Простой смысл | По-английски |
|---|---|---|
| промпт | ваше задание модели: вопрос, контекст, код, требования, всё в одном тексте | prompt |
| few-shot пример | образец ответа внутри промпта: «пиши вот так» | few-shot example |
| XML-тег | метки вроде `<kod>…</kod>`, которые разделяют части промпта | XML tag |

Вспомогательные слова объясняются одной фразой там, где встречаются впервые: **контекст** (сведения о задаче),
**формат ответа** (как должен выглядеть ответ), **критерий успеха** (когда ответ считается «хорошим»),
**системный промпт** (system prompt) и **prefill**.

Сначала вопрос из CL-1.01. Почему мы даём каждый промпт три раза?

**A)** модель каждый раз делает сэмплирование (sampling), ответ может меняться · **B)** с `temperature: 0` хватило бы
одного раза, но мы забыли · **C)** API отвечает на первый запрос коротко

<details>
<summary>Ответ</summary>

**A.** На каждом шаге модель считает вероятности для следующего токена и выбирает один (сэмплирование). Поэтому один и
тот же промпт может дать разные ответы, а один ответ может оказаться случайным. Если вы выбрали «B», вы забыли два
вывода CL-1.01. Во-первых, даже `temperature: 0` не гарантирует полной одинаковости. Во-вторых, у нынешних моделей
температуры (`temperature`) нет вовсе: в документации Sonnet 5.5 сказано «Sampling parameters return an error»
(«параметры сэмплирования возвращают ошибку»). «C» выдумано: такого правила нет.

</details>

## Вопрос в одну строку: семь догадок

Первый промпт — одна строка:

```console
$ cat promptlar/1-yomon.txt
Go'da xato tekshirish ishlamayapti, nega?
```

Все три ответа оказались списком с заголовками. Заголовки первого ответа:

```console
$ grep -E '^\*\*[0-9]' javoblar/1-yomon/1.txt
**1. Xato e'tiborsiz qoldirilgan**
**2. Shadowing (`:=` bilan o'zgaruvchini qayta e'lon qilish)**
**3. Nil interfeys tuzog'i**
**4. Xatolarni noto'g'ri solishtirish**
**5. Goroutine ichidagi xatolar**
**6. `defer` ichidagi xatolar**
**7. `panic`/`recover` bilan aralashtirish**
```

`grep -E '^\*\*[0-9]'` выводит только строки, которые начинаются с `**` и цифры, то есть жирные заголовки Markdown. Семь
догадок, все — ошибки, которые в Go действительно встречаются: игнорирование ошибки, затенение (shadowing), ловушка nil
в интерфейсе, неправильное сравнение ошибок, ошибки в горутинах, в `defer`, смешивание с `panic`/`recover`. Наша
ошибка — пункт 4: сравнение обёрнутой ошибки через `==`. Во 2-м и 3-м ответах тоже по семь догадок, настоящая причина
на 4-м и 3-м месте. Конец ответа:

```console
$ tail -7 javoblar/1-yomon/1.txt

Aniq sababni topish uchun, iltimos, quyidagilarni yuboring:
- Muammoli kod bo'lagi
- Kutgan natija va aslida nima bo'layotgani
- Agar bor bo'lsa, xato xabari yoki chiqish (output)

Xohlasangiz, ish papkasidagi Go fayllarni o'zim ko'rib chiqaman, faqat qaysi fayl ekanini ayting.
```

Claude попросил код, ожидаемый и фактический результат (и текст ошибки, если есть); 2-й и 3-й ответы попросили ещё
версию Go (`go version`). Это не плохой ответ: на вопрос без кода иначе не ответишь. Модель не может ответить
без догадок, потому что кода она не видит. Последняя фраза («если хотите, я сам посмотрю Go-файлы в рабочей папке»)
любопытна: в эксперименте Claude не мог читать файлы, это мы увидим в следующем разделе.

## Как проводился эксперимент

Все ответы получены одним скриптом (`takrorla.sh`, «повтори»). Он использует **режим print** Claude Code (`claude -p`):
передаёт промпт, выводит ответ и завершается, чат не открывается.

```bash filename="takrorla.sh" showLineNumbers
#!/usr/bin/env bash
# takrorla.sh promptlar/2-kontekst.txt [N]
# Promptni Claude'ga N marta (standart 3) beradi, javoblarni javoblar/<prompt>/ ga yozadi:
#   <i>.txt   javob matni, oʻzgartirilmagan
#   <i>.json  sana, model, tokenlar, vaqt
# Javob har safar boshqacha boʻlishi mumkin: shuning uchun uchta javob saqlaymiz.
set -euo pipefail
prompt=$(realpath "$1"); n=${2:-3}; model=${MODEL:-claude-sonnet-5-5}
dir=$(realpath javoblar)/$(basename "$prompt" .txt); mkdir -p "$dir"
cd "$(mktemp -d)"   # boʻsh papka: CLAUDE.md va loyiha fayllari taʼsir qilmasin
for i in $(seq 1 "$n"); do
  # boʻsh system prompt, asboblarsiz: Claude faqat bizning promptni oladi
  claude -p --model "$model" --effort high --system-prompt "" --tools "" \
    --setting-sources "" --strict-mcp-config --disable-slash-commands \
    --no-session-persistence --output-format json < "$prompt" > raw.json
  jq -r .result raw.json > "$dir/$i.txt"
  jq --arg sana "$(date -u +%FT%TZ)" --arg model "$model" \
    --arg prompt "$(basename "$prompt")" \
    '{sana: $sana, model: $model, prompt: $prompt, effort: "high",
      stop_reason, duration_ms, output_tokens: .usage.output_tokens,
      input_tokens_jami: (.usage.input_tokens + .usage.cache_creation_input_tokens
                     + .usage.cache_read_input_tokens),
      models: (.modelUsage | keys)}' raw.json > "$dir/$i.json"
  echo "$dir/$i.txt: $(wc -w < "$dir/$i.txt") soʻz"
done
```

| Строка | Код | Что делает |
|---|---|---|
| 7 | `set -euo pipefail` | если какая-то команда упадёт, скрипт остановится |
| 8 | `n=${2:-3}`, `model=${MODEL:-…}` | число повторов (по умолчанию 3) и модель (по умолчанию `claude-sonnet-5-5`) |
| 9 | `dir=…/javoblar/<имя промпта>` | `promptlar/3-format.txt` → `javoblar/3-format/` |
| 10 | `cd "$(mktemp -d)"` | переходит в пустую временную папку: CLAUDE.md и файлы проекта на ответ не влияют |
| 13 | `--effort high --system-prompt "" --tools ""` | высокий effort, пустой **системный промпт**, инструментов нет: Claude не может читать файлы и запускать команды |
| 14–15 | `--setting-sources ""` … `--output-format json` | настройки, MCP и slash-команды выключены; сессия не сохраняется; результат в JSON |
| 16 | `jq -r .result` | текст ответа без изменений пишется в `<i>.txt` |
| 17–23 | `jq … > "$dir/$i.json"` | рядом записываются дата, модель, effort, число токенов и время |
| 24 | `wc -w` | выводит на экран число слов в ответе |

**Системный промпт** (system prompt) — постоянная инструкция, которую модель получает до вашего сообщения; на неё похожа
инструкция Project из CL-1.02. Мы оставили его пустым, чтобы на ответ влиял только сам промпт.

Две честные оговорки (из README):

1. **Добавка CLI.** Даже с `--system-prompt ""` CLI всё равно добавляет короткий системный текст. Для промпта в одну
   строку `input_tokens_jami` («входные токены, всего») равно 581, а сам промпт — около 12 токенов. Значит, добавка —
   около 570 токенов, и её содержимого мы не видим. Фраза «сам посмотрю файлы» в ответе на плохой промпт, скорее всего,
   оттуда.
2. **Запись Haiku.** В списке `models` в `.json` есть и `claude-haiku-5-5`. Это небольшой служебный вызов самого CLI,
   ответ написал Sonnet 5.5.

В промпт по очереди добавляем четыре вещи: контекст, формат ответа, пример и XML-теги. На каждом шаге измеряем
программой на Go, как меняется ответ. Семь промптов построены вокруг одной ошибки, каждый добавляет к предыдущему
одну вещь:

| Промпт | Что добавлено | Вопрос |
|---|---|---|
| `1-yomon` («плохой») | одна строка | почему не работает проверка ошибки? |
| `2-kontekst` | кто, какой проект, версия Go, ожидаемый результат, весь код, вывод `go run` | тот же |
| `3-format` | формат ответа (ровно 3 строки) и почему именно такой | тот же |
| `4-misol` («пример») | один образец ответа для другой ошибки (nil map) | тот же |
| `5-xml` | то же содержание, что в 4, но в XML-тегах | тот же |
| `6-test` | код + задача, в XML-тегах | напиши табличный тест для `holat` |
| `7-test-misol` | 6 + тест `kabisa` из GO-1.07 как пример | тот же |

7 промптов × 3 = 21 ответ, плюс в домашнем задании ещё 2 × 3 = 6 ответов. Всё на GitHub, с датой и моделью.

## Контекст: покажите промпт коллеге, не знающему задачи

Руководство Anthropic по промптам (*Prompting best practices*) сравнивает Claude с «блестящим, но новым сотрудником»:
он не знает ваших правил и рабочих процессов. Там же способ проверки: покажите промпт коллеге, который почти ничего не
знает о задаче, и попросите его выполнить.

Коллега, получив наш вопрос в одну строку, сразу спросит: какой код? какая версия Go? что ожидалось и что получилось?
Те же вопросы задаёт любой шаблон issue на GitHub: *steps to reproduce*, *expected*, *actual*, *version*. И Claude в
конце ответа спросил ровно это. В этом смысле промпт — техническое задание (ТЗ): исполнитель знает только то, что
написано.

Во втором промпте есть всё, о чём спросил бы коллега. Начало:

```console
$ head -3 promptlar/2-kontekst.txt
Men Go'ni o'rganyapman va bozor degan onlayn do'kon backend'ini yozyapman. Go 1.26.8.
Mavjud bo'lmagan buyurtma uchun 404 qaytishi kerak, lekin 500 qaytyapti.
Xatoni o'zim tuzatib, sababini tushunmoqchiman.
```

В трёх строках: «Я изучаю Go и пишу бэкенд интернет-магазина bozor. Go 1.26.8. Для несуществующего заказа должен
возвращаться 404, а возвращается 500. Хочу сам исправить ошибку и понять причину». То есть кто пишет и какой проект,
версия Go, ожидаемый результат (404) и фактический (500). Запомните третью строку, она ещё понадобится. Это
**контекст** — сведения о задаче. Отличие от контекстного окна из CL-1.01: контекстное окно — весь текст, который видит
модель, а контекст — нужные факты, которые вы туда положили.

Ниже — весь код. Вот файл, вставленный в промпт:

```go filename="bozor/main.go" showLineNumbers
package main

import (
	"errors"
	"fmt"
)

var ErrTopilmadi = errors.New("buyurtma topilmadi")

var buyurtmalar = map[string]string{"1": "olma, 2 kg"}

func topish(id string) (string, error) {
	b, ok := buyurtmalar[id]
	if !ok {
		return "", fmt.Errorf("topish %s: %w", id, ErrTopilmadi)
	}
	return b, nil
}

// holat: handler shu kodni HTTP javobga yozadi
func holat(err error) int {
	if err == nil {
		return 200
	}
	if err == ErrTopilmadi {
		return 404
	}
	return 500
}

func main() {
	for _, id := range []string{"1", "42"} {
		_, err := topish(id)
		fmt.Printf("GET /buyurtma/%s → %d %v\n", id, holat(err), err)
	}
}
```

| Строка | Код | Что делает |
|---|---|---|
| 8 | `var ErrTopilmadi = errors.New(…)` | одно значение ошибки на уровне пакета, **sentinel-ошибка** (GO-1.14): `ErrTopilmadi` («не найдено») |
| 10 | `var buyurtmalar = map[string]string{…}` | map вместо «базы»: есть только заказ `"1"` (`buyurtmalar` — «заказы») |
| 12–18 | `func topish(id string) (string, error)` | ищет заказ (`topish` — «найти»); если не нашёл, возвращает `ErrTopilmadi`, обёрнутую через `%w` |
| 15 | `fmt.Errorf("topish %s: %w", id, ErrTopilmadi)` | новая ошибка: текст `topish 42: buyurtma topilmadi`, внутри — исходная `ErrTopilmadi` |
| 21–29 | `func holat(err error) int` | превращает ошибку в код статуса HTTP (`holat` — «статус»): `nil` → 200, не найдено → 404, остальное → 500 |
| 25 | `if err == ErrTopilmadi {` | **ошибка здесь**: обёрнутая ошибка — это не сама `ErrTopilmadi` |
| 31–35 | `main` | имитирует два запроса: `/buyurtma/1` и `/buyurtma/42` |
| 34 | `fmt.Printf("GET /buyurtma/%s → %d %v\n", …)` | `%s` — строка, `%d` — целое число, `%v` — текст ошибки (`<nil>`, если `nil`) |

Под кодом промпт приводит его фактический вывод. Получите его сами:

```console
$ go run ./bozor
GET /buyurtma/1 → 200 <nil>
GET /buyurtma/42 → 500 topish 42: buyurtma topilmadi
```

Заказа 42 нет, ожидался 404, а вернулся 500. Причину знают те, кто смотрел GO-1.14:

```text
err, который вернул topish("42"):
  *fmt.wrapError  "topish 42: buyurtma topilmadi"
        │ Unwrap()
        ▼
  ErrTopilmadi    "buyurtma topilmadi"

err == ErrTopilmadi            → false  (два разных значения)
errors.Is(err, ErrTopilmadi)   → true   (смотрит вглубь по цепочке)
```

`==` сравнивает только внешнее значение. А `errors.Is` идёт по цепочке ошибок через `Unwrap` и находит внутри
`ErrTopilmadi`. Исправление — одна строка:

```console
$ diff bozor/main.go tuzatildi/main.go
25c25
< 	if err == ErrTopilmadi {
---
> 	if errors.Is(err, ErrTopilmadi) {
```

`diff` выводит разницу двух файлов: `25c25` — «изменилась строка 25», `<` — старый файл, `>` — новый
(`tuzatildi` — «исправлено»).

Постоянный контекст (кто вы, какой проект, какая версия Go) не обязательно писать каждый раз: для этого есть
инструкция Project из CL-1.02. А в этом эксперименте мы нарочно написали его в самом промпте, чтобы измерение было
чистым.

## Ответ с контекстом: причина найдена, готовой строки нет

Контекст добавлен. Что, по-вашему, будет в ответе?

**A)** причина найдена, и внутри есть строка `if errors.Is(err, ErrTopilmadi) {`, которую можно скопировать ·

## Формат ответа: три строки и «почему»

В третий промпт добавляем **формат ответа** — как должен выглядеть ответ. Это и есть **ограничение** из названия
урока: ровно три строки и больше ничего. Конец промпта:

```console
$ tail -4 promptlar/3-format.txt
Javobni terminalda o'qiyman, shuning uchun o'zbekcha, aynan uch qator yoz, boshqa hech narsa qo'shma:
Sabab: <bitta gap>
Tuzatish: <o'zgaradigan bitta Go qatori>
Tekshirish: <bitta buyruq>
```

Перевод: «Я читаю ответ в терминале, поэтому пиши по-узбекски, ровно три строки, больше ничего не добавляй:
`Sabab:` (причина) &lt;одно предложение>, `Tuzatish:` (исправление) &lt;одна изменяемая строка Go>, `Tekshirish:` (проверка)
&lt;одна команда>». В первой строке вместе с форматом указана и его причина: «читаю ответ в терминале». Документация
Anthropic (*Add context to improve performance*) говорит: если объяснить, почему правило важно, Claude лучше понимает
вашу цель, «Claude can generalize from the explanation» («Claude может обобщить из объяснения»). Это утверждение
документации: отдельный эффект фразы с причиной мы не измеряли.

Формат — как контракт API: сторона, которая читает ответ (вы, терминал или скрипт), заранее знает, какое поле где.
Результат:


31 слово, три строки и готовое исправление. Мы дали промпт три раза, и все три ответа вышли почти слово в слово

## Измерение: критерий успеха заранее

Фраза «ответ стал лучше» должна быть числом, а не ощущением. Страница Anthropic *Prompt engineering overview* требует
двух вещей до того, как писать промпт: **критерия успеха** (когда ответ считается хорошим) и способа эмпирически
проверить его. У нас критерий ясен: строка исправления есть, и она работает. Способ проверки — программа на Go в папке
`olchov/` («измерение»). Она измеряет 15 ответов на промпты 1–5.

Прежде чем смотреть таблицу, подумайте: с какого промпта заполнится столбец `404` (строку от Claude вставляют в код и
запускают), и насколько пример (4) и XML (5) улучшат результат?

точной задаче ничего не изменили: формат уже был 3/3, улучшать было нечего. Если вы ждали от примера и XML большого

Число слов упало с 340 примерно до 30. Формат и готовая строка появились только с 3-го промпта. Главное — последний

Полный текст программы — в `olchov/main.go` (227 строк). Здесь главные части. Столбец `format`:

```go
// formatda: boʻsh boʻlmagan qatorlar aynan uchta va kerakli soʻzlar bilan boshlanadi
func formatda(javob string) bool {
	var q []string
	for _, l := range strings.Split(javob, "\n") {
		if strings.TrimSpace(l) != "" {
			q = append(q, strings.TrimSpace(l))
		}
	}
	return len(q) == 3 && strings.HasPrefix(q[0], "Sabab:") &&
		strings.HasPrefix(q[1], "Tuzatish:") && strings.HasPrefix(q[2], "Tekshirish:")
}
```

Ответ делится на строки, пустые отбрасываются. Затем три условия: строк ровно три, и каждая начинается с нужного слова.
`strings.HasPrefix(s, p)` — начинается ли строка `s` с `p`. Комментарии в коде на узбекском, как во всём курсе:
«formatda: непустых строк ровно три, и они начинаются с нужных слов».

Выделение строки `Tuzatish:`:

```go
// tuzatish: «Tuzatish:» qatoridagi Go kodi (` belgilarisiz)
func tuzatish(javob string) (string, bool) {
	for _, l := range strings.Split(javob, "\n") {
		l = strings.TrimSpace(l)
		if s, ok := strings.CutPrefix(l, "Tuzatish:"); ok {
			s = strings.TrimSpace(strings.Trim(strings.TrimSpace(s), "`"))
			return s, s != ""
		}
	}
	return "", false
}
```

`strings.CutPrefix` отрезает `Tuzatish:` в начале строки и возвращает остаток; `ok` — префикс был. `strings.Trim(…,
"`")` убирает обратные кавычки Markdown: `` `if errors.Is(err, ErrTopilmadi) \{` `` →
`if errors.Is(err, ErrTopilmadi) {`.

Столбец `404` — главный, потому что он запускает ответ:

```go
// ishlat: tuzatilgan kodni vaqtinchalik papkada ishga tushiradi, /buyurtma/42 holatini qaytaradi
func ishlat(kod, yangi string) string {
	if !strings.Contains(kod, eski) {
		return "eski qator topilmadi"
	}
	dir := vaqtinchalik(map[string]string{"main.go": strings.Replace(kod, eski, yangi, 1)})
	defer os.RemoveAll(dir)
	cmd := exec.Command("go", "run", ".")
	cmd.Dir = dir
	out, err := cmd.CombinedOutput()
	if err != nil {
		return "kompilyatsiya xatosi"
	}
	for _, l := range strings.Split(string(out), "\n") {
		if s, ok := strings.CutPrefix(l, "GET /buyurtma/42 → "); ok {
			return strings.Fields(s)[0]
		}
	}
	return "natija yoʻq"
}
```

```text
ответ ──► строка «Tuzatish:» ──► вместо строки 25 в bozor/main.go
                                  (eski = "if err == ErrTopilmadi {")
      ──► временная папка: main.go + go.mod ──► go run .
      ──► «GET /buyurtma/42 → 404 …» ──► "404"
```

`eski` («старое») — константа в начале файла: `"if err == ErrTopilmadi {"`. `strings.Replace(kod, eski, yangi, 1)`
заменяет её строкой от Claude (1 — только первое вхождение). `vaqtinchalik` («временный») создаёт новую папку и пишет
туда `main.go` и `go.mod`. `exec.Command("go", "run", ".")` запускает программу в этой папке, `cmd.CombinedOutput()`
забирает её вывод. Если код не компилируется — `kompilyatsiya xatosi` («ошибка компиляции»). Если компилируется, берётся
первое слово в строке заказа 42: `404` или `500`. `defer os.RemoveAll(dir)` удаляет папку, когда функция завершится.

Поэтому столбец `404` означает не «Claude сказал правильно», а «строка от Claude заработала». Не читать ответ модели, а
запускать его — практическая форма правила из CL-1.01.

## Пример: форма, которую трудно описать словами

**Few-shot пример** — образец ответа, вставленный в промпт. Он показывает то, что трудно объяснить словами. Например,
стиль тестов нашего курса: как называется таблица, как записываются случаи, каким бывает сообщение об ошибке. Описать
это словами долго, показать один существующий файл — коротко. Новому разработчику в команде вы тоже открываете
существующий тест и говорите: «тесты пишем так».

Пример в 4-м промпте близок к этому, но для другой ошибки (nil map), чтобы Claude не мог скопировать из него ответ:

Образец («для другой ошибки»): «Sabab: map, объявленная через var, равна nil, в nil map писать нельзя. Tuzatish:
narxlar := map[string]int\{\}. Tekshirish: go run ./narx» (`narxlar` — «цены»). В таблице измерения 4-misol ничем не

  `<misol>`».

## XML-теги и длинные промпты

В 5-м, 6-м и 7-м промптах используются **XML-теги**: каждая часть промпта внутри своего тега. Как блок кода в Markdown
или *boundary* в multipart-запросе, тег точно говорит, где часть начинается и где кончается. Структура 5-го промпта:

```console
$ grep -n '^<' promptlar/5-xml.txt
1:<kontekst>
5:</kontekst>
7:<kod fayl="bozor/main.go">
44:</kod>
46:<natija buyruq="go run ./bozor">
49:</natija>
51:<format>
56:</format>
58:<misol>
64:</misol>
66:<savol>Nega 404 emas?</savol>
```

`grep -n` выводит и номер строки. По содержанию 5-й промпт совпадает с 4-м, только разбит на теги (`kontekst`, `kod`,
`natija` — «результат», `format`, `misol` — «пример», `savol` — «вопрос»). В 7-м промпте теги особенно нужны: в нём два
разных кода на Go.

```text
<kod fayl="bozor/main.go">      наш код: тест пишем для него
   …
</kod>
<misol fayl="kabisa_test.go">   только образец, другой пакет (kabisa)
   …
</misol>
<vazifa>                        что нужно сделать
   …
</vazifa>
```

Теги отделяют наш код от кода, который лишь образец (`vazifa` — «задача»). Документация Anthropic (*Structure prompts
with XML tags*) говорит: теги помогают однозначно разобрать сложный промпт; имена должны быть понятными и одинаковыми во
всех промптах; если у содержимого есть естественная иерархия, вкладывайте теги друг в друга. Особых «правильных» имён
тегов нет: мы использовали узбекские имена (`kod`, `misol`, `vazifa`), и ответы вышли правильными.

Но честный вывод: отдельный эффект XML в этом эксперименте мы не увидели. В таблице измерения 4-misol и 5-xml
одинаковы: 3/3, 3/3, 3/3.

Для длинных промптов в документации есть ещё один конкретный совет (*Long context prompting*). Если текст длиннее
20 000 токенов, кладите длинные документы в начало промпта, а вопрос — в конец. В тестах Anthropic вопрос в конце
улучшал качество ответа до 30 процентов, особенно в сложных промптах с несколькими документами. Это число не про XML, а
про место вопроса. Наши маленькие промпты — меньше 1 400 токенов (`input_tokens_jami` 1327 и 1374, вместе с добавкой
CLI) — к этому не относятся: варианты 4 и 5 дали одинаковый результат.

| Размер промпта | Совет | В нашем эксперименте |
|---|---|---|
| маленький, одна задача | хватает точного контекста + формата | после 3-format ничего не изменилось |
| несколько разных частей (код + образец) | разделяйте XML-тегами | 7-й промпт: теги говорят, какой код наш |
| 20 000+ токенов, много документов | документы в начале, вопрос в конце | не проверяли (документация: до 30 процентов лучше) |

## Два приёма из старых руководств: prefill и temperature

В старых руководствах в интернете встречаются ещё два приёма. На нынешних моделях оба не работают.

**Prefill** — написать начало ответа Claude за него: в конце списка сообщений запроса стоит сообщение assistant, и
модель его продолжает. Курс Anthropic *Prompt Engineering Interactive Tutorial* учит этому в 5-й главе («Speaking for
Claude»): `{"role": "assistant", "content": prefill}`. Это хороший курс, но написан он для старой модели Claude 3 Haiku.
А migration guide четырёх нынешних моделей говорят:

| Модель | Prefill | `temperature`, `top_p`, `top_k` |
|---|---|---|
| Sonnet 5.5 | «rejects a prefilled last assistant turn with a 400 error» | «Sampling parameters return an error» |
| Opus 5.5 | «Don't end `messages` with a prefilled assistant turn: it is rejected» | «Omit `temperature`, `top_p`, and `top_k`» |
| Haiku 5.5 | «rejects it with a 400 error, even with thinking turned off» | уберите |
| Fable 5.2 | «Prefilling the assistant message returns a 400 error» | «Omit `temperature`, `top_p`, and `top_k`» |

400 — HTTP-код «неверный запрос»: API запрос вообще не выполняет. Второй приём — настройка `temperature`, `top_p` и
`top_k` (параметры сэмплирования из CL-1.01). Если их отправить, теперь тоже вернётся ошибка. Для этой страницы мы API
не вызывали, поэтому текста ошибки не показываем: всё выше — цитаты из документации.

В обоих случаях документация указывает один путь: прямо напишите своё желание в самом промпте. Наш промпт 3-format
делает именно это: как начинается ответ, задаёт не prefill, а требование формата.

<details>
<summary>Ответ</summary>

</details>

## Частые ошибки

### 1. «Модель видит мой код»

Классическое заблуждение этой темы. Модель видит только текст промпта (CL-1.01). На вопрос без кода она написала список
на 340–374 слова с семью догадками и в конце попросила код (раздел «Вопрос в одну строку»). Исправление: положите в
промпт всё, что есть в баг-репорте, — код, версию, ожидаемый и фактический результат.

### 2. Противоречивый промпт

Тихая ошибка: никакого сообщения нет, просто приходит не тот ответ, которого вы ждали. Если написать «исправлю сам», а в
формате попросить строку `Tuzatish:`, вы получите готовый код (раздел «Противоречивый промпт»). Исправление: направьте
пожелание и формат в одну сторону. Если хотите учиться — `Ishora:` и «готовый код не пиши».

### 3. «Пример и XML всегда помогают»

В нашей маленькой задаче они ничего не изменили (4-misol = 5-xml = 3-format). Пример изменил форму, а не правильность.
Пример переносит и ненужный шаблон: в 3-м задании домашней работы Claude перенял из комментариев примера даже букву
`ʻ`. Исправление: добавляйте пример, только когда важна форма, делайте их несколько и разными, и измеряйте результат.

### 4. Prefill или `temperature` из старого руководства

На нынешних моделях такой запрос вернётся с ошибкой 400 (раздел «Два приёма из старых руководств»). Мы API не вызывали,
поэтому текста ошибки не показываем. Исправление: уберите параметр или последнее сообщение assistant и напишите своё
желание в промпте.

### 5. «Сработало один раз — значит, промпт хороший»

Один ответ может быть случайностью. Даже три почти одинаковых ответа ещё не доказательство (CL-1.01: одинаковость — не
правильность). У нас оценку «правильно» дают только столбцы `404` и `PASS`/`FAIL`, потому что они запускают код.
Исправление: давайте каждый промпт несколько раз и проверяйте ответ запуском.

### 6. Ошибки программы: другая папка и запуск без `./`

`olchov` читает сохранённые файлы из текущей папки. Если запустить его вне папки урока (`cd ..` — на папку выше):

```console
$ cd .. && go run ./cl-03-prompt/olchov
bu papkadan ishga tushiring: open bozor/main.go: no such file or directory
exit status 1
```

Первую строку написала программа (строка 41): «bu papkadan ishga tushiring» («запускайте из этой папки»), затем ошибка
Go: «не удалось открыть `bozor/main.go`: нет такого файла или каталога». `exit status 1` добавляет `go run`.
Исправление: `cd cl-03-prompt` и `go run ./olchov`.

Если написать без `./`:

```console
$ go run olchov
package olchov is not in std (/nix/store/h3rc4y3szd0391wryw9hslrijdvni030-go-1.26.8/share/go/src/olchov)
```

«Пакета `olchov` нет в стандартной библиотеке». Без `./` Go ищет `olchov` не как папку, а как имя стандартного пакета
вроде `fmt`. Путь в скобках — место, куда установлен Go, у вас он будет другим. Исправление: `go run ./olchov`.

```console
homework/javoblar/qiyin/3.txt:4
javoblar/7-test-misol/1.txt:0
javoblar/7-test-misol/2.txt:0
javoblar/7-test-misol/3.txt:0
```

`grep -c` выводит число совпавших строк в каждом файле. В ответах на 7-й промпт был обычный `'`, а в промпте с двумя
примерами — `ʻ` (`oʻralgan`). Это маленький, но настоящий образец ненужного шаблона (*unintended pattern*), о котором
предупреждает документация. Все три теста прошли с `tuzatildi/` и упали с `bozor/`.

🔴 Решение — в `homework/guru/main.go`. Она регулярным выражением считает в каждом ответе-тесте строки `func Test` и
случаи таблицы (строки, начинающиеся с `{"nom", …}` или `nom: "…"`):

```console
$ go run ./homework/guru

```
