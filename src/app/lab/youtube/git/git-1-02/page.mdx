## Nimani oʻrganasiz

Siz kalitli `.env` faylini GitHub'ga push qildingiz. Bir daqiqadan keyin xatoni koʻrib, faylni oʻchirdingiz va yana
push qildingiz. Papkada `.env` yoʻq, oxirgi commit xabari «kalitni oʻchirdim». Savol: kalit endi xavfsizmi?
Javob: yoʻq. Bitta buyruq uni tarixdan qaytarib beradi. Tadqiqotchilar sinov matnini push qilganda, skanerlari uni
odatda 20 soniyada topgan: bir daqiqa juda uzoq vaqt.

**Bitta gʻoya:** oʻchirish — unutish emas. Har commit butun loyihaning surati, eski suratlar tarixda qoladi, shuning
uchun push qilingan kalit endi ochiq hisoblanadi. Birinchi qadam — kalitni almashtirish (rotate), tarixni tozalash
esa keyin va faqat kerak boʻlsa. Eng yaxshisi — `.gitignore`ni birinchi commit'dan oldin yozish.

Dars oxirida siz:

- «oʻchirilgan» kalitni `git show`, `git log -- .env` va `git grep` bilan tarixdan topasiz;
- kalit sizganda toʻgʻri tartibni bilasiz: avval rotate, keyin jurnallar, kerak boʻlsa `git filter-repo` va force
  push — har birining cheklovlari bilan;
- kuzatilayotgan `.env`ni `git rm --cached` bilan chiqarib, `.gitignore`ni `.env*` va `!.env.example` bilan yozasiz;
- GitHub'ning secret scanning va push protection himoyalari nimani qiladi va nimani qilmasligini aytib bera olasiz.

Bugungi uchta asosiy yangi soʻz:

| Soʻz | Oddiy maʼnosi | Inglizcha |
|---|---|---|
| sir | begona odam bilmasligi kerak boʻlgan qiymat: API kalit, maʼlumotlar bazasi paroli, token | secret |
| kalitni almashtirish (rotate) | provayderda yangi kalit yaratib ilovaga berish va eskisini bekor qilish | rotate (revoke) |
| kuzatiladigan fayl | git allaqachon commit'ga olgan va har oʻzgarishini koʻradigan fayl | tracked file |

Yordamchi soʻzlar matnda birinchi uchraganda bitta gap bilan tushuntiriladi: **force push** (serverdagi tarixni
sizdagi bilan almashtiruvchi push), **push protection** (GitHub'ning kalitli push'ni toʻxtatadigan himoyasi).

Avval GIT-1.01 dan bitta savol. Uchinchi commit'da faylni oʻchirdingiz. Ikkinchi commit'ning tree'si oʻzgaradimi?

**A)** ha, fayl undan ham oʻchadi · **B)** yoʻq, eski commit oʻzgarmaydi, yangi commit yangi surat qoʻshadi ·
**C)** ikkinchi commit butunlay yoʻqoladi

<details>
<summary>Javob</summary>

**B.** Commit obyekti mazmunining hash'i bilan nomlangan. Uni oʻzgartirsangiz, hash ham, demak commit ham boshqa
boʻlardi. `git rm` + commit faqat *keyingi* suratda faylni qoldirmaydi. Oldingi surat va undagi fayl (blob) joyida
qoladi. «A» ni tanlagan boʻlsangiz, commit'ni joyida tahrirlanadigan narsa deb oʻyladingiz. «C» — tarixni qayta
yozish, uni `git rm` qilmaydi.

</details>

## Kalit «oʻchirildi», lekin tarixda turibdi

Avval mashq repolarini quramiz. `qur.sh` ikkita repo yasaydi: `loyiha` (kalit push qilinib, keyin «oʻchirilgan»)
va `tuzoq` (`.env` birinchi commit'danoq kuzatiladi; uni keyinroq ishlatamiz). Skript ichini keyingi boʻlimda ochamiz.

```console
$ ./qur.sh
tayyor: loyiha/ va tuzoq/
```

`loyiha` tarixi va papkasi (`ls -A` — yashirin fayllarni ham koʻrsatadi, `.` va `..` dan tashqari):

```console
$ cd loyiha && git log --oneline && ls -A
36288b8 kalitni o'chirdim
cdd4176 lokal sozlamalar
4590f4e to'lov: kalit muhitdan
.git
main.go
```

Uchta commit: eng yangisi tepada. Oxirgisining xabari `kalitni o'chirdim`, papkada esa faqat `.git` va `main.go`.
`.env` yoʻq. Endi `git show HEAD~1:.env` yozamiz: «HEAD'dan bitta oldingi commit'dagi `.env` faylini koʻrsat».
Nima chiqadi?

**A)** xato: bunday fayl yoʻq · **B)** kalit qatori · **C)** boʻsh qator

<details>
<summary>Javob</summary>

**B.** `HEAD~1` — bu `cdd4176`, yaʼni `.env` qoʻshilgan commit. Uning suratida `.env` bor, va bu surat oʻzgarmaydi.
«A» ni tanlagan boʻlsangiz, git'ga diskdagi papkani soʻradingiz deb oʻyladingiz: `<commit>:<fayl>` diskka emas,
commit ichidagi tree'ga qaraydi.

</details>

```console
$ cd loyiha && git show HEAD~1:.env
TOLOV_KALIT=soxta_9f2c7a41e8b3
```

Kalit qaytdi. Tarix rasmda:

```text
 main ──► 36288b8 "kalitni o'chirdim"        surat: main.go
             │ parent
             ▼
          cdd4176 "lokal sozlamalar"         surat: main.go, .env   ◄── kalit shu yerda
             │ parent
             ▼
          4590f4e "to'lov: kalit muhitdan"   surat: main.go
```

GitHub'dagi repo ham xuddi shu commit'larni saqlaydi. Repoga kira oladigan har kim `cdd4176` ni ochib, `.env` ni
oʻqiy oladi. Tadqiqotchilar GitHub'ga sinov matnini push qilganda, ularning skaneri uni mediana **20 soniyada**
topgan (yarim soniyadan 4 daqiqadan koʻproqqacha; NDSS 2019). Demak, «bir daqiqadan keyin oʻchirdim» juda kech.

Kod esa toʻgʻri yozilgan: kalit kodda emas. Muammo boshqa joyda — `.env` faylining oʻzi commit'ga tushgan.

## Mashq reposi qanday qurilgan: `qur.sh`

Avval ilova. `main.go` kalitni muhitdan oʻqiydi, xuddi Node'dagi `process.env.TOLOV_KALIT`, Python'dagi
`os.environ["TOLOV_KALIT"]` yoki PHP'dagi `getenv('TOLOV_KALIT')` kabi:

```go filename="fayllar/main.go" showLineNumbers
package main

import (
	"fmt"
	"os"
)

// Kalit koddan emas, muhitdan o'qiladi (SYS-0.02). Lekin .env fayli ham git'ga tushmasligi kerak.
func main() {
	kalit := os.Getenv("TOLOV_KALIT")
	if kalit == "" {
		fmt.Println("TOLOV_KALIT berilmagan")
		os.Exit(1)
	}
	fmt.Println("to'lov tizimiga ulandik, kalit uzunligi:", len(kalit))
}
```

| Qator | Kod | Nima qiladi |
|---|---|---|
| 10 | `kalit := os.Getenv("TOLOV_KALIT")` | muhit oʻzgaruvchisini oʻqiydi; `kalit` («kalit», key) — yangi oʻzgaruvchi; oʻzgaruvchi yoʻq boʻlsa, boʻsh satr |
| 11–14 | `if kalit == "" { … os.Exit(1) }` | kalit berilmagan boʻlsa, xabar chiqarib, 1 kodi bilan chiqadi |
| 15 | `fmt.Println(…, len(kalit))` | kalitning oʻzini emas, faqat uzunligini chiqaradi |

Bu darsda Go dasturini ishga tushirmaymiz: `main.go` faqat «kalit koddan tashqarida» ekanini koʻrsatadi. `.env`
— shu muhit oʻzgaruvchilarini lokal saqlaydigan oddiy matn fayli (`fayllar/env.txt` dan nusxa), ichida bitta qator:
`TOLOV_KALIT=soxta_9f2c7a41e8b3`.

Endi skriptning oʻzi:

```bash filename="qur.sh" showLineNumbers
#!/usr/bin/env bash
# Ikkita mashq repo'sini noldan quradi. Muallif va vaqt qat'iy (vaqt.sh). git >= 2.29.
#   loyiha/: .env commit qilingan, keyingi commit'da "o'chirilgan"
#   tuzoq/:  .env birinchi commit'dayoq kuzatila boshlagan
# Kalit soxta: soxta_... hech qayerda ishlamaydi.
set -e; cd "$(dirname "$0")"
rf=--ref-format=files; git init -h 2>&1 | grep -q ref-format || rf=   # eski git'da bu bayroq yo'q
yangi() { rm -rf "$1"; mkdir "$1"; cd "$1"; git init -q --template= -b main --object-format=sha1 $rf
  git config user.name Lola; git config user.email lola@example.com; git config commit.gpgsign false
  git config core.hooksPath /dev/null
git config core.pager cat; git config color.ui false; git config core.abbrev 7
git config core.autocrlf false; git config core.excludesFile /dev/null; git config core.attributesFile /dev/null
git config log.decorate false; git config branch.sort refname
git config merge.ff true; git config merge.stat true; }

yangi loyiha
cp ../fayllar/main.go .
git add main.go; . ../vaqt.sh; git commit -q -m "to'lov: kalit muhitdan"
cp ../fayllar/env.txt .env
git add .; . ../vaqt.sh; git commit -q -m "lokal sozlamalar"
git rm -q .env; . ../vaqt.sh; git commit -q -m "kalitni o'chirdim"
cd ..

yangi tuzoq
cp ../fayllar/main.go .; cp ../fayllar/env.txt .env
git add .; . ../vaqt.sh; git commit -q -m "birinchi commit"
cd ..
echo "tayyor: loyiha/ va tuzoq/"
```

| Qator | Kod | Nima qiladi |
|---|---|---|
| 6 | `set -e; cd "$(dirname "$0")"` | birinchi xatoda toʻxtaydi; skript turgan papkaga oʻtadi |
| 7 | `rf=--ref-format=files … \|\| rf=` | yangi git'da ref'lar oddiy fayllarda saqlansin; eski git bu bayroqni bilmasa, `rf` boʻsh |
| 8–14 | `yangi() { … }` | funksiya: papkani noldan yaratadi, `git init` (birinchi branch `main`, hash SHA-1), ism `Lola`, imzo va hook'lar oʻchiq, chiqish koʻrinishi qatʼiy. Hammasi GIT-1.01 dagi kabi: global sozlamangiz natijani oʻzgartirmasin |
| 16–18 | `yangi loyiha`, `cp …main.go .`, `git add main.go; … git commit` | 1-commit: faqat `main.go` |
| 19–20 | `cp ../fayllar/env.txt .env`, `git add .; … git commit` | 2-commit: `git add .` hamma yangi faylni oldi, `.env` ham tushdi. Xatoning aynan oʻzi |
| 21 | `git rm -q .env; … git commit -q -m "kalitni o'chirdim"` | 3-commit: `.env` diskdan va keyingi suratdan oʻchadi |
| 24–26 | `yangi tuzoq`, ikkala faylni nusxalash, `git add .`, commit | `tuzoq`: `.env` birinchi commit'danoq kuzatiladi |
| 28 | `echo "tayyor: …"` | yuqoridagi yagona natija qatori |

Vaqtni `vaqt.sh` qatʼiy qiladi (GIT-1.01 dagi bilan bir xil, faqat sana boshqa):

```bash filename="vaqt.sh" showLineNumbers
# Manba qiling: `. ../vaqt.sh` (repo ichidan). Commit vaqtini qat'iy qiladi:
# 2026-02-02 09:00 (+05:00) va har bir mavjud commit uchun +10 daqiqa.
# Shuning uchun commit hash'lari sizda ham, bizda ham bir xil chiqadi.
# muallif repo sozlamasidan olinsin (user.name/email), muhitdagi qiymatdan emas
unset GIT_AUTHOR_NAME GIT_AUTHOR_EMAIL GIT_COMMITTER_NAME GIT_COMMITTER_EMAIL
n=$(git rev-list --all --count 2>/dev/null || echo 0)
t=$((1770004800 + n * 600))
export GIT_AUTHOR_DATE="@$t +0500" GIT_COMMITTER_DATE="@$t +0500"
```

`n` — repodagi commit'lar soni, `1770004800` — 2026-02-02 09:00 Toshkent vaqti Unix soniyalarida, har commit uchun
+600 soniya. `. ../vaqt.sh` skriptni joriy shell'da bajaradi, shuning uchun `export` qilingan vaqt keyingi
`git commit`ga yetib boradi (SYS-0.02). Oʻz repongizda bu kerak emas.

## Tarixdan qidirish: `git log -- .env` va `git grep`

Hujumchi faqat oxirgi commit'ga qaramaydi. Palo Alto Networks'ning Unit 42 tadqiqotida kalit aynan «oʻtgan
commit'ning orqasiga yashiringan» edi, va u baribir topildi. Biz ham ikki usul bilan qidiramiz.

Birinchisi: `git log` ga `--` dan keyin fayl yoʻlini bersak, faqat shu faylga tekkan commit'lar chiqadi. Nechta?

**A)** 0: `.env` hozir yoʻq · **B)** 1: faqat qoʻshgan commit · **C)** 2: qoʻshgan va oʻchirgan commit'lar

<details>
<summary>Javob</summary>

**C.** Faylni qoʻshish ham, oʻchirish ham — shu faylga tegadigan oʻzgarish. «A» ni tanlagan boʻlsangiz, `git log`
diskka qaraydi deb oʻyladingiz: u tarixni oʻqiydi.

</details>

```console
$ cd loyiha && git log --oneline -- .env
36288b8 kalitni o'chirdim
cdd4176 lokal sozlamalar
```

Ikkinchisi — fayl nomini bilmasangiz ham ishlaydi. `git rev-list --all` hamma ref'lardan yetib boriladigan har bir
commit'ning toʻliq hash'ini chiqaradi. `$(…)` ularni `git grep` ga argument qilib beradi, `git grep` esa har bir
commit suratida `TOLOV_KALIT=` matnini qidiradi:

```console
$ cd loyiha && git grep TOLOV_KALIT= $(git rev-list --all)
cdd41765c96056540bd26de63175c88de2e570da:.env:TOLOV_KALIT=soxta_9f2c7a41e8b3
```

Natija `<commit>:<fayl>:<qator>` shaklida: commit hash'i, fayl nomi va kalitning oʻzi. Bitta buyruq — butun tarix.

Katta repoda `$(git rev-list --all)` buyruq argumentlari chegarasidan (`ARG_MAX`) oshib ketishi mumkin. Unda
`git log --all -p -S 'TOLOV_KALIT='` (pastda, uy vazifasida) yoki `git rev-list --all | xargs git grep 'TOLOV_KALIT='`
ishlating.

## 1-qadam: kalitni almashtirish (rotate)

Videodagi pauza savoli. Reponi yopiq (private) qilsak yoki butunlay oʻchirsak, kalit xavfsiz boʻladimi?

**A)** ha, yopiq repoda uni hech kim koʻrmaydi · **B)** ha, agar tarixni ham tozalasak · **C)** yoʻq, kalitning
nusxalari allaqachon boshqa joylarda

<details>
<summary>Javob</summary>

**C.** Push qilingan zahoti kalit nusxalari tarqaladi: skanerlarda, fork'larda, hamkasblarning kompyuterlaridagi
clone'larda. Reponi yopish, oʻchirish yoki tarixni tozalash bu nusxalarga yetib bormaydi. Toyota kodni 2022-yil
15-sentabrda yopgan, kalitni esa 17-sentabrda almashtirgan: oradagi ikki kun kalit hali ishlagan. «A» va «B» —
serverdagi nusxani yagona nusxa deb oʻylash.

</details>

Shuning uchun birinchi qadam — **sir**ni (secret) almashtirish. Bu **rotate** deyiladi: provayderda yangi kalit
yaratasiz, ilovaga berasiz, keyin eskisini bekor qilasiz (**revoke**). GitHub hujjati ham shuni aytadi: «as a first
step you need to revoke and/or rotate that secret» («birinchi qadam sifatida siz bu sirni bekor qilishingiz va/yoki
almashtirishingiz kerak»).

| # | Qadam | Nega |
|---|---|---|
| 1 | Fayldagi **hamma** sirlarni roʻyxatga oling | `.env`da odatda bir nechta: DB paroli, JWT siri, API kalitlar. Bittasini almashtirish yetmaydi |
| 2 | Provayder panelida yangi kalit yarating, ilovaga bering, keyin eskisini bekor qiling | eski kalit bekor qilinmaguncha u ishlaydi |
| 2a | Tez almashtira olmasangiz, eskisini **darhol** bekor qiling | ilova biroz ishlamay turishi oʻgʻirlikdan arzon: Unit 42 da hujumchilarga 5 daqiqa yetgan |
| 3 | Provayder jurnallarini (AWS CloudTrail, DB loglari) **birinchi push vaqtidan** boshlab tekshiring | kalit qachondan beri ochiq, oʻsha paytdan beri kim ishlatgan |
| 4 | Begona odam yaratgan narsalarni (serverlar, foydalanuvchilar, yangi kalitlar) topib oʻchiring, hisob-fakturani koʻring | Unit 42 tajribasida hujumchilar bir nechta regionda EC2 serverlar ochib, kriptovalyuta qazishgan |
| 5 | Shundan keyin, kerak boʻlsa, tarixni tozalang | keyingi boʻlim |

Unit 42 haqida bitta aniqlik: AWS kalitni karantin siyosati bilan cheklagan, serverlar tadqiqotchilar bu siyosatni
ataylab almashtirgandan keyin ochilgan. Xulosa: provayderga xabar borishi kalit bekor qilindi degani emas.

## 2-qadam (kerak boʻlsa): tarixni tozalash

Tarixni tozalash — keyingi qadam va har doim ham shart emas. U almashtirib boʻlmaydigan maʼlumot sizganda kerak:
mijozlar roʻyxati, shaxsiy maʼlumot, oson almashtirilmaydigan kalit. GitHub hujjati buning uchun **git-filter-repo**
vositasining yangi versiyasini tavsiya qiladi. Videoda bu kod kartochka sifatida koʻrsatilgan (bu repoda alohida fayl
emas, README'da bor):

```bash
# git-filter-repo >= 2.47 kerak; yangi clone'da ishlang
git clone git@github.com:SIZ/loyiha.git && cd loyiha
git log --all --name-only --format= | grep -E '(^|/)\.env' | sort -u
git filter-repo --sensitive-data-removal --invert-paths --path .env --path api/.env
git log --all -p -S 'SIR_QIYMATI'   # har bir sir uchun boʻsh chiqishi kerak
# jamoa push'ni toʻxtatsin: force push keyingi ishlarni oʻchiradi
git push --force --mirror origin    # refs/pull xatolari kutilgan
```

| Qator | Kod | Nima qiladi |
|---|---|---|
| 2 | `git clone … && cd loyiha` | serverdan **yangi** clone (`SIZ` — sizning GitHub nomingiz). Ehtiyot uchun filter-repo odatda faqat yangi clone'da ishlaydi |

## Tozalash ham hammasini tozalamaydi

Force push faqat **serverdagi** tarixni almashtiradi. Undan keyin ham kalit qoladigan joylar:

| Qayerda | Nima boʻladi | Kim tozalay oladi |
|---|---|---|
| hamkasbning eski clone'i | u oddiy push qilsa ham kalit serverga **qaytadi** (pastdagi tajriba) | faqat hamkasbning oʻzi: hamma qayta clone qiladi |
| fork'lar | eski commit'lar ularda qoladi | fork egasi |
| pull request havolalari, GitHub keshi | eski commit'lar ochilaveradi | faqat GitHub Support, va odatda faqat kalitni almashtirib boʻlmaydigan hollarda |
| hash orqali | NDSS tadqiqotchilari tarixi qayta yozilgan commit'ni ham hash'i orqali GitHub'dan ochib olishgan | — |

Shuning uchun GitHub hujjati ochiq aytadi: kalit almashtirilgan boʻlsa, tarixni qayta yozish «may not be
warranted» — «shart boʻlmasligi mumkin».

Birinchi qatorni oʻzimiz tekshirdik. Quyidagi skript **kurs papkasida yoʻq**: biz uni alohida yozib, ikki marta
ishga tushirdik (natija bir xil). GitHub oʻrnida lokal **bare** repo (ishchi fayllarsiz, faqat `.git` mazmuni boʻlgan
repo) `server.git` turadi. `men` — siz, `hamkasb` — kalit tozalanishidan oldin clone qilgan hamkasb.

```bash
#!/usr/bin/env bash
# Force push'dan keyin hamkasbning eski nusxasi kalitni serverga qaytaradi.
# Dars papkasiga saqlang va ./qur.sh dan keyin ishga tushiring: bash qayta.sh
# git-filter-repo >= 2.47 kerak. server.git — GitHub o'rnidagi bare repo.
set -e; cd "$(dirname "$0")"
rm -rf server.git hamkasb men
git clone -q --bare loyiha server.git
git clone -q server.git hamkasb; git -C hamkasb remote set-url origin ../server.git
git clone -q server.git men; git -C men remote set-url origin ../server.git

cd men
git filter-repo --sensitive-data-removal --invert-paths --path .env >/dev/null 2>&1
git push -q --force --mirror origin
echo "== server, force push'dan keyin:"; git -C ../server.git log --oneline

cd ../hamkasb
echo "== hamkasb pull qildi:"; git pull -q; git status -sb | head -1
echo "== hamkasb oddiy push qildi:"; git push origin main 2>&1
echo "== serverda kalit:"; git -C ../server.git grep TOLOV_KALIT= $(git -C ../server.git rev-list --all)
```

Uni dars papkasiga `qayta.sh` nomi bilan saqlang. `git -C <papka>` — buyruqni shu papkada bajaradi. `remote set-url origin ../server.git` server manzilini nisbiy
yoʻl qiladi, shunda natijada kompyuteringizdagi toʻliq yoʻl chiqmaydi. `git status -sb` — qisqa holat, birinchi
qatorda branch va serverga nisbatan nechta commit oldinda ekani.

Hamkasb `pull` qiladi, keyin oddiy (force emas) push. Serverda kalit qaytadimi?

**A)** yoʻq, `pull` uning tarixini server bilan bir xil qiladi · **B)** ha, `pull` eski commit'larni oʻchirmaydi va
push ularni qaytaradi

<details>
<summary>Javob</summary>

**B.** Hamkasbdagi `main` da `4590f4e ◄ cdd4176 ◄ 36288b8` bor. Serverdagi `4590f4e` uning ajdodi, shuning uchun
`pull` hech narsani oʻzgartirmaydi: git «siz 2 commit oldindasiz» deydi. Push esa oddiy fast-forward: server
`main` i `36288b8` ga suriladi va `cdd4176` ichidagi `.env` bilan birga qaytadi. «A» — `pull` serverni koʻchirib
oladi deb oʻylash: u faqat yetishmaganini qoʻshadi.

</details>

```console

4590f4e to'lov: kalit muhitdan
== hamkasb pull qildi:

== hamkasb oddiy push qildi:
To ../server.git
   4590f4e..36288b8  main -> main
```

## `.gitignore` tuzogʻi: kuzatilayotgan fayl

Endi kalit qayta tushmasligining oldini olamiz. Koʻpchilik `node_modules/` ni yozgandek `.gitignore` ga `.env`
yozadi va «ish bitdi» deb oʻylaydi. `tuzoq` reposida `.env` birinchi commit'danoq **kuzatiladi**: git uni allaqachon
commit'ga olgan va har oʻzgarishini koʻradi. Bunday fayl **kuzatiladigan fayl** (tracked file) deyiladi.

`.gitignore` ga `.env` yozamiz va `.env` ga kalitsiz bitta sozlama qoʻshamiz (`>>` — fayl oxiriga yozish).
`git status --short` nima koʻrsatadi?

**A)** `.env` umuman koʻrinmaydi: u endi eʼtiborsiz · **B)** ` M .env` — oʻzgargan · **C)** `!! .env` — eʼtiborsiz
qoldirilgan

<details>
<summary>Javob</summary>

**B.** `.gitignore` faqat hali kuzatilmagan fayllarga taʼsir qiladi. gitignore hujjati: «Files already tracked by Git
are not affected» («git allaqachon kuzatayotgan fayllarga taʼsir qilmaydi»). «A» yoki «C» ni tanlagan boʻlsangiz,
`.gitignore` ni hamma fayl uchun filtr deb oʻyladingiz: u faqat yangi, kuzatilmagan fayllarni `git add` dan
yashiradi.

</details>

```console
$ cd tuzoq && echo .env > .gitignore && echo DEBUG=1 >> .env && git status --short
 M .env
?? .gitignore
```

` M .env` — fayl oʻzgargan, git uni koʻrdi. `?? .gitignore` — yangi, hali kuzatilmagan fayl. Keyingi `git commit -a`
yoki `git add .` `.env` ni yana commit'ga oladi.

Faylni kuzatuvdan chiqarish uchun `git rm` ni `--cached` bayrogʻi bilan beramiz: u faylni **index**dan (keyingi
commit'ga tayyorlangan roʻyxat, GIT-2.02 da batafsil) oʻchiradi, diskka tegmaydi. Keyin commit qilamiz.
`--ignored` — `git status` eʼtiborsiz qoldirilgan fayllarni ham koʻrsatsin:

```console
$ cd tuzoq && git rm -q --cached .env && git add .gitignore && . ../vaqt.sh && git commit -qm ".env kuzatuvdan chiqdi" && git status --short --ignored && ls -A
!! .env
.env
.git
.gitignore
main.go
```

`!! .env` — fayl endi **eʼtiborsiz qoldirilgan** (ignored), lekin `ls -A` uni koʻrsatyapti: u diskda qoldi. Qaysi
qoida uni yashirayotganini `git check-ignore -v` aytadi:

```console
$ cd tuzoq && git check-ignore -v .env
.gitignore:1:.env	.env
```

Shakli `<fayl>:<qator>:<qoida>`, keyin tab va yoʻl: `.gitignore` ning 1-qatoridagi `.env` qoidasi `.env` ni yashiradi.

| Holat | `.env` kuzatiladimi | `git status` | Diskda |
|---|---|---|---|
| `qur.sh` dan keyin | ha | toza | bor |
| `.gitignore` + `DEBUG=1` | ha | ` M .env` | bor |
| `git rm --cached` + commit | yoʻq | `!! .env` (`--ignored` bilan) | bor |

Ikki diqqat:

1. **Yangi kalitni `.env` ga faqat shundan keyin yozing.** Fayl hali kuzatilayotganda yozsangiz, keyingi
   `git commit -a` yangi kalitni ham sizdiradi («Koʻp uchraydigan xatolar», 3-band).
2. **Eski commit'dagi kalit tarixda qolaveradi:**

```console
$ cd tuzoq && git show HEAD~1:.env
TOLOV_KALIT=soxta_9f2c7a41e8b3
```

Yana bir yon taʼsir: hamkasblar bu commit'ni `pull` qilganda ularning `.env` fayli **oʻchadi** (git uchun bu
«fayl oʻchirildi» oʻzgarishi). Oldindan nusxa olib qoʻyishsin.

## Toʻgʻri odat: `.gitignore` birinchi commit'dan oldin

Sir faqat `.env` da boʻlmaydi: SSH kaliti, maʼlumotlar bazasi paroli va token'lar ham xuddi shunday sizadi. Toʻgʻri
odat oddiy: `.gitignore` **birinchi commit'dan oldin** yoziladi. Unga `.env` bilan boshlanadigan hamma fayllarni
qoʻshing, `.env.example` ni esa undov belgisi `!` bilan istisno qiling:

```text
.env*
!.env.example
```

`.env*` — `.env`, `.env.local`, `.env.production` va boshqalar. `!.env.example` — «bu faylni yashirma». Repoga
faqat `.env.example` qoʻshiladi: unda oʻzgaruvchi nomlari bor, qiymatlari yoʻq (`fayllar/env.example` dagi kabi,
bitta qator `TOLOV_KALIT=`). Haqiqiy qiymatlar kompyuteringizda yoki server va CI'ning maxfiy sozlamalarida
(masalan, GitHub Actions secrets) turadi. Kalit fayllari uchun `*.pem` va `id_*` qoidalari ham foydali.

Koʻp hollarda sabab `git add .` buyrugʻi: u eʼtiborsiz qoldirilmagan hamma narsani qoʻshadi. `qur.sh` ning 20-qatori
aynan shunday edi. Commit'dan oldin `git status` (yoki `git diff --cached`) natijasini oʻqing. Commit'dan oldin kalit
qidiradigan skanerni beshinchi modulda oʻrnatamiz:
[GIT-5.04 · Git hook'lar: commit'dan oldin `gofmt`, lint va secret skaneri](/lab/youtube/git#git-5-04).

## Koʻp uchraydigan xatolar

Bu boʻlimdagi 3–6-misollar videoda yoʻq: biz ularni `./qur.sh` dan keyingi toza holatda ishga tushirdik.

### 1. «Faylni oʻchirdim — kalit ketdi»

Mavzuning asosiy notoʻgʻri tasavvuri. `git rm .env` + commit (yoki GIT-1.01 dagi `git revert`) faqat keyingi
suratdan faylni oladi, eski commit'da kalit qoladi va `git show HEAD~1:.env` uni qaytaradi («Kalit «oʻchirildi»,
lekin tarixda turibdi» boʻlimi). Tuzatish: kalitni rotate qiling, faylni emas.

### 2. «Reponi yopdim (yoki oʻchirdim) — xavf yoʻq»

Nusxalar skanerlarda, fork'larda va clone'larda qoladi. Toyota misolida yopish va kalitni almashtirish orasida ikki
kun oʻtgan, shu vaqt kalit ishlagan («1-qadam» boʻlimidagi javob). Tuzatish: avval rotate.

### 3. `.gitignore` yozildi, lekin `.env` hali kuzatilmoqda

`tuzoq` da `.gitignore` ga `.env` yozamiz, `.env` ga yangi kalitni yozamiz va odatdagidek `git commit -a` qilamiz
(`-a` — kuzatilayotgan hamma oʻzgargan fayllarni oladi):

```console
$ cd tuzoq && echo .env > .gitignore && echo TOLOV_KALIT=soxta_yangi > .env && . ../vaqt.sh && git commit -qam "kalit almashtirildi" && git show HEAD:.env
TOLOV_KALIT=soxta_yangi
```

Xato xabari yoʻq — bu jim xato. Yangi kalit ham commit'ga tushdi, `.gitignore` toʻxtatmadi. Tuzatish: avval
`git rm --cached .env` + commit, keyin yangi kalit.

### 4. `--cached` siz `git rm`

```console
$ cd tuzoq && git rm -q .env && ls -A
.git
main.go
```

`.env` diskdan ham oʻchdi: `git rm` faylni index'dan **va** ishchi fayllardan oladi. Lokal sozlamalaringiz yoʻqoldi.
Tuzatish: kuzatuvdan chiqarish uchun `git rm --cached .env`.

### 5. `.gitignore` da faqat `.env`

`.env.local` yaratib, `git add .` qilamiz:

```console
$ cd tuzoq && echo .env > .gitignore && git rm -q --cached .env && touch .env.local && git add . && git status --short
D  .env
A  .env.local
A  .gitignore
```

`D  .env` — `.env` kuzatuvdan chiqadi, lekin `A  .env.local` — yangi fayl commit'ga **qoʻshilmoqda**. `.env` qoidasi
aynan `.env` nomiga mos keladi, `.env.local` ga emas. `check-ignore` ham buni tasdiqlaydi:

```console
$ cd tuzoq && git check-ignore -v .env.local
```

Hech narsa chiqmadi (chiqish kodi 1): bu faylni hech bir qoida yashirmaydi. Tuzatish: `.env*` va `!.env.example`
(«Toʻgʻri odat» boʻlimi).

### 6. filter-repo eski repoda

`loyiha` ning oʻzida (yangi clone'da emas) tozalashga urinsak:

```console
$ cd loyiha && git filter-repo --sensitive-data-removal --invert-paths --path .env

this does not look like a fresh clone.
  (expected at most one entry in the reflog for HEAD)
Please operate on a fresh clone instead.  If you want to proceed
anyway, use --force.
```

«Toʻxtatildi: bu yangi clone'ga oʻxshamaydi, shuning uchun repo tarixini qaytarib boʻlmaydigan qilib qayta
yozmayman». Qavs ichida sabab: HEAD'ning reflog jurnalida (GIT-1.01) bittadan koʻp yozuv bor, yaʼni bu repoda ish qilingan.
Tuzatish: `--force` emas, yangi clone (`git clone -q loyiha toza`).

### 7. `git log -S TOLOV_KALIT` — ortiqcha commit

`-S` matn *soni* oʻzgargan commit'larni beradi. `=` siz qidirsak, `main.go` dagi `os.Getenv("TOLOV_KALIT")` ham
mos keladi:

```console
$ cd loyiha && git log --oneline -S TOLOV_KALIT

36288b8 kalitni o'chirdim
```

### 8. `--path .env` bilan «hammasi tozalandi»

Jim xato. `--path .env` faqat ildizdagi `.env` ni oʻchiradi: `api/.env`, `.env.local` yoki nomi oʻzgargan fayl
qoladi (GitHub hujjati: fayl nomini emas, toʻliq yoʻlni bering). Tuzatish: avval tarixdagi hamma env fayllarni
roʻyxatga oling («2-qadam» boʻlimidagi 3-qator), har birini `--path` bilan bering, keyin har bir sir qiymatini
`git log --all -p -S` bilan tekshiring.

## Oʻzingizni tekshiring

1. Nega keyingi commit'da `.env` ni oʻchirish kalitni tarixdan olib tashlamaydi?

<details>
<summary>Javob</summary>

Har commit — butun loyihaning oʻzgarmas surati. `git rm` + commit yangi surat qoʻshadi, eski surat (`cdd4176`) va
undagi `.env` blob'i joyida qoladi. `git show HEAD~1:.env` yoki `git grep … $(git rev-list --all)` uni topadi.

</details>

2. Kalit push qilindi. Toʻgʻri tartib qanday?

<details>
<summary>Javob</summary>

Avval rotate: fayldagi hamma sirlar uchun yangi kalit → ilova, eskisi bekor (tez almashtira olmasangiz — darhol
bekor). Keyin provayder jurnallari birinchi push vaqtidan, begona yaratilgan resurslarni oʻchirish. Shundan keyin,
kerak boʻlsa, yangi clone'da `git filter-repo`, mazmun boʻyicha tekshiruv, jamoa bilan kelishib force push va
hamma qayta clone qiladi.

</details>

3. `tuzoq` ni `./qur.sh` bilan qayta qurdingiz. Bu nima chiqaradi?

```text
cd tuzoq && echo .env > .gitignore && git status --short --ignored
```

<details>
<summary>Javob</summary>

Faqat `?? .gitignore`. `.env` hali kuzatiladi va oʻzgarmagan, shuning uchun u na ` M`, na `!!` boʻlib chiqadi:
kuzatilayotgan faylni `.gitignore` eʼtiborsiz qoldira olmaydi.

```console
$ cd tuzoq && echo .env > .gitignore && git status --short --ignored
?? .gitignore
```

</details>

4. GIT-1.01 dan: filter-repo ishlagandan keyin `4590f4e` ning hash'i nega oʻzgarmadi, `cdd4176` niki esa yoʻqoldi?

<details>
<summary>Javob</summary>

Commit hash'i uning mazmunidan hisoblanadi: tree (surat), parent, muallif, vaqt, xabar. `4590f4e` ning surati va
parent'i (u yoʻq) oʻzgarmadi, demak hash ham shu. `cdd4176` ning suratidan `.env` olingach, u hech narsani
oʻzgartirmaydigan boʻsh commit boʻlib qoldi, filter-repo esa bunday commit'larni tashlab yuboradi. `36288b8` ham
shunday. Qolgan har qanday keyingi commit'ning hash'i parent orqali oʻzgargan boʻlardi.

</details>

5. Push protection yoqilgan. Bu kalit hech qachon sizmaydi degani-mi?

<details>
<summary>Javob</summary>

Yoʻq. U faqat maʼlum formatdagi kalitlarni taniydi, foydalanuvchilar uchun faqat ochiq repolarda ishlaydi, uni
sabab koʻrsatib chetlab oʻtish mumkin. Oddiy satr (`soxta_…`) yoki parol oʻtib ketishi mumkin. Asosiy himoya —
`.gitignore` birinchi commit'dan oldin va `git add .` oʻrniga `git status` ni oʻqish.

</details>

## Uy vazifasi

Kurs papkasi: [lessons/git-02-env-leak](https://github.com/abdurahmon27/go-backend-uz/tree/main/lessons/git-02-env-leak).

1. 🟢 **Oson.** `./qur.sh`, keyin `loyiha` tarixidan kalitni oʻzingiz toping.
2. 🟡 **Oʻrta.** `tuzoq` da `.gitignore` ni shunday yozingki, `.env` bilan boshlangan hamma fayllar yashirinsin,
   `.env.example` esa koʻrinsin. `.env.local` va `.env.production` bilan tekshiring.
3. 🟠 **Qiyin.** Kalit qaysi commit'da paydo boʻlganini `git log -S 'TOLOV_KALIT='` bilan toping.
4. 🔴 **Guru.** `loyiha` ni clone qiling, `git filter-repo` bilan `.env` ni tozalang va kalit qolmaganini tekshiring.

Javoblar skripti:
[homework/javoblar.sh](https://github.com/abdurahmon27/go-backend-uz/blob/main/lessons/git-02-env-leak/homework/javoblar.sh)
(`bash homework/javoblar.sh`, dars papkasidan). U repolarni noldan quradi va har bir javobni koʻrsatadi. Guru qismi
uchun `git-filter-repo` 2.47+ kerak: u boʻlmasa, skript oʻrnatish havolasini chiqarib toʻxtaydi. Avval oʻzingiz
urinib koʻring.

<details>
<summary>Javob</summary>

🟢 `git show HEAD~1:.env` yoki `git grep TOLOV_KALIT= $(git rev-list --all)` →
`cdd4176…:.env:TOLOV_KALIT=soxta_9f2c7a41e8b3`.

🟡 `.gitignore`: `.env*` va `!.env.example`. Skript avval `git rm --cached .env` qiladi, `.env.example` ni qoʻshadi va
commit qiladi. `git status --short --ignored` uchala env faylni `!!` bilan koʻrsatadi, `git ls-files` (kuzatilayotgan
fayllar roʻyxati) esa `.env.example`, `.gitignore`, `main.go`. `git show HEAD~1:.env` hali ham kalitni chiqaradi:
tarix oʻzgarmadi.

🟠 `git log --oneline -S TOLOV_KALIT=` matn soni oʻzgargan ikki commit'ni beradi: `36288b8` (oʻchirdi) va `cdd4176`
(qoʻshdi). Birinchisini `--reverse` (eskidan yangiga) va `head -1` bilan olamiz: `cdd4176 lokal sozlamalar`. Nega
`=` muhim — «Koʻp uchraydigan xatolar», 7-band.

🔴 `git clone -q loyiha toza && cd toza && git filter-repo --sensitive-data-removal --invert-paths --path .env`.
Tarixda faqat `4590f4e` qoladi, `.env` ga tekkan commit yoʻq, `git log --all -p -S soxta_9f2c7a41e8b3` boʻsh.
Haqiqiy repoda bundan keyin jamoa bilan kelishib `git push --force --mirror origin`, hamma qayta clone qiladi. Kalit
esa baribir **rotate** qilinadi: bu birinchi qadam edi.

</details>
