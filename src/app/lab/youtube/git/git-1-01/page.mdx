## Nimani oʻrganasiz

Siz `git add`, `git commit` va `git push` ni har kuni yozasiz. Savol: `git branch chegirma` yozsangiz, butun loyiha
nusxalanadimi? Bugun buni `.git` papkasining ichida tekshiramiz. Javob: `.git/refs` ichida bor-yoʻgʻi bitta yangi fayl
paydo boʻladi, unda 40 belgilik hash va qator oxiri belgisi, jami 41 bayt.

**Bitta gʻoya:** commit — bu butun loyihaning surati (snapshot) va oldingi commit'ga havola, branch esa odatda
bitta commit hash'i yozilgan kichik fayl. Git ichida sehr yoʻq: hash bilan nomlangan obyektlar va ularga havola
qiluvchi kichik fayllar bor, xolos.

Dars oxirida siz:

- `git cat-file -p` bilan commit, tree va blob obyektlarini ochib, ularning har bir qatorini oʻqiysiz;
- hash qayerdan kelishini `git hash-object` va `sha1sum` bilan oʻzingiz tekshirasiz;
- branch va `HEAD` qaysi faylda turishini, fast-forward merge shu faylni qanday surishini koʻrsatib bera olasiz;
- `main` ga tushgan xatoni tarixni buzmasdan `git revert` bilan qaytarasiz va revert nimani *qilmasligini* bilasiz.

Bugungi uchta asosiy yangi soʻz:

| Soʻz | Oddiy maʼnosi | Inglizcha |
|---|---|---|
| surat (snapshot) | commit paytidagi butun loyihaning holati: farqlar roʻyxati emas | snapshot |
| obyekt | `.git/objects` dagi, oʻz mazmunining hash'i bilan nomlangan yozuv: **blob** (fayl mazmuni), **tree** (papka), **commit** | object (blob, tree, commit) |
| ref (havola) | ichida commit hash'i yozilgan nom: branch shunday ref, `HEAD` esa odatda branch'ga havola | ref (reference) |

Yordamchi soʻzlar matnda birinchi uchraganda bitta gap bilan tushuntiriladi: **parent** (oldingi commit),
**HEAD** (hozir turgan joyingiz), **fast-forward** (branch faylini oldinga surish), **revert** (teskari commit).

## Yangi branch: 41 baytlik fayl

Avval mashq repo'sini quramiz. `qur.sh` ichida nima borligini keyingi boʻlimlarda qatorma-qator ochamiz. Hozircha
natija yetarli: ikkita commit, eng yangisi tepada.

```console
$ ./qur.sh
daac3a4 narx dasturi
e657f41 README
```

Endi `chegirma` degan branch ochamiz. Diskda nima paydo boʻladi?

**A)** loyihaning toʻliq nusxasi · **B)** `.git` ichida yangi papka, obyektlar nusxasi bilan · **C)** bitta kichik fayl

<details>
<summary>Javob</summary>

**C.** `git branch chegirma` faqat `.git/refs/heads/chegirma` faylini yozadi. Ichida — hozirgi commit'ning toʻliq
hash'i. «A» yoki «B» ni tanlagan boʻlsangiz, branch'ni loyiha nusxasi deb oʻyladingiz. Git'da branch hech narsani
nusxalamaydi.

</details>

```console
$ cd ombor && git branch chegirma && find .git/refs -type f | sort && cat .git/refs/heads/chegirma
.git/refs/heads/chegirma
.git/refs/heads/main
daac3a47cb72faf965c5385ab1002bc04bf89b45
```

`find .git/refs -type f` — `.git/refs` ichidagi hamma fayllar, `sort` ularni alifbo tartibida qoʻyadi. Ikkita fayl:
`main` (u avvaldan bor edi) va yangi `chegirma`. `chegirma` ning ichida 40 belgilik hash: bu `daac3a4` commit'i,
`./qur.sh` chiqargan birinchi qator. Fayl hajmini oʻlchaymiz:

```console
$ cd ombor && wc -c .git/refs/heads/chegirma && tail -c 3 .git/refs/heads/chegirma | od -An -c
41 .git/refs/heads/chegirma
   4   5  \n
```

`wc -c` baytlarni sanaydi: 41. `tail -c 3` faylning oxirgi 3 baytini oladi, `od -An -c` ularni belgi-belgi koʻrsatadi
(`-An` — chap tomondagi manzil ustunisiz). Oxirgi uchta bayt: hash'ning soʻnggi ikki belgisi `4`, `5` va qator oxiri
`\n`. Demak 40 belgi + 1 = 41 bayt. Butun branch shu.

Bu «standart sozlamada» shunday: SHA-256 repo'da hash 64 belgi boʻladi va fayl 65 bayt, kelajakdagi **reftable**
formatida esa ref'lar alohida fayllarda turmaydi (bu haqda «Branch'ni qoʻlda yasash» boʻlimida).

## Commit — diff emas, surat

Koʻp dasturchi commit'ni oʻzgarishlar roʻyxati, yaʼni **diff** deb oʻylaydi: «bu commit `main.go` dagi bitta qatorni
oʻzgartirdi». Aslida git har commit'da **butun loyihaning suratini** saqlaydi. Pro Git kitobi buni shunday deydi:
Git oʻz maʼlumotini «miniatyura fayl tizimining **snapshot**'lari ketma-ketligi» deb biladi.

`git show` yoki `git diff` koʻrsatadigan diff esa commit ichida saqlanmaydi. Uni git ikki surat orasida har safar
qaytadan hisoblab chiqaradi.

Surat yonida commit'da yana bor:

- muallif va vaqt;
- xabar (`-m "…"`);
- **parent** — oldingi commit'ning hash'i.

Frontend'dagi oʻxshashi: React'da state'ni joyida oʻzgartirmaysiz, har safar yangi state obyektini berasiz. Ikki
holat orasidagi farqni esa kerak boʻlganda hisoblash mumkin. Git commit'lari ham shunday: har biri toʻliq,
oʻzgarmas holat, farq — hisoblanadigan narsa. Farqi: git surat ichidagi har bir fayl va papkaga uning mazmunidan
olingan hash bilan nom beradi. Bu nimaga olib kelishini «Oʻzgarmagan fayl qayta saqlanadimi?» boʻlimida koʻramiz.

## Mashq repo'si qanday qurilgan: `qur.sh`

`git init` boʻsh repo va uning ichida `.git` papkasini yaratadi. `git add` faylni keyingi commit'ga tayyorlab qoʻyadi.
`git commit` esa suratni olib, tarixga yozadi. Skript shu uch buyruqni ishlatadi, qolgani hash'lar hamma joyda bir
xil chiqishi uchun.

```bash filename="qur.sh" showLineNumbers
#!/usr/bin/env bash
# ombor/ ni noldan quradi: ikkita commit. Muallif va vaqt qat'iy (vaqt.sh). git >= 2.29.
set -e; cd "$(dirname "$0")"; rm -rf ombor; mkdir ombor; cd ombor
rf=--ref-format=files; git init -h 2>&1 | grep -q ref-format || rf=   # eski git'da bu bayroq yo'q
git init -q --template= -b main --object-format=sha1 $rf
git config user.name Lola
git config user.email lola@example.com
git config commit.gpgsign false; git config core.hooksPath /dev/null   # imzo va hook’lar hash’ni o’zgartiradi
git config core.pager cat; git config color.ui false; git config core.abbrev 7
git config core.autocrlf false; git config core.excludesFile /dev/null; git config core.attributesFile /dev/null
git config log.decorate false; git config branch.sort refname
git config merge.ff true; git config merge.stat true

cp ../fayllar/README.md .
git add README.md
. ../vaqt.sh; git commit -q -m "README"

cp ../fayllar/main.go .
git add main.go
. ../vaqt.sh; git commit -q -m "narx dasturi"
git log --oneline
```

| Qator | Kod | Nima qiladi |
|---|---|---|
| 1 | `#!/usr/bin/env bash` | skript `bash` bilan ishga tushadi |
| 3 | `set -e; cd …; rm -rf ombor; mkdir ombor; cd ombor` | birinchi xatoda toʻxtaydi; skript papkasiga oʻtadi; eski `ombor` ni oʻchirib, boʻshini yaratadi |
| 4 | `rf=--ref-format=files … \|\| rf=` | `git init -h` yordam matnidan (`2>&1` — stderr bilan birga) `ref-format` soʻzini jim (`-q`) qidiradi: topilsa (git 2.45+), ref'lar oddiy fayllarda saqlansin; topilmasa (`\|\|`), `rf` boʻsh |
| 5 | `git init -q --template= -b main --object-format=sha1 $rf` | boʻsh repo va `.git`: birinchi branch `main`, hash SHA-1, namuna fayllarsiz |
| 6–7 | `git config user.name` / `user.email` | muallif ismi va emaili, faqat shu repo uchun |
| 8 | `commit.gpgsign false`, `core.hooksPath /dev/null` | commit imzosi va hook'lar oʻchiq: ular commit mazmunini, demak hash'ni oʻzgartirishi mumkin |
| 9–12 | `core.pager cat`, `color.ui false`, `core.abbrev 7`, … | chiqish koʻrinishini qotiradi: pager va rang yoʻq, qisqa hash 7 belgi; global sozlamangizdagi qator oxiri, ignore va attributes fayllari eʼtiborsiz; `git log` bezaksiz, `git branch` nom boʻyicha, merge fast-forward qila oladi va statistika chiqaradi |
| 14–16 | `cp …README.md .`, `git add`, `. ../vaqt.sh; git commit` | birinchi surat: faqat `README.md` |
| 18–20 | xuddi shunday `main.go` bilan | ikkinchi surat: `README.md` + `main.go` |
| 21 | `git log --oneline` | yuqoridagi ikki qator: qisqa hash va xabar |

Vaqtni `vaqt.sh` qatʼiy qiladi:

```bash filename="vaqt.sh" showLineNumbers
# Manba qiling: `. ../vaqt.sh` (ombor/ ichidan). Commit vaqtini qat'iy qiladi:
# 2026-01-05 10:00 (+05:00) va har bir mavjud commit uchun +10 daqiqa.
# Shuning uchun commit hash'lari sizda ham, bizda ham bir xil chiqadi.
# muallif repo sozlamasidan olinsin (user.name/email), muhitdagi qiymatdan emas
unset GIT_AUTHOR_NAME GIT_AUTHOR_EMAIL GIT_COMMITTER_NAME GIT_COMMITTER_EMAIL
n=$(git rev-list --all --count 2>/dev/null || echo 0)
t=$((1767589200 + n * 600))
export GIT_AUTHOR_DATE="@$t +0500" GIT_COMMITTER_DATE="@$t +0500"
```

- 5-qator: muhitda `GIT_AUTHOR_NAME` kabi oʻzgaruvchi boʻlsa, uni olib tashlaydi, ism repo sozlamasidan olinadi.
- 6-qator: repo'dagi commit'lar soni (`n`). `$(…)` buyruq natijasini qiymat qilib oladi; commit hali yoʻq boʻlsa (`||`), `0`.
- 7-qator: `$((…))` — shell arifmetikasi. `1767589200` — 2026-01-05 10:00 Toshkent vaqti, Unix soniyalarida; har commit
  uchun +600 soniya (10 daqiqa).
- 8-qator: git bu ikki muhit oʻzgaruvchisidan vaqtni oladi. `@` dan keyin Unix vaqti, `+0500` — UTC'dan farq.

`. ../vaqt.sh` (nuqta va boʻsh joy) skriptni **joriy** shell'da bajaradi, shuning uchun `export` qilingan qiymatlar
keyingi `git commit` ga yetib boradi. `bash vaqt.sh` esa alohida jarayonda ishlardi va muhit u bilan birga yoʻqolardi
(SYS-0.02).

Oʻz repo'ngizda bularning hech biri kerak emas: ism va emailni bir marta yozasiz, keyin oddiy `git commit`.

```bash
git config --global user.name "Ism"
git config --global user.email "siz@example.com"
```

## Commit ichida nima bor

Endi commit'ning ichini ochamiz. `git cat-file -p` obyektni oʻqiladigan koʻrinishda chiqaradi (`-p` — *pretty-print*).
**HEAD** — hozir turgan joyingiz, yaʼni hozirgi branch'ning oxirgi commit'i.

```console
$ cd ombor && git cat-file -p HEAD
tree 651f29e7e2b98f1f8f5b84a4051ff7e85e41e3fb
parent e657f417275efcc319ccce4e1badded9976a8fa6
author Lola <lola@example.com> 1767589800 +0500
committer Lola <lola@example.com> 1767589800 +0500

narx dasturi
```

| Qator | Nima |
|---|---|
| `tree 651f29e…` | loyiha papkasining surati: tree obyektining hash'i (keyingi boʻlimda ochamiz) |
| `parent e657f41…` | oldingi commit'ning 40 belgilik hash'i. Shu havola commit'larni zanjirga ulaydi |
| `author Lola … 1767589800 +0500` | kodni yozgan odam va vaqt: Unix soniyalari, yonida UTC'dan farq (+5 soat, Toshkent vaqti): 2026-01-05 10:10 |
| `committer …` | commit'ni yaratgan odam. Koʻpincha muallif bilan bir xil; boshqa birovning patch'ini qoʻllasangiz, farq qiladi |
| boʻsh qator, `narx dasturi` | commit xabari |

Diff yoʻq: commit ichida faqat surat (tree), parent, kim, qachon va nima uchun. Butun zanjirni `git log` bilan
koʻramiz. `%h` — qisqa hash, `%p` — parent'ning qisqa hash'i, `%s` — xabar:

```console
$ cd ombor && git log --format='%h  parent: %p  %s'
daac3a4  parent: e657f41  narx dasturi
e657f41  parent:   README
```

Birinchi commit'da parent yoʻq: u zanjirning boshi.

## tree va blob

`tree` ichida har bir fayl yoki ichki papka uchun bitta qator bor. `'HEAD^{tree}'` — «HEAD commit'ining tree'si»;
qoʻshtirnoq shell `{}` ga tegmasligi uchun.

```console
$ cd ombor && git cat-file -p 'HEAD^{tree}'
100644 blob 51c4fee9be20d18260ace91ce44e4b9c0ca396ab	README.md
100644 blob 12b6d3bcf6f52e8be1d6f34b155db13dfbc46215	main.go
```

Har qatorda toʻrt narsa: **rejim**, obyekt turi, hash va nom. Olti xonali rejim — ruxsatlar emas, fayl turi:

| Rejim | Maʼnosi |
|---|---|
| `100644` | oddiy fayl (bizdagi ikkalasi) |
| `100755` | bajariladigan fayl |
| `120000` | symlink |
| `040000` | ichki papka: bu qator yana bir `tree` ga havola |

Fayl mazmuni **blob** degan obyektda turadi. `HEAD:main.go` — «HEAD tree'sidagi `main.go`»:

```console
$ cd ombor && git cat-file -p HEAD:main.go
package main

import "fmt"

func main() { fmt.Println("non: 3000 so'm") }
```

Faylning oʻzi chiqdi. Blob'da fayl nomi ham, vaqt ham yoʻq, faqat mazmuni bor: nom tree'da turadi. Obyektlar diskda
zlib bilan siqilgan holda yotadi, shuning uchun ularni `cat` bilan emas, `git cat-file` bilan oʻqiymiz.

Ikkala commit va ularning obyektlari bitta rasmda:

```text
 .git/refs/heads/main
        │
        ▼
 commit daac3a4 "narx dasturi" ──parent──► commit e657f41 "README"
        │ tree                                    │ tree
        ▼                                         ▼
 tree 651f29e                              tree 19c7d67
 ├── README.md ──► blob 51c4fee ◄───────── └── README.md
 └── main.go   ──► blob 12b6d3b
```

## Oʻzgarmagan fayl qayta saqlanadimi?

Videodagi pauza savoli. `README.md` birinchi commit'da qoʻshilgan, ikkinchisida esa oʻzgarmagan. Ikkala commit —
toʻliq surat. Ikkinchi surat uchun git README'ni yana bir marta saqlaydimi?

**A)** ha, har surat oʻz nusxasini saqlaydi · **B)** yoʻq, ikkala tree bitta blob'ga havola qiladi · **C)** yoʻq, chunki
ikkinchi commit faqat diff'ni saqlaydi

<details>
<summary>Javob</summary>

**B.** Hash mazmundan hisoblanadi. Mazmun bir xil boʻlsa, hash ham bir xil, demak obyekt ham bitta. Ikkinchi tree
oʻsha blob'ga havola qiladi, yangi nusxa yaratilmaydi. «A» ni tanlagan boʻlsangiz, surat = nusxa deb oʻyladingiz.
«C» — dars boshidagi «commit = diff» xatosi: commit'da diff yoʻq.

</details>

Tekshiramiz. `HEAD~1` — HEAD'ning parent'i; `git rev-parse` nomni toʻliq hash'ga aylantiradi:

```console
$ cd ombor && git rev-parse HEAD:README.md HEAD~1:README.md
51c4fee9be20d18260ace91ce44e4b9c0ca396ab
51c4fee9be20d18260ace91ce44e4b9c0ca396ab
```

Ikkala commit'dagi README hash'i bir xil. Repodagi hamma obyektlarni turi bilan chiqaramiz (`cut -c1-20` har qatorning
birinchi 20 belgisini qoldiradi):

```console
$ cd ombor && git cat-file --batch-all-objects --batch-check='%(objecttype) %(objectname)' | cut -c1-20
blob 12b6d3bcf6f52e8
tree 19c7d673a51f53a
blob 51c4fee9be20d18
tree 651f29e7e2b98f1
commit daac3a47cb72f
commit e657f417275ef
```

Ikkita commit, ikkita tree va ikkita blob, jami oltita. README uchun bitta blob: yuqoridagi rasmdagi kabi.

Bu yerda JavaScript bilan farq koʻrinadi. JS'da `{ a: 1 }` va `{ a: 1 }` — ikki xil obyekt, `===` `false` beradi:
obyektning nomi xotiradagi joyi. Git'da obyektning nomi mazmunining hash'i, shuning uchun bir xil mazmun doim bitta
obyekt boʻladi. Bunday saqlash **content-addressable** deyiladi.

Clone qilingan yoki katta repo'da git obyektlarni alohida fayllarda emas, **packfile** degan paketlarga yigʻadi
(`git gc`, push va clone paytida). Paket ichida oʻxshash fayllar farq (delta) koʻrinishida siqiladi. Lekin bu faqat
saqlash usuli: `git cat-file -p` baribir toʻliq tree va toʻliq faylni qaytaradi, commit baribir toʻliq surat.

## Hash qayerdan keladi

Hash'ni oʻzimiz tekshiramiz. `git hash-object --stdin` standart kirishdan kelgan matnning blob hash'ini hisoblaydi.
`printf 'non: 3000\n'` — bitta qatorli matn (`\n` — qator oxiri), jami 10 bayt:

```console
$ printf 'non: 3000\n' | git hash-object --stdin
2ecbbc99c0932c7b1430e07e274c706f3afb62ef
```

Endi xuddi shu hash'ni git'siz olamiz. `sha1sum` ga sarlavha beramiz: `blob` soʻzi, boʻsh joy va uzunlik (`10`).
Keyin nol bayt (`\0`) va oʻsha matn keladi:

```console
$ printf 'blob 10\0non: 3000\n' | sha1sum
2ecbbc99c0932c7b1430e07e274c706f3afb62ef  -
```

Natija harfma-harf bir xil (`-` — «standart kirishdan oʻqildi» degani). Demak, obyekt hash'i =
SHA-1(`<tur> <uzunlik>\0` + mazmun). macOS'da `sha1sum` oʻrniga `shasum` ishlating.

Bitta raqamni oʻzgartirsak, hash'ning faqat oxiri oʻzgaradimi?

**A)** ha, oxirgi bir-ikki belgi · **B)** yoʻq, butunlay boshqa hash · **C)** hash oʻzgarmaydi, uzunlik bir xil

<details>
<summary>Javob</summary>

**B.** Pastdagi natijaga qarang: bitta raqam oʻzgardi, 40 belgining hammasi boshqa. «C» ni tanlagan boʻlsangiz,
hash uzunlikdan hisoblanadi deb oʻyladingiz: uzunlik sarlavhaning faqat bir qismi, mazmun ham hisobga kiradi.

</details>

```console
$ printf 'non: 3001\n' | git hash-object --stdin
a3fad3e262bce90907d0538b01444aaa526edd9a
```

Commit ham obyekt, uning mazmunida esa `parent` hash'i bor. Shuning uchun eski commit'ni qayta yozsak, undan keyingi
hamma commit'larning hash'i ham oʻzgaradi: har biri oʻzidan oldingisining hash'ini ichida saqlaydi.

SHA-1 endi eskirgan hisoblanadi. Git'ning BreakingChanges hujjati Git 3.0 da yangi repo'lar uchun standart hash'ni
SHA-256 ga almashtirishni rejalashtiradi (sanasi belgilanmagan). Hash'ni Go'da oʻzimiz hisoblash —
[GIT-7.01](/lab/youtube/git#git-7-01).

## Branch — bitta hash yozilgan fayl, HEAD — hozirgi branch

Endi branch'ning oʻziga qaraymiz. Avval `HEAD`:

```console
$ cd ombor && cat .git/HEAD
ref: refs/heads/main
```

`HEAD` faylida odatda hash emas, boshqa ref'ga yoʻl turadi: `refs/heads/main`. Yaʼni `HEAD` hozir qaysi branch'da
turganingizni bildiradi. `main` faylida esa:

```console
$ cd ombor && cat .git/refs/heads/main
daac3a47cb72faf965c5385ab1002bc04bf89b45
```

Oxirgi commit'ning 40 belgilik hash'i. Pro Git'ning taʼrifi ham shunday: branch — commit'lar zanjiridagi oxirgi
commit'ga havola. Unda nusxa ham, papka ham yoʻq.

```text
 .git/HEAD                    .git/refs/heads/main         .git/objects
 ┌──────────────────────┐     ┌──────────────────┐        ┌────────────────────┐
 │ ref: refs/heads/main │ ──► │ daac3a47cb72…45  │ ─────► │ commit daac3a4 …   │
 └──────────────────────┘     └──────────────────┘        └────────────────────┘
   qaysi branch'dasiz           branch = 41 bayt            oʻzgarmas obyekt
```

JS bilan solishtirsak: commit — muzlatilgan (`Object.freeze`) obyekt, branch esa unga havola saqlaydigan `let`
oʻzgaruvchi. Yangi commit yangi obyekt yaratadi va oʻzgaruvchini unga qayta bogʻlaydi; eski obyekt joyida qoladi.

«Odatda» degan soʻz muhim. Commit'ga toʻgʻridan-toʻgʻri oʻtsangiz (`git switch --detach`), `HEAD` faylida hash turadi:
bu **detached HEAD** deyiladi. Bu misol videoda yoʻq, faqat koʻrish uchun (oxiridagi `git switch -q main` sizni
`main` ga qaytaradi):

```console
$ cd ombor && git switch -q --detach HEAD~1 && cat .git/HEAD && git switch -q main
e657f417275efcc319ccce4e1badded9976a8fa6
```

## Branch'ni qoʻlda yasash (faqat tajriba)

Isbot uchun `git branch` buyrugʻisiz yangi branch yaratamiz: birinchi commit'ning hash'ini oddiy faylga yozamiz.
`>` — buyruq natijasini faylga yozish.

```console
$ cd ombor && git rev-parse HEAD~1 > .git/refs/heads/eski && git branch
  chegirma
  eski
* main
```

`git branch` roʻyxatida `eski` paydo boʻldi (`*` — `HEAD` turgan branch). Fayl yozildi — branch bor. Lekin bu faqat
tushunish uchun tajriba. `git branch` yoki `git update-ref` qiymatni tekshiradi va **reflog** jurnaliga ham yozadi
(reflog — branch qayerlarda boʻlganining jurnali, [GIT-3.02](/lab/youtube/git#git-3-02)):

```console
$ cd ombor && ls .git/logs/refs/heads/
chegirma
main
```

`chegirma` va `main` uchun jurnal bor, qoʻlda yozilgan `eski` uchun yoʻq. Bundan tashqari:

- git ref'larni baʼzan `.git/packed-refs` degan bitta faylga yigʻadi (`git gc` yoki `git pack-refs --all` dan keyin);
  unda `refs/heads` ichidagi fayllar yoʻqoladi;
- Git 3.0 da yangi repo'lar uchun ref'larni **reftable** formatida saqlash rejalashtirilgan.

Shuning uchun ref fayllariga qoʻlda tegmang: branch yaratish uchun `git branch <nom> <commit>` ishlating.

## Branch'da ishlash: switch, status, add, commit

Endi `chegirma` branch'iga oʻtamiz va narxni oʻzgartiramiz. Narxga 10 foiz chegirma qilmoqchi edik, lekin xato qilib,
narxni nolga tushirdik. `git switch -q chegirma` — `HEAD` ni `chegirma` ga oʻtkazadi (`-q` — jim). `sed -i.bak
's/3000/0/' main.go` faylda `3000` ni `0` ga almashtiradi (`.bak` zaxira nusxasi macOS'da ham ishlashi uchun, keyin
uni `rm` oʻchiradi). `git status --short` oʻzgargan fayllarni qisqa koʻrsatadi:

```console
$ cd ombor && git switch -q chegirma && sed -i.bak 's/3000/0/' main.go && rm main.go.bak && git status --short
 M main.go
```

` M` — fayl oʻzgargan, lekin hali `git add` qilinmagan. `git add` uni tayyorlaydi, keyin commit qilamiz (vaqt yana
`vaqt.sh` dan):

```console
$ cd ombor && git add main.go && . ../vaqt.sh && git commit -m "chegirma: 10 foiz"
[chegirma 5a239b1] chegirma: 10 foiz
 1 file changed, 1 insertion(+), 1 deletion(-)
```

`[chegirma 5a239b1]` — qaysi branch'ga va qanday hash bilan yozildi. Endi hamma branch'larni koʻramiz (`--all` —
hamma ref'lardan, `--decorate` — har commit yonida unga havola qiladigan ref'lar):

```console
$ cd ombor && git log --oneline --decorate --all
5a239b1 (HEAD -> chegirma) chegirma: 10 foiz
daac3a4 (main) narx dasturi
e657f41 (eski) README
```

Faqat `chegirma` oldinga yurdi, `main` esa joyida qoldi. `HEAD -> chegirma` — `HEAD` faylida endi
`ref: refs/heads/chegirma`.

| Fayl | `qur.sh` dan keyin | `chegirma` commit'idan keyin |
|---|---|---|
| `.git/HEAD` | `ref: refs/heads/main` | `ref: refs/heads/chegirma` |
| `refs/heads/main` | `daac3a4…` | `daac3a4…` |
| `refs/heads/chegirma` | `daac3a4…` | `5a239b1…` |
| `refs/heads/eski` | — | `e657f41…` |

## Merge: fast-forward

Endi `main` ga qaytib, chegirmani merge qilamiz. Git yangi commit yaratadimi?

**A)** ha, ikki parent'li merge commit · **B)** yoʻq, `main` fayliga `chegirma` ning hash'i yoziladi · **C)** `chegirma`
dagi commit `main` ga nusxalanadi

<details>
<summary>Javob</summary>

**B.** `chegirma` ochilgandan beri `main` da yangi commit boʻlmagan: `main` ning oxirgi commit'i `chegirma` ning
ajdodi. Bunday holda birlashtiradigan narsa yoʻq, git `main` ni oldinga suradi. Bu **fast-forward** deyiladi.
«A» — ikkala branch'da yangi commit boʻlgandagi holat. «C» ni tanlagan boʻlsangiz, commit branch'ga tegishli deb
oʻyladingiz: commit bitta, ikkala branch shunchaki unga havola qiladi.

</details>

```console
$ cd ombor && git switch -q main && git merge chegirma
Updating daac3a4..5a239b1
Fast-forward
 main.go | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

`Updating daac3a4..5a239b1` — `main` `daac3a4` dan `5a239b1` ga surildi; `Fast-forward` — merge commit kerak
boʻlmadi. Git `main` fayliga `chegirma` ning hash'ini yozdi va ishchi fayllarni (working tree) ham yangiladi: diskdagi
`main.go` endi `0` li versiya. Ikki branch fayli endi bir xil:

```console
$ cd ombor && cat .git/refs/heads/main .git/refs/heads/chegirma
5a239b10ba4641d54a7500d0de49f8352df729ce
5a239b10ba4641d54a7500d0de49f8352df729ce
```

Ikkala branch'da yangi commit boʻlsa, ikki parent'li merge commit paydo boʻladi. Uni ikkinchi modulda koʻramiz:
[GIT-2.02](/lab/youtube/git#git-2-02).

## Revert: xatoni yangi commit bilan qaytarish

Dasturni ishga tushiramiz:

```console
$ cd ombor && go run main.go
non: 0 so'm
```

Non nol soʻm. Xato allaqachon `main` branch'iga tushib boʻldi. Tarixni oʻchirmaymiz, `git revert` ishlatamiz: u
koʻrsatilgan commit'ning teskari oʻzgarishini **yangi commit** sifatida yozadi (`--no-edit` — xabarni muharrirsiz,
avtomatik).

Revert'dan keyin `git log --oneline` nechta commit koʻrsatadi?

**A)** 3: xatoli commit tarixdan chiqib ketadi · **B)** 4: xatoli commit ham, uning teskarisi ham · **C)** 2

<details>
<summary>Javob</summary>

**B.** Revert hech narsani oʻchirmaydi, faqat qoʻshadi. «A» ni tanlagan boʻlsangiz, revert'ni `git reset` bilan
adashtirdingiz: `reset` branch faylini orqaga suradi va tarixni qayta yozadi ([GIT-3.01](/lab/youtube/git#git-3-01)).

</details>

```console
$ cd ombor && . ../vaqt.sh && git revert --no-edit HEAD
[main 14b041d] Revert "chegirma: 10 foiz"
 Date: Mon Jan 5 10:30:00 2026 +0500
 1 file changed, 1 insertion(+), 1 deletion(-)
```

` Date:` qatori faqat bizda chiqadi: muallif vaqti `vaqt.sh` orqali alohida berilgan. Oʻz repo'ngizda bu qator
boʻlmaydi.

```console
$ cd ombor && git log --oneline
14b041d Revert "chegirma: 10 foiz"
5a239b1 chegirma: 10 foiz
daac3a4 narx dasturi
e657f41 README
```

Tarixda endi toʻrtta commit bor, hech biri yoʻqolmadi. Narxni tekshiramiz:

```console
$ cd ombor && go run main.go
non: 3000 so'm
```

Narx yana 3000 soʻm. Jamoa ishlaydigan branch'da aynan shu yoʻl xavfsiz: hamkasblaringizda bor commit'lar oʻzgarmaydi,
faqat ustiga yangisi qoʻshiladi, shuning uchun hech kimning tarixi buzilmaydi.

**Lekin diqqat:** revert eski commit'ni oʻchirmaydi. Commit'ga parol yoki kalit tushgan boʻlsa, u `5a239b1` kabi
tarixda qoladi va `git cat-file -p` bilan baribir oʻqiladi. Nima qilish kerakligi — keyingi dars,
[GIT-1.02](/lab/youtube/git/git-1-02).

## Butun model bitta jadvalda

| Buyruq | `.git` ichida nima oʻzgaradi |
|---|---|
| `git commit` | yangi obyektlar (oʻzgargan fayllar uchun blob, tree'lar, commit) + hozirgi branch fayliga yangi hash |
| `git branch X` | yangi fayl `refs/heads/X`, ichida hozirgi commit hash'i (+ reflog) |
| `git switch X` | `HEAD` fayliga `ref: refs/heads/X` + ishchi fayllar shu commit'ga moslanadi |
| `git merge X` (fast-forward) | hozirgi branch fayliga `X` ning hash'i + ishchi fayllar |
| `git revert C` | `C` ning teskarisi boʻlgan yangi commit; eski obyektlar joyida |

Qisqacha: commit — butun loyiha surati va parent'ga havola. Branch — odatda bitta hash yozilgan kichik fayl. `HEAD`
qaysi branch'da turganingizni koʻrsatadi. Fast-forward merge shu faylni oldinga suradi. Revert xatoni yangi commit
bilan qaytaradi va tarixni buzmaydi. Rebase, reset va reflog ham aynan shu obyektlar va ref'lar ustida ishlaydi.

## Koʻp uchraydigan xatolar

Bu boʻlimdagi buyruqlarning baʼzilari videoda yoʻq: biz ularni oʻsha mashq repo'sida ishga tushirdik, har birining
oldida qaysi holatdan ekanini yozdik.

### 1. «Commit — bu diff»

Eng koʻp uchraydigan notoʻgʻri tasavvur. Unga ishonsangiz, «oʻzgarmagan fayl qayerda saqlanadi?» yoki «nega bitta
commit'ni tiklash uchun oldingilarini qoʻllash shart emas?» degan savollarga javob topa olmaysiz. Commit ichida diff
yoʻq: `tree`, `parent`, muallif, vaqt va xabar («Commit ichida nima bor» boʻlimi). Diff'ni `git show` va `git diff`
ikki surat orasida hisoblaydi. Paketlardagi delta esa faqat saqlash usuli («Oʻzgarmagan fayl qayta saqlanadimi?»).

### 2. «Commit'im yoʻqoldi»: `git log` faqat hozirgi branch'ni koʻrsatadi

Holat: `chegirma` commit'idan keyin, merge'dan oldin (`./qur.sh`, `git branch chegirma`, keyin «Branch'da ishlash»
boʻlimidagi ikki buyruq). `main` ga oʻtib, tarixga qarasangiz:

```console
$ cd ombor && git switch -q main && git log --oneline
daac3a4 narx dasturi
e657f41 README
```

`5a239b1` yoʻq. U oʻchmagan: oddiy `git log` faqat `HEAD` dan parent'lar boʻylab orqaga yuradi, `5a239b1` esa
`main` ning ajdodi emas. Hamma ref'lardan koʻrish uchun `--all`:

```console
$ cd ombor && git log --oneline --all
5a239b1 chegirma: 10 foiz
daac3a4 narx dasturi
e657f41 README
```

### 3. `cd ombor` ikki marta

Sahifadagi buyruqlar dars papkasidan boshlanadi. `ombor` ichida turib yana `cd ombor && …` yozsangiz:

```console
$ cd ombor && git log --oneline
bash: cd: ombor: No such file or directory
```

Qanday oʻqiladi: `bash: cd:` — xatoni bash'ning `cd` buyrugʻi yozdi; `ombor: No such file or directory` — «`ombor`
degan fayl yoki papka yoʻq»: siz allaqachon uning ichidasiz. `&&` dan keyingi buyruq ishlamadi. Tuzatish: `cd ombor && `
qismini yozmang yoki avval `cd ..`. (zsh'da xabar matni biroz boshqacha: `no such file or directory: ombor`.)

### 4. Obyektni `cat` bilan oʻqish

`.git/objects/51/c4fee9…` — README blob'ining fayli (hash'ning birinchi ikki belgisi papka nomi). `cat` bilan ochsangiz,
ekranga oʻqib boʻlmaydigan baytlar chiqadi. Birinchi ikki baytga qaraymiz (`-tx1` — har baytni 16 lik sonda):

```console
$ cd ombor && head -c 2 .git/objects/51/c4fee9be20d18260ace91ce44e4b9c0ca396ab | od -An -tx1
 78 01
```

`78 01` — zlib sarlavhasi (RFC 1950: `78` — deflate siqish): fayl siqilgan. Tuzatish:
`git cat-file -p 51c4fee` yoki `git cat-file -p HEAD:README.md`. Clone qilingan yoki `git gc` qilingan repo'da bu
fayl umuman boʻlmasligi mumkin: obyekt packfile ichida.

### 5. Ref faylini qoʻlda notoʻgʻri yozish

Holat: dars oxiri (revert'dan keyin). Hash oʻrniga branch nomini yozib koʻramiz:

```console
$ cd ombor && echo chegirma > .git/refs/heads/buzuq && git branch
warning: ignoring broken ref refs/heads/buzuq
  chegirma
  eski
* main
```

`warning: ignoring broken ref refs/heads/buzuq` — «ogohlantirish: buzilgan `refs/heads/buzuq` ref'i eʼtiborsiz
qoldirildi». Ref faylida 40 belgilik hash (yoki `ref: …`) kutiladi. Git xato bermadi, branch shunchaki roʻyxatda
yoʻq. Buzuq faylni oʻchiramiz:

```console
$ cd ombor && rm .git/refs/heads/buzuq && git branch
  chegirma
  eski
* main
```

Toʻgʻri yoʻl — git buyrugʻi: u nomni hash'ga aylantiradi, tekshiradi va reflog yozadi.

```bash
git branch buzuq chegirma            # yoki: git update-ref refs/heads/buzuq chegirma
```

### 6. `git gc` dan keyin branch fayli yoʻq

Holat: 5-xatodan keyin. `git gc` (`-q` — jim) obyektlar va ref'larni yigʻib qoʻyadi:

```console
$ cd ombor && git gc -q && cat .git/refs/heads/main
cat: .git/refs/heads/main: No such file or directory
```

«`.git/refs/heads/main`: bunday fayl yoki papka yoʻq». Branch yoʻqolmadi, u `.git/packed-refs` ga koʻchdi. Branch
qayerda saqlanganidan qatʼi nazar, uning hash'ini `git rev-parse` beradi:

```console
$ cd ombor && git rev-parse main
14b041d603417386d5d82e8f1e0bde53420b4980
```

```console
$ cd ombor && cat .git/packed-refs
# pack-refs with: peeled fully-peeled sorted 
5a239b10ba4641d54a7500d0de49f8352df729ce refs/heads/chegirma
e657f417275efcc319ccce4e1badded9976a8fa6 refs/heads/eski
14b041d603417386d5d82e8f1e0bde53420b4980 refs/heads/main
```

Qoida: skriptlarda `cat .git/refs/heads/…` emas, `git rev-parse <branch>` yozing.

### 7. «Hash'larim videodagidan boshqacha»

Oʻz repo'ngizda (yoki `qur.sh` siz qoʻlda qurilgan repo'da) hash'lar boshqacha chiqadi. Bu xato emas: commit
mazmunida ism, email va soniyagacha vaqt bor, ular boshqa boʻlsa, hash ham boshqa. Blob hash'lari esa faqat
mazmunga bogʻliq: `printf 'non: 3000\n' | git hash-object --stdin` hamma joyda `2ecbbc99…` beradi. `qur.sh` orqali
qurilgan repo'da hash'lar farq qilsa, git versiyangizni tekshiring (`git --version`, kamida 2.29).

### 8. «Revert qildim — kalit tarixdan ketdi»

Ketmadi. Revert yangi commit qoʻshadi, eski commit va uning blob'i joyida qoladi («Revert» boʻlimi). Sizib chiqqan
kalitni avval bekor qilish kerak: [GIT-1.02](/lab/youtube/git/git-1-02).

## Oʻzingizni tekshiring

1. Commit obyektida qaysi qatorlar bor va ularning qaysi biri commit'larni zanjirga ulaydi?

<details>
<summary>Javob</summary>

`tree` (loyiha surati), `parent` (oldingi commit hash'i; birinchi commit'da yoʻq), `author`, `committer` (ism, email,
Unix vaqti va UTC'dan farq) va xabar. Zanjirni `parent` ulaydi. Diff qatori yoʻq.

</details>

2. Branch fayli `.git/refs/heads/main` da nima turadi va nega u 41 bayt?

<details>
<summary>Javob</summary>

Oxirgi commit'ning toʻliq SHA-1 hash'i: 40 ta hex belgi va qator oxiri `\n`, jami 41 bayt. SHA-256 repo'da 65 bayt
boʻlardi; `git gc` dan keyin fayl umuman boʻlmasligi mumkin (`packed-refs`).

</details>

3. Revert'dan keyingi commit'ni oching. `parent` qatorida qaysi hash turadi?

```text
cd ombor && git cat-file -p HEAD
```

<details>
<summary>Javob</summary>

Xatoli commit `5a239b1…`: revert uning ustiga qoʻshildi. `tree` esa `651f29e…` — `qur.sh` dagi ikkinchi commit'ning
tree'si bilan bir xil, chunki fayllar yana 3000 soʻmli holatga qaytdi. Bir xil mazmun — bir xil hash.

```console
$ cd ombor && git cat-file -p HEAD
tree 651f29e7e2b98f1f8f5b84a4051ff7e85e41e3fb
parent 5a239b10ba4641d54a7500d0de49f8352df729ce
author Lola <lola@example.com> 1767591000 +0500
committer Lola <lola@example.com> 1767591000 +0500

Revert "chegirma: 10 foiz"

This reverts commit 5a239b10ba4641d54a7500d0de49f8352df729ce.
```

</details>

4. `git merge chegirma` nega yangi commit yaratmadi? Qachon yaratgan boʻlardi?

<details>
<summary>Javob</summary>

`chegirma` ochilgandan beri `main` da yangi commit yoʻq edi, shuning uchun git `main` faylini `chegirma` ning
hash'iga surdi (fast-forward) va ishchi fayllarni yangiladi. Ikkala branch'da yangi commit boʻlganda ikki parent'li
merge commit paydo boʻladi (GIT-2.03).

</details>

5. Jamoa ishlaydigan `main` da xato commit bor. Nega `git revert`, va u nimani qilmaydi?

<details>
<summary>Javob</summary>

Revert tarixni qayta yozmaydi, faqat teskari commit qoʻshadi: hamkasblardagi commit'lar va hash'lar oʻzgarmaydi.
Lekin eski commit'ni oʻchirmaydi: unga tushgan parol yoki kalit tarixda qoladi.

</details>

6. SYS-0.01 dan: `git branch chegirma` dan keyin (`./qur.sh` dan keyingi holatda) bu nima chiqaradi?

```text
cd ombor && find .git/refs -type f | wc -l
```

<details>
<summary>Javob</summary>

`2`. `find` ikki fayl yoʻlini (`main` va `chegirma`) pipe'ga yozadi, `wc -l` ularni sanaydi.

```console
$ cd ombor && git branch chegirma && find .git/refs -type f | wc -l
2
```

(Bu yerda `git branch chegirma` ham bor: `./qur.sh` dan keyin toza holatda tekshirish uchun.)

</details>

🟢 `git add` + `git commit`, keyin `git cat-file -p HEAD`: `parent` — revert commit'i `14b041d6…`, `tree` — yangi
(`sut.txt` qoʻshildi).

🟡 `sed -i.bak 's/3000/2700/' main.go`, `git commit -am "…"`, `go run main.go` → `non: 2700 so'm`.

🟠 `Deleted branch eski (was e657f41).` Faqat ref fayli oʻchdi. Commit joyida va yetib boriladi:
`git merge-base --is-ancestor e657f41 main` muvaffaqiyatli, chunki u `main` ning ajdodi. (`git cat-file -t` yetarli
dalil emas: hech bir ref yetib bormaydigan commit ham `gc` uni tozalaguncha `commit` deydi.) `-d` faqat merge qilingan
branch'ni oʻchiradi, merge qilinmaganini `-D` oʻchiradi. Unda commit'ni odatda `git reflog` orqali topasiz, lekin
qoʻlda yozilgan `eski` ning reflog'i yoʻq: faqat `git fsck --lost-found` yordam beradi.

🔴 Commit hash'i boshqa (`914b512…` → `cdd8662…`), chunki xabar (va bizda committer vaqti) commit mazmunida.
`tree` (`4cf5d8f7…`) va `parent` (`5f4efe00…`) oʻzgarmaydi: fayllar ham, oldingi tarix ham bir xil. Eski commit
oʻchmaydi, `git reflog` da turadi. Push qilingan commit'ni amend qilmang: bu tarixni qayta yozish, hamkasblarga
muammo ([GIT-2.01](/lab/youtube/git#git-2-01), [GIT-3.01](/lab/youtube/git#git-3-01)).
